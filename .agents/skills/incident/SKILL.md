# 障害対応スキル(incident)

本番・運用の異常に対し、**課題体系との照合を原因究明の前に出す**ことを工程で強制するスキル(Phase 22-3 で新設)。動機は 2026-09-04〜05 の logic-training-1 投稿停止(約 13 時間): 恒久対策込みの課題が 2026-07-22 の時点で書かれていたのに、障害調査中に照合されず 2 回目の発生を許した。
**ルールの正は `docs/issues/index.html` セクション 4**(特に 4.6 エスカレーション・4.7 事象記録との切り分け・4.9 クローズと再発)。運用手順の正は `docs/app/operation.html` セクション 4(失敗時ポリシー)。矛盾したらそちらが勝つ。起動する場面・しない場面の一覧の出典は `docs/ideas/issue-tracking-system.md`(転記下書き末尾)。

**レーン**: 記録と起票は課題レーン(常に並行可・宣言不要。本スキルの起動が宣言を兼ねる)。**コードでの修正は本スキルの中では行わない** — 課題を起票して `/step`(開発レーン)で行う。緊急のホットフィックスが要る判断になったら、その場で開発レーンを宣言して `/step` 相当で進める(本スキルはその判断まで。他に開発レーンのセッションが動いていないかを確認する)。

## 0. 起動する場面・しない場面

**起動する**(本番・運用で異常が起きたと人間が認識した瞬間):
1. 失敗通知が届いたとき(SFN 失敗アラーム・ECS 異常終了通知・CloudWatch アラーム。通知文を貼って起動)
2. 通知はないが異常に気づいたとき(投稿が出ていない・内容がおかしい・インサイトが欠けている・コメント返信が返っていない)
3. 別の作業中に本番の異常を見つけたとき(週次補充で在庫の状態が想定と違う、月次 KPI 転記でデータが欠けている等)。いったん本スキルに切り替えて切り分け、終わったら元の作業へ戻る

**起動しない**:
- 開発中のローカル失敗(pytest・cdk synth・ビルド失敗は通常の開発ループ)
- 設計レビューの指摘・気づいた改善点(`/issue` の起票)
- 確認待ちリストの NG(計画書の「NG 時の扱い」列に従い `/issue` で起票)

## 1. 工程(順番を入れ替えない)

### (1) 症状の聞き取り

何が・いつから・どのセット(アカウント)か・通知文があればその全文、を聞く。**追加質問は最大 3 つ**(原因の推測はまだしない)。ここで次の 3 つの検索キーを作る: **症状語**(例: 投稿停止・exit 1・container ERROR・0 件処理・トークン失効)・**セット名**(logic-training-1 / pref-ranking-1 / umigame-soup-1)・**パス**(症状から疑われる `services/<name>/` `infra/lib/<stack>` 等)。

### (2) 照合 — 原因究明の前に提示する(必須。該当なしでも宣言する)

次の 3 系統を検索キーで引き、**結果を定型で会話に貼ってから (3) に進む**:

| 対象 | 場所 | 引き方 |
|---|---|---|
| 課題体系(live + クローズ) | `docs/issues/index.html` | `grep -n -i "<症状語\|セット名\|パス>" docs/issues/index.html`。当たった行は ID・ステータス・トリガー・発生履歴を読む。クローズ節の 解消 / 受容 行も対象(再発の検知) |
| 確認待ちリスト | 開発計画 `docs/plans/development-plan.html#pending-checks` と当該セット計画書 `docs/plans/<set_code>.html` の確認待ちリスト | トリガー列・確認内容列を同じキーで grep。観察待ちの項目がこの異常で NG になっていないか |
| 事象記録 | 横断・基盤 = `docs/plans/development-log.html#incidents` / セット固有 = `docs/plans/<set_code>-log.html` の「トラブル対応の記録」 | 同じキーで grep。「前にも起きた事象」の日付と復旧手順を拾う |

**提示の定型**(すべて埋める。該当なしは「該当なし」と書く):

```
照合結果(原因究明の前に提示)
- 予言されていた課題: I-0xx「<課題>」— ステータス <…> / トリガー <…> / 発生履歴 <…>(→ 4.6 により今回は n 回目)
- 前にも起きた事象: <日付>(<記録リンク>)— 復旧手順 <要約>
- 確認待ちの該当: <対象>(<計画書>)— NG 時の扱い <…>
- 該当なし: <系統名>
```

該当があれば「前回の復旧手順がそのまま使えるか」「恒久対策が課題として既に書かれているか」を先に言う。**照合を飛ばして原因究明に入らない**(初回試行は開発計画の確認待ちリストの対象で、この順序が判定基準)。

### (3) 切り分けと復旧(本番操作は人間ゲート)

- **Claude が行う**(読み取りのみ): SFN 実行履歴・ECS タスクの終了理由・CloudWatch Logs の読み取り(`aws stepfunctions list-executions` / `describe-execution` / `aws logs filter-log-events` 等)、DB の状態確認(`generation_runs` `posts` `batch_execution_logs` `*_stock_items` の SELECT)。手順の正は `docs/app/operation.html` セクション 4。長いログはファイルに落として Codex に `sandbox: read-only` で一次解析させ、要約だけ受け取る
- **ユーザーが行う = 人間ゲート**(本スキルの denylist): DB の手動補正(UPDATE / DELETE)・Scheduler の停止 / 有効化・SFN の手動実行・`cdk deploy`・Secrets の更新・SNS 側の操作。Claude は operation.html の該当手順と実行する SQL / コマンドを提示し、実行結果を貼ってもらう
- 復旧の判断は**恒久対策込み**で行う: (2) で予言されていた課題があれば「今回の応急処置」と「その課題の展開(恒久対策)」を分けて提示する。応急処置だけで閉じない
- コード修正が要ると判明したら、ここで止めて (4)(5) を先に済ませ、課題を起票して `/step` へ(ホットフィックスの緊急度はユーザー判断)

### (4) 事象記録を書く(障害 1 件につき必ず 1 件)

- **セット固有** → `docs/plans/<set_code>-log.html` の「トラブル対応の記録」表(列: 日付 / 問題 / 解決策)。既存行の書き方(2026-09-04 の logic-training-1 の行等)に揃える
- **横断・基盤**(複数セットに及ぶ・インフラ・DB・CI/CD 起因) → `docs/plans/development-log.html#incidents` の「事象記録」表(列: 日付 / Phase-Step / 事象 / 復旧・解決策 / 課題)。「課題」列には (5) で起票・更新した ID を `#I-0xx` リンクで書く
- 書くこと: 症状(いつから・何が)・原因(切り分けの結果)・復旧手順(誰が何をしたか)・影響(停止時間・欠番)。**「これから変えるべきこと」は書かない**(それは課題体系へ)
- 記録ファイルの「最終更新」を更新する

### (5) 課題の更新(4.6 / 4.7 / 4.9)

(2) の照合結果に応じて、`docs/issues/index.html` を次のとおり更新する(起票の書式は `/issue` の起票モードと同じ 9 列):

- **既存課題の再発**(live に該当行あり): 発生履歴列に「日付(記録リンク)」を追加し、**エスカレーション判定**を明示する — 1 回目 = 記録 + 再判断(据え置き継続を選んでよいが、トリガーを「次に発生したとき(現在 1 回。2 回目で据え置き不可)」に更新)/ **2 回目 = 据え置き不可**。既定は展開(ステップ・フェーズの起票。下書きは 4 項目様式 + 5.1 チェックリスト。転記は展開先のレーン)、受容へ倒すのはユーザーの明示判断があるときのみ(理由付き)。既定より緩めるならトリガー列に理由を書く
- **クローズ済み課題の再発**(解消 / 受容の行に該当): 行を live の該当レーン節へ戻す(ID・発生履歴を継続)。解消済みの再発は「対策が効いていない」ので 起票 ステータスに戻して対応方針を再検討、受容の再発は受容の根拠が崩れたとしてエスカレーション規則を適用
- **新しい恒久対策が要る**(該当なし・または既存課題では防げない): 新規起票。ステータスは対応方針が決まれば 据え置き(発生実績型トリガー「次に発生したとき(現在 1 回。2 回目で据え置き不可)」を既定)、未決なら 起票
- **その場で直した対策**(DB 補正のやり方・手順の追記・設定変更など、この障害の中で完了した変更): 課題として起票し**即 解消 に落とす**(クローズ節へ直接。結果列に「解消: <何を変えたか>(コミット / 記録リンク)」)。「何が変わったか」の知識をクローズ節に集める
- **確認待ちの NG**: 該当行の「NG 時の扱い」列に従う(結果列に日付 + NG + 記録リンクを書き、追補ステップか課題として起こす)
- index.html の「最終更新」を更新し、`<tr id=` の ID 重複なし・`<td>` 9 個(クローズ節は 8 個)を grep で確認する

### (6) コミット・push

日本語メッセージ・`pull --rebase`・**ファイル指定 add**(並行セッションの変更を巻き込まない)。触るのは `docs/issues/index.html`・記録ファイル・計画書の確認待ちリスト(結果列)のみ。`services/` `shared/` `infra/` `database/` は触らない。

## 2. 終了チェックリスト(全部 ✅ になるまで終えない)

1. 照合結果の定型を (3) の前に貼った
2. 復旧した(または人間ゲート待ちで停止した理由と、ユーザーが実行する手順を提示した)
3. 事象記録 1 件を記録ファイルに書いた(セット固有 or 横断)
4. 課題体系を更新した: 再発なら発生履歴 +1 とエスカレーション判定の明示 / 新規なら起票 / その場の対策は起票して即 解消 / 該当なしなら「課題体系: 更新なし(理由)」と宣言
5. 確認待ちリストの該当行があれば結果列を書いた
6. コミット + push 済み。コード修正が要るなら起票した課題の ID と、次に打つ `/step` を提示した
7. 別作業の途中で起動した場合は元の作業に戻る旨を宣言した

## 3. 2026-09-04 に当てはめると(工程の検算)

「9/4 21:00 の画像生成 SFN 失敗 → 9/5 の投稿も失敗・投稿停止」で起動 → (2) で課題 2026-07-22 起票「空の generation_run が投稿バッチを恒久的に詰まらせる」(現 I-014)と事象 2026-08-06(LT 記録)が即座に出る → 「1 回目の発生実績あり・今回 2 回目 = 据え置き不可」を原因究明の前に提示 → (3) 応急処置(空 run の取り消し・在庫の文字数修正)と恒久対策(選定条件に generated_media 存在を追加 + 文字数上限の投入時同期)の 2 本立てで判断 → (4) LT 記録に事象 1 行 → (5) I-014 の発生履歴 +1・展開の下書き、文字数上限の同期は新規起票 → (6) push。

## 落とし穴

- **照合を後回しにしない**。ログを見始めると原因究明に吸われる。定型を貼るまで `aws` コマンドを打たない
- 課題の行に復旧の経緯を書かない(4.7。行が肥大する。経緯は記録ファイル)
- 「発生頻度を見て判断」のような回数なしトリガーで据え置かない(4.4 禁止事項。回数を書く)
- 復旧して安心して事象記録と課題更新を飛ばさない(初回試行の判定基準 ②「終了時に事象記録 + 課題の更新が漏れなく行われるか」)
- 本スキル内で `services/` 等のコードを直さない。直したくなったら課題を起票して `/step`(開発レーン・1 セッション制約)へ
