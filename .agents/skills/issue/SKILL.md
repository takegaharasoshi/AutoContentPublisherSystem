# 課題スキル(issue)

開発・運用で見つかった課題(= 何もしないと損なわれるもの)を `docs/issues/` で起票・醸成・追跡するスキル。スキル idea(Claude Code は `/idea`、Codex は `$idea`)と同型で、正の置き方だけが逆(アイデアは MD が正、課題は **index.html の表が唯一の正**)。
**ルールの正は `docs/issues/index.html` セクション 4**(4.1 単位 / 4.2 列 / 4.3 ステータス 4 つ / 4.4 トリガー 5 型 / 4.5 2 層構造と終了規律 / 4.6 エスカレーション / 4.7 事象との切り分け / 4.8 レーン・照合・棚卸し / 4.9 クローズ)。本スキルは手順と迷いやすい分岐だけを持ち、矛盾したら index.html が勝つ。Claude Code(`/issue`)と Codex 直接セッション(`$issue`)の両方から同じ手順で使う(エージェント別の差分は末尾の節)。

**レーン**: `docs/issues/` 配下 + 本スキルで閉じる限り課題レーン(常に並行可・宣言不要)。本スキルの起動は課題レーン宣言を兼ねる。**展開(ステップ起票)だけは展開先の計画書のレーン**(開発計画なら開発レーン、セット計画書ならそのセットレーン)で行う。本スキルは展開の下書きまで用意し、転記は当該レーンのセッションで行う(自セッションがそのレーンなら続けて転記してよい)。

**ファイル**: 正は `docs/issues/index.html` の表(live = レーン別 4 節 `#lane-dev` `#lane-logic-training-1` `#lane-pref-ranking-1` `#lane-umigame-soup-1` / クローズ = `#closed`)。**起票時にファイルは作らない**。壁打ちを始める時点で `docs/issues/<slug>.md` を `_template.md` から作る。ステータス・トリガー・発生履歴は表にだけ書き MD に写さない。**どのモードも、終わったら必ず index.html の表を更新する**(表の同期は本スキルの責務)。

**使い分け**: 本番・運用の異常が起きている最中は本スキルではなくスキル incident(Claude Code 専用の `/incident`。照合 → 復旧 → 事象記録 → 課題更新)。障害から出た恒久対策の起票は incident の工程 (5) が本スキルの起票手順を呼ぶ。「やれば増える価値がある」ものは課題ではなくアイデア(スキル idea を起動。Claude Code は `/idea`、Codex は `$idea`)。

## モード判定

- 「課題がある / 〜が問題 / これは直すべき / 起票して」 → **起票**
- 「〜の課題を壁打ちしたい / 対応方針を決めたい / I-0xx を詰めたい」 → **壁打ち**(対象未指定なら live の 起票 ステータス行と、トリガーが引かれた据え置き行から候補を提示)
- 「棚卸し / トリガーの確認 / 課題の見直し」 → **棚卸し**

## 1. 起票モード(目標 1〜2 分)

1. **リトマス**(4.1): 「放置したとき何が損なわれるか」を 1 文で言えるか。言えなければアイデア(スキル idea の捕捉へ誘導。Claude Code は `/idea`、Codex は `$idea`)。事象(起きたこと・復旧の経緯)は書かない(記録ファイルの領分。4.7)
2. **重複・再発の照合**: `grep -n -i "<対象パス|セット名|キーワード>" docs/issues/index.html` で live + クローズを引く。同じ課題が live にあれば新規行を作らず、その行の対応方針・トリガーを更新する。クローズ節の 受容 行に当たり、新しい事実で再検討が要るなら live へ戻す(ID・発生履歴は継続)
3. **ID の採番**: `grep -o 'id="I-[0-9]*"' docs/issues/index.html | sort | tail -1` の次番(レーン横断で一意・クローズ後も再利用しない。行の `<tr id="I-0xx">` と ID 列を同値にする)
4. **行を書く**(4.2 の 9 列。live の該当レーン節の表末尾に追加):
   - 対象パス: リポジトリルートからのパス(複数可・ディレクトリ単位でよい)。**`/step` が触るパスで grep する列**なので設計書・スキルも漏らさず書く。セット固有ならセット名も書く(補充スキルがセット名で照合)
   - 課題: 何が損なわれる(うる)か 1〜3 文 / 対応方針: どう変えるか 1〜3 文(未決なら「未決」)
   - ステータス: 対応方針が未決なら **起票**、決まっていて今やらないなら **据え置き**(トリガー必須)。起票時点で展開が決まっているなら 展開済み(リンク)
   - トリガー: 4.4 の 5 型(パス型 / セット型 / 日付型 / 発生実績型 / 節目型)のどれかに当てはめる。**「未定」「将来」「頻度を見て」は禁止**。発生実績型は回数を必ず書く(「現在 n 回。2 回目で据え置き不可」)。日付型の相対表現は絶対日付を併記。具体トリガーが書けないなら 受容(理由付きでクローズ節)
   - 発生履歴: 発生実績型なら日付 + 事象記録リンクの羅列、なければ「—」 / 壁打ち: 「—」
5. **表の HTML を機械確認**: `<tr id=` の ID が重複していないこと、`<td>` が 9 個であることを grep で確認する
6. **復唱**: 課題・対応方針・トリガーを一言で復唱して認識ズレを確認(ズレたら行だけ直す)
7. index.html の「最終更新」を更新し、**git コミット + push**(日本語メッセージ・`pull --rebase`・ファイル指定 add)

壁打ち中・`/step` の途中・補充作業中の割り込み起票も同じ手順(復唱は一言で済ませ、すぐ本筋に戻る)。セットレーンのセッションが開発レーン向けの課題を見つけた場合も、課題レーンは並行可なのでその場で起票してよい(起票文面の提示止まりにしない)。

## 2. 壁打ちモード

**開始**:
1. 対象行(1 行または同系統の複数行。例: 可視化 3 件 I-006・I-017・I-025)を index.html から読み、対象パスに挙がる設計書・コードの該当箇所で文脈を復元する
2. `docs/issues/<slug>.md` が無ければ `_template.md` から作る(フロントマター issue_id / lane・要旨・選択肢と判断・原文メモ・壁打ち記録)。**複数行をまとめて壁打ちするときは 1 ファイルにし、各行の壁打ち列から同じファイルへリンクする**。行の壁打ち列に `<a href="<slug>.md">壁打ち</a>` を付ける(初回試行は開発計画の確認待ちリストの対象。着手時に該当行を照合する)
3. 既にファイルがあれば要旨・選択肢・原文メモ・壁打ち記録を読む

**観点リスト**(全部やる必要はない。足りない観点をエージェントが選んで振る):
① 損なわれるものの具体化(発生したら誰が・いつ・どれだけ困るか。まだ起きていないなら確率と影響) ② 対応方針の選択肢(最小の対策 / 恒久対策 / 何もしない。それぞれのコスト) ③ 今やらない理由の妥当性(据え置きなら「引かれる瞬間を検知できるトリガー」が書けるか) ④ 発生実績とエスカレーション(発生履歴列・4.6 の回数規則。2 回発生済みなら着地は 展開 か 受容〔ユーザーの明示判断〕のみ) ⑤ 同系統課題との統合(同じ対象パス・同じ「〜がない」系は 1 ステップに束ねるか) ⑥ 展開先のレーンと粒度(開発計画のフェーズ / セット計画書の改修 / 既存フェーズへの同梱) ⑦ 受容の可否(直さなくても損なわれないと言い切れる根拠)

**壁打ち中に何か出てきたら 3 パターン判定**(エージェントが判定を提案する):
- 対象課題の対応方針の一部 → MD の選択肢に書く(独立させない)
- 別の課題(放置すると別のものが損なわれる) → **その場で起票(セクション 1)して相互リンク。壁打ちはしない**
- 価値を足すアイデア → スキル idea の捕捉へ(Claude Code は `/idea`、Codex は `$idea`。課題体系には書かない)

脱線の方が重要になったら、元の課題を終了規律で明示的に着地させてから乗り換える(暗黙の混線禁止)。

**終了規律(必須チェックリスト。4.5)**:
1. **着地**: 次の 3 つのどれか。「なんとなく放置」は許さない
   - **据え置き**: 対応方針を確定し、トリガーを 4.4 の書式で更新(引かれる瞬間を入口が検知できる形に)
   - **展開**: ステップ・フェーズとして計画書に起票する。下書きは `docs/plans/index.html` セクション 5 の **4 項目様式(内容 / 完了条件 / 人間ゲート / 停止点・上限)** で書き、書く前に **5.1 起票チェックリスト**(自セッション外の出来事は完了条件に入れず確認待ち 5.2 へ・人間ゲートは push 直後に行えるものか・ユーザー判断はゴール対象外・20〜30 ターン超や 2 レーンまたぎは割る・**触るパスで課題表を照合し、同じ対象パスの据え置き課題を同梱するか決める**)を通す。転記は展開先のレーンで行い(自セッションがそのレーンなら続けて行う)、転記後にステータスを 展開済み・対応方針列にステップへのリンク
   - **受容**: 直さない・再判断もしないと決めた理由を書いてクローズ節(`#closed`)へ移す(列: ID / 起票日 / レーン / 対象パス / 課題 / 結果〔**受容**: 理由〕/ クローズ日 / 発生履歴)。再検討の余地があるなら受容ではなく据え置き(トリガー付き)
2. 壁打ち記録に蒸留を追記(論点・判断・積み残し・着地。会話ログは貼らない)
3. 要旨(対応方針の現在形)を丸ごと書き直す。選択肢と判断を最新化
4. 構成図・比較表が要るときだけ詳細 HTML `<slug>.html` へ昇格し、MD の要旨をリンク 1 行に置き換える
5. **index.html の表を同期**(ステータス・対応方針・トリガー・壁打ちリンク。受容はクローズ節へ移動。最終更新も更新)。表と MD が乖離したら表が正
6. git コミット + push(日本語メッセージ・`pull --rebase`・ファイル指定 add)

**着地の使い分けで迷ったら**: 「トリガーが引かれたとき何をするか」で決める。再判断する = 据え置き(まだ決めていない・条件次第)、実行するだけ = 展開(決めた)、何もしない = 受容(決めた・理由付き)。「○○したら考えよう」は原則据え置きだが、○○を入口が検知できる書式(4.4)で書けないなら受容へ倒す。

## 3. 棚卸しモード

節目は月次 KPI 転記(運用設計 6.3)・フェーズ完了・改修完了(新しい儀式は作らない。確認待ちリストの棚卸しと同時に行う)。

1. live の 4 節をトリガー列を上から確認し、**日付型・節目型**で条件が満たされた行を拾う(パス型・セット型・発生実績型は `/step`・補充スキル・`/incident` の入口が引くので、ここでは「入口が引きそびれていないか」だけ見る)
2. 満たされた行: その場で 据え置き継続(トリガー更新)/ 展開(下書きを用意して当該レーンへ)/ 受容 を決める。決められないなら壁打ち(セクション 2)を提案
3. **起票 のまま残っている行**(対応方針未決)は目安「次の棚卸しまで」を過ぎているので、ここで対応方針を決めるか壁打ちに回す(墓場化防止)
4. 開発計画・セット計画書の確認待ちリスト(トリガー列)も同じ作法で見て、NG の行があれば「NG 時の扱い」列に従い課題として起票する
5. クローズ節が 50 行を超えていたら `closed.html` へ分ける(4.9。本ページにリンクを残す)
6. index.html(と計画書の確認待ちリスト)を更新してコミット + push

## 落とし穴

- **行に復旧の経緯を書かない**(4.7。行が肥大する。「何が起きたか」は記録ファイル、「何を変えるか」が課題)。障害対応の最中に本スキルを起動していたら スキル incident に切り替える(Claude Code の `/incident`。Codex 直接セッションでは作業を止めてユーザーに報告する)
- 据え置きでトリガーが空・「未定」のままにしない(構造的に眠りっぱなしになる。書けないなら受容)
- 表と MD に同じ情報を二重に書かない。ステータス・トリガー・発生履歴は表にだけ。整理された現在形の置き場は 1 箇所(浅いうちは MD 要旨、昇格後は詳細 HTML)
- ID を振り直さない・再利用しない(計画書・記録から `#I-0xx` でリンクされる)
- 展開の転記を課題レーンのまま行わない(展開先の計画書のレーンで。開発レーンは常に 1 セッションの制約が働く)
- 壁打ちの成果物は「対応方針の検討記録」であり設計書ではない。展開後の設計 Fix は `docs/app` `docs/infra` で行う

## エージェント別の差分(Phase 23-2 で追加)

本スキルは Claude Code と Codex 直接セッションで共用する(実体は `.agents/skills/issue/SKILL.md`、`.claude/skills/issue` はシンボリックリンク)。手順・終了規律は共通で、違うのは次の点だけ。

- **起動**: Claude Code は `/issue`、Codex は `$issue`。`/step` `/incident` は Claude Code 専用のため、Codex では **展開の転記(計画書への起票)を行わず下書きの用意で止める**(展開先が開発計画なら開発レーンで、セット計画書ならそのセットレーンのセッションで転記する)。障害の疑いがあるときは Codex では作業を止めてユーザーに報告し、`/incident` は Claude Code で起動してもらう
- **`/goal` 行**: 本スキルは起動時のゴール行を持たない(起票 1〜2 分・棚卸しは表の走査のため)。壁打ちを長く回すときにユーザーがゴールを立てる場合、Claude Code は末尾に `or stop after N turns` を付け、Codex はその句を外して打つ(Codex では無視される)。Codex 側の停止手段は `/goal pause` / `/goal clear`。Codex にはターン上限がないため、ゴール行に「3 ターン進捗がなければ blocked を申告して止まる」を明記する
- **完了申告前の再確認(Codex)**: Codex の `/goal` は自己申告で完了になるため、終了規律の最後(コミット + push)の前に実コマンドで状態を確かめてから申告する — `git status --short`(触ったのが `docs/issues/` だけか)・起票なら `grep -c '<tr id="I-' docs/issues/index.html` と `grep -o 'id="I-[0-9]*"' docs/issues/index.html | sort | uniq -d`(ID 重複なし)・`git log origin/main..HEAD --oneline`(push 済みなら空)。出力を会話に貼る
- **リサーチ**: 壁打ちで外部情報が要るとき、Claude Code は WebSearch / WebFetch、Codex は組み込みの web_search(デスクトップアプリでは既定で有効。CLI なら `codex --search`)か curl で自分で行う(MCP 経由の委譲はしない)
- **触ってよいパス(Codex)**: `docs/issues/` のみ。棚卸し手順 4 の「計画書の確認待ちリスト」は、開発計画(`development-plan.html`)が禁止パスのため Codex は**読むだけ**にし、NG の行があれば課題として起票するにとどめる(結果列の記入は Claude Code のセッションで行う)。セット計画書の確認待ちリストは許可パスなので更新してよい
