## 1. 手順(1 候補ずつ回す)

工程は **対象選択 → 原案確認 → 人間による理由の言語化 → AI の修正 → 再判定 → 分類(個別修正 / 共通ルール / 仮説)→ 合意したスキル差分の反映 → 記録**。3・5・7 は人間の作業で、**自動で成立させた扱いにしない**。

1. **対象選択(人間)**: 各バッチの `INDEX.md`(`tally.py --write-index` の生成物)から `ng` / `hold` / `final_ng` を集めて一覧提示し、ユーザーが振り返る候補を選ぶ。件数の目安は 1 セッション 3〜10 件。選ばれなかった候補はそのまま残す(消さない・期限を付けない)。`withdrawn`(重複・出典 NG)と `approved`(承認済み)は対象外
2. **原案確認**: 候補ファイルの**最新版の問題文・答え・図の内容・出典メモと、これまでの判定履歴**をそのまま提示する(要約や言い換えをしない。`final_ng` は完成稿での判定も併せて出す)
3. **理由の言語化(人間)**: 「どこが引っかかったか」を聞く。**答えは一言でも・空欄でもよい**。空欄のときは AI が推測で埋めず、次の 4 で**仮説として明示**する。ユーザーの発言は記録に**原文のまま**残す(音声入力の誤変換は文脈で読み替えてよいが、内容を足さない)
4. **AI の修正**: 理由(または仮説)に基づく修正版を **1 案** 書き、候補ファイルへ「版 N+1(修正版・日付)」として**追記**する(版 1 の原案・判定は書き換えない。別ファイルへ切り出すときは `supersedes` を使う)。修正版は候補の範囲(問題文・答え・図の内容・出典メモ)にとどめ、つかみ・ヒント・情景は書かない。仮説に基づく修正は、修正版の冒頭に「(AI 仮説: …に基づく修正)」と書いて区別する
5. **再判定(人間)**: 修正版に **OK / NG / 保留** を返してもらう(理由は再び任意)。結果は追記した版の `### 判定` に「段階: 振り返り」で記録し、フロントマターの `state` を更新する(下の「候補へ戻す条件」)。**同じ候補で修正を 2 回繰り返しても決まらなければ保留にして次へ**進む(1 候補に時間をかけない)
6. **分類**: 言語化された理由を次の 3 つに分ける。**分類の主語はユーザーの理由**であり、AI の推測で共通ルールを作らない
   - **個別修正**: その候補にしか当てはまらない(この問題の答えが 2 通りある、この語呂が伝わらない等)。修正版で完結し、スキルは変えない
   - **共通ルール**: ユーザーが「他の問題でも避けたい / 揃えたい」と**方針として明示**したもの。7 の合意を経てスキルへ差分反映する
   - **仮説**: 理由が空欄・曖昧で、AI が推測した傾向。**スキルには反映せず記録に残すだけ**。同じ仮説が別の候補でもユーザーの言葉で裏付けられたら、そのとき共通ルールの候補として提示する
7. **合意したスキル差分の反映(人間の合意が前提)**: 共通ルールに分類したものだけ、① 既存の承認例(直近バッチの `stock_items.py` の承認済み問題・補充スキルの参照例)との**衝突を確認**し(新ルールで承認済みの問題が NG になるなら、その旨を提示してユーザーに再考を求める)、② 補充スキルの該当節への**差分案を会話に貼り**、③ ユーザーが「反映してよい」と言ってから書き換える。**合意前にスキルを変えない**。差分は「基準 1 行 + 根拠になった候補 ID + 記録へのリンク」を最小単位にし、参照例を足すときは投稿対象外の検証例ではなく実候補の修正版を使う(例に `example: true` のダミーを載せない)
8. **記録**: `content/quiz-stock/logic-training-1/candidates/reviews/<YYYY-MM-DD>.md`(同日 2 回目は `-2`)に、対象ごとの「候補 ID・版・元の判定 → 再判定・ユーザーの理由(原文)・分類・修正の要点・更新したスキル箇所(またはなし)」と、セッション末尾に「仮説の一覧(未確認のまま)」「反映した差分のコミット」を書く(書式はセクション 2)。`tally.py <batch dir> --write-index` を回して形式チェックの出力を貼る。**初回の振り返りが終わったら**セット計画書の確認待ちリスト「振り返りスキルの初回利用」の結果列を埋める(週次補充と振り返りの負担は分けて書く)

### 候補へ戻す条件(R-3-1 の形式に合わせる)

| 振り返り前 | 再判定 | フロントマター `state` | 意味 |
|---|---|---|---|
| `ng` / `hold` / `final_ng` | OK | `ok` | **候補 OK に戻る**。次回の週次補充の G1b で目標数に入れば完成稿へ進む。**振り返りの OK は投入の承認ではない**(`stock_items.py` への転記・投入は本スキルで行わない) |
| `ng` / `hold` / `final_ng` | NG | `ng` | 修正版でも NG。理由があれば分類し、なければ仮説のまま残す |
| `ng` / `hold` / `final_ng` | 保留 | `hold` | 決めきれない。次回の選別か振り返りで再判定 |
| `ng` / `hold` / `final_ng` | (未判定で終了) | `unreviewed` | 修正版を追記したが再判定に至らなかった。次回の週次補充の選別に混ぜてよい |
| 修正しない(理由の記録だけ) | — | 変えない | 版も追記しない。記録にだけ残す |

- `final_ng` から OK に戻るとき、`stock_no` は空にする(完成稿だった番号は `stock_items.py` から外れているため。再び完成稿にするときに G1b が新しい `no` を振る)。`batch` は変えない(どの回で作ったかの記録)
- `tally.py` は「本文の最後の `- 判定:`」と `state` の整合を検査するので、追記した版の判定欄が最後になるようにする(空欄 = `unreviewed`)
- `approved` の候補・投入済みの問題は本スキルで触らない(承認済み内容の保護)。`withdrawn` は終端で戻さない

## 2. 記録の書式(`candidates/reviews/<YYYY-MM-DD>.md`)

```markdown
# 候補の振り返り 2026-MM-DD(quiz-review-learn)

- 対象: <バッチ名>(ng 2・hold 1・final_ng 1 から 4 件を選択)。選ばれなかった候補: そのまま残置
- 反映した差分: なし / quiz-stock-replenish セクション 3 夜(コミット <sha>)
- 所要と負担(任意): 振り返り n 分。補充とは分けて記録する

## 個別修正
| 候補 | 版 | 元の判定 → 再判定 | ユーザーの理由(原文) | 修正の要点 | 更新したスキル箇所 |
|---|---|---|---|---|---|
| [m02](../<batch>/m02.md) | 1 → 2 | NG → OK | 「答えが 2 通りあるから」 | 条件を 1 つ足して答えを一意にした | なし(個別) |

## 共通ルール(合意済み)
| 候補 | 版 | 元の判定 → 再判定 | ユーザーの方針(原文) | 衝突確認 | 反映した差分 |
|---|---|---|---|---|---|
| [n01](../<batch>/n01.md) | 1 → 2 | 保留 → OK | 「…は全部避けたい」 | 承認済み A01〜A44 に該当なし | SKILL.md セクション 3 夜に基準 1 行(コミット <sha>) |

## 仮説(未確認・スキルには反映しない)
| 候補 | 版 | 元の判定 → 再判定 | ユーザーの理由 | AI の仮説 | 次に確かめること |
|---|---|---|---|---|---|
| [m01](../<batch>/m01.md) | 1 | NG → (未修正) | (空欄) | 答えの語が日常語でなく想起しにくい? | 同じ仮説が別候補でユーザーの言葉で出たら共通ルール候補へ |
```

- 3 表とも「候補 ID → ファイル」「版」「元の判定 → 再判定」「ユーザーの理由(原文)」「更新したスキル箇所」を必ず持ち、候補ファイル側の判定欄には「理由(任意): 振り返り <日付> 参照」と書く。これで **原案(候補ファイルの版 1)・判定(各版の判定欄)・修正版(版 N+1)・根拠(記録のユーザーの理由)・更新するスキル箇所(記録の差分列 + コミット)** を相互に追える
- 「反映しない」結論も記録する(理由が残れば成立。空の節は「該当なし」と書く)

## 3. 守ること(denylist・禁止事項)

- **既存の承認例との衝突確認なしに共通ルールを足さない**(手順 7 ①)。承認済みの問題が NG になる一般化は差分を再検討する
- **合意前のルール変更禁止**: ユーザーが差分案に「反映してよい」と言うまで補充スキルを書き換えない。仮説からスキルを変えない
- **理由不明の補完禁止**: ユーザーが理由を書かなかった候補に理由を作らない。AI の推測は必ず「仮説」と書いて分ける(候補ファイルの `理由(任意)` 欄にも AI の推測を書かない)
- **全件消化や期限を必須にしない**: 残った NG / 保留は残ってよい。振り返りの回数・間隔は決めない
- **原案・判定を上書きしない**(版の追記のみ)。`approved` / 投入済みは触らない
- **投入しない**: 振り返りの OK は候補 OK。`stock_items.py` への転記・`insert_quiz_stock.sql`・Aurora / ローカル DB・S3・イラスト生成・動画ビルド・SNS 投稿設定はすべて対象外(週次補充の G1b 以降の仕事)
- 反映先は補充スキルの作問基準・参照例のみ。`validate.py` の上限値・設計書・`AGENTS.md`・共通設計書に触る必要が出たら該当パスと実施条件を提示して止まる
