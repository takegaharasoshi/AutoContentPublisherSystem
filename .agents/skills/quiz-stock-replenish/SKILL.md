# 問題ストック補充スキル(quiz-stock-replenish)

logic-training-1 セットの問題ストック(`quiz_stock_items`)を、16-2 初期整備(2026-08)で確立した品質・手順で補充するためのスキル。
運用ルールの正は `docs/app/operation.html` セクション 3(在庫確認クエリ・補充閾値 = 未使用 7 問/組以上・著作権ガイドライン)、フィールド仕様の正は `docs/app/generators/gpt-quiz-multicut.html` セクション 5。本スキルはそれらに「同品質で量産するための勘所」を足すもので、矛盾したら設計書が勝つ。Claude Code(`/quiz-stock-replenish`)と Codex 直接セッション(`$quiz-stock-replenish`)の両方から同じ手順で使う(リサーチ・イラスト生成の手段と `/goal` 行の扱いはエージェント別に異なる。末尾の「エージェント別の差分」節)。

**昼スロット(noon = L3 / standard・フェルミ推定)は 16-4d(2026-08-24)で当分停止中**(スキップ率の高止まりによるユーザー決定。経緯・凍結範囲は `docs/app/sets/logic-training-1.html` 冒頭の注記が正)。**補充対象は朝(L1 / light)と夜(L1 / deep)の 2 組のみ**で、L3 / standard は在庫確認で数字が小さくても補充しない(既存在庫は凍結・残置)。セクション 3 の昼の執筆勘所は再開時の参照用として残している。

**資材の置き場**: `content/quiz-stock/<set_code>/<バッチ名>/`(git 管理)。バッチごとに自己完結の資材一式 — 単一ソース `stock_items.py`・検証 `validate.py` / `verify_logic.py`・生成 `generate.py`・リサーチ `research*.md`(source_note が参照する出典台帳)・投入した `insert_quiz_stock.sql` — を置く。参照実装は初期整備の `content/quiz-stock/logic-training-1/2026-08-initial/`。補充時は最新バッチの一式を新しいバッチディレクトリ(`2026-08-w3` 等)へコピーして同じ流れを回し、**投入完了時にディレクトリごとコミットする**(`review.md` は generate.py の派生物のため gitignore 済み・コミットしない)。plans/ は使い捨てスクラッチ用で、ストック資材は置かない。

## 0. 在庫確認(入口)

operation.html セクション 3 の在庫確認クエリ(16-3b 拡張版)で「型 × 難度」ごとの在庫を確認し、7 問を下回る組を補充対象にする。**ただし L3 / standard(昼)は 16-4d で停止中のため、数字にかかわらず補充対象にしない。**quiz-prebuilt 方式では**「未使用かつビルド済み」(`unused_built`)を在庫と数える**。`unbuilt` 列が 0 以外なら投入済みのビルド漏れなので、補充より先にセクション 7 のビルドを終わらせる。再利用 WARNING・未ビルト WARNING がログに出ていたら優先対応。

## 1. リサーチ(Web 裏取り)

- 類型の候補出しと流布の裏取りを Web で行う。手段はエージェント別(差分節): Claude Code は WebSearch / WebFetch(まとまった裏取りは MCP ワーカーの Codex に curl で行わせてもよい)、Codex 直接セッションは組み込みの web_search(デスクトップアプリでは既定で有効。CLI なら `codex --search`)か curl で自分で行う。DuckDuckGo は bot challenge が出ることが多いので、検索は web_search か既知の流布サイトへの直接アクセスを優先する
- 成果物は「類型・解法構造の要約・出典 URL」のみ。**問題文の転載は禁止**(著作権: アイデア・解法構造は保護されず、表現は保護される)
- **裏取りの基準を取り違えない**: 16-2 では「Wikipedia 級のページで古典と明記」に偏り、folklore 級なぞなぞをほぼ全部『未確認』にする実績があった。採用可否の基準は **作者不詳 + 複数の独立サイトに流布 = folklore 級 = 安全側**。流布例 URL を 1 件以上直接確認し、それを証跡として `research*.md` に残す(裏取りを別のワーカーに任せた場合も、採用判断は本スキルを回しているエージェントが行う)
- 除外するもの: 特定サイト・書籍固有の創作問題(アイデア自体に強い独自性があり出所が特定できるもの)、実在企業名を冠した断定(「〇〇社の入社試験」)、解釈が割れて炎上しうる問題(男女パラドックス等)

## 1.5 候補の準備と選別(G1a → 人間の選別。改修 R-3〔2026-09-22〕で追加)

完成稿を書く前に、**問題文・答え・必要な図の内容・出典メモだけの「候補」を目標の 2 倍**用意し、人間が **OK / NG / 保留 を反射的に返す**工程。形式・状態・集計規則・表示例の正は `content/quiz-stock/logic-training-1/candidates/README.md`(雛形 `_template.md`・集計 `tally.py`・投稿対象外の検証例 `examples/`)。

1. **目標と候補数**: 工程 0 の不足数 = 目標(朝夜別・各最大 7)。`tally.py plan --target <朝> <夜>` で候補数(目標の 2 倍)を出す。**前バッチの余剰 OK(`state: ok` のまま残った候補)があれば先に数える**(`--carry-from <前バッチ dir>`。持ち越す候補は新バッチへ `git mv` してよいが `batch` 欄は変えない)
2. **候補を書く**: `candidates/<batch>/m01.md …`(朝 = m・夜 = n)。工程 1 の Web 裏取り(folklore 級・流布例 URL・転載禁止)はこの段階で行い `source` に必ず入れる。題材・解法構造の既出照合(前バッチ・Aurora の `summary`)もここで済ませ、重複は `withdrawn` にする。つかみ・ヒント・解説・情景は書かない
3. **提示**: スロットごとに 1 候補 3 行(問題文 / 答え / 図)で一覧提示し、**OK / NG / 保留 だけ**を求める(README セクション 5 の表示例)。**理由は任意。書かれなかった理由を推測で埋めない**。迷いは保留でよい
4. **記録**: 返答を各候補ファイルの判定欄と `state` に反映し(原案は書き換えない)、`tally.py <batch dir> --write-index` を回して出力を会話に貼る。**INDEX.md は生成物**(手で直さない)
5. **判定**: 朝夜別に「不足 = 目標 − OK・追加 = 不足 × 2」。**朝夜の両方で不足 0 になるまで G1b へ進まない**(片方だけ満たしても仕上げない・未レビューが残る間は追加数を確定しない)。不足があれば **G1a のゴールを再度立て、不足分の 2 倍を朝夜別に追加**する(1〜4 を繰り返す)
6. **G1b へ**: OK が朝夜とも目標に達したら、OK のうち**目標数だけ**を `stock_items.py` へ転記して `state: drafting`・`stock_no` を記録し、セクション 2 以降(仕上げ → 機械検証 → 1 問ずつレビュー)へ進む。**余剰 OK は仕上げない**(`ok` のまま次回へ持ち越す)。**候補 OK は完成稿の承認ではない**(投入の承認は従来どおり完成稿の 1 問ずつレビュー)
7. **完成稿からの差し戻し**: 完成稿レビューで NG になった問題は `stock_items.py` から外し、候補ファイルに「段階: 完成稿 / 判定: NG」を追記して `state: final_ng`(再選別待ち。OK には数えない)。目標に足りなくなったら余剰 OK を先に使い、それでも足りなければ 5 に戻る。承認済み(`approved`)の候補・問題は変更しない
8. **NG・保留の扱い**: 候補ディレクトリに残す(消さない・理由を後付けしない)。理由の言語化とスキルへの反映は後日の振り返りスキル `/quiz-review-learn`(`.agents/skills/quiz-review-learn/SKILL.md`。R-3-2〔2026-09-22〕で整備・**Claude Code 専用**)の仕事で、週次補充の中では行わない。振り返りで OK に戻った候補は `state: ok` の候補 OK として次回の G1b に混ざる(記録は `candidates/reviews/<日付>.md`)。本スキルの作問基準(セクション 2・3)の差分は、振り返りで合意した共通ルールだけを根拠(候補 ID・記録)付きで足す
9. **再開地点**: `STATUS.md` に「いま G1a / 選別待ち / G1b のどこか・朝夜別の OK 数と不足・次に何をするか」を書き、候補側は `INDEX.md` と各ファイルの `state` が正。別セッションはこの 2 つを読めば再開できる状態に保つ

## 2. 執筆 = 完成稿の準備(G1b。候補 OK が朝夜とも目標数に達してから)

候補 OK のうち目標数だけを単一ソース(`stock_items.py` 形式)に 1 問 = 1 dict で書く(候補の問題文・答えは仕上げで整えてよいが、趣旨が変わるなら候補ファイルへ版を追記する)。フィールドと上限:

| フィールド | 上限 | 表示場所 |
|---|---|---|
| hook(つかみ) | 20 字 | **キャプション 1 行目のみ**(16-4c で動画からは外れた。動画上部の「つかみ帯」はスロット別の `slot_hook` = `prompt_configs.parameters` 側の可変値) |
| hint(ヒント) | 20 字 | カット 3 の吹き出し(カウントダウンと同時) |
| question(問題文) | 80 字 | 全カット常時表示 |
| answer(答え) | 30 字 | キャプションのみ(動画に出さない) |
| explanation(解説) | 80 字(L3 のみ 240 字) | キャプションのみ |
| coach_comment(コーチの一言) | 30 字 | キャプション末尾 |
| tags | 10 字 × ちょうど 3 | 記録用 |
| summary(出題要旨) | 100 字 | 記録用・重複管理の単位 |
| illustration_scene(イラストの情景) | 200 字 | 問題文の下に配置するイラストの生成指示文 |

※ hint は 16-2 中のカット構成変更(問題カット廃止 → 考える + 動的ヒント化)で追加。カット構成・フィールド仕様は方式設計書へ正式反映済み(16-2b。2026-08-07)で、方式設計書セクション 5・8.1 が正。

### 全フィールド共通の勘所(16-2 人間レビューで確立)

- **問題文**: 答え・解法がそのまま見える書き方をしない。難度はひと手間の足し引きで調整する — 例: 動物ダジャレは並び順をシャッフルする(そのままの順は簡単すぎ)、「トラが9匹」→「9匹の虎」の語順替え、文字なぞは漢字表記にして「ひらがなに直す」ステップを足す。**並べ替え系は途中に答えの部分文字列が現れないか必ず確認**(「カメ・サイ・ラクダ」は「サイカメラクダ」に"カメラ"が漏れる)
- **つかみ(hook)**: 解き方のヒントを言わない(それは hint の役割)。問題文と同じ情報の繰り返しも NG。雑学フック(「虫は世界に100万種いるらしいぞ!」)や驚きの一言(「壊しても使えるのか!」)が有効。数字を出すなら実数 + 「らしいぞ」で断定を避ける
- **ヒント(hint)**: コーチのキャラ(体育会系だが威圧しない・前向き)を必ず出す — 「〜だ!」「〜みろ!」「〜だぞ!」。カウントダウン中の最後の後押しなので、ある程度直球でよい
- **コーチの一言**: キャプションで答え・解説まで読んだ人への締め。キャラ必須。説教にしない
- **別解への態度**: 潰すより取り込む(「とればとるほど増える」は年 + 写真を両方正解に)。取り込む場合は表記も整合させる(「取る/撮る」の揺れはひらがな化で吸収)。取り込めない別解は解説で軽く触れるか、問題文の条件で閉じる
- **表記の使い分け**: ひらがな/漢字は難度調整のレバー。問題文で変換ステップを要求するなら、hint がその変換を後押しする組み合わせにする(例: 問題「弟」× hint「ひらがなで書いてみるんだ!」)
- **つかみの NG 実例(16-2 昼レビュー)**: 問題文の言い換えそのまま(「自販機、何台あると思う?」≒ 問題文)は NG。答えの単位とズレる語も NG(時間の答えに「衝撃の額」)。「実は…」等の同型パターンを近い出題順で繰り返さない
- **定型句・数値の重複回避**: hint の言い回し(「何人に1〜か見積もれ!」)や答えの数値(約2000人が 2 問)がスロット内の近い出題順で重複しないようにする。数値は丸め方で差別化できる(2000→1900 は実勢にも近かった)
- **隣接回避は型だけでなく題材も**: 通勤×2 問のような題材かぶりも隣接させない。移動は問題番号を保ったままリスト順(= INSERT 順)だけ変える(A12・B08 方式)

### イラストの情景の方針(ユーザー確定)

前提: **イラストは背景ではない**。問題文の下に独立した一枚絵として配置される(16-2 で確認。「背景イラスト」は過去の名残で誤り)。淡い環境描写の「壁紙」ではなく、主役がはっきりした構図で書くこと。

1. **答えの物は絶対に描かない**(タオルの問題にタオルを描かない・カメラの問題にカメラを描かない)
2. 基本構図は **「思い込みを絵で見せる + 大きな『?』」**(硬そうな岩に?・穴だらけで水が漏れるバケツ・「こわれもの注意」の箱に?・ティッシュを取ると減る)。視聴者の誤った前提を可視化して裏切る
3. **スロットの時間帯要素を必ず入れる**(朝日・昼の街・夜の照明)。抽象構図(宇宙から見た地球等)でも朝日などで時間帯を出す
4. 人物は後ろ姿か遠景まで・顔は描かない(セット共通ルール)。問題の題材の動物・物は積極的に描いて楽しくしてよい
5. **絵が答えをバラす間接経路に注意**: 影が答えの問題で朝日のランナーを描くと影が描画される → 「地面に影は描かない」と明記するか題材を変える。カレンダーの明日のマスに?も答えバレ
6. 視線を答えから散らす構図も有効(文字数えの問題 → たくさんのオモチャで遊ぶ子どもたち)
7. **答えが数値の問題(L3)は題材を直接・大量に描いてよい**: 数は答えをバラさない。規模感は「無限に並ぶ定食」「スプーンとお皿の山」のような誇張が有効で、ユーザーは遠回しな連想(理髪店のサインポール・ベビー靴)より題材の直接描写(髪をとかして抜ける・新生児室のベビーベッド群)を好む
8. 顔 NG は構図で回避する: 「後ろ姿の人が髪をとかす」「赤ちゃんの顔は描かない」のように後ろ姿指定か描写除外を情景文に明記する
9. **提示物そのものを絵に出す問題(黒板の式・紙の文字など)は、描くべき文字を情景文に明示し字形まで指定する**(16-4e でコード側の禁止を「情景で指定されていない文字は描かない」に緩和済み。情景文に書いた文字だけが描かれるので、「あいうおお」「西=?」のように**一字一句そのまま**書く。書き漏らすと描かれない)

## 3. スロット別の執筆勘所

### 朝 = L1 / light(なぞなぞ・言葉あそび)

**採用基準(2026-09-w3 のレビューで確定。作問前に必読。ここを外すと 1 問に 5 回の差し替えが発生する)**

却下の 2 大理由(ユーザーの言葉):

1. **「単純な計算問題(算数・数学的な問題)になっている」** — 答えが数値であること自体は NG ではない。**解く工程が計算になっている**ものが NG。
   却下例: トーナメントの試合数(99)・漢数字の画数・3 時 15 分の角度(7.5 度)・本棚の虫(24cm)・マラソンの順位(2 位)・8 を 8 個で 1000・地球のロープ(16cm)・時計の文字盤の 3 分割(各 26)
2. **「操作が素直で、一手で解けるものは簡単」** — 法則・仕掛けが 1 段で見抜けるものは、正しくても通らない。
   却下例: 止まった時計 vs 遅れる時計・鏡に映せない顔(寝顔)・濁点の法則(天気→電気)・循環並べ替え(時計→毛糸)・多義動詞(つく = 嘘 / たてる = 顔)・合体漢字(日寺言十 = 時計)・位置抽出の暗号(けんか)・隠れ数字の数列

承認された型(2026-09-w3):

- **視覚パズル**: 「5+5+5=550」に線 1 本 → 545+5=550(数字ではなく**記号**をいじる領域の転換)
- **参加型**: 好きな数 → 2 倍 → +10 → ÷2 → 元の数を引く = 必ず 5(**視聴者が頭の中で実演でき、全員同じ答えになる驚き**)
- **法則発見 / 領域の飛躍**: お・ひ・?・く・こ = 指の頭文字(数字でも五十音でもなく**身体の名前**)
- **法則発見 / 非自明な操作**: 柿→菊、雨→芋、蟹→絹 → 馬→えみ(**読みに直す → 母音を 1 段送る**。逆読み・並べ替え・濁点では説明できない)

作問時の自己点検(3 つとも満たさないものは提示前に捨てる):

- 解く工程が計算になっていないか(数えるだけ・足すだけ・公式を使うだけは NG)
- 操作・法則が素直すぎないか(逆さ読み・濁点・並べ替え・多義動詞・隠れ言葉・合体漢字は「一手」と見なされる)
- 答えを聞いた人が「そう来たか」と言うか(3 秒で納得するものは「簡単」判定)

**提示の作法**: 問題文に文字列・式・語の一覧を書かず、**黒板やカードのイラストで見せる**(A37・A40・A44・A45)。この場合イラストの字形検品が成立条件になるのでセクション 7 の申し送りに書く。


- 広く流布した定番なぞなぞのみ(ダジャレ・文字位置・文字数え・逆説・言い回し)。テンポよくクスッと笑えて 10〜30 秒で解ける規模
- 類型を分散させ、**同型(文字数え等)を出題順で隣接させない**(出題順 = INSERT 順 = 単一ソースのリスト並び。必要ならブロックを並べ替える)
- 懐かしさ(子どもの頃に聞いた)はコメント誘発の武器。ただし幼稚になりすぎないよう文面は大人向けに書き直す

### 昼 = L3 / standard(フェルミ推定) — **16-4d(2026-08-24)で当分停止中。補充しない。以下は再開時の参照用**

- **フェルミ推定を維持する**(2026-08-01 ユーザー決定。「意外な数字クイズ」への拡張は不採用)
- 題材は「身近で意外」を最優先: 一生の睡眠 = 約25年・一生に歩く距離 = 地球3周半、のように**自分ごと + 規模の驚き**があるもの。16-2 初期整備では施設数系(駅・ポスト・美容室)より生活実感系が好まれた(ただし下記の捻り方針以降は、施設数系でも捻った分解が要る題材なら可)
- **問題は「捻った分解」を標準にする(2026-08-07 ユーザー決定・次回補充から適用)**: 仮定 = 答えの量そのもの(スマホは1日何時間? 睡眠は1日何時間?)という**直接換算型は標準にしない**。**非直接的な仮定を最低 1 つ**経由する問題を選ぶ。例: 「日本国内の電柱の数は?」= ①人が住みインフラのある土地を国土の約 20% と仮定 ②道路沿いに 50m 四方(2,500 m²)に 1 本の密度と仮定、の 2 段の捻りで解く。16-2 の初期 42 問は直接換算型が多いが承認済みのため置き換えない
- **解説は 5 ステップ構造で書く(2026-08-07 ユーザー決定・捻り型とセット適用)**: ①**前提**(問題の定義・範囲を確定)→ ②**ベース**(何を基準に数えるかを宣言して式の骨格を立てる。例: 自動車台数 = 世帯数×平均所有数)→ ③**分解**(非直接的な仮定を置いて要素を具体化)→ ④**計算** → ⑤**実勢チェック**(「実際は約〜とされる」と桁の乖離を確認)。複数の解法があっても 1 つの手法を最後まで通す。⑤に使う実勢値はリサーチ段階で出典付きで確認しておく
- **question の上限は 80 字**(改修 R-2〔2026-09-19〕で 90 → 80 字へ変更)。R-2 の版面では問題文に使える高さが 294px で、フォント下限 44px でも収まるのは全角 80 字まで(81 字以上は 5 行になり溢れる)。次回補充時は validate.py の `LIMITS["question"]` も 80 に追随させること(前バッチからのコピー時は 90 のままのため要修正)
- **explanation の上限は L3 のみ 240 字**(5 ステップは 80 字に入らない。16-2b で方式設計書セクション 5 へ正式反映済み)。DDL は TEXT/JSON のため変更不要・キャプション専用フィールドのため版面影響なし。次回補充時は validate.py の上限も 240 字(L3 のみ)に追随させること
- 答えは「約〇〇(目安)」の幅表現必須。解説に使った仮定と「〇〇×〇〇」の式の形を必ず入れる(80 字内。validate.py は × を必須チェックするので ÷ だけの式にしない)
- **仮定と固定値を書き分ける**(2026-08-07 ユーザー決定): 自分で置く数は「〜と仮定すると/〜と仮定。」と明示し、固定値(365日・24時間・人口1.2億)や既知の統計(就業者数・出生数)は事実として書く。既知の平均値しか使わない問題(抜け毛の 10 万本・毛周期)には仮定表現を付けない。答えと式の数字は一致させる(ズレるなら「25〜27年ほど」の幅表現にする)
- 公式・物理定数を与えて計算させる問題は L3 ではない(15-13 の矯正を踏襲)
- 算数は必ず verify_logic.py に検算を追加して機械検証する

### 夜 = L1 / deep(とんち・水平思考・ひっかけ)

- 古典のみ: 一休咄(屏風の虎・このはし)、Situation puzzle の定番(エレベーターの男・しゃっくり)、故事(ゴルディアスの結び目・ソロモンの審判)、定番ひっかけ(ライオンの部屋・バスの運転手・ろうそく残数)
- **プラットフォーム配慮の置き換えを恐れない**: 銃 → 大きな物音、死刑囚 → ゲームの扉、など構造を保ったまま表現を安全にする(著作権的にも書き直しの一部)
- 水平思考系は答えが「想定解」であることを意識し、問題文の条件で別解を塞ぐ(「中身を知る店長が必ずハズレを開ける」等の前提を明記)
- 「じっくり考えたら直感がひっくり返る」「そうきたか」の読後感を狙う

**条件が答えを手渡していないか(2026-09-w3 の C45 却下で確定。作問時の必須点検)**

夜の却下理由は「簡単すぎる」だが、その正体は難度ではなく**問題文に並べた条件を組み合わせるだけで手順が組み上がってしまう**構造にある。

- **却下例(C45 初案・曹沖のゾウ)**: 「ゾウを乗せられる船がある」「船に印をつけられる」「岸に石と小さな秤がある」。ユーザーの言葉は「この手順、この条件を組み合わせれば、かなり素直に導き出される回答かなと思いましたので、ちょっと簡単すぎる」。**条件を 3 つ挙げた時点で「船に乗せる → 印 → 石に積み替える → 石を量る」が一直線に出る**
- **承認例(C45 差し替え・つかえたトラック)**: 「高さ制限の橋に、トラックの屋根が数センチつかえて進めない。荷台は空で、橋を壊すことも車を切ることもできない。どうやって通す?」→ 答えは「タイヤの空気を抜く」。**問題文に出てくるもの(橋・屋根・荷台)はすべて答えと無関係で、答えの対象(タイヤ)は一度も登場しない**。解く人が自分で注意の向きを変えないと出てこない
- **点検の手順**: 書き上げたら、**問題文に挙げた道具・条件だけを並べて「これを素直につなぐと答えになるか」を自分で試す**。なるなら条件を書きすぎている。答えの対象を問題文から消せないか、注意が向く先(見せる物)と答えのある場所をずらせないかを検討する
- 「道具を渡して手順を考えさせる」型そのものは夜の本線だが、**渡す道具は答えの直前までしか渡さない**。C43(ロウソク・画びょうの箱)は道具を渡すが、箱を「入れ物」から「台」へ読み替える一段があるので成立している
- 別解封じ(前項)と食い合う点に注意する。別解を塞ぐつもりで条件を足すと、その条件が答えへの道順になることがある。塞ぐのは**答え以外の経路**で、答えの経路を説明しない

**設定そのものが答えの形になっていないか(2026-09-w3 の C47 却下で確定)**

条件の書きすぎだけでなく、**異常な状況設定それ自体**が答えを描いてしまうことがある。

- **却下例(C47 初案・チェスの同時対局)**: 「初心者が達人2人と別々の盤で同時に対局。片方で白の先手、もう片方で黒の後手を持つ」。ユーザーの言葉は「通常は1対1なのに別々の盤で同時に対局という通常ではありえない状況、そんな中、片方で白の先手、もう片方で黒の後手という補足説明。簡単に答えが導き出せます」。**「2つある」「役割がちょうど補い合う」と書いた時点で、あとは2つをつなぐだけ**になる
- **承認例(C47 差し替え・新聞紙1枚の上の2人)**: 状況は日常そのもの(新聞紙1枚と大人2人)で、**答えの中心であるドアは問題文に一度も出てこない**。条件をいくら組み合わせてもドアは出てこず、部屋という枠の外へ目を向けて初めて出てくる
- **点検の手順**: 設定が日常的でない場合、**「なぜこの異常な状況なのか」を自問する**。答えを成立させるためだけに用意した設定なら、視聴者にもそう見える。日常の状況で成立する類型を探し直す
- 夜の強い問題は「**日常の状況 + ありえない要求**」の形をしている(新聞紙1枚で触れられない・板より広い堀を板2枚で渡る・橋につかえたトラックを通す)。逆に弱い問題は「ありえない状況 + 自然な要求」になっている

**難しさを問題文に書いたか(同 C47 の 2 度目の指摘)**

矛盾が芯にある問題は、**その矛盾を文面で宣言しないと「普通にできる」と読まれる**。C47 は「新聞紙1枚の上に大人2人が立つ。手を伸ばしても触れられない」だけでは何が難しいか伝わらず、「**普通なら手が届く距離だが**」の一句を足して成立した。書き上げたら「この問題の難しさはどこかと聞かれて、問題文の中を指させるか」を確認する。

2. **イラスト生成(imagegen)**: `work/prompts/<id>.txt` の全文をプロンプトにして imagegen で生成し、`work/illustrations_raw/<id>.png` へ保存する。生成の手段はエージェント別(差分節): Claude Code は MCP ワーカーの Codex に生成させる(`codex exec` の image_gen も可)、Codex 直接セッションは組み込みの imagegen で自分で生成する。どちらでも **生成した側が「情景で指定されていない文字・数字・記号の混入」を確認し、混入時は再生成する**(1 問通し確認でも初回混入 → 再生成が実際に発生した)。提示物問題(情景文に文字を明示した問題)は逆に**指定した文字が字形どおり正確に描かれているか**を確認する。プロンプト末尾に **3:2(1536x1024)の明示行**が入っている(16-5 追加)。imagegen は指定しないと 16:9 前後で出力が揺れ、3:2 以外は次の intake で左右が捨てられるため、**保存されたファイルのサイズが 1536x1024 か(`python3 -c "from PIL import Image; print(Image.open('<path>').size)"` 等)を生成した側が確認し、違えば再生成する**
3. **取り込み → ビルド**: `intake.py` → `build.py`。build.py は**ホスト(WSL)で実行**し(`S3_BUCKET_NAME=<bucket> python3 build.py`。依存は pymysql のみ)、Remotion レンダリングと ffmpeg 処理だけを Docker に委譲する(改修 R-1〔2026-09-03〕で Pillow 組版から Remotion へ載せ替え。事前に `remotion-render` / `image-batch:ffmpeg-check` の 2 イメージをビルドしておく。README 参照)。イラスト未配置の行は自動スキップされるので部分ビルドでよい
   - `intake.py` は 3:2 でない素材を **WARNING + 切り捨て率**で報告する。被写体が端にある問題(操作パネル等)は切り捨てで見切れるため、警告が出たら該当問題のイラストだけ再生成する
   - レンダラー変更を既ビルド分へ反映する場合は **`build.py --rebuild`**(ビルド済み行を対象・BGM は `video_audio_asset_id` を引き継ぎ LRU を消費しない)
4. **全数人間レビュー**: `review_sheet.py` → `work/review.html`。観点はイラスト(文字混入・画風・情景適合)・版面・音。NG は imagegen 再試行または `illustration_scene` 修正(DB 更新)→ 再ビルド
5. **配置**: 承認 id を `approved.txt` に列挙 → `publish.py --dry-run` で `upload_prebuilt.sh` / `update_prebuilt.sql` を確認 → 本実行(S3 アップロード + ローカル MySQL 反映)→ Aurora へ `work/update_prebuilt.sql` を Data API で適用。**Aurora SQL は安定キー(set_code + question_text・BGM は s3_key)で解決する形式・S3 ファイル名も id ではなく `content_key`**(ローカルと Aurora で AUTO_INCREMENT id が一致しないため。id 直指定の SQL・id 入りの S3 キーを作らない)。適用後は更新行数 = 承認件数を確認
6. **締め**: 在庫確認クエリ拡張版で `unbuilt` = 0 を確認し、ツール・台帳の変更をコミット
