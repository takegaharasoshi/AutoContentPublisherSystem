# ステップ着手スキル(step)

計画書のステップ着手を 1 つの入口に絞り、**起動 = レーン宣言 + `/goal` の完了条件宣言**とするスキル(Phase 19-2 で導入)。
レーン判定・並行作業ルールの正は `docs/plans/index.html`、ゴール運用の検討経緯は `docs/ideas/claude-code-loop-goal-skills.html`。矛盾したら index.html が勝つ。

## 0. 前提(/goal の起動制約)

`/goal` は **Claude 自身・スキル・フックからは起動できない**。ユーザーの入力でのみ起動する。したがって本スキルの責務は「テンプレを埋めた `/goal` 行を提示するところまで」で、**goal が立つ(ユーザーが行を打つ)まで工程に着手しない**。ユーザーは `/goal`(引数なし)で現在の設定を確認できる。

## 1. 引数の解釈(レーン判定の一次振り分け)

| 引数の形 | レーン | 読む計画書 |
|---|---|---|
| `16-12` のようにステップ番号のみ | 開発レーン | `docs/plans/development-plan.html` |
| `logic-training-1 R-1-2` のように set_code + 識別子 | セットレーン(そのセット) | `docs/plans/<set_code>.html` |

- set_code の一覧は `docs/plans/index.html` セクション 1(現在: fantasy-animals-1 / logic-training-1 / pref-ranking-1)
- 引数がない・計画書に該当ステップが見つからない場合は、推測で進めずユーザーに確認する

## 2. 手順

1. **計画書を読む**: 該当ステップの「内容」「完了条件」「人間ゲート」「停止点・上限」(4 項目様式。正は `docs/plans/index.html` セクション 5)を確認する。前提ステップが未完了なら着手可否をユーザーに確認する
   - **移行済み計画書**(Phase 25 で導入。25-5〔2026-09-22〕で**開発計画とセット計画書 3 本すべてが移行済み**。対象の正は `tools/docs_plan_check.py` の `REGISTERED_PAGES`、様式の正は `docs/plans/index.html` セクション 5.0)では、常時表示の「着手条件」「結果 / 現況」「1. 何をするか」「守る条件」「2. 完了条件」「3. 人が確認すること・止まる場所」**と、折りたたみ「実装の細部・背景」(`details[data-field="implementation"]`)の両方を読む**(着手に必要な仕様・定数・設計判断の理由は折りたたみ側にある)。「4. 作業記録」の折りたたみは前回の中断地点を引き継ぐときだけ読む。ゴール行に埋めるのは常時表示側の記載(完了条件は折りたたみの中にない)
   - **未移行の計画書**は 2026-09-22 時点で存在しない(`REGISTERED_PAGES` 外の計画書が新設された場合だけ、従来どおり 4 項目をそのまま読む)
   - **旧形式フォールバック**(Phase 19-4。**未移行の計画書に限る** = 2026-09-22 時点では発動しない。移行済み計画書に完了条件のないステップがあれば様式違反なので、推測で 4 項目を作らず構造検査〔手順 6 の脚注〕で検出された不備として報告する): 「完了条件」のないステップは、「内容」から完了条件(機械検証できる形)・人間ゲート・停止点の案を作り、ユーザーの確認を得てからゴール行に埋める。人間ゲートがステップの途中に入る・20〜30 ターンを超えそう・2 レーンをまたぐなら、その場で分割を提案する。確定した内容で計画書のステップを 4 項目に書き換えてから着手する(書き換え自体はそのセッションで行う)
2. **対象外の判定**: ステップが「(ユーザー)」「ユーザー判断」のもの(目視確認・go/no-go 判断等)は **goal 対象外として断る**(自走できない)。週次補充は本スキルではなく補充スキル(`/quiz-stock-replenish` / `/ranking-stock-replenish`)の入口から行う
3. **触るパスの列挙とレーン判定**: ステップで触るパスを列挙し、`docs/plans/index.html` セクション 2 の判定表に当てる。**セット計画書のステップでも、開発レーンのパス(`services/` `shared/` `infra/` `database/`・共通設計書・CLAUDE.md)が 1 つでも入るなら開発レーンとして扱う**(このとき「開発レーンは常に 1 セッション」の制約が働くため、他に開発レーンのセッションが動いていないかユーザーに確認する)
4. **確認待ちリストの照合**(Phase 19-5 で導入。ルールは `docs/plans/index.html` セクション 5.2): 開発レーンなら開発計画末尾の「確認待ちリスト」、セットレーンなら当該セット計画書の「確認待ちリスト」を読み、**手順 3 で列挙した触るパス・このステップで起きる出来事(push・デプロイ・ビルド等)がトリガー列に該当する行**を拾う。該当行があれば、その「確認内容・判定基準」の確認と「結果」列への記入(日付 + 結果 + 記録へのリンク)を**ゴールの完了条件に含める**。該当なしなら「確認待ち: 該当なし」と一言宣言する(照合したことを残す)。リストの節が無い計画書は該当なしとして進む
   - **課題表の照合**(Phase 22-4 で導入。ルールは `docs/issues/index.html` セクション 4.8): 手順 3 で列挙した触るパスで `docs/issues/index.html` の live 表(レーン別の節)の**対象パス列**を照合し(`grep -n "<パス>" docs/issues/index.html`。ディレクトリ単位・設計書・スキルのパスも含める。セットレーンならセット名でも引く)、該当行の有無を宣言する。**該当行があれば黙って通り過ぎず**、そのゴールの中で「同梱する(展開 = 完了条件に足す)/ トリガーを更新して据え置き継続 / 受容」のどれかを決めて表を更新する(判断はゴール文の完了条件に「(n) 課題表 I-xxx の扱いを決めて表に反映」として入れる。トリガーが本ステップの出来事に当たらない行は「据え置き継続・トリガー更新なし」と宣言すれば表の更新は不要)。該当なしなら「課題表: 該当なし」と一言宣言する。ステップが課題の展開(起票元が `I-xxx`)なら、その行を**展開元の課題**として控える(完了手順で使う)
5. **レーン宣言**: 「開発レーン: 16-12」「セットレーン: logic-training-1 R-1-2」の形で、レーンと触るパス・確認待ち・課題表の照合結果を会話冒頭で宣言する
6. **/goal 行の提示**: セクション 3 のレーン別テンプレに番号・名称・(セットレーンなら set_code)を埋め、コードブロックで提示して「この行を打ってください」と伝える。ステップに完了条件・停止点が書かれていれば、テンプレの汎用条件をその記載で置き換える(テンプレは骨組み、計画書の記載が正)。手順 4 で該当した確認待ち行があれば「(n) 確認待ちリストの『<対象>』を確認し結果列に記入」を完了条件に足す。**goal が立つまで工程に着手しない**(展開文からの自動起動は効かない前提で、必ず提示 → ユーザー起動の流れを取る)

## 3. ゴール文テンプレ

### A: 開発レーンのステップ実行

```
/goal 開発レーン・ステップ <番号> <名称>。完了条件: (1) 計画書の「内容」にある成果物が揃う、(2) 該当サービスの pytest が全パス(要約行を会話に貼る)、(3) infra/ を触った場合は cdk synth が成功、(4) 関連設計書と計画書(チェック・完了日・要点)を更新、(5) 日本語メッセージでコミット済み。services/ shared/ infra/ database/ を触った場合は push せず、差分を提示して確認待ちで終える。docs のみなら pull --rebase → push まで行う。cdk deploy・本番 DDL 適用・publish は行わない。or stop after 20 turns
```

### A′: セットレーンのステップ実行

```
/goal セットレーン <set_code>・ステップ <番号> <名称>。完了条件: (1) セット計画書の「内容」にある成果物が揃う、(2) ビルド・検証ツールの出力(build.py --dry-run / validate 等、該当するもの)を会話に貼る、(3) セット計画書(チェック・完了日・要点)とセット記録を更新、(4) 日本語メッセージでコミットし pull --rebase → push まで行う(content/ と docs/plans/<set> は CodePipeline を起動しないため push まで可)。S3 差し替え・Aurora / ローカル DB の更新・SNS 投稿設定の変更は行わず、レビュー用の成果物(プレビュー動画・review.html)を提示して終える。services/ shared/ infra/ database/ に触る必要が出たら手を止めて報告する(開発レーン行き)。or stop after 20 turns
```

- セットレーンでは**配置(S3・DB 差し替え)を人間レビュー後の別ゴールに切る**。レビュー承認後に配置用のゴールを改めて提示する
- 大きなステップを 1 本のゴールにしない(1 ステップ 1 ゴール。長引くなら分割を提案する)

## 4. ガードレール(ゴール実行中)

- **denylist**: `cdk deploy` / 本番 DDL 適用 / `publish.py`・`apply_aurora.py` の投入 / SNS 投稿 / Secrets への接触 / `docs/plans/` のルール変更 — ゴール文にかかわらず行わない
  - **`docs/plans/` のルール変更の限定例外**(Phase 25-3 で明文化): ①**ユーザーがそのフェーズの変更ファイルを名指しで承認**しており、かつ②**フリーズ窓**(他セッションが 1 本も動いていない)で実施する場合だけ、名指しされた範囲に限って改訂してよい。無関係な規約変更・ついでの整理へは広げない。ステップの追加・分割・状態更新といった**通常の計画書更新はルール変更ではない**ので、この禁止に当たらない
- **証跡を会話に貼る**: pytest 要約行・検証ツール出力・件数クエリの結果は省略せずそのまま貼る(/goal の evaluator は会話ログしか見ない)
- **コードを触るゴールは auto mode で走らせない**(push の許可プロンプトが「差分確認後に push」のゲートを兼ねるため)。夜間実行なら Ctrl+C できる端末で
- `services/` / `shared/` を触る push に至った場合は、push 直後に CLAUDE.md「Git 運用ルール」の D 定型行(CodePipeline 完走確認の /goal)を提示する
- **確認待ちの結果は必ず書く**: ゴール内で確認待ち行を確認したら、結果列に日付 + 結果を記入し、OK なら行を記録(`development-log.html` / `<set_code>-log.html`)へ移す。NG なら「NG 時の扱い」列に従い、追補ステップか課題として起こす(黙って結果列を空のままにしない)
- **ステップを新たに起こす・分割するとき**は `docs/plans/index.html` セクション 5.1 の起票チェックリストを通す(自セッション外の出来事は完了条件に入れず確認待ち項目へ。触るパスで課題表を照合し、該当する据え置き課題を同梱するかトリガーを更新する)。**移行済み計画書に足すときは `docs/plans/_templates/step.html` の枠をコピー**し、ID・状態・属性を書き換えて進行中グループ(`[data-plan-group="active"]`)に置く(必須欄を空にしない。記録がまだなら「着手前のため記録なし」と書く)

## 5. 完了手順(ゴールの最後に必ず)

1. 計画書のステップを更新する。**移行済み計画書**では (a) `data-status="done"` + `data-completed="YYYY-MM-DD"` と状態表示、(b) 常時表示の「結果 / 現況」を結果 1〜2 行に書き換え、(c) 折りたたみ「作業記録」に実施記録を書き、(d) **そのステップを同じフェーズの完了済みグループ(`details[data-plan-group="done"]`・進行中より上・`open` を付けない)へ移す**。**未移行の計画書**(2026-09-22 時点は存在しない)では従来どおりチェック + 完了日 + 要点を書く。どちらも、記録ファイル(`development-log.html` / `<set_code>-log.html`)への詳細転記が間に合わなくても計画書側の更新は遅らせない(移管の時期は `docs/plans/index.html` セクション 4)。計画整理で本文を記録ファイルへ移したときは、計画書の記録欄を**記録へのリンクだけ**に置き換える(移した本文を残さない)
2. 手順 4 で該当した確認待ち行の結果列を埋める(上のガードレール)
3. **展開元の課題があればクローズ節へ移す**(Phase 22-4 で導入。ルールは `docs/issues/index.html` セクション 4.9): ステップの起票元が課題 `I-xxx`(計画書のステップに `#I-xxx` リンクがある・手順 4 で控えた行)なら、ステップ完了時に `docs/issues/index.html` の live 表からその行を末尾のクローズ節へ移し、ステータスを 解消 にしてクローズ日 + ステップ・コミットへのリンクを書く(ID・起票日はそのまま)。ステップが課題を部分的にしか解消しないときは行を残し、対応方針・トリガー列を更新して据え置き継続にする(どちらにしたかを会話に宣言する)。課題の展開ではないステップは「クローズ移動: 該当なし」
4. **移行済み計画書を更新したら構造検査**: `python3 tools/docs_check.py --plan-only` を実行し、出力を会話に貼る(NG なら直してから進む)。検査は構造と参照しか見ないので、差分のステップについて「守る条件を文章として拾えているか・要約が正しいか・記録と最新状態が一致するか」は自分で読み直す。CSS・テンプレートを変えた場合や計画書を新たに移行した場合は `python3 tools/docs_check.py --widths 360,390,768,1280` も回す。`REGISTERED_PAGES` 外の計画書だけを更新したときは不要(2026-09-22 時点では該当なし)
5. コミット・`pull --rebase` → push(ゴール文の停止点に従う)
