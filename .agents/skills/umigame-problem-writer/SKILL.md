# ウミガメのスープ作問スキル（umigame-problem-writer）

umigame-soup-1 の問題を **1 問ずつ** 作るための手順。21-4a（2026-09-04〜07）で「制約から逆算して書き、コア = 引っ掛けるポイントを決める工程を飛ばした結果、コアのない知識クイズを書いてしまう」失敗が出たため、note 記事 [ウミガメのスープ作問法](https://note.com/suekai0217/n/n35128e606a9b)（4 ステップ・良い問題の 3 条件・2 類型）を手順に固定し、**コア宣言を書けない案は問題にしない**ことを本スキルの一番のルールとする。

本スキルは作問だけを担う。素材 14 項目の仕様・字数・件数の正は `docs/app/sets/umigame-soup-1.html` セクション 4、機械検査は同バッチの `validate.py`、プローブテストは `probe_test.py`、投入 SQL は `generate.py`（使い方は `content/umigame-stock/umigame-soup-1/README.md`）。ここには重複記載しない。矛盾したら設計書・ツールが勝つ。

**構成**（2026-09-20 に型別へ分冊）: 本ファイルは両型に共通の工程。型ごとの工程 3（コア宣言）と工程 4（不思議にする）・型固有のコア検査と失敗パターンは分冊に置く。

| 型 | `puzzle_type` | 分冊 | 作り方の要点 |
|---|---|---|---|
| 物語復元型 | `story` | [story.md](story.md) | **物語先行方式**（2026-09-22 に 21-4a-4 で再設計・一本化）: 5〜7 文の完結した物語を先に書いて物語単体の面白さで検査し、「どこを隠すと最も不可解で復元の納得が最大か」を選んで切り出す。ミスリードは要件にしない。ゴール A では物語 2〜3 本 + 各の切り出し案を提示する |
| 意味誤誘導型 | `misdirection` | [misdirection.md](misdirection.md) | 慣用句・多義語・定型表現の**言い方を変えて**誤認させ、常識の逆を 1 つ足す。語の仕掛けがコア。**21-4a-3 で一時 Fix**（2026-09-22。通過 7 問の実績。以後の修正は週次補充の反復で） |

**バッチの型構成は両型同数**（2026-09-20 ユーザー決定。第 1 バッチは 14 問 = story 7 / misdirection 7）。型は起動時に宣言し、無指定なら在庫の少ない型を選ぶ。

## 0. 原理（記事の要点。変えずに守る）

- 問題は「わからないストレス」と「解けたときのカタルシス」でできている。ストレスをカタルシスに変えるのは**納得感**。納得感を作るのが下の 3 条件
- **良い問題の 3 条件**: ① 答えの**コア**がハッキリしている（「ここで引っ掛けてやろう」という出題者の悪意が一つに定まっている。コアが定まると正解判定のタイミングが決まる）② **動線**がある（問題文の取っ掛かりから正解までの最短ルートが無理なく存在する。特に最初の質問が明確）③ **現実離れしていない**（架空設定・マニアック知識に頼らない。小中学校の知識までは可）
- **2 類型**: **物語復元型**（隠蔽。完結した物語 A→B→C から一部を切り出して出す。ミスリードなし、深いカタルシス）/ **意味誤誘導型**（改竄。言い換えで誤認させ、正させてカタルシスを生む。手軽で現在の主流）。どちらも正統。4 ステップは意味誤誘導型向け、物語復元型は「A→B→C を書いて B を抜く」が最も有効な切り出し
- 記事の結び「ロジカルなメソッドは存在しない。自由に作ってほしい」。手順は補助輪であり、**手順を全部踏んでもコアが立たない案は捨てる**（手順を踏んだことは採用理由にならない）
- 通過した問題に共通する条件（21-4a-2〜21-4a-3 の観察。misdirection 7 問 + story 3 問のすべて）: **誤認を強制する仕掛け + 具体的な仕組み・出来事への着地**。型が違っても、反転後が「動機・感情・習慣の説明」で終わる案はカタルシスが小さく通らない

## 1. 工程（会話に「作問ログ」として全工程を貼る）

各工程の結果を下の見出しのまま会話に書く。レビューはこのログを「コア宣言 → 問題文 → 素材」の順に見る。**工程 3 でコア宣言が書けなければ工程 1 か 2 に戻る**（戻った回数と捨てた案も書く）。

### 工程 0: 型の宣言

- 引数または在庫の型の偏り（`validate.py` の集計行）から型を決めて宣言し、その分冊を読む。1 問の途中で型を変えない（変えるなら工程 1 からやり直し、捨てた案として記録する）
- 分冊の工程 3・4 は本ファイルの工程 3・4 の位置に差し込んで使う

### 工程 1: モチーフ（ランダム語から）

```bash
shuf -n 3 .claude/skills/umigame-problem-writer/motifs.txt
```

- 3 語を引き、1 語を選ぶ（引いた 3 語と選んだ理由を書く。3 語とも連想が広がらなければ引き直してよい。引き直しも書く）
- 既存問題・他者の自作問題・リサーチ台帳の題材から**始めない**（21-4a で「例として渡された問題」の登場人物を置き換えただけの問題を書いて取り下げになった。着想元が外にある案は工程 7 で落ちる）
- 型に合う語に寄せてよい: **story は「状況・場所・出来事を持つ語」**（そこで何かが起きる・時間が経つと変わる語）、**misdirection は「動作・慣用句・多義を持つ語」**

### 工程 2: 連想

- モチーフから **10 個以上**書き出す。観点: その物でする動作 / 使う場面・場所 / 関わる人 / 道具 / 慣用句・多義語 / 「ふつうはこう」という常識 / 困りごと
- story ではさらに: **その語のまわりで人に起きる出来事・事情・感情の動き**（誰が関わるか / どんな事情か / どんな行き違い・偶然・約束・勘違いが起きるか / 前と後で気持ちがどう変わるか）。仕組み・性質だけで物語にしない（story.md 前段）
- ここで面白がらない。量を出す

### 工程 3: コア宣言（型別。分冊の工程 3 を使う）

- 様式は型別（story: 「物語「〈一文要約〉」の〈B〉を隠して「〈A→C の見え方〉」を出す → 復元: 〈B を戻した一文〉」/ misdirection: 「〈語・状況〉を〈誤認させる読み〉と読ませる → 実際は〈反転後の事実〉」）
- 両型共通のコア検査（分冊の型別検査と合わせて、すべて Yes でなければ戻る）:
  - 「引っ掛けてやろう」と言える悪意が**一つ**あるか（複数のコアが混ざっていないか。混ざったら一つに絞る）
  - 反転後の事実を言い当てた瞬間に「正解です！」と宣言できるか（正解判定のタイミングが決まるか）
  - 答えが**知識の有無**で決まっていないか（知っていれば即答・知らなければ到達不能なら、それは知識クイズであってコアではない。21-4a の再々稿「一年中見える星座」がこの失敗）
  - **反転後の事実に落差があるか**。反転を一文で声に出して「そういうことか」が出るか。「動機・感情・習慣の説明」（時計を合わせていた / 留守宅の防犯 / 故郷の砂 / 商品の売り文句）で終わる反転は落差が小さい

### 工程 4: 不思議にする（型別。分冊の工程 4 を使う）

- 共通の守り: 足す不思議は **1 つ**（2 つ以上足すと動線が消える）。**因果を主張する文には受け皿を 1 つ置く**（「働く男たちは」「見た人たちのおかげで」のように、仕事・場面・読み手のどれか 1 つの枠。枠がないと不思議ではなく意味不明に見える〔21-4a-2 U11〕。2 つ置くと A の手がかりが増えて易しくなる）
- 問題文の草案を書く（この時点では字数を気にしない。「なぜ？」「どういうこと？」で締める）

### 工程 4.5: 手がかりの棚卸し（難しさの調整）

21-4a-2 の U01 で、同じコアのまま問題文の手がかりを削っただけで「分かりやすすぎる」→「とてもよい」に変わった（初稿: 半年前に「濃くなった」で落ち込む対称形 + 「〜ましたね」+「同じ相手」/ 改稿: 「久しぶりに会った相手」+「相手もにこにこ笑っていた」+「何度も頭を下げた」）。草案の手がかりを全部列挙し、次の基準で残すものを選ぶ。

- 手がかりを 2 種類に分ける。**A = 正体のカテゴリを直接指すもの**（肩書・場所・口調〔丁寧語は職業をにじませる〕・時間経過・「量が変わる」と分かる対称形〔同じ現象を 2 回書く〕・**登場人物の属性**〔「少年・少女」は遊びを、「老人」は昔話を連想させる。21-4a-3 U16 の指摘: 真相が遊びなら登場人物は「男・女」にして子どもを問題文から外す〕）/ **B = 行動・感情で示すもの**（泣く・笑う・頭を下げる・何度も・久しぶりに）
- **残すのは B を中心に 2〜3 個。A は 0 個が既定**（21-4a-2 の U13 改稿でユーザーが確定した難易度基準。A を 1 個置くのは、下の消去法の動線がどうしても組めないときの救済に限る）。A が 2 個以上あると、問題文を読んだだけで真相のカテゴリ（医療・職業・遊び…）が絞れてしまう
- 検査: 「初見の読者が最初に浮かべる誤読（工程 3 の〈誤認させる読み〉/〈誤った補完〉）が、問題文だけで最後まで維持されるか」。誤読を否定する材料（対称形・専門的な口調・関係を示す語）を問題文に置いていたら削る
- 削った分は `fact_sheet` と `expected_questions` に回す（問題文から消しても、質問されれば「はい」で答えられる事実として残す）。動線は問題文ではなく質問で開くのが基本
- **A = 0 個のときの動線の組み方**: 取っ掛かりは問題文の語ではなく矛盾そのもの。序盤に出る誤認先の質問（関係・入手経路など）をすべて「いいえ」で塞ぎ、消去法で問題文中の対象物（手紙・道具…）へ目を移させる。「いいえ」が情報になるよう、誤認先の枝は確定事実シートで全部塞いでおく（U13: 血縁・伝聞・有名人が全部いいえ → 残るのは手紙そのもの → 「最近書かれたもの？」で時間の扉が開く）
- 難易度の目安: **既定は 4（A = 0 個）で作る**。A を 1 個 = 3（動線の救済時のみ）/ A を 2 個以上 = 1〜2 は U10「道の駅」のような即答狙いの問だけ許す

### 工程 5: 動線検査

- **取っ掛かり**: 問題文のどの語・どの矛盾から攻め始めるかを 1 つ決める（例: 「大金」/ 「反対方向」/ 「凍りついた」の意味）
- **最短ルート**: 取っ掛かりから正解までの質問を 3〜5 個並べ、各質問に「はい / いいえ」で答えたとき次の質問が自然に出るかを見る。途中で「関係ありません」しか返せない質問しか思いつかない区間があれば、問題文に手がかりを足す
- **story は動線を 2 本**引く（A 側から: 「A の状況はふつうか」を潰していく線 / C 側から: 「なぜ C になったか」を追う線）。どちらか一方しか引けない案は切り出し方（story.md 工程 4S）を見直す
- このルートは工程 9 の `expected_questions` の骨（正解に向かう質問）になる。工程 4.5 で削った手がかりは、このルートの質問として「はい」で回収できているかを見る

### 工程 6: 現実性検査

- 架空設定・特殊な職業のルール・地域限定の慣習に頼っていないか。使う知識は小中学校まで
- 「そう考えればよかったのか」と言えるか（回答者が自分で気づける）。言えないなら工程 3 へ
- **動機の現実性**: 「その人は本当にそれを、その頻度で（毎日・毎朝）するか」と 1 回問う。知識の範囲が正しくても、動機が「自分で直したから気になって毎日見に来る」のように作り手の都合なら現実離れ（21-4a-2 U11 修理版がこの失敗）。動機は実在の習慣・仕事・事情に置く
- セット固有の守り: **誰も死なない・事件が起きない日常の不思議**を基本にする（子ども向けアカウント。問題文の語感が強い動詞〔殴る・襲う・撃つ〕は避ける。**story は例外で、死や別れの題材を可とする**〔2026-09-22 ユーザー決定。story.md 冒頭〕）。難易度は 1〜5 で自己申告し、根拠を書く

### 工程 7: 既存問題との照合

- `content/umigame-stock/umigame-soup-1/batch-01/research.md` の 30 件（コア列）と、台帳の「オリジナル性の基準」に照らす。**コアの構造が同じ**（例: 曜日名が馬の名前 / ホーム = 本塁 / 外科医は母親）なら捨てる。`fame: classic` の構造は語を変えても捨てる
- 自分の記憶にある有名問題（本家ウミガメのスープ・エレベーターの男・雪だるまのニンジン等）と同じ構造でないか、もう一度言葉にして確かめる。**story は有名問題の大半がこの型**（台帳 #01〜#15）なので、隠した B の構造（溶けて消えた / 本人が別人 / 実は昼 / 高さの取り違え…）を台帳の 15 件と一つずつ突き合わせる
- Web 検索（Codex `--search exec`）で類題を引く。**仕組みの一致だけ**（同じ実在の仕組みを真相の背景に使う投稿問題があるが、コア・問題文・場面が異なり着想元でもない）は取り下げ理由にせず、人間ゲートの判断材料として出す（U17 の判断・2026-09-20: ラテシンの「猫よけペットボトルの収れん」と仕組みが重なったが採用）。有名問題（classic / known）との一致は構造ごと捨てる
- 借りてよいのは型と仕掛けの構造まで。モチーフ・真相・問題文は新規。着想元が外部にあると分かった案はここで取り下げる（`source_note` に出典を書くと `validate.py` が NG にするのは意図どおり）
- **コアが「よくある構造」（差し引きの計量・数字や物のすり替えのような算数的・定番トリック）に乗っている懸念があるときは、ゴール A（コア宣言の提示）の前に Web 照合を先行する**（21-4a-3 U20 の巡: 素材化まで済ませた後の照合で、らてらての投稿問題とコア構造が同一と判明し、素材の差し戻しになった。コアゲート前の 1 クエリで防げる手戻り）

### 工程 9: 素材化と機械検査

- `stock_items.py` の 1 問（`_item(...)`）を書く。`puzzle_type` を宣言した型にし、管理項目 `core` にコア宣言をそのまま入れる。`source_note` は「完全オリジナル」宣言 + 型 + モチーフ → 連想 → 逆にした常識（story は物語の一文要約と隠した B）（既存の問の書きぶりに倣う）
- `fact_sheet` に**核心の定義文（「影」= レントゲンの影、「打つ」= 麺を打つ、story なら B そのもの）を書かない**。出題者はシートの文をそのまま補足に引用するため、定義文があると 1 問目の返答で正体が漏れる（21-4a-2 の U01 で実測: 定義文あり = ほぼ全応答で漏れ / 「〜ではない」「〜の中にある」の周辺事実だけ = 漏れ 0）。核心は `truth` にだけ書き、シートは否定形・位置関係・時系列・「関係ない事項」で組む。出題者は truth を根拠に はい / いいえ を判断できる
- `fact_sheet` は動線の各質問に答えられる事実 + 「問題に関係ない事項」の明示。`expected_questions` は最短ルートの質問 + 引っかけ（誤認先を深掘りする質問。「いいえ」）+ 無関係 + 正解宣言（平叙文で真相を言い当てたもの）を混ぜる。`play_example` の 3 往復は取っ掛かりの質問から始め、1 つは「はい」
- `hook`（つかみ帯）は**必ず「？」で終える**（2026-09-26 の素材の全数レビューでユーザー決定。今後のすべての問に適用）。上限 14 字・目安 12 字前後で、「？」も字数に含める。`validate.py` が「？」で終わらないフックを NG にする（新しいバッチへ `validate.py` をコピーすれば検査も引き継がれる）
- **問題文の語を 1 つずつ真相と突き合わせる**。動作・感情の語（帰る・泣く・笑う・頭を下げる・満足そう）ごとに「真相のどの事実がこれを起こすか」を言えるか確かめる。言えない語・矛盾する語（問題文「帰っていく」に対し真相「仕事へ向かう」）は問題文か真相を直す（21-4a-2 U11 の指摘）。**時制も合わせる**: 真相が「常にそうしている状態」なら問題文は状態形（「書いている」「毎朝〜する」）、一回の出来事なら過去形（「書いた」）。「書いた」と書くと読者はリアルタイムの一回の行為として読む（21-4a-2 U11 の指摘）
- 想定質問に**境界の質問を置かない**。コアの反転をそのまま聞く形（「直した人ですか？」「氷鬼ですか？」）は出題者の返答が「はい」と「正解です！」で揺れる。部分を聞く形（「修理に関わりましたか？」「鬼ごっこの仲間ですか？」）か、真相を全部言う平叙文（正解宣言用）のどちらかにする
- `validate.py` → `probe_test.py --only <no>` → `leak_count.py`（核心語辞書に 1 行足す）→ `generate.py --dry-run`（手順は README）。プローブの不一致は確定事実シートの穴として直す。プロンプト側の修正は `master_prompt.txt` の正を守る

## 2. 提示前の自己検査（この 8 行を会話に書く）

1. コア宣言: 1 文・型の様式どおり・一つ
2. 正解判定: 何を言われたら「正解です！」か（1 文）
3. 動線: 取っ掛かりの語と最短ルート（質問 3〜5 個。story は A 側・C 側の 2 本）
4. 現実性: 使った知識の範囲・架空設定なし・誰も死なない（story は死・別れの題材可）
5. 照合: 台帳の該当行（なし / #NN の構造を借りた）と、記憶にある有名問題との違い
6. 型と難易度（根拠付き）
7. 手がかりの棚卸し: 草案にあった手がかりの一覧（A / B の別）と、残したもの・削ったもの・削った分をどの質問に回したか
8. 文の成立: 因果の受け皿（仕事・場面・読み手のどれを置いたか）と、問題文の語・時制が真相と一致していること

## 3. 失敗パターン（両型共通。型固有の分は分冊）

- **制約から逆算する**: 「オリジナルであること」「〜という条件を残すこと」から書き始めると、コアを決める工程が飛ぶ。条件は工程 7 と 9 で検査するものであって、出発点にしない
- **知識クイズ**: 「実は〜という性質がある」が答えの中心になる（周極星・特定の法律・業界慣習）。回答者が問題文から推理して気づけないなら捨てる
- **コアが複数**: 「勘違いした」「実は別人」「実は昔の話」が同時に入る。一つに絞るか、物語復元型なら B を一つにする
- **語の置き換えだけの改変**: 例として見た問題の登場人物・舞台を変えただけの案。着想元が外にある時点で落とす
- **不思議を盛りすぎ**: 逆を 2 つ以上足して問題文が矛盾だらけになり、取っ掛かりが消える
- **動機・感情・習慣で説明する反転**（21-4a-2 U11「時計を合わせていた」・U14「種なしスイカの売り文句」・21-4a-3 U15 の巡の story 案 2 件「留守宅の防犯」「故郷の砂」）: 反転後が「〜のためにそうしていた」で終わると、仕掛けがあっても落差が小さい。反転後は**何が起きたか・どういう仕組みか**が言える形にする
- **手がかりの置きすぎ**（21-4a-2 U01 初稿 / 21-4a-3 U16 初稿）: 対称形・丁寧語・「同じ相手」・登場人物の属性で真相のカテゴリが問題文だけで絞れた。コアが良くても A の手がかりが 2 個以上あると易しくなる。工程 4.5 で削る

## 4. レビューの受け方（人間ゲート）

- 指摘は「**問題の修正**」（その問だけ直す）と「**スキルの修正**」（同じ失敗を次の問でも起こす手順の穴）に分けて記録し、スキルの修正は本ファイル（型固有なら分冊）に反映してから次の問へ進む
- レビューは「コア宣言 → 問題文 → 素材一式 → プローブ結果（review.html）」の順。コア宣言で落ちた案は素材を直さず工程 1 か 2 に戻る
- **1 問は 2 ゴールに切る**（21-4a-3 U16 の教訓。`/goal` の Stop フックは「承認待ちの停止」を未達と判定して止まらない）: ゴール A = 工程 0〜3（コア宣言の提示まで。ゴール文の完了条件を「コア宣言と自己検査 1〜2 を会話に提示」にする）→ 人間ゲート → ゴール B = 工程 4〜9 + 機械検査 + 記録 + コミット。**ゴール B の完了条件も「素材一式とプローブ結果の提示 + コミットまで」で切り、素材の人間ゲートと指摘の反映は含めない**（21-4a-5 U20 の教訓: 「指摘を反映する」を入れると提示後の返答待ちが未達と判定され、Stop フックが止まれない。指摘の反映・push はユーザーの返答後に通常の会話か次のゴールで行う）
- 判定・取り下げの経緯はバッチの `STATUS.md` に残す
