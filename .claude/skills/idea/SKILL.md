# アイデアスキル(idea)

意思決定**前**の事業アイデアを `docs/ideas/` で捕捉・醸成するスキル。
**ルールの正は `docs/ideas/index.html` セクション 4**(単位・6 ステータス・2 層構造・終了規律・レーン)。本スキルは手順と迷いやすい分岐だけを持ち、矛盾したら index.html が勝つ。

**レーン**: `docs/ideas/` 配下で閉じる限りアイデアレーン(常に並行可・宣言不要)。本スキルの起動はアイデアレーン宣言を兼ねる。「待機 → 採用」の転記だけは development-plan / 事業戦略書に触れるため開発レーン作業(本スキルは転記下書きの用意まで)。

**ファイル**: 1 アイデア 1 ファイル `docs/ideas/<slug>.md`(テンプレート `_template.md`)。MD が唯一の正。深化したら詳細 HTML `<slug>.html` を作り、整理された現在形はそちらへ移す(MD の要旨はリンク 1 行に置換)。**どのモードも、終わったら必ず `index.html` の表を更新する**(閲覧層の同期は本スキルの責務)。

## モード判定

- 「アイデアがある / 思いついた / メモしておいて」 → **捕捉**
- 「〜の壁打ちをしたい / 〜を詰めたい」 → **壁打ち**(対象未指定なら index.html の「今動ける」から候補を提示)
- 「棚卸し / 条件待ちの確認」 → **棚卸し**

## 1. 捕捉モード(目標 1〜2 分)

1. 殴り書きを聞く。**追加質問は最大 2 つまで**、タイトルと要旨が作れない場合のみ(単位の曖昧さは問わない。整形は醸成の仕事)
2. `_template.md` から `<slug>.md` を作成: status=inbox、原文メモに**発言を原文のまま**保存、要旨 3 行程度を Claude が書く
3. **要旨を復唱**して認識ズレを確認(ズレたら要旨だけ直す。原文メモは触らない)
4. index.html の「今動ける」表に 1 行追加

壁打ち中の割り込み捕捉も同じ手順(ただし復唱は一言で済ませ、すぐ本筋に戻る)。

## 2. 壁打ちモード

**開始**: 対象の MD(+ 詳細 HTML)を読んで文脈復元。原文メモにも目を通す(要約で削れたニュアンスの回収)。

**観点リスト**(全部やる必要はない。足りない観点を Claude が選んで振る):
① 視聴者価値・企画の面白さ ② 収益との接続(事業戦略書との整合) ③ 既存資産との関係(既存セット・基盤・ストック運用とのシナジー / カニバリ) ④ 実現手段とコスト(初期・運用) ⑤ リスク・不確実性 ⑥ MVP スコープ(あえて作らないもの) ⑦ 採用判断に足りない情報は何か

**壁打ち中に何か出てきたら 3 パターン判定**(Claude が判定を提案する):
- 親の実現に必要なもの → 親ファイルの前提条件リストへ(独立させない)
- 独立の価値があるもの(親を見送っても単独でやる価値) → その場で inbox 捕捉 + 相互リンク。**醸成はしない**
- 親アイデア自体の変化(ピボット) → 新ファイルではなく本体を書き換える

脱線の方が重要になったら、元アイデアを終了規律で明示的に着地させてから乗り換える(暗黙の混線禁止)。

**終了規律(必須チェックリスト)**:
1. ステータス着地: 醸成中のまま / 再醸成待ち(+condition 必須) / 待機(+condition 必須) / 採用 / 見送り(+理由)
2. 壁打ち記録に蒸留を追記(論点・判断・積み残し。会話ログは貼らない)
3. 要旨(or 詳細 HTML)を最新化
4. 内容が MD の可読性を超えたら(構成図・多セクションが必要になったら)詳細 HTML へ昇格
5. index.html の表を更新
6. git コミット + push(日本語メッセージ・pull --rebase)

**着地の使い分けで迷ったら**: 「条件が満たされたとき何をするか」で決める。壁打ちを再開する = 再醸成待ち(まだ決めていない)、転記するだけ = 待機(決めた)。「○○したら検討しよう」は原則**再醸成待ち**(実行の約束ではなく再判断の約束)。

## 3. 棚卸しモード

1. index.html の「条件待ち」表の条件列を上から順に確認
2. 満たされたもの: 再醸成待ち → 醸成中へ戻して壁打ち再開を提案 / 待機 → 転記下書きを用意し、開発レーンでの転記を促す
3. 「今動ける」に長期滞留している inbox があれば、壁打ちするか見送るかを問う(墓場化防止)
4. index.html を更新してコミット + push

## 落とし穴

- 壁打ちで技術検討(構成・コスト)に踏み込むのは歓迎だが、成果物は**採用判断のための検討記録**であり設計書ではない。採用時に docs/app・docs/infra へインプットとして引き継ぎ、設計 Fix はそちらで行う(詳細 HTML には「設計書に非ず」の位置づけを明記)
- 再醸成待ち・待機で condition が空のままにしない(構造的に眠りっぱなしになる)
- MD と HTML に同じ情報を二重に書かない。整理された現在形の置き場は常に 1 箇所(浅いうちは MD 要旨、昇格後は詳細 HTML)
