# 問題ストック補充スキル(quiz-stock-replenish)

logic-training-1 セットの問題ストック(`quiz_stock_items`)を、16-2 初期整備(2026-08)で確立した品質・手順で補充するためのスキル。
運用ルールの正は `docs/app/operation.html` セクション 3(在庫確認クエリ・補充閾値 = 未使用 7 問/組以上・著作権ガイドライン)、フィールド仕様の正は `docs/app/generators/gpt-quiz-multicut.html` セクション 5。本スキルはそれらに「同品質で量産するための勘所」を足すもので、矛盾したら設計書が勝つ。

**昼スロット(noon = L3 / standard・フェルミ推定)は 16-4d(2026-08-24)で当分停止中**(スキップ率の高止まりによるユーザー決定。経緯・凍結範囲は `docs/app/sets/logic-training-1.html` 冒頭の注記が正)。**補充対象は朝(L1 / light)と夜(L1 / deep)の 2 組のみ**で、L3 / standard は在庫確認で数字が小さくても補充しない(既存在庫は凍結・残置)。セクション 3 の昼の執筆勘所は再開時の参照用として残している。

**資材の置き場**: `content/quiz-stock/<set_code>/<バッチ名>/`(git 管理)。バッチごとに自己完結の資材一式 — 単一ソース `stock_items.py`・検証 `validate.py` / `verify_logic.py`・生成 `generate.py`・リサーチ `research*.md`(source_note が参照する出典台帳)・投入した `insert_quiz_stock.sql` — を置く。参照実装は初期整備の `content/quiz-stock/logic-training-1/2026-08-initial/`。補充時は最新バッチの一式を新しいバッチディレクトリ(`2026-08-w3` 等)へコピーして同じ流れを回し、**投入完了時にディレクトリごとコミットする**(`review.md` は generate.py の派生物のため gitignore 済み・コミットしない)。plans/ は使い捨てスクラッチ用で、ストック資材は置かない。

## 0. 在庫確認(入口)

operation.html セクション 3 の在庫確認クエリ(16-3b 拡張版)で「型 × 難度」ごとの在庫を確認し、7 問を下回る組を補充対象にする。**ただし L3 / standard(昼)は 16-4d で停止中のため、数字にかかわらず補充対象にしない。**quiz-prebuilt 方式では**「未使用かつビルド済み」(`unused_built`)を在庫と数える**。`unbuilt` 列が 0 以外なら投入済みのビルド漏れなので、補充より先にセクション 7 のビルドを終わらせる。再利用 WARNING・未ビルト WARNING がログに出ていたら優先対応。

## 1. リサーチ(Codex 委譲)

- Codex に Web リサーチを委譲する。**Codex 環境に web_search ツールはない**。`config: {"sandbox_workspace_write.network_access": true}` でネットワークを許可し、curl でのページ取得・検索(DuckDuckGo は bot challenge が出ることが多い)を指示する
- 成果物は「類型・解法構造の要約・出典 URL」のみ。**問題文の転載は禁止**(著作権: アイデア・解法構造は保護されず、表現は保護される)
- **Codex の裏取りは「Wikipedia 級のページで古典と明記」に偏り、folklore 級なぞなぞをほぼ全部『未確認』にする**(16-2 の実績)。これは基準の取り違えであり、採用可否は Claude が判断する: **作者不詳 + 複数の独立サイトに流布 = folklore 級 = 安全側**。Claude 自身の WebSearch で流布例 URL を 1 件以上直接確認し、それを証跡にする
- 除外するもの: 特定サイト・書籍固有の創作問題(アイデア自体に強い独自性があり出所が特定できるもの)、実在企業名を冠した断定(「〇〇社の入社試験」)、解釈が割れて炎上しうる問題(男女パラドックス等)

## 2. 執筆(Claude)

単一ソース(`stock_items.py` 形式)に 1 問 = 1 dict で書く。フィールドと上限:

| フィールド | 上限 | 表示場所 |
|---|---|---|
| hook(つかみ) | 20 字 | **キャプション 1 行目のみ**(16-4c で動画からは外れた。動画上部の「つかみ帯」はスロット別の `slot_hook` = `prompt_configs.parameters` 側の可変値) |
| hint(ヒント) | 20 字 | カット 3 の吹き出し(カウントダウンと同時) |
| question(問題文) | 90 字 | 全カット常時表示 |
| answer(答え) | 30 字 | キャプションのみ(動画に出さない) |
| explanation(解説) | 80 字(L3 のみ 240 字) | キャプションのみ |
| coach_comment(コーチの一言) | 30 字 | キャプション末尾 |
| tags | 10 字 × ちょうど 3 | 記録用 |
| summary(出題要旨) | 100 字 | 記録用・重複管理の単位 |
| illustration_scene(イラストの情景) | 200 字 | 問題文の下に配置するイラストの生成指示文 |

※ hint は 16-2 中のカット構成変更(問題カット廃止 → 考える + 動的ヒント化)で追加。カット構成・フィールド仕様は方式設計書へ正式反映済み(16-2b。2026-08-07)で、方式設計書セクション 5・8.1 が正。

### 全フィールド共通の勘所(16-2 人間レビューで確立)

- **問題文**: 答え・解法がそのまま見える書き方をしない。難度はひと手間の足し引きで調整する — 例: 動物ダジャレは並び順をシャッフルする(そのままの順は簡単すぎ)、「トラが9匹」→「9匹の虎」の語順替え、文字なぞは漢字表記にして「ひらがなに直す」ステップを足す。**並べ替え系は途中に答えの部分文字列が現れないか必ず確認**(「カメ・サイ・ラクダ」は「サイカメラクダ」に"カメラ"が漏れる)
- **つかみ(hook)**: 解き方のヒントを言わない(それは hint の役割)。問題文と同じ情報の繰り返しも NG。雑学フック(「虫は世界に100万種いるらしいぞ!」)や驚きの一言(「壊しても使えるのか!」)が有効。数字を出すなら実数 + 「らしいぞ」で断定を避ける
- **ヒント(hint)**: コーチのキャラ(体育会系だが威圧しない・前向き)を必ず出す — 「〜だ!」「〜みろ!」「〜だぞ!」。カウントダウン中の最後の後押しなので、ある程度直球でよい
- **コーチの一言**: キャプションで答え・解説まで読んだ人への締め。キャラ必須。説教にしない
- **別解への態度**: 潰すより取り込む(「とればとるほど増える」は年 + 写真を両方正解に)。取り込む場合は表記も整合させる(「取る/撮る」の揺れはひらがな化で吸収)。取り込めない別解は解説で軽く触れるか、問題文の条件で閉じる
- **表記の使い分け**: ひらがな/漢字は難度調整のレバー。問題文で変換ステップを要求するなら、hint がその変換を後押しする組み合わせにする(例: 問題「弟」× hint「ひらがなで書いてみるんだ!」)
- **つかみの NG 実例(16-2 昼レビュー)**: 問題文の言い換えそのまま(「自販機、何台あると思う?」≒ 問題文)は NG。答えの単位とズレる語も NG(時間の答えに「衝撃の額」)。「実は…」等の同型パターンを近い出題順で繰り返さない
- **定型句・数値の重複回避**: hint の言い回し(「何人に1〜か見積もれ!」)や答えの数値(約2000人が 2 問)がスロット内の近い出題順で重複しないようにする。数値は丸め方で差別化できる(2000→1900 は実勢にも近かった)
- **隣接回避は型だけでなく題材も**: 通勤×2 問のような題材かぶりも隣接させない。移動は問題番号を保ったままリスト順(= INSERT 順)だけ変える(A12・B08 方式)

### イラストの情景の方針(ユーザー確定)

前提: **イラストは背景ではない**。問題文の下に独立した一枚絵として配置される(16-2 で確認。「背景イラスト」は過去の名残で誤り)。淡い環境描写の「壁紙」ではなく、主役がはっきりした構図で書くこと。

1. **答えの物は絶対に描かない**(タオルの問題にタオルを描かない・カメラの問題にカメラを描かない)
2. 基本構図は **「思い込みを絵で見せる + 大きな『?』」**(硬そうな岩に?・穴だらけで水が漏れるバケツ・「こわれもの注意」の箱に?・ティッシュを取ると減る)。視聴者の誤った前提を可視化して裏切る
3. **スロットの時間帯要素を必ず入れる**(朝日・昼の街・夜の照明)。抽象構図(宇宙から見た地球等)でも朝日などで時間帯を出す
4. 人物は後ろ姿か遠景まで・顔は描かない(セット共通ルール)。問題の題材の動物・物は積極的に描いて楽しくしてよい
5. **絵が答えをバラす間接経路に注意**: 影が答えの問題で朝日のランナーを描くと影が描画される → 「地面に影は描かない」と明記するか題材を変える。カレンダーの明日のマスに?も答えバレ
6. 視線を答えから散らす構図も有効(文字数えの問題 → たくさんのオモチャで遊ぶ子どもたち)
7. **答えが数値の問題(L3)は題材を直接・大量に描いてよい**: 数は答えをバラさない。規模感は「無限に並ぶ定食」「スプーンとお皿の山」のような誇張が有効で、ユーザーは遠回しな連想(理髪店のサインポール・ベビー靴)より題材の直接描写(髪をとかして抜ける・新生児室のベビーベッド群)を好む
8. 顔 NG は構図で回避する: 「後ろ姿の人が髪をとかす」「赤ちゃんの顔は描かない」のように後ろ姿指定か描写除外を情景文に明記する

## 3. スロット別の執筆勘所

### 朝 = L1 / light(なぞなぞ・言葉あそび)

- 広く流布した定番なぞなぞのみ(ダジャレ・文字位置・文字数え・逆説・言い回し)。テンポよくクスッと笑えて 10〜30 秒で解ける規模
- 類型を分散させ、**同型(文字数え等)を出題順で隣接させない**(出題順 = INSERT 順 = 単一ソースのリスト並び。必要ならブロックを並べ替える)
- 懐かしさ(子どもの頃に聞いた)はコメント誘発の武器。ただし幼稚になりすぎないよう文面は大人向けに書き直す

### 昼 = L3 / standard(フェルミ推定) — **16-4d(2026-08-24)で当分停止中。補充しない。以下は再開時の参照用**

- **フェルミ推定を維持する**(2026-08-01 ユーザー決定。「意外な数字クイズ」への拡張は不採用)
- 題材は「身近で意外」を最優先: 一生の睡眠 = 約25年・一生に歩く距離 = 地球3周半、のように**自分ごと + 規模の驚き**があるもの。16-2 初期整備では施設数系(駅・ポスト・美容室)より生活実感系が好まれた(ただし下記の捻り方針以降は、施設数系でも捻った分解が要る題材なら可)
- **問題は「捻った分解」を標準にする(2026-08-07 ユーザー決定・次回補充から適用)**: 仮定 = 答えの量そのもの(スマホは1日何時間? 睡眠は1日何時間?)という**直接換算型は標準にしない**。**非直接的な仮定を最低 1 つ**経由する問題を選ぶ。例: 「日本国内の電柱の数は?」= ①人が住みインフラのある土地を国土の約 20% と仮定 ②道路沿いに 50m 四方(2,500 m²)に 1 本の密度と仮定、の 2 段の捻りで解く。16-2 の初期 42 問は直接換算型が多いが承認済みのため置き換えない
- **解説は 5 ステップ構造で書く(2026-08-07 ユーザー決定・捻り型とセット適用)**: ①**前提**(問題の定義・範囲を確定)→ ②**ベース**(何を基準に数えるかを宣言して式の骨格を立てる。例: 自動車台数 = 世帯数×平均所有数)→ ③**分解**(非直接的な仮定を置いて要素を具体化)→ ④**計算** → ⑤**実勢チェック**(「実際は約〜とされる」と桁の乖離を確認)。複数の解法があっても 1 つの手法を最後まで通す。⑤に使う実勢値はリサーチ段階で出典付きで確認しておく
- **explanation の上限は L3 のみ 240 字**(5 ステップは 80 字に入らない。16-2b で方式設計書セクション 5 へ正式反映済み)。DDL は TEXT/JSON のため変更不要・キャプション専用フィールドのため版面影響なし。次回補充時は validate.py の上限も 240 字(L3 のみ)に追随させること
- 答えは「約〇〇(目安)」の幅表現必須。解説に使った仮定と「〇〇×〇〇」の式の形を必ず入れる(80 字内。validate.py は × を必須チェックするので ÷ だけの式にしない)
- **仮定と固定値を書き分ける**(2026-08-07 ユーザー決定): 自分で置く数は「〜と仮定すると/〜と仮定。」と明示し、固定値(365日・24時間・人口1.2億)や既知の統計(就業者数・出生数)は事実として書く。既知の平均値しか使わない問題(抜け毛の 10 万本・毛周期)には仮定表現を付けない。答えと式の数字は一致させる(ズレるなら「25〜27年ほど」の幅表現にする)
- 公式・物理定数を与えて計算させる問題は L3 ではない(15-13 の矯正を踏襲)
- 算数は必ず verify_logic.py に検算を追加して機械検証する

### 夜 = L1 / deep(とんち・水平思考・ひっかけ)

- 古典のみ: 一休咄(屏風の虎・このはし)、Situation puzzle の定番(エレベーターの男・しゃっくり)、故事(ゴルディアスの結び目・ソロモンの審判)、定番ひっかけ(ライオンの部屋・バスの運転手・ろうそく残数)
- **プラットフォーム配慮の置き換えを恐れない**: 銃 → 大きな物音、死刑囚 → ゲームの扉、など構造を保ったまま表現を安全にする(著作権的にも書き直しの一部)
- 水平思考系は答えが「想定解」であることを意識し、問題文の条件で別解を塞ぐ(「中身を知る店長が必ずハズレを開ける」等の前提を明記)
- 「じっくり考えたら直感がひっくり返る」「そうきたか」の読後感を狙う

## 4. 機械検証(執筆後に必ず)

- `validate.py`: 全フィールドの文字数・tags 数・L3 の「約〜(目安)」形式・source_note の URL 有無
- `verify_logic.py`: L3 の算数(全問検算)・文字なぞの文字数(count で機械確認)・ブルートフォース可能な論理問題は全列挙で一意解 + 答え一致を確認
- **執筆直後の自己点検を省かない**: 16-2 初稿で「両ケース矛盾で解なし」の論理破綻が実際に発生した。なぞなぞ・とんちの「想定解」は機械検証できないため、そこは人間レビューが唯一の砦であることをレビュー依頼時に明示する

## 5. 人間レビュー

- **1 問ずつチャットで**提示する(ファイル一括レビューは好まれない)。項目名は日本語(つかみ・ヒント・問題文・答え・解説・コーチの一言・タグ・出題要旨・イラストの情景・出典メモ)+ 表示場所の補足を付ける
- 気づいた問題(答えバレ・重複・別解リスク)は**先回りして自己申告 + 代案**を添える
- 修正が入ったら単一ソースへ反映 → validate/generate を回してから次の問題へ。承認済み問題の勝手な変更はしない
- 横展開指示(「他の〜も同様に」)が出たら対象を列挙して一括適用し、適用先を明示する

## 6. 投入(レビュー全問承認後)

- `generate.py` が出力する `insert_quiz_stock.sql` を使用(set_id は `set_code` サブクエリ解決でローカル/Aurora 共通)
- **`content_key`(`{slot_code}-{3 桁連番}`。V007 = 16-3d 決定)は generate.py の SQL がスロット内の既存最大連番 + 1 を適用時に解決する**。手動採番しない・両環境へ同じ SQL を適用する(NOT NULL のため採番漏れは投入時に必ずエラー)
- 事前に Aurora の `quiz_items.summary` 全件と突合し、既出題と解法構造・題材が重複しないことを最終確認
- ローカル: `docker exec -i acps-mysql mysql --default-character-set=utf8mb4 ...`(utf8mb4 指定必須)。事前にトランザクション + ROLLBACK でドライランする
- Aurora: Data API(`aws rds-data execute-statement`)。auto mode classifier にブロックされる場合はユーザーに許可を求める
- 投入後: 在庫確認クエリで件数・内訳を確認し、`docs/development-log.md` に補充記録を残す

## 7. 動画ビルド・レビュー・配置(quiz-prebuilt。投入後に必ず)

投入しただけの行(`video_s3_key IS NULL`)は出題候補にならない。技術設計の正は `docs/app/generators/quiz-prebuilt.html` セクション 8、運用ルールの正は operation.html セクション 3 手順 5。ツーリングは `content/video-build/logic-training-1/`(使い方は同ディレクトリの README.md。生成物は `work/` で gitignore)。

1. **プロンプト書き出し**: `export_prompts.py`(実行は `cd services/image-batch && uv run python ../../content/video-build/logic-training-1/export_prompts.py`。以下の Python 実行も同じ uv 環境)
2. **イラスト生成(Codex imagegen 委譲)**: `work/prompts/<id>.txt` の全文を渡し、imagegen で生成して `work/illustrations_raw/<id>.png` へ保存させる。**「?」以外の文字・数字・記号の混入を Codex 自身に確認させ、混入時は再生成」を指示に含める**(1 問通し確認でも初回混入 → 再生成が実際に発生した)。プロンプト末尾に **3:2(1536x1024)の明示行**が入っている(16-5 追加)。imagegen は指定しないと 16:9 前後で出力が揺れ、3:2 以外は次の intake で左右が捨てられるため、**保存されたファイルのサイズが 1536x1024 かを Codex に確認させ、違えば再生成させる**
3. **取り込み → ビルド**: `intake.py` → `build.py`。build.py は Docker 実行(README の docker run 例が動作確認済みの形: `~/.aws` 読み取りマウント + `LOCAL_DB_HOST=host.docker.internal` + `--user $(id -u):$(id -g)`)。イラスト未配置の行は自動スキップされるので部分ビルドでよい
   - `intake.py` は 3:2 でない素材を **WARNING + 切り捨て率**で報告する。被写体が端にある問題(操作パネル等)は切り捨てで見切れるため、警告が出たら該当問題のイラストだけ再生成する
   - レンダラー変更を既ビルド分へ反映する場合は **`build.py --rebuild`**(ビルド済み行を対象・BGM は `video_audio_asset_id` を引き継ぎ LRU を消費しない)
4. **全数人間レビュー**: `review_sheet.py` → `work/review.html`。観点はイラスト(文字混入・画風・情景適合)・版面・音。NG は imagegen 再試行または `illustration_scene` 修正(DB 更新)→ 再ビルド
5. **配置**: 承認 id を `approved.txt` に列挙 → `publish.py --dry-run` で `upload_prebuilt.sh` / `update_prebuilt.sql` を確認 → 本実行(S3 アップロード + ローカル MySQL 反映)→ Aurora へ `work/update_prebuilt.sql` を Data API で適用。**Aurora SQL は安定キー(set_code + question_text・BGM は s3_key)で解決する形式・S3 ファイル名も id ではなく `content_key`**(ローカルと Aurora で AUTO_INCREMENT id が一致しないため。id 直指定の SQL・id 入りの S3 キーを作らない)。適用後は更新行数 = 承認件数を確認
6. **締め**: 在庫確認クエリ拡張版で `unbuilt` = 0 を確認し、ツール・台帳の変更をコミット
