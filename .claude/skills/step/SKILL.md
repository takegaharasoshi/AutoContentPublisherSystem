# ステップ着手スキル(step)

計画書のステップ着手を 1 つの入口に絞り、**起動 = レーン宣言 + `/goal` の完了条件宣言**とするスキル(Phase 19-2 で導入)。
レーン判定・並行作業ルールの正は `docs/plans/index.html`、ゴール運用の検討経緯は `docs/ideas/claude-code-loop-goal-skills.html`。矛盾したら index.html が勝つ。

## 0. 前提(/goal の起動制約)

`/goal` は **Claude 自身・スキル・フックからは起動できない**。ユーザーの入力でのみ起動する。したがって本スキルの責務は「テンプレを埋めた `/goal` 行を提示するところまで」で、**goal が立つ(ユーザーが行を打つ)まで工程に着手しない**。ユーザーは `/goal`(引数なし)で現在の設定を確認できる。

## 1. 引数の解釈(レーン判定の一次振り分け)

| 引数の形 | レーン | 読む計画書 |
|---|---|---|
| `16-12` のようにステップ番号のみ | 開発レーン | `docs/plans/development-plan.html` |
| `logic-training-1 R-1-2` のように set_code + 識別子 | セットレーン(そのセット) | `docs/plans/<set_code>.html` |

- set_code の一覧は `docs/plans/index.html` セクション 1(現在: fantasy-animals-1 / logic-training-1 / pref-ranking-1)
- 引数がない・計画書に該当ステップが見つからない場合は、推測で進めずユーザーに確認する

## 2. 手順

1. **計画書を読む**: 該当ステップの「内容」「完了条件」「人間ゲート」「停止点・上限」(4 項目様式。正は `docs/plans/index.html` セクション 5)を確認する。前提ステップが未完了なら着手可否をユーザーに確認する
   - **旧形式フォールバック**(Phase 19-4): 「完了条件」のないステップは、「内容」から完了条件(機械検証できる形)・人間ゲート・停止点の案を作り、ユーザーの確認を得てからゴール行に埋める。人間ゲートがステップの途中に入る・20〜30 ターンを超えそう・2 レーンをまたぐなら、その場で分割を提案する。確定した内容で計画書のステップを 4 項目に書き換えてから着手する(書き換え自体はそのセッションで行う)
2. **対象外の判定**: ステップが「(ユーザー)」「ユーザー判断」のもの(目視確認・go/no-go 判断等)は **goal 対象外として断る**(自走できない)。週次補充は本スキルではなく補充スキル(`/quiz-stock-replenish` / `/ranking-stock-replenish`)の入口から行う
3. **触るパスの列挙とレーン判定**: ステップで触るパスを列挙し、`docs/plans/index.html` セクション 2 の判定表に当てる。**セット計画書のステップでも、開発レーンのパス(`services/` `shared/` `infra/` `database/`・共通設計書・CLAUDE.md)が 1 つでも入るなら開発レーンとして扱う**(このとき「開発レーンは常に 1 セッション」の制約が働くため、他に開発レーンのセッションが動いていないかユーザーに確認する)
4. **確認待ちリストの照合**(Phase 19-5 で導入。ルールは `docs/plans/index.html` セクション 5.2): 開発レーンなら開発計画末尾の「確認待ちリスト」、セットレーンなら当該セット計画書の「確認待ちリスト」を読み、**手順 3 で列挙した触るパス・このステップで起きる出来事(push・デプロイ・ビルド等)がトリガー列に該当する行**を拾う。該当行があれば、その「確認内容・判定基準」の確認と「結果」列への記入(日付 + 結果 + 記録へのリンク)を**ゴールの完了条件に含める**。該当なしなら「確認待ち: 該当なし」と一言宣言する(照合したことを残す)。リストの節が無い計画書は該当なしとして進む
5. **レーン宣言**: 「開発レーン: 16-12」「セットレーン: logic-training-1 R-1-2」の形で、レーンと触るパス・確認待ちの照合結果を会話冒頭で宣言する
6. **/goal 行の提示**: セクション 3 のレーン別テンプレに番号・名称・(セットレーンなら set_code)を埋め、コードブロックで提示して「この行を打ってください」と伝える。ステップに完了条件・停止点が書かれていれば、テンプレの汎用条件をその記載で置き換える(テンプレは骨組み、計画書の記載が正)。手順 4 で該当した確認待ち行があれば「(n) 確認待ちリストの『<対象>』を確認し結果列に記入」を完了条件に足す。**goal が立つまで工程に着手しない**(展開文からの自動起動は効かない前提で、必ず提示 → ユーザー起動の流れを取る)

## 3. ゴール文テンプレ

### A: 開発レーンのステップ実行

```
/goal 開発レーン・ステップ <番号> <名称>。完了条件: (1) 計画書の「内容」にある成果物が揃う、(2) 該当サービスの pytest が全パス(要約行を会話に貼る)、(3) infra/ を触った場合は cdk synth が成功、(4) 関連設計書と計画書(チェック・完了日・要点)を更新、(5) 日本語メッセージでコミット済み。services/ shared/ infra/ database/ を触った場合は push せず、差分を提示して確認待ちで終える。docs のみなら pull --rebase → push まで行う。cdk deploy・本番 DDL 適用・publish は行わない。or stop after 20 turns
```

### A′: セットレーンのステップ実行

```
/goal セットレーン <set_code>・ステップ <番号> <名称>。完了条件: (1) セット計画書の「内容」にある成果物が揃う、(2) ビルド・検証ツールの出力(build.py --dry-run / validate 等、該当するもの)を会話に貼る、(3) セット計画書(チェック・完了日・要点)とセット記録を更新、(4) 日本語メッセージでコミットし pull --rebase → push まで行う(content/ と docs/plans/<set> は CodePipeline を起動しないため push まで可)。S3 差し替え・Aurora / ローカル DB の更新・SNS 投稿設定の変更は行わず、レビュー用の成果物(プレビュー動画・review.html)を提示して終える。services/ shared/ infra/ database/ に触る必要が出たら手を止めて報告する(開発レーン行き)。or stop after 20 turns
```

- セットレーンでは**配置(S3・DB 差し替え)を人間レビュー後の別ゴールに切る**。レビュー承認後に配置用のゴールを改めて提示する
- 大きなステップを 1 本のゴールにしない(1 ステップ 1 ゴール。長引くなら分割を提案する)

## 4. ガードレール(ゴール実行中)

- **denylist**: `cdk deploy` / 本番 DDL 適用 / `publish.py`・`apply_aurora.py` の投入 / SNS 投稿 / Secrets への接触 / `docs/plans/` のルール変更 — ゴール文にかかわらず行わない
- **証跡を会話に貼る**: pytest 要約行・検証ツール出力・件数クエリの結果は省略せずそのまま貼る(/goal の evaluator は会話ログしか見ない)
- **コードを触るゴールは auto mode で走らせない**(push の許可プロンプトが「差分確認後に push」のゲートを兼ねるため)。夜間実行なら Ctrl+C できる端末で
- `services/` / `shared/` を触る push に至った場合は、push 直後に CLAUDE.md「Git 運用ルール」の D 定型行(CodePipeline 完走確認の /goal)を提示する
- **確認待ちの結果は必ず書く**: ゴール内で確認待ち行を確認したら、結果列に日付 + 結果を記入し、OK なら行を記録(`development-log.html` / `<set_code>-log.html`)へ移す。NG なら「NG 時の扱い」列に従い、追補ステップか課題として起こす(黙って結果列を空のままにしない)
- **ステップを新たに起こす・分割するとき**は `docs/plans/index.html` セクション 5.1 の起票チェックリストを通す(自セッション外の出来事は完了条件に入れず確認待ち項目へ)
