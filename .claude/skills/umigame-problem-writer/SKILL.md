# ウミガメのスープ作問スキル（umigame-problem-writer）

umigame-soup-1 の問題を **1 問ずつ** 作るための手順。21-4a（2026-09-04〜07）で「制約から逆算して書き、コア = 引っ掛けるポイントを決める工程を飛ばした結果、コアのない知識クイズを書いてしまう」失敗が出たため、note 記事 [ウミガメのスープ作問法](https://note.com/suekai0217/n/n35128e606a9b)（4 ステップ・良い問題の 3 条件・2 類型）を手順に固定し、**コア宣言を書けない案は問題にしない**ことを本スキルの一番のルールとする。

本スキルは作問だけを担う。素材 14 項目の仕様・字数・件数の正は `docs/app/sets/umigame-soup-1.html` セクション 4、機械検査は同バッチの `validate.py`、プローブテストは `probe_test.py`、投入 SQL は `generate.py`（使い方は `content/umigame-stock/umigame-soup-1/README.md`）。ここには重複記載しない。矛盾したら設計書・ツールが勝つ。

## 0. 原理（記事の要点。変えずに守る）

- 問題は「わからないストレス」と「解けたときのカタルシス」でできている。ストレスをカタルシスに変えるのは**納得感**。納得感を作るのが下の 3 条件
- **良い問題の 3 条件**: ① 答えの**コア**がハッキリしている（「ここで引っ掛けてやろう」という出題者の悪意が一つに定まっている。コアが定まると正解判定のタイミングが決まる）② **動線**がある（問題文の取っ掛かりから正解までの最短ルートが無理なく存在する。特に最初の質問が明確）③ **現実離れしていない**（架空設定・マニアック知識に頼らない。小中学校の知識までは可）
- **2 類型**: **物語復元型**（隠蔽。完結した物語 A→B→C から一部を切り出して出す。ミスリードなし、深いカタルシス）/ **意味誤誘導型**（改竄。言い換えで誤認させ、正させてカタルシスを生む。手軽で現在の主流）。どちらも正統。4 ステップは意味誤誘導型向け、物語復元型は「A→B→C を書いて B を抜く」が最も有効な切り出し
- 記事の結び「ロジカルなメソッドは存在しない。自由に作ってほしい」。手順は補助輪であり、**手順を全部踏んでもコアが立たない案は捨てる**（手順を踏んだことは採用理由にならない）

## 1. 工程（会話に「作問ログ」として全工程を貼る）

各工程の結果を下の見出しのまま会話に書く。レビューはこのログを「コア宣言 → 問題文 → 素材」の順に見る。**工程 3 でコア宣言が書けなければ工程 1 か 2 に戻る**（戻った回数と捨てた案も書く）。

### 工程 1: モチーフ（ランダム語から）

```bash
shuf -n 3 .claude/skills/umigame-problem-writer/motifs.txt
```

- 3 語を引き、1 語を選ぶ（引いた 3 語と選んだ理由を書く。3 語とも連想が広がらなければ引き直してよい。引き直しも書く）
- 既存問題・他者の自作問題・リサーチ台帳の題材から**始めない**（21-4a で「例として渡された問題」の登場人物を置き換えただけの問題を書いて取り下げになった。着想元が外にある案は工程 7 で落ちる）
- 20 問以上あるバッチで型が偏っているときは、選ぶ語を「動作・慣用句を持つ語（意味誤誘導向き）」「状況・場所（物語復元向き）」に寄せてよい

### 工程 2: 連想

- モチーフから **10 個以上**書き出す。観点: その物でする動作 / 使う場面・場所 / 関わる人 / 道具 / 慣用句・多義語 / 「ふつうはこう」という常識 / 困りごと
- ここで面白がらない。量を出す

### 工程 3: 言い方を変える → コア宣言

- 連想の 1 つを**具体化**（手を握る → アイドルの手を握る）または**抽象化**（麺を打つ → 打たれたもの）して、別の状況へ誤認させられる言い方を探す
- 見つかったら**コア宣言**を 1 文で書く。様式は固定:

  ```
  コア: 「<問題文中の語・状況>」を <誤認させる読み> と読ませる → 実際は <反転後の事実>
  ```

- コア検査（すべて Yes でなければ戻る）:
  - 「引っ掛けてやろう」と言える悪意が**一つ**あるか（複数のコアが混ざっていないか。混ざったら一つに絞る）
  - 反転後の事実を言い当てた瞬間に「正解です！」と宣言できるか（正解判定のタイミングが決まるか）
  - 答えが**知識の有無**で決まっていないか（知っていれば即答・知らなければ到達不能なら、それは知識クイズであってコアではない。21-4a の再々稿「一年中見える星座」がこの失敗）

### 工程 4: 不思議にする

- 誤認先の常識を **3 つ以上**列挙する（例: 握手会 → 「客が金を払う」「並ぶ」「一瞬で終わる」）
- そのうち 1 つの**逆**を問題文に足して状況を矛盾させる（握手して大金を得た）。足すのは 1 つで足りる。2 つ以上足すと動線が消える
- 問題文の草案を書く（この時点では字数を気にしない。「なぜ？」「どういうこと？」で締める）

### 工程 5: 動線検査

- **取っ掛かり**: 問題文のどの語から攻め始めるかを 1 つ決める（例: 「大金」/ 「反対方向」）
- **最短ルート**: 取っ掛かりから正解までの質問を 3〜5 個並べ、各質問に「はい / いいえ」で答えたとき次の質問が自然に出るかを見る。途中で「関係ありません」しか返せない質問しか思いつかない区間があれば、問題文に手がかりを足す
- このルートは工程 9 の `expected_questions` の骨（正解に向かう質問）になる

### 工程 6: 現実性検査

- 架空設定・特殊な職業のルール・地域限定の慣習に頼っていないか。使う知識は小中学校まで
- 「そう考えればよかったのか」と言えるか（回答者が自分で気づける）。言えないなら工程 3 へ
- セット固有の守り: **誰も死なない・事件が起きない日常の不思議**を基本にする（子ども向けアカウント。問題文の語感が強い動詞〔殴る・襲う・撃つ〕は避ける）。難易度は 1〜5 で自己申告し、根拠を書く

### 工程 7: 既存問題との照合

- `content/umigame-stock/umigame-soup-1/batch-01/research.md` の 30 件（コア列）と、台帳の「オリジナル性の基準」に照らす。**コアの構造が同じ**（例: 曜日名が馬の名前 / ホーム = 本塁 / 外科医は母親）なら捨てる。`fame: classic` の構造は語を変えても捨てる
- 自分の記憶にある有名問題（本家ウミガメのスープ・エレベーターの男・雪だるまのニンジン等）と同じ構造でないか、もう一度言葉にして確かめる
- 借りてよいのは型と仕掛けの構造まで。モチーフ・真相・問題文は新規。着想元が外部にあると分かった案はここで取り下げる（`source_note` に出典を書くと `validate.py` が NG にするのは意図どおり）

### 工程 8（物語復元型のみ）: A→B→C を書く

- 完結した物語を 3 段で書く（A: 状況 / B: 隠す出来事 / C: 結果）。**A→C を出して B を隠す**のが基本。C だけを出すのは難しくなるので難易度 4 以上のときだけ
- A と C の両方から攻められるか（動線が 2 本あるか）を確かめる。この型はストレスが大きいので、3 条件の検査を意味誤誘導型より厳しくかける

### 工程 9: 素材化と機械検査

- `stock_items.py` の 1 問（`_item(...)`）を書く。管理項目 `core` にコア宣言をそのまま入れる。`source_note` は「完全オリジナル」宣言 + 型 + モチーフ → 連想 → 逆にした常識（既存の問の書きぶりに倣う）
- `fact_sheet` に**核心の定義文（「影」= レントゲンの影、「打つ」= 麺を打つ 等）を書かない**。出題者はシートの文をそのまま補足に引用するため、定義文があると 1 問目の返答で正体が漏れる（21-4a-2 の U01 で実測: 定義文あり = ほぼ全応答で漏れ / 「〜ではない」「〜の中にある」の周辺事実だけ = 漏れ 0）。核心は `truth` にだけ書き、シートは否定形・位置関係・時系列・「関係ない事項」で組む。出題者は truth を根拠に はい / いいえ を判断できる
- `fact_sheet` は動線の各質問に答えられる事実 + 「問題に関係ない事項」の明示。`expected_questions` は最短ルートの質問 + 引っかけ（誤認先を深掘りする質問。「いいえ」）+ 無関係 + 正解宣言（平叙文で真相を言い当てたもの）を混ぜる。`play_example` の 3 往復は取っ掛かりの質問から始め、1 つは「はい」
- `validate.py` → `probe_test.py --only <no>` → `generate.py --dry-run`（手順は README）。プローブの不一致は確定事実シートの穴として直す。プロンプト側の修正は `master_prompt.txt` の正を守る

## 2. 提示前の自己検査（この 6 行を会話に書く）

1. コア宣言: 1 文・様式どおり・一つ
2. 正解判定: 何を言われたら「正解です！」か（1 文）
3. 動線: 取っ掛かりの語と最短ルート（質問 3〜5 個）
4. 現実性: 使った知識の範囲・架空設定なし・誰も死なない
5. 照合: 台帳の該当行（なし / #NN の構造を借りた）と、記憶にある有名問題との違い
6. 型と難易度（根拠付き）

## 3. 失敗パターン（21-4a の教訓。同じ道に入っていないか工程 3 で見る）

- **制約から逆算する**: 「オリジナルであること」「〜という条件を残すこと」から書き始めると、コアを決める工程が飛ぶ。条件は工程 7 と 9 で検査するものであって、出発点にしない
- **知識クイズ**: 「実は〜という性質がある」が答えの中心になる（周極星・特定の法律・業界慣習）。回答者が問題文から推理して気づけないなら捨てる
- **コアが複数**: 「勘違いした」「実は別人」「実は昔の話」が同時に入る。一つに絞るか、物語復元型なら B を一つにする
- **語の置き換えだけの改変**: 例として見た問題の登場人物・舞台を変えただけの案。着想元が外にある時点で落とす
- **不思議を盛りすぎ**: 逆を 2 つ以上足して問題文が矛盾だらけになり、取っ掛かりが消える

## 4. レビューの受け方（人間ゲート）

- 指摘は「**問題の修正**」（その問だけ直す）と「**スキルの修正**」（同じ失敗を次の問でも起こす手順の穴）に分けて記録し、スキルの修正は本ファイルに反映してから次の問へ進む
- レビューは「コア宣言 → 問題文 → 素材一式 → プローブ結果（review.html）」の順。コア宣言で落ちた案は素材を直さず工程 1 か 2 に戻る
- 判定・取り下げの経緯はバッチの `STATUS.md` に残す
