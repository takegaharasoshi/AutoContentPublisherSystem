# 候補ディレクトリ(logic-training-1・作問の 2 段階化 = 改修 R-3)

週次補充の **G1a(候補準備)→ 人間の選別 → G1b(完成稿準備)** で使う「候補」の置き場。
手順の正は補充スキル `.agents/skills/quiz-stock-replenish/SKILL.md`(セクション 1.5)、方針の経緯は
`docs/ideas/quiz-authoring-efficiency.html`、計画は `docs/plans/logic-training-1.html` 改修 R-3。矛盾したらスキル → 計画書の順に勝つ。

## 1. 置き方

```
candidates/
├── README.md            # 本書(形式・状態・集計規則・表示例・旧手順との対応表)
├── _template.md         # 1 候補 1 ファイルの雛形(コピーして使う)
├── tally.py             # 朝夜別の集計・追加数・仕上げ可否の判定・INDEX.md の生成
├── examples/            # 投稿対象外の検証例(example: true。実問題の承認記録・投入 SQL に混ぜない)
│   ├── w0-example-round1/       # 候補 14 / 14 → OK 朝 5 / 夜 4 → 追加 4 / 6
│   ├── w0-example-round2/       # 追加後 → OK 朝 7 / 夜 5 → 追加 0 / 4(朝だけ満たしても進まない)
│   └── w0-example-transitions/  # 未レビュー・余剰 OK・原案 → 修正版・完成稿 NG → 再選別・別ファイル修正版・完成稿承認
│   └── w0-example-review/       # 振り返り(quiz-review-learn・R-3-2)の 4 例: 仮説のまま残る NG・個別修正・共通ルール差分・final_ng → 候補 OK(reviews/ に記録の実例)
├── reviews/             # 振り返りの記録(quiz-review-learn。<YYYY-MM-DD>.md・1 セッション 1 ファイル。バッチをまたぐのでここ)
└── <batch>/             # 実際のバッチ(2026-09-w4 等。stock_items.py のバッチ名と同じ)
    ├── m01.md … n14.md  # 1 候補 1 ファイル(m = 朝・n = 夜)
    └── INDEX.md         # tally.py --write-index が生成する一覧(ID・状態・版・リンクだけ)
```

- **原記録(各候補ファイル)が正**。一覧 `INDEX.md` は ID・状態・版・リンクだけを持ち、内容や判定を書かない(生成物。手で編集しない)
- **原案と判定は上書きしない**。直すときは「版 N+1」を同じファイルの末尾に追記し、フロントマターの `version` を上げる
- 候補 = 問題文・答え・必要な図の内容・出典メモだけ。つかみ・ヒント・解説・コーチの一言・情景は候補に書かない(仕上げ = G1b の仕事)
- 候補ファイルは投入資材ではない。投入は従来どおり `stock_items.py` → `generate.py` → `insert_quiz_stock.sql`

## 2. 必須項目(フロントマター)

| 項目 | 必須 | 意味 |
|---|---|---|
| `id` | ○ | バッチ内で一意。`m01`〜(朝)/ `n01`〜(夜)。ファイル名と同じ |
| `batch` | ○ | 作ったバッチ名(`2026-09-w4`)。持ち越しても変えない(どの回で作ったかの記録) |
| `slot` | ○ | `morning` / `night` |
| `state` | ○ | 下の状態(8 種) |
| `version` | ○ | 本文の最新の「版 N」 |
| `supersedes` | — | 別ファイルへ切り出した修正版のときだけ元の `id`。元の候補は集計から外れる |
| `stock_no` | — | 完成稿へ進めたら `stock_items.py` の `no`(A47 等) |
| `source` | ○ | 流布例 URL を 1 件以上(候補段階で Web 裏取り。問題文の転載は禁止) |
| `example` | — | 投稿対象外の検証例だけ `true` |

本文は「版 N」ごとに **問題文・答え・必要な図の内容・出典メモ** と **判定(判定・日付・段階・理由〔任意〕)**。`tally.py` は本文の最後の `- 判定:` と `state` の食い違いを NG にする。

## 3. 状態と遷移

| `state` | 意味 | OK に数える | 次の遷移 |
|---|---|---|---|
| `unreviewed` | 未レビュー(判定欄が空) | × | 人間の選別で ok / ng / hold |
| `ok` | **候補 OK**(問題文・答え・図の内容に対する反射的な OK。完成稿の承認ではない) | ○ | 目標数だけ drafting へ。余った分は ok のまま次回へ持ち越し(余剰 OK) |
| `ng` | NG(理由は任意) | × | 後日の振り返り(`/quiz-review-learn`)で修正版を追記 → 再判定(ok / ng / hold。未判定なら unreviewed) |
| `hold` | 保留(理由は任意) | × | 同上、または次回の選別で再判定 |
| `drafting` | 完成稿へ進行中(`stock_items.py` に転記済み・1 問ずつレビュー中) | ○ | 承認 → approved / 完成稿 NG → final_ng |
| `approved` | 完成稿承認(1 問ずつの人間レビュー通過 = 投入対象) | ○ | 投入後は変更しない(承認済み内容の保護) |
| `final_ng` | 完成稿 NG → 再選別待ち(候補には戻るが OK には数えない) | × | 振り返りで修正版を追記 → 再判定(OK なら ok = 候補 OK。`stock_no` は空に戻す。投入ではない)。または withdrawn |
| `withdrawn` | 取り下げ(重複・出典 NG 等) | ×(候補数にも入れない) | 終端 |

- **理由空欄は有効**。ng / hold に理由を書かなくてよく、AI が推測で埋めない(理由の言語化は後日の振り返りへ)
- **同じ候補の複数版は 1 件**として数える(同じファイルの版 1・版 2 で 2 件にしない。別ファイルの修正版は `supersedes` で元を外す)
- **候補 OK と完成稿承認は別物**。候補 OK は「仕上げてよい」の意味で、投入の承認ではない。完成稿の 1 問ずつレビューは従来どおり行う
- **完成稿からの差し戻し**: 完成稿レビューで NG になった問題は `stock_items.py` から外し、候補ファイルへ「段階: 完成稿 / 判定: NG」を追記して `final_ng` にする。目標に足りなくなったら G1a へ戻り不足数の 2 倍を追加する(既に ok で余っている候補があればそれを先に使う)

## 4. 集計の規則(`tally.py`)

```bash
# 候補数の計画(目標の 2 倍)
python3 content/quiz-stock/logic-training-1/candidates/tally.py plan --target 7 7
# バッチの集計 + 一覧生成(前バッチの余剰 OK を持ち越すなら --carry-from <前バッチ dir>)
python3 content/quiz-stock/logic-training-1/candidates/tally.py content/quiz-stock/logic-training-1/candidates/<batch> --target 7 7 --write-index
```

- 目標は朝夜別(既定 7 / 7)。**用意する候補 = 目標の 2 倍**(初回 14 / 14)
- **不足 = 目標 − OK、追加 = 不足 × 2**(OK 朝 5 / 夜 4 → 追加 朝 4 / 夜 6。OK 朝 7 / 夜 5 → 追加 朝 0 / 夜 4)
- **朝夜の両方で不足 0 になるまで G1b へ進まない**(片方だけ満たしても仕上げない)。未レビューが残る間は追加数を確定しない
- 余剰 OK = OK − 目標(正のとき)。候補 OK のまま次回バッチへ持ち越し、完成稿にはしない
- 終了コード 0 = 形式チェック OK。1 = 必須項目・state・判定の整合・id 重複のどれかが NG(出力の `NG:` 節)

検証例の出力(2026-09-22 実行。`examples/` の 3 バッチ):


遷移例(`w0-example-transitions`)で確認できること: `m09` = 原案 NG(理由空欄)→ 版 2 を追記して OK、1 件として 1 回だけ加算 / `m10` = 未レビューが残ると追加数を確定しない / `n06` = 完成稿 NG → `final_ng`(OK に数えない) / `n07` → `n07r` = 別ファイルの修正版が `supersedes` で元を外す / `n08` = 完成稿承認(`approved`・`stock_no` あり)は OK に数える / 朝 OK 9 に対し目標 7 → 余剰 2。

## 5. 候補レビューの表示例(チャット)

候補はスロットごとに **1 候補 3 行**で一覧提示し、人間は **OK / NG / 保留 だけ**を返す(理由不要。書きたければ書く)。

```
【朝・候補選別 14 件】各候補に OK / NG / 保留 を返してください(理由は不要。未判定はそのまま残ります)
m01 問題文: 黒板の式に線を 1 本足して正しい式にする
    答え: + に斜線で 4(545+5=550)  図: 黒板の式
m02 問題文: …
    答え: …  図: なし
…
```

返答の例(1 行でよい): `OK: m01 m03 m05 m07 m10 / NG: m02 m06 m08 m09 m12 m13 / 保留: m04 m11 m14`
→ エージェントが各ファイルの判定欄と `state` を更新し、`tally.py` の出力を貼って「追加 朝 4 / 夜 6」または「G1b へ進める」を宣言する。**判定に迷ったら保留でよい**(理由を求めない)。

## 7. 振り返り(`/quiz-review-learn`・R-3-2)との接点

NG・保留・完成稿 NG の候補は、週次補充とは別の時間に振り返りスキル `.agents/skills/quiz-review-learn/SKILL.md`(**Claude Code 専用**)で理由を言語化 → 修正版を追記 → 再判定し、**一般化できた理由だけ**を補充スキルの作問基準へ差分反映する。候補ファイルの形式は変えず、次の 2 点だけが足される。

- **段階「振り返り」**: 追記した版の `### 判定` に `段階: 振り返り` と書く。`tally.py` は段階を見ないため、最後の判定と `state` の整合だけが検査対象(OK → `ok`・NG → `ng`・保留 → `hold`・空欄 → `unreviewed`)
- **記録 `reviews/<YYYY-MM-DD>.md`**: 個別修正 / 共通ルール / 仮説の 3 表(候補 ID・版・元の判定 → 再判定・ユーザーの理由〔原文〕・更新したスキル箇所)。候補ファイルの理由欄からは「振り返り <日付> 参照」で戻れる。`reviews/` はバッチではないので `tally.py` に渡さない

振り返りの OK は**候補 OK**(`state: ok`)であって投入の承認ではない。完成稿への転記・投入は次回の週次補充の G1b 以降で行う。検証例は `examples/w0-example-review/`(4 例 + `reviews/2026-09-22.md`)。
