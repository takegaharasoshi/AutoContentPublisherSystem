要約

このページは配信面のバッチ 3 本（画像生成〔選定〕・SNS 投稿・インサイト収集）が、ECS タスクの中で何をどの順に行うかを定める。機能別の基本設計 投稿（2・3 章）と インサイト収集（4 章）の処理の詳細にあたる。実行基盤（Scheduler・Step Functions・タスク定義）は infra/workflow.html が持ち、このページはその器の中のアプリの処理だけを書く。図 1 は 3 本のバッチの起動のつながりと、読み書きするデータを表す。

項目要点
処理の単位1 回の画像生成バッチ起動 = 1 生成実行（generation_runs）= アカウントごとに 1 投稿（1 章）
画像生成バッチセットに割り当てた生成方式（方式カタログ）を呼び、返った最終メディアを S3 と generated_media に登録する。稼働中の 3 セットはすべて事前ビルド方式で、実行時は在庫から動画を 1 本選ぶだけ（2 章）
SNS 投稿バッチセット × SCHEDULED_AT で当回の生成実行だけを選び、posts の 5 状態で二重投稿を防ぎながら投稿する。一過性エラーは公開前だけやり直す（3 章）

1. 前提・不変条件

3 本のバッチに共通する前提をまとめる。要約の「処理の単位」と、起動・DB 接続・実行ログの決まりを詳しくしたもの。

  • 1 回の画像生成バッチ起動 = 1 投稿（アカウントごと）を不変条件とする（定義の正はアプリ設計大枠 セクション 2）。1 回の生成実行を generation_runs エンティティとして永続化し、SNS 投稿バッチは生成実行を処理対象の単位とする
  • 本書の処理手順（骨格）は全セット共通とする。セットごとに変わりうる箇所は本文中に「セット別拡張ポイント」と明示し、各セットでどの方式を使うかはセット別設計書に記録する（セット別設計書のルール）
  • 実行ログ記録（共通）: 両バッチとも、SET_CODE から batch_sets を解決した直後（set_id が確定した時点。生成実行の解決や投稿対象の決定より前）に batch_execution_logs へ実行ログを記録する（記録手順は下記を参照）。SET_CODE の解決に失敗した場合（batch_sets が存在しない）は set_id が確定できないため記録は行わず、既存の Step Functions 失敗アラームで検知する。正常終了時は status='succeeded'、異常終了時は status='failed' に更新する。このログ記録自体の INSERT/UPDATE が失敗した場合はバッチ全体を終了コード 1 とする → 理由 D-17
  • 起動経路は Step Functions 経由に限る（Phase 10-1 でインフラ構築の知見を反映）: 手動での再実行を含め、バッチは必ず Step Functions（先頭ステートの DB 準備確認 WaitForDbReady 経由）で起動する。バッチアプリ自身は DB 接続リトライを持たない（infra/workflow.html セクション 2）。EXECUTION_ARN は常に設定される（手動 RunTask 時の空値は考慮しない） → 理由 D-18
  • DB アクセスの共通部品: DB 接続には共通ライブラリ shared/acps_shared を使用する（connect() はリトライなし・autocommit OFF。commit は呼び出し側の責務）。本書の INSERT-or-fetch 等の手順は明示的な commit を前提とする

batch_execution_logs の INSERT/UPDATE 手順（Step Functions Retry 対応） → 理由 D-01

generation_runs（セクション 2 手順 2）と同じ INSERT-or-fetch パターンを適用する。
  • INSERT 成功 → 新規の実行ログ（attempt_count=1、status='running'）
  • UNIQUE 制約違反 → 既存行を (execution_arn, batch_type) で取得し、attempt_count をインクリメントして status='running' に UPDATE する（前回試行時点の error_message 等は上書きされる。試行ごとの履歴は保持せず、直近の試行状態のみを保持する設計とする）

2. 画像生成バッチ処理フロー

この章は、機能別の基本設計 投稿 3 章の「選定」の段を、アプリの処理手順まで詳しくしたもの。手順 1〜5 の骨格は全方式で共通で、方式ごとの違いは 2.1 の方式モジュールの中に閉じる。

名称と対象範囲（Phase 14-4 の動画対応を反映） 「画像生成バッチ」（image-batch）の名称は歴史的経緯であり、本フローの成果物は方式が返す最終メディア（画像または動画）である。 動画（リール）対応でもフローの骨格（手順 1〜5）は変わらず、違いは方式（セクション 2.1）の中に閉じる。バッチ名・サービス名・ステートマシン名はリネームしない。
システムとしての対応範囲と初期運用の切り分け システムは1 つの prompt_config から複数画像を保存することと1 セットに複数 prompt_config を持たせることの両方を処理できるようにする（初期実装からこの前提で作る。旧設計の「2 枚目以降は破棄」は採用しない）。 一方、初期運用は 1 セットにつき有効な prompt_config を 1 件のみ設定し、そのプロンプト文言自体を「1 枚だけ生成される」よう作り込む運用ルールとする（セット追加手順は アプリ運用設計 セクション 2.1）。 「1 起動 = 1 プロンプト = 生成画像 1 枚 = 1 投稿 = 投稿画像 1 枚」は設定値・運用ルールで実現する結果であり、システムの実装上の制約ではない。
  1. SET_CODE から batch_sets を解決する。存在しなければ異常終了（終了コード 1）。is_active=0 ならスキップして正常終了（終了コード 0）
  2. 生成実行（generation_runs）を解決する（set_id × SCHEDULED_AT の UNIQUE 制約に対する INSERT を試みる）
    • INSERT 成功 → 新規の生成実行（今回のスケジュール枠の初回実行）
    • UNIQUE 制約違反 → 既存の生成実行を取得する（Step Functions Retry によるタスク再起動、または重複トリガーと判断）。手順 4 で未完了分のみ処理する
  3. 対象の prompt_configs（is_active=1）を全件取得する。0 件なら設定ミスとして異常終了（終了コード 1）（投稿すべき画像を 1 つも作れないため）。1 件以上ある場合はすべてを手順 4 で処理する（初期運用は 1 件を想定するが、複数件でも正しく処理できる）
  4. 各 prompt_config ごとに順次処理する。1 件の失敗は他の prompt_config の処理をブロックしない（例外を捕捉し次の prompt_config へ進む。全体の成否は手順 5 で判定する）
    1. 完了判定: (generation_run_id, prompt_config_id) の組み合わせで generated_media レコードの有無を確認する。存在すれば当該 prompt_config は完了済みとしてスキップする（Step Functions Retry によるタスク再起動時に、生成 API を再度呼び出さないため）
    2. 未完了の場合、セットに割り当てられた生成方式（セクション 2.1 の契約に従う strategy モジュール）を実行し、生成された最終メディアをすべて受け取る。0 件ならこの prompt_config の生成失敗としてログ出力し、次の prompt_config へ進む（生成 API 呼び出し自体の一時的失敗は Step Functions Retry に委ねる）
    3. 受け取った最終メディアはすべて保存する（1 件でも複数件でも同じ経路で処理する。旧設計の「2 枚目以降は破棄」は採用しない）
    4. 各メディアを S3 に保存する（キー規約は data-model.html セクション 5。投稿可能な最終形式への変換は方式側の責務であり、共通骨格は方式が返した形式〔file_format〕に従いプレフィックス・拡張子・Content-Type を決めてそのまま保存する。方式が中間生成物〔例: 動画の元静止画〕を返した場合は S3 保存のみ行い、DB には記録しない）
    5. メディアごとに generated_media にレコードを登録する（S3 キー、prompt_config_id、同一 (generation_run_id, prompt_config_id) 内での並び順を表す output_index、フォーマット・寸法・尺・使用音源〔動画のみ〕、プロンプト本文・パラメータのスナップショットを含む）。1 件ごとの DB 登録が成功した時点でそのメディアを完了とする。S3 保存後に DB 登録が失敗した場合は S3 に orphan が残るが許容する
  5. 全 prompt_config の処理後、終了コードを決定して終了する: すべての prompt_config が完了すれば終了コード 0（成功により SNS 投稿ワークフローが自動起動される）。1 つでも未完了が残れば終了コード 1（Step Functions Retry / Catch に委ねる。SNS 投稿バッチの失敗判定方針（3.4）と同じパターン）
再開処理の簡略化に関する既知の割り切り 完了判定は「(generation_run_id, prompt_config_id) に 1 件でも generated_media が存在するか」で行う。生成が複数メディアのうち一部だけ DB 登録できず失敗した場合でも、再実行時は「1 件存在する = このプロンプトは完了済み」としてスキップし、残りのメディアは生成し直さない → 理由 D-19

2.1 セット別拡張ポイント: 生成方式（strategy モジュール構造）

生成ロジックの構成 → 理由 D-02

アプリ資材（コンテナ・CI/CD パイプライン）はサービス単位で全セットが共有し、image-batch の内部を次の 3 要素で構成する。

  • 共通骨格: セクション 2 の手順 1〜3・5 と手順 4 の枠組み（完了判定 = 冪等性のアンカー、S3 保存、DB 登録）。方式によらず共通
  • 生成方式 strategy モジュール: generators/<方式名>.py（1 方式 1 ファイル）
  • 方式名レジストリ: 方式名 → モジュールの対応表。新方式の追加は「新規ファイル + レジストリ 1 行」に閉じ、既存方式のファイルには触れない

方式の割当は DB のセット設定（batch_sets.generator_name。data-model.html セクション 4.1）で行い、コードに set_code の分岐は書かない。 共有部品（共通骨格・API クライアント）の変更は CI/CD パイプラインの pytest ゲート（infra/cicd.html）で守る。

生成方式の契約（方式インターフェース）

方式は投稿可能な最終形式の最終メディア（画像・動画）を返す → 理由 D-03

  • 方式はセット設定（プロンプト設定等）と実行コンテキスト（生成実行の scheduled_at 等）を受け取り、投稿可能な最終形式の最終メディア（1 件以上。本体 + メタ情報〔file_format・寸法・尺・使用音源等〕）を返す。投稿要件に合わせた形式変換（例: PNG → JPEG 変換、ffmpeg 合成）は方式側の責務
  • 方式は最終メディアに加えて中間生成物（例: 動画の元になる静止画）を返してよい。共通骨格は中間生成物を S3 に保存するのみで、DB には記録しない（data-model.html セクション 4.5・セクション 5）
  • 冪等性（完了判定）・S3 保存・DB 登録は共通骨格の責務であり、方式は関与しない。方式が補助テーブル（例: 音源ストック audio_assets の選曲と last_used_at 更新〔data-model.html セクション 4.8〕、出題履歴 quiz_items の INSERT〔同セクション 4.9〕）を読み書きすることは許容するが、commit は共通骨格に委ね、生成メディアの DB 登録と同一トランザクションで確定させる（登録に失敗した場合にローテーション等の副作用だけが進むことを防ぐ）
  • 特定の生成 API・変換ツールに固有のリクエスト・レスポンス処理やパラメータは方式側（generators/<方式名>.py と方式別設計書）に閉じる。共通設計書・共通骨格には特定 API 名を書かない

実行コンテキスト（実装上は GeneratorContext）には、共通骨格が確定済みの生成実行の scheduled_at（UTC）と generation_run_id が入る。方式は環境変数 SCHEDULED_AT を直接読まない → 理由 D-04

セット別拡張ポイント: プロンプトの決め方 → 理由 D-05

初期運用は 1 セット 1 prompt_config（固定プロンプト、1 枚生成となるようプロンプト文言で制御）とする。将来の 生成 AI にプロンプト自体を考えさせてから画像を生成する方式などは、新しい生成方式（generators/ の strategy モジュール）として追加し方式カタログに登録する。 1 セットに複数 prompt_config を有効化してのローテーション選択・カルーセル素材化などは、運用ルールの変更（有効化する prompt_config 件数・プロンプト文言）で実現できる。 いずれの場合も手順 2 の生成実行の枠組み（1 起動 = 1 生成実行 = 1 投稿分のコンテンツ）は変えない。どのセットがどの方式を使うかはセット別設計書に記録する。

3. SNS 投稿バッチ処理フロー

この章は、機能別の基本設計 投稿 3 章の「投稿」の段を詳しくしたもの。3.1 で当回の生成実行を選び、3.2 の状態で二重投稿を防ぎ、3.3 の手順で投稿し、3.4 で成否を決める。

処理対象の単位は「投稿」= 生成実行 × 投稿先アカウントとする（メディア単位ではない）。フィード画像投稿とリール投稿の違いは手順内の分岐（posts.media_type。data-model.html セクション 4.6）に閉じ、投稿対象の決定・状態遷移・失敗方針は共通。ストーリーズ再掲（batch_sets.stories_enabled のセットのみ。V004・15-10）もこの単位の内側で「リール成功後の追加投稿行（media_type='story'）」として扱い、投稿対象の決定は変えない（3.3 手順 2 の 7）。

3.1 投稿対象の決定（当回固定。Phase 26-1 で改訂）

投稿バッチは当回 = 自分を起動した予定時刻の生成実行だけを扱う。セット × 予定時刻（SCHEDULED_AT）で生成実行を特定し、過去分・別の回へは戻らない。生成に失敗した回・当回を投稿できなかった回は欠番を許容する（A-1 壁打ち記録 セクション 4 の初期方針）。

  1. SET_CODE から batch_sets を解決する（画像生成バッチと同じ扱い。is_active=0 のセットで何もせず正常終了する現行動作は変えない）
  2. 入力契約: SCHEDULED_AT は必須。UTC・秒精度の YYYY-MM-DDTHH:MM:SSZ だけを受け付け、実在しない日時（2 月 30 日等）も拒否する。欠落・空・不正形式はDB 接続・外部 API 呼び出しの前に異常終了する。現在時刻の代入・最新の生成実行の検索・最古の生成実行へのフォールバックは行わず、旧選定へ戻す互換モードも設けない。値は画像生成バッチと同じ正規化（data-model.html セクション 6）で DATETIME にして比較する
  3. 当回の生成実行を段階ごとに判定する: ① 指定 run の取得（set_id × scheduled_at の完全一致）→ ② 素材（generated_media）の有無 → ③ 有効アカウントごとの投稿状態。単一の検索の「該当なし」だけで結論を出さず、どの段階で止まったかを結果型（理由）で返す（実装形は結果型で確定。SQL は data-model.html セクション 4.4）
  4. 投稿処理（3.3）に入るのは結果が「選定」のときだけ。素材の存在はキャプション組み立て（3.3 手順 2 の 3）より前に確定している（素材 0 件の実行がキャプション生成・素材取得で例外になり後続を塞いだ I-014 の経路を断つ）

期限ガード（scheduled_at から一定時間を過ぎた実行の投稿を止める仕組み）は置かない。自動経路の最大遅延は約 8.6 時間で、予定時刻を指定した手動実行は運用者が素材の時間帯を確かめてから行う（operation.html セクション 4.1） → 理由 D-07

Phase 9-3 での厳密化（26-1 で当回に限定）: 「未完了」の判定 ③ の判定は、Step Functions Retry によるタスク再起動時に同じ生成実行を再選択して 3.2 の復旧ロジックへつなげる必要があるため、 「posts 行が 1 つもない」ではなく「有効なアカウントのうち少なくとも 1 つが終端状態（success / failed / published_unconfirmed）に達していない」を条件とする（Phase 9-3 の定義を維持し、対象を当回の 1 件に限定した）。 一度でも試行して有効な全アカウントが終端状態に達した生成実行は、自動では再対象にしない = 再試行なし・欠番許容。

1 回の実行で扱う生成実行は当回の 1 件だけで、処理件数の上限設定（BATCH_SIZE_LIMIT 等）はない。過去に投稿できなかった生成実行をまとめて追いつかせる制御は持たず、過去分は人間が対象 run の予定時刻を指定して手動起動する（将来の追いつくモードは別経路） → 理由 D-08

3.2 posts の状態遷移（冪等性・二重投稿防止）

posts は生成実行 × アカウント × メディア種別で一意（UNIQUE 制約 (generation_run_id, sns_account_id, media_type)。V004 で media_type を追加）とし、attempt_number 相当のカラムは持たない。1 つの投稿対象・1 メディア種別について作られる行は常に 1 行であり、その行の状態遷移だけで進行状況を表現する（Phase 28 で入れた一過性エラーのやり直し〔3.3 の段階別の扱い〕も同じ行の中で行い、行を増やさない）（ストーリーズを有効化したセットではリール行 + ストーリーズ行の最大 2 行。ストーリーズ行も同じ 5 状態を使う）。

Step Functions Task Retry（同一実行内の再起動）での復旧 SNS 投稿 ECS タスクが異常終了し Step Functions の Retry（最大 2 回、30 秒間隔。infra/workflow.html セクション 6）でタスク全体が再起動された場合、対象生成実行に紐づく有効アカウントごとに posts の状態を確認し、以下のとおり分岐する。
  • 行が存在しない、または pending（platform_container_id 未設定）→ 最初から実行（コンテナ作成 → パブリッシュ）
  • （Phase 28）一過性エラーのやり直し回数はタスクのメモリ内でだけ数え、DB に持たない。やり直しの途中でタスクが落ちて Retry で再起動された場合は、行の状態から上記どおり再開し、やり直しの回数も 0 から数え直す（タスクの異常終了は稀なため、合計回数が 1 回を超えうることは受け入れる）
  • container_created（platform_container_id 設定済み、platform_post_id 未設定）→ パブリッシュから再開（同じ container_id を使い、新しいコンテナは作らない）
  • success → スキップ（このアカウントへの投稿は完了済み）
  • failed / published_unconfirmed → スキップ（同一実行内の Step Functions Retry でも自動では再試行しない。終端状態の扱いは全実行を通じて一貫させる）
この分岐により、Step Functions Retry が働いても既に成功・終端状態のアカウントへの無駄な API 呼び出しは発生しない。 なおストーリーズ行（media_type='story'）はこの復旧分岐の対象外: 投稿対象の決定が先行するリール行で決まるため、リール行が終端状態に達した実行は Retry で再選択されない（ストーリーズ行が途中状態のまま残った場合の扱いは 3.3「ストーリーズ再掲の投稿フロー」を参照）。

3.3 処理手順

  1. 対象の生成実行に対し、セットの有効な投稿先アカウント（sns_accounts）ごとに順次処理する。1 アカウントの失敗は他アカウントの処理をブロックしない（例外を捕捉し次のアカウントへ進む）
  2. posts の状態（3.2）に基づき、未完了のアカウントについて処理を進める:
    1. posts レコードが存在しなければ pending で作成する（INSERT-or-skip。3.2 の復旧分岐により、既存行がある場合は作成せずその状態から再開する。投稿前の事前記録により二重投稿を防止する）。作成時に media_type を投稿対象の先頭メディアの file_format から導出して設定する（'mp4' → 'reel'、それ以外 → 'feed_image'。data-model.html セクション 4.6）
    2. 初期構築の仕様: 生成実行に紐づくメディアのうち最初の 1 件のみを post_media で紐づける（選択順序は generated_media.id 昇順 = 最も早く生成された 1 件。1 セット複数 prompt_config や 1 プロンプト複数メディアにより生成実行が複数のメディアを保存していても、投稿するのは常に 1 件とする）。将来のカルーセル対応では、生成実行内の複数メディアを並び順付きで束ねる処理に拡張する
    3. キャプションテンプレートを適用して投稿本文を組み立てる（テンプレートには AI 開示ハッシュタグを必ず含める運用ルール。operation.html セクション 3）。テンプレートにプレースホルダが含まれる場合は、当該生成実行の出題・投稿履歴（quiz_items / ranking_items）から動的に展開する（16-1 決定・17-2 でランキング系を追加。展開規則は 3.4「セット別拡張ポイント: キャプションの作り方」）。展開後の最終文が posts.caption_text_snapshot に保存される点は従来どおり
    4. S3 Presigned URL を発行し（有効期限 1 時間）、Instagram Graph API のコンテナ作成 API（POST /{ig-user-id}/media）を呼び出す。パラメータは media_type で分岐する:
      • feed_image → image_url（presigned URL）を渡す（従来どおり）
      • reel → media_type=REELS + video_url（presigned URL）+ share_to_feed=true（プロフィールのフィード面にも表示する。14-2 壁打ち決定事項 #8）を渡す。カバー画像は指定せずデフォルト（動画の先頭フレーム）とする（Phase 14-4 決定・14-8 の実機確認で妥当性を確認済み。cover_url / thumb_offset は指定しない）。この仕様を前提に、各生成方式は先頭フレームがカバー・サムネイルとして成立するように 1 カット目を設計する（kenburns = 元静止画とほぼ同じ絵 / gpt-quiz-multicut = 問題提示の版面をカバー兼用にする 16-1 テコ入れ設計）
      取得した platform_container_id を即座に保存し、posts.status を container_created に更新する。一過性エラーは作成からやり直す（段階別の扱い）
    5. コンテナのステータス（GET /{container-id}?fields=status_code,status。status は ERROR の理由文字列を記録するために取る〔26-6〕）を FINISHED になるまで有限回数・タイムアウト付きでポーリングする（Meta 側のメディア処理が非同期のため。手順 5 のパブリッシュ API は FINISHED 到達前に呼び出すと失敗しうる）。リール（動画）はメディア処理が分オーダーになり得るため、ポーリング間隔・上限は画像より長くメディア種別ごとに設定する（14-9 で確定: 画像は現行の間隔 3 秒 × 最大 10 回を維持、動画は間隔 10 秒 × 最大 60 回 = 上限約 10 分。14-8 の実測〔10 秒動画で FINISHED まで 33.5 秒〕に対する十分なマージン。動画の最大待ち時間 10 分は Step Functions の RunSnsPostBatchTask タイムアウト 3600 秒〔infra/workflow.html セクション 4〕に収まるため、インフラ側の変更は不要）。ERROR を受け取った場合（理由文字列を error_message・api_response・ログに残す。data-model.html 4.6）、またはポーリングが上限に達し FINISHED に到達しなかった場合は、パブリッシュ API を呼び出さずに status='failed' に更新する（パブリッシュ要求を送信していないため published_unconfirmed の対象外）。ただし ERROR と照会の一過性エラーは、failed にする前にコンテナ作成から 1 回やり直す（上限到達はやり直さない。段階別の扱い）
    6. パブリッシュ API（POST /{ig-user-id}/media_publish）を呼び出す
      • 成功 → platform_post_id を保存し status='success' に更新
      • 明確な失敗（投稿未完了と判定できる応答）→ status='failed' に更新
      • 一過性エラー → コンテナの status_code を照会して分岐する（PUBLISHED → published_unconfirmed / FINISHED → 同じコンテナで公開を 1 回だけ再送 / それ以外・照会失敗 → published_unconfirmed。段階別の扱い）
      • 重複 publish 応答、またはタイムアウト・接続断で結果不明 → status='published_unconfirmed' に更新
      • 成功直後の問題スナップショット出力（batch_sets.problem_snapshot_enabled=1 のセットのみ。Phase 21-3 設計・21-5b 実装）: リール行が success に達した直後に、当該生成実行の umigame_items（問題文・真相・確定事実シート・ルール帯）と対象セットの prompt_configs.prompt_text（AI 出題者プロンプトのセット固定部分。is_active=1 の id 昇順 1 件）から JSON を組み、S3 assets/{set_code}/problems/{platform_post_id}.json へ PUT する（media_id = media_publish の応答 id。スキーマは セット別設計書 10.7.2）。PUT 成功で umigame_items.snapshot_s3_key / snapshot_written_at を更新する。出力失敗は投稿失敗にしない（WARNING ログ + snapshot_s3_key NULL のまま次へ。手動再出力は運用側。21-5b の実装では、リール行の success 更新を commit した後に別トランザクションで出力し、失敗時はスナップショット側だけをロールバックする = 投稿の成功記録を巻き戻さない）。フラグが 0 のセット・umigame_items 行のない実行では何もしない。コメント自動返信の Lambda はこの JSON だけを読み Aurora に触れない（infra/stacks.html 3.6）
    7. ストーリーズ再掲（batch_sets.stories_enabled=1 のセットのみ。Phase 15-10 追加）: リール行が success に達した場合のみ、同一動画をストーリーズへ再掲する。posts へ media_type='story' の行を pending で INSERT-or-skip（既存ストーリーズ行があればその状態から 3.2 と同型の分岐で再開・終端ならスキップ。post_media は手順 2 と同様にストーリーズ行にも同一メディアを display_order=0 で 1 行紐づける〔15-12 実装〕。キャプションは非対応のため caption_template_id / caption_text_snapshot は NULL のまま）→ 同一 MP4 の Presigned URL でコンテナ作成（media_type=STORIES + video_url。キャプション・share_to_feed・カバーは指定しない〔ストーリーズはキャプション非対応〕）→ ステータスポーリング（動画の間隔 10 秒 × 最大 60 回を流用）→ パブリッシュ（結果の反映は手順 6 と同じ。一過性エラーの扱いもリールと同じで、やり直しの回数はストーリーズ行で別に数える）。リール行が success 以外で終わったアカウントではストーリーズ行を作成しない
  3. 全アカウントの処理後、3.4 の方針に基づき終了コードを決定して終了する

一過性エラーの段階別の扱い（Phase 28-1 設計・28-2 実装）

投稿 1 行（posts の 1 行 = リール行・ストーリーズ行それぞれ）について、段階 × 失敗の種類ごとに次のとおり扱う。公開前（作成・処理待ち）は二重投稿の心配がないので作成からやり直し、公開の後は未公開を確定できたときだけ再送する。実装は services/sns-post-batch/app/processing.py（作成〜処理待ちのループと _publish_with_recovery）と instagram_api.py の is_transient_api_error（28-2〔2026-10-17〕）。

  • PUBLISHED → published_unconfirmed。error_message の先頭を「PUBLISHED 確認済み:」にする（公開済みだが media_publish の応答がないためメディア ID が取れない。人が ID を補って success に直す = operation.html 4.2）
  • FINISHED → 同じコンテナ ID で公開を 1 回だけ再送する。同じコンテナは 1 回しか公開できないため、照会の後で先の要求が公開まで進んでいても 2 件目の投稿にはならない（重複応答 → published_unconfirmed）。再送の結果: 成功 → success / 一過性でない API エラー → failed / 一過性エラー・重複応答・結果不明 → published_unconfirmed（再送は 1 回だけ。2 回目の照会はしない）
  • それ以外の status_code（ERROR・EXPIRED・IN_PROGRESS 等）・照会自体の失敗 → published_unconfirmed（未公開を確定できないため）

「一過性」の判定: 次のどれかに当たる失敗を一過性とする。

  • Graph API のエラー応答で error.is_transient が true
  • Graph API のエラー応答で error.code が 1（API Unknown）または 2（API Service）。Meta のエラーコード表で「一時的な障害の可能性。待ってやり直す」とされるもので、is_transient が付かない応答でも一過性に含める
  • 処理待ちでのコンテナ status_code=ERROR（理由文字列に関係なく 1 回はやり直す。形式不正など恒久的な ERROR はやり直しも ERROR になり failed で終わる）
  • ① ② の段階でのタイムアウト・接続断・応答本文の読み取り失敗（InstagramTransportError 相当）。③ では結果不明として扱い、一過性には含めない

レート制限（code 4 / 17 / 32 / 613 や HTTP 429）は、is_transient: true が付いていない限り一過性に含めない。やり直しの前に待ちは入れない。処理待ちの上限到達はやり直さない → 理由 D-20

やり直しの回数: 1 行につき「① ② の作成からのやり直し 1 回」と「③ の再送 1 回」を別々に持つ（両方使うことはありうる）。回数はタスクのメモリ内で数え、DB には持たない（3.2）。

記録の形:

  • 作り直したコンテナの ID は platform_container_id を上書きする（状態は container_created のまま）。最初のコンテナ ID と最初のエラーは WARNING ログに出す
  • やり直し・照会が起きた行の api_response は、次の形の JSON にする（起きなかった行は従来どおり、失敗した呼び出しの応答 JSON をそのまま保存する）: 
    {
  "final": <最後に失敗した呼び出しの応答。成功で終わった場合は null>,
  "first_error": {"stage": "create" | "poll" | "publish",
                  "container_id": "<そのときのコンテナ ID>",
                  "response": <最初の失敗の応答 JSON。転送エラーなら {"transport_error": "<例外の文字列>"}>},
  "container_check": <③ の照会の応答 JSON。照会しなかった・失敗した場合は null>
}
    やり直しが成功して success になった行も、この JSON を api_response に残す（一過性エラーの発生頻度を後から数えるため）。error_message は success なら NULL のまま
  • error_message は最後の失敗の内容にし、やり直しを使った場合は末尾に「（作成から 1 回やり直し済み）」「（公開を 1 回再送済み）」を付ける

この扱いの導入後も、Step Functions の Retry・ASL・DB スキーマ（状態値 5 つ）・終了コードの方針（3.4）は変わらない → 理由 D-09

3.4 「失敗」の定義・通知粒度・終了コード方針

  • 失敗の定義: 対象の生成実行に対し、有効な投稿先アカウントのうち1 つでも success にならなかった場合（failed または published_unconfirmed で終わったアカウントが 1 つでもある場合）を失敗とする。ストーリーズを有効化したセット（stories_enabled=1）では、リール行とストーリーズ行の両方が success であることを当該アカウントの成功条件とする（ストーリーズ失敗もリール行の success は保持したまま失敗として扱う。15-10）
  • 終了コード: 全アカウントが成功条件を満たすなら 0。1 つでも満たさないなら 1
  • 終了コード 1 により Step Functions の既存 Retry（最大 2 回）が働くが、3.2 の状態遷移によって success / 終端状態のアカウントはスキップされるため、Retry によって無駄な API 呼び出しが増えることはない。Retry を使い切ってもなお非 success が残る場合は Catch → Fail 状態に遷移し、既存の CloudWatch Alarm（ExecutionsFailed）で通知される
  • 検知経路の正確化（2026-07-29、Phase 15-10 で確認）: 投稿が終端状態（failed / published_unconfirmed）で確定した失敗は、Retry の再実行時に投稿対象の決定（data-model.html セクション 4.4）で ALREADY_TERMINAL となり再実行が成功終了するため、ExecutionsFailed アラームには現れない。この場合の検知は 1 回目の終了コード 1 を捕捉する ECS タスク異常終了通知（EventBridge Rule。infra/workflow.html セクション 9）が担う。ExecutionsFailed が発報するのは、非終端状態のまま失敗が続く場合（stale・インフラ障害・タスク起動失敗等）である。ストーリーズ失敗の検知（3.3「ストーリーズ再掲の投稿フロー」）もこの ECS タスク異常終了通知の経路に乗る
  • 通知粒度: 初期スコープでは個別アカウント・個別失敗理由ごとのカスタムメトリクスは持たない。既存の Step Functions 失敗アラーム 1 本のみで通知し、詳細な原因（どのアカウント・どの段階で失敗したか）は CloudWatch Logs と posts テーブル（status / api_response）で確認する運用とする（確認手順は アプリ運用設計 セクション 4.1）
  • 一過性エラーのやり直し（Phase 28）はこの判定の前にアプリ内で済ませる: やり直し・再送で success になった行は成功として数え、使い切って failed / published_unconfirmed で終わった行だけが失敗になる（3.3 の段階別の扱い）。終了コード・Retry・通知の経路は変えない
  • published_unconfirmed も「対応が必要な状態」として終了コード 1 の対象に含める（success と明確に区別し、運用者に手動確認を促すため）

メトリクスの束ね方と自動縮退（16-9 実装） → 理由 D-15

  • metric_type（total_value の要否）と breakdown はリクエスト全体に掛かる単一パラメータであり、要件の異なるメトリクスを 1 リクエストに混在させられない。したがって「1 メディア = 1 リクエスト」ではなく MetricRequest（メトリクス群 + metric_type + breakdown）単位で束ねる。実際のリクエスト数は リール = 1 回、フィード画像 / ストーリーズ = 2 回（通常値 + breakdown 付き 1 本）、アカウント日次 = 1 日あたり 2 回
  • 対象 media_type で未対応のメトリクス名を 1 つでも含めるとリクエスト全体が HTTP 400（code: 100）になる（部分成功しない）。2025-12 追加分（reels_skip_rate / reposts 等）は一次リファレンス本文が取得制限で読めず対応表を完全確定できなかったため、実装側に縮退を持たせた: グループが 400 になったらメトリクスを 1 個ずつ呼び直して成功分だけ採用し、無効なメトリクス名をラン内のキャッシュに記録して以降は最初から除外する（縮退のコストは 1 ラン × 1 media_type につき 1 回のみ）。除外したメトリクス名は WARNING ログに出るため、運用者はログから「現行 API で無効な名前」を確認して定数を更新できる
  • アカウント日次は 1 リクエスト = UTC 1 日（since / until をその日の 00:00〜翌 00:00 UTC で指定）とする。metric_type=total_value のメトリクスは範囲を渡すと範囲全体の集計値 1 個しか返らず日別に分解できないため、4.2 の「範囲取得」は日単位ループとして実装した

4.1 実行スケジュールと収集ウィンドウ

実行スケジュールと収集ウィンドウ → 理由 D-16

  • 1 日 2 回、06:00・18:00 JST にセットごとに実行する（Scheduler 定義は infra/workflow.html セクション 1.6）。
  • アカウント日次指標は UTC 日締め（09:00 JST）のため、18:00 JST の回で前日 UTC 日の確定値を約 9 時間遅れで取得できる
  • 収集ウィンドウ: feed_image / reel は投稿後 14 日間（環境変数 MEDIA_LOOKBACK_DAYS、既定 14。後から変更可能だが過去分の欠測は埋まらない）、story は投稿後 24 時間（API 期限そのもの）。
  • 呼び出し量の概算（現行規模: リール 4 + ストーリーズ 3/日）: 1 ランあたり最大でも約 50 コール/アカウントで、200 コール/時（app-user あたり）の制限に大きな余裕がある。セット・スロット増にも耐える

4.2 処理手順

  1. SET_CODE から batch_sets を解決し、batch_execution_logs へ実行ログを記録する（セクション 1 の INSERT-or-fetch パターン。batch_type は本バッチ用の値を追加する）
  2. セット配下の有効な投稿先アカウント（sns_accounts.is_active=1、platform='instagram'）ごとに順次処理する:
    1. 認証情報の取得: Secret 名規約 acps/{env}/{set_code}/sns/{platform}/{account_code}（SNS 投稿バッチと同一規約）で access_token / ig_user_id を取得する
    2. アカウント日次の収集: DB の MAX(metric_date) + 1 日から直近の閉じた UTC 日までを 1 日ずつ取得し（日単位で取る理由は D-15）、account_insights_daily へ INSERT IGNORE（upsert-once）する。範囲は API 保持上限の 90 日でキャップする。テーブルが空の初回実行は自動的に 90 日分のバックフィルになる。直近の閉じた UTC 日の行には IG User の followers_count（ユーザーフィールド）も記録する
    3. メディアレベルの収集: 対象 = 当該アカウントの posts のうち status='success' かつ platform_post_id IS NOT NULL で、feed_image / reel は posted_at が MEDIA_LOOKBACK_DAYS 以内、story は posted_at が 24 時間以内のもの（posted_at 昇順）。各行について全メトリクスを取得し、post_insights へ INSERT-or-skip（UNIQUE (post_id, scheduled_at)）で追記する。当該ラン（同一 scheduled_at）で収集済みの post_id は API 呼び出し自体を行わずスキップする（再実行時のコール数削減。16-9 実装）
  3. コメント記録の取り込み（21-7b。環境変数 COMMENT_LOG_BUCKET があるときだけ）: S3 の comment-log/{set_code}/ の直近数日分を umigame_comment_logs へ INSERT IGNORE で取り込み、保持期限切れの行を消す。コメント返信経路は Aurora 停止中でも動くため直接書けず、本バッチの起動に相乗りして Aurora の起動回数を増やさない。記録の無いセットは一覧が空で終わる。仕様の正は セット設計書 10.8.1。例外はその回を failed にする（手順 2 の部分失敗とは別。インサイト収集が例外で中断した回は取り込まない）
  4. 実行ログを succeeded / failed に更新して終了する（終了コードは 4.3）

4.3 冪等性・部分失敗・終了コード

  • 冪等性: post_insights は UNIQUE (post_id, scheduled_at)（scheduled_at = Scheduler の実行予定時刻）、account_insights_daily は UNIQUE (sns_account_id, metric_date) への INSERT-or-skip / INSERT IGNORE。Step Functions Retry による再実行は欠測分だけを埋める（取得済みスナップショットの重複・上書きは起きない）
  • 部分失敗は続行: メディア 1 件・日次 1 日単位の取得失敗は WARNING ログを残して次へ進む。全対象の処理後、失敗が 1 件でも残っていれば終了コード 1（SNS 投稿バッチと同じフェイルラウド方針。SFN Retry → Catch → 既存の ExecutionsFailed アラームで通知）。成功分は commit 済みのため失いはしない
  • 対象不存在は失敗に数えない: 投稿が Instagram 上で手動削除された場合やストーリーズが取得期限を過ぎていた場合の「対象が存在しない」系エラーは、WARNING スキップとして失敗件数に含めない（ウィンドウ内の残り期間、毎回失敗して恒常アラームになるのを防ぐ。認可エラー・レート制限エラー等は通常の失敗として扱う）
    • サイレント失敗防止のガード（16-9 実装で追加）: Meta の API は「削除済み」と「権限不足」を同一エラー（HTTP 400 / code:100 / error_subcode:33）で返すため、無条件スキップは instagram_manage_insights 未付与を成功として握り潰す。そこで ①対象不存在スキップの適用はメディアレベル限定（アカウント日次の対象不存在は設定不備とみなし通常の失敗）、②あるアカウントのメディア収集で「対象が 1 件以上あり・成功 0 件・全件が対象不存在スキップ」だった場合はアカウント単位の失敗として計上、③全メトリクスグループが無効で 1 件もリクエストが成立しなかった場合は空メトリクスを保存せず失敗として計上する
  • レート制限の連続失敗で打ち切り（16-9 実装で追加）: 同一アカウント内でレート制限起因の失敗が 3 件連続したら、そのアカウントの残作業を打ち切って ERROR ログを出す（無駄な連打の抑止）。打ち切りは失敗として扱う
  • 投稿バッチとの独立性: 本バッチは posts を読み取るのみで書き換えない。収集失敗が投稿フロー（セクション 3）へ影響することはない

5. ワークフロー連携（環境変数の使い方）

Scheduler・Step Functions からバッチへ渡る環境変数を、各バッチがどう使うかをまとめる。

D-07 期限ガード（大幅に遅延した旧実行の投稿を止める仕組み）は置かない

決めたこと
scheduled_at から一定時間を過ぎたら投稿しない期限ガードは置かず、予定時刻を指定した手動実行の可否は運用者が確認して決める（operation.html 4.1）
理由
当回固定は「後続の回が過去分を拾う」ことを防ぐが、朝の実行そのものが夜まで遅延した場合や夜に朝の予定時刻を指定して手動実行した場合は、完全一致だけでは朝の素材が夜に出る。これを実時刻で止める期限ガード（scheduled_at から一定時間を過ぎたら投稿しない）は、次の理由で導入しない（26-2 の対象に app/clock.py・期限値の受け渡しは追加しない）。
  • 自動経路の最大遅延が回の間隔より短い: Scheduler の再送上限 3600 秒（MaximumEventAgeInSeconds）+ 親の WaitForDbReady 900 秒 + RunImageBatchTask 3600 秒 × 3 回（Retry 2 回）+ 子の WaitForDbReady 900 秒 + RunSnsPostBatchTask 3600 秒 × 3 回 ≒ 最大約 8.6 時間（すべてのタイムアウト・Retry を使い切る最悪値。infra/workflow.html セクション 1.2・1.4・6）。現行の最短間隔は logic-training-1 の夜 21:00 → 朝 7:30 の 10.5 時間（朝 → 夜は 13.5 時間）、pref-ranking-1・umigame-soup-1 は 1 日以上で、自動経路では次の回の時刻に届かない
  • 手動実行は人間ゲート: 予定時刻を指定した手動起動は、運用者が対象 run の時間帯と素材の焼き込み表示（朝 / 夜のラベル）を確認してから行う手順にする（operation.html セクション 4.1）。過去の回を意図的に出す復旧（例: 週 4 回の umigame-soup-1 の欠番を翌日に出す）を期限ガードで一律に止めると、正当な手動復旧の例外設計が要り複雑になる
  • 例外: 期限ガードを置かないため例外の規定はない。手動実行の可否は上記の確認で人間が判断する
  • 再判断の条件: 同一セットの回の間隔が自動経路の最大遅延（約 8.6 時間）を下回る構成を有効化するとき（例: logic-training-1 の昼スロット 12:30 の再開 = 朝 7:30 から 5 時間）、Task タイムアウト・Retry 回数を延ばすとき、または遅延した実行が次の回の時刻を越えて投稿した事象が 1 回でも起きたとき。その時点で許容遅延・判定のタイミング（選定時 / パブリッシュ直前）・手動復旧の例外を設計する

D-08 1 回の実行で扱う生成実行は当回の 1 件

決めたこと
