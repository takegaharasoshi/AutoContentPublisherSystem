3. 主キーと冪等性キー・セット境界の整合性

主キーと FK 参照の方針（旧設計を踏襲） 各テーブルの主キーは AUTO_INCREMENT の id とし、他テーブルからの FK 参照は基本的に id に対して行う。 generation_runs の「set_id × scheduled_at」は FK の参照先ではなく、冪等性を保証する UNIQUE 制約としてのみ使用する。 scheduled_at に入る値は EventBridge Scheduler が渡すスケジュール上の実行予定時刻（UTC）であり、 リトライ・再実行でも同じスロットなら同じ値になるため、スロットの安定した識別子として機能する。
セット境界の整合性を保証する複合 FK（旧設計のパターンを踏襲・拡張） generated_media・posts・quiz_items（15-5 追加）・post_insights / account_insights_daily（16-7 追加）は、参照先テーブルの主キー id に加えて set_id を非正規化して保持し、 (set_id, 対象カラム) → 参照先テーブル(set_id, id) の複合 FK を張る（参照先テーブル側は UNIQUE (set_id, id) を持つ）。 これにより、異なるセットに属する generation_runs / prompt_configs / sns_accounts / caption_templates / audio_assets（14-4 追加。generated_media.audio_asset_id の参照先）/ quiz_stock_items（16-1 追加。quiz_items.stock_item_id の参照先）/ posts（16-7 追加。post_insights.post_id の参照先として V009 で UNIQUE (set_id, id) を追加）を 誤って組み合わせて参照することを DB レベルで防止する。この保証はセット境界までとし、 「post_media.generated_media_id が同一 generation_run に属すること」のような、より粒度の細かい整合性はアプリ層の責務とする （複合 FK をここまで深くすると generation_run_id の非正規化が連鎖し複雑さに見合わないと判断。セクション 4.6 に既知の割り切りとして明記）。

4. テーブル定義（詳細）

全テーブルの正確な型・制約・インデックスは database/V001__initial_schema.sql と V002（動画対応差分。14-5 で作成。セクション 8）を正とする。以下は各テーブルの設計意図。

4.1 batch_sets

  • set_code（UNIQUE）が S3 キー・Secret 名・EventBridge Scheduler 入力・環境変数 SET_CODE に使われる外部識別子。DB 内部の FK 参照はすべて id で行う
  • generator_name がセットに割り当てる生成方式（image-batch の strategy モジュール）を決める。値は方式名レジストリのキーであり、方式カタログ（batch-flow.html セクション 2.1）に載っている方式名を設定する
  • is_active=0 でセット廃止を表現する（レコードは削除しない。operation.html セクション 2.2）
決定（2026-07-18、Phase 10-3）: 生成方式カラム generator_name の追加（V001 直接修正） 「方式の割当は DB のセット設定で行う」（batch-flow.html セクション 2.1、2026-07-12 合意）に対し、合意より前に作成した V001 に方式名カラムがなかった設計ギャップを、generator_name カラムの追加で決着した。 V001 は Aurora 未適用（適用は Phase 10-4）のため、マイグレーション（V002）は作らず V001 を直接修正した（ユーザー確定）。カラム仕様と理由:
  • generator_name VARCHAR(50) NOT NULL（デフォルトなし）: 方式未割当のセットは画像生成バッチを実行できないため、セット登録時に明示的な割当を強制する
  • ENUM にしない: 方式の追加を「新規ファイル + レジストリ 1 行」に閉じる原則（batch-flow.html セクション 2.1）を守るため、方式追加に DDL 変更を伴わせない
  • FK・UNIQUE・専用インデックスなし: 方式はコード側レジストリの概念であり DB エンティティではない。未知の方式名の検証はアプリ層の責務（バッチ起動時のレジストリ解決で設定ミスとしてエラー）。複数セットが同一方式を共有できる
決定（2026-07-29、Phase 15-10）: ストーリーズ連続投稿の有効化フラグ stories_enabled の追加（V004） stories_enabled TINYINT(1) NOT NULL DEFAULT 0 を追加する。1 のセットは SNS 投稿バッチがリール投稿成功後に同一動画をストーリーズへ再掲する（15-9 ユーザー決定。フローは batch-flow.html セクション 3.3）。
  • セット単位のカラムで持つ理由: ストーリーズ再掲は「セットの投稿演出」の選択であり（15-9 でセット単位の有効化を決定）、バッチが実行時に参照する挙動スイッチのため設計書では表現できない（generator_name と同じ性質）。sns_accounts に持つと複数アカウント時に設定が分散し、生成方式（generator_name）に絡めると投稿側の関心が生成側へ漏れる
  • DEFAULT 0 により既存セット（fantasy-animals-1）の挙動は不変。logic-training-1 の有効化は 15-14 のセット登録時に UPDATE で行う
  • TINYINT(1) は is_active と同型（真偽フラグの既存慣行）

4.2 prompt_configs

  • is_active=1 の全件が画像生成バッチのループ対象（batch-flow.html セクション 2）。初期運用は 1 セット 1 件のみ有効化する運用ルールで「1 起動 1 枚生成」を実現する
  • UNIQUE (set_id, id) は generated_media からの複合 FK の参照先として使用する

4.3 caption_templates

決定: 紐づけ単位はセット、選定ルールは id 昇順の 1 件 キャプションテンプレートの紐づけ単位はセットとする（プロンプト設定単位にはしない。画像の内容とキャプションは独立に差し替えたいケースが多いため）。 SNS 投稿バッチは投稿本文の組み立て時（batch-flow.html セクション 3.3 手順 3）に、対象セットの caption_templates から is_active=1 のうち id 昇順で先頭の 1 件を選択して適用する。 複数の is_active=1 レコードを持つこと自体はテーブル制約上許容する（将来のローテーション・バリエーション拡張の余地）が、 初期運用では 1 セットにつき is_active=1 は 1 件のみ設定する運用ルールとする（prompt_configs の運用方針と対称）。 is_active=1 が 0 件の場合はキャプションなし（空文字）で投稿処理を継続する（画像投稿の続行を優先し、キャプション欠落は投稿失敗の理由にしない）。
決定（2026-08-01、Phase 16-1）: プレースホルダ展開方式の導入（テンプレート + quiz_items の動的組み立て） 答え・解説を動画からキャプションへ移すテコ入れ（docs/plans/development-plan.html Phase 16 冒頭の方針 (3)）のため、template_text にプレースホルダ （{{hook}} / {{question}} / {{answer}} / {{explanation}} / {{coach_comment}}）を書けるようにし、 SNS 投稿バッチが投稿時に当該生成実行の quiz_items（question_text / answer_text / content_fields）から展開する。 スキーマ変更はなし（プレースホルダはテンプレート文言の規約であり、展開規則〔プレースホルダあり = quiz_items 行必須・なし = 従来どおり素通し〕は batch-flow.html セクション 3.3 の decision を正とする）。実装は 16-3、テンプレートの差し替えは 16-4（2026-08-08 適用済み）。
  • template_text はキャプション本文とハッシュタグを含む 1 本のテキスト（Instagram の投稿本文はキャプション欄 1 つのため分割しない）。プレースホルダを含む場合は投稿時に展開される（上記 decision）
  • posts.caption_template_id + posts.caption_text_snapshot で「どのテンプレートを」「どんな本文で」投稿したかを追跡する（generated_media のプロンプトスナップショットと同じ設計思想）。プレースホルダ展開の導入後は caption_template_id が指すのはテンプレート側のみで、展開後の最終文は caption_text_snapshot が唯一の記録になる（展開元の出題データは quiz_items を generation_run_id で辿って復元できる）

4.4 generation_runs

  • UNIQUE (set_id, scheduled_at) が冪等性キー。画像生成バッチはこの制約への INSERT 成否で「新規スロット」か「同一スロットへの再実行（Step Functions Retry・重複トリガー）」かを判定する（batch-flow.html セクション 2 手順 2）
  • 投稿済みかどうかのフラグ・生成完了かどうかのフラグはどちらも持たない。前者は posts の有無、後者は generated_media の有無から導出する（状態を単一のテーブルに集約せず、実体（メディア・投稿）の存在自体を正とする設計）
決定: SNS 投稿バッチの投稿対象決定クエリの正確な定義

batch-flow.html セクション 3.1 の「投稿試行が一度もない生成実行」は、データモデルとしては以下のとおり厳密化する。 ある generation_run が投稿対象の候補（actionable）となるのは、 有効な（is_active=1）投稿先アカウントのうち少なくとも 1 つについて、posts 行が存在しないか、終端状態（success / failed / published_unconfirmed）に達していない場合である。 対象は actionable な generation_run のうち scheduled_at が最も古い 1 件。

SELECT gr.id
FROM generation_runs gr
WHERE gr.set_id = :set_id
  AND EXISTS (
    SELECT 1 FROM sns_accounts sa
    WHERE sa.set_id = gr.set_id AND sa.is_active = 1
      AND NOT EXISTS (
        SELECT 1 FROM posts p
        WHERE p.generation_run_id = gr.id
          AND p.sns_account_id = sa.id
          AND p.status IN ('success','failed','published_unconfirmed')
      )
  )
ORDER BY gr.scheduled_at ASC, gr.id ASC
LIMIT 1;

この定義により: (1) 新規の generation_run（posts なし）は当然対象になる (2) Step Functions Retry による同一実行内のタスク再起動時も同じ生成実行が再選択され、batch-flow.html セクション 3.2 の復旧ロジック（pending / container_created からの再開）が機能する (3) 異常終了（Step Functions のリトライ上限到達等）で pending / container_created のまま残った generation_run は、後続の別実行でも自動的に再選択され続ける（stale データとして後続投稿をブロックし得る問題の検知・補正手順は operation.html セクション 4.3 で確定した）。 「一度でも試行（失敗含む）した生成実行は自動では再対象にしない」（batch-flow.html セクション 3.1）は、「有効な全アカウントが終端状態に達した」場合を指すと解釈する。

インデックスは generation_runs.uq_generation_runs_set_id (set_id, id)（scheduled_at 順スキャン）と posts.uq_posts_generation_run_account_media (generation_run_id, sns_account_id, media_type)（NOT EXISTS 部分検索。V004 拡張後も左端プレフィックスで使用できる）の左端プレフィックスで十分であり、追加インデックスは設けない。

ストーリーズ行（media_type='story'。V004）は本クエリの判定に影響しない: ストーリーズ行はリール行が success に達した後にのみ作成される（batch-flow.html セクション 3.3）ため、「終端状態の posts が存在するか」の判定は常に先行するリール（またはフィード画像）行で決まり、クエリ自体は V004 後も変更しない。この不変条件により、ストーリーズが未投稿・失敗のまま残っても後続の生成実行の投稿はブロックされない（リールの success を巻き戻さない 15-9 決定と整合）。

4.7 batch_execution_logs との役割分担

決定: generation_runs と batch_execution_logs は独立（相互 FK なし） batch_execution_logs は「バッチプログラムの 1 回の起動（Step Functions 実行 / ECS タスク）」を記録する運用ログであり、 generation_runs は「1 回の起動が作った投稿単位のコンテンツ」を表す業務データである。 両者は目的が異なるため FK で結合しない。画像生成バッチは SET_CODE 解決前や generation_run 確定前に失敗する場合もあり、 batch_execution_logs は generation_run の有無に関わらず必ず 1 件記録される必要があるため、独立させる方が実装が単純になる。 どの実行がどの generation_run を作ったかを調べたい場合は、started_at と generation_runs.created_at の近接時刻で運用者が突き合わせる（通常は 1 実行 : 1 生成実行の関係になるため実務上問題ない）。

status / attempt_count の INSERT/UPDATE 手順（Step Functions Retry による再起動時に UNIQUE (execution_arn, batch_type) と衝突しないための INSERT-or-fetch パターン）は batch-flow.html セクション 1 を参照（Phase 9-5 レビューで確定）。

16-8 追加: batch_type ENUM に第 3 のバッチの値 insights_collection を V009 で追加した（ENUM('image_generation', 'sns_posting', 'insights_collection')）。ENUM の末尾追加のため既存行の値・アプリの参照は影響を受けない。バッチ種別を増やすたびに DDL 変更が要る形式だが、種別は「バッチの本数」であり増減が稀・値の一覧が固定されている方が運用ログの集計で扱いやすいため、ENUM のまま踏襲する。

なお、画像生成と SNS 投稿は別ステートマシンのため、1 つの論理実行（画像生成 → 連鎖起動された SNS 投稿）に対応する 2 行は execution_arn が異なる。子ワークフローは親と同一の実行名で起動される（infra/workflow.html セクション 3）ため、両バッチの実行ログを突き合わせる場合は execution_arn 末尾の実行名部分で相関を取る（Phase 10-1 でインフラ構築の知見を反映）。

6. 時刻の取り扱い

  • DB の全 DATETIME カラムはUTC で保存する。MySQL の DATETIME 型はタイムゾーン情報を持たないため、アプリケーション側で UTC に変換してから格納する
  • generation_runs.scheduled_at の正規化: EventBridge Scheduler が渡す環境変数 SCHEDULED_AT は ISO 8601（YYYY-MM-DDTHH:MM:SSZ、秒精度、Z 接尾辞で UTC を示す）。アプリケーションは末尾の Z を除去し YYYY-MM-DD HH:MM:SS 形式にして DATETIME カラムへ格納する（タイムゾーン変換は不要。すでに UTC のため）
  • CURRENT_TIMESTAMP は DB セッションのタイムゾーンに依存するため、アプリケーションは DB 接続直後に SET time_zone = '+00:00' を実行する
  • Aurora 側でも可能な限り Parameter Group で time_zone='UTC' を設定し、手動 DDL / Query Editor 実行時も UTC 前提を維持する
  • 冪等性キー（generation_runs の UNIQUE 制約）の比較・判定もすべて UTC ベースで行う。1 日複数回実行は scheduled_at の時刻部分で区別される
  • 表示時のタイムゾーン変換（UTC → Asia/Tokyo 等）はアプリケーション層の責務とする（初期実装では管理画面がないため当面発生しない）
