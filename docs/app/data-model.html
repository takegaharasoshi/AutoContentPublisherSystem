要約

このページはアプリの主要なテーブルと関係（データモデル）を定める。基本設計（全体）5 章 データの流れのテーブルを、列と制約の意図まで詳しくしたもの（データは機能をまたぐため、基本設計から直接このページへつなぐ）。正確な型・制約は database/ の DDL が正で、このページは設計の意図を書く。図 1 は中心のテーブルだけを抜き出した関係図。

項目要点
中心のテーブルgeneration_runs（1 回の画像生成バッチ起動 = 1 行 = 投稿の単位。set_id × scheduled_at で一意）
投稿の記録posts（生成実行 × アカウント × メディア種別で 1 行・5 状態）+ post_media
在庫と出題履歴事前ビルド方式ごとに在庫（*_stock_items）と出題履歴（quiz_items / ranking_items / umigame_items）の組。在庫は LRU 順繰りで使う（4 章）
効果測定post_insights・account_insights_daily（JSON 全量）+ KPI のビュー（4.11）
セット境界子テーブルに set_id を持たせた複合 FK で、別セットの行を組み合わせた参照を DB で防ぐ（3 章）
時刻DB の DATETIME はすべて UTC（6 章）

3. 主キーと冪等性キー・セット境界の整合性

全テーブルに共通するキーの決まり。

主キーと FK 参照の方針（旧設計を踏襲） 各テーブルの主キーは AUTO_INCREMENT の id とし、他テーブルからの FK 参照は基本的に id に対して行う。 generation_runs の「set_id × scheduled_at」は FK の参照先ではなく、冪等性を保証する UNIQUE 制約としてのみ使用する。 scheduled_at に入る値は EventBridge Scheduler が渡すスケジュール上の実行予定時刻（UTC）であり、 リトライ・再実行でも同じスロットなら同じ値になるため、スロットの安定した識別子として機能する。

セット境界の整合性を保証する複合 FK → 理由 D-01

generated_media・posts・quiz_items（15-5 追加）・post_insights / account_insights_daily（16-7 追加）は、参照先テーブルの主キー id に加えて set_id を非正規化して保持し、 (set_id, 対象カラム) → 参照先テーブル(set_id, id) の複合 FK を張る（参照先テーブル側は UNIQUE (set_id, id) を持つ）。 これにより、異なるセットに属する generation_runs / prompt_configs / sns_accounts / caption_templates / audio_assets（14-4 追加。generated_media.audio_asset_id の参照先）/ quiz_stock_items（16-1 追加。quiz_items.stock_item_id の参照先）/ posts（16-7 追加。post_insights.post_id の参照先として V009 で UNIQUE (set_id, id) を追加）を 誤って組み合わせて参照することを DB レベルで防止する。この保証はセット境界までとし、 「post_media.generated_media_id が同一 generation_run に属すること」のような、より粒度の細かい整合性はアプリ層の責務とする 。

4. テーブル定義（詳細）

テーブルごとの列と設計の意図。全テーブルの正確な型・制約・インデックスは database/ の DDL（V001__initial_schema.sql と V002 以降の差分。セクション 8）を正とする。

4.1 batch_sets

  • set_code（UNIQUE）が S3 キー・Secret 名・EventBridge Scheduler 入力・環境変数 SET_CODE に使われる外部識別子。DB 内部の FK 参照はすべて id で行う
  • generator_name がセットに割り当てる生成方式（image-batch の strategy モジュール）を決める。値は方式名レジストリのキーであり、方式カタログ（batch-flow.html セクション 2.1）に載っている方式名を設定する
  • is_active=0 でセット廃止を表現する（レコードは削除しない。operation.html セクション 2.2）

generator_name（生成方式の割当） → 理由 D-02

  • generator_name VARCHAR(50) NOT NULL（デフォルトなし）
  • ENUM にしない
  • FK・UNIQUE・専用インデックスなし: 未知の方式名の検証はアプリ層の責務（バッチ起動時のレジストリ解決で設定ミスとしてエラー）。複数セットが同一方式を共有できる

stories_enabled（ストーリーズ再掲の有効化。V004） → 理由 D-03

stories_enabled TINYINT(1) NOT NULL DEFAULT 0 を追加する。1 のセットは SNS 投稿バッチがリール投稿成功後に同一動画をストーリーズへ再掲する（15-9 ユーザー決定。フローは batch-flow.html セクション 3.3）。
  • DEFAULT 0 により既存セット（fantasy-animals-1）の挙動は不変。logic-training-1 の有効化は 15-14 のセット登録時に UPDATE で行う
  • TINYINT(1) は is_active と同型（真偽フラグの既存慣行）

problem_snapshot_enabled（問題スナップショットの出力。V012） → 理由 D-04

problem_snapshot_enabled TINYINT(1) NOT NULL DEFAULT 0 を追加する。1 のセットは SNS 投稿バッチがリール投稿成功直後に、当該実行の umigame_items と prompt_configs.prompt_text から問題スナップショット JSON を S3 assets/{set_code}/problems/{media_id}.json へ出力する（batch-flow.html セクション 3.3 手順 6。コメント自動返信経路〔infra/stacks.html 3.6〕の読み取り元）。Phase 31（31-2 設計）で quiz_items の実行にも広げ、logic-training-1 は 31-5 で 1 にする（quiz 用 JSON の読み手は脳みそコーチの正解返信 Lambda〔infra/stacks.html 3.7〕。quiz 側は出力の記録列を持たない）。
  • DEFAULT 0 により既存 3 セットの挙動は不変。umigame-soup-1 の有効化は 21-7 のセット登録で行う
  • DDL は database/V012__umigame_stock.sql（本文は 21-4a。本フラグの ALTER と 4.14 / 4.15 の CREATE を同一ファイルに含める）

4.2 prompt_configs

  • is_active=1 の全件が画像生成バッチのループ対象（batch-flow.html セクション 2）。初期運用は 1 セット 1 件のみ有効化する運用ルールで「1 起動 1 枚生成」を実現する
  • UNIQUE (set_id, id) は generated_media からの複合 FK の参照先として使用する

4.3 caption_templates

紐づけ単位はセット、選定ルールは id 昇順の 1 件 → 理由 D-05

キャプションテンプレートの紐づけ単位はセットとする。 SNS 投稿バッチは投稿本文の組み立て時（batch-flow.html セクション 3.3 手順 3）に、対象セットの caption_templates から is_active=1 のうち id 昇順で先頭の 1 件を選択して適用する。 複数の is_active=1 レコードを持つこと自体はテーブル制約上許容するが、 初期運用では 1 セットにつき is_active=1 は 1 件のみ設定する運用ルールとする（prompt_configs の運用方針と対称）。 is_active=1 が 0 件の場合はキャプションなし（空文字）で投稿処理を継続する。

プレースホルダ展開（16-1） → 理由 D-06

template_text にプレースホルダ （{{hook}} / {{question}} / {{answer}} / {{explanation}} / {{coach_comment}}）を書けるようにし、 SNS 投稿バッチが投稿時に当該生成実行の quiz_items（question_text / answer_text / content_fields）から展開する。 スキーマ変更はなし（プレースホルダはテンプレート文言の規約であり、展開規則〔プレースホルダあり = quiz_items 行必須・なし = 従来どおり素通し〕は batch-flow.html 3.4「キャプションの作り方」 を正とする）。実装は 16-3、テンプレートの差し替えは 16-4（2026-08-08 適用済み）。
  • template_text はキャプション本文とハッシュタグを含む 1 本のテキスト（Instagram の投稿本文はキャプション欄 1 つのため分割しない）。プレースホルダを含む場合は投稿時に展開される（上記「プレースホルダ展開」）
  • posts.caption_template_id + posts.caption_text_snapshot で「どのテンプレートを」「どんな本文で」投稿したかを追跡する（generated_media のプロンプトスナップショットと同じ設計思想）。プレースホルダ展開の導入後は caption_template_id が指すのはテンプレート側のみで、展開後の最終文は caption_text_snapshot が唯一の記録になる（展開元の出題データは quiz_items を generation_run_id で辿って復元できる）

4.4 generation_runs

  • UNIQUE (set_id, scheduled_at) が冪等性キー。画像生成バッチはこの制約への INSERT 成否で「新規スロット」か「同一スロットへの再実行（Step Functions Retry・重複トリガー）」かを判定する（batch-flow.html セクション 2 手順 2）
  • 投稿済みかどうかのフラグ・生成完了かどうかのフラグはどちらも持たない。前者は posts の有無、後者は generated_media の有無から導出する（状態を単一のテーブルに集約せず、実体（メディア・投稿）の存在自体を正とする設計）

SNS 投稿バッチの投稿対象決定クエリの定義（当回固定） → 理由 D-07

batch-flow.html セクション 3.1 の当回固定は、データモデルとしては以下のとおり定義する。 当回の generation_run が投稿対象（SELECTED）となるのは、 ① set_id × scheduled_at（入力の SCHEDULED_AT）が完全一致し、② generated_media が 1 件以上あり、③ 有効な（is_active=1）投稿先アカウントのうち少なくとも 1 つについて posts 行が存在しないか終端状態（success / failed / published_unconfirmed）に達していない場合である。 成立条件を 1 文にすると次のとおり（手動確認でもこの形を使う）。

SELECT gr.id
FROM generation_runs gr
WHERE gr.set_id = :set_id
  AND gr.scheduled_at = :scheduled_at
  AND EXISTS (
    SELECT 1 FROM generated_media gm
    WHERE gm.generation_run_id = gr.id
  )
  AND EXISTS (
    SELECT 1 FROM sns_accounts sa
    WHERE sa.set_id = gr.set_id AND sa.is_active = 1
      AND NOT EXISTS (
        SELECT 1 FROM posts p
        WHERE p.generation_run_id = gr.id
          AND p.sns_account_id = sa.id
          AND p.status IN ('success','failed','published_unconfirmed')
      )
  );

アプリは上の 1 文をそのまま使わず、①〜③ を段階に分けて判定し理由を返す（0 行の理由が「当回の run がない（RUN_NOT_FOUND）」「素材がない（NO_MEDIA）」「全アカウント終端済み（ALREADY_TERMINAL）」のどれかを区別するため。前 2 つは異常終了、最後は 0 件の正常終了。結果の分類は batch-flow 3.1 の表）。① は UNIQUE (set_id, scheduled_at) により高々 1 行なので LIMIT は不要。

この定義により: (1) 新規の当回 generation_run（posts なし）は対象になる (2) Step Functions Retry による同一実行内のタスク再起動時も、入力の予定時刻が変わらないため同じ生成実行が再選択され、batch-flow.html セクション 3.2 の復旧ロジック（pending / container_created からの再開）が機能する (3) 異常終了で pending / container_created のまま残った過去の generation_run や空の generation_run は、後続の別の回からは選ばれず、後続投稿をブロックしない（記録の確定は operation.html セクション 4.3 の人間の補正）。 「一度でも試行（失敗含む）した生成実行は自動では再対象にしない」は、当回の「有効な全アカウントが終端状態に達した」場合を指す。

インデックスは ① が generation_runs.uq_generation_runs_idempotency (set_id, scheduled_at)、② が generated_media の冪等性キー（generation_run_id が左端）、③ が posts.uq_posts_generation_run_account_media (generation_run_id, sns_account_id, media_type) の左端プレフィックスで足り、追加インデックス・DDL の変更は不要。

ストーリーズ行（media_type='story'。V004）は本クエリの判定に影響しない: ストーリーズ行はリール行が success に達した後にのみ作成される（batch-flow.html セクション 3.3）ため、「終端状態の posts が存在するか」の判定は常に先行するリール（またはフィード画像）行で決まる。ストーリーズが未投稿・失敗のまま残っても、その回が再選択されることはない（リールの success を巻き戻さない 15-9 決定と整合）。

4.7 batch_execution_logs との役割分担

generation_runs と batch_execution_logs は独立（相互 FK なし） → 理由 D-11

batch_execution_logs は「バッチプログラムの 1 回の起動（Step Functions 実行 / ECS タスク）」を記録する運用ログであり、 generation_runs は「1 回の起動が作った投稿単位のコンテンツ」を表す業務データである。 どの実行がどの generation_run を作ったかを調べたい場合は、started_at と generation_runs.created_at の近接時刻で運用者が突き合わせる（通常は 1 実行 : 1 生成実行の関係になるため実務上問題ない）。

status / attempt_count の INSERT/UPDATE 手順（Step Functions Retry による再起動時に UNIQUE (execution_arn, batch_type) と衝突しないための INSERT-or-fetch パターン）は batch-flow.html セクション 1 を参照（Phase 9-5 レビューで確定）。

16-8 追加: batch_type ENUM に第 3 のバッチの値 insights_collection を V009 で追加した（ENUM('image_generation', 'sns_posting', 'insights_collection')）。ENUM の末尾追加のため既存行の値・アプリの参照は影響を受けない。ENUM のまま踏襲する → 理由 D-33。

なお、画像生成と SNS 投稿は別ステートマシンのため、1 つの論理実行（画像生成 → 連鎖起動された SNS 投稿）に対応する 2 行は execution_arn が異なる。子ワークフローは親と同一の実行名で起動される（infra/workflow.html セクション 3）ため、両バッチの実行ログを突き合わせる場合は execution_arn 末尾の実行名部分で相関を取る（Phase 10-1 でインフラ構築の知見を反映）。

6. 時刻の取り扱い

DB とアプリでの時刻の扱い。

  • DB の全 DATETIME カラムはUTC で保存する。MySQL の DATETIME 型はタイムゾーン情報を持たないため、アプリケーション側で UTC に変換してから格納する
  • generation_runs.scheduled_at の正規化: EventBridge Scheduler が渡す環境変数 SCHEDULED_AT は ISO 8601（YYYY-MM-DDTHH:MM:SSZ、秒精度、Z 接尾辞で UTC を示す）。アプリケーションは末尾の Z を除去し YYYY-MM-DD HH:MM:SS 形式にして DATETIME カラムへ格納する（タイムゾーン変換は不要。すでに UTC のため）
  • CURRENT_TIMESTAMP は DB セッションのタイムゾーンに依存するため、アプリケーションは DB 接続直後に SET time_zone = '+00:00' を実行する
  • Aurora 側でも可能な限り Parameter Group で time_zone='UTC' を設定し、手動 DDL / Query Editor 実行時も UTC 前提を維持する
  • 冪等性キー（generation_runs の UNIQUE 制約）の比較・判定もすべて UTC ベースで行う。1 日複数回実行は scheduled_at の時刻部分で区別される
  • 表示時のタイムゾーン変換（UTC → Asia/Tokyo 等）はアプリケーション層の責務とする（初期実装では管理画面がないため当面発生しない）
