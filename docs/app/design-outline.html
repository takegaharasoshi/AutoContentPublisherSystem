要約

このページはアプリ設計（docs/app/）の親ページで、設計書の分け方、全セットに共通の処理の単位、分冊とインフラ設計の受け渡しを定める。基本設計（全体）3 章 配信面の 4 系統のうち、アプリの処理にあたる部分の詳細設計の入口にあたる。図 1 は、アプリ設計書が「共通 → 方式別 → セット別」の 3 層に分かれ、どの層が何を持つかを表す。

項目要点
設計書の分け方共通設計書 4 本 + 方式別（generators/）+ セット別（sets/）。セット追加で sets/ が 1 本、方式の本採用で generators/ が 1 本増える（1 章）
処理の単位1 回の画像生成バッチ起動 = 1 生成実行 = アカウントごとに 1 投稿（2 章）
セットの表し方セットは DB のレコード・設定カラムと Scheduler・Secret で表し、スタックは機能単位（1.1）
受け渡しの契約SET_CODE・SCHEDULED_AT・Secret 名規約の意味（5 章）

アプリ設計書の一覧と、それぞれが何を持つかを表にする。全体方針と分冊間の整合はこのページ、ドメイン別の中身は各分冊が正。

1.1 セット別設計書のルール（複数セット前提の 3 層構造）

セットと生成方式が増えても共通設計書を変えずに済むよう、設計書を 3 層に分ける決まり → 理由 D-01。

  • 3 層構造: 共通設計書（本書 + 3 分冊）は全セット共通の骨格と生成方式の契約・方式カタログを定め、セット追加・方式追加では変更しない（方式カタログへの 1 行追加・状態の更新を除く）。増える設計書は、生成方式の本採用で docs/app/generators/<方式名>.html が 1 本、セット追加で docs/app/sets/<set_code>.html が 1 本
  • 方式層のルール: 生成方式の設計は batch-flow.html に直接書き足さず、1 方式 1 本で分冊する。batch-flow.html に置くのは契約（方式インターフェース）と方式カタログ（1 方式 1 行の表）のみ（batch-flow.html セクション 2.1）。試行段階では設計書を書かず、セットが本採用した時点で作成する
  • セット別設計書の標準記載項目: テーマ、投稿先アカウント構成、スケジュール（投稿頻度）、プロンプトの作り方（固定 / AI 生成等）、キャプションの作り方（テンプレート / AI 生成等）、失敗時ポリシー、音源の構成（動画方式のセットのみ）、共通フローからの差分・特記事項
  • 拡張ポイント方式: セットごとに変わりうる箇所は、共通分冊側に「セット別拡張ポイント」として明示する（batch-flow.html セクション 2・3）。新しい方式が共通の骨格に影響する場合は、共通分冊に拡張ポイントを追記した上で、セット別設計書には選択と差分のみを書く（同じ情報を 2 箇所に書かない）
  • 実データとの役割分担: プロンプト文言・スケジュール時刻等の実データの正は DB / CDK コード。セット別設計書には意図・方針・方式の選択を書く
  • 廃止・退役時の扱い: セット廃止（スクラップ&ビルド）では設計書を削除せず、廃止の旨を付けて履歴として残す（手順は operation.html セクション 2.2）。採用セットがなくなった生成方式も設計書を残し、方式カタログのステータスを「退役」（コードを残す）か「廃止」（コードからも外す）にする
  • セットとインフラ: スタックは機能単位で、セットの追加だけでは増えない。セットは「Scheduler（ImageBatchStack の画像生成 + InsightsBatchStack のインサイト収集 2 件）+ Secrets Manager の Secret + DB レコード」として表される（operation.html セクション 2.1）。セットが新しい機能を持ち込む場合は、その機能のスタックが増える（umigame-soup-1 のコメント自動返信 = CommentReplyStack）。このときインフラ設計書にもその機能の節が増える → 理由 D-04
  • 資材の共有: アプリ資材（コンテナ・CI/CD パイプライン）はサービス単位で全セットが共有し、セット差分は DB のセット設定と生成方式の strategy モジュール（batch-flow.html セクション 2.1）で表す → 理由 D-02
  • 作成タイミング: 実ファイル・雛形は必要になった時点で作成する（sets/ はセット追加時、generators/ は方式の本採用時）

2. 全体方針: 処理単位の不変条件

全セット・全方式に共通する処理の単位を定める。バッチ処理フロー設計の手順はすべてこの単位の上に立つ。

不変条件: 1 回の画像生成バッチ起動 = 1 投稿（アカウントごと）。1 回の生成実行が「1 投稿分のコンテンツ」を作り、この単位を generation_runs（生成実行）エンティティとして永続化する。投稿バッチは生成実行を処理対象の単位とする → 理由 D-03。

  • カルーセル投稿でも「1 実行で生成された複数メディア = 1 投稿に束ねるメディア群」となり、この不変条件は変わらない
  • 動画（リール）でも不変（1 実行 = 動画 1 本 = 1 投稿）。ストーリーズ再掲はリール成功後の追加の投稿行として同じ実行の内側で扱う
  • 多プラットフォーム展開時は、同一の生成実行がアカウント数分の投稿レコードになる（内容は 1 つ）

この不変条件のもとでの処理手順の骨子（画像生成: セット解決 → 生成実行の作成 = 冪等性のアンカー → 方式の実行・S3 保存・DB 登録 / SNS 投稿: 当回の生成実行〔セット × SCHEDULED_AT で特定〕を対象にアカウントごとに投稿）は、分冊 バッチ処理フロー設計 に定める。

3. データモデル概要

2 章の単位をテーブルの構造で保証する考え方の要約。テーブルの全体と ER 図はデータモデル設計が正。

generation_runs（生成実行）を中心に、posts（投稿 = 生成実行 × アカウント × メディア種別）・post_media（1 投稿 : N メディアの中間テーブル）・generated_media（生成メディア: 画像・動画）を置き、セット配下の設定として batch_sets / prompt_configs / caption_templates / sns_accounts / audio_assets（音源）を持つ。事前ビルド方式は方式ごとに在庫テーブル（quiz_stock_items / ranking_stock_items / umigame_stock_items）と出題履歴テーブル（quiz_items / ranking_items / umigame_items）の組を持つ。効果測定はインサイト収集バッチが post_insights（投稿別スナップショット）・account_insights_daily（アカウント日次）へ、コメント記録は umigame_comment_logs へ蓄積する。運用ログは batch_execution_logs。

データモデルは全セット共通であり、セット間の違いはレコード・設定カラムで表現する。

4. 運用方針の骨子

アプリの運用の方針を一覧にする。手順の正はアプリ運用設計。

  • セット追加: セット別設計書の作成 → Secret 作成・検証 → DB 登録 → Scheduler 追加 deploy → is_active で稼働開始
  • セット廃止: is_active=0 + Scheduler 削除。データと設計書は残す
  • プロンプト / キャプション / 音源: DB 直接運用（管理画面は将来拡張）
  • 投稿失敗時: 通知のみ・必要時のみ手動起動。一過性エラーは公開前だけアプリ内で 1 回やり直す（Phase 28）
  • トークン: 投稿用の Instagram トークンは手動で再認可し、リマインダー 1 件で期限を管理する。コメント返信用（umigame-soup-1）はトークン更新 Lambda が毎週自動で更新する
  • 効果測定: インサイト収集バッチによる自動収集 + API 外指標の手動確認・月次 KPI 転記

5. ワークフロー連携・Secret 規約の意味付け

インフラ設計とアプリ設計の受け渡しに使う識別子の意味を定める。フロー上の使い方は batch-flow.html セクション 5、Secret の運用は operation.html セクション 5。

項目意味付け
SET_CODE batch_sets.set_code（人が定義する安定した外部識別子）。EventBridge Scheduler の入力で指定し、各バッチが受け取って内部 ID に解決する
SCHEDULED_AT スケジュール実行時刻（UTC、Scheduler の <aws.scheduler.scheduled-time> 由来）。生成実行（generation_runs）の冪等性キー（セット × SCHEDULED_AT で一意）であり、1 日複数回実行は DATETIME 粒度で区別される。インサイト収集バッチも受け取り、post_insights の冪等性キーに使用する。SNS 投稿バッチも必須で受け取り、投稿対象の生成実行をセット × SCHEDULED_AT の完全一致で特定する。形式は UTC・秒精度の YYYY-MM-DDTHH:MM:SSZ に固定し、欠落・不正時に現在時刻を代入したり最古の生成実行へフォールバックしたりしない（親 → 子 SFN の受け渡しは infra/workflow.html セクション 3・4、選定と結果の分類は batch-flow.html セクション 3.1） → 理由 D-05
SNS Secret 規約の構成要素 acps/{env}/{set_code}/sns/{platform}/{account_code} のうち、set_code = batch_sets.set_code、account_code = sns_accounts.account_code（作成後変更不可、Secret 名導出専用）。1 セット多プラットフォーム展開とも {platform} の分岐で整合する
アプリ用環境変数（BATCH_SIZE_LIMIT 等） 件数の総量制御用は追加しない（batch-flow.html セクション 5）。インサイト収集バッチの収集ウィンドウ MEDIA_LOOKBACK_DAYS は総量制御ではなく対象期間の指定（batch-flow.html セクション 4.1）

D-01 設計書を共通 / 方式別 / セット別の 3 層に分ける

決めたこと
共通設計書はセット・方式の追加で変えず、方式の本採用で generators/ が 1 本、セット追加で sets/ が 1 本増える体系にする
理由
A-4 計画レビューで「スクラップ&ビルドでセットが増えていく前提で、共通・上位の設計は変更せず、セットが増えるたびに設計書が 1 本増えるような管理しやすい体系にしたい」というユーザー要望を受け、まず共通 / セット別の 2 層にした（要望の記録は A-1 壁打ち記録の追記）。その後、生成方式もスクラップ&ビルドで多数試作する想定から、方式層を加えた 3 層（契約 / 方式 / セット）へ広げた。方式の設計を batch-flow.html に書き足さないのは肥大化を防ぐため
日付・出典
2026-07-06（2 層）・2026-07-12 合意 → 2026-07-15 反映（3 層。開発記録 の 10-1）

D-02 セット間のデプロイ分離・資材分離はしない

決めたこと
アプリ資材（コンテナ・CI/CD パイプライン）はサービス単位の共有を続け、セット差分は DB のセット設定と生成方式 strategy モジュールで表す
理由
現時点のセット数・変更頻度では、分離の手間に見合う独立性の利得がない
退けた案
①デプロイ分離（Scheduler の payload でセットごとに使うタスク定義リビジョンを固定）②資材分離（セットをサービスとして切り出す）の段階的エスカレーション。将来デプロイ分離を入れる場合は、セット間の結合点が DB スキーマの後方互換性に移る点に留意する（関連論点は課題体系）
日付・出典
2026-07-12 整理

D-03 処理の単位を「画像」ではなく「生成実行」にする

決めたこと
「1 生成実行 = 1 投稿（アカウントごと）」を不変条件とし、投稿対象の単位を生成実行にする
理由
旧設計と A-2 初版は「画像」単位で投稿対象を検索していたが、A-2 レビューでのユーザー指摘（投稿バッチの処理単位は「投稿」であるべき。画像単位では将来のカルーセルで画像の束ね方が定まらない）を受けて変えた。将来のセット別失敗時ポリシー（追いつく / 捨てる）は、投稿対象の検索とは別の経路として設計する（batch-flow.html 3.4）
退けた案
画像単位の投稿対象検索（旧設計）
日付・出典
2026-07-06（A-2 レビュー）

D-04 スタックは機能単位とし、セットの追加では増やさない

決めたこと
CDK スタックは機能単位とし、セットは既存スタック内の Scheduler + Secret + DB レコードで表す。セットが新しい機能を持ち込むときだけ、その機能のスタックを足す
理由
Step Functions・ECS タスク定義・コンテナイメージを全セットで共有し、Scheduler が渡す set_code でセットを切り替える構成のため、セットごとのスタックは要らない（2026-07-06 のユーザー質問を受けて明記）。当初は「インフラ設計書・CDK スタックはセット追加で増えない・変わらない」と書いていたが、umigame-soup-1 はコメント自動返信という新しい機能を持ち込み CommentReplyStack が増えたため、「増えるのは機能の追加のとき」と改めた（課題 I-040 の掃除リスト）
日付・出典
2026-07-06・2026-10-18 改め（30-7）

D-05 SNS 投稿バッチにも SCHEDULED_AT を渡す

決めたこと
SNS 投稿の Step Functions にも scheduled_at を渡し、投稿バッチは当回の生成実行をセット × SCHEDULED_AT の完全一致で特定する
理由
A-3（インフラ設計との突き合わせ）の帰結は「SNS 投稿 Step Functions への scheduled_at 追加は不要」（最古の actionable な生成実行を選ぶ方式）だったが、空の生成実行が後続を塞ぐ事象（I-014）が起きたため改めた（理由の詳細は batch-flow.html D-06）
日付・出典
2026-07-06（A-3）→ 2026-10-13 改め（Phase 26-1。実装 26-2・本番切替 26-3）
