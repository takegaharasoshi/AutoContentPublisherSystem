1. 方式概要

イラスト〜動画を事前にローカルでビルドし、全数人間レビューのうえ S3 に作り置きしておき、実行時は問題ストック（quiz_stock_items）の LRU 順繰り選定と事前動画の取得・返却だけを行う軽量なクイズ方式。実行時に外部 API（画像生成・LLM）を一切呼ばず、Pillow 組版・ffmpeg 合成も行わない。動画の作り（16 秒・4 カット・版面固定・答えはキャプションへ）は gpt-quiz-multicut の 16-1 / 16-2b 設計をそのまま踏襲し、生成のタイミングを実行時からビルド時へ移しただけの関係にある。

決定（2026-08-08 ユーザー決定、16-3 完了後の仕様変更）: 動画の事前生成方式への転換 16-3 の実 API 品質確認で、情景が意味的に文字を誘発するケース（動物園ゲートの「ZOO」看板・階数ボタンの数字）はプロンプトの禁止指定では抑えきれないことが判明した。一方、Codex 組み込みの画像生成（imagegen。サブスク内・API 課金なし）に画風指定 1 行を足した再試行では、6 枚全てがブランドのフラットイラスト調に統一され禁止事項も全遵守となり品質面で最良だった（比較の詳細は development-log.md の 16-3 (8)）。これを受け、実行時生成をやめ事前生成へ転換する。狙いは 3 点:
  • イラスト API 費のゼロ化: imagegen はサブスク内のため、logic-training-1 の生成 API 定常費が消える（事業戦略書セクション 3.1）
  • 品質担保の構造化: 投稿される完成形（動画そのもの）を事前に全数人間レビューできる。イラストの文字混入・画風ブレは「レビューで弾いて再生成」で確実に止まる（プロンプト禁止だけに頼らない）
  • 実行時の失敗面の縮小: 実行時の失敗要因が「ストック選定 + S3 取得 + 投稿」だけになり、生成起因の障害（8/4 型のイラスト生成失敗等）が構造的に消える
生成基盤インフラ（Step Functions・Scheduler・ECS・共通骨格）は fantasy-animals-1 が使い続けるため不変。切替は batch_sets.generator_name の UPDATE 1 本で行い、旧方式へも同じ操作で戻せる（prompt_configs は無変更で両方式に有効）。

2. 契約の実装

共通の契約（batch-flow.html「生成方式の契約」）を generate(context: GeneratorContext) -> GeneratorResult で実装する。冪等性（完了判定）・S3 保存・DB 登録・トランザクション制御は共通骨格（processing.py）の責務であり、本方式は関与しない。共通骨格・SNS 投稿バッチ・キャプション展開（プレースホルダ 5 種）は一切変更しない。

処理順序: ① parameters 検証 → ② スロット解決 → ③ 問題ストック取得（ビルド済み限定の LRU。セクション 4） → ④ S3 から事前動画を取得（欠落はフェイルラウド。セクション 5）→ ⑤ quiz_items INSERT + ストックの last_used_at / use_count 更新 → ⑥ GeneratorResult を返す。フォント・コーチアセット・SE・BGM の事前検査、API キー取得（API_SECRET_ARN）はいずれも不要（実行時に使わないため。所要は旧方式の数分から数十秒レベルへ短縮見込み）。

3. 入力（parameters とスロット解決）

parameters のキー仕様・検証・スロット解決ロジックは gpt-quiz-multicut と完全に同一（方式設計書セクション 3 を正とする。slots の 5 フィールド必須・休止パラメータの無視・JST 時による決定的解決・早朝の巻き戻し）。これにより logic-training-1 の登録済み prompt_configs は無変更で使え、切替（16-4）は batch_sets.generator_name の UPDATE のみになる。スロットの quiz_type / difficulty はストック取得の絞り込みキー、slot_code / slot_label はビルド時の版面（パレット・時間帯ラベル）に対応する（セクション 8 の warn）。

4. 問題ストックの取得（ビルド済み限定の LRU 順繰り）

出題は quiz_stock_items（data-model.html セクション 4.10）から LRU 順繰りで取得する。gpt-quiz-multicut の選定クエリ（同セクション 5）に対する差分は、事前動画がビルド済みの行（video_s3_key IS NOT NULL）だけを候補にする絞り込みが加わる点のみ。

SELECT id, question_text, answer_text, content_fields, video_s3_key, video_audio_asset_id
  FROM quiz_stock_items
 WHERE set_id = %s AND quiz_type = %s AND difficulty = %s AND is_active = 1
   AND video_s3_key IS NOT NULL
 ORDER BY last_used_at ASC, id ASC LIMIT 1
  • 0 件は RuntimeError で異常終了（ストック未投入・全行無効化に加え「投入済みだが全行未ビルド」も検知するフェイルラウド）
  • 再利用（last_used_at IS NOT NULL の行を選んだ場合）は WARNING ログ（補充遅延のサイン。従来どおり）
  • 未ビルトの有効在庫（video_s3_key IS NULL）が同じ型・難度に存在する場合も WARNING ログを出す（COUNT 1 本。投入後のビルド漏れ・ビルド待ちのサイン。週次の在庫確認クエリ拡張版〔operation.html セクション 3〕でも拾える）
  • 防御的フィールド検査は維持: question_text / answer_text / content_fields の必須・非空・文字数上限（gpt-quiz-multicut セクション 5 のフィールド仕様を正とする）。動画には使わないが、キャプションのプレースホルダ展開（quiz_items 経由）の入力になるため検査を残す。不備は異常終了
  • last_used_at / use_count の UPDATE は事前動画の取得成功後に行い、commit は共通骨格に委ねる（失敗時はストック消費の副作用ごとロールバック。従来どおり）
決定（16-3b）: 未ビルト行は「選ばれない」のであって「エラーにしない」 未ビルト行を候補に含めてから video_s3_key IS NULL をエラーにする案は、他にビルド済み在庫があるのに 1 行の未ビルトでスロットが止まるため不採用。絞り込みで除外すれば、週次補充の「投入 → ビルド」の間に実行が走っても投稿は止まらない（新規行は未使用でも候補外のまま）。未ビルトの滞留は上記 WARNING と在庫確認クエリ拡張版で検知する。
決定（16-3b）: 再利用時の同一動画の再投稿を許容する 旧方式（実行時生成）ではイラストを毎回新規生成するため、同じ問題の再出題でも見た目が変わった。本方式では再利用時に完全に同一の動画がもう一度投稿される。これを許容する（ユーザー決定の 16-3b 具体化）: 再利用は補充遅延時のフォールバックであり頻度が低く（在庫 2 週間分 + 週次補充の運用では発生しないのが正常）、発生しても同一動画の再登場は 2 週間以上空く。16-1 で「再利用は意図的な再出題として許容」と決定済みで、見た目の同一性はその延長にある。Instagram 側の同一動画再投稿の制限は現時点で確認されていない（問題が出た場合は再ビルドで対応する）。

5. 事前動画の取得

選定したストック行の video_s3_key から MP4 を取得する（acps_shared.s3.get_object）。キーの値はビルドツーリングが登録した assets/{set_code}/prebuilt/{content_key}.mp4（命名規約は data-model.html セクション 5。ファイル名は環境非依存の業務キー content_key で組む — 16-3d 決定。参照は常に DB カラム経由で行い、方式がキーを組み立てることはしない — audio_assets.time_slot と同じ「S3 プレフィックスは配置規約に留める」原則）。

  • 取得失敗（NoSuchKey・アクセスエラー）は異常終了（フェイルラウド。DB は「ビルド済み」なのに実体がない = DB と S3 の不整合であり、縮退して別の問題に差し替えることはしない）
  • 取得したバイト列をそのまま MediaOutput として返す。再エンコード・検査変換は行わない（形式はビルド時にレンダラーが保証し、全数レビューで確認済み）。寸法・尺のメタ情報は方式定数（1080x1920 / 16 秒）を記録する

7. エラーハンドリング

方式内のリカバリループはない。異常（parameters 不正・ビルド済みストック 0 件・ストック行のフィールド不備・video_audio_asset_id 未記録・事前動画の取得失敗）はすべて例外を送出し、共通骨格が捕捉 → ロールバック → Step Functions Retry → 失敗アラーム通知につながる（gpt-quiz-multicut セクション 11 と同型）。実行時の失敗要因が大きく減るため、残る主な失敗面は SNS 投稿側（Graph API）になる。

8. 事前ビルドパイプライン（供給側の設計）

事前動画の供給はローカルの事前ビルドツーリングが担う。ツーリングは content/video-build/<set_code>/ に置いて git 管理し（置き場・運用ルールは operation.html セクション 3）、週次補充（ストック投入）とセットで回す。工程は 5 段:

  1. 対象抽出: video_s3_key IS NULL の有効ストック行を列挙する（初回 = 16-3d は 42 問全量、以後は補充分のみ）
  2. イラスト生成（imagegen 委譲 + 3:2 センタークロップ）: 行の illustration_scene からイラストプロンプトを組み立て（gpt-quiz-multicut のコード側固定プロンプト〔情景 + スロット別ムード + ブランド配色 + 禁止事項 = 同セクション 6〕を移植し、画風 1 行を恒久追加 = 下記 decision）、Codex 組み込み画像生成（imagegen）で生成する。imagegen は 3:2 の直接指定ができない（生成元 1672x941 等）ため、3:2 センタークロップ → 1536x1024 リサイズの後処理を掛けて組版入力の縦横比を旧方式と一致させる
  3. 組版 + ffmpeg ビルド: gpt_quiz_multicut.py のレンダラー（Pillow 組版 + ffmpeg 合成。8 枚版面・連続ズーム・SE ディレイ・BGM トリム + afade）を import して流用する（作りは 同セクション 8〜9 を正とし、本書には重複記載しない）。BGM はスロット別 LRU 選曲 + last_used_at 更新をビルド時に行う（セクション 6 の decision）。実行環境はホストに ffmpeg がないため image-batch の Docker イメージにリポジトリをマウントして実行する（16-3 のオフライン確認と同じ方法）
  4. レビューシート生成 → 全数人間レビュー: ビルドした動画（+ イラスト・カット代表画像）を一覧できるレビューシートを生成し、ユーザーが全数レビューする。NG はイラスト再生成（imagegen 再試行）または情景修正（illustration_scene の書き直し → DB 更新）→ 再ビルドで解消する（レビュー観点は operation.html セクション 3 の手順 5）
  5. S3 アップロード + DB 反映: 承認された動画を assets/{set_code}/prebuilt/{content_key}.mp4 へアップロードし（イラスト原画 {content_key}_illustration.png も再ビルド資産として併置。DB 記録なし）、quiz_stock_items の video_s3_key / video_audio_asset_id / video_built_at（V006）をローカル MySQL と Aurora の両方へ UPDATE する。Aurora 反映 SQL と S3 ファイル名のどちらも環境ローカルな id を使わない（安定キー = set_code + question_text と content_key で解決。data-model.html セクション 4.10 の V007 コールアウト）
決定（16-3b）: イラストは imagegen（Codex サブスク内）+ 画風指定行の恒久化 16-3 (8) の比較（gpt-image-1 実 API vs imagegen vs imagegen + 画風行）で、imagegen + 画風 1 行（フラットデザイン・ベクター調・写実禁止・全枚統一）が禁止事項の全遵守と画風の一貫性を両立し品質面で最良だった。事前ビルドのイラスト生成はこの組み合わせを採用し、画風行をツーリングのプロンプトへ恒久化する。OpenAI Images API は使わない（イラスト API 費ゼロ化）。imagegen は Codex への委譲実行（MCP）であり自動化バッチには組み込めないが、事前ビルドは人間レビューを挟むローカル運用のため委譲ベースで成立する。
版面・スロット構成・音源の変更は事前動画の再ビルドを伴う 事前動画にはスロット別パレット・slot_label・BGM・SE・版面がベイクされている。以下の変更は該当する事前動画の全再ビルド + 差し替えが必要になる（実行時生成なら設定変更だけで済んだものが、ビルド資産の更新作業になるトレードオフ）:
  • 版面・カット構成・尺の変更（レンダラー改修 → 全量再ビルド）
  • parameters.slots の型・難度 ⇔ スロット対応やパレット・slot_label の変更（該当スロットの再ビルド。事前動画は行の型・難度から一意に決まるスロット向けにビルドされるため、対応を変えると版面とスロットが食い違う）
  • BGM の差し替え（ミュート検知時を含む。is_active=0 にするだけでは既ビルド動画に古い曲が残る — operation.html セクション 4.4 の追記を参照。対象は video_audio_asset_id で特定できる）
