適用状態 17-2（2026-08-10）で設計 Fix。実装は 17-4（ビルドツーリング + Remotion 本組み + 方式モジュール）、初期 30 ネタのビルド・S3 配置と稼働開始は 17-5 以降を予定（ステップ分割は development-plan.md Phase 17）。本書は目標設計であり、実装時の差分は decision コールアウトで追記する。

1. 方式概要

背景イラスト〜ナレーション付きランキング動画を事前にローカルでビルドし、全数人間レビューのうえ S3 に作り置きしておき、実行時はランキングストック（ranking_stock_items）の LRU 順繰り選定と事前動画の取得・返却だけを行う軽量な方式。実行時に外部 API（画像生成・LLM・TTS）を一切呼ばない。「作り置き + 全数レビュー + 実行時は取得のみ」の構造は quiz-prebuilt と同型で、差分は以下の 3 点。

  • レンダラーが Remotion（React ベースのプログラム動画生成。Pillow + ffmpeg の組版ではなくコンポーネントとフレーム補間で版面・アニメーションを記述する）。フォーマットは TOP5 地図ルーレット型（セクション 8.2）
  • フルナレーション: セリフ単位の TTS（VOICEVOX）をタイムライン定数へフレーム同期させてベイクする（セクション 8.3）
  • 2 尺: 同一ネタから 20 秒版・30 秒版の 2 本をビルドし、スロット（parameters.slots[].duration_seconds）がどちらを投稿するかを決める（セクション 3。尺比較の検証設計は セット別設計書セクション 3）
決定（2026-08-10、17-2 巡 2）: Remotion ローカル事前ビルド方式の採用と方式名 Phase 17 の決定方針（development-plan.md Phase 17 冒頭の 9 点 = 17-1 で Fix）のうち「生成方式 = Remotion ローカル事前ビルド（quiz-prebuilt 同型の作り置き + 全数人間レビュー）」を方式として具体化する。狙いは quiz-prebuilt と同じ 3 点（生成 API 定常費ゼロ〔Remotion・VOICEVOX とも無料。事業戦略書セクション 3.1〕・投稿される完成形の全数人間レビュー・実行時の失敗面の縮小）。方式名は quiz-prebuilt の「コンテンツ種別 + prebuilt」の命名慣例に倣い ranking-prebuilt とした（代替案 pref-ranking-prebuilt はセットコードに寄り過ぎ〔方式は他セットでも再利用しうる〕、remotion-prebuilt は技術基盤名で既存カタログと命名粒度が揃わないため不採用）。

2. 契約の実装

共通の契約（batch-flow.html「生成方式の契約」）を generate(context: GeneratorContext) -> GeneratorResult で実装する。冪等性（完了判定）・S3 保存・DB 登録・トランザクション制御は共通骨格（processing.py）の責務であり、本方式は関与しない。共通骨格・SNS 投稿バッチの変更は、キャプション展開へのランキング系プレースホルダ追加（batch-flow.html セクション 3.3 の decision。実装 17-4）のみ。

3. 入力（parameters とスロット解決・2 尺）

prompt_configs.parameters の slots 配列でスロットを定義する。スロット解決ロジック（SCHEDULED_AT の JST 時による決定的解決・早朝の巻き戻し）は gpt-quiz-multicut（方式設計書セクション 3）と同一規則を本方式内に実装する。Scheduler の Input にスロット・尺は持たせない（時刻だけがスロットの指定。operation.html セクション 2.1 の warn）。

slots のフィールド必須役割
from_jst_hour必須スロットの適用開始時刻（JST 時）。クイズ方式と同じ境界規則
slot_code必須スロット識別子（Scheduler 名のサフィックスと対応）
duration_seconds必須このスロットが投稿する尺（20 または 30 のみ許容。それ以外は parameters 不正として異常終了）。ストック取得の絞り込み（当該尺の事前動画がビルド済みの行のみ候補）と、S3 から取得するカラム（video_s3_key_20s / _30s）の選択に使う
決定（2026-08-10、17-2 巡 2・巡 3）: 尺はスロット単位の固定値とする 2 尺（20 秒 / 30 秒）のどちらを投稿するかはスロットの設定値 duration_seconds で固定する。日付・乱数による実行時の出し分けロジックは持たない（決定的解決の維持。同じスロットの再実行は必ず同じ尺になり、冪等性と検証の解釈が単純になる）。尺比較の検証（17-6）は「昼 = 20 秒 / 夜 = 30 秒」のスロット分離で行い、時間帯交絡の打ち消し（検証後半のスワップ）や尺確定後の一本化は parameters の UPDATE だけで行える（両尺ビルド済みのため設定変更と資産が食い違わない。検証の回し方は セット別設計書セクション 3）。クイズ方式の slot_label（時間帯ラベル帯）・quiz_type / difficulty（型・難度絞り込み）に相当するフィールドは本方式にはない — ランキングのネタはスロット非依存で、版面にも時間帯要素を持たないため。

4. ランキングストックの取得（当該尺ビルド済み限定の LRU 順繰り）

ネタは ranking_stock_items（data-model.html セクション 4.13）から LRU 順繰りで取得する。quiz-prebuilt の選定（同セクション 4）との差分は、絞り込みが型・難度ではなく「スロットの尺に対応する事前動画がビルド済み」である点のみ（{尺カラム} は duration_seconds から video_s3_key_20s / video_s3_key_30s のどちらかに解決する。20 / 30 以外は事前に検証済みのため SQL 組み立ては安全）。

SELECT id, title, content_fields, ranking_data, {尺カラム} AS video_s3_key, video_audio_asset_id
  FROM ranking_stock_items
 WHERE set_id = %s AND is_active = 1
   AND {尺カラム} IS NOT NULL
 ORDER BY last_used_at ASC, id ASC LIMIT 1
  • 0 件は RuntimeError で異常終了（ストック未投入・全行無効化に加え「投入済みだが当該尺が全行未ビルド」も検知するフェイルラウド）
  • 再利用（last_used_at IS NOT NULL の行を選んだ場合）は WARNING ログ（補充遅延のサイン）
  • 当該尺が未ビルトの有効在庫が存在する場合も WARNING ログを出す（COUNT 1 本。投入後のビルド漏れ・ビルド待ちのサイン。週次の在庫確認クエリ〔operation.html セクション 3〕でも拾える）
  • 防御的フィールド検査: title 非空、content_fields の必須キー（hook / trivia / source_display / result_list）の存在・非空、ranking_data.entries が 5 件で rank 1〜5 が一意であること、video_audio_asset_id 非 NULL。動画には使わないがキャプションのプレースホルダ展開（ranking_items 経由）の入力になるため検査する。不備は異常終了（投入ミスの検知）
  • last_used_at / use_count の UPDATE は事前動画の取得成功後に行い、commit は共通骨格に委ねる（失敗時はストック消費の副作用ごとロールバック）
決定（17-2 巡 2）: last_used_at は 2 尺共通（尺別に持たない） 同一ネタの 20 秒版と 30 秒版は同じ内容の別尺であり、片方を投稿した直後にもう片方が別スロットで選ばれると同一アカウントに実質同じ内容が近接して並ぶ。これを防ぐため LRU の状態（last_used_at / use_count）は尺別に分けず 1 組だけ持ち、どちらの尺で使ってもネタ全体が LRU キューの末尾に回る。どの尺で投稿したかの記録は履歴側（ranking_items.duration_seconds）が持ち、尺別の効果検証はそちらで行う（data-model.html セクション 4.12）。
決定（17-2 巡 2）: 未ビルト行・片尺のみビルド済みの行は「選ばれない」のであって「エラーにしない」 quiz-prebuilt セクション 4 の decision を踏襲する。当該尺が未ビルトの行は絞り込みで候補から除外され、他のビルド済み在庫で投稿は止まらない（週次補充の「投入 → ビルド」の間に実行が走っても安全）。片尺のみビルド済みの行はその尺のスロットの候補にだけ入る（尺確定後は勝ち尺のみビルドする運用〔operation.html セクション 3〕になるため、これは正常な状態でもある）。未ビルトの滞留は WARNING と在庫確認クエリで検知する。

5. 事前動画の取得

選定したストック行の当該尺カラム（video_s3_key_20s / _30s）から MP4 を取得する（acps_shared.s3.get_object）。キーの値はビルドツーリングが登録した assets/{set_code}/prebuilt/{content_key}_20s.mp4 / _30s.mp4（命名規約は data-model.html セクション 5。環境非依存の業務キー content_key で組む — quiz-prebuilt の 16-3d 決定を最初から適用。参照は常に DB カラム経由で行い、方式がキーを組み立てることはしない）。

  • 取得失敗（NoSuchKey・アクセスエラー）は異常終了（フェイルラウド。DB は「ビルド済み」なのに実体がない = DB と S3 の不整合であり、縮退して別のネタ・別の尺に差し替えることはしない）
  • 取得したバイト列をそのまま MediaOutput として返す。再エンコード・検査変換は行わない（形式はビルド時に Remotion レンダラーが保証し、全数レビューで確認済み）。寸法は方式定数（1080x1920）、尺はスロットの duration_seconds を記録する

7. エラーハンドリング

方式内のリカバリループはない。異常（parameters 不正〔duration_seconds が 20 / 30 以外を含む〕・当該尺のビルド済みストック 0 件・ストック行のフィールド不備・video_audio_asset_id 未記録・事前動画の取得失敗）はすべて例外を送出し、共通骨格が捕捉 → ロールバック → Step Functions Retry → 失敗アラーム通知につながる（quiz-prebuilt セクション 7 と同型）。実行時の主な失敗面は SNS 投稿側（Graph API）になる。

8. 事前ビルドパイプライン（供給側の設計）

8.1 工程（5 段）

事前動画の供給はローカルの事前ビルドツーリングが担う。ツーリングは content/video-build/<set_code>/ に置いて git 管理し（置き場・運用ルールは operation.html セクション 3）、週次補充（ストック投入）とセットで回す。工程は 5 段:

  1. 対象抽出: ビルド対象尺のカラム（検証期は video_s3_key_20s と _30s の両方、尺確定後は勝ち尺のみ）が NULL の有効ストック行を列挙する（初回 = 17-5 は 30 ネタ全量、以後は補充分のみ）
  2. 背景イラスト生成（imagegen 委譲）: 行の content_fields.bg_motif（ネタのテーマに合わせた背景モチーフの指示文）からプロンプトを組み立て、Codex 組み込み画像生成（imagegen）で 9:16 の背景を 1 ネタ 1 枚生成する（2 尺で共用）。プロンプトにはセットの画風固定行（セット別設計書セクション 4）とサイズ明示行（quiz-prebuilt の 16-4b 決定と同じ手法）を付け、「文字・数字・記号を描かない」を必須指定とする（下記 decision の再利用要件①）。生成物は assets/{set_code}/prebuilt/{content_key}_bg.png として S3 に併置する（再ビルド資産。DB 記録なし）
  3. TTS 合成 + Remotion レンダリング（2 本）: 行の narration（尺別 cue 台本）を VOICEVOX（ローカル Docker）でセリフ単位に合成 → 実測長の予算検査（セクション 8.3。超過はビルドエラー） → 音声ファイル群 + ranking_data + 版面文言 + 背景をコンポジションの props に渡し、Remotion で 20 秒版・30 秒版をレンダリングする。BGM は audio_assets の time_slot IS NULL の有効曲から LRU 選曲 + last_used_at 更新をビルド時に行い（quiz-prebuilt セクション 6 の decision と同じ移管）、2 尺共通の 1 曲を video_audio_asset_id に記録する
  4. レビューシート生成 → 全数人間レビュー: ビルドした動画（2 尺）+ 背景イラストを一覧できるレビューシートを生成し、ユーザーが全数レビューする。NG は背景再生成（imagegen 再試行・bg_motif 書き直し）またはセリフ・版面文言の修正（DB 更新）→ 再ビルドで解消する（レビュー観点は operation.html セクション 3）
  5. S3 アップロード + DB 反映: 承認された動画を assets/{set_code}/prebuilt/{content_key}_20s.mp4 / _30s.mp4 へアップロードし、ranking_stock_items の video_s3_key_20s / video_s3_key_30s / video_audio_asset_id / video_built_at をローカル MySQL と Aurora の両方へ UPDATE する。Aurora 反映 SQL と S3 ファイル名のどちらも環境ローカルな id を使わない（content_key で解決。quiz-prebuilt の 16-3d 決定を最初から適用）
決定（2026-08-10、17-2 巡 2・巡 3）: 英語圏展開セットを見据えた再利用要件 4 点 次セット候補として同内容を英語で発信する海外向けセットが計画されている（ユーザー方針。時期未定）。ネタ・素材・コンポジションを言語違いで再利用できるよう、本方式の実装は以下を必須要件とする:
  1. 背景イラストに文字を焼き込まない（imagegen プロンプトで「文字・数字・記号を描かない」を必須指定。背景は言語非依存の共用素材になる）
  2. Remotion コンポジションの画面文言はすべて props 経由（コンポーネント内のハードコード禁止。文言の正はストック行の content_fields / narration）
  3. TTS はアダプタ層で分離（cue テキスト → 音声ファイル + 実測長のインターフェースを固定し、VOICEVOX 固有の呼び出しはアダプタ内に閉じる。英語セットでは別エンジンのアダプタに差し替える）
  4. ネタソース・県換算テーブルは言語非依存の形式で保持（ranking_data は数値・都道府県コードのみで言語を含まない。表示文言は content_fields / narration に分離済み = データモデル側の対応。data-model.html セクション 4.13）
ツーリングの共通 core 化（言語共通部の抽出）は英語セット追加時に行い、17-2 時点は pref-ranking-1 専用構成のままとする（YAGNI。ユーザー Fix）。

8.2 動画の作り（TOP5 地図ルーレット型コンポジション）

版面は 1080x1920 / 30fps。構成要素は上から タイトル帯（ネタの title）・日本地図（ルーレット演出の主役）・順位行スタック（確定した順位を 5 位から積み上げ）・キャラ常駐枠 + 吹き出し（実況）・最下部の出典行帯。配色はパレットトークン（Palette 型）で駆動し、値はセットのデザイントークン（セット別設計書セクション 8）を正とする。検証プロトタイプは plans/ranking-set-research/remotion-proto/（git 管理外。本組み実装 = 17-4 でコンポジションをリポジトリへ移した時点でコードが正となる）。

ルーレット演出: 各順位の発表は「地図上で候補県が高速に光る（スピン）→ 停止フラッシュで確定 → 確定県が順位色に塗られ、順位行に県名・数値が追記される」の繰り返し。確定済みの県は塗りが残るため、動画の進行とともに地図が塗り上がっていく。

決定（2026-08-10、17-2 巡 1）: 固定アンカー + 予算検査方式（可変尺方式は不採用） 音声の実測長に合わせてアンカー・尺を動かす「可変尺方式」は、セリフを直すたびに版面演出（スピン・フラッシュ・行追記）との同期が崩れ、2 尺のタイムライン Fix が意味を失うため不採用。採用方式:
  • 各 cue の開始フレームは尺別のタイムライン定数（アンカー表）に固定する。アンカー間隔から各 cue の時間予算が決まる
  • ビルド時、VOICEVOX の合成結果の実測長が予算を超過したらビルドエラーにする（静かに次の cue へ食い込ませない）。第一の対処はセリフの修正（短く書き直す）、第二の手段として話速 speedScale の引き上げ（上限 1.2。それ以上は聞き取りにくくなるため禁止）
  • 予算内の余りは無音で吸収する（cue の頭をアンカーに揃える）
話者・既定の合成パラメータ（速度・抑揚）はセット固有のため セット別設計書セクション 7。
決定（2026-08-11、17-3 のストックレビュー）: 煽り cue の新設と 5〜2 位 cue の統合

変更 1: teaser（煽り）を intro の直後に必須で置く。導入でタイトルを言った直後に視聴者へ 1 位を予想させ、結果を見届ける動機を作る。冒頭で一度参加させることが完走率・コメントの両方に効くという想定で、全ネタ必須とする（validate 相当のフィールド検査で欠落を落とす）。

変更 2: 5〜2 位の r*_call（呼び込み）と r*_name（県名）を 1 本の cue r5〜r2 に統合する。「まずは5位、埼玉県！」のように 1 息で言い切る形にする。1 位だけは r1_call（タメ）と r1_name（発表）を分けたままにする（タメ → 発表の間が演出の核であり、ここを統合すると 1 位の見せ場が消えるため）。

この 2 点で捻出した尺が teaser の原資であり、20 秒 = 600f / 30 秒 = 900f の総尺と、1 位シーン・結果総覧・締めの配分は変えていない（20 秒版は順位シーンが 2.5s → 2.0s、30 秒版は順位コメントが 2.0s → 1.5s に縮む）。

変更 3: 締めのセリフを「呼びかけ」から「中身のある一言」に変える。20 秒版の outro は 「みんなはわかったかな？」で全ネタ共通とし、冒頭の teaser で促した予想の答え合わせで閉じる。30 秒版は県名を並べるだけの recap を廃止し、recap + outro を closing 1 本に統合して、そのネタの含意（content_fields.trivia の核）を口語で言い切る（例: 「納豆好きの地図は、きれいに北へ寄ってるな！」）。結果の一覧は結果総覧シーンの画面とキャプションの result_list で担保されており、読み上げで重ねる価値が低いという判断。保存の呼びかけはナレーションから外れるが、キャプションの TOP5 再掲（セット別設計書セクション 5）が保存の動機を担う。

統合に伴う実装上の制約が 2 つある。①アンカーの後ろ合わせ: 統合 cue は「◯位は」の呼び込みで始まり県名で終わるため、頭合わせのままだと県名の発話が停止フラッシュより早く終わる。順位シーンに限り、県名部分の発話開始が停止フラッシュに重なるようアンカーを詰める（実測長からの逆算。17-4 で調整）。②吹き出しの表示開始: 統合 cue のテキストは県名を含むため、キャラの吹き出しにスピン中から出すと結果が先にばれる。順位シーンの吹き出しは停止フラッシュ以降に限る（セクション 8.2）。

8.4 再ビルドが必要になる変更

版面・タイムライン・素材の変更は事前動画の再ビルドを伴う 事前動画には版面・パレット・背景・ナレーション・BGM がベイクされている。以下の変更は該当する事前動画の全再ビルド + 差し替えが必要になる:
  • 版面・タイムライン・尺構成の変更（コンポジション改修 → 全量再ビルド）
  • パレット（デザイントークン）・キャラアセット・地図 SVG の変更（17-4 の PD 地図差し替えは全量再ビルドの契機。ただし 17-4 は初期ビルド前のため実質影響なし）
  • BGM の差し替え（ミュート検知時を含む。対象は video_audio_asset_id で特定できる）・VOICEVOX 話者やセリフの変更
一括再ビルドはツーリングの --rebuild（ビルド済み行を対象に、BGM を video_audio_asset_id から引き継いで再ビルド = 選曲 LRU を消費せず、last_used_at〔投稿キュー〕も変えない。quiz-prebuilt の 16-4b と同型）で行う。再ビルド後の全数レビュー → S3 上書き → 両環境 DB 反映は新規ビルドと同じ。
