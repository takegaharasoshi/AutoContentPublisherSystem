1. 方式概要

ウミガメのスープ 1 問につきリール動画（1080x1920・30fps・24 秒・AAC）をローカルで事前にビルドし、全数人間レビューのうえ S3 に作り置く。実行時（画像生成バッチ）はストック umigame_stock_items のうちビルド済みの行を LRU 順繰りで 1 件選び、事前動画を S3 から取得して GeneratorResult として返すだけで、外部 API・レンダリングを実行時に使わない（定常費ゼロ路線。quiz-prebuilt / ranking-prebuilt と同じ思想）。

  • レンダラー: Remotion 4.0.520（create-video 雛形 + Remotion Skills 2.0 の指針〔remotion-create / remotion-markup / remotion-render〕で作ったコンポジション）。レンダリングは既存どおり build.py からの Docker 委譲（remotion-render イメージへの bind-mount + npx remotion render）
  • フォーマット: 9:16・24 秒 = 720 フレーム固定・ループ前提（末尾と先頭の状態を一致させる）。つかみ帯 + 問題カード + ルール帯を常時表示し、下部ゾーンでキャラ 2 体の吹き出しが時間で切り替わる（セクション 8.2）
  • 素材: ストック 1 件 = 素材 14 項目（セット別設計書 4）。背景イラストは imagegen で 1 問 1 枚、キャラ 2 体はセット固定
  • ナレーション: ローカル GPU の Irodori-TTS v4.1-Small（声 G4「kamerock-chubby」のクローン。21-5c で Amazon Polly Takumi 125% → Gemini 3.8 Flash TTS → Irodori と切替）で冒頭の 2 cue（問題文・ルール）だけを読む。吹き出しとは同期しない
  • 参加型の要素は方式の外: コメント自動返信は SNS 投稿バッチが出力する問題スナップショット（batch-flow.html 3.3 手順 6）と Lambda（infra/stacks.html 3.6）が担い、本方式は umigame_items に問題固有部分をスナップショットしておくところまでを責務とする

2. 契約の実装

共通の契約（batch-flow.html「生成方式の契約」）を generate(context: GeneratorContext) -> GeneratorResult で実装する。冪等性（完了判定）・S3 保存・DB 登録・トランザクション制御は共通骨格（processing.py）の責務であり、本方式は関与しない。共通骨格・SNS 投稿バッチの変更は、キャプション展開への umigame 系プレースホルダ追加と、publish 成功直後の問題スナップショット出力（batch-flow.html 3.3。実装 21-5b）の 2 点のみ。

要素使い方
context.prompt_configparameters（尺。セクション 3）・set_id。prompt_text は本方式では未使用（セット別設計書 5.1 の decision により AI 出題者プロンプトのセット固定部分に充てる。読むのは SNS 投稿バッチのスナップショット出力）

処理順序: ① parameters 検証 → ② ストック取得（ビルド済み限定の LRU。セクション 4） → ③ S3 から事前動画を取得（欠落はフェイルラウド。セクション 5）→ ④ umigame_items INSERT + ストックの last_used_at / use_count 更新 → ⑤ GeneratorResult を返す。フォント・キャラアセット・BGM の事前検査、API キー取得はいずれも不要（実行時に使わないため）。

実装（2026-09-26、21-5b）: services/image-batch/app/generators/umigame_prebuilt.py・REGISTRY 名 umigame-prebuilt 設計どおりに実装した。設計より厳しくした点が 2 つある: ① parameters は duration_seconds の 1 キーだけを許し、slots など他のキーがあれば不正として異常終了する（単一スロットの宣言を設定ミスから守るため） ② ストック行の video_audio_asset_id が NULL の行も異常終了にする（ビルド済みの行は BGM を焼き込んでいるので、NULL は publish 手順の不備）。ストックは取得 SQL（セクション 4）により未使用の行を id の小さい順に消費するため、投入時の INSERT 順がそのまま投稿順になる（21-5a の POST_ORDER。単体テストで ORDER BY 句と選ばれる行を押さえている）。

3. 入力（parameters。単一スロット・単尺）

prompt_configs.parameters は次の 1 キーのみ。スロット定義（slots）は持たない（投稿は 20:00 の 1 日 1 回・尺は 1 つのため。セット別設計書 3）。

フィールド必須役割
duration_seconds必須投稿する尺。24 のみ許容（それ以外は parameters 不正として異常終了）。MediaOutput.duration_seconds に転記し、ストック行の video_s3_key が指す動画の尺と一致することの宣言でもある
決定（2026-09-04、21-3）: 単尺・単一スロット。尺の複数化は想定しない ranking-prebuilt の 2 尺（スロット別の固定値）と違い、本方式は 24 秒の 1 尺だけを持つ。理由: ① 21-2 の人間ゲートで「24 秒・ループ前提」をフォーマットの基準として承認済み ② 尺は問題文 + ルールのナレーション予算（8.3）とビート（8.2）から決まり、尺を変えると版面の不変条件（周期は 720 の約数）ごと作り直しになる ③ 参加型の効果はコメント欄で出るため尺比較の検証価値が低い。将来尺を変える場合は parameters.duration_seconds と timeline.ts の定数を同時に変え、全数再ビルドする（8.4）。slots を持たないため、SCHEDULED_AT による決定的解決のロジックは本方式に含めない。

4. ストックの取得（ビルド済み限定の LRU 順繰り・軸なし）

SELECT id, content_key, problem_text, truth, fact_sheet, rule_text, caption, hook,
       video_s3_key, video_audio_asset_id, use_count
FROM umigame_stock_items
WHERE set_id = %s AND is_active = 1 AND video_s3_key IS NOT NULL
ORDER BY last_used_at IS NULL DESC, last_used_at ASC, id ASC
LIMIT 1 FOR UPDATE;
  • 絞り込み: セット専属・有効・ビルド済み（video_s3_key IS NOT NULL）のみ。難易度・型・スロットの軸は持たない（ranking-prebuilt と同じ 3 カラム索引 KEY (set_id, is_active, last_used_at)）
  • 0 件はフェイルラウド（縮退しない）。在庫水位の監視は運用側（週次補充。在庫 14 件以上を目安 = セット計画書で管理）
  • 再利用 WARNING: 選んだ行の use_count >= 1 なら WARNING ログ（「ストック枯渇により再出題」）。参加型の性質上、同じ問題の再出題はコメント欄の推理が使い回されるため、既存 2 セットより再利用の弊害が大きい。補充が追いつかない場合は再出題より投稿スキップ（is_active=0 による一時停止）を優先する運用とする（課題が出たら課題体系の umigame-soup-1 節へ）
  • 取得後、同一トランザクションで last_used_at = NOW() / use_count = use_count + 1 に更新し、umigame_items に問題固有部分をスナップショットする（セクション 6）
  • 防御的フィールド検査: fact_sheet が配列でない・problem_text が空などは方式内で検出して異常終了（スナップショット出力がコメント経路の前提になるため、投稿前に止める）

5. 事前動画の取得

umigame_stock_items.video_s3_key（assets/{set_code}/prebuilt/{content_key}.mp4。data-model.html 5）から MP4 を取得し、MediaOutput のバイト列として返す。方式はキーを組み立てず常にカラム経由で参照する。取得失敗（NoSuchKey・権限）は縮退せず異常終了（NULL でない = ビルド済みの宣言と S3 の実体が食い違う状態は、ツーリング側の publish 手順の不備なので投稿を止めて気づく）。

7. エラーハンドリング

方式内リカバリループ（再生成・代替素材）は持たない。すべて異常終了させ、共通骨格が generation_runs.status='failed' にして Step Functions の失敗アラームで通知する。

  • parameters 不正（duration_seconds ≠ 24・欠落）→ 異常終了
  • ストック 0 件（有効・ビルド済みなし）→ 異常終了（フェイルラウド）
  • 事前動画の取得失敗 → 異常終了
  • ストック行のフィールド不正（JSON の型・必須空）→ 異常終了
  • 再出題（use_count >= 1）→ 続行 + WARNING

  • 暫定 BGM（2026-09-24 に正式トラックへ差し替え・再ビルド済み。仕組みは次の曲の追加前の検証用に残す）: umigame 用の 24 秒トラックが未調達だったため、第 1 バッチは PoC の bgm_24s.m4a（logic-training-1 night track01 の 20 秒版を 24 秒にループ。20 秒地点に継ぎ目あり）を provisional として使ってビルドした。publish.py は暫定 BGM の動画を検査エラーにする（正式トラックの調達 → prepare_bgm.py → 再ビルド〔レンダリングからやり直し〕が publish の前提）
  • つかみ帯のフォントは字数で縮める: 74px の 1 行に収まるのは 11 字まで（内寸 828px）。12〜13 字のフック（第 1 バッチで 4 問）が折り返して問題カードの下に隠れたため、UmigameReel.tsx で min(74, floor(828 / 字数) - 1) の字数フィット + 折り返し禁止にした
  • ビルド検査: ffprobe（1080x1920・30fps・24.0±0.2 秒・AAC）と、最終 MP4 のフレーム 0 / 719 の平均絶対差（仮の閾値 3.0。第 1 バッチの実測は 1.8 前後）。結果は work/manifest.json に残り、review_sheet.py が work/review.html に並べる

8.2 動画の作り（24 秒・ループ前提のコンポジション）

1080x1920・30fps・720 フレーム。版面は logic-training-1 の骨格（常時表示の上部 + 時間で切り替わる下部）に寄せ、イラストは背景に敷く。

ゾーン要素備考
背景（全面）問題の情景イラスト 1 枚 + 薄いオーバーレイ。ゆっくりしたズーム呼吸（周期 720）中間調で生成し、暗くしすぎない（21-2 決定）
上部（常時・不変）つかみ帯（hook・74px・1 行。光沢スイープ + 呼吸）→ 見出し「問題」（アクセントバー伸縮）+ 問題カード（problem_text 全文・44px）→ ルール帯（rule_text・34px・2 行）幅 900・左右余白 90 で中央寄せ（第 3 稿）。フレーム 0 から末尾まで不変
下部（時間で切替）出題者カメロック（左下に常駐。浮遊 + 呼吸。「はい」の返答時だけ喜びポーズ）+ 名札 / 質問者 Jr.（右寄り。浮遊）/ 吹き出し（スナップ切替 + ポップイン + 小さな跳ね 30px + SE）右 12% は Instagram UI に空ける。吹き出し 42px・1 行上限は出題者 17 字 / Jr. 16 字

ビート（timeline.ts の BEATS）:

区間フレーム内容
導入0〜90（3 秒）出題者「質問してみて！」（吹き出しは静止 = 継ぎ目でフレーム 0 と一致させるためポップインしない）
3 往復90〜450（4 秒 × 3）各往復: Jr. の質問 60f → 質問を残したまま出題者の返答を追加 60f。返答「はい」の往復で出題者が喜びポーズに切り替わる
出題者の締め450〜570（4 秒）「何度でも答えるよ。コメントで質問！」（グロー脈動）
Jr. の締め570〜708（4.6 秒）「面白かったら、いいね、フォローよろしくね！」（吹き出しのみ・ナレーションなし）
継ぎ目708〜720（0.4 秒）導入と同じ状態へ戻す

不変条件（logic-training-1 の timeline.ts を踏襲。モジュール読み込み時に検査）:

  • フレーム 720 = フレーム 0（ループの継ぎ目が見えない）。ビルド後に最終 MP4 のフレーム 0 と 719 の差分で検証する
  • 周期アニメーション（つかみ帯の光沢 120 / 呼吸 144 / 見出しバー 144 / 出題者の浮遊 120・呼吸 180 / Jr. の浮遊 90 / 締めのグロー 90 / 名札の点 80 / 背景ズーム 720）の周期はすべて 720 の約数
  • 吹き出しの切替はスナップ（クロスフェードは二重露光に見える。R-1 の実測）。切替フレームで SE を 1 回鳴らし、小さな跳ね（30px・減衰 0.8 秒）を付ける
  • ビートは順序どおり・隙間なし・末尾が 720

8.3 ナレーションと TTS のフレーム同期（固定アンカー + 予算検査）

cue開始内容予算
problemフレーム 15（0.5 秒）narration.problem（表示文と別の読み上げ用の文）problem 実測長 + 1.2 秒 + rule 実測長 ≦ 21.0 秒（= 開始 0.5 秒 + 21 秒 < 継ぎ目 23.6 秒に 2 秒の余裕）

  • 2 cue を1 回の合成で読ませ（Irodori-TTS infer.py・参照音声 6 本で声 G4 をクローン・cuda / BF16・--seconds で全体の長さを指定）、文字数比に最も近い 0.3 秒以上の無音で 2 つに切り分けて前後の無音を 0.05 秒残して削る。別々に作るとルール文で口調が変わるため（21-5c の PoC 知見）。実測長を props に渡してアンカーへ配置する。吹き出しとは同期しないため、cue の長短で版面は変わらない
  • 長さの制御と取り直し: 話速調整（atempo）はせず、--seconds 20.0 で合成する（PoC で自然長 23〜25 秒の問が 19.0〜20.8 秒に収まった）。2 cue + 間の合計が 21 秒を超えたら、seed を 1 つ進めて --seconds を 0.5 秒縮めて取り直す（1 回のビルドで最大 3 テイク = 20.0 / 19.5 / 19.0 秒）。聞いて気になった問は build.py --retake-tts --content-key <key> で seed を進めて長さを初期値から取り直す。narration.json にモデル・参照音声（名前と sha256）・精度・seed・長さ・切断位置・試したテイク・通算の合成回数（attempt）を残し、文・モデル・参照音声・精度・長さの設定が一致して予算内ならキャッシュを使う
  • 予算超過はビルドエラー（3 テイクとも超えたら問題文か cue の句読点を削る）。infer.py の失敗（GPU・環境の問題）はその場でビルドを中断する
  • BGM は @remotion/media の <Audio> で 24 秒トラックをそのまま敷く（ループなし = 継ぎ目なし）。ナレーション区間は BGM を -6dB 程度ダッキングし、SE は切替フレームに置く。最終 MP4 を -14 LUFS / -2 dBTP へ正規化
  • TTS アダプタは差し替え可能にする（Irodori が既定。Gemini 版〔日次上限のため本番では使わない〕・Polly 版・VOICEVOX 版は残置）。Irodori はビルド時にローカル GPU で実行し、API キー・AWS の Secret は要らない。声と設定の正はセット資産の assets/design.json と参照音声 assets/voice/kamerock-g4/（セット別設計書 8）

8.4 再ビルドが必要になる変更

事前動画はベイク済み。以下を変えたら対象ストックを再ビルドして publish.py で差し替える
  • 素材の表示部分（problem_text / hook / rule_text / play_example / character_lines / narration / 背景）。truth / fact_sheet / expected_questions / caption / source_note の修正は再ビルド不要（版面に出ないため）。ただし caption は umigame_items に投稿時点でスナップショットされるため、修正は以後の投稿から効く
  • 版面（timeline.ts / UmigameReel.tsx）・キャラ画像・フォント・SE・尺
  • TTS のモデル・参照音声・精度・長さ（design.json の narration 節と assets/voice/kamerock-g4/）・cue 間の間隔。拡散モデルのため seed・精度が変わると別テイクになり尺と読みが揺れるので、再合成した問は全数を試聴し直す
  • Remotion / @remotion/media の版（見た目が変わりうる）
再ビルド後は video_built_at を更新する。全数再ビルドは在庫（14〜30 件）に対して 1 件 2〜3 分（TTS 約 45 秒 × テイク数 + レンダリング）で、背景再生成を伴わなければ 1 時間以内。
