要約

このページは生成方式 umigame-prebuilt（ウミガメのスープのリール動画の事前ビルド方式）の実行時の仕様（2〜7 章）を定める。機能別の基本設計 投稿の「選定」の段で、umigame-soup-1 の在庫から 1 本を選ぶ部分の詳細にあたる。動画の作り方・ビルドは生産の詳細設計 umigame-soup-1、セット固有の設定は sets/umigame-soup-1.html。版面の座標・ビート・効果の実装の正は remotion/src/timeline.ts と UmigameReel.tsx。図 1 は実行時の流れ。

1. 方式概要

ウミガメのスープ 1 問につきリール動画（1080x1920・30fps・29 秒・AAC。2026-10-17 のセット改修 R-1 までは 24 秒）をローカルで事前にビルドし、全数人間レビューのうえ S3 に作り置く。実行時（画像生成バッチ）はストック umigame_stock_items のうちビルド済みの行を LRU 順繰りで 1 件選び、事前動画を S3 から取得して GeneratorResult として返すだけで、外部 API・レンダリングを実行時に使わない（定常費ゼロ路線。quiz-prebuilt / ranking-prebuilt と同じ思想）。

  • レンダラー: Remotion 4.0.520（create-video 雛形 + Remotion Skills 2.0 の指針〔remotion-create / remotion-markup / remotion-render〕で作ったコンポジション）。レンダリングは既存どおり build.py からの Docker 委譲（remotion-render イメージへの bind-mount + npx remotion render）
  • フォーマット: 9:16・29 秒 = 870 フレーム固定・一本道（2026-10-17 のセット改修 R-1 でループ前提をやめた）。先頭 5 秒の導入シーン（「新体験」スタンプ・見出し・「今日の謎」の hook・キャラの自己紹介）の後、つかみ帯 + 問題カード + ルール帯を常時表示し、下部ゾーンでキャラ 2 体の吹き出しが時間で切り替わる（セクション 8.2）
  • 素材: ストック 1 件 = 素材 18 項目（セット別設計書 4）。背景イラストは imagegen で 1 問 1 枚、キャラ 2 体はセット固定
  • ナレーション: ローカル GPU の Irodori-TTS v4.1-Small（声 G4「kamerock-chubby」のクローン。21-5c で Amazon Polly Takumi 125% → Gemini 3.8 Flash TTS → Irodori と切替）で冒頭の 2 cue（問題文・ルール）だけを読む。吹き出しとは同期しない
  • 参加型の要素は方式の外: コメント自動返信は SNS 投稿バッチが出力する問題スナップショット（batch-flow.html 3.3 手順 6）と Lambda（infra/stacks.html 3.6）が担い、本方式は umigame_items に問題固有部分をスナップショットしておくところまでを責務とする

2. 契約の実装

共通の契約（batch-flow.html「生成方式の契約」）を generate(context: GeneratorContext) -> GeneratorResult で実装する。冪等性（完了判定）・S3 保存・DB 登録・トランザクション制御は共通骨格（processing.py）の責務であり、本方式は関与しない。共通骨格・SNS 投稿バッチの変更は、キャプション展開への umigame 系プレースホルダ追加と、publish 成功直後の問題スナップショット出力（batch-flow.html 3.3。実装 21-5b）の 2 点のみ。

処理順序: ① parameters 検証 → ② ストック取得（ビルド済み限定の LRU。セクション 4） → ③ S3 から事前動画を取得（欠落はフェイルラウド。セクション 5）→ ④ umigame_items INSERT + ストックの last_used_at / use_count 更新 → ⑤ GeneratorResult を返す。フォント・キャラアセット・BGM の事前検査、API キー取得はいずれも不要（実行時に使わないため）。

実装（services/image-batch/app/generators/umigame_prebuilt.py・REGISTRY 名 umigame-prebuilt） → 理由 D-01

設計どおりに実装した。設計より厳しくした点が 2 つある: ① parameters は duration_seconds の 1 キーだけを許し、slots など他のキーがあれば不正として異常終了する ② ストック行の video_audio_asset_id が NULL の行も異常終了にする。ストックは取得 SQL（セクション 4）により未使用の行を id の小さい順に消費するため、投入時の INSERT 順がそのまま投稿順になる（21-5a の POST_ORDER。単体テストで ORDER BY 句と選ばれる行を押さえている）。

3. 入力（parameters。単一スロット・単尺）

prompt_configs.parameters は次の 1 キーのみ。スロット定義（slots）は持たない（投稿は日・火・木・土の 20:00 に 1 回ずつ〔週 4 回〕・尺は 1 つのため。セット別設計書 3）。

フィールド必須役割
duration_seconds必須投稿する尺。29 のみ許容（それ以外は parameters 不正として異常終了）。MediaOutput.duration_seconds に転記し、ストック行の video_s3_key が指す動画の尺と一致することの宣言でもある

単尺・単一スロット（現行 29 秒。parameters は duration_seconds の 1 キーだけ）。slots を持たないため、SCHEDULED_AT による決定的解決のロジックは本方式に含めない。尺を変えるときは parameters.duration_seconds と timeline.ts の定数を同時に変え、全数再ビルドする（8.4） → 理由 D-02

許容する尺は ALLOWED_DURATIONS = frozenset({29})。宣言値をそのまま generated_media.duration_seconds に記録し、実尺は測らない（quiz-prebuilt・ranking-prebuilt と同じ） → 理由 D-03

4. ストックの取得（ビルド済み限定の LRU 順繰り・軸なし）

SELECT id, content_key, problem_text, truth, fact_sheet, core_points, judge_criteria, core_words, reveal_text, rule_text, caption, hook,
       video_s3_key, video_audio_asset_id, use_count
FROM umigame_stock_items
WHERE set_id = %s AND is_active = 1 AND video_s3_key IS NOT NULL
ORDER BY last_used_at IS NULL DESC, last_used_at ASC, id ASC
LIMIT 1 FOR UPDATE;
  • 絞り込み: セット専属・有効・ビルド済み（video_s3_key IS NOT NULL）のみ。難易度・型・スロットの軸は持たない（ranking-prebuilt と同じ 3 カラム索引 KEY (set_id, is_active, last_used_at)）
  • 0 件はフェイルラウド（縮退しない）。在庫水位の監視は運用側（週次補充。在庫 8 件以上〔週 4 回 × 2 週間分〕を目安 = セット計画書で管理。21-6i で週 4 回にしたため 14 件から変更）
  • 再利用 WARNING: 選んだ行の use_count >= 1 なら WARNING ログ（「ストック枯渇により再出題」）。参加型の性質上、同じ問題の再出題はコメント欄の推理が使い回されるため、既存 2 セットより再利用の弊害が大きい。補充が追いつかない場合は再出題より投稿スキップ（is_active=0 による一時停止）を優先する運用とする（課題が出たら課題体系の umigame-soup-1 節へ）
  • 取得後、同一トランザクションで last_used_at = NOW() / use_count = use_count + 1 に更新し、umigame_items に問題固有部分をスナップショットする（セクション 6）
  • 防御的フィールド検査: fact_sheet が配列でない・problem_text が空などは方式内で検出して異常終了（スナップショット出力がコメント経路の前提になるため、投稿前に止める）

5. 事前動画の取得

umigame_stock_items.video_s3_key（assets/{set_code}/prebuilt/{content_key}.mp4。data-model.html 5）から MP4 を取得し、MediaOutput のバイト列として返す。方式はキーを組み立てず常にカラム経由で参照する。取得失敗（NoSuchKey・権限）は縮退せず異常終了（NULL でない = ビルド済みの宣言と S3 の実体が食い違う状態は、ツーリング側の publish 手順の不備なので投稿を止めて気づく）。

7. エラーハンドリング

方式内リカバリループ（再生成・代替素材）は持たない。すべて異常終了させ、共通骨格が generation_runs.status='failed' にして Step Functions の失敗アラームで通知する。

  • parameters 不正（duration_seconds ≠ 29・欠落）→ 異常終了
  • ストック 0 件（有効・ビルド済みなし）→ 異常終了（フェイルラウド）
  • 事前動画の取得失敗 → 異常終了
  • ストック行のフィールド不正（JSON の型・必須空）→ 異常終了
  • 再出題（use_count >= 1）→ 続行 + WARNING

D-02 単尺・単一スロットにし、尺の複数化は想定しない

決めたこと
本方式は 1 尺だけを持ち、slots を持たない（2026-10-17 の R-1 で 24 秒 → 29 秒に変え、ループ前提をやめた）
理由
ranking-prebuilt の 2 尺（スロット別の固定値）と違い、本方式は 24 秒の 1 尺だけを持つ。理由: ① 21-2 の人間ゲートで「24 秒・ループ前提」をフォーマットの基準として承認済み ② 尺は問題文 + ルールのナレーション予算（8.3）とビート（8.2）から決まり、尺を変えると版面の不変条件（周期は 720 の約数）ごと作り直しになる ③ 参加型の効果はコメント欄で出るため尺比較の検証価値が低い。将来尺を変える場合は parameters.duration_seconds と timeline.ts の定数を同時に変え、全数再ビルドする（8.4）。2026-10-17 追記（R-1）: 単尺のまま 24 秒 → 29 秒へ変え、ループ前提（②の周期の制約）をやめた（8.2 の決定）。画像バッチ側は課題 I-041 を Phase 29 で合わせる（下の決定）。slots を持たないため、SCHEDULED_AT による決定的解決のロジックは本方式に含めない。

2026-09-04（21-3）・2026-10-17 追記（R-1）

D-03 尺の宣言値を 29 へそろえる

決めたこと
許容値を ALLOWED_DURATIONS = frozenset({29}) にし、宣言値をそのまま generated_media.duration_seconds に記録する（実尺は測らない）
理由
R-1 で動画は 29 秒になったが、画像バッチは 24 しか許さず generated_media.duration_seconds に 24 を記録していた（I-041）。許容値を先に 29 だけにすると Aurora の宣言値 24 の回で異常終了し、Aurora を先に 29 にすると旧コードで異常終了するため、29-1 で許容値を ALLOWED_DURATIONS = frozenset({24, 29}) に広げ → 29-2 で Aurora の prompt_configs.parameters を 29 へ切り替え → 29-3 で 29 のみに戻す 3 段にした。宣言値をそのまま記録する作り（実尺は測らない）は quiz-prebuilt・ranking-prebuilt と揃えて変えない。登録 SQL（01_prompt_caption.sql・03_audio_assets.sql）は 29-1 で 29 を正にした。29-2（2026-10-17）で Aurora・ローカルの宣言値と BGM の尺を 29 にし、R-1-5 の後に 24 で記録された生成結果 1 件を補正。同日 20:00 の定時で 29 の記録を確認したうえで、29-3 で ALLOWED_DURATIONS = frozenset({29}) に戻した。
日付・出典
2026-10-17（Phase 29。課題 I-041）
