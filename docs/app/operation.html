要約

このページはアプリ（業務）の運用の手順を定める。機能別の基本設計 投稿（2・4 章）・トークン更新（5 章）・インサイト収集（6 章）の「運用の手順」にあたる。インフラの運用（デプロイ・Aurora の一時停止・監視の仕組み・コスト）は infra/operation.html、在庫の動画の作り方は生産の詳細設計が持つ。図 1 は、運用者が手を動かす場面と、このページの章の対応を表す。

項目要点
セットの追加セット別設計書 → Secret 作成・検証 → DB 登録 → Scheduler 追加 deploy（有効のまま）→ is_active で稼働開始（2.1）
投稿の失敗通知のみ（欠番許容）。手動の再投稿は対象 run の scheduled_at を指定して SFN から起動する（4 章）
トークン投稿用は手動の再認可 + リマインダー 1 件、コメント返信用は Lambda が毎週自動更新（5.4）
KPI月初 4 日以降に集計ランナーでビューを引き、セット計画書と事業戦略書へ転記（6.3）

手順 3: CDK の ImageBatchStack に EventBridge Scheduler を追加して deploy する

入力に set_code を指定したスケジュールを、投稿時刻 1 つにつき 1 件追加する。Schedule 名は命名規約 acps-{env}-image-generation-{set_code}[-{slot_code}] に従う（スロット対応方式のセットはスロットごとに 1 件・slot_code をサフィックスに付ける）。 命名規約・cron 式・Scheduler 定義の書き方は infra/workflow.html セクション 1.5、実装は image-batch-stack.ts の imageGenerationSchedules 配列（ここに 1 エントリ追加するだけでよい）。 変更後のデプロイは cdk deploy -c env=prod --exclusively ImageBatchStack（イメージタグ 3 つの Context 指定が必須。指定ルール・現行タグの確認方法は infra/cicd.html セクション 3.2）。

Scheduler は有効のまま deploy してよい: 画像生成・SNS 投稿・インサイト収集の 3 バッチは batch_sets.is_active=0 のセットでは何もせず正常終了するため、登録中のセットは is_active=0 で置き、稼働開始は is_active を 1 にする UPDATE で切り替える（21-7 で決定。infra/workflow.html セクション 1.5 の決定 21-7。適用例は content/umigame-stock/umigame-soup-1/set-registration/）。

あわせてインサイト収集 Scheduler をセットごとに 2 件（acps-{env}-insights-collection-{set_code}-{morning|evening}。06:00 / 18:00 JST）InsightsBatchStack へ追加して deploy する（infra/workflow.html セクション 1.6。16-10 で新設された第 3 のバッチ。17-2 で本手順に明記）。

スロット対応方式のセットは、スケジュール時刻がそのままスロットの指定になる parameters.slots を持つクイズ方式（quiz-prebuilt 等）では、どのスロットとして生成するかを方式側が SCHEDULED_AT の JST 時から決定的に解決する（Scheduler の Input にスロットは持たせない）。 スケジュール時刻を from_jst_hour の境界をまたいで変更すると生成されるスロットが変わるため、時刻の変更時はセット別設計書のスロット表と必ず突き合わせること。

2.2 セット廃止・入れ替え（スクラップ&ビルド）

  1. batch_sets.is_active=0 に更新する（両バッチは is_active=0 のセットをスキップして正常終了する）。この時点でスケジュールが残っていても実害はないため、順序を厳密に守る必要はないが、次のステップより先に行うことを推奨する
  2. CDK から該当セットの Scheduler 定義をすべて削除して deploy する（イメージタグの Context 指定が必須。infra/cicd.html セクション 3.2）。削除対象は 2 スタックにまたがる: image-batch-stack.ts の画像生成（スロット非対応なら 1 件・対応ならスロット数分）と insights-batch-stack.ts のインサイト収集 2 件（06:00 / 18:00。16-10 で追加）。DISABLED 化ではなく削除する（定義の中身はコード内のコメントに残す） → 理由 D-11
  3. データ（DB レコード = メタ情報・投稿履歴）は削除せず残す。S3 実体（画像・動画ファイル）はインフラの 30 日ライフサイクルで自動削除される対象であり「残す」対象に含まない（Phase 9-3 で確定。データモデル設計 セクション 5）。音源ストック（audio/{set_code}/）はライフサイクル対象外のため自動削除されないが、廃止時もレコード・ファイルとも削除せず残す（容量は僅少で、セット復活・類似セットでの再利用可能性があるため。Phase 14-4 で確定）
  4. セット別設計書は削除せず、廃止の旨（バッジ・廃止日）を付けて履歴として残す。あわせてセット計画書のステータス・事業戦略書（予算・セットポートフォリオ）も停止に合わせて更新する
初回実地の気づき（2026-09-03、Phase 20-1 で fantasy-animals-1 を停止）

上記手順どおりで完了し、手順の変更は不要だった。実地で分かった注意点は次の 2 つ。

  • インサイト追跡ウィンドウが打ち切られる: インサイト収集バッチも is_active=0 のセットをスキップして正常終了する（services/insights-batch/app/main.py）ため、手順 1 を適用した時点で「最終投稿から 14 日」の追跡が止まる。最終投稿分の 14 日データまで採りたい場合は、手順 1 の UPDATE だけを 14 日遅らせる（Scheduler の削除は先に行ってよい。新規投稿が止まるだけで収集は動く）。20-1 では打ち切りを許容した
  • Scheduler は 2 スタックにまたがる: 2.1 の「セット追加で増えるのは Scheduler 定義 1 件」は 16-10 のインサイト収集 Scheduler 追加以前の記述であり、現在は 1 セットあたり画像生成 + インサイト収集 2 件が増える。廃止時の削除漏れを防ぐため、cdk diff の削除リソースが想定件数と一致することを deploy 前に確認する

3. プロンプト・キャプション・音源・ストック管理

DB に置く設定（プロンプト・キャプションテンプレート・音源）の変え方。在庫（ストック）の作り方・投入・ビルドはセットごとの生産の詳細設計へ移してあり、ここには導線だけを置く。

prompt_configs・caption_templates・audio_assets・quiz_stock_items（16-1 新設）は DB 直接操作（Query Editor 等）で登録・変更する。管理画面は将来拡張。生成時にはプロンプトのスナップショットが generated_media に、出題のスナップショットが quiz_items に、キャプションのスナップショット（プレースホルダ展開後の最終文）が posts に記録されるため、変更しても過去の生成・投稿記録は影響を受けない。

軽微な文言修正（履歴を残さない場合）

既存の有効行を直接 UPDATE する。過去の生成実行への影響はスナップショットにより発生しない。

UPDATE prompt_configs SET prompt_text = '(新しいプロンプト本文)' WHERE id = :prompt_config_id;
UPDATE caption_templates SET template_text = '(新しいキャプション本文)' WHERE id = :caption_template_id;

差し替え（旧設定を無効化して残す場合）

新しいレコードを追加し、旧レコードを is_active=0 にする。prompt_configs は「is_active=1 が 0 件」だと画像生成バッチが異常終了する（batch-flow.html セクション 2）ため、必ず 1 トランザクションで実行し、0 件になる瞬間を作らない。

START TRANSACTION;
INSERT INTO prompt_configs (set_id, prompt_text, negative_prompt, parameters, is_active)
VALUES (:set_id, '(新しいプロンプト本文)', NULL, NULL, 1);
UPDATE prompt_configs SET is_active = 0 WHERE id = :old_prompt_config_id;
COMMIT;

caption_templates は is_active=1 が 0 件でも投稿処理は継続する（キャプションなしで投稿。data-model.html セクション 4.3）ため、トランザクションは必須ではないが同様の手順で問題ない。

プレースホルダ入りのテンプレート（展開規則は batch-flow.html 3.4「キャプションの作り方」）も上の手順（UPDATE / INSERT + 無効化）で直してよい。プレースホルダの綴り（既知の 10 種）を崩さないことと、テンプレートの系（クイズ系 / ランキング系 / umigame 系）をセットの方式に合わせること（展開元の行がないと投稿が異常終了する）に注意する → 理由 D-01

AI 利用の開示（ハッシュタグ）の運用ルール

AI 開示ハッシュタグは #AIart → 理由 D-02

事業戦略書の必須要件「AI 利用の開示」（14-2 壁打ち決定事項 #7: ハッシュタグ方式）の具体タグを #AIart に確定する。
  • 全セットのキャプションテンプレート（caption_templates.template_text）に #AIart を必ず含める。テンプレートの新規登録・差し替え時のチェック項目とする（セクション 2.1 のチェックリスト・INSERT 例にも反映済み）
  • テンプレート経由で全投稿に確実に付与される（投稿処理側の実装は不要。キャプション 0 件時の投稿は従来どおり継続されるため、テンプレート登録漏れは週次のミュート確認〔セクション 4.4〕等の目視で拾う）
  • プラットフォームが公式の AI ラベル指定手段（API パラメータ）を提供した場合は、その時点で移行を検討する

音源の調達・前処理・登録（動画方式のセットのみ）

リール用 BGM は権利クリア済み音源をセットごとに 3〜5 曲、前処理済みの完成形で S3 にストックし、投稿ごとに順繰りローテーションする（data-model.html セクション 4.8）。前処理は事前手動（S3 登録前に 1 回だけ）で行い、合成時はそのまま多重化する → 理由 D-12。事前ビルド方式のセットの BGM は動画のビルド時に焼き込む（セットごとの作り方は生産の詳細設計）。

手順 1: 調達（ライセンス確認と証跡の控え）

  • CC0・フリーライセンス音源（Pixabay License 等）を優先する。CC-BY はクレジット表記の運用が必要になるため避け、CC-BY-NC（非商用）は使用不可（収益化コンテンツのため。14-2 壁打ち記録 セクション 2.2）
  • ダウンロード時に証跡 3 点（出典 URL・ライセンス種別・取得日）を控える（手順 4 で audio_assets のカラムに記録する。別ドキュメントでの管理はしない）

手順 2: 前処理（ffmpeg。ローカルで 1 回だけ）

動画の尺は方式カタログ（batch-flow.html セクション 2.1）の該当方式に合わせる（gpt-image-kenburns = 10 秒、クイズ方式 = 20 秒素材。15-5 で尺可変に一般化。クイズ方式は 16-1 の 16 秒化後も 20 秒素材のまま — トリムと終端フェードはレンダラー（gpt-quiz-multicut）の ffmpeg 側で吸収するため、既存素材の再前処理は不要で新規調達時も 20 秒で作る〔方式設計書セクション 9〕）。尺に合わせて切り出し、音量正規化（ラウドネス）とフェードを掛け、AAC（.m4a）で書き出す。AAC に統一するのは、合成時に MP4 コンテナへ再エンコードなしで多重化できるため。

# 例: 原曲の 12 秒地点から 10 秒を切り出し、ラウドネス正規化 + フェードを掛けて AAC 化する
# （20 秒尺の方式では -t 20・afade=t=out:st=19 に読み替える。フェード長は尺によらず in 0.5 秒 / out 1 秒）
ffmpeg -ss 12 -i source.mp3 -t 10 \
  -af "loudnorm=I=-14:TP=-1.5:LRA=11,afade=t=in:st=0:d=0.5,afade=t=out:st=9:d=1" \
  -c:a aac -b:a 128k -ar 48000 -ac 2 track01.m4a
  • 切り出し位置（-ss）は曲のサビ・盛り上がりに合わせて試聴しながら決める。20 秒尺ではループ耐性（切り出し末尾から先頭に戻っても違和感がないか）も確認する
  • ラウドネス正規化は I=-14（ストリーミング標準の -14 LUFS）を目安とし、曲間の音量差をなくす
  • 書き出し後に必ず試聴確認する（頭切れ・フェードの不自然さ・ノイズ）

ラウドネス正規化は 2 パス方式 → 理由 D-03

上の 1 コマンド版（単一パス loudnorm）は形の例で、実際はパス 1 で対象区間を解析（print_format=json）し、得た measured_* 値と linear=true を指定してパス 2 で線形適用する。

  • 解析は切り出し後の区間に対して行う（原曲全体ではない）
  • フェードは正規化の後段に置く。フェードアウトの分だけ最終実測値は目標 -14 をわずかに下回るが、全曲一律のため曲間差は生じない
  • 実装スクリプトは 14-6 で使用した 2 パス処理（process() 関数で 1 曲ずつ解析 → 適用）を踏襲する
ランキング方式（ranking-prebuilt / pref-ranking-1）の前処理は上記と 2 点違う（17-5b） ①尺は 30 秒ちょうど（動画と同尺。コンポジションは曲が短いとループするため、30 秒未満だと動画内でループの継ぎ目が鳴る）②フェードは焼き込まない（頭 0.5 秒 / 尻 1.5 秒のフェードはコンポジション側が掛けるため、素材にも焼くと二重に掛かる）。さらに曲数も 3〜5 曲ではなく 1 曲（世界観をそろえるためのユーザー判断。ミュート検知時の影響範囲と併せてセット別設計書セクション 6（17-5b）に記録）。ラウドネスの 2 パス方式（I = -14 LUFS）と AAC 化は共通ルールどおり。手順 2〜4（切り出し・正規化・S3 キーの決定・audio_assets 登録 SQL の生成）は専用ツール content/video-build/pref-ranking-1/prepare_bgm.py がまとめて行う（証跡 3 点は work/bgm/tracks.json に書けば SQL に転記される）。理由の詳細はセット別設計書セクション 6。

手順 3: S3 への配置

aws s3 cp track01.m4a s3://acps-prod-images-{アカウントID}/audio/{set_code}/track01.m4a

audio/ プレフィックスは 30 日ライフサイクルの対象外（Phase 14-6 で images/・videos/ のプレフィックス限定へ変更済み。infra/stacks.html セクション 3.1）。時間帯で BGM を出し分けるセット（logic-training-1）は audio/{set_code}/{morning|noon|night}/track01.m4a のスロット別プレフィックスに置く（data-model.html セクション 5）。

手順 4: audio_assets への登録

セクション 2.1 手順 2 の (5) の INSERT を使う（証跡 3 点 + duration_seconds を必ず入れる）。時間帯で BGM を出し分けるセットは time_slot に S3 のスロットプレフィックスと同じ slot_code（morning / noon / night 等）を指定する（選曲のスロット判定はこのカラムで行い、S3 プレフィックスは配置規約に留める。data-model.html セクション 4.8）。

効果音（SE）の調達・登録（クイズ方式のセットのみ。Phase 15-5 新設）

クイズ方式はカウントダウンティック・誘導チャイム（15-4 ユーザー決定時の呼称は「正解チャイム」。16-1 でキャプション誘導の注意喚起へ用途変更、ファイル名 answer_chime.m4a は不変）の SE 2 種を使う。SE は BGM ローテーション外・カットタイミング固定の固定アセットだが、証跡一元管理の原則を保つため audio_assets に asset_type='se' で登録する（data-model.html セクション 4.8）。

  • 調達: BGM と同じ基準（CC0 / Pixabay License 等。手順 1 の証跡 3 点を控える）
  • 前処理: ラウドネス正規化（2 パス loudnorm）は掛けない（短尺 SE には不適切）。ピークを -1.5 dBTP 目安に整え、AAC（.m4a）化のみ行う。ティックは 1 秒間隔 × 5 打の 5 秒連続ファイル、チャイムは 1〜2 秒に整える（配置タイミング・音量バランスの設計は方式側。15-6 実装）
  • 配置と登録: S3 キーは固定ファイル名規約 audio/{set_code}/se/countdown_tick.m4a / audio/{set_code}/se/answer_chime.m4a。audio_assets へ asset_type='se' で INSERT する（セクション 2.1 手順 2 の (5) と同型 + asset_type 指定）。レンダラー（gpt-quiz-multicut）は起動時にこの 2 キーの有効レコード存在を検査し、欠品は設定ミスとして異常終了する（quiz-prebuilt では事前ビルド時に検査される）
  • 差し替え: BGM と同様に is_active=0 + 代替の登録で行う（固定ファイル名のため S3 オブジェクトの置き換えでもよいが、証跡を更新するため原則レコードを追加し旧レコードを無効化する）

ローテーションと曲の入れ替え

  • 選曲は順繰り（asset_type='bgm' のうち last_used_at が最古の有効レコード。未使用曲が最優先。SE は対象外）。曲の追加はいつでも INSERT のみでよい（追加曲は未使用のため次回に使われる）
  • 曲を外す場合は is_active=0 に更新する（レコードは削除しない。証跡・使用履歴を残す）
  • 動画方式のセットで有効音源が 0 件になると画像生成バッチが異常終了する（設定ミス扱い。data-model.html セクション 4.8）。prompt_configs の差し替えと同様、無効化する場合は先に代替曲を登録してから行い、0 件になる瞬間を作らない
  • 時間帯スロット対応のセット（クイズ方式）の 0 件判定はスロットごと: あるスロットで「time_slot 一致 + NULL（共通曲）」の有効 BGM が 0 件になると、当該スロットの処理（quiz-prebuilt では動画ビルド、実行時合成方式では当該スロットの実行）だけが異常終了する（他スロットは動き続けるため気づきにくい）。スロット別曲の差し替え時も「先に代替を登録してから無効化」を守り、スロット単位で 0 件の瞬間を作らない（15-10。順繰り〔last_used_at 最古〕はスロット絞り込み内で維持される）

4. 投稿失敗時の対応

この章は、機能別の基本設計 投稿で失敗したときの運用者の手順を詳しくしたもの。

基本は通知のみ（欠番許容） → 理由 D-13。ただし Phase 28（28-1 設計・28-2 実装）から、一過性エラーはバッチが段階別に自動で処理する: 公開前（コンテナ作成・処理待ち）はコンテナ作成から 1 回だけやり直し、公開の一過性エラーはコンテナの status_code を照会して未公開（FINISHED）のときだけ同じコンテナで 1 回再送する（表と判定基準の正は batch-flow.html 3.3「一過性エラーの段階別の扱い」）。通知が来るのはそれでも success にならなかった場合で、運用者の手順（4.1〜4.3）は変わらない。やり直しが起きた行は api_response が {"final", "first_error", "container_check"} の形になる。

障害対応の入口はスキル /incident（22-3〔2026-09-19〕新設。手順の正は .claude/skills/incident/SKILL.md）。失敗通知・「投稿が出ていない」など本番・運用の異常を認識したら、本セクションの手順に入る前に /incident を起動し、課題体系との照合（予言されていた課題・前にも起きた事象）→ 切り分け・復旧（本番操作は人間ゲート）→ 事象記録 → 課題の更新の順で進める（ルールは課題体系 4.7）。本セクション 4.1〜4.4 はその中の「切り分け・復旧」で参照する手順。

4.1 確認手順

  1. 失敗時はメール通知（MonitoringStack のアラーム / EventBridge Rule。仕組みは infra/workflow.html セクション 7〜10）を受ける
  2. Step Functions 実行履歴・CloudWatch Logs で、どのステートで・どのアカウントで失敗したかを確認する
  3. posts テーブルで失敗の詳細（status / error_message / api_response）を確認する: 
    SELECT p.id, p.media_type, p.status, p.error_message, p.api_response, p.updated_at,
       sa.account_code, gr.scheduled_at
FROM posts p
JOIN sns_accounts sa ON sa.id = p.sns_account_id
JOIN generation_runs gr ON gr.id = p.generation_run_id
JOIN batch_sets bs ON bs.id = gr.set_id
WHERE bs.set_code = 'fashion-set-1'
ORDER BY p.updated_at DESC
LIMIT 20;
  4. 必要な場合のみ、SNS 投稿ワークフロー（sns-posting-sfn）を手動で単独起動する（infra/operation.html セクション 1.2）。再実行は必ず Step Functions 経由で行い、ECS RunTask の直接実行は使わない（batch-flow.html セクション 1 の前提。理由は batch-flow.html D-18）。手動起動では対象生成実行の実際の scheduled_at を入力に明示し、その回だけが処理される（batch-flow.html セクション 3.1。26-1 で当回固定に変更。現在時刻を便宜的に入れない。入力例は infra/operation.html セクション 1.2）。一度試行して有効な全アカウントが終端状態になった分は再実行しても投稿されない（ALREADY_TERMINAL。意図的に再対象にしたい場合は 4.2 を参照）。起動前に次のクエリで対象 run を確認する: 
    -- 手動起動する回の確認（scheduled_at は UTC。JST 列で時間帯を確かめる）
SELECT gr.id AS generation_run_id, gr.scheduled_at,
       CONVERT_TZ(gr.scheduled_at, '+00:00', '+09:00') AS scheduled_at_jst,
       (SELECT COUNT(*) FROM generated_media gm WHERE gm.generation_run_id = gr.id) AS media_count,
       sa.account_code, p.media_type, p.status
FROM generation_runs gr
JOIN batch_sets bs ON bs.id = gr.set_id
JOIN sns_accounts sa ON sa.set_id = gr.set_id AND sa.is_active = 1
LEFT JOIN posts p ON p.generation_run_id = gr.id AND p.sns_account_id = sa.id
WHERE bs.set_code = :set_code
  AND gr.scheduled_at = :scheduled_at;

4.2 手動補正手順

DB を手動補正する前に、対象の set_code・post_id・現在の値をセット記録（docs/plans/<set_code>-log.html の「トラブル対応の記録」）に記録してから更新する。横断・基盤起因の事象は開発記録の「事象記録」へ（記録先の二分は Phase 18 で導入、22-2 で開発記録側へ移設。恒久対策の課題は課題体系に起票する）。

published_unconfirmed を投稿済みに補正する

Instagram 側で投稿済みを確認できた場合のみ実行する。error_message が「PUBLISHED 確認済み:」で始まる行（Phase 28。公開の一過性エラー後にバッチがコンテナの PUBLISHED を確認済み）は投稿済みが確定しているので、メディア ID と投稿日時だけを調べて補正する。メディア ID は GET /{ig-user-id}/media?fields=id,timestamp,media_product_type,permalink の一覧から、その回の投稿時刻・種別（リール / ストーリーズ）で特定する（ストーリーズは GET /{ig-user-id}/stories。24 時間を過ぎると引けないため早めに補正する）。

UPDATE posts
SET status = 'success',
    platform_post_id = '(確認できた Instagram media ID)',
    posted_at = '(確認できた投稿日時 UTC)',
    error_message = NULL
WHERE id = :post_id
  AND status = 'published_unconfirmed';

failed / published_unconfirmed を未投稿として再試行可能にする

Instagram 側で未投稿を確認し、原因を解消した上で実行する。posts は UNIQUE (generation_run_id, sns_account_id, media_type) のため新規行は作れず、既存行を pending に戻して「最初から実行」扱いにする（batch-flow.html セクション 3.2 の復旧ロジック）。Instagram のメディアコンテナは時間経過で無効になり得るため、platform_container_id を含めてクリアし常にコンテナ作成からやり直す。

注意: ストーリーズ行（media_type='story'）にはこの補正は効かない 投稿対象の決定はリール行の終端状態で決まるため（data-model.html セクション 4.4）、ストーリーズ行を pending に戻しても後続実行では再選択・再処理されない。 ストーリーズは 24 時間で消える再掲コンテンツであり遅延再投稿の価値が低いため、失敗したストーリーズ行は failed のまま欠番として許容する（15-10。リール本体の投稿は成立している）。どうしても再掲したい場合のみ、Graph API を手動で呼び出す（バッチの再実行では行わない）。 
UPDATE posts
SET status = 'pending',
    platform_container_id = NULL,
    platform_post_id = NULL,
    caption_template_id = NULL,
    caption_text_snapshot = NULL,
    error_message = NULL,
    api_response = NULL
WHERE id = :post_id
  AND status IN ('failed', 'published_unconfirmed');
注意: 補正しただけでは再投稿されない（26-1 で変更） SNS 投稿バッチは自分を起動した回（当回）の生成実行だけを処理する（batch-flow.html セクション 3.1）。後続の定時実行は、補正して pending に戻した過去の生成実行を拾わない。補正した回を投稿したい場合は、4.1 の確認クエリで対象 run を確かめ、その run の scheduled_at を指定して sns-posting-sfn を手動起動する（時間帯の確認を含む。4.1 手順 4）。

4.3 stale データ（未完了のまま残った生成実行）の扱い

data-model.html セクション 4.4 で確認したとおり、pending / container_created のまま終端状態に達しない posts 行が残ると、その生成実行は同じ回の Retry では復旧に使われるが、後続の回からは選ばれない（当回固定。batch-flow.html 3.1）。これは主に、ECS タスクの異常終了（OOM Kill・Fargate 基盤障害等）でアプリケーションが例外を捕捉して failed に更新する前に強制終了した場合に起こる。後続投稿はブロックしないが、放置すると投稿の有無が不確定な記録が残り、投稿漏れに気づきにくい（投稿ゼロ・stale の可視化は I-006・I-025 で別途扱う）。

stale 専用のアラーム・カスタムメトリクスはない。運用者は既存の失敗通知を起点に、以下のクエリで stale な行の有無を確認する → 理由 D-14。

-- 各セットの未完了 (generation_run, account) を一覧表示（古い順。当回固定以後は後続をブロックしないが、記録の確定のため確認する）
SELECT bs.set_code, gr.id AS generation_run_id, gr.scheduled_at,
       sa.account_code, p.media_type, p.status, p.updated_at
FROM generation_runs gr
JOIN batch_sets bs ON bs.id = gr.set_id
JOIN sns_accounts sa ON sa.set_id = gr.set_id AND sa.is_active = 1
LEFT JOIN posts p ON p.generation_run_id = gr.id AND p.sns_account_id = sa.id
WHERE bs.is_active = 1
  AND (p.id IS NULL OR p.status NOT IN ('success', 'failed', 'published_unconfirmed'))
ORDER BY gr.scheduled_at ASC;
  • 判定の目安: 1 日複数回実行する運用のため、status が pending / container_created のまま updated_at から半日以上経過している行は stale の疑いが強い（対応する Step Functions 実行がすでに終了しているにもかかわらず DB が更新されていない状態）。行が存在しない（p.id IS NULL）だけの場合は、直近の生成実行がまだ処理待ちなだけの通常状態であり stale ではない
  • ストーリーズ行（media_type='story'。V004）の stale は後続投稿をブロックしない: 投稿対象の決定はリール行の終端状態で決まるため（data-model.html セクション 4.4）、ストーリーズ行が途中状態のまま残っても次の生成実行の投稿は進む。補正は同じく 4.2 の手順で終端状態（実際の投稿有無に応じて success / failed）へ更新して記録を確定させるのみでよい（pending へ戻す補正は効かない — 4.2 の注意を参照）
  • 対応: 対象の Step Functions 実行履歴・CloudWatch Logs で実際の投稿有無を確認し、4.2 の手順で success（実際は投稿済みだった場合）または failed（実際は未投稿だった場合）の終端状態に補正する。終端状態に補正して記録を確定させる（後続の投稿対象決定には影響しない）。その回を改めて投稿したい場合は 4.2 の注意のとおり予定時刻を指定して手動起動する
  • 将来的にセット別失敗時ポリシー（追いつく / 捨てる。batch-flow.html）を導入する際は、stale データの扱いも合わせて再設計する

  2. ミュート・警告を検知した場合:

手順 4: アプリへの権限付与（App Review を回避する 2 つのロール）

本システムはユーザー自身のアカウントにのみ投稿するため、Meta のアプリレビューは不要（他者のアカウントに投稿する場合のみ必須）。代わりに以下 2 つのロールを設定する。

  1. アプリの管理者ロール: アプリの「アプリの役割」→「役割」で、Facebook アカウント（既存 ID の使い回しでよい）が「管理者」または「開発者」になっていることを確認する（アプリ作成者は通常自動で管理者になる）
  2. Instagram テスターロール（投稿権限に必須）: 同じ「アプリの役割」画面の「Instagram テスター」タブで「メンバーを追加」→ 投稿に使う Instagram プロアカウントのユーザー名を入力して招待する。 続けて Instagram 側（PC ブラウザ。スマホアプリには「テスターへのご招待」メニューがない）でログインし、「設定」パネル右上の検索ボックスに「テスター」と入力して「テスターへのご招待」を開き、招待を承認する（通知欄に届く場合もある）
2 つのロールの違い 「管理者」ロールはアプリ全体（Facebook 側）の管理権限であり、Instagram Graph API の権限付与とは別軸。投稿権限のトークンを発行するには、Instagram テスターロールの承認が別途必須（管理者ロールだけでは不足する）。

手順 5: 権限付与とトークン取得

  1. 短期アクセストークンの取得: Graph API Explorer を開く → 右上の「Meta App」で対象アプリを選択 → 「User or Page」→「Get User Access Token」→ 権限（instagram_basic / instagram_content_publish / pages_show_list / pages_read_engagement / business_management）を選択 → 「Generate Access Token」→ Facebook ログインのポップアップで許可する。「Access Token」欄の文字列が短期トークン（有効期限 1 時間）
    既存アプリ流用時、権限付与ポップアップでのページ選択に注意（2026-07-27） 再認可のポップアップでは管理対象ページのチェックリストが出る。今回追加するページにチェックを入れる（漏れると次の /me/accounts に新ページが出てこない）と同時に、運用中の既存セットのページのチェックを外さない。外すとそのページへのアクセスが取り消され、稼働中セットの投稿が停止する。 なお新しいトークンを発行しても既存の長期トークン文字列自体は失効しないため、既存セットの Secret を更新する必要はない。
  2. 長期アクセストークンへの交換: ブラウザで以下の URL を値を埋めて開く（GET リクエストのため URL を開くだけでよい） 
    https://graph.facebook.com/v21.0/oauth/access_token?grant_type=fb_exchange_token&client_id=<APP_ID>&client_secret=<APP_SECRET>&fb_exchange_token=<SHORT_LIVED_TOKEN>
    APP_ID / APP_SECRET はアプリの「アプリの設定」→「基本設定」で確認できる。レスポンスの access_token が長期トークン。token_expires_at に控える値は expires_in ではなく debug_token の実測値を使う（算出方法は 5.4）
  3. ig_user_id の取得: 2 段階で引く。まず管理対象の Facebook ページ一覧から対象ページの id（= PAGE_ID）を確認する 
    https://graph.facebook.com/v21.0/me/accounts?access_token=<LONG_LIVED_TOKEN>
    次にその PAGE_ID で Instagram 側の ID を引く 
    https://graph.facebook.com/v21.0/<PAGE_ID>?fields=instagram_business_account&access_token=<LONG_LIVED_TOKEN>
    返り値の instagram_business_account.id が ig_user_id（17841 で始まる 17 桁前後の数字）。 /me/accounts が返すのは Facebook ページ ID であり ig_user_id ではない点に注意する（15-7 で取り違えが発生した）。 ページ「基本データ」画面の URL に出る数字を PAGE_ID として使うと失敗する場合がある（Business Suite 上の別 ID を指している可能性があるため）ので、必ず /me/accounts の値を使う。
    instagram_business_account フィールド自体が返らない場合は、ページと Instagram の連携が未完了か instagram_basic 権限が付いていない
実値をこの手順の外に出さない App Secret・アクセストークン・ig_user_id はすべてブラウザ操作で完結させ、会話ログ・コマンド履歴・チャットには残さない。取得した 3 値（access_token / ig_user_id / token_expires_at）はメモに控え、Secret 作成（2.1 手順 1・5.3 手順 1）ではマネジメントコンソールから直接入力する（5.5 の画像生成 API キーと同じく、実 API キー・トークンはコンソールで手で設定し CLI・会話に残さない）。

手順 6: Secret を作成する（コンソールで入力できない場合の CloudShell 方式）

通常はマネジメントコンソールの Secrets Manager 画面から直接入力する（2.1 手順 1）。スマホの AWS コンソールアプリなどシークレット値の入力欄に貼り付けができない環境では、CloudShell から以下の 2 段階で作成する（15-7 で実施）。トークンをコマンドライン・シェル履歴に残さないことが要件。

  1. トークンを環境変数へ読み込む。この 1 行だけを単独で貼り付けて実行する（複数行をまとめて貼ると続きの行が read の入力として消費されてしまう）。実行後の入力待ちでトークンを貼り付ける（画面には表示されない） 
    umask 077; read -rsp "token: " TOKEN; echo; echo "len=${#TOKEN}"
    表示される len で貼り付け欠けを検知する（長期ユーザートークンは EAA 始まりの 190〜200 文字程度）
  2. 一時ファイル経由で Secret を作成する。このコマンド自体にトークンは含まれないため履歴に残ってよい 
    printf '{"access_token":"%s","ig_user_id":"<IG_USER_ID>","token_expires_at":"<EXPIRES_AT>"}' "$TOKEN" > ~/sec.json \
  && aws secretsmanager create-secret --region ap-northeast-1 \
       --name acps/prod/<set_code>/sns/instagram/<account_code> \
       --secret-string file://$HOME/sec.json; rm -f ~/sec.json; unset TOKEN
    CloudShell の $HOME は永続化されるため、一時ファイルは umask 077 で作成し実行後に必ず削除する

作り直す場合は aws secretsmanager delete-secret --region ap-northeast-1 --secret-id <名前> --force-delete-without-recovery で即時削除してからやり直す。

手順 7: 作成した Secret を検証する（17-5b 新設。DB 登録より前に行う）

Secret の値は目視できないため、投稿バッチを動かす前に「トークンが有効か」「ig_user_id が本当に新アカウントを指しているか」を機械的に確認する。値を出力しない形で実行できる（下記は日付・ユーザーネームだけを表示する）。

aws secretsmanager get-secret-value --region ap-northeast-1 --secret-id <Secret 名> \
  --query SecretString --output text | python3 -c "
import sys, json, urllib.request, datetime
d = json.load(sys.stdin); t = d['access_token']; ig = str(d['ig_user_id'])
b = json.load(urllib.request.urlopen('https://graph.facebook.com/v21.0/debug_token?input_token=%s&access_token=%s' % (t, t)))['data']
f = lambda x: datetime.datetime.fromtimestamp(x, datetime.timezone.utc).strftime('%Y-%m-%dT%H:%M:%SZ') if x else 'never'
print('valid=%s expires_at=%s data_access=%s' % (b.get('is_valid'), f(b.get('expires_at')), f(b.get('data_access_expires_at'))))
print('scopes =', ','.join(sorted(b.get('scopes', []))))
a = json.load(urllib.request.urlopen('https://graph.facebook.com/v21.0/%s?fields=username,media_count&access_token=%s' % (ig, t)))
print('ig_user_id -> username=%s media_count=%s' % (a.get('username'), a.get('media_count')))"
  • username が新セットのアカウントであること（新規開設直後なら media_count=0）。既存セットのユーザーネームが返ったら ig_user_id の取り違え
  • scopes に instagram_content_publish と instagram_manage_insights の両方があること（後者が無いとインサイト収集が失敗する = セクション 5.4）
  • data_access の値を token_expires_at に記録し、その 7 日前へリマインダーを更新する（セクション 5.4）
再認可のページ選択漏れは「既存アカウントの ID が入る」形で表面化する（2026-08-26・17-5b の実例） 17-5b では、手順 5 の再認可ポップアップで新しい Facebook ページにチェックを入れ忘れたため /me/accounts に新ページが出ず、そこから引いた ig_user_id が既存セット（fantasy-animals-1）のアカウントを指したまま Secret に入っていた。形式（17841 始まりの 17 桁）は正しく、DB 登録も投稿バッチの起動も通ってしまうため、そのまま稼働すると別セットのアカウントへ投稿される。手順 7 の username 確認はこの取り違えを検出するためのもので、15-7 の「PAGE_ID を ig_user_id と取り違える」事象と同じ根（/me/accounts 周辺）から来ている。復旧は「新ページを含めて再認可 → /me/accounts が全ページを返すことを確認 → 対象ページの instagram_business_account.id で Secret を更新（put-secret-value。旧バージョンは残るため戻せる）」。

5.2 Secret 名規約の最終確認

Secret 名規約 acps/{env}/{set_code}/sns/{platform}/{account_code}（infra/security.html セクション 1.2）と、構成要素の意味付け（set_code = batch_sets.set_code、account_code = sns_accounts.account_code）はアプリ設計大枠 セクション 5で確定済みであり、本規約に変更はない。account_code は Secret 名導出専用のため作成後変更不可。変更が必要な場合は新アカウント（新しい account_code）として追加し、旧アカウントは is_active=0 にする。

Phase 10-1 での再確認（2026-07-15 実施済み） 本規約は Phase 0〜8（インフラ構築）を経ずに Phase 9 として前倒しで確定したものであるため、Phase 10-1（アプリ設計の最終 Fix）でインフラ実態と突き合わせて再確認した。 IAM ポリシー（プレフィックスベースの Secret 読み取り権限。infra/security.html セクション 2.1）・Secret 運用の実態と矛盾はなく、規約は変更なしで最終確認とする。

5.4 Instagram アクセストークン更新の具体手順とリマインド運用

コメント返信用トークン（umigame-soup-1）は自動更新。本節の手動更新・リマインドは投稿用トークンだけが対象 → 理由 D-05

コメント返信用の長期トークン（Instagram ログイン方式・Secret acps/{env}/umigame-soup-1/comment-reply{-staging} の ig_access_token）は 60 日で失効するが、トークン更新 Lambda が毎週月曜 04:00 JST に GET /refresh_access_token で更新し、新しいトークンと token_expires_at を Secret に書き戻す（構成は infra/stacks.html セクション 3.6）。リマインダーは登録しない。運用者が行うのは次の 3 つだけ。
  • 初回投入: 面ごとに長期トークンを手動で取得して Secret に入れる（PoC README の手順）。更新 API は発行から 24 時間以上経ったトークンしか受け付けないため、投入直後の手動実行は失敗する。初回の自動更新は翌週の月曜で、それまでに失効することはない。投入前（トークンが空）の週は、更新処理が「未投入のため更新しない」として正常終了する（アラームは鳴らない）
  • 失敗通知が来たとき（acps-prod-comment-reply-token-refresh-errors）: 更新 Lambda acps-prod-comment-reply-token-refresh のログで原因を見る。Graph API の一時障害なら Lambda を手動実行するか翌週を待つ（失敗した週は Secret が書き換わらず、旧トークンで返信は続く）。トークン失効・権限取り消しなら長期トークンを取り直して Secret に入れる。token_expires_at が 14 日以内に迫っていたら翌週を待たずに直す
  • 手動実行・確認（トークン値を出力しない形で実行する） 
    aws lambda invoke --region ap-northeast-1 \
  --function-name acps-prod-comment-reply-token-refresh-staging /dev/stdout
aws secretsmanager get-secret-value --region ap-northeast-1 \
  --secret-id acps/prod/umigame-soup-1/comment-reply-staging \
  --query SecretString --output text | python3 -c "import sys, json; print(json.load(sys.stdin)['token_expires_at'])"
    本番面は末尾の -staging を外す。応答の token_expires_at が実行時刻から約 60 日後になり、Secret の値と一致すれば成功

期限は debug_token の実測値（data_access_expires_at）で管理する → 理由 D-06

実際に効く期限はdata_access_expires_at（データアクセス期限。再認可から 90 日）で、これを過ぎると再認可までデータアクセスが失われる。
  • 無期限トークンが発行されるのはアプリが開発モードかつ当該ユーザーがアプリの管理者/開発者である現在の構成に依存する挙動。将来アプリを Live モードへ移行した場合は 60 日失効に戻る可能性があるため、移行時に本節を再確認する
  • 複数セットのトークンが同一アプリ・同一 Facebook ユーザーで発行されている場合、data_access_expires_at はセットごとではなくユーザー×アプリの組で 1 つ。いずれか 1 セットの再認可で全セット分が同時に延長される（15-7 の再認可で既存 fantasy-animals-1 の期限も 2026-10-25 へ延びたことを実測で確認）。したがってリマインダーはアカウントごとではなく 1 件に集約する
  • 期限の確認コマンド（トークン値を出力しない形で実行する） 
    aws secretsmanager get-secret-value --region ap-northeast-1 --secret-id <Secret 名> \
  --query SecretString --output text | python3 -c "
import sys, json, urllib.request, datetime
d = json.load(sys.stdin); t = d['access_token']
u = 'https://graph.facebook.com/v21.0/debug_token?input_token=%s&access_token=%s' % (t, t)
b = json.load(urllib.request.urlopen(u))['data']
f = lambda x: datetime.datetime.fromtimestamp(x, datetime.timezone.utc).isoformat() if x else 'never'
print('expires_at =', f(b.get('expires_at')), '| data_access =', f(b.get('data_access_expires_at')))"
  • token_expires_at（Secret 内の運用メモ）には data_access_expires_at の実測値を YYYY-MM-DDTHH:MM:SSZ で記録する

再認可スコープに instagram_manage_insights を含める（16-7） → 理由 D-07

インサイト収集バッチは既存の投稿用権限に加えて instagram_manage_insights スコープを必要とする（16-6 調査 (5)）。既存の長期トークンに新スコープは自動付与されないため、16-11（稼働確認）の冒頭で 5.1 手順 5 を instagram_manage_insights を含めて再実行し、新トークンで Secret を更新する。以後の定期更新（下記手順）でも同スコープを含めて再認可する。
2026-08-10 に実施済み。実施時の追加知見: Graph API Explorer の権限ドロップダウンに instagram_manage_insights が最初は出てこない。Explorer はアプリのユースケースに追加済みの権限しか列挙しないため、先にアプリダッシュボード →「ユースケース」→ Instagram ユースケースの「カスタマイズ」→ 権限一覧で instagram_manage_insights を追加する必要がある（PC ブラウザ推奨）。この際、Instagram の API セットアップ種別は「Facebook ログインを使用した Instagram API」のまま変更しない — 「Instagram ログインを使用した Instagram API」に切り替えるとスコープ体系（instagram_business_*）とエンドポイント（graph.instagram.com）が変わり、稼働中の投稿バッチ・インサイトバッチがいずれも動かなくなる。 この再認可により data_access_expires_at も延長されるため、実施後は下記リマインダーの日付を新期限の 7 日前へ更新する。自社管理アカウントのみの利用のため Standard Access の範囲でアプリレビューは不要の見込み。
  1. 上記の実測値（data_access_expires_at）の7 日前を目安に、Meta の長期トークン更新フロー（5.1 手順 5 の再実行。スコープに instagram_manage_insights を含める — 上記「再認可スコープ」）でトークンを再発行し、新しい期限を取得する
  2. 取得した新トークンで Secrets Manager の値を更新する（access_token と token_expires_at の両方を更新する） 
    aws secretsmanager put-secret-value \
  --secret-id acps/prod/fashion-set-1/sns/instagram/main-account \
  --secret-string '{"access_token":"(新トークン)","ig_user_id":"...","token_expires_at":"2026-11-04T00:00:00Z"}'
  3. 更新後、SNS 投稿ワークフローを手動実行するか次回の自動実行を待って、新トークンで認証が成功することを確認する

リマインドの運用（手動・全セットで 1 件） → 理由 D-08

token_expires_at は Secret 内の運用メモであり、アプリケーションはこの値を認証には使用しない（infra/security.html セクション 1.3）。管理画面（将来拡張）がない現時点では、Secrets Manager から失効日時を横断的に一覧する仕組みも持たない。 そのため初期運用では、期限の 7 日前を目安に運用者自身がカレンダー等の外部ツールにリマインダーを設定する運用とする。 2026-07-27 以降はリマインダーを 1 件に集約する（セットごとにアプリを分けた場合はアプリごとに 1 件）。
現在の登録内容: 2026-11-16（期限 2026-11-23 の 7 日前。fantasy-animals-1 / logic-training-1 / pref-ranking-1 の 3 セットをカバー。2026-08-26 の 17-5b（pref-ranking-1 のアカウント開設に伴う再認可）で data_access_expires_at が 2026-11-08T10:58:20Z → 2026-11-23T16:39:43Z へ延長されたことに伴う更新。既存セットのトークンを debug_token で実測して確認した〔expires_at は引き続き無期限〕）

6.2 収集失敗時の対応・欠測の考え方

  • 検知: 既存パターンと同じく Step Functions 失敗アラーム（ExecutionsFailed）+ ECS タスク異常終了通知。詳細な原因は CloudWatch Logs（どのメディア・どの日次で失敗したか WARNING/ERROR ログ）で確認する
  • 復旧は自動: 冪等性キー（batch-flow.html セクション 4.3）により、失敗ランの Retry・次回ランは欠測分だけを埋める。手動補正は原則不要
  • 欠測の考え方: feed_image / reel はウィンドウ内の次ランで最新累計値が取れるため実害は小さい（失敗ラン時点のスナップショット 1 点が欠けるのみ）。story は 24 時間期限があるため、期限内の 2 回（06:00・18:00 JST）が両方失敗するとそのストーリーズの計測値は永久欠測になる（許容する。分析時は期限内最後のスナップショットを最終値として扱う）。account_insights_daily は 90 日以内なら後追いで埋まる
  • 投稿の手動削除・アーカイブ: Instagram 上で投稿を削除した場合、以後の収集は「対象不存在」の WARNING スキップになる（失敗扱いにはならない。batch-flow.html セクション 4.3）。アーカイブも削除と同じ扱いになる — 16-11（2026-08-10）の実測で、アーカイブ済みメディアは Graph API から code 100 / subcode 33（オブジェクト不存在）で読めなくなることを確認した。プロフィール整理のつもりのアーカイブでインサイトが取れなくなるため、比較・検証に使いたい投稿はアーカイブしない。なお収集済みのスナップショットは post_insights に残るため、失われるのは以後の更新のみ（アーカイブ前に収集が回っていれば影響は小さい）
  • 閲覧者不足によるインサイト非開示（16-11 で判明）: 閲覧者が少ないメディアに対して Meta は全メトリクスを (#10) Not enough viewers for the media to show insights で拒否する（プライバシー閾値）。ストーリーズでは常態的に発生するため、InstagramInsightsUnavailable として対象不存在と同じ WARNING スキップに分類しており失敗にはならない（ログは Insights withheld below Instagram's viewer threshold）。リーチが伸びれば自然に取得できるようになるため、運用上の対応は不要。post_insights に行が入らないことが該当メディアの記録になる

D-03 ラウドネス正規化は 2 パス方式にする

D-05 コメント返信用トークンは Lambda で毎週自動更新する
