2. セット追加・廃止

2.1 セット追加手順

新しいセット（テーマ）を追加する手順を以下の順序で行う。順序を守る理由: Secret を先に作らないと DB に sns_accounts を登録しても投稿バッチが認証情報を取得できず即失敗するため（セクション 5.3 と同じ理由）。

手順 0: セット別設計書を作成する

docs/app/sets/<set_code>.html に、標準記載項目（テーマ、投稿先アカウント構成、スケジュール、プロンプト / キャプションの方式選択、失敗時ポリシー、共通フローからの差分）を記録する（ルールはアプリ設計大枠 セクション 1.1）。雛形は以下を複製して使う。

手順 1: Secrets Manager に SNS 認証 Secret を作成する

名前規約・値のスキーマは infra/security.html セクション 1.2〜1.3（構成要素の意味付けはセクション 5.2 で最終確認済み）。

aws secretsmanager create-secret \
  --name acps/prod/fashion-set-2/sns/instagram/main-account \
  --secret-string '{"access_token":"...","ig_user_id":"...","token_expires_at":"2026-09-05T00:00:00Z"}'

手順 2: DB にセットのレコードを登録する

Query Editor で以下の順に INSERT する（後続テーブルが set_id を参照するため、この順序を守る）。

DB 直接操作の共通注意（Phase 6 の実機確認より。本書のすべての SQL 操作に共通）
  • Query Editor の接続時は「データベースを変更する」で DB 名 acps を必ず指定する。未指定のまま実行すると No database selected (1046) で失敗する
  • Aurora が自動一時停止中に Query Editor / Data API を実行すると DatabaseResumingException が返る。アクセス自体が再開のトリガーになるため、数十秒待って再試行する
  • Query Editor の「最近」タブでは SQL 中の日本語が文字化けして表示されるが、表示上の問題のみで保存データは正しい（utf8mb4）
-- (1) batch_sets（generator_name は方式カタログ〔batch-flow.html セクション 2.1〕の方式名を設定する。
--     リール成功後にストーリーズへ再掲するセットは stories_enabled=1 を指定する〔省略時 0 = 無効。
--     batch-flow.html セクション 3.3〕）
INSERT INTO batch_sets (set_code, name, description, generator_name, stories_enabled, is_active)
VALUES ('fashion-set-2', 'ファッション系セット2', 'セット2の説明', '(方式名)', 0, 1);
-- 発行された id を以降の set_id として使う

-- (2) prompt_configs（初期運用は is_active=1 を 1 件のみ）
INSERT INTO prompt_configs (set_id, prompt_text, negative_prompt, parameters, is_active)
VALUES (:set_id, '(プロンプト本文。1 枚だけ生成されるよう文言で制御)', NULL, NULL, 1);

-- (3) caption_templates（0 件でも投稿は継続できるが、通常は 1 件登録する。
--     AI 開示ハッシュタグ #AIart を必ず含める〔セクション 3 の運用ルール〕）
INSERT INTO caption_templates (set_id, template_text, is_active)
VALUES (:set_id, '(キャプション本文 + ハッシュタグ。#AIart を含める)', 1);

-- (4) sns_accounts（手順 1 で作成した Secret の account_code と一致させる）
INSERT INTO sns_accounts (set_id, platform, account_code, account_name, is_active)
VALUES (:set_id, 'instagram', 'main-account', 'アカウント表示名', 1);

-- (5) audio_assets（動画方式のセットのみ。前処理済み音源を S3 に配置してから登録する。
--     調達・前処理・証跡の詳細はセクション 3。asset_type 省略時は DEFAULT 'bgm'。
--     gpt-quiz-multicut 方式の SE 2 種は asset_type='se' + 固定ファイル名で登録する〔セクション 3〕。
--     時間帯で BGM を出し分けるセットは time_slot に parameters.slots の slot_code
--     〔morning / noon / night 等〕を指定する〔省略時 NULL = スロット無関係。data-model.html セクション 4.8〕）
INSERT INTO audio_assets (set_id, s3_key, time_slot, title, source_url, license_type, license_note, acquired_at, duration_seconds, is_active)
VALUES (:set_id, 'audio/fashion-set-2/track01.m4a', NULL, '(曲名)', '(出典 URL)', 'CC0', NULL, '2026-07-24', 10, 1);

手順 3: CDK の ImageBatchStack に EventBridge Scheduler を追加して deploy する

入力に set_code を指定したスケジュールを、投稿時刻 1 つにつき 1 件追加する。Schedule 名は命名規約 acps-{env}-image-generation-{set_code}[-{slot_code}] に従う（スロット対応方式のセットはスロットごとに 1 件・slot_code をサフィックスに付ける）。 命名規約・cron 式・Scheduler 定義の書き方は infra/workflow.html セクション 1.5、実装は image-batch-stack.ts の imageGenerationSchedules 配列（ここに 1 エントリ追加するだけでよい）。 変更後のデプロイは cdk deploy -c env=prod --exclusively ImageBatchStack（イメージタグ 3 つの Context 指定が必須。指定ルール・現行タグの確認方法は infra/cicd.html セクション 3.2）。

スロット対応方式のセットは、スケジュール時刻がそのままスロットの指定になる parameters.slots を持つ方式（gpt-quiz-multicut 等）では、どのスロットとして生成するかを方式側が SCHEDULED_AT の JST 時から決定的に解決する（Scheduler の Input にスロットは持たせない）。 スケジュール時刻を from_jst_hour の境界をまたいで変更すると生成されるスロットが変わるため、時刻の変更時はセット別設計書のスロット表と必ず突き合わせること。
初セットは既存プレースホルダ Scheduler を転用した（Phase 10-1〜13-1 の経緯。現在は解消済み） ImageBatchStack には Phase 5 で作成したプレースホルダ Scheduler acps-prod-image-generation-schedule（機能名。State=DISABLED・プレースホルダ cron・入力 set_code=fashion-set-1）が存在し、初セット fantasy-animals-1 の追加ではこれを転用した（Phase 13-1・2026-07-22 に本番時刻で ENABLED 化 → 14-12 に 1 日 1 回へ変更）。 この機能名は 2 セット目の追加時（Phase 15-15・2026-07-29）に命名規約に沿って acps-prod-image-generation-fantasy-animals-1 へリネーム済みで、現在は全スケジュールが本手順どおりの命名になっている（転用は初セット限りの経緯として記録）。

手順 4: 動作確認

画像生成 Step Functions を手動実行し（infra/operation.html セクション 1.2 の「手動での画像生成実行」）、CloudWatch Logs で当該 set_code の生成・投稿が成功することを確認する。

セット追加チェックリスト
  • セット別設計書（docs/app/sets/<set_code>.html）を作成した
  • Secrets Manager に acps/{env}/{set_code}/sns/{platform}/{account_code} を作成した（DB 登録より先）
  • batch_sets → prompt_configs → caption_templates → sns_accounts（→ 動画方式のセットは audio_assets）の順に DB へ登録した
  • キャプションテンプレートに AI 開示ハッシュタグ #AIart を含めた（セクション 3）
  • 動画方式のセットは、前処理済み音源（3〜5 曲）を S3 の audio/{set_code}/ に配置し、証跡（出典 URL・ライセンス種別・取得日）込みで audio_assets に登録した（セクション 3）
  • gpt-quiz-multicut 方式のセットは、SE 2 種（カウントダウンティック・正解チャイム）を audio/{set_code}/se/ の固定ファイル名で配置し、asset_type='se' + 証跡込みで audio_assets に登録した（セクション 3）。固定アセット（キャラポーズ画像等）を assets/{set_code}/ に配置した（data-model.html セクション 5）
  • 時間帯で BGM を出し分けるセットは、parameters.slots の全 slot_code について time_slot 一致（または NULL）の有効 BGM が 1 曲以上あることを確認した（0 件のスロットがあると当該スロットの実行が異常終了する。セクション 3）
  • ストーリーズ再掲するセットは batch_sets.stories_enabled=1 を設定した（batch-flow.html セクション 3.3）
  • ImageBatchStack に Scheduler を追加して cdk deploy した（イメージタグ 3 つを Context 指定。infra/cicd.html セクション 3.2）
  • 手動実行で生成・投稿の成功を CloudWatch Logs で確認した
セット追加で CDK スタックは増えない スタック（FoundationStack / ImageBatchStack / SnsPostBatchStack / MonitoringStack）は機能単位であり、セット単位ではない。 セットを追加しても新しいスタックは作られず、増えるのは既存 ImageBatchStack 内の Scheduler 定義 1 件 + Secrets Manager の Secret + DB レコードのみ。 Step Functions・ECS タスク定義・コンテナイメージは全セット共有で、Scheduler が渡す set_code によってどのセットの処理を行うかが決まる。 したがって、インフラ設計書もセット追加では変更不要（2026-07-06 ユーザー質問を受けて明記）。

2.2 セット廃止・入れ替え（スクラップ&ビルド）

  1. batch_sets.is_active=0 に更新する（両バッチは is_active=0 のセットをスキップして正常終了する）。この時点でスケジュールが残っていても実害はないため、順序を厳密に守る必要はないが、次のステップより先に行うことを推奨する
  2. CDK から該当セットの Scheduler 定義を削除して deploy する（イメージタグ 3 つの Context 指定が必須。infra/cicd.html セクション 3.2）
  3. データ（DB レコード = メタ情報・投稿履歴）は削除せず残す。S3 実体（画像・動画ファイル）はインフラの 30 日ライフサイクルで自動削除される対象であり「残す」対象に含まない（Phase 9-3 で確定。データモデル設計 セクション 5）。音源ストック（audio/{set_code}/）はライフサイクル対象外のため自動削除されないが、廃止時もレコード・ファイルとも削除せず残す（容量は僅少で、セット復活・類似セットでの再利用可能性があるため。Phase 14-4 で確定）
  4. セット別設計書は削除せず、廃止の旨（バッジ・廃止日）を付けて履歴として残す

3. プロンプト・キャプション・音源管理

prompt_configs・caption_templates・audio_assets は DB 直接操作（Query Editor 等）で登録・変更する。管理画面は将来拡張。生成時にはプロンプトのスナップショットが generated_media に、キャプションのスナップショットが posts に記録されるため、変更しても過去の生成・投稿記録は影響を受けない。

軽微な文言修正（履歴を残さない場合）

既存の有効行を直接 UPDATE する。過去の生成実行への影響はスナップショットにより発生しない。

UPDATE prompt_configs SET prompt_text = '(新しいプロンプト本文)' WHERE id = :prompt_config_id;
UPDATE caption_templates SET template_text = '(新しいキャプション本文)' WHERE id = :caption_template_id;

差し替え（旧設定を無効化して残す場合）

新しいレコードを追加し、旧レコードを is_active=0 にする。prompt_configs は「is_active=1 が 0 件」だと画像生成バッチが異常終了する（batch-flow.html セクション 2）ため、必ず 1 トランザクションで実行し、0 件になる瞬間を作らない。

START TRANSACTION;
INSERT INTO prompt_configs (set_id, prompt_text, negative_prompt, parameters, is_active)
VALUES (:set_id, '(新しいプロンプト本文)', NULL, NULL, 1);
UPDATE prompt_configs SET is_active = 0 WHERE id = :old_prompt_config_id;
COMMIT;

caption_templates は is_active=1 が 0 件でも投稿処理は継続する（キャプションなしで投稿。data-model.html セクション 4.3）ため、トランザクションは必須ではないが同様の手順で問題ない。

セット別拡張ポイント（再掲） AI によるプロンプト生成・AI キャプション生成は将来のセット別拡張ポイント（バッチ処理フロー設計 セクション 2・3）。どのセットがどの方式かはセット別設計書に記録する。本セクションの手順は「固定文を DB で管理する」初期実装に対するものであり、AI 生成方式導入時は別途手順を定める。

AI 利用の開示（ハッシュタグ）の運用ルール

決定（2026-07-24、Phase 14-4）: AI 開示ハッシュタグは #AIart とする 事業戦略書の必須要件「AI 利用の開示」（14-2 壁打ち決定事項 #7: ハッシュタグ方式）の具体タグを #AIart に確定する。 AI 生成コンテンツの開示タグとして最も一般的で、海外リーチ前提のセット・国内向けセットのどちらでも通用するため 1 タグに絞る（タグ枠の節約）。
  • 全セットのキャプションテンプレート（caption_templates.template_text）に #AIart を必ず含める。テンプレートの新規登録・差し替え時のチェック項目とする（セクション 2.1 のチェックリスト・INSERT 例にも反映済み）
  • テンプレート経由で全投稿に確実に付与される（投稿処理側の実装は不要。キャプション 0 件時の投稿は従来どおり継続されるため、テンプレート登録漏れは週次のミュート確認〔セクション 4.4〕等の目視で拾う）
  • プラットフォームが公式の AI ラベル指定手段（API パラメータ）を提供した場合は、その時点で移行を検討する

音源の調達・前処理・登録（動画方式のセットのみ）

リール用 BGM は権利クリア済み音源をセットごとに 3〜5 曲、前処理済みの完成形で S3 にストックし、投稿ごとに順繰りローテーションする（data-model.html セクション 4.8）。前処理は事前手動（S3 登録前に 1 回だけ）で行い、バッチは合成時にそのまま多重化する（Phase 14-4 決定。バッチ内前処理を持たないことで動画方式の処理・失敗パターンを増やさない）。

手順 1: 調達（ライセンス確認と証跡の控え）

  • CC0・フリーライセンス音源（Pixabay License 等）を優先する。CC-BY はクレジット表記の運用が必要になるため避け、CC-BY-NC（非商用）は使用不可（収益化コンテンツのため。14-2 壁打ち記録 セクション 2.2）
  • ダウンロード時に証跡 3 点（出典 URL・ライセンス種別・取得日）を控える（手順 4 で audio_assets のカラムに記録する。別ドキュメントでの管理はしない）

手順 2: 前処理（ffmpeg。ローカルで 1 回だけ）

動画の尺は方式カタログ（batch-flow.html セクション 2.1）の該当方式に合わせる（gpt-image-kenburns = 10 秒、gpt-quiz-multicut = 20 秒。15-5 で尺可変に一般化）。尺に合わせて切り出し、音量正規化（ラウドネス）とフェードを掛け、AAC（.m4a）で書き出す。AAC に統一するのは、合成時に MP4 コンテナへ再エンコードなしで多重化できるため。

# 例: 原曲の 12 秒地点から 10 秒を切り出し、ラウドネス正規化 + フェードを掛けて AAC 化する
# （20 秒尺の方式では -t 20・afade=t=out:st=19 に読み替える。フェード長は尺によらず in 0.5 秒 / out 1 秒）
ffmpeg -ss 12 -i source.mp3 -t 10 \
  -af "loudnorm=I=-14:TP=-1.5:LRA=11,afade=t=in:st=0:d=0.5,afade=t=out:st=9:d=1" \
  -c:a aac -b:a 128k -ar 48000 -ac 2 track01.m4a
  • 切り出し位置（-ss）は曲のサビ・盛り上がりに合わせて試聴しながら決める。20 秒尺ではループ耐性（切り出し末尾から先頭に戻っても違和感がないか）も確認する
  • ラウドネス正規化は I=-14（ストリーミング標準の -14 LUFS）を目安とし、曲間の音量差をなくす
  • 書き出し後に必ず試聴確認する（頭切れ・フェードの不自然さ・ノイズ）
決定: ラウドネス正規化は 2 パス方式を用いる（Phase 14-6 の実作業で確定） 上記の 1 コマンド版（単一パス loudnorm）は動的正規化のため精度が粗く、14-6 で 4 曲を処理したところ実測 Integrated が -12.5〜-15.3 LUFS と約 2.8 dB ばらついた（曲間の音量差をなくすという目的に対して不十分）。 そこでパス 1 で対象 10 秒区間を解析（print_format=json）し、得た measured_* 値と linear=true を指定してパス 2 で線形適用する方式に変更した。同じ 4 曲でばらつきは 1.1 dB（-13.8〜-14.9 LUFS）に収まった。
  • 解析は切り出し後の 10 秒区間に対して行う（原曲全体ではない。実際に使う区間の音量に合わせるため）
  • フェードは正規化の後段に置く（フェード込みで解析すると測定値が下振れするため）。フェードアウトの分だけ最終実測値は目標 -14 をわずかに下回るが、全曲一律のため曲間差は生じない
  • 実装スクリプトは 14-6 で使用した 2 パス処理（process() 関数で 1 曲ずつ解析 → 適用）を踏襲する

手順 3: S3 への配置

aws s3 cp track01.m4a s3://acps-prod-images-{アカウントID}/audio/{set_code}/track01.m4a

audio/ プレフィックスは 30 日ライフサイクルの対象外（Phase 14-6 で images/・videos/ のプレフィックス限定へ変更済み。infra/stacks.html セクション 3.1）。時間帯で BGM を出し分けるセット（logic-training-1）は audio/{set_code}/{morning|noon|night}/track01.m4a のスロット別プレフィックスに置く（data-model.html セクション 5）。

手順 4: audio_assets への登録

セクション 2.1 手順 2 の (5) の INSERT を使う（証跡 3 点 + duration_seconds を必ず入れる）。時間帯で BGM を出し分けるセットは time_slot に S3 のスロットプレフィックスと同じ slot_code（morning / noon / night 等）を指定する（選曲のスロット判定はこのカラムで行い、S3 プレフィックスは配置規約に留める。data-model.html セクション 4.8）。

効果音（SE）の調達・登録（gpt-quiz-multicut 方式のセットのみ。Phase 15-5 新設）

クイズ方式はカウントダウンティック・正解チャイムの SE 2 種（15-4 ユーザー決定）を使う。SE は BGM ローテーション外・カットタイミング固定の固定アセットだが、証跡一元管理の原則を保つため audio_assets に asset_type='se' で登録する（data-model.html セクション 4.8）。

  • 調達: BGM と同じ基準（CC0 / Pixabay License 等。手順 1 の証跡 3 点を控える）
  • 前処理: ラウドネス正規化（2 パス loudnorm）は掛けない（短尺 SE には不適切）。ピークを -1.5 dBTP 目安に整え、AAC（.m4a）化のみ行う。ティックは 1 秒間隔 × 5 打の 5 秒連続ファイル、チャイムは 1〜2 秒に整える（配置タイミング・音量バランスの設計は方式側。15-6 実装）
  • 配置と登録: S3 キーは固定ファイル名規約 audio/{set_code}/se/countdown_tick.m4a / audio/{set_code}/se/answer_chime.m4a。audio_assets へ asset_type='se' で INSERT する（セクション 2.1 手順 2 の (5) と同型 + asset_type 指定）。方式は起動時にこの 2 キーの有効レコード存在を検査し、欠品は設定ミスとして異常終了する
  • 差し替え: BGM と同様に is_active=0 + 代替の登録で行う（固定ファイル名のため S3 オブジェクトの置き換えでもよいが、証跡を更新するため原則レコードを追加し旧レコードを無効化する）

ローテーションと曲の入れ替え

  • 選曲は順繰り（asset_type='bgm' のうち last_used_at が最古の有効レコード。未使用曲が最優先。SE は対象外）。曲の追加はいつでも INSERT のみでよい（追加曲は未使用のため次回に使われる）
  • 曲を外す場合は is_active=0 に更新する（レコードは削除しない。証跡・使用履歴を残す）
  • 動画方式のセットで有効音源が 0 件になると画像生成バッチが異常終了する（設定ミス扱い。data-model.html セクション 4.8）。prompt_configs の差し替えと同様、無効化する場合は先に代替曲を登録してから行い、0 件になる瞬間を作らない
  • 時間帯スロット対応のセット（gpt-quiz-multicut）の 0 件判定はスロットごと: あるスロットで「time_slot 一致 + NULL（共通曲）」の有効 BGM が 0 件になると、当該スロットの実行だけが異常終了する（他スロットは動き続けるため気づきにくい）。スロット別曲の差し替え時も「先に代替を登録してから無効化」を守り、スロット単位で 0 件の瞬間を作らない（15-10。順繰り〔last_used_at 最古〕はスロット絞り込み内で維持される）

4. 投稿失敗時の対応

初期実装は自動再試行なし・通知のみ（欠番許容）。1 日複数回投稿するため、1 回の欠番は致命的でないという判断（A-1 壁打ち記録 セクション 4）。

4.1 確認手順

  1. 失敗時はメール通知（MonitoringStack のアラーム / EventBridge Rule。仕組みは infra/workflow.html セクション 7〜10）を受ける
  2. Step Functions 実行履歴・CloudWatch Logs で、どのステートで・どのアカウントで失敗したかを確認する
  3. posts テーブルで失敗の詳細（status / error_message / api_response）を確認する: 
    SELECT p.id, p.media_type, p.status, p.error_message, p.api_response, p.updated_at,
       sa.account_code, gr.scheduled_at
FROM posts p
JOIN sns_accounts sa ON sa.id = p.sns_account_id
JOIN generation_runs gr ON gr.id = p.generation_run_id
JOIN batch_sets bs ON bs.id = gr.set_id
WHERE bs.set_code = 'fashion-set-1'
ORDER BY p.updated_at DESC
LIMIT 20;
  4. 必要な場合のみ、SNS 投稿ワークフロー（sns-posting-sfn）を手動で単独起動する（infra/operation.html セクション 1.2）。再実行は必ず Step Functions 経由で行い、ECS RunTask の直接実行は使わない（バッチは DB 接続リトライを持たず、Aurora 自動一時停止中の直接起動は失敗するため。batch-flow.html セクション 1 の前提）。投稿対象の決定ロジックは自動実行と同じため、その時点で最古の actionable な生成実行（data-model.html セクション 4.4）が処理される。一度試行して失敗した分は自動では再対象にならない（意図的に再対象にしたい場合は 4.2 を参照）

4.2 手動補正手順

DB を手動補正する前に、対象の set_code・post_id・現在の値を development-plan.md の「トラブルシューティングログ」に記録してから更新する。

published_unconfirmed を投稿済みに補正する

Instagram 側で投稿済みを確認できた場合のみ実行する。

UPDATE posts
SET status = 'success',
    platform_post_id = '(確認できた Instagram media ID)',
    posted_at = '(確認できた投稿日時 UTC)',
    error_message = NULL
WHERE id = :post_id
  AND status = 'published_unconfirmed';

failed / published_unconfirmed を未投稿として再試行可能にする

Instagram 側で未投稿を確認し、原因を解消した上で実行する。posts は UNIQUE (generation_run_id, sns_account_id, media_type) のため新規行は作れず、既存行を pending に戻して「最初から実行」扱いにする（batch-flow.html セクション 3.2 の復旧ロジック）。Instagram のメディアコンテナは時間経過で無効になり得るため、platform_container_id を含めてクリアし常にコンテナ作成からやり直す。

注意: ストーリーズ行（media_type='story'）にはこの補正は効かない 投稿対象の決定はリール行の終端状態で決まるため（data-model.html セクション 4.4）、ストーリーズ行を pending に戻しても後続実行では再選択・再処理されない。 ストーリーズは 24 時間で消える再掲コンテンツであり遅延再投稿の価値が低いため、失敗したストーリーズ行は failed のまま欠番として許容する（15-10。リール本体の投稿は成立している）。どうしても再掲したい場合のみ、Graph API を手動で呼び出す（バッチの再実行では行わない）。 
UPDATE posts
SET status = 'pending',
    platform_container_id = NULL,
    platform_post_id = NULL,
    caption_template_id = NULL,
    caption_text_snapshot = NULL,
    error_message = NULL,
    api_response = NULL
WHERE id = :post_id
  AND status IN ('failed', 'published_unconfirmed');
注意: 補正しても即座には処理されない場合がある SNS 投稿バッチは常にその時点で最古の actionable な生成実行 1 件のみを処理する（batch-flow.html セクション 3.1）。補正対象より古い actionable な生成実行が他に残っている場合、次回実行（自動 / 手動を問わず）はそちらが先に処理される。補正対象を優先させたい場合は、以下のクエリ（data-model.html セクション 4.4のクエリを転用）で、補正対象の generation_run_id がその時点で最古の actionable であることを確認してから手動実行する。 
SELECT gr.id
FROM generation_runs gr
WHERE gr.set_id = :set_id
  AND EXISTS (
    SELECT 1 FROM sns_accounts sa
    WHERE sa.set_id = gr.set_id AND sa.is_active = 1
      AND NOT EXISTS (
        SELECT 1 FROM posts p
        WHERE p.generation_run_id = gr.id
          AND p.sns_account_id = sa.id
          AND p.status IN ('success','failed','published_unconfirmed')
      )
  )
ORDER BY gr.scheduled_at ASC, gr.id ASC
LIMIT 1;
古い actionable な生成実行が他にもある場合は、4.3 の stale データの扱いを先に検討する。

4.3 stale データ（未完了のまま残った生成実行）の扱い

data-model.html セクション 4.4 で確認したとおり、pending / container_created のまま終端状態に達しない posts 行が残ると、その生成実行は後続の実行でも自動的に再選択され続ける。これは主に、ECS タスクの異常終了（OOM Kill・Fargate 基盤障害等）でアプリケーションが例外を捕捉して failed に更新する前に強制終了した場合に起こる。投稿対象決定は「最古の actionable」を選ぶ方式のため、この状態の生成実行が残り続けると同一セットの後続投稿がブロックされる点が運用上の注意点である。

決定: 自動検知の仕組みは追加しない（既存アラーム 1 本に一本化する方針を維持） stale 専用の CloudWatch アラームやカスタムメトリクスは追加しない（batch-flow.html セクション 3.4 の「通知は既存の Step Functions 失敗アラーム 1 本に一本化」という決定と整合させる）。運用者は既存の失敗通知を起点に、以下のクエリで stale な行の有無を確認する運用とする。 
-- 各セットの actionable な (generation_run, account) を一覧表示（古い順）
SELECT bs.set_code, gr.id AS generation_run_id, gr.scheduled_at,
       sa.account_code, p.media_type, p.status, p.updated_at
FROM generation_runs gr
JOIN batch_sets bs ON bs.id = gr.set_id
JOIN sns_accounts sa ON sa.set_id = gr.set_id AND sa.is_active = 1
LEFT JOIN posts p ON p.generation_run_id = gr.id AND p.sns_account_id = sa.id
WHERE bs.is_active = 1
  AND (p.id IS NULL OR p.status NOT IN ('success', 'failed', 'published_unconfirmed'))
ORDER BY gr.scheduled_at ASC;
  • 判定の目安: 1 日複数回実行する運用のため、status が pending / container_created のまま updated_at から半日以上経過している行は stale の疑いが強い（対応する Step Functions 実行がすでに終了しているにもかかわらず DB が更新されていない状態）。行が存在しない（p.id IS NULL）だけの場合は、直近の生成実行がまだ処理待ちなだけの通常状態であり stale ではない
  • ストーリーズ行（media_type='story'。V004）の stale は後続投稿をブロックしない: 投稿対象の決定はリール行の終端状態で決まるため（data-model.html セクション 4.4）、ストーリーズ行が途中状態のまま残っても次の生成実行の投稿は進む。補正は同じく 4.2 の手順で終端状態（実際の投稿有無に応じて success / failed）へ更新して記録を確定させるのみでよい（pending へ戻す補正は効かない — 4.2 の注意を参照）
  • 対応: 対象の Step Functions 実行履歴・CloudWatch Logs で実際の投稿有無を確認し、4.2 の手順で success（実際は投稿済みだった場合）または failed（実際は未投稿だった場合）の終端状態に補正する。終端状態に補正することで、後続の投稿対象決定が次の生成実行へ進めるようになる
  • 将来的にセット別失敗時ポリシー（追いつく / 捨てる。batch-flow.html）を導入する際は、stale データの扱いも合わせて再設計する

4.4 リール音源のミュート検知（著作権誤検知）の週次確認

権利クリア済みのフリー音源でも、プラットフォームの著作権検知（Content ID 型の照合）が誤検知して公開後に自動ミュートする可能性がある（14-2 壁打ち記録 セクション 7）。ミュートは投稿失敗ではないため既存のアラームでは検知できず、当面は手動確認の運用とする（Phase 14-4 決定。stale データ確認〔4.3〕と同様、専用の自動検知は追加しない方針と整合）。

  1. 週 1 回、Instagram アプリで直近 1 週間のリール投稿（1 日 1 本運用で 7 件目安）を再生し、音が出ること・ミュート警告が表示されていないことを確認する
  2. ミュート・警告を検知した場合:
    1. 該当投稿に使われた音源を特定する: 
      SELECT aa.id, aa.title, aa.s3_key, aa.source_url
FROM posts p
JOIN post_media pm ON pm.post_id = p.id
JOIN generated_media gm ON gm.id = pm.generated_media_id
JOIN audio_assets aa ON aa.id = gm.audio_asset_id
WHERE p.platform_post_id = '(Instagram media ID)';
    2. 先に代替曲を登録してから、該当 audio_assets を is_active=0 に更新する（0 件になる瞬間を作らない。セクション 3）
    3. 投稿自体は削除しない（表示・再生数・フォロワー接点は残す。ミュートのままでも Ken Burns の映像は成立する）
    4. development-plan.md の「トラブルシューティングログ」に、対象投稿・曲・検知日を記録する（同一曲の再発防止）

5. Secret 運用（SNS 認証・画像生成 API キー）・トークン更新

5.1 Instagram アカウント準備（プロアカウント化 〜 長期アクセストークン取得）

新しいセットで Instagram 投稿を行う場合、Secret 作成（2.1 手順 1・5.3 手順 1）の前提として毎回必要になる外部準備。Meta 側の UI・仕様は変更されうるため、詰まった場合は Meta 公式ドキュメント（Instagram Platform documentation）を最新の一次情報として確認する。12-1（fantasy-animals-1・main-account）で実際に踏んだ手順を元に記載し、15-7（logic-training-1・main-account）の 2 セット目で判明した論点を追記した。

手順 1: Instagram プロアカウント化

投稿に使う Instagram アカウントをプロアカウント（ビジネス or クリエイター）に変更する。個人アカウントのままでは投稿 API を利用できない。

2 セット目以降: アカウントセンターへの追加とクロスポストの確認（2026-07-27） 新規 Instagram アカウントの作成時に「このアカウントセンターで新しい Instagram アカウントを作成しますか？」と尋ねられる。既存アカウントセンターに追加してよい（アカウント切替が楽になり、後続手順の権限付与も同一 Facebook 個人アカウントで完結する。別アカウントセンターに分けても、どのみち同じ Facebook 個人アカウントからページを管理するため Meta 側では紐付き、分離の実効性は乏しい）。 ただし追加後はアカウントセンター →「コネクテッドエクスペリエンス」→「プロフィール間のシェア」がオフであることを確認する。オンだとセット間で投稿が相互転載され、セットごとの世界観が壊れる。
15-7 時点では、当該機能は Facebook 個人アカウントまたは Threads をアカウントセンターに追加しないと有効化されない仕様であり（Instagram プロフィール同士だけでは選択肢が出ない）、確認のみで対応不要だった。

手順 2: Facebook ページとの連携

Instagram Graph API（投稿権限を含むフル機能版）は Facebook ページ経由の権限フローが必要で、Instagram プロアカウント 1 件につき Facebook ページが 1 件必要。

2 セット目以降: 既存 Facebook ページは流用できない（2026-07-27） Facebook ページ 1 件にリンクできる Instagram プロフィールは 1 件のみで、逆も同様。既存セットのページに新しい Instagram アカウントをリンクしようとすると「Instagram プロフィールはすでにリンク済みです」で弾かれる。 セットを追加するたびに Facebook ページも新規作成する（ページ名は Instagram の表示名と揃えるとよい。カテゴリは API 動作に影響しない）。作成した新ページに切り替えてから、下記の連携手順を実行する。
連携の途中でビジネスポートフォリオの選択を求められた場合は、既存の命名に揃えて {set_code} 名のポートフォリオを新規作成する。制限で作成できない場合は既存ポートフォリオへ追加しても差し支えない（トークン取得は /me/accounts でページ一覧を引くため、ポートフォリオの分け方に依存しない）。
実施メモ（2026-07-19） Instagram アプリ側の連携メニューからはうまく連携できなかったため、Facebook ページ側から以下の手順で連携した。
  1. Facebook で対象ページに切り替える
  2. ページの「設定」を開く
  3. 「リンクするアカウント」を開く
  4. 「Instagram」を選択
  5. 「アカウントをリンク」を押す
  6. Instagram のユーザー名とパスワードでログイン
  7. 確認画面を進めて接続する

手順 3: Meta Developer アカウント + アプリ作成

developers.facebook.com で Meta Developer アカウントを作成（要 Facebook アカウント）→ 新規アプリ作成 → ユースケースは「Business」を選択する。App ID / App Secret が発行される（App Secret はトークン交換〔手順 5〕で使用する）。

決定: 2 セット目以降は既存 Meta アプリを流用する（2026-07-27・15-7 のユーザー決定） 1 つの Meta アプリで複数の Facebook ページ・複数の Instagram アカウントを扱えるため、セットごとに新規アプリを作らず既存アプリを流用する。本手順 3 をスキップでき、App ID / App Secret も再利用できる。手順 4 の Instagram テスター招待のみセットごとに実施する。 セットごとにアプリを分ければ障害・凍結の影響を切り離せるが、手順 3〜4 を一から実施する手間とレビュー基準の再確認が必要になるため、初期スコープでは流用を採る。

手順 4: アプリへの権限付与（App Review を回避する 2 つのロール）

本システムはユーザー自身のアカウントにのみ投稿するため、Meta のアプリレビューは不要（他者のアカウントに投稿する場合のみ必須）。代わりに以下 2 つのロールを設定する。

  1. アプリの管理者ロール: アプリの「アプリの役割」→「役割」で、Facebook アカウント（既存 ID の使い回しでよい）が「管理者」または「開発者」になっていることを確認する（アプリ作成者は通常自動で管理者になる）
  2. Instagram テスターロール（投稿権限に必須）: 同じ「アプリの役割」画面の「Instagram テスター」タブで「メンバーを追加」→ 投稿に使う Instagram プロアカウントのユーザー名を入力して招待する。 続けて Instagram 側（PC ブラウザ。スマホアプリには「テスターへのご招待」メニューがない）でログインし、「設定」パネル右上の検索ボックスに「テスター」と入力して「テスターへのご招待」を開き、招待を承認する（通知欄に届く場合もある）
2 つのロールの違い 「管理者」ロールはアプリ全体（Facebook 側）の管理権限であり、Instagram Graph API の権限付与とは別軸。投稿権限のトークンを発行するには、Instagram テスターロールの承認が別途必須（管理者ロールだけでは不足する）。

手順 5: 権限付与とトークン取得

  1. 短期アクセストークンの取得: Graph API Explorer を開く → 右上の「Meta App」で対象アプリを選択 → 「User or Page」→「Get User Access Token」→ 権限（instagram_basic / instagram_content_publish / pages_show_list / pages_read_engagement / business_management）を選択 → 「Generate Access Token」→ Facebook ログインのポップアップで許可する。「Access Token」欄の文字列が短期トークン（有効期限 1 時間）
    既存アプリ流用時、権限付与ポップアップでのページ選択に注意（2026-07-27） 再認可のポップアップでは管理対象ページのチェックリストが出る。今回追加するページにチェックを入れる（漏れると次の /me/accounts に新ページが出てこない）と同時に、運用中の既存セットのページのチェックを外さない。外すとそのページへのアクセスが取り消され、稼働中セットの投稿が停止する。 なお新しいトークンを発行しても既存の長期トークン文字列自体は失効しないため、既存セットの Secret を更新する必要はない。
  2. 長期アクセストークンへの交換: ブラウザで以下の URL を値を埋めて開く（GET リクエストのため URL を開くだけでよい） 
    https://graph.facebook.com/v21.0/oauth/access_token?grant_type=fb_exchange_token&client_id=<APP_ID>&client_secret=<APP_SECRET>&fb_exchange_token=<SHORT_LIVED_TOKEN>
    APP_ID / APP_SECRET はアプリの「アプリの設定」→「基本設定」で確認できる。レスポンスの access_token が長期トークン。token_expires_at に控える値は expires_in ではなく debug_token の実測値を使う（算出方法は 5.4）
  3. ig_user_id の取得: 2 段階で引く。まず管理対象の Facebook ページ一覧から対象ページの id（= PAGE_ID）を確認する 
    https://graph.facebook.com/v21.0/me/accounts?access_token=<LONG_LIVED_TOKEN>
    次にその PAGE_ID で Instagram 側の ID を引く 
    https://graph.facebook.com/v21.0/<PAGE_ID>?fields=instagram_business_account&access_token=<LONG_LIVED_TOKEN>
    返り値の instagram_business_account.id が ig_user_id（17841 で始まる 17 桁前後の数字）。 /me/accounts が返すのは Facebook ページ ID であり ig_user_id ではない点に注意する（15-7 で取り違えが発生した）。 ページ「基本データ」画面の URL に出る数字を PAGE_ID として使うと失敗する場合がある（Business Suite 上の別 ID を指している可能性があるため）ので、必ず /me/accounts の値を使う。
    instagram_business_account フィールド自体が返らない場合は、ページと Instagram の連携が未完了か instagram_basic 権限が付いていない
実値をこの手順の外に出さない App Secret・アクセストークン・ig_user_id はすべてブラウザ操作で完結させ、会話ログ・コマンド履歴・チャットには残さない。取得した 3 値（access_token / ig_user_id / token_expires_at）はメモに控え、Secret 作成（2.1 手順 1・5.3 手順 1）ではマネジメントコンソールから直接入力する（5.5 の画像生成 API キーと同じ理由。実 API キー・トークンはコンソール手動設定とし CLI・会話に残さない方針）。

手順 6: Secret を作成する（コンソールで入力できない場合の CloudShell 方式）

通常はマネジメントコンソールの Secrets Manager 画面から直接入力する（2.1 手順 1）。スマホの AWS コンソールアプリなどシークレット値の入力欄に貼り付けができない環境では、CloudShell から以下の 2 段階で作成する（15-7 で実施）。トークンをコマンドライン・シェル履歴に残さないことが要件。

  1. トークンを環境変数へ読み込む。この 1 行だけを単独で貼り付けて実行する（複数行をまとめて貼ると続きの行が read の入力として消費されてしまう）。実行後の入力待ちでトークンを貼り付ける（画面には表示されない） 
    umask 077; read -rsp "token: " TOKEN; echo; echo "len=${#TOKEN}"
    表示される len で貼り付け欠けを検知する（長期ユーザートークンは EAA 始まりの 190〜200 文字程度）
  2. 一時ファイル経由で Secret を作成する。このコマンド自体にトークンは含まれないため履歴に残ってよい 
    printf '{"access_token":"%s","ig_user_id":"<IG_USER_ID>","token_expires_at":"<EXPIRES_AT>"}' "$TOKEN" > ~/sec.json \
  && aws secretsmanager create-secret --region ap-northeast-1 \
       --name acps/prod/<set_code>/sns/instagram/<account_code> \
       --secret-string file://$HOME/sec.json; rm -f ~/sec.json; unset TOKEN
    CloudShell の $HOME は永続化されるため、一時ファイルは umask 077 で作成し実行後に必ず削除する

作り直す場合は aws secretsmanager delete-secret --region ap-northeast-1 --secret-id <名前> --force-delete-without-recovery で即時削除してからやり直す。

5.2 Secret 名規約の最終確認

Secret 名規約 acps/{env}/{set_code}/sns/{platform}/{account_code}（infra/security.html セクション 1.2）と、構成要素の意味付け（set_code = batch_sets.set_code、account_code = sns_accounts.account_code）はアプリ設計大枠 セクション 5で確定済みであり、本規約に変更はない。account_code は Secret 名導出専用のため作成後変更不可。変更が必要な場合は新アカウント（新しい account_code）として追加し、旧アカウントは is_active=0 にする。

Phase 10-1 での再確認（2026-07-15 実施済み） 本規約は Phase 0〜8（インフラ構築）を経ずに Phase 9 として前倒しで確定したものであるため、Phase 10-1（アプリ設計の最終 Fix）でインフラ実態と突き合わせて再確認した。 IAM ポリシー（プレフィックスベースの Secret 読み取り権限。infra/security.html セクション 2.1）・Secret 運用の実態と矛盾はなく、規約は変更なしで最終確認とする。

5.3 既存セットへの SNS アカウント追加手順

新規セット追加（セクション 2.1）とは異なり、既存セットに投稿先アカウントを追加する場合（将来の多プラットフォーム展開等）の手順。

  1. Secrets Manager にシークレットを作成する（DB 登録より先に行う）。値のスキーマは infra/security.html セクション 1.3 を参照 
    aws secretsmanager create-secret \
  --name acps/prod/fashion-set-1/sns/instagram/sub-account \
  --secret-string '{"access_token":"...","ig_user_id":"...","token_expires_at":"2026-09-05T00:00:00Z"}'
  2. sns_accounts にレコードを追加する。account_code はシークレット名と一致させ、作成後は変更しない 
    INSERT INTO sns_accounts (set_id, platform, account_code, account_name, is_active)
VALUES (:set_id, 'instagram', 'sub-account', 'サブアカウント表示名', 1);
  3. 動作確認: SNS 投稿ワークフローを手動実行し、追加したアカウントへの投稿（またはシークレット取得）が成功することを確認する

5.4 Instagram アクセストークン更新の具体手順とリマインド運用

決定: 期限は「60 日」ではなく debug_token の実測値で管理する（2026-07-27・15-7 の実測に基づく改訂） 15-7 で 2 アカウント分のトークンを debug_token で確認したところ、いずれも expires_at = 0（無期限）であり、当初記載の「60 日で失効」は現構成では発生していなかった。実際に効く期限はdata_access_expires_at（データアクセス期限。再認可から 90 日）で、これを過ぎると再認可までデータアクセスが失われる。
  • 無期限トークンが発行されるのはアプリが開発モードかつ当該ユーザーがアプリの管理者/開発者である現在の構成に依存する挙動。将来アプリを Live モードへ移行した場合は 60 日失効に戻る可能性があるため、移行時に本節を再確認する
  • 複数セットのトークンが同一アプリ・同一 Facebook ユーザーで発行されている場合、data_access_expires_at はセットごとではなくユーザー×アプリの組で 1 つ。いずれか 1 セットの再認可で全セット分が同時に延長される（15-7 の再認可で既存 fantasy-animals-1 の期限も 2026-10-25 へ延びたことを実測で確認）。したがってリマインダーはアカウントごとではなく 1 件に集約する
  • 期限の確認コマンド（トークン値を出力しない形で実行する） 
    aws secretsmanager get-secret-value --region ap-northeast-1 --secret-id <Secret 名> \
  --query SecretString --output text | python3 -c "
import sys, json, urllib.request, datetime
d = json.load(sys.stdin); t = d['access_token']
u = 'https://graph.facebook.com/v21.0/debug_token?input_token=%s&access_token=%s' % (t, t)
b = json.load(urllib.request.urlopen(u))['data']
f = lambda x: datetime.datetime.fromtimestamp(x, datetime.timezone.utc).isoformat() if x else 'never'
print('expires_at =', f(b.get('expires_at')), '| data_access =', f(b.get('data_access_expires_at')))"
  • token_expires_at（Secret 内の運用メモ）には data_access_expires_at の実測値を YYYY-MM-DDTHH:MM:SSZ で記録する
  1. 上記の実測値（data_access_expires_at）の7 日前を目安に、Meta の長期トークン更新フロー（5.1 手順 5 の再実行）でトークンを再発行し、新しい期限を取得する
  2. 取得した新トークンで Secrets Manager の値を更新する（access_token と token_expires_at の両方を更新する） 
    aws secretsmanager put-secret-value \
  --secret-id acps/prod/fashion-set-1/sns/instagram/main-account \
  --secret-string '{"access_token":"(新トークン)","ig_user_id":"...","token_expires_at":"2026-11-04T00:00:00Z"}'
  3. 更新後、SNS 投稿ワークフローを手動実行するか次回の自動実行を待って、新トークンで認証が成功することを確認する
決定: リマインドは手動管理・全セットで 1 件に集約する（自動リマインドは導入しない） token_expires_at は Secret 内の運用メモであり、アプリケーションはこの値を認証には使用しない（infra/security.html セクション 1.3）。管理画面（将来拡張）がない現時点では、Secrets Manager から失効日時を横断的に一覧する仕組みも持たない。 そのため初期運用では、期限の 7 日前を目安に運用者自身がカレンダー等の外部ツールにリマインダーを設定する運用とする（セット数が少ない初期スコープでは許容範囲と判断）。 当初は「アカウントごとに登録」としていたが、上記のとおり data_access_expires_at がユーザー×アプリの組で共通であり 1 回の再認可で全セットが延長されるため、2026-07-27 以降はリマインダーを 1 件に集約する（セットごとにアプリを分けた場合はアプリごとに 1 件）。
現在の登録内容: 2026-10-18（期限 2026-10-25 の 7 日前。fantasy-animals-1 / logic-training-1 の両方をカバー）
セット数が増えて手運用が破綻する場合は、Secrets Manager を横断的に読み取り token_expires_at が近いものを通知する仕組み（Lambda + EventBridge 等）の導入を将来検討する（設計課題リストに記録）。
15-16（2026-07-29）の要否判断で本方針を確定: 自動化は導入しない。リマインダーがセット数に比例しない構造（Meta アプリ 1 つにつき 1 件）になったため、2026-07-07 の設計課題「セット数増で手運用が破綻」の前提が崩れた。再検討トリガーは ①Meta アプリを複数に分けた場合 ②Live モード移行で 60 日失効に戻った場合 ③管理画面（将来拡張）の導入時、の 3 点。

5.5 画像生成 API キーの設定（Phase 10 開始時に必須）

画像生成 API キー用 Secret acps/prod/image/api-key は、インフラ構築（Phase 5-3）で「箱」のみ作成済みで、値はランダムなプレースホルダのままである（infra/stacks.html セクション 3.1 の decision）。アプリ実装（Phase 10）で画像生成 API を呼び出す前に、実際の API キーへ差し替える。

  1. マネジメントコンソールの Secrets Manager で acps/prod/image/api-key を開き、「シークレットの値を取得」→「編集」で api_key キーの値を、利用する画像生成 API（初期方式が使う API。方式カタログは batch-flow.html セクション 2.1）の API キーに差し替える。値スキーマ {"api_key": "..."} は infra/security.html セクション 1.3 を参照
  2. 差し替え後、画像生成ワークフローの実行で認証が成功することを確認する
注意: スタック再作成で値が失われる この Secret の RemovalPolicy は Delete のため、FoundationStack を destroy → 再作成すると手動設定した API キー値は失われる。再作成後はコンソールから再設定が必要（infra/stacks.html セクション 3.1）。

6. Phase 9-4 の決定事項まとめ

  • セット追加手順を 5 ステップ（設計書雛形 → Secret 作成 → DB 登録（batch_sets → prompt_configs → caption_templates → sns_accounts の順）→ Scheduler 追加 deploy → 動作確認）に具体化し、チェックリスト化した（2.1）
  • プロンプト・キャプションの変更は「直接 UPDATE（履歴を残さない）」と「新規 INSERT + 旧行 is_active=0（履歴を残す）」の 2 方式を定義し、prompt_configs は 0 件化を避けるためトランザクションで実行することを確定した（3）
  • 投稿失敗時の手動補正は、旧設計の attempt_number ベースの再試行を採用せず、posts 行を pending に戻して「最初から実行」扱いにする方式で再投稿可能にすると確定した。あわせて、補正しても投稿対象決定が「最古の actionable」を優先するため即座に処理されるとは限らない点を明記した（4.2）
  • stale データ（pending / container_created のまま残った生成実行が後続投稿をブロックする問題）について、専用の自動検知は追加せず、既存の失敗アラームを起点に定期確認クエリで検出し 4.2 の手順で終端状態に補正する運用と確定した（4.3）
  • SNS Secret 規約 acps/{env}/{set_code}/sns/{platform}/{account_code} は変更なしで最終確認とし、既存セットへのアカウント追加手順（Secret 作成 → DB 登録の順）を新規セット追加手順と分けて明文化した（5.2〜5.3）
  • Instagram トークン更新のリマインドは、管理画面がない初期スコープでは運用者による手動リマインダー設定とし、自動化は将来課題として設計課題リストに記録した（5.4）
