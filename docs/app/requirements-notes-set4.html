② リール版面・尺・ナレーション・BGM・イラスト（叩き台）

ユーザーの要望: 構成は logic-training-1 に寄せる。フック・問題文・遊び方のルールはずっと表示し、下部でキャラクターとコメント（吹き出し）が時間経過で切り替わる。ナレーションは問題文とルールの読み上げのみで吹き出しと同期しない。イラストは背景に使う。

decision: 版面の叩き台（2026-09-03 ユーザー決定。21-2 の PoC で修正する前提）
  • 尺 = 20 秒（600 フレーム・30fps）・1 尺のみ・ループ前提（末尾と先頭の状態を一致させる。周期アニメーションの周期は総フレームの約数。logic-training-1 の timeline.ts の不変条件を踏襲）
  • ずっと表示する要素（フレーム 0 から末尾まで不変）: つかみ帯（フック文）/ 見出し「問題」+ 問題文の全文（段階表示はしない。R-1-3 の教訓）/ 問題文直下のルール帯「『はい / いいえ / 関係ない』で答えられる質問をコメントしてね。出題者が全部返事します」（logic-training-1 の時間帯ピルに相当する固定要素）
  • 背景 = 問題の情景イラスト 1 枚を全面に敷き、暗いオーバーレイの上にカードを乗せる（logic-training-1 はカード内にイラスト矩形を置くが、本セットは下部ゾーンを吹き出しに使い切るため背景へ回す）
  • 時間で切り替わる要素（下部ゾーン。右 12% は Instagram UI に空ける）: 出題者キャラを下部左に常駐（logic-training-1 のコーチの位置）。質問者キャラが吹き出しで質問例を出し、出題者が「はい。」「いいえ。」「関係ありません。」と短く返す。切り替えはクロスフェードせずスナップ（二重露光に見える実測は R-1 で確認済み）。吹き出し出現の SE は 1 種のみ
  • ビート案: 導入 3 秒（出題者「質問してみて！」）→ 3 往復 × 4 秒（質問 2 秒 → 返答 2 秒）→ 締め 5 秒（出題者「正解が出るまで何度でも答えるよ。コメントで質問！」）→ 末尾 0.4 秒で導入の状態へ戻す
  • キャラ構成 = 出題者 1 体 + 質問者 1 体（いずれも imagegen の静的アセット、表情差分は各 1〜2。pref-ranking-1 の五郎と同じ固定アセット方式）。質問者を 1 体に絞るのは将来「助手」サブアカウントとして独立させる可能性があり、管理しやすくするため（ユーザー判断。Claude の当初案は質問者 3 体）
  • キャラ設定（仮）: 出題者 = 探偵風のウミガメ（アカウントの顔。真相を握る側）、質問者 = 助手（プレイヤー側の代表。助手サブアカウント構想と名前を揃える）。名前・ビジュアルの細部・画風は 21-2 の試し生成で決める
  • ナレーション = あり。VOICEVOX で冒頭に問題文とルール帯を 1 回だけ読む（吹き出しと同期させない）。問題文 60〜80 字 + ルール 30 字で 12〜14 秒程度の見込み。pref-ranking-1 の TTS アダプタと実測長の予算検査を流用し、超過はビルドエラー。話者は 21-2 で試聴して決める
  • BGM = 既存 CC0 プール（audio_assets）から LRU 選曲（quiz-prebuilt / ranking-prebuilt と同じビルド時の移管）
  • イラスト = 1 問 1 枚 imagegen。画風は暗めの単色トーンにシルエット寄りのフラットイラスト。真相の手がかりを描かない指示を固定にする（問題文の情景のみ）。文字は入れない

③ 生成方式と Remotion Skills の導入先

decision（2026-09-03。方式名はユーザー決定、導入先は Claude に一任）
  • 方式名 = umigame-prebuilt（「コンテンツ種別 + prebuilt」の命名慣例。Remotion ローカル事前ビルド = ranking-prebuilt 同型・定常費ゼロ路線）
  • Remotion Skills は skills CLI でリポジトリルートに導入する: npx skills add remotion-dev/skills -a claude-code -a codex -y。導入対象は best-practices / create / markup / render / docs / upgrade の 6 本（maps・captions・saas・interactivity・multimedia は本セットで使わないため入れない）
  • 配置の前提: skills CLI は正本を .agents/skills/<skill>/ に置き、.claude/skills/<skill> にスキル単位のシンボリックリンクを張る。ディレクトリ丸ごとのリンクではないため、自前スキルの実ディレクトリ .claude/skills/ と共存できる（= 計画書 21-1 ③ の候補①が CLI の既定動作そのもの）。21-2 の導入時に実測し、スキル単位リンクにならなければ手動でスキル単位リンクに切り替える
  • コミット対象 = 正本（.agents/skills/remotion-*）+ リンク（.claude/skills/remotion-*）+ CLI のロックファイル。更新は npx skills update（導入した版は 21-2 の README に記録）
  • レンダリング経路は既存どおり build.py からの Docker 委譲（npx remotion render）を維持する

⑤ AI 出題者のモデルと月額試算・利用上限

decision（2026-09-03 ユーザー決定）
  • モデル = gpt-5.6-luna（PoC の gpt-4o-mini から変更）。API 上のモデル ID と単価は 21-6 の実装時にダッシュボードで確認する（本書には単価を書かない）。PoC のプロンプトは gpt-4o-mini で検証したものなので、21-4b のプローブテストは luna で行う
  • 試算の枠組み: 返信 1 件 = 入力 600 トークン前後（問題文・真相・確定事実シート・ルール・質問）+ 出力 30 トークン程度。月 6,000 件で入力 3.6M・出力 0.2M トークン。事業戦略書 3.1 の費目「コメント自動返信の LLM API（従量のみ・月数百円規模）」の範囲に収まる見込み。単価確認後に外れていれば 21-6 で戦略書を直す
  • 利用上限は 2 段: OpenAI 側のプロジェクト月額予算上限 + Reply Lambda の予約同時実行数（SQS が吸収するため取りこぼしにはならない）。モデルはプローブテスト後、本番稼働まで固定

⑥ コメント経路の構成とコード置き場・デプロイ方式

decision（2026-09-03 ユーザー決定）
  • 経路 = Lambda Function URL（署名検証のみ）→ Webhook Lambda → SQS + DLQ → Reply Lambda。API Gateway は採らない（WAF・スロットリングが要るまで不要。Function URL は無料）
  • コード置き場 = services/comment-reply/（pytest 付き。PoC ハンドラを Webhook / Reply に分割して移植）
  • デプロイ = CDK asset（外部依存ゼロの Python のままバンドル不要。コンテナではないため CodePipeline は通さず、手動 cdk deploy の既存ルールに乗せる）

⑦ Meta アプリの使い分けと UmigamePocStack・プライバシーポリシー

ユーザーから「既存セット（logic-training-1 等）の Meta アプリは使えないのか」の確認があり、以下の判断材料で「投稿は既存アプリ流用のまま、コメント Webhook だけ新規アプリ」に決着した。

  • 既存アプリは開発モードで、稼働中セットの無期限トークンはその構成に依存する（運用設計 5.1 の実測記録）。コメント Webhook は PoC で「開発モードでは一切届かない」と実証済みのため、既存アプリで受けるには公開モードへ切り替える必要があり、logic-training-1 / pref-ranking-1 のトークンが 60 日失効へ戻る可能性がある
  • API の方式が違う: 既存アプリは Facebook ページ経由（graph.facebook.com）、PoC は Instagram ログイン方式（graph.instagram.com。署名鍵は Instagram アプリシークレット）。既存アプリで受けるなら Webhook 購読手順と返信経路を作り直して再実証が要る
  • 自動返信の規約リスクを既存資産から切り離せる（2026-08-28 の桜アカウント見送りと同じ考え方）
decision（2026-09-03 ユーザー決定）
  • 投稿 = 既存 Meta アプリの流用（運用設計 5.1 の通常手順。Facebook ページを新規作成して umigame.soup.jp を連携。2026-07-27 の「2 セット目以降は既存アプリ流用」決定はそのまま）
  • コメント Webhook = 本番用 Meta アプリを新規作成し公開モードで運用（Instagram ログイン方式。PoC の手順をそのまま本番アカウントで再実施）。PoC アプリ + test_tkghr はステージング専用のまま維持
  • umigame.soup.jp は両方のアプリに接続する（投稿用に既存アプリ、コメント用に新規アプリ）。投稿バッチが記録する media_id と Webhook の media.id が同じ値かを 21-6 でステージング面で照合する（S3 スナップショット problems/{media_id}.json のキーが一致しなければ経路が成立しない）
  • プライバシーポリシー = S3 静的ホスティング（公開モードの必須要件。21-6 の CDK に HTML 1 枚を載せる）
  • UmigamePocStack は 21-6 で新スタックを同一コードから本番面・ステージング面の 2 面で立て、ステージング用 Meta アプリの Webhook 先を切り替えた後に削除する（PoC ハンドラを別コードで残すと本番と乖離するため。2 面分の定常費はほぼゼロ）。ステージング面の長期トークン失効は開発計画の確認待ちリストで追う
