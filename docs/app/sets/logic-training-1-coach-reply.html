logic-training-1 の正解返信

設計（未実装） 最終更新: 2026-10-24（Phase 31-2 で新設。実装は 31-3、AWS は 31-4、本番開始は 31-5・31-6） 1 段上: 機能別の基本設計 脳みそコーチの正解返信

要約

このページは、脳みそコーチ（logic-training-1）の正解コメントへの定時の自動返信について、アプリの振る舞いを書く詳細設計である。1 回の起動の手順、返信の対象から外すもの、判定と一番乗り、返信文、問題スナップショットと状態ファイルの形、過去の投稿のバックフィル、運用（始め方・止め方・誤った返信の消し方）を扱う。AWS の定義は CDK スタック実装仕様 3.7 にある。

図 1 は、1 件のコメントが返信されるかどうかの分かれ道を表す。上から順に除外の条件を当て、最後まで残ったものだけを判定し、確信が高い正解だけに返す。

項目要点
対象/me/media の一覧に出る投稿のうち、問題スナップショットがある投稿の、返信の開始日時より後のトップレベルのコメント → 理由 D-01
判定LLM（Anthropic の API）が、問題文・答え・解説を基にコメントを correct / alt / wrong / unsure と確信の高さに分ける。返すのは correct かつ確信 high だけ
一番乗りその投稿のそれより前のコメントがすべて wrong と判定済みで、運用者の返信がまだない投稿の最初の正解にだけ添える → 理由 D-03
状態S3 の状態ファイル（コメント数の前回値・投稿ごとの判定済み）。DB には書かない
止め方SSM パラメータ reply-enabled を off にする 1 コマンド（次の起動から返信が止まる）

1. 1 回の起動の手順

Lambda acps-{env}-coach-reply-run の 1 回の起動で、次の順に処理する。Graph API は Instagram ログイン方式（graph.instagram.com）で、Secret の返信専用アプリのトークンを使う。

  1. SSM パラメータ reply-enabled（on / off）と reply-not-before（ISO 8601 の UTC 日時）を読む。どちらかが読めない・形が不正なら、返信せずにエラー終了する（アラームで知らせる）
  2. Secret からトークンと自分のユーザー名を読む（ユーザー名は GET /me?fields=user_id,username で取り、起動の中だけ使う）
  3. GET /me/media?fields=id,timestamp,comments_count&limit=100 をページ送りで最後まで読む（2026-10 時点で約 150 本 = 2 ページ）
  4. 状態ファイル state/media-counts.json を読み、comments_count が前回値と違う投稿（増えた・減った・初めて見た）だけを選ぶ。前回値のない投稿は初回として扱う
  5. 選んだ投稿ごとに: 問題スナップショット {PROBLEMS_PREFIX}{media_id}.json を読む。なければ「スナップショットなし」としてコメント数だけ更新して次へ（停止中の昼のフェルミ推定・ストーリーズなど）
  6. コメントを GET /{media_id}/comments?fields=id,text,username,timestamp,replies{id}&limit=50 でページ送りで最後まで読み、2 章の除外を当てる
  7. 残ったコメントを投稿ごとにまとめて LLM で判定する（3 章。1 回の呼び出しで最大 20 件。それを超えたら分ける）
  8. 返す対象のコメントに、時刻の古い順に 1 件ずつ返信する（POST /{comment_id}/replies?message=…。スイッチが off なら呼ばない）。1 件返すごとに状態ファイル state/judged/{media_id}.json を書き直す
  9. 投稿の処理が最後まで終わったら、その投稿のコメント数の前回値を更新する。判定に失敗したコメントが残る投稿は前回値を更新せず、次の起動で読み直す
  10. 最後に state/media-counts.json を書き、起動の要約（投稿数・読んだ投稿・判定した件数・返信した件数・失敗）を INFO ログに 1 行で出す

Lambda の予約同時実行数は 1 にして、起動が重ならないようにする。1 回の起動が上限時間（300 秒）を超えそうなときは、処理できた投稿までで状態を書いて終わり、残りは次の起動に回す（コメント数の前回値を更新しないので取りこぼさない）。

2. 返信の対象から外すもの

次の表は、読み出したコメントのうち判定に回さないものと、その見分け方。見分け方は 31-1 の実測（31-1 作業記録）に基づく。

外すもの見分け方記録
返信の行（コメントへの返信）トップレベルの一覧には返信も重ねて出る。どれかのコメントの replies に同じ ID があれば返信の行とみなす → 理由 D-02しない（数えない）
運用者（自分のアカウント）の行トップレベルの行の username が自分のユーザー名しない
本文のない行text がない（削除・制限済みと見られる。31-1 で 1,912 件中 1 件）しない
判定済み状態ファイル judged/{media_id}.json にコメント ID がある—
返信済み（運用者の手での返信・この機能の返信）replies の中に、自分のトップレベルの行と同じ ID がある。replies の各行には username が返らないため、この突き合わせで見分ける → 理由 D-02verdict: "operator_replied"
返信の開始日時より前のコメントtimestamp < reply-not-beforeverdict: "before_start"（判定はしない）
一覧に出ない投稿・スナップショットのない投稿/me/media に出ない投稿は読まない。出てもスナップショットがなければ読まない → 理由 D-01起動の要約ログの件数だけ

運用者は自動の返信が付いていないコメントに、これまでどおり手で返してよい。手での返信は次の起動で「返信済み」として拾われ、自動では返さない。

3. 判定・一番乗り・返信文

3.1 判定

判定は LLM の 1 回の呼び出しで、1 つの投稿の未判定のコメントをまとめて扱う。モデル・プロンプト・確信の閾値は 31-3 のオフライン評価で決め、決めた値をこの節に書き戻す。

  • 渡すもの: スナップショットの問題文（question_text）・答え（answer_text）・解説（explanation）・ヒント（hint。あれば）と、コメントの ID・本文の一覧。コメント主の名前は渡さない
  • 返させるもの: コメントごとに verdict（correct = 用意した答えと同じ / alt = 答えとは違うが正解と言える / wrong = 外れ / unsure = 答えになっていない・判断できない）と confidence（high / low）と短い理由。JSON で受け、形が不正なら判定の失敗として扱う
  • 返す条件: verdict = correct かつ confidence = high だけ。alt は手での運用で「〇〇でも正解だぞ」と中身に合わせて返しているため、自動では返さない
  • 失敗: API エラー・タイムアウト・応答の形の不正はその投稿の未判定のコメントを判定済みにせず、次の起動で判定し直す。同じコメントが 3 回続けて失敗したら verdict: "judge_failed" として以後は判定しない
  • オフライン評価の合格線（31-3）: 31-1 の評価用データで、運用者が外れ・判定なしとしたコメントを「返す」と判定した件数が 0 件。正解（517 件）のうち返せた割合を記録する

3.2 一番乗り

「一番乗りだな」は、その投稿で最初に正解したコメントにだけ添える。次の 3 つをすべて満たすときに限る → 理由 D-03。

  1. その投稿に、運用者の返信（手での返信）がまだない
  2. そのコメントより時刻が前のトップレベルのコメント（運用者の行・返信の行を除く）が、すべて wrong と判定済み（または 1 件もない）。開始日時より前のコメントは判定しないので、開始前のコメントがある投稿では付かない
  3. 状態ファイルのその投稿の first_correct_replied が false

3.3 返信文

返信文は定型文の候補からランダムに選ぶ（LLM で作らない）。候補は手での運用の文面（31-1 の運用者の返信）から作り、コードの定数に持つ。返信の先頭には @{username} を付ける（手での返信と同じ見た目）。

  • 正解: 例「正解！！お見事👏」「正解💪💪 お見事👏」「正解！お見事👏👏」（候補は 31-3 で 8 本程度に増やす）
  • 正解 + 一番乗り: 例「正解！！お見事👏 一番乗りだな💪💪」

4. 問題スナップショット（quiz 用）

投稿バッチは、batch_sets.problem_snapshot_enabled = 1 のセットで、quiz_items 行のある実行のリールの投稿に成功した直後、次の JSON を S3 assets/{set_code}/problems/{media_id}.json に書く（バッチ処理フロー）。ウミガメのスナップショット（schema_version 4）とは kind で見分ける。

{
  "schema_version": 1,
  "kind": "quiz",
  "set_code": "logic-training-1",
  "media_id": "18108280241184087",
  "posted_at": "2026-10-23T22:33:47Z",
  "quiz_type": "L1",
  "difficulty": "light",
  "question_text": "…",
  "answer_text": "…",
  "explanation": "…",          // content_fields.explanation
  "hint": "…",                 // content_fields.hint（ないときは null）
  "source": "post"             // 投稿バッチ = post / バックフィル = backfill
}

4.1 過去の投稿のバックフィル

フラグを立てる前の投稿にはスナップショットがないため、本番開始の前に一度だけ DB から書き出す。スクリプトは services/coach-reply/tools/backfill_snapshots.py（31-3 で作る）。

  1. RDS Data API で posts（status = 'success'・platform_post_id あり・セットが logic-training-1）と quiz_items を generation_run_id で結んで読む（SELECT だけ。Aurora を起こすのはこの 1 回。31-1 の poc/logic-training-reply-eval/collect.py answers と同じ問い合わせ）
  2. S3 に同じキーがまだない投稿だけ、上の形（source: "backfill"）で書く。既にあるキーは上書きしない
  3. 既定は書かずに件数だけ出す（--dry-run が既定、書くときは --apply）。実行は 31-5 でユーザーが行う

投稿バッチの出力が失敗した投稿も、同じスクリプトを流し直せば埋まる（既にあるキーは飛ばすため、何度流してもよい）。

5. 状態ファイル

状態は画像バケットの coach-reply/{SET_CODE}/state/ に置く（本番面 logic-training-1・ステージング面 logic-training-1-staging）。ライフサイクルは掛けない（判定済みを消すと再判定してしまうため）。

ファイル中身
media-counts.json{"updated_at": "…", "media": {"<media_id>": {"comments_count": 12, "checked_at": "…"}}}
judged/{media_id}.json{"media_id": "…", "first_correct_replied": false, "comments": {"<comment_id>": {"verdict": "correct", "confidence": "high", "reason": "…", "replied": true, "reply_id": "…", "first": false, "switch": "on", "judged_at": "…", "fail_count": 0}}}。verdict は判定の 4 値のほか operator_replied / before_start / judge_failed

コメント本文とコメント主の名前は状態ファイルに残さない（判定の理由は短い文だけ）。調べるときはコメント ID で Instagram から引く。

6. 返信スイッチと開始日時

パラメータ値意味
/acps/{env}/coach-reply{-staging}/reply-enabledon / off（CDK の初期値は off）off では判定と記録だけを行い、返信を呼ばない。記録には switch: "off" と replied: false を書き、そのコメントは後で on にしても返さない（判定済みのため）
/acps/{env}/coach-reply{-staging}/reply-not-beforeISO 8601 の UTC 日時（CDK の初期値は遠い未来 2099-01-01T00:00:00Z）これより前のコメントには返さない。本番開始の go のとき（31-6）に開始の日時を入れる → 理由 D-04

CDK はパラメータを作るだけで、値の変更は CLI で行う（再デプロイで値が初期値へ戻らないよう、CDK 側は値の変更を無視する設定にする。31-4）。

7. 運用

7.1 始め方（31-5・31-6）

  1. バックフィルを --dry-run で流して件数を確かめ、--apply で書く
  2. 投稿バッチのフラグを立てる: UPDATE batch_sets SET problem_snapshot_enabled = 1 WHERE set_code = 'logic-training-1';（データの更新で DDL ではない）。次の投稿の後に assets/logic-training-1/problems/{media_id}.json ができたことを確かめる
  3. スイッチを off のまま、開始日時を今にして 1 回手で起動し、ログの要約と状態ファイルを確かめる（返信は呼ばれない）
  4. go の後、開始日時をあらためて今にしてからスイッチを on にする（off の間に判定したコメントには返さないため、試しの起動の後に開始日時を進める）
aws ssm put-parameter --name /acps/prod/coach-reply/reply-not-before --value "$(date -u +%Y-%m-%dT%H:%M:%SZ)" --overwrite
aws ssm put-parameter --name /acps/prod/coach-reply/reply-enabled --value on --overwrite

7.2 止め方

aws ssm put-parameter --name /acps/prod/coach-reply/reply-enabled --value off --overwrite

次の起動から返信が止まる（判定と記録は続く）。起動そのものを止めたいときは Scheduler acps-prod-coach-reply-run を無効にする（aws scheduler update-schedule … --state DISABLED。再デプロイで有効に戻るため、長く止めるなら CDK 側も直す）。

7.3 誤った返信を見つけたとき

  1. すぐスイッチを off にする（7.2）
  2. 誤った返信を消す: Instagram アプリでその返信を長押し → 削除する（運用者のアカウントで消せる。API で消す場合は返信専用アプリのトークンで DELETE /{reply_id}。reply_id は状態ファイルにある）
  3. 状態ファイルのそのコメントはそのまま残す（判定済みのままなので、on に戻しても返し直さない）。必要なら運用者が手で返し直す
  4. /incident で事象を記録し、判定の誤りを課題として起票する。直すまでスイッチは off のまま

7.4 監視・トークン

  • Lambda のエラー（SSM・Secret が読めない・Graph API の一覧の失敗・状態ファイルの書き込みの失敗）は MonitoringStack のアラームで SNS へ通知する。判定の失敗はエラーにせず、ログの要約に件数を出す
  • トークンは週 1 回の Lambda acps-prod-coach-reply-token-refresh が更新する（ウミガメと同じ方式。トークン更新）。トークンが失効すると一覧の失敗でアラームが鳴る
  • 返信専用アプリのプライバシーポリシーの URL は、31-1 ではウミガメの URL を暫定で借りている。31-4 で CoachReplyStack の専用バケットを作ったら、Meta アプリの設定の URL を差し替える（ユーザー作業）

7.5 ステージング面での試験（31-4）

テスト用アカウント（test_tkghr）の投稿に、ステージング用のスナップショット assets/logic-training-1/staging/problems/{media_id}.json を手で置き、別のアカウントから正解・外れのコメントを書いてから aws lambda invoke --function-name acps-prod-coach-reply-run-staging で起動する。正解に返信が付き、外れに付かず、2 回目の起動で同じコメントを判定し直さず、スイッチを off にすると返信が止まることを確かめる。

判断の記録

本文の「→ 理由 D-xx」から飛んでくる先。

D-01 対象は一覧に出る投稿で、スナップショットのあるものに限る

決めたこと
コメントを読むのは /me/media の一覧に出る投稿だけで、問題スナップショットのない投稿は読まない。DB にある投稿でも一覧に出ないものは扱わない
理由
31-1 の実測で、DB の投稿 367 件のうち 215 件が一覧（media_count 152）に出ず、そのうち 213 件はメディア ID を直接指定しても「存在しない・権限がない」で読めなかった（アーカイブ・削除などが考えられるが未確認）。視聴者がコメントできるのは表示されている投稿なので、一覧を正とする。正解がわからない投稿で返すことは D-04（確信が高いときだけ返す）に反する
日付・出典
2026-10-24（31-1 の実測・31-2）

D-02 返信の行と返信済みは ID の突き合わせで見分ける

決めたこと
トップレベルの一覧に重ねて出る返信の行は、どれかの replies に同じ ID があるかで見分ける。返信済みかどうかは、replies の中に自分のトップレベルの行と同じ ID があるかで見分ける
理由
31-1 の実測で、replies{} の各行には username が返らなかった（902 件すべて）。一方、運用者の返信 841 件はすべてトップレベルの一覧にも username 付きで出ていたため、ID で結べば書き手がわかる。replies{from} で書き手が取れるかは 31-3 で試し、取れればそちらに替えてよい
日付・出典
2026-10-24（31-1 の実測・31-2）

D-03 一番乗りは、前のコメントがすべて外れと判定済みのときだけ添える

決めたこと
運用者の返信がまだなく、そのコメントより前のコメントがすべて wrong と判定済みの投稿の、最初の正解にだけ「一番乗り」を添える
理由
一番乗りの誤り（本当は先に正解した人がいる）も視聴者に見える誤りになるため、判定していない・迷ったコメントが前にあるときは付けない。開始前のコメントは判定しないので、開始前からコメントのある投稿では付かない（取りこぼしは無害）。運用者がすでに返している投稿は、運用者が一番乗りを付けた可能性があるため付けない
日付・出典
2026-10-24 アイデアの壁打ち（一番乗りは開始前を含めた時刻順で判定し、過去に正解が付いている投稿では付けない）を、判定しないコメントがある場合まで含めて具体化（31-2）

D-04 開始日時より前のコメントには返さない

決めたこと
SSM パラメータ reply-not-before より前のコメントは判定せず、返信もしない
理由
全投稿を対象にするため、開始の時点で過去の未返信のコメント（31-1 で 205 件）に一斉に返信してしまうのを避けるため。数日前のコメントへの返信は手での運用にもない見え方になる
日付・出典
2026-10-24 アイデアの壁打ち（対象の投稿の範囲）
