1. テーマ

社会人向けロジカルトレーニング（15-2 決定）。日本の社会人の日常を題材にしたクイズ形式の縦型ショート動画を 1 日 3 回投稿する（16-4d で昼スロットを当分停止中のため、現在は朝・夜の 1 日 2 回。冒頭の注記を参照）。世界観は「毎日 3 分の頭の体操ジム」で、進行役として脳のマスコット「脳みそコーチ」（ヘッドバンド + ホイッスル + 力こぶ / フラットベクター・ネイビー × アンバー）が全カットに登場する。

出題は 2 種類（parameters.slots の quiz_type で時間帯ごとに固定）。出題は人間レビュー済みの問題ストック（quiz_stock_items）からの取得のみで、誤答リスクは投入時のレビューで担保する（16-1 でストックのみ方式へ転換。調達・投入の運用は operation.html セクション 3）。

3. スケジュール（投稿頻度）

1 日 3 回（朝 7:30 / 昼 12:30 / 夜 21:00 JST）。15-4 の決定（目安）を 15-15 でこの時刻に最終確定し、スロットごとに Scheduler を 1 件ずつ（計 3 件）追加して ENABLED 化した（ユーザー決定）。16-4d（2026-08-24）で昼の Scheduler を DISABLED 化し、現在は朝・夜の 1 日 2 回（冒頭の注記を参照）。コンテンツ生成に数分かかるため、実投稿はスケジュール時刻の数分後になる。

どのスロットとして生成するかは実行時刻（SCHEDULED_AT の JST 時）から決定的に解決する。parameters.slots の from_jst_hour の境界と、対応する Scheduler は以下（早朝の巻き戻しを含む解決規則は方式側の実装による）。

4. プロンプトの作り方

16-1 の生成チェーン休止に伴い、prompt_configs.prompt_text は未使用（休止）。実行時に使われるのは parameters（スロット定義）のみで、出題内容は問題ストック（operation.html セクション 3）が担う。登録済みの文言・値は変更せず残置する（方式側が無視する。生成経路を再開する場合と、ストック執筆時の文体ガイド〔題材・question・L3・hook 等の条件は 16-2 の執筆ガイドラインとしてそのまま有効〕のため）。

登録済みの文言（15-13 で設計・15-14 でローカル & Aurora へ登録済み。16-2 のストック執筆ガイドを兼ねる）。

社会人向けロジカルトレーニング「脳みそコーチのロジトレ」。世界観は「毎日3分の頭の体操ジム」。
ヘッドバンドとホイッスルを着けた脳のマスコット「脳みそコーチ」が進行役として出題する。

【視聴者】
・日本の社会人（20〜40代）。専門知識ゼロ・紙とペンなしで解けること。

【題材】
・日本の社会人の日常（通勤・オフィス・会議・コンビニ・自炊・週末の家事など）を舞台にする。
・実在の企業名・商品名・人名・作品名・時事の出来事は使わない。人物は A・B・C など無色の呼び方にする。
・図や表を見ないと解けない問題にしない。頭の中だけで追える情報量にする。

【question】
・声に出して10秒で読める長さ。解くのに必要な条件をすべて問題文に書き切る。
・曖昧語（たぶん・一般に・など）を使わず、答えが一意に決まる書き方にする。

【L3（フェルミ推定）のとき】
・身近な数量の「規模」を推し量る問題にする（例: 〜は日本全国で約何台か / 1年で約何回か）。
・公式・物理定数・換算値を問題文で与えて計算させる問題にしない。日常の観察から分解して概算できる問いにする。

【hook】
・今日の一問への短い呼びかけ。答え・解法のヒントは出さない。

【explanation】
・考え方の筋道を一本だけ、順を追って示す。L3 は使った数値と「○○×○○」の式の形を必ず含める。

【coach_comment】
・脳みそコーチのひとこと。体育会系だが威圧しない、明るく前向きな励まし。

【tags】
・日本語の短い語（例: 論理クイズ / 推定力 / 朝の一問）。記号は付けない。

【illustration_scene】
・問題の舞台になっている日本の日常風景を、簡潔な一文で描写する。
・人物を出す場合は後ろ姿か遠景までにし、顔を描き込まない。脳のマスコットは描かない。
・答えが分かってしまう物・数えられる並び・図表は描写しない。

decision: 15-13 の試し打ち（実 API・3 スロット）で確定した 4 点（1・2 は生成チェーン休止後は歴史的記録）
  1. L3 の出題方向を明文化: 初回の試し打ちで「水 500mL を 20℃ から 80℃ へ温める…何分？」のように定数を与える計算問題が出た（フェルミ推定ではない）。プロンプトへ「規模を推し量る問題にする / 公式・定数を与えて計算させない」を追記し、「日本全国で平日の昼休みにコンビニで買われるおにぎりは 1 日約何個？」型に矯正した（この出題方向はストック執筆ガイドとして 16-2 でも有効）
  2. max_regenerations を 3 → 5: 夜（L1 / deep）の 5 要素の順序パズルは独立 LLM 検証（答えを伏せた別解答）が誤答して不合格になることがあり、4 回上限では 3 回に 1 回ほど再生成を使い切って異常終了した。上限を 6 回（初回 + 5）にすると 3 回連続で成功（16-1 の生成チェーン休止によりこのパラメータ自体が休止）
  3. 昼のパレットをライトブルーへ変更（ユーザー決定）: 15-9 の初期値では昼＝ダークネイビーで夜とほぼ同じ見た目になっていた。朝＝クリーム / 昼＝ライトブルー / 夜＝ダークネイビーの 3 段構成にして時間帯のだし分けを視覚的に成立させた（コード側 SLOT_PALETTES の noon を差し替え）
  4. 禁則処理を組版へ追加: 句読点や閉じ括弧が行頭に落ちる（「話します
    。C は…」）事象が全カットで出ていたため、行頭禁則・行末禁則を満たす位置まで分割を追い出す処理を _wrapped_lines に入れた（本セット固有ではなく方式共通の改善）
14-11 の知見の流用 fantasy-animals-1 のプロンプト設計で効いた「①構成の明示 ②毎回変える要素の明示 ③Instagram UI セーフエリア」のうち、①②は上記の題材・question 条件として文言に取り込んだ。③は本方式ではプロンプト側の指定が不要で、レンダラーがセーフエリアを計算して文字とコーチを配置する（旧 Pillow 組版は右 12% / 下 15%。改修 R-1 の Remotion 版は高さ依存の 2 ゾーンで、上部は左右対称・右 12% の予約は下部のイラスト・コーチ・吹き出しだけに掛ける）。イラストはカード内の専用ブロックに敷かれる（15-14 で全面背景から変更）ため、文字の見切れは構造的に発生しない。

ファイル仕様: RGBA の PNG（他モード・非 PNG は異常終了）。4 枚とも 900 × 1290 px の共通キャンバスで、4 ポーズ共通の倍率で拡縮したうえで下端中央そろえにしてある。組版側は COACH_BOX（300 × 430 px）へ縦横比を保って収め、セーフエリアの右下に配置する。共通キャンバス・共通倍率にしておくことで、カットが切り替わってもコーチの大きさと立ち位置が動かない。

生成物はプログラム検査 + 目視で受け入れ判定する。プログラム検査は ①背景の透過率 15% 超 ②四隅が完全透過 ③オフホワイトの不透明画素が一定数以上の 3 点。③は 15-13 で追加した検査で、ヘッドバンドの白面まで透過に抜ける事故（明るいカットでは背景が透けて白く見えるため気づけず、夜のダークパレットで初めて破綻する）を捕まえるためのもの。目視では姿勢の破綻（指の崩れ・腕の融合）・ヘッドバンドの色化け・輪郭外のノイズ画素を確認し、不合格なら生成し直す。
作り直す場合の入力（リファレンス画像・生成プロンプト・正規化スクリプト）は plans/15-13-trial/ にある（plans/ は Git 管理外）。

8. 失敗時ポリシー

共通の失敗時ポリシー（operation.html セクション 4）に準拠する。本セット固有の注意点は以下（16-1 のストックのみ方式・16-3b の事前生成方式を反映）。実行時の失敗要因は「ストック選定 + 事前動画取得 + 投稿」だけになり、生成起因の障害（イラスト生成失敗・組版の収まり不足等）はビルド時のローカル作業へ移った。

  • ビルド済みストック 0 件（スロットの型・難度に一致する有効かつ video_s3_key IS NOT NULL の行なし）は異常終了し、その回は投稿しない（未投入・全行無効化・全行未ビルドの検知。quiz-prebuilt セクション 4）。取得した行のフィールド不備（必須欠落・文字数超過）も同様に異常終了（投入ミスの検知。キャプション展開の入力保護）
  • 未使用ストックが尽きた場合は利用済みストックを再利用する（LRU で最古使用分から。投稿は止まらない。同一動画の再投稿になる点は許容 = quiz-prebuilt セクション 4 の decision）。再利用時は WARNING ログが出るため、補充遅延のサインとして在庫確認 → 補充を行う（operation.html セクション 3）
  • 事前動画の S3 欠落（DB はビルド済みなのに実体なし）は縮退せず異常終了（DB と S3 の不整合の検知）
  • ストーリーズ投稿の失敗はリールの success を巻き戻さない。終端状態で確定した投稿失敗は Step Functions の再実行では検知できないため、検知は ECS タスク異常終了通知が担う（batch-flow.html セクション 3.4）

9. 共通フローからの差分・特記事項

使用方式は quiz-prebuilt（16-3b の転換。batch_sets.generator_name は 16-4〔2026-08-08〕で切替済み）: ストック LRU 選定 → S3 の事前動画取得 → 返却のみの軽量実行（generators/quiz-prebuilt.html）。動画の作り・組版は当初 gpt-quiz-multicut（generators/gpt-quiz-multicut.html。実行時方式としては休止）のレンダラーを事前ビルドへ転用していたが、改修 R-1（2026-09-03）で Remotion へ載せ替え、以後は quiz-prebuilt.html セクション 8 を正とする。既存セット（gpt-image-kenburns）とは生成方式が異なるが、出力がリール用 MP4 である点は共通。SNS 投稿バッチ側の差分はストーリーズ連続投稿（15-12 で実装）とキャプションの動的組み立て（16-1 設計・16-3 実装。プレースホルダを含むテンプレートを登録する唯一のセット）で、いずれも 16-3b の転換による変更はない。

本セットは共通テーブルのうち quiz_stock_items（問題ストック）と quiz_items（出題履歴。16-1 で stock_item_id による突合を追加）を使う唯一のセットである（data-model.html セクション 4.9 / 4.10）。
