1. テーマ

都道府県ランキング（17-1 決定）。統計・調査データに基づく都道府県 TOP5 を、日本地図のルーレット演出で発表するフルナレーション付き縦型ショート動画を 1 日 1 回投稿する。進行役は金の 3 段表彰台がボディのお祭り実況キャラ「表彰台五郎」（ひょうしょうだいごろう。赤ねじり鉢巻 + ハンドマイク、1 位発表時のみ軍配を掲げる）。ビジュアルは和モダン（生成り地 × 藍 × 金。セクション 8）。

  • フォーマットは TOP5 地図ルーレット型のみ（17-1 巡 1 決定。全県塗り型は第 2 候補として設計骨子のみ = 方式設計書 付録 A）。下位順位（ワースト）は扱わない。ネタ選定基準は「下位の県の人が笑って自虐できるか」（事業戦略書セクション 6）
  • 尺は 30 秒（フルナレーション。2026-08-24 ユーザー判断で確定 = セクション 3 の decision）。各ネタは 30 秒版 1 本のみビルドする。20 秒版のコンポジション・タイムラインは実装済みのまま休眠（増便・尺再検討時の保険として残す）
  • ネタは人間レビュー済みのランキングストック（ranking_stock_items）からの取得のみ。出典実在・県換算の検証は投入時のレビューで担保する（調達・検証・投入の運用は operation.html セクション 3）。市区町村単位の統計（家計調査等）は世帯数加重平均で県換算し、換算した旨を動画の出典行とキャプションに明記する（Phase 17 決定方針）

動画の作り（タイムライン・版面・ルーレット演出・TTS 同期）は方式設計書（generators/ranking-prebuilt.html セクション 8.2〜8.3）を参照。動画は実行時に生成せず、事前にビルドして全数人間レビューのうえ S3 に作り置く。

3. スケジュール（投稿頻度）

1 日 1 回（夜 20:00 JST）（2026-08-24 のユーザー決定。17-2 巡 3 の「1 日 2 回〔昼 12:30 / 夜 20:00〕」から変更）。ネタ供給が週 7 ネタ + 動画レビューに半減し、人間レビューの負荷を抑えて立ち上げる。生成費は 0 円のため頻度のコスト制約はない（事業戦略書セクション 3.1）。増便（1 日 2 回へ）は初速を見て判断する。

どのスロットとして実行するかは実行時刻（SCHEDULED_AT の JST 時）から決定的に解決する（方式設計書セクション 3）。スロットは投稿する尺（duration_seconds）を切り替える（クイズ方式のような型・難度・BGM・配色の切替はない）。

4. プロンプトの作り方

ストック方式のため prompt_configs.prompt_text は未使用（logic-training-1 の 16-1 以降と同じ扱い。NULL 相当の空文言で登録する）。実行時に使われるのは parameters（スロット定義と尺）のみで、コンテンツはランキングストック（operation.html セクション 3）が担う。

登録する prompt_configs.parameters（キー仕様は 方式設計書セクション 3）:

{
  "slots": [
    {"from_jst_hour": 17, "slot_code": "evening", "duration_seconds": 30}
  ]
}

背景イラストの imagegen プロンプト方針（ビルド時。方式設計書セクション 8.1 工程 2）: ネタごとの content_fields.bg_motif（テーマに沿った背景モチーフの指示文。例: 餃子と湯気の屋台風モチーフ）に、セット共通の画風固定行を付けて生成する。画風固定行の要件: ①和モダン（生成り地・淡墨茶・金の落ち着いた配色でセクション 8 のパレットと調和。17-2 時点は「藍」だったが、17-4a のパレット Fix〔藍 → 淡墨茶〕に合わせて 17-4e で修正した）②フラットイラスト調・写実禁止 ③版面の文字を邪魔しない低コントラストの装飾密度 ④文字・数字・記号を描かない（再利用要件①）⑤9:16 のサイズ明示。文言は 17-4e で確定した（content/video-build/pref-ranking-1/export_prompts.py の STYLE_LINE / SIZE_LINE / NO_TEXT_LINE が正。上記 5 要件をこの 3 行が満たす）。背景モチーフはネタのテーマ由来であり、固定の和風装飾を常設するものではない（17-1 決定の記録どおり）。

6. 音源の構成

BGM はスロット共通の汎用曲を audio_assets（time_slot = NULL / asset_type='bgm'）に登録する（調達・前処理・証跡は operation.html セクション 3 の共通ルール。S3 キーは audio/pref-ranking-1/{ファイル名}.m4a。調達は 17-5b で実施 = 下記 decision）。選曲はビルド時の LRU ローテーション（1 ネタ 1 曲〔尺を問わず共通〕・video_audio_asset_id に記録 = 方式設計書セクション 8.1 工程 3）。実行時は audio_assets を使わない。

決定（17-2 巡 3、設計者判断）: SE は初期構成では使わない クイズ方式の SE 2 種（カウントダウン・チャイム）に相当する効果音は初期構成に含めない。スピン停止・1 位発表の強調は映像演出（停止フラッシュ・バースト・キャラのポーズ切替）とナレーションの実況が担うため。ナレーション + BGM + SE の 3 層は音のミキシング調整コストも上がる。17-4 の実装・レビューで「発表の瞬間に音の区切りが欲しい」と判明した場合は、quiz 前例の asset_type='se' + 固定ファイル名方式で追加する（構造は既存のまま使える）。

BGM はナレーションを妨げない音量にビルド時のミキシングで調整する。曲の差し替えは既ビルド動画に反映されないため再ビルドが必要（方式設計書セクション 8.4）。

決定（2026-08-11、17-4d）: ミキシングの値（実測校正） BGM はナレーションの 18 LU 下・ダッキングなし（頭 0.5 秒フェードイン / 尻 1.5 秒フェードアウト、曲が尺より短いときはループ）。ナレーションがほぼ全編を占めるため、ダッキングを入れても常時作動して定常減衰と変わらないと判断した。ゲイン定数は remotion/src/audio.ts が正。配信レベル（絶対的なラウドネス）はコンポジションでは決めず、レンダリング後の ffmpeg loudnorm（remotion/scripts/normalize_loudness.py。目標 I = -14 LUFS / TP = -1.5 dBTP）で揃える。根拠と実測値は方式設計書セクション 8.3 の decision（17-4d）。
決定（2026-08-26、17-5b）: BGM 素材の前処理仕様（共通ルールからの差分） 本セットの BGM 素材は 30 秒ちょうど（動画と同尺）に切り出し、フェードは焼き込まない（曲数は下記 decision のとおり 1 曲）。ラウドネスは共通ルールどおり 2 パス loudnorm（linear）で I = -14 LUFS / TP = -1.5 dBTP に揃える。理由: ①コンポジションは曲が尺より短いとループするため、30 秒未満の素材だと動画内でループの継ぎ目が鳴る ②フェードは上記 decision（17-4d）のとおりコンポジション側が頭 0.5 秒 / 尻 1.5 秒で掛けるため、素材にも焼くと二重に掛かる ③ミキシングゲイン BGM_GAIN は -13.8 LUFS の音源で校正した値で、素材のラウドネスがばらつくと曲ごとに BGM の音量が変わる。前処理・S3 キー・audio_assets 登録 SQL の生成は専用ツール content/video-build/pref-ranking-1/prepare_bgm.py が行う（operation.html セクション 3 の共通手順 2〜4 の本セット版）。
決定（2026-08-26、17-5b、ユーザー判断）: BGM は 1 曲運用（共通ルールの 3〜5 曲に対する差分） 全ネタで同じ 1 曲を使う。理由はセットとしての世界観をそろえるため（毎日 1 投稿・同じキャラの実況という構成上、曲が入れ替わるとシリーズとしての手触りが散る）。登録曲は「Japan Instrumental Background Music」（Tunetank / Pixabay Content License・クレジット不要。証跡は audio_assets の各カラム）。LRU 選曲の機構はそのままで、常に同じ 1 曲が選ばれる。
  • 影響範囲の申し送り: BGM は動画にベイクされるため、この 1 曲がミュート検知（operation.html セクション 4.4）にかかった場合、在庫の全本が同時に影響を受け、差し替えには全本の再ビルドが要る（--rebuild。方式設計書セクション 8.4）。登録曲は Pixabay の配布ページに Content ID Registered の表示があるため、この確認は毎週きちんと回す
  • 曲を増やす場合は audio_assets へ INSERT するだけでよい（未使用曲が LRU の先頭に来る）。ただし既ビルド分の BGM は変わらないため、統一したい場合は再ビルドが必要

9. 失敗時ポリシー

共通の失敗時ポリシー（operation.html セクション 4）に準拠する。本セット固有の注意点は以下（quiz-prebuilt 採用セットの 3 点セットを踏襲 + 尺別の在庫判定）。実行時の失敗要因は「ストック選定 + 事前動画取得 + 投稿」だけで、生成起因の障害はビルド時のローカル作業へ移っている。

  • 当該尺のビルド済みストック 0 件（有効かつスロットの尺の video_s3_key_20s / _30s が非 NULL の行なし）は異常終了し、その回は投稿しない（フェイルラウド。方式設計書セクション 4）。取得した行のフィールド不備（必須欠落・ranking_data の構造不正）も同様に異常終了（キャプション展開の入力保護）
  • 未使用ストックが尽きた場合は利用済みストックを LRU で再利用する（投稿は止まらない。同一動画の再投稿になる点は許容・再利用時は WARNING ログ = 補充遅延のサイン。水位を守っていれば発生しない = operation.html セクション 3）
  • 事前動画の S3 欠落（DB はビルド済みなのに実体なし）は縮退せず異常終了（DB と S3 の不整合の検知。別の尺・別のネタへの差し替えはしない）
  • ストーリーズ投稿の失敗はリールの success を巻き戻さない。終端状態で確定した投稿失敗の検知は ECS タスク異常終了通知が担う（batch-flow.html セクション 3.4）
  • 1 日 1 回のため、1 回の失敗はその日の投稿の欠落に留まる。当日リカバリの手順・判断基準は共通課題（development-plan.md 設計課題リスト 2026-07-26）に従う
