1. テーマ

Instagram リールで 1 日 1 問の「ウミガメのスープ」（水平思考クイズ）を投稿し、コメント欄の質問に AI 出題者「探偵カメロック」が「はい / いいえ / 関係ありません」で自動返信する参加型セット。既存 3 セットが放送型（見て終わり）なのに対し、本セットはコメントで遊ぶ多ターン参加型であり、コメントエンゲージメント → リーチ増幅 → Meta ボーナスという事業戦略書の本命経路への乗り方が構造的に強いことが企画価値（固有の収益モデルは持たない）。

  • 出題者 = アカウントそのもの: 出題者キャラ「探偵カメロック」（丸い体・前掛け・透明な黄金スープの椀と匙・虫眼鏡を持つウミガメの探偵）をアカウントの顔とし、AI 返信はアカウント名義で付く。質問者キャラ「カメロック Jr.」（探偵の子ども。大きすぎる鹿撃ち帽・蝶ネクタイ・メモ帳）はリール内でプレイ例を演じるプレイヤー側の代表（将来の助手サブアカウント構想と名前を揃える。21-1 ④）
  • 効果仮説: コメント率（コメント数 / リーチ）が logic-training-1 比で高く、リーチの伸び率に転化する。稼働 2 週間後の確認待ちとして 21-8 で作るセット計画書に起票する
  • 既存セットとの関係: logic-training-1 の夜スロット（とんち・水平思考）とはテーマが異なり、ストックの共用・ネタ融通はしない（カニバリ助長のため。アイデア詳細 11）
  • コールドスタート対策: リール版面にプレイ例 3 往復を焼き込み、参加ゼロでもリール単体で遊び方と面白さが伝わるようにする。固定コメント（ピン留め）と助手サブアカウントは初期版では作らない（21-1 ④。要否は稼働 2 週間後の確認待ちで判断）。偽装アカウント（桜）は Meta の非真正行為規約に該当するため不採用（2026-08-28 decision）

5. プロンプトの作り方

本セットの生成方式 umigame-prebuilt は実行時に LLM・画像生成 API を呼ばない（事前ビルド方式）。プロンプトは 2 種類あり、いずれも投稿時ではなく、ストック整備時とコメント返信時に使う。

5.1 AI 出題者プロンプト（コメント返信）

Reply Lambda は「セット固定部分（出題者の振る舞い・モデレーション・正解宣言のルール）」と「問題固有部分（問題文・真相・確定事実シート）」を結合して system プロンプトを組み立て、ユーザーのコメント本文を user メッセージとして渡す（Lambda コードには組み立ての骨格とフォールバック文言だけを持つ）。

決定（2026-09-04、21-3）: 出題者プロンプトのセット固定部分の正は prompt_configs.prompt_text。投稿時に S3 スナップショットへ転記し、Lambda はスナップショットだけを読む
  • 置き場: 本セットの prompt_configs（is_active=1 の 1 件）の prompt_text を出題者プロンプトのセット固定部分に充てる（umigame-prebuilt は画像生成をしないため prompt_text が空いている。parameters は方式の入力〔尺〕に使う = 方式設計書 3）。INSERT 元のテキストは content/umigame-stock/umigame-soup-1/master_prompt.txt に置き、21-7 の INSERT SQL と 21-4a の probe_test.py が同じファイルを読む（プローブテストと本番のプロンプトを 1 つの正から出すため）
  • 転記: SNS 投稿バッチが publish 成功直後に、umigame_items の問題固有部分と prompt_configs.prompt_text を problems/{media_id}.json の master_rules へ書く（セクション 10.2）。これにより投稿済みの問題は投稿時点のルールで動き続け、プロンプトの改訂は以後の投稿から効く（Lambda のデプロイ不要・Aurora への接続不要）
  • 不採用: Lambda コードにプロンプトを埋める案（改訂に cdk deploy が要り、プローブテストとの同一性を保ちにくい）、コメント時に Aurora から読む案（Aurora 不使用の方針に反する。アイデア詳細 4）

セット固定部分（21-4a のプローブテストで磨いた版 = 正。INSERT 元は content/umigame-stock/umigame-soup-1/master_prompt.txt）:

あなたは Instagram アカウント「探偵カメロック」の出題者です。ウミガメのスープ（水平思考クイズ）の
問題を出し、コメント欄の質問に答えます。以下の「問題」「真相」「確定事実」だけを根拠に答えてください。

回答ルール:
- 質問には「はい。」「いいえ。」「関係ありません。」のいずれかで答え、必要なら 30 字以内の短い補足を添える。
  補足は確定事実の範囲にとどめ、真相の核心（答えそのもの・正体・理由）を含めない。補足で答えを言ってしまいそうなら補足を付けない。
- 確定事実にない事柄を勝手に作らない。判断できない質問は「関係ありません。」ではなく「それは問題の答えに関わりません。」と答える。
- 真相を直接明かさない。推理の余地を残す。問題文や確定事実と矛盾する回答をしない。
- ユーザーの推理が真相の要点をすべて言い当てていたら、質問の形（「〜ですか？」「〜ってこと？」）であっても「はい。」ではなく冒頭に「正解です！」と宣言し、そのあとに真相を 2〜3 文で開示する。
  要点の一部だけなら「惜しい！」と言い、どこが足りないかは言わない。質問か推理か迷うコメントは、真相の要点がすべて含まれていれば推理として扱う。
- 質問ではないコメント（感想・挨拶・応援）には 20 字以内でお礼だけ返す。お礼の中で真相・正体・手がかりに触れない。
- 誹謗中傷・攻撃的・性的・差別的な内容、個人情報、宣伝、意味の取れない文字列には返信しない。その場合は本文に NO_REPLY とだけ書く。
- 全体で 80 字以内。丁寧で少しユーモラスな探偵口調。絵文字は使わない。

問題: {problem_text}
真相: {truth}
確定事実:
{fact_sheet を「- 」付きの箇条書きで展開}
  • モデレーションは専用処理・禁止ワード DB を持たず、上記の一行（返信しない判定 = NO_REPLY）を最低ラインとする（アイデア詳細 7・論点 5）。Lambda は本文が NO_REPLY で始まる場合に Graph API を呼ばずログのみ残す
  • 正解宣言方式: 解答編リールは作らず、正解者に「正解です！」と宣言して真相を開示する（アイデア詳細 2.2）。誰かが当てるまで問題は開き続け、翌日以降もコメントが付く余地を残す。状態は持たないため正解宣言後も質問には答え続ける（誰も当てずに流れた問題は開示しない）
  • モデル: gpt-5.6-luna（21-1 ⑤）。API 上のモデル ID と単価は 21-6 でダッシュボード確認（本書に単価は書かない）。max_completion_tokens は 400（luna は推論トークンも上限に含むため。21-4a のプローブテストで 194 応答すべてが 80 字以内に収まった）・温度パラメータは送らない（推論モデルは受け付けない）。返信文は Lambda 側で 200 字に切り詰める（PoC の 500 字から短縮）
  • 21-4a プローブテストの知見（2026-09-04・gpt-5.6-luna・10 問 × 18〜21 応答）: 21-3 案のままだと ① 補足で真相の核心を言う（「はい。教え子たちの体重です」）② 感想コメントへのお礼で正体をほのめかす（「犯人は玉ねぎでした」）③ 質問の形の正解推理（「〜ってこと？」）に「はい」で答えて宣言しない、の 3 系統の漏れが出た。上記プロンプトの 3 行（補足の範囲・お礼で触れない・質問形でも推理扱い）はその対策で、再実行で ①② は解消、③ は 10 問中 1 問で残る（人間ゲートで反復）。残る不一致は「〜は重要ですか」への「いいえ」と「関係ありません」の揺れで、意味上は同等（probe_test.py の機械判定は同義扱い）
  • フォールバック: OpenAI 呼び出し失敗（タイムアウト・5xx・キー未設定）は固定文言「『はい / いいえ』で答えられる質問をコメントしてね！」を返す PoC の挙動を踏襲するが、SQS 経由の再試行が先（stacks.html 3.6）。固定文言は最終試行でのみ使い、DLQ 行きにしない

6. キャプションの作り方

キャプションはストックの caption フィールド（本文 + ハッシュタグ。#AIart 必須）に問題ごとに書き、caption_templates.template_text は {{caption}} の 1 行とする。SNS 投稿バッチは umigame_items から umigame 系プレースホルダ（{{caption}} / {{problem_text}} / {{hook}} / {{rule_text}}）を展開する（batch-flow.html 3.3 の decision。実装 21-5b）。

  • 構成（PoC の実例）: 「【ウミガメのスープ 第 N 問】」+ 問題文の再掲 + 遊び方（「はい / いいえ / 関係ない」で答えられる質問をコメントしてね。出題者のカメロックが全部返事します。正解が出るまで何度でもどうぞ）+ ハッシュタグ（#ウミガメのスープ #水平思考 #推理クイズ #なぞなぞ #謎解き #クイズ #AIart）。ただし問題番号「第 N 問」は書かない（ストックは LRU で消費され投稿順が確定しないため。PoC の表記は本番では使わない）
  • AI 開示: #AIart はストック側の必須項目として validate.py で検査する（テンプレートが {{caption}} のみのため、運用設計 3 の「テンプレートに含める」ルールの担保はストック検証に移る）。ナレーションは Amazon Polly のためクレジット表記は不要（VOICEVOX 時代の常設クレジット行は本セットにはない）
  • テンプレートを {{caption}} だけにする理由: ハッシュタグの固定部を分けると「問題固有のタグを足したい」ときに 2 箇所を見ることになり、素材項目 14 項目の表（セクション 4）とも食い違うため。固定尾部が必要になったらテンプレート側に足す（DDL 変更なし）

8. ナレーション・TTS（Amazon Polly Neural / Takumi）

決定（2026-09-04、21-2 人間ゲート）: TTS は Amazon Polly Neural・話者 Takumi・話速 125%。問題文とルールの間は 1.2 秒 VOICEVOX 3 話者（玄野武宏・白上虎太郎・冥鳴ひまり）と Polly 3 話者を BGM 合成で試聴し、Polly Takumi を採用。Polly の日本語男性声は Takumi のみ（Generative エンジンは日本語未対応）。採用によりキャプションのクレジット表記が不要になり、VOICEVOX Engine の起動も要らない。実測: 問題文 78 字 + ルール 37 字を 125% で 17.8 秒（24 秒尺に対して余裕あり）。
  • 読み上げる文: 冒頭に narration.problem → 1.2 秒 → narration.rule の 2 cue だけ（吹き出しと同期させない。21-1 ②）。開始は 0.5 秒（15 フレーム）、2 cue + 間の合計は 21 秒以内（継ぎ目 708 フレームに掛からない予算。方式設計書 8.3）
  • 実行: ビルド時にローカルで scripts/narration_polly.py（~/.aws の資格情報で polly:SynthesizeSpeech。新規の Secret は不要）。アダプタは差し替え可能な形にし、VOICEVOX 版（narration.py）は残す（21-2 申し送り）。費用は Neural 100 万字あたり数ドル・1 問 120 字のため無視できる
  • 予算検査: cue の実測長が予算を超えたらビルドエラー（問題文を削る）。pref-ranking-1 の予測長 / 実測長の許容差（0.08 秒）は 12 秒級の cue では足りないため、cue 長に比例した許容差にする（21-2 所見）

10. コメント自動返信の運用

コメント時の処理は投稿時（既存 ECS + Aurora）と完全に分離し、Aurora を一切使わない。S3 の問題スナップショットを media_id キーの読み取り専用データストアとして使う（アイデア詳細 4）。インフラの構成（Function URL → Webhook Lambda → SQS FIFO + DLQ → Reply Lambda → S3 / OpenAI / Graph API。VPC 外・NAT 不要）は stacks.html 3.6、監視は workflow.html 8、Secret は security.html 1.3 が正。本節はアプリの振る舞いと運用ルールを書く。

10.1 1 日の動き

時間帯流れAurora
20:00 リール投稿画像生成 SFN（ストック LRU → 事前動画取得 → umigame_items INSERT）→ SNS 投稿 SFN（キャプション展開 → publish）→ publish 成功直後に problems/{media_id}.json を S3 へ出力（10.2）起動（従来どおり）→ 0 ACU へ

10.2 投稿後スナップショット problems/{media_id}.json

SNS 投稿バッチは batch_sets.problem_snapshot_enabled=1 のセットについて、リール行が success に達した直後に S3 assets/{set_code}/problems/{media_id}.json を PUT し、umigame_items.snapshot_s3_key / snapshot_written_at に記録する（共通フローの拡張ポイント = batch-flow.html 3.3 手順 6。データは data-model.html 4.14）。media_id は posts.platform_post_id（media_publish の応答 id）。

  "set_code": "umigame-soup-1",
  "media_id": "17912345678901234",
  "content_key": "001-lighthouse-letter",
  "posted_at": "2026-09-20T11:00:12Z",
  "problem_text": "……なぜ？",
  "truth": "……",

  • スナップショットの出力失敗は投稿失敗にしない（投稿は成功しているため posts.status は success のまま）。snapshot_s3_key が NULL の行を運用の確認クエリで拾い、手動で再出力する（content/umigame-stock/.../tools/write_snapshot.py を 21-5b で用意）。スナップショットが無い投稿へのコメントは Reply Lambda が S3 404 として返信せずログのみ残す（DLQ に入れない）
  • プレフィックス assets/…/problems/ は 30 日ライフサイクルの対象外（images/ videos/ 限定）のため、投稿済み問題は残り続ける = 翌日以降のコメントにも答えられる

10.3 返信の振る舞い（MVP スコープ）

  • 返信する: 自アカウントのリールへのコメントと、そのスレッドへの返信（parent_id 付き。推理の続きであることが多い）。判定はすべて AI 出題者プロンプト（5.1）に委ねる
  • 返信しない: 自分の返信（from.id == ig_user_id。無限ループ防止）/ プロンプトが NO_REPLY を返したコメント / スナップショットの無い media_id（本セット以外の投稿・出力失敗）
  • 作らないもの（アイデア詳細 7）: ユーザーごとの質問回数制限・コメント回数の DB 管理・禁止ワード DB・ルールベース判定・会話状態管理・Lambda メモリキャッシュ・コメント処理からの Aurora アクセス・翌日の解答編リール。将来のゲーム化構想を理由に状態管理を先行実装しない（ステートレス方針）
  • 重複返信の抑止: Meta Webhook は同一イベントを再送しうるため、SQS FIFO の重複排除 ID に comment_id を使う（5 分窓）。窓外の再送で二重返信が起きる可能性は許容する（stacks.html 3.6 の decision）

10.4 利用上限・費用

  • 上限は 2 段（21-1 ⑤）: ① OpenAI 側のプロジェクト月額予算上限 ② Reply Lambda の予約同時実行数（初期値 2。SQS が吸収するため取りこぼしにならず、上限到達時は返信が遅れるだけ）
  • 試算の枠組み: 返信 1 件 = 入力 600 トークン前後（問題文・真相・確定事実シート・ルール・質問）+ 出力 30 トークン程度。月 6,000 件（1 日 200 コメント）で入力 3.6M・出力 0.2M トークン。事業戦略書 3.1 の費目「コメント自動返信の LLM API（従量のみ・月数百円規模）」の範囲。単価確認後に外れていれば 21-6 で戦略書を直す。AWS 側（Lambda・SQS・S3 GET 月 6,000 回・CloudWatch）は無料枠内〜数十円
  • モデルはプローブテスト後、本番稼働まで固定。差し替えは Secret ではなく Lambda の環境変数（OPENAI_MODEL）で行う

10.5 監視・運用

  • DLQ アラーム（acps-prod-comment-reply-dlq-messages。DLQ の可視メッセージ数 ≥ 1）が初期版の唯一の能動監視。通知が来たら DLQ のメッセージ本文（コメント id・media_id）と Reply Lambda のログで原因を見る（OpenAI 障害 / Graph API のトークン失効 / スナップショット欠落）。復旧後に DLQ → 元キューへ再駆動（SQS コンソールの「DLQ 再処理」）。手順は infra/operation.html 4.1
  • トークン: コメント返信用の長期トークン（Instagram ログイン方式）は 60 日で失効する。初期版は投稿用トークンと同じく手動更新とし、失効日は token_expires_at を Secret に持たせて 運用設計 5.4 のリマインド運用に載せる。自動リフレッシュ（GET /refresh_access_token）の要否は開発計画の設計課題（2026-09-04）で追う
  • ステージング面: PoC 資材（Meta アプリ + test_tkghr + 同一コードのステージング面スタック）を恒久利用し、プロンプト改訂・Lambda 改修は必ずステージング面で実コメントを打ってから本番の Webhook 先を切り替える
  • コメント欄の目視: 稼働初期（2 週間）は毎日コメント欄を目視し、ネタバレ回答・矛盾回答・不適切な返信がないかを確認する。問題があればストックを is_active=0 にし、プロンプト（5.1）を直してステージングで再検証する。週次補充スキル（21-8）にチェック項目として組み込む

11. 失敗時ポリシー

  • 投稿側は共通フローどおり（batch-flow.html 3.2 / operation.html 4）。事前動画の取得失敗・ストック 0 件はフェイルラウド（縮退しない）。1 日 1 回のため 1 回の失敗はその日の投稿の欠落に留まる。当日リカバリの判断は共通課題（設計課題リスト 2026-07-26）に従う
  • スナップショット出力の失敗は投稿失敗にせず、NULL 行の確認クエリと手動再出力で回復する（10.2）
  • コメント側: Reply Lambda の失敗は SQS の再試行（最大 3 回）→ DLQ → アラーム。返信が遅れる・付かないことはあっても投稿には影響しない。Webhook Lambda は署名検証に失敗した要求を 401 で拒否し、正常受信は SQS へ入れた時点で 200 を返す（Meta の再送を招かないため、enqueue 失敗以外は 200）
  • OpenAI の長期障害: 予約同時実行数と SQS の保持期間（4 日）内なら復旧後に自動で返信が付く。それを超えた分は DLQ から手動で再駆動するか、古すぎれば破棄する（返信の鮮度を優先）
