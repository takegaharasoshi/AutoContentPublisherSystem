Claude Code のループ / ゴール系スキルを開発プロセスに組み込む

本書の位置づけ（設計書に非ず） 採用判断のための検討記録。ここに書いた組み込み案・テンプレート文・ガードレールは暫定であり、運用ルールの正ではない。採用が決まったら CLAUDE.md（git 運用・Codex 連携）、補充スキル（.claude/skills/*-stock-replenish/）、docs/plans/index.html（並行作業ルール）へ落とし込み、そこで確定する。

1. 一言で

Claude Code の /goal（完了条件を宣言して到達まで自走）と /loop（時間ベースの反復。引数なしなら .claude/loop.md を読んで自走）を、本プロジェクトの「ステップ実行」「夜間のストック整備」「常駐の見回り」に組み込み、人間が張り付く時間を減らして開発速度を上げる。実行環境はローカル CLI（WSL）で端末は常時起動できる。Routines（クラウド無人実行）は今回のスコープ外。

2. 機能の事実（公式ドキュメント・CHANGELOG で確認済み）

機能何をするか押さえるべき仕様
/goal <条件>
（v2.1.139〜）		完了条件を宣言し、各ターン末に Haiku が会話ログだけを見て「達成 / 未達 / 不可能」を判定。未達なら続行判定はコマンドを実行しない（証跡を会話に出させる必要がある）。条件は 4,000 字まで。or stop after N turns がソフト上限として機能。数ターン tool 未使用で警告停止。権限モードは変えない。claude -p "/goal ..." で headless 実行可。/goal clear で解除。連続 8 回ブロックで強制解除
/loop <間隔> <prompt>
（v2.1.71〜）		固定間隔で prompt を再実行（内部は cron）セッションが開いている間だけ動く。7 日で失効。Esc で起床を取消
/loop <prompt>自己ペース。毎回 1 分〜1 時間の次回間隔を Claude が決め、終わったら自分で停止停止条件は prompt 内に書く（例: 「5 回連続 green まで」）
/loop（引数なし）内蔵の保守 prompt、または .claude/loop.md（> ~/.claude/loop.md）を読んで自走。既定は「未完作業の継続 → PR の CI / レビュー / コンフリクト対応 → バグハント・簡素化。新規着手はしない」loop.md は構造自由・25,000 bytes で切詰・編集は次イテレーションから反映。/usage に Loops の内訳が出る

役割分担: /loop は時間駆動（見守り・定期）、/goal は条件駆動（1 タスクの完走）。両者は「timer を外側・condition を内側・skill を最内」に重ねるのがコミュニティの定石。

3. 実践者の使い方（X・Zenn・GitHub の二次情報。2026-09 時点）

取得制約 X / Reddit / Zenn 本体は本セッションの環境から直接取得できず、GitHub 上のキュレーション（serenakeyitan/awesome-agent-loops 等）と検索スニペット経由の二次情報。パターンの分類は一次情報を優先し、投稿の細部は要再確認。
#パターン典型例本プロジェクトへの示唆
P1テスト / lint が通るまで /goal（最も共有が多い）/goal all tests pass and lint is clean — stop after 20 turns。API 移行を「全ファイルが v2 を import・tests pass・typecheck clean」で宣言し「マルチエージェント構成より単一 /goal が良かった」との報告も開発レーンのステップ実行にそのまま当てはまる。完了条件 = 「pytest 全パス + 設計書更新 + コミット済み」
P2夜間の自走ビルド・QA を /loop 30m 〜 2hestie 木村氏: 移行後の QA を「テスト計画 → Playwright 実行 → 差分修正 → push → 進捗をファイル追記」で一晩完走。green_tea: /loop 2h /evolve で 1 機能ずつ実装 → テスト → commit「明確なゴール + 人間判断の排除 + 進捗ファイル」が要点。ストック補充の「レビュー提示直前まで」を夜間に回す型
P3引数なし /loop + loop.md を「現場監督（foreman）」にするmoai-adk: 毎回 1 カード・冪等・報告のみ（AskUserQuestion 不可前提）・スキル欠落時は自己停止。dominno / cobusgreyling: 信頼レベル L1（報告のみ）→ L2（実装者 + 別検証者）→ L3（無人）を loop.md に宣言し、denylist（auth / secrets / infra / CI / migrations）を置く「セッションを跨いで自走」に最も近い型。本プロジェクトでは計画書・バックログ・在庫水位が「カンバン」に相当する
P4PR / CI の見守りを /loop 10m/loop 10m run gh pr checks 1234; if all pass ...、/loop 20m /review-pr 1234push 後の CodePipeline 完走待ちがこれ。最小の導入
P5大型リファクタを /goal + サブエージェント専用ブランチ・1 単位 1 コミット・レビュア通過必須・auto-merge しない、をセットで運用Codex 委譲と組み合わせる型（Claude = 監督、Codex = 作業者、/goal = 判定）

3.1 実践者が挙げる落とし穴

  • 「main で /goal は自殺行為」: 無人実行はブランチ / worktree で。本プロジェクトは「コミット即 push main」ルールなので、無人区間では push の扱いを決める必要がある（セクション 5）
  • context rot: /goal は Ralph loop の「外部オラクル」を内蔵化したものだが、イテレーションごとに context を捨てないので長時間タスクで劣化する。長い作業は「1 ステップ 1 ゴール」に刻むか、シェルの while ループで claude -p "/goal ..." を回して都度 context を捨てる
  • 判定できない条件は永遠に未達: 未登録のスキル名を条件に書いて 30 回超ループした報告（#58348）。「レビューが終わった」のような人間判断も同類。決定的に検証できる条件だけ書き、証跡（テスト出力・件数）を会話に出させる
  • 30 行超のゴール文で evaluator が落ちる（#58192。/goal clear で復旧）。トークン / 時間の予算機能は両者とも未搭載（要望 #56085）。「Unattended loops make unattended mistakes」
  • 裸 /loop が loop.md を無視した版があった（#47883。回避: /loop follow .claude/loop.md）

4. 本プロジェクトへの組み込み案（第 2 巡）

第 1 巡の「ポーリングだけ」から広げ、実践パターンに沿って 4 案に再編。導入は信頼レベル順（L1 報告のみ → L2 機械工程まで → L3 無人）で段階的に上げる。

案型内容レーン人間が残る点
A. ステップ実行の標準ラッパーP1 / P5開発レーンの各ステップを /goal で起動する。テンプレ: /goal <ステップ番号> の実装が完了: pytest 全パス（出力を貼る）・cdk synth 成功・関連設計書の更新・日本語メッセージでコミット済み。cdk deploy / DDL 適用 / publish は行わない。or stop after 20 turns。実装は従来どおり Codex 委譲（Claude = 監督、/goal = 判定）開発AWS 稼働確認（現行どおり）。push の扱いは論点 1
B. 夜間ストック整備P2補充スキルの「レビュー提示直前まで」を 1 本の /goal に: /goal quiz 朝スロット 7 問がリサーチ → 執筆 → validate / verify_logic 全パス → review 用にまとめ済み。投入（publish / apply）・S3 配置は禁止。or stop after 30 turns。翌朝レビュー後に第 2 ゴール「承認済み N 件を投入 → ビルド → unbuilt=0 → S3 配置 → 記録更新」セット（並行可）1 問ずつのレビュー・review.html 承認・動画全数レビュー（現行どおり）
C. 常駐の見回り（loop.md）P3.claude/loop.md を書き、引数なし /loop で自走。L1 から開始: 在庫水位（quiz 3 組 × 7 問下限・ranking 14 件）、CodePipeline 状態、アイデア inbox の滞留、計画書 ⇄ 記録の整合を確認して報告ファイルに追記するだけ。L2 で「承認済みストックのビルド・配置」など判断ゼロのセットレーン工程を許可。開発レーンの変更は permanent denylist（レーン 1 セッション制約のため）アイデア / セット報告を読んで次の指示を出す
D. CodePipeline 完走待ちP4/loop 2m または /goal 該当パイプラインが Succeeded かつタスク定義の新リビジョンが登録済み。CLAUDE.md の git 運用ルールに定型文として 1 行追加開発なし

5. ガードレール（採用時に CLAUDE.md / loop.md へ落とす候補）

  • denylist: cdk deploy、本番 DDL 適用、publish.py / apply_aurora.py の投入、SNS 投稿、Secrets への接触、docs/plans/ のルール変更。ゴール文と loop.md の両方に明記
  • 証跡を会話に出す: pytest の要約行・件数クエリの結果・unbuilt=0 の出力をそのまま貼らせる（evaluator は会話しか見ない）
  • 上限: 必ず or stop after N turns。夜間は Ctrl+C できる端末で、朝一で /usage の Loops 内訳を見る
  • レーン規律: ゴール文の冒頭でレーンを宣言。開発レーンのゴール実行中はユーザー自身も開発レーンを触らない（1 セッション制約）
  • 1 ステップ 1 ゴール: 大きなフェーズを 1 本のゴールにしない（context rot）

6. 未決の論点（第 3 巡で決める）

  1. 無人区間の push: 「コミット即 push main」ルールと「main で無人 /goal は危険」の衝突。候補は (a) 現行どおり push まで（稼働確認は現行と同じくユーザー）、(b) services/ shared/ infra/ database/ を触るゴールは「コミットまで・push は差分確認後」に止める、(c) 作業ブランチに push してユーザーが main へ取り込む。推奨は (b): docs だけのゴールは (a) でよい
  2. 最初に試す案: 推奨は D（最小）→ A（16-12 の DDL・ビュー生成が自然な初回）→ B（quiz か ranking）→ C（loop.md は L1 から）の順。ただし「想定していた使い方」が C（常駐自走）なら C-L1 を先に始めても損はない（報告のみで安全）
  3. B の対象: quiz（1 問ずつレビュー・朝 / 夜スロット）と ranking（review.html 一括承認・一次データのパース検証あり）のどちらが夜間自走に向くか。機械検証が厚い ranking の方が「レビュー提示直前まで」の自走価値が高いと見る
