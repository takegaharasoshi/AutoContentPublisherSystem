本書の位置づけ（設計書に非ず） 採用判断のための検討記録。ここに書いた組み込み案・テンプレート文・ガードレールは暫定であり、運用ルールの正ではない。採用が決まったら CLAUDE.md（git 運用・Codex 連携）、補充スキル（.claude/skills/*-stock-replenish/）、docs/plans/index.html（並行作業ルール）へ落とし込み、そこで確定する。

1. 一言で

Claude Code の /goal（完了条件を宣言して到達まで自走）と /loop（時間ベースの反復。引数なしなら .claude/loop.md を読んで自走）を、本プロジェクトの「ステップ実行」「夜間のストック整備」「常駐の見回り」に組み込み、人間が張り付く時間を減らして開発速度を上げる。実行環境はローカル CLI（WSL）で端末は常時起動できる。Routines（クラウド無人実行）は今回のスコープ外。

2. 機能の事実（公式ドキュメント・CHANGELOG で確認済み）

機能何をするか押さえるべき仕様
/goal <条件>
（v2.1.139〜）		完了条件を宣言し、各ターン末に Haiku が会話ログだけを見て「達成 / 未達 / 不可能」を判定。未達なら続行判定はコマンドを実行しない（証跡を会話に出させる必要がある）。条件は 4,000 字まで。or stop after N turns がソフト上限として機能。数ターン tool 未使用で警告停止。権限モードは変えない。claude -p "/goal ..." で headless 実行可。/goal clear で解除。連続 8 回ブロックで強制解除
/loop <間隔> <prompt>
（v2.1.71〜）		固定間隔で prompt を再実行（内部は cron）セッションが開いている間だけ動く。7 日で失効。Esc で起床を取消
/loop <prompt>自己ペース。毎回 1 分〜1 時間の次回間隔を Claude が決め、終わったら自分で停止停止条件は prompt 内に書く（例: 「5 回連続 green まで」）
/loop（引数なし）内蔵の保守 prompt、または .claude/loop.md（> ~/.claude/loop.md）を読んで自走。既定は「未完作業の継続 → PR の CI / レビュー / コンフリクト対応 → バグハント・簡素化。新規着手はしない」loop.md は構造自由・25,000 bytes で切詰・編集は次イテレーションから反映。/usage に Loops の内訳が出る

役割分担: /loop は時間駆動（見守り・定期）、/goal は条件駆動（1 タスクの完走）。両者は「timer を外側・condition を内側・skill を最内」に重ねるのがコミュニティの定石。

3.1 実践者が挙げる落とし穴

  • 「main で /goal は自殺行為」: 無人実行はブランチ / worktree で。本プロジェクトは「コミット即 push main」ルールなので、無人区間では push の扱いを決める必要がある（セクション 5）
  • context rot: /goal は Ralph loop の「外部オラクル」を内蔵化したものだが、イテレーションごとに context を捨てないので長時間タスクで劣化する。長い作業は「1 ステップ 1 ゴール」に刻むか、シェルの while ループで claude -p "/goal ..." を回して都度 context を捨てる
  • 判定できない条件は永遠に未達: 未登録のスキル名を条件に書いて 30 回超ループした報告（#58348）。「レビューが終わった」のような人間判断も同類。決定的に検証できる条件だけ書き、証跡（テスト出力・件数）を会話に出させる
  • 30 行超のゴール文で evaluator が落ちる（#58192。/goal clear で復旧）。トークン / 時間の予算機能は両者とも未搭載（要望 #56085）。「Unattended loops make unattended mistakes」
  • 裸 /loop が loop.md を無視した版があった（#47883。回避: /loop follow .claude/loop.md）

4. 本プロジェクトへの組み込み案（第 2 巡）

第 1 巡の「ポーリングだけ」から広げ、実践パターンに沿って 4 案に再編。導入は信頼レベル順（L1 報告のみ → L2 機械工程まで → L3 無人）で段階的に上げる。

  • C（loop.md の常駐見回り）は不要として見送り。「セッションを跨ぐ自走」は本アイデアの対象外（Routines も対象外）
  • 無人区間の push: services/ shared/ infra/ database/ を触るゴールは「コミットまで。push は差分確認後」に止める。docs だけのゴールは現行どおり pull --rebase → push まで
  • 試す順: D → A → B

5. ガードレール（採用時に CLAUDE.md / スキルへ落とす候補）

  • denylist: cdk deploy、本番 DDL 適用、publish.py / apply_aurora.py の投入、SNS 投稿、Secrets への接触、docs/plans/ のルール変更。ゴール文と loop.md の両方に明記
  • 証跡を会話に出す: pytest の要約行・件数クエリの結果・unbuilt=0 の出力をそのまま貼らせる（evaluator は会話しか見ない）
  • 上限: 必ず or stop after N turns。夜間は Ctrl+C できる端末で、朝一で /usage の Loops 内訳を見る
  • レーン規律: ゴール文の冒頭でレーンを宣言。開発レーンのゴール実行中はユーザー自身も開発レーンを触らない（1 セッション制約）

7. 確実に実行される仕組み（起動点の設計）

前提となる事実（公式ドキュメントで確認） /goal は Claude 自身・スキル・フックからは起動できない。起動できるのはユーザーの入力（対話の /goal ...、headless の claude -p "/goal ..."）と、カスタムスラッシュコマンドの展開文に含めた /goal（公式上は有効。初回に実機確認する）。/loop も同じく Claude からは起動できない。したがって「確実に実行される」とは「Claude が勝手にやる」ではなく、作業の入口を 1 つに絞り、その入口に /goal の定型行を埋め込み、goal が立つまで Claude が着手しない規律を持たせることで実現する。

計画書には how を書かない。計画書は「何をやるか」の置き場で、「どう起動するか」を毎ステップに書くと肥大化する（Phase 18 の肥大化防止ルールにも反する）。development-plan.html の「進め方の方針」に 1 行（ステップ実行は /step 経由、手順は CLAUDE.md）を置くだけにする。「計画書を起こすためのスキル」は不要: 計画書は壁打ちで起こす現行運用のままでよく、必要なのは計画書を読む側の着手スキルである。

7.1 ゴール文のテンプレ（暫定。採用時にスキル / CLAUDE.md へ落として確定）

A: 開発レーンのステップ実行

/goal 開発レーン・ステップ <番号> <名称>。完了条件: (1) 計画書の「内容」にある成果物が揃う、(2) 該当サービスの pytest が全パス（要約行を会話に貼る）、(3) infra/ を触った場合は cdk synth が成功、(4) 関連設計書と計画書（チェック・完了日・要点）を更新、(5) 日本語メッセージでコミット済み。services/ shared/ infra/ database/ を触った場合は push せず、差分を提示して確認待ちで終える。docs のみなら pull --rebase → push まで行う。cdk deploy・本番 DDL 適用・publish は行わない。or stop after 20 turns

A′: セットレーンのステップ実行（セット計画書の進行中ステップ。例: logic-training-1 改修 R-1-2 / R-1-4）

/goal セットレーン <set_code>・ステップ <番号> <名称>。完了条件: (1) セット計画書の「内容」にある成果物が揃う、(2) ビルド・検証ツールの出力（build.py --dry-run / validate 等、該当するもの）を会話に貼る、(3) セット計画書（チェック・完了日・要点）とセット記録を更新、(4) 日本語メッセージでコミットし pull --rebase → push まで行う（content/ と docs/plans/<set> は CodePipeline を起動しないため push まで可）。S3 差し替え・Aurora / ローカル DB の更新・SNS 投稿設定の変更は行わず、レビュー用の成果物（プレビュー動画・review.html）を提示して終える。services/ shared/ infra/ database/ に触る必要が出たら手を止めて報告する（開発レーン行き）。or stop after 20 turns

セットレーンでは「配置（S3・DB 差し替え）」を人間レビュー後の別ゴールに切る（B の G3 と同じ考え方）。ユーザー判断のステップ（R-1-1 の目視・R-1-3 の go / no-go）は goal にしない。

B: quiz 週次補充（3 本。人間レビューの前後で切る）

/goal セットレーン logic-training-1・週次補充 G1。完了条件: 朝・夜スロットの在庫確認クエリで不足数を確認し（出力を貼る）、不足分（各スロット最大 7 問）のリサーチ → 執筆 → スキル セクション 4 の機械検証が全問パス（出力を貼る）→ 1 問ずつ提示できる状態。投入・S3 配置・Aurora 更新は行わない。人間レビューは開始しない。or stop after 30 turns

/goal セットレーン logic-training-1・週次補充 G2。完了条件: レビューで承認された N 問を投入（セクション 6）→ export_prompts → イラスト生成（文字混入・1536x1024 の自己確認込み）→ intake → build → review_sheet で work/review.html を生成。配置（publish）は行わない。or stop after 30 turns

/goal セットレーン logic-training-1・週次補充 G3。完了条件: approved.txt の承認 id を publish（dry-run → 本実行）→ Aurora 適用の更新行数 = 承認件数（出力を貼る）→ 在庫確認クエリで unbuilt = 0（出力を貼る）→ ツール・台帳の変更をコミット・push・セット記録を更新。or stop after 15 turns

D: CodePipeline 完走待ち

/goal push したコミット <sha> について、触ったサービスの CodePipeline が Succeeded になり、対応するタスク定義の新リビジョンが登録されたことを aws cli の出力を貼って確認する。失敗した場合は失敗ステージとログ要約を提示して停止する（自分で修正・再 push しない）。or stop after 15 turns
