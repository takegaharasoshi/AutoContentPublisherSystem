## 要旨

整理された現在形は [claude-code-loop-goal-skills.html](claude-code-loop-goal-skills.html) を参照（機能の事実・実践者の使い方 5 パターン・組み込み案 A〜D・ガードレール・未決の論点）。

一言で: `/goal`（完了条件宣言）と `/loop`（時間反復・loop.md 自走）を「ステップ実行の標準ラッパー」「夜間ストック整備」「常駐の見回り」「CodePipeline 待ち」の 4 案として組み込む。実行環境はローカル CLI（WSL）・端末常時起動、Routines はスコープ外。第 3 巡で「無人区間の push の扱い」と「最初に試す案」を決める。

## 前提条件・再検討トリガー

- **実行環境（2026-09-02 確定）**: ローカル CLI（WSL）が主、端末を開けっぱなしにできる。`/loop` `/goal` はセッション存続前提なので成立する。**Routines は今回のスコープ外**（ユーザー決定）
- **`/goal` の完了条件は決定的に検証できる形にし、証跡を会話に出させる**（evaluator はコマンドを実行せず会話しか見ない）。人間判断を含む条件・未登録スキル名は永遠に未達になる
- **無人区間の push の扱いを決める**（詳細 HTML セクション 6 論点 1）。決まるまで A 案は開始しない
- **並行作業ルールとの関係**: 開発レーンのゴール実行中はユーザー自身も開発レーンを触らない。loop.md は開発レーンの変更を permanent denylist にする。確認が確実になれば「開発レーン 1 本 = パイプライン確認の混線防止」の緩和材料になり得るが、レーンをまたぐ論点なので採用時に開発レーンの設計課題リストへ記録する
- **後続段階の再検討トリガー**: Routines は「セッションを跨ぐ無人実行」が必要になった時点で再検討（在庫水位の週次判定、16-12 確定後の週次 KPI 集計）
- **作らないもの**: 補充の完全無人化（人間レビューが規律）、AWS 稼働確認の代替（目視が仕様）

## 壁打ち記録

### 2026-09-02（第 1 巡: 対象確定と組み込み先の棚卸し）

- **論点 1: 「ゴール」スキルの正体** — 公式ドキュメントで `/goal` の実在を確認。`/loop` が時間ベース、`/goal` が条件ベース、Routines がクラウド無人実行と役割が分かれており、「セッションを跨いで自走」は `/loop` `/goal` ではなく Routines の領分。要旨・前提条件に整理済み
- **論点 2: 組み込み先の棚卸し** — プロジェクトの作業プロセスから「待ち・ポーリング・定型反復・完了条件の複数ラウンド」を洗い出した。人間判断ゼロで機械判定できるのは (a) CodePipeline 完走待ち、(b) 補充スキル内の画像再生成・モーラ予算・`unbuilt=0` の 3 ループ。人間判断が埋まるのは 1 問ずつのレビュー・review.html 承認・動画全数レビュー・AWS 稼働確認・音源ミュート確認で、これらは無人化しない（リマインドまで）
- **判断**: 組み込みは「人間判断が埋まっていない区間」に限定し、3 段（CodePipeline 待ち → 補充スキルの機械判定区間 → Routines の判定 + 通知）で考える。トークン面の懸念は小さく、本体のリスクは無人自走による規律違反（承認前の投入・push）
- **MVP 案**: 第 1 段 = 次に `services/` `shared/` へ push する機会に `/goal`（または `/loop 2m`）でパイプライン完走確認を試し、うまくいけば CLAUDE.md の git 運用ルールに定型文として 1 行追加（開発レーンの作業 → 待機経由）。第 2 段 = quiz / ranking の補充スキルに `/goal` の完了条件文を組み込む（セットレーンで完結するため、セット計画書の進行中ステップへ直接展開可）
- **積み残し（ユーザーに確認する）**: ① 普段の実行環境（ローカル CLI か web か）と端末を開けっぱなしにできるか、② Routines から Aurora / AWS に到達させる意思があるか（認証情報をクラウド側に置くことの是非）、③ 第 2 段は quiz と ranking のどちらから試すか、④ 第 1 段を「試してから決める（醸成中のまま）」か「決めて待機に落とす」か
- **着地**: 醸成中のまま（積み残し①〜④の回答で第 2 巡へ）

### 2026-09-02（第 2 巡: 実践パターンの取り込みと組み込み案の再編）

- **前提の確定**: 実行環境はローカル CLI（WSL）・端末常時起動。Routines はスコープ外（ユーザー決定）。第 1 巡の「セッションを跨ぐ自走 = Routines」は本アイデアから外れ、`/loop`（loop.md 自走）が「常駐」の担い手になる
- **論点: 第 1 巡は使い方の想定がズレていた** — ポーリングに絞ったが、実践者の主用途は「`/goal` でテストが通るまで完走」「夜間の自走ビルド・QA」「loop.md を現場監督にした自走」。X・Zenn・GitHub の二次情報から 5 パターン（P1〜P5）と落とし穴（main で無人 /goal は危険・context rot・判定不能条件で永久ループ）を整理し、詳細 HTML へ昇格
- **判断**: 組み込み案を 4 案に再編 — A. ステップ実行の標準ラッパー（`/goal` + Codex 委譲）、B. 夜間ストック整備（レビュー提示直前まで）、C. 常駐の見回り（loop.md・L1 報告のみから）、D. CodePipeline 完走待ち。導入は信頼レベル L1 → L3 で段階的に。ガードレール（denylist・証跡・ターン上限・レーン宣言・1 ステップ 1 ゴール）を採用時の落とし込み候補として明文化
- **積み残し（第 3 巡）**: ① 無人区間の push（推奨: services/ 等を触るゴールはコミットまで、docs のみは push まで）、② 最初に試す案（推奨: D → A → B → C。想定が C なら C-L1 先行も可）、③ B の対象は quiz か ranking か（推奨: ranking）
- **着地**: 醸成中のまま（詳細 HTML 昇格済み）
