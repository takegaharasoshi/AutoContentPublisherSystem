## 要旨

Claude Code の `/loop`（時間ベースの反復）・`/goal`（完了条件を宣言して到達まで自走）・Routines（クラウド側で無人実行する定期ジョブ）を、単発利用ではなく本プロジェクトの開発プロセスに組み込み、「待ち」と「機械判定できる反復」を Claude に任せて開発速度を上げる。

2026-09-02 の壁打ち第 1 巡で、組み込み先を「人間の判断が埋まっていない区間」に限定する方針とし、候補を 3 段に整理した:

1. **push 後の CodePipeline 完走・タスク定義リビジョン確認**（CLAUDE.md の git 運用ルール）— 純粋なポーリングで人間判断ゼロ。`/loop` または `/goal` で無人化する第 1 候補
2. **週次ストック補充スキルの機械判定区間**（画像の文字混入・サイズ確認 → 再生成、モーラ予算超過 → 短縮 → 再ビルド、`unbuilt=0` まで）— `/goal` の完了条件として組み込む。人間レビュー（1 問ずつ・review.html・動画全数）はそのまま残し、ループは「レビュー提示直前まで」と「承認後の配置〜締め」の 2 区間に分割する
3. **Routines による定期の判定 + 通知**（在庫水位の週次確認、稼働確認待ち・音源ミュート確認のリマインド、16-12 確定後の週次 KPI 集計）— 実行環境から Aurora / AWS に届くかの確認待ち。判定と通知だけの軽量プロンプトに留め、執筆・投入は無人化しない

評価軸は「速度向上」対「トークン消費・レビュー負荷・無人自走の暴走リスク」。ポーリング 1 回は数百トークン、`/goal` の条件判定は Haiku で軽いため、コストよりも「承認前に投入・push しない規律をループのプロンプトに明記できるか」がガードレールの本体。

事業コンテンツではなく開発プロセス（作業環境）の改善アイデア。同系統: [voice-input-tooling](voice-input-tooling.md)（音声入力ツール導入）。

## 前提条件・再検討トリガー

- **対象の確定（2026-09-02 済）**: ループ = `/loop`（固定間隔 `/loop 5m <prompt>` or 自動間隔 `/loop <prompt>`。セッション内に閉じ、7 日で失効。CLI・web・リモートとも可）。ゴール = `/goal <完了条件>`（各ターン末に Haiku が条件を判定し、満たすまで継続。再開時に復元、`-p` で非対話一括実行可）。加えて Routines（Anthropic クラウドで cron / API / GitHub イベント起動、最小間隔 1 時間、発火ごとに新規セッション、許可プロンプトなし）が「セッションを跨いで無人で回す」用途の実体
- **実行環境の確認（未）**: `/loop` `/goal` はセッションが生きている間しか動かない。普段の作業がローカル CLI（WSL）か web かで「端末を開けっぱなしにできるか」が変わる。Routines は独立セッションなので、そこから Aurora（VPC 内）・AWS CLI・Instagram Graph API に到達できるか（認証情報の受け渡し）を確認しないと候補 3 は成立しない
- **`/goal` の完了条件は機械検証可能な形にする**: 判定は小型モデルが行うため、「パイプラインが Succeeded」「`unbuilt=0`」のようにコマンド出力で白黒がつく条件に限定する。「レビューが終わった」のような人間判断を含む条件は置かない
- **並行作業ルールとの関係**: 候補 1 のループ中は開発レーンを占有し続ける（開発レーンは常に 1 セッション）。逆に、確認が確実になれば「開発レーンを 1 本に絞る理由 = パイプライン確認の混線防止」（`docs/plans/index.html` セクション 2）の緩和材料になり得る — これはレーンをまたぐ論点なので、採用時に開発レーンの設計課題リストへ記録する
- **後続段階の再検討トリガー**: 16-12（指標セット確定）完了後に「週次 KPI 集計 + 計画書 KPI 欄更新」の Routines 化を再検討する（データ収集は EventBridge で自動化済み、欠けているのは集計・転記のみ）
- **作らないもの**: Routines による補充の完全無人化（人間レビューが規律として埋まっているため）、`/loop` による稼働確認の代替（ユーザーの目視が仕様）

## 壁打ち記録

### 2026-09-02（第 1 巡: 対象確定と組み込み先の棚卸し）

- **論点 1: 「ゴール」スキルの正体** — 公式ドキュメントで `/goal` の実在を確認。`/loop` が時間ベース、`/goal` が条件ベース、Routines がクラウド無人実行と役割が分かれており、「セッションを跨いで自走」は `/loop` `/goal` ではなく Routines の領分。要旨・前提条件に整理済み
- **論点 2: 組み込み先の棚卸し** — プロジェクトの作業プロセスから「待ち・ポーリング・定型反復・完了条件の複数ラウンド」を洗い出した。人間判断ゼロで機械判定できるのは (a) CodePipeline 完走待ち、(b) 補充スキル内の画像再生成・モーラ予算・`unbuilt=0` の 3 ループ。人間判断が埋まるのは 1 問ずつのレビュー・review.html 承認・動画全数レビュー・AWS 稼働確認・音源ミュート確認で、これらは無人化しない（リマインドまで）
- **判断**: 組み込みは「人間判断が埋まっていない区間」に限定し、3 段（CodePipeline 待ち → 補充スキルの機械判定区間 → Routines の判定 + 通知）で考える。トークン面の懸念は小さく、本体のリスクは無人自走による規律違反（承認前の投入・push）
- **MVP 案**: 第 1 段 = 次に `services/` `shared/` へ push する機会に `/goal`（または `/loop 2m`）でパイプライン完走確認を試し、うまくいけば CLAUDE.md の git 運用ルールに定型文として 1 行追加（開発レーンの作業 → 待機経由）。第 2 段 = quiz / ranking の補充スキルに `/goal` の完了条件文を組み込む（セットレーンで完結するため、セット計画書の進行中ステップへ直接展開可）
- **積み残し（ユーザーに確認する）**: ① 普段の実行環境（ローカル CLI か web か）と端末を開けっぱなしにできるか、② Routines から Aurora / AWS に到達させる意思があるか（認証情報をクラウド側に置くことの是非）、③ 第 2 段は quiz と ranking のどちらから試すか、④ 第 1 段を「試してから決める（醸成中のまま）」か「決めて待機に落とす」か
- **着地**: 醸成中のまま（積み残し①〜④の回答で第 2 巡へ）
