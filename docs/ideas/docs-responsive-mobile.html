設計書 HTML のスマホ閲覧対応

採用方針確定: 2026-09-20 / 採用・転記: 2026-09-21 / 壁打ち記録
位置づけ（設計書に非ず）採用判断のための検討記録。ユーザーが方針一式に合意し、2026-09-21 に開発計画 Phase 24へ転記して採用で着地した。以降の議論・実施記録は開発計画と開発記録が正。実装方式・詳細な列幅は開発レーンで設計 Fix する。

1. 目的と範囲

スマホ幅に表が押し込まれ、細い列の折り返しで極端に縦長になる問題を解消する。一般の表は列幅を保ち、課題・アイデア一覧は情報のまとまりごとに読めるカードにする。

  • アーカイブを除く設計書 HTML 全体に一般表の対策を適用。2026-09-20 のソース確認時点で 44 ページ・196 表。実装開始時に再集計する（本詳細ページの追加などで増えるため、固定の期待件数にしない）。共通 CSS・viewport meta は当時の全 44 ページに存在。
  • 共通の表示規則を基本に、合わない表だけ個別調整する。本文の文字サイズは維持し、狭い画面では左右余白を少し減らす。
  • 計画体系・計画書内の一般表の列幅対策は対象。計画書の構成・ステップ表示の再設計は PC でも見づらいという別課題 I-036 で扱い、今回には含めない。
  • 配信経路の変更、図・目次の全面改修、図の描き直し、専用拡大機能は対象外。今回の変更でページ全体が横にはみ出す箇所は直す。

2. 一般の表

  • 項目名・日付など短い列はなるべく折り返さず、説明列は文章として読める幅を確保する。長文は適度に折り返し、収まらない分は表の中だけ横スクロールする。
  • 短い表は画面幅に収める。全表に一律の固定幅や全セル折り返し禁止を適用する方針にはしない。
  • 文字縮小・文章省略で収めない。元から長い内容の行高まで短くすることは保証せず、狭い列への圧縮による過剰な折り返しを防ぐ。
  • 先頭列固定は初期対応に含めない。列幅改善後に必要性が分かった場合に再検討する。

3. 課題・アイデア一覧のカード

切り替えの初期値は画面幅 768 CSS px 未満。試作で境界を調整する場合は理由と検証結果を記録する。PC では表形式を維持する。

  • 課題: 各レーンの一覧とクローズ済み一覧。ID・課題の内容・状態・対応方針・トリガーを常時表示する。クローズ済みは状態・対応方針に相当する結果と根拠を表示する。対象パス・発生履歴・日付などは補足に置く。
  • アイデア: 「今動ける」「条件待ち」「クローズ」の全一覧。タイトル・状態・要旨・待機条件、クローズ済みの結果・採用先または見送り理由を、各一覧に存在する項目に応じて常時表示する。更新日・補足情報などは補足に置く。
  • 詳細ページ・壁打ち記録へのリンクは常時表示する。同じページの運用ルール説明表は一般表として扱う。
  • 既存項目・文面を使用し、独立した短い課題名の新設や要約の書き直しは必須にしない。

補足情報の操作

  • 「補足情報」は初期状態で閉じ、タップして開閉できる。複数カードを同時に開ける。開閉状態の保存は追加しない。
  • ブラウザー内検索で折りたたんだ補足情報を発見できることを確認する。課題 ID への直接リンクも維持する。
  • 独自検索・絞り込み・並べ替えは追加しない。

4. 更新・保守の方針

PC 用とスマホ用の文章を二重管理せず、同じ内容から表示を切り替える。行追加時にも同じ表示が適用される形とする。追加の表示処理が動かない場合にも元の表で読めるようにし、外部サービスへの依存は増やさない。

表示のための HTML 属性や共通のローカル資材が必要になる可能性はあるため、CSS だけで実現することは制約にしない。具体的な実装方法は、ブラウザー内検索・直接リンク・表示処理が動かない場合の読みやすさを満たすよう開発レーンで決める。

5. 確認基準

  • 代表ページ: 計画体系・事業戦略・課題一覧・アイデア一覧。
  • 幅: 360 / 390 / 430 CSS px、切り替え境界の前後（初期値なら 767 / 768 CSS px）、PC 1280 CSS px。
  • 全現役 HTML: 対象件数を記録し、上記の幅でページ全体の横はみ出しを機械確認する。リンク・参照先・アンカーと HTML の整合を確認し、既存不備と今回の差分を区別する。
  • 代表ページ: 長文・短い表・カード開閉・表内横スクロール・ライト／ダーク・PC の表表示を目視確認する。主要項目と詳細リンクが展開せず読めることを確認する。
  • 機能確認: 補足内にある語をブラウザー内検索で発見できること、課題 ID の直接リンク、複数カードの同時展開、追加の表示処理が動かない場合の表表示を確認する。
  • 最後にユーザーが普段使っているスマホで、表とカードの読みやすさ・横スクロール・開閉・補足情報の検索を確認する。使用した OS・ブラウザーを結果とともに記録する。

列の具体的な数値や検索を成立させる実装方式は設計・試作で決める事項であり、方針未決として残すものではない。既存不備や環境制約で確認できない項目は、証跡・影響を記録し、未確認のまま合格扱いにしない。

6. 開発レーンへの転記下書き

転記済み（2026-09-21）: 開発レーンの単独セッションで開発計画 Phase 24へ登録した。作業案 A は機械検証できる中間点で 24-1（一般表の列幅対策 + 検証ツール tools/docs_check.py）と 24-2（課題・アイデア一覧のカード化）に分割し（計画体系 5.1-4）、作業案 B は 24-3（ユーザー判断・ゴール対象外）とした。方針・確認基準は変更していない。着手は /step 24-1。

課題表の照合（2026-09-21 の転記時に再照合済み。該当は I-036 のみで、同課題のトリガーへ「Phase 24 の完了時にも照合」を追記）: I-036 は同梱しない（ユーザー指示により構成改善を分離済み）。I-030 は計画体系の並行作業ルールの課題で、表示変更とは別件のため同梱せず既存トリガーを維持。他の据え置き課題には今回の一般表・カード表示に直接該当するものなし。転記時には最新の課題表を再照合する。

5.1 チェック: 実装と機械確認を一つの工程とし、ユーザー実機確認は別ステップ・ゴール対象外にする。自セッション外の確認を実装の完了条件に含めない。実機確認は成果物の push 直後から実施可能で、後日の効果観察を待つ計画ではないため確認待ち項目は新設しない。共通資産の表示改修として開発レーンに集約し、I-036 や並行作業ルールの改訂に広げない。
