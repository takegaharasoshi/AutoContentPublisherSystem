## 要旨

開発・運用で見つかった課題を、アイデア体系と同じく「壁打ち → 回収タイミングを決める → トリガーで再判断」の動線に載せる仕組み（種別: 運用）。動機は 2026-09-04〜05 の logic-training-1 投稿停止（約 13 時間）。原因の一つは設計課題リストに 2026-07-22 の時点で恒久対策込みで書かれていたのに回収されなかった。

**3 巡目（2026-09-07）の現在形**: **課題体系 `docs/issues/` を、アイデア体系と並ぶ独立の体系として新設する**（3 巡目でピボット。理由は壁打ち記録参照）。開発レーン計画書の設計課題リストと各セット計画書のバックログは**廃止して `docs/issues/` へ移し**、置き場は「課題体系（両レーンの課題）+ 確認待ちリスト（計画書内・ステップ付随）」の 2 つに減る。中身は 7 点。

1. **構造（アイデア体系と同型・ただし正が逆）**: `docs/issues/index.html` が **ダッシュボード兼・唯一の正**（全課題 1 行ずつ。列 = 起票日 / レーン〔開発 or セット名〕/ 対象パス / 課題 / 対応方針 / ステータス / トリガー / 発生履歴 / 壁打ちリンク）。**壁打ちを始める課題だけ** `docs/issues/<slug>.md` を作り、壁打ち記録と整理された対応方針を置く（起票時にはファイルを作らない）。詳細 HTML は構成図が要るときだけ。ルールの正は index.html のセクション
2. **ステータス 4 つ**: 起票（対応方針未決）/ 据え置き（トリガー必須。主役）/ 展開済み（ステップ・フェーズへのリンク）/ 解消・受容（クローズ。受容 = 直さない・再判断もしないと決めたもの、理由付き）。**「未定」禁止**。解消・受容は記録ページ（`docs/issues/closed.html` か index 末尾）へ移す
3. **課題レーン**: `docs/issues/` 配下 + `.claude/skills/issue/` `.claude/skills/incident/` で閉じる作業は**常に並行可・宣言不要**（アイデアレーンと同じ）。セットレーンのセッションが開発レーン向けの課題をその場で起票できるようになる（現状はレーン越えのため起票文面の提示止まり）
4. **スキル 2 本**: `/issue`（起票 / 壁打ち / 棚卸し。`/idea` と同型で、壁打ちは終了規律で 据え置き〔トリガー更新〕/ 展開〔ステップ起票〕/ 受容 のどれかに着地）と `/incident`（障害対応。最初の工程で課題表と確認待ちを症状・パス・セット名で照合し「予言されていたか」を先に出す → 恒久対策込みで対処を判断 → 事象をセット記録へ → 発生履歴の更新・エスカレーション判定・新規起票）
5. **照合の入口 5 つ**: (a) `/step` 起動時に触るパスで課題表を照合（確認待ちの照合に追加）(b) 補充スキル起動時にセット名で照合 (c) `/incident` (d) **起票チェックリスト（`docs/plans/index.html` 5.1）に「課題表の照合」を追加**（アイデアの採用転記・フェーズ起票・セット改修起票のすべてで、触るパスに該当する据え置き課題を同梱するかトリガーを更新する）(e) 定期棚卸しは月次 KPI 転記とフェーズ・改修完了の節目に相乗り
6. **エスカレーション規則**: 「発生実績を見て判断」型のトリガーには回数を書く。既定は「1 回目 = 記録 + 再判断、2 回目 = 据え置き不可・起票必須」
7. **確認待ちリストとの関係**: 計画書内に残す（ステップ・レーンに紐づく短命の観察項目）。トリガーの書式と棚卸し節目は課題体系のルールを共有し、NG 時の「課題として起票」の行き先は `docs/issues/`。課題とアイデアの境界（リトマス）: 課題 = 何もしないと損なわれるものがある / アイデア = やれば増える価値がある

8. **事象記録との切り分け（4 巡目）**: 課題体系が持つのは「これから変えるべきこと + トリガー」だけ。**起きたことの記録（事象・復旧手順・解決策）は記録ファイルに残す** — セット固有はセット記録、横断・基盤は開発記録。開発計画書の「トラブルシューティングログ」は**節として廃止**し、既存 3 行は開発記録の「事象記録」節へ移す（計画書 = 生きている項目、記録 = 詳細、の分担どおり。以後の開発レーンの事象もそこへ追記）。障害 1 件 = 事象記録 1 件（必ず）+ 課題 0〜n 件（恒久対策が要るとき。**その場で直した対策も課題として起票し即 解消 へ落とす** — 「何が変わったか」の知識を課題体系に集める）+ 既存課題の発生履歴更新（再発のとき）。`/incident` の照合対象は課題体系（live + closed）と確認待ちに加えて**事象記録も含める**（「予言されていたか」と「前にも起きたか」の両方を出す）
9. **セットバックログとの切り分け（4 巡目）**: バックログは廃止し、行の性質で 3 方向に振り分ける — 課題（変えるべきこと）→ 課題体系 / 観察・判断待ち（何を見て何なら OK。例: 16-4e の効果観察、pref-ranking-1 の初速観測）→ そのセット計画書の確認待ちリスト / 他レーン課題への参照行（例: pref-ranking-1 の 2026-08-10 の項）→ 削除（課題体系の 1 行に関係セットを書けば足りる）。セット別の一覧が欲しい要求は、`docs/issues/index.html` を**レーンごとの節（開発 / セットごと）**に分けることで満たす（1 ファイル内なので照合先は 1 つのまま）
10. **完了したものの扱い（5 巡目で確定）**: 解消・受容した行は **index.html 末尾の「クローズ」節**へ移す（アイデア体系と同じ形。別ファイルにはしない。クローズ節が 50 行を超えて閲覧の妨げになったら `closed.html` へ分ける、を運用ルールに書く）。**解消** = 展開したステップの完了時に `/step` が行をクローズ節へ移す（完了日 + ステップ・コミットへのリンク）。**受容** = 直さないと決めた理由付きでクローズ節へ。再発したら `/incident` がクローズ節から live へ戻し（発生履歴を継続）、エスカレーション規則を適用する。開発記録末尾の「設計課題リスト（解消済み）」は 22-2 でクローズ節へ移してリンクに置換。確認待ちの OK は従来どおり記録ファイルへ

**移行**: 既存 24 行（設計課題リスト 19 + logic-training-1 バックログ 2 + pref-ranking-1 バックログ 3）を導入時に一括で振り分け・新様式へ書き直す。計画書側の節はリンク 1 行に置換。実装は開発レーンの Phase 22 として起票する（転記下書きは末尾）。

## 前提条件・再検討トリガー

- 暫定運用（決定済み）: 課題管理体系ができるまで、課題は開発レーン計画書の設計課題リストに置く。アイデア体系には入れない（「1 アイデア = 事業の意思決定単位」のリトマス試験が濁るため）。境界のリトマス: 課題 = 「何もしないと損なわれるものがある」（既存の欠陥・持ち越し）、アイデア = 「やれば増える価値がある」
- 2026-09-05 の障害で見つかった 4 件は設計課題リストに反映済み（コミット 64a2132）。体系ができたら一括で移す（1 巡目の方向では「移す」ではなく「同じ表の列を改訂して書き直す」になる）
- 関連: `docs/plans/index.html` セクション 5.2（確認待ちリスト・トリガー駆動）と `/idea` 棚卸しモードが既存の動線。`/step` は現状、確認待ちリストのみ照合し課題表は読まない（`.claude/skills/step/SKILL.md` 手順 4）
- 実装は `docs/plans/` のルール変更 + `.claude/skills/` の改修のため**開発レーン**（`docs/plans/` 自体の整理はフリーズ窓で単独実施）。採用時は Phase として起票する
