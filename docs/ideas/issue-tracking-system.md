## 要旨

開発・運用で見つかった課題を、アイデア体系と同じく「壁打ち → 回収タイミングを決める → トリガーで再判断」の動線に載せる仕組み（種別: 運用）。動機は 2026-09-04〜05 の logic-training-1 投稿停止（約 13 時間）。原因の一つは設計課題リストに 2026-07-22 の時点で恒久対策込みで書かれていたのに回収されなかった。

**1 巡目（2026-09-07）の現在形**: 新しい置き場は作らず、**既存の 3 種の表（設計課題リスト・セットバックログ・確認待ちリスト）を「トリガー付き項目」として同じ仕組みに揃え、照合の入口を増やす**方向。中身は 4 点。

1. **列の改訂**: 課題表の「対応時期」を確認待ちと同じ「トリガー」列（機械的に照合できる書き方。「未定」禁止）に置き換え、「発生履歴」列を分離する。ステータスは 4 つ（起票 / 据え置き〔トリガー必須〕/ 展開済み / 解消・受容）
2. **照合の入口を 3 つ足す**: (a) `/step` の照合を確認待ちだけでなく課題表の「対象パス」列にも広げる（「sns-post-batch の次回改修時」型のトリガーが実際に引かれる）(b) 補充スキルの照合をセットバックログにも広げる (c) **障害対応の入口 `/incident`（仮）を新設**し、最初の工程で両レーンの課題表・確認待ちを症状・パス・セット名で照合して「予言されていたか」を出し、最後の工程で発生履歴の更新と起票を強制する
3. **エスカレーション規則**: 「発生実績を見て判断」型のトリガーには回数を書く。既定は「1 回目 = 記録 + 再判断、2 回目 = 据え置き不可・起票必須」（今回ユーザーが手動で行った判断を規則化する）
4. **定期棚卸し**: 新しい儀式を作らず、月次 KPI 転記（operation.html 6.3）とフェーズ・改修完了の節目に相乗りする

確認待ちリストは「同じ仕組みの別名」で正しいが、トリガー時の動作が違う（確認 = 観察して判定・1 回で閉じる / 課題 = 再判断・据え置きを繰り返す）ため、**表は分けたまま、トリガー書式・照合入口・棚卸し節目だけを共通化**する。アイデア体系の「待機 / 再醸成待ち」の関係と同型。

## 前提条件・再検討トリガー

- 暫定運用（決定済み）: 課題管理体系ができるまで、課題は開発レーン計画書の設計課題リストに置く。アイデア体系には入れない（「1 アイデア = 事業の意思決定単位」のリトマス試験が濁るため）。境界のリトマス: 課題 = 「何もしないと損なわれるものがある」（既存の欠陥・持ち越し）、アイデア = 「やれば増える価値がある」
- 2026-09-05 の障害で見つかった 4 件は設計課題リストに反映済み（コミット 64a2132）。体系ができたら一括で移す（1 巡目の方向では「移す」ではなく「同じ表の列を改訂して書き直す」になる）
- 関連: `docs/plans/index.html` セクション 5.2（確認待ちリスト・トリガー駆動）と `/idea` 棚卸しモードが既存の動線。`/step` は現状、確認待ちリストのみ照合し課題表は読まない（`.claude/skills/step/SKILL.md` 手順 4）
- 実装は `docs/plans/` のルール変更 + `.claude/skills/` の改修のため**開発レーン**（`docs/plans/` 自体の整理はフリーズ窓で単独実施）。採用時は Phase として起票する

## 原文メモ

### 2026-09-07

アイデアがあります。「課題管理体系を作る」。

アイデア体系（docs/ideas/）と同じように、開発・運用で見つかった課題も
方針を壁打ちして、どのタイミングで回収するかを決めて進める仕組みにしたい。
種別は「運用」想定。

■ 動機（2026-09-04〜05 の投稿停止障害から）
logic-training-1 の投稿が約 13 時間止まった。原因のひとつ「空の
generation_run が残ると投稿バッチが恒久的に詰まる」は、開発レーン計画書の
設計課題リストに 2026-07-22 の項として恒久対策込みで書かれており、今回の
障害を 2 か月前に予言していた。にもかかわらず「対応時期: 発生実績を見て
判断」というトリガーが引かれず、1 回目の発生（2026-08-06）でも再判断されず、
2 回目の今回に至った。障害調査中も既存の課題リストとの照合をしていない。

つまり本質は「置き場所が分かりにくい」ことより、**書いた回収トリガーを
引く動線がない**こと。設計課題リストは「対応時期」列にトリガーを書くところ
までアイデア体系と同じだが、アイデア体系にある「再醸成待ち + 再検討トリガー
+ /idea 棚卸しモード」に相当する動線がないため、書いた瞬間に凍結される。

■ 特に効きそうだと思っている案
障害が起きたら既存の課題リストを照合する手順を組み込むこと。今回それを
やっていれば、原因究明の前に「予言されていた」と分かり、対処を恒久対策
込みで判断できた。

■ 壁打ちで詰めたい論点（現時点で見えているもの）
1. 4 つ目の置き場を作らないこと。現状すでに「開発レーン計画書の設計課題
   リスト」「セット計画書のバックログ」「確認待ちリスト」の 3 箇所があり、
   統廃合の設計が要る
2. ステータス設計。課題は「今は直さない」が正常な着地として長く続くため、
   アイデアの 6 ステータスとは主役が違う（「据え置き（トリガー付き）」が
   大半になる）
3. 棚卸しの起動条件。定期棚卸しに加えて、障害発生時の自動照合を手順に
   組み込めるか
4. 確認待ちリストとの関係。あちらは既にトリガー駆動で動いており、課題体系と
   同じ仕組みの別名になっている可能性がある

■ 暫定運用（決定済み）
課題管理体系ができるまで、課題は従来どおり開発レーン計画書の設計課題リストに
置く。今回見つかった 4 件は 2026-09-05 に反映済み（コミット 64a2132）。
アイデア体系には入れない（「1 アイデア = 事業の意思決定単位」というリトマス
試験が濁るため）。体系ができたら一括で移す。

## 壁打ち記録

### 2026-09-07（1 巡目・Claude 単独の下調べと提案。ユーザーの返答待ち）

**現状の事実確認**（設計課題リスト 19 行・logic-training-1 バックログ 2 行・確認待ち 4 + 2 行を読んだ）

- 課題表の列は「日付 / 対象ドキュメント / 課題 / 対応方針 / 対応時期」。対応時期は自由文で、19 行中「未定（将来拡張）」「発生頻度を見て判断」型が 7 行。対応方針列に発生履歴・据え置き判断の経緯が追記され続けて肥大している（2026-07-22 の項が典型）
- 確認待ちの列は「日付・対象 / トリガー / 確認内容・判定基準 / NG 時の扱い / 結果」。トリガーは「機械的に照合できる形」と規定され、`/step`（パス照合）と補充スキル（「次の週次補充」照合）が起動時に読む。**課題表を読む入口はどこにもない**
- 2026-07-22 の項は 1 回目の発生（2026-08-06）でも表に追記され「ストック方式への転換で経路縮小」を理由に据え置かれている。つまりトリガーは 1 回目には引かれており、失敗の本質は「引く動線がない」に加えて **「再判断の規則がなく、据え置きが無限に選べた」** こと。2 回目の今回はユーザーが「2 回目をもって据え置き解除」と手動で判断した。これを規則化できる
- 障害の記録先は現状 3 つに分かれている: 事象 = セット記録、恒久対策 = 課題表、復旧コミット = git。障害対応中に課題表を見に行く工程はない

**論点 1（置き場）への判断案**: 4 つ目は作らない。「置き場の統廃合」ではなく **「3 種の表を同じ仕組み（トリガー付き項目）として揃える」** が答え。レーン分割（開発 / セット）は「誰が動くか」のルーティングキーなので残す。課題 1 件 1 MD ファイル方式（アイデア体系型）は採らない — 課題は件数が多く粒が小さく、表の行で足りる。詳細 HTML やダッシュボードも作らない

**論点 2（ステータス）への判断案**: 4 つに絞る。①起票（対応方針未決）②据え置き（トリガー必須。主役）③展開済み（ステップ・フェーズへのリンク）④解消 / 受容（クローズ。受容 = 直さない・再判断もしないと決めたもので理由付き。アイデアの見送りと同型）。**「未定」を禁止**し、据え置きは必ずトリガーか受容のどちらかに倒す。加えて **発生履歴列**（日付の羅列）と **エスカレーション規則**（「発生実績を見て判断」型は回数を明記。既定: 1 回目 = 記録 + 再判断、2 回目 = 据え置き不可）

**論点 3（起動条件）への判断案**: 入口は「手順書に書く」のではなく「スキルが起動時に読む」形にする（この計画体系で実際に動いているのはそれだけ、という実績に基づく）。(a) `/step` の照合対象を課題表の対象パス列へ拡張 (b) 補充スキルの照合対象をセットバックログへ拡張 (c) 障害対応スキル `/incident`（仮）の新設 — 工程: 症状・セット名・パスで両レーンの課題表 + 確認待ちを照合 → 該当があれば「予言されていた」を先に提示し、恒久対策込みで対処を判断 → 事象の記録（セット記録）→ 発生履歴の更新 / エスカレーション判定 / 新規起票。(d) 定期棚卸しは月次 KPI 転記とフェーズ・改修完了の節目に相乗り（新しい儀式を作らない）

**論点 4（確認待ちとの関係）への判断案**: 同じ仕組みで正しい。違いはトリガー時の動作（確認 = 観察して OK / NG を判定し 1 回で閉じる。課題 = 再判断で据え置きを繰り返しうる）。アイデア体系の「待機（決めた。転記するだけ）/ 再醸成待ち（決めていない。再判断する）」と同型。**表は分けたまま**、トリガー書式・照合入口・棚卸し節目を共通化する。確認待ちの NG 時の扱い「課題として起票」が両者をつなぐ

**リスク・コスト**: `/step` 起動ごとに課題表を読むトークンコスト。対処は「対象パス列の grep で該当行だけ読む」設計にし、発生履歴を対応方針列から分離して行を短くする。ソロ運用の過剰設計リスクは、新規ファイル・新ディレクトリ・ダッシュボードを作らないことで抑える

**MVP スコープ（作らないもの）**: 課題 1 件 1 ファイル、詳細 HTML、ダッシュボード、5 つ以上のステータス、新しい定期儀式、CloudWatch 等のシステム側の検知（それは個別課題 2026-07-07・2026-08-23 の領分）

**採用判断に足りない情報（次巡でユーザーに聞く）**

1. 障害対応の入口をスキル `/incident` として作ることに同意するか（手順書への記載だけで済ませたいか）
2. 課題表と確認待ちを表として分けたままにするか、1 表に「種別」列で統合するか（Claude の推奨は分けたまま）

5. 名称。「課題管理体系」より「トリガー付き項目の運用」のほうが実態に近いが、呼び名をどうするか
