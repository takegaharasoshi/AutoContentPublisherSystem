## 要旨

logic-training-1（脳みそコーチ）の投稿に付いた**正解のコメントにだけ**、「正解！お見事！」系の返信をすぐ自動で返す。仕組みは[ウミガメ](umigame-soup-set.md)のコメント自動返信と同じ形だが、**ウミガメには手を入れず専用に別に作る**（専用の Meta アプリ・複製したコード・新しいスタック。共通経路は投稿バッチのスナップショット出力だけで、セット単位のフラグで切り替える）。最初の正解には「一番乗りだな」を添える。朝（なぞなぞ）・夜（とんち・水平思考）の両方で始める。
**確信が高いときだけ返し、迷ったら黙る**（外れに「正解！」と返すのは致命的、正解を返し漏らすのは人間が後で返せば無害という非対称性）。別解・外れへの返信は人間に残す（次の段階の候補）。
運用中のアカウントなので、**見える返信を最後まで出さない順**（オフライン評価 → ステージング → 本番のシャドー運用 1 週間 → 止めるスイッチ付きの本番返信）で進める。
動機は、手での返信が会話とファン化を生んでいる体感（正しい前提として扱う）と、コメントが増えて手が回らなくなったこと（2026-09 第 3 週以降は週 230〜250 件前後・1 日 30 件超）。

ペルソナ全体（台詞・出題の口調を「考えることを応援するコーチ」へ寄せる）は 2026-10-24 に別アイデア [logic-training-coach-persona-design](logic-training-coach-persona-design.md) へ切り出した。

## 前提条件・再検討トリガー

- **基本方針（2026-10-24）**: ウミガメのコメント返信（`services/comment-reply/`・`CommentReplyStack`・その Meta アプリ）には手を入れず、**脳みそコーチ専用に別に作る**（専用の Meta アプリ・新しいサービス〔例: `services/logic-training-reply/`〕に今のコードを複製して削る・新しい CDK スタック・Secret・トークン更新も別）。目的は凍結そのものではなく、既存機能へ影響するリスクを減らすこと
- **Meta アプリを分ける理由**: Webhook の送り先はアプリごとに 1 つのため、同じアプリにつなぐとウミガメの受け付け Lambda に脳みそコーチの通知が届き、振り分けの改修が要る
- **共通経路は投稿バッチだけ**: 正解の受け渡しは、投稿バッチ（`services/sns-post-batch/`）が投稿後に問題スナップショットを S3 へ書く方式（ウミガメと同じ）を `quiz_items` にも広げる。書く・書かないは既存のセット単位のフラグ `batch_sets.problem_snapshot_enabled` で切り替え、ウミガメの分岐は触らない。影響は回帰テストで押さえる
- **未確認**: 新しい Meta アプリ（Instagram ログイン方式）を公開モードにして脳みそコーチのアカウントのコメント Webhook を受けられるか（プライバシーポリシーの URL が必須）。過去のコメントと自分の返信を読み出せるか（オフライン評価の材料。投稿用トークンか新アプリのトークンにコメント読み取りの権限が要る）

## 転記下書き（開発レーンのフェーズ案。転記時に `docs/plans/_templates/step.html` の枠へ流し込む）

**進め方の原則**: 運用中のアカウントでのリスクは「視聴者に見える誤った返信」に集まるため、見える返信を最後まで出さない順に進める（オフライン評価 → ステージング → 本番のシャドー運用 → 止めるスイッチ付きの本番返信）。

課題表: I-046（`services/comment-reply/` を触るステップの起票時）は**該当しない**（ウミガメのコードは触らないため据え置きのまま）。I-015・I-017 は `services/sns-post-batch/` が対象パスだが内容が無関係（転記時に同梱しない判断を起票文に残す）。ほか該当なし。

### N-1 新しい Meta アプリの準備とオフライン評価の材料集め

- **内容**: 脳みそコーチ専用の Meta アプリ（Instagram ログイン方式）を作り、テスト用アカウントと脳みそコーチのアカウントをつないでトークンを取る（公開モード・プライバシーポリシーの URL を含む）。そのトークンまたは投稿用トークンで、過去の投稿のコメントと運用者の返信・問題の正解を読み出し、評価用データ（正解 / 別解 / 外れのラベル = 運用者の返信）にまとめる
- **完了条件**: 評価用データのファイルがあり、件数とラベルの内訳が開発記録に書かれている。読み出せなかった場合は理由と代替の取り出し方が書かれている
- **人間ゲート**: Meta 側のアプリ作成・アカウント接続はユーザー作業
- **停止点・上限**: 公開モードにできない・Webhook の権限が取れない場合は方針の判断で停止（ユーザー判断）

### N-2 設計

- **内容**: 新しいサービス・スタックの構成（受け付け・キュー・返信・トークン更新・Secret・**返信の有効 / 無効のスイッチ**〔再デプロイなしで 1 コマンドで切り替える〕）、正解の判定（確信が高いときだけ返す閾値・一番乗り・定型文の候補とランダム選択・判定の材料が正解の文言だけで足りるか）、投稿バッチのスナップショットを `quiz_items` へ広げる仕様、誤った返信を消す運用手順を設計書に書く（機能別の基本設計に新しいページ + 詳細設計。ストック側に受けてよい表現の幅を持たせる場合はセットレーンへ起票）
- **完了条件**: 設計書が更新され、`python3 tools/docs_check.py` が通る
- **人間ゲート**: 設計レビュー（ユーザー判断・ゴール対象外）
- **停止点・上限**: レビューは最大 2 巡・blocker のみ修正

### N-3 実装とオフライン評価

- **内容**: 新しいサービスを今のコメント返信のコードから複製して作る（正解のみ判定・一番乗り・定型文・返信スイッチ・シャドー時は記録だけ書く）。投稿バッチのスナップショット出力を `quiz_items` に広げる（フラグが立っていないセットの動作は変えない）。N-1 の評価用データで判定を流し、運用者の返信と突き合わせる（Codex 委譲）
- **完了条件**: 両サービスの pytest 全パス（投稿バッチはウミガメ・既存セットの回帰を含む）。オフライン評価で外れを「正解」と判定した件数が 0 件、正解の拾えた割合が開発記録にある
- **人間ゲート**: なし（`services/sns-post-batch/` の push 後のパイプライン完走は `/goal` で確認）
- **停止点・上限**: 外れへの「正解」が出たら閾値やプロンプトを直して 2 回まで再評価、それでも出たら停止。20〜30 ターンを超えそうなら投稿バッチと新サービスで割る

### N-4 CDK とステージング試験

- **内容**: 新しいスタック（本番面・ステージング面）を CDK に足す（`CommentReplyStack` のクラスは触らない）。ステージング面でテスト用アカウントに実コメントを打ち、受け付け → 判定 → 返信 → 記録と、返信スイッチの切り替えを確かめる
- **完了条件**: ステージングで正解に返信が付き、外れには付かず、スイッチを切ると返信が止まる（記録だけ書かれる）ことを確かめた記録がある
- **人間ゲート**: `cdk deploy` と Meta の Webhook の送り先の設定はユーザー作業
- **停止点・上限**: 試験が通らなければ原因を記録して停止

### N-5 本番のシャドー運用（ユーザー判断・ゴール対象外）

- **内容**: 本番面を返信スイッチ「切」のまま脳みそコーチのアカウントにつなぎ、投稿バッチのフラグを立てる。1 週間、判定の記録だけを書き、運用者は今までどおり手で返す。記録と運用者の返信を比べる
- **完了条件**: シャドー期間の記録の集計（判定件数・外れへの「正解」件数・運用者の返信との一致）が開発記録にあり、ユーザーが本番返信の go / no-go を出している
- **人間ゲート**: go / no-go はユーザー
- **停止点・上限**: 外れへの「正解」が 1 件でも出たら直して 1 週間延長

### N-6 本番返信の開始

- **内容**: go を受けて返信スイッチを「入」にする（朝・夜の両方）。止める手順と誤った返信を消す手順を運用手順として確認する
- **完了条件**: スイッチが入り、最初の正解コメントに返信が付いたことを確認した記録がある
- **人間ゲート**: スイッチの切り替えはユーザーの go の後
- **停止点・上限**: 誤った返信を見つけたら即スイッチを切って課題を起票する

### 確認待ち（ステップにしない）

- 本番返信の開始 2 週間後（日付は開始時に確定）: コメント記録で外れへの「正解」返信が 0 件か、コメント数（logic-training-1 の 1 投稿あたり中央値）が手で返していた時期（2026-10 第 1〜2 週・12.5〜16 件）の水準に戻るか。NG なら返信を止めて課題として起票する

## 原文メモ

> 新しいアイデアです。
>
> 脳みそコーチのアカウントのコンセプトをより本当にコーチやパーソナルトレーナーのような、コーチ感の強いアカウントにしていくというアイデアです。
>
> ユーザーがコメントしてきた内容に対して否定はせず、「偉い」「頑張れ」のように、考える（脳みそを使う）という行為に対して応援をする方向性のアカウントにします。
>
> その手段として、コメント自動返信機能を使って「頑張れ」といったコメントをすぐに送れるようにしたいと考えています。
>
> なぜそう考えたかというと、これまでのアカウント運用のなかで、見てくれる、コメントをくれる人たちの年齢層はお年寄りの方が結構多いと感じたためです。
>
> お年寄りというと、どこか寂しさを抱えているようなイメージもあるので、そこで応援してくれるような存在のアカウントになれれば楽しんでもらえるし、もっとこのアカウントを好きになってくれるんじゃないかなと思ったからです。

## 壁打ち記録

### 2026-10-24（1 回目）

- **効果の仮説**: 手での返信の体感から正しい前提として扱う（検証の MVP は置かない）。自動化の動機は、コメントの増加と仕事の都合で手で返せなくなったこと
- **コメントの量（本番 DB・2026-09 以降の 104 本）**: 週合計は 9 月第 1 週 117 件 → 9 月第 3 週〜10 月第 2 週は 230〜250 件前後。1 投稿の中央値 4 → 16 件。朝・夜の差は小さい（朝 12・夜 10）。10 月第 3 週は 107 件に下がった。Instagram のコメント数には運用者の返信も含まれるはずで、手での返信が減った時期と重なる（返信が会話を増やしていた傍証になりうる）。中身はほとんどが自分で考えた回答
- **手での運用ルール（自動化の仕様の元）**: 正解 →「正解！お見事！」系の定型文（最初の正解には「一番乗りだな」）。用意した答えと違うが正解と言える回答 →「〇〇でも正解だぞ」「ナイス別解」。外れ → 中身に応じて「〇〇という制約があるぞ」、またはアイデアだけを褒める
- **判断**: 全部を自動化するのは難しいため、**正解への返信から**始める。朝・夜の両方で始める。確信が高いときだけ返す（誤って「正解」と返すのは致命的、返し漏らしは無害）。bot 感は定型文の複数候補とランダム選択で抑える。一番乗りはコメント記録で判定できるため MVP に入れる
- **切り出し**: ペルソナ全体の設計 → [logic-training-coach-persona-design](logic-training-coach-persona-design.md)（独立の価値あり・inbox）
- **積み残し**: アカウントを今のアプリにつなげるか（N-1）。判定の材料として正解の文言だけで足りるか（N-2）。別解・外れへの返信（自動化の次の段階。正解返信の稼働後に再検討）

### 2026-10-24（1 回目の続き: リスクを抑える進め方）

- **進め方**: 運用中のアカウントでのリスクは「視聴者に見える誤った返信」に集まる。見える返信を最後まで出さない順にする — 過去のコメントと運用者の返信をラベルにしたオフライン評価 → ステージング → 本番のシャドー運用（返信せず記録だけ・1 週間・誤った「正解」が出たら延長）→ 再デプロイなしで止められるスイッチ付きの本番返信（朝・夜の両方）。期間と範囲はエージェントの推奨で決めた（違えば直す）
- **既存機能との分け方**: 今の返信機能をセット切り替え式に改修する案は取らない。ウミガメへの影響を減らすため、専用の Meta アプリ（Webhook の送り先はアプリごとに 1 つ）・コードの複製（`shared/` への共通化はウミガメのコードを書き換えるため取らない）・新しいスタックで別に作る。凍結は絶対の目的ではなく、影響のリスクを減らすのが目的（ユーザー）
- **投稿バッチ**: 手が入ってよい（ユーザー）。確認の結果、投稿バッチは全セット共通の 1 本で、セットの登録・キャプション・スナップショット出力の有無（`batch_sets.problem_snapshot_enabled`）は DB の設定、中身の種類（quiz / ranking / umigame）ごとの読み出しはコード。**既存の種類のセットを足すときは DB だけ、新しい種類を足すときはコードに手が入る**。今回はスナップショット出力を `quiz_items` に広げ、フラグでウミガメと切り離す
- **課題表**: I-046 はウミガメのコードを触らなくなったため同梱しない（据え置きのまま）
