## 要旨

logic-training-1（クイズセット）の事前ビルド動画を、現行の Pillow 組版 + ffmpeg 合成
（`services/image-batch` の `gpt_quiz_multicut` を `content/video-build/logic-training-1/build.py` が流用）から、
pref-ranking-1 で実証済みの Remotion（`content/video-build/pref-ranking-1/remotion/`）に載せ替えれば、
より良い動画が作れるのではないか、という仮説。

壁打ち 1 巡目（2026-09-02）で分かった構造: 現行動画は 16 秒・3 カット・**7 枚の静止版面のうち 5 枚が完全静止**、
動きはコーチ吹き出しのバウンド 2 箇所のみ、TTS・ナレーション・字幕なし。表現力の差は構造的に大きく、
Remotion 基盤（Docker 化・レンダリング時間・LICENSES・pytest）は社内で整備済みなので**技術リスク・API 費用はほぼゼロ**。
一方、**「動きが乏しいから離脱している」という動機は docs 上に裏付けがない**（設計課題リスト・セット計画書のどちらにも
動画品質の課題は起票されていない）。16-5 効果検証が 9 月上旬に実施適期で、先に作り直すと 16-4c/16-4d に続く
3 度目のフォーマット変更となり水準評価の母集団が再分断される。

現時点の見立て（2 巡目で確定・3 巡目で絞り込み）: ユーザーの狙いは **① 動き ③ 版面表現力**。維持カーブ 3 本は
0〜2 秒の崖がなく 16 秒全体で一定勾配に減る形で、**冒頭フック用途の動きは主因に効かない**。残る用途は**ペーシング**
（問題を読み終えてからカウントダウンまでの死に時間と、静止 5 枚のカウントダウンを動きで埋める）。
ただし現行の 8 秒・13 秒イベントに変曲点が出ていない以上、動きで留まる保証はなく、**プロトタイプ 1 本 → 次回補充バッチでの
パイロット → 全数載せ替え**の 3 段で確かめながら進める案を 3 巡目で組んだ。情報設計（16 秒・3 カット・答えはキャプション）は変えない。
## 前提条件・再検討トリガー

- **順序**: 16-5 効果検証（現行フォーマットの絶対水準）を先に済ませ、作り直しは**その後**に投入する。
  作り直しの投入日はセット記録に必ず残す（16-11 で前後比較は放棄済みだが、推移解釈に変更日が要る）
- **維持カーブは取得済み（2026-09-02・3 本）**: 0〜2 秒の崖は**なく**、16 秒かけて一定勾配で減り続ける形。
  冒頭の動き不足（R-1 型）は主因ではない。詳細は壁打ち記録 2 巡目
- **在庫規模**: ストック 77 問（稼働 56 = 朝 28 / 夜 28、昼 21 は凍結）。版面変更は全数再ビルド + S3・DB 差し替え
  + **全数人間レビュー**が必須（quiz-prebuilt 設計書セクション 8 の warn。16-4c は 63 本）。
  再ビルド自体は pref-ranking-1 の R-1 実績（30 本 42 分）から 1 時間以内の見込み。コストの本体は人間レビュー
- **MVP の線引き（3 巡目で更新）**: 16 秒・3 カット・SE タイミング（tick 8.0 秒 / chime 13.0 秒）・答えはキャプション、の
  情報設計は変えない。変えるのはレンダラーと「カット内の動き」だけ。TTS は入れない。BGM・SE の設計も維持。
  動きの候補は壁打ち記録 3 巡目の表を参照
- **段階投入（3 巡目で追加）**: (a) 既存 1 問で Remotion プロトタイプを作り、現行動画と並べて目視比較（git 管理外 → 採用なら移設。
  pref-ranking-1 の `remotion-proto/` と同じ手順） → (b) 次回の週次補充バッチ（w6 相当・約 14 問）だけ新版面でビルドし、
  混在投稿で新旧の維持カーブを比較 → (c) 効けば残り全数を再ビルド・差し替え。(b) は「版面変更は全数再ビルド」の warn からの
  意図的な逸脱で、判断はユーザー。2026-09-02 時点で w5（14 問）は**ビルド済み**のため、無料で乗れる未ビルド在庫はない
- **成否の見方**: アプリ画面の維持カーブで、2〜8 秒の勾配が浅くなるか / 8 秒（カウントダウン開始）に変曲点が出るか。
  0:06 の値（現行 40〜47%）と 0:16 の値（現行 20〜32%）を新旧で比べる。サンプルは各 3 本以上
- **レーン**: `content/video-build/logic-training-1/` + `docs/app/generators/quiz-prebuilt.html` + セット計画書は
  セットレーン。ただし `docs/app/batch-flow.html` の方式カタログ行が「Pillow 組版 → ffmpeg 連結」と技術を明記しており、
  ここを直すと共通設計書に触れる = 開発レーン行き。`services/image-batch` の `gpt_quiz_multicut` は残置（休止方式・削除しない）
  なら `services/` は触らない。採用時にレーンを確定する
- **共通化は理由にしない**: ツーリングの共通 core 化は「英語セット追加時まで YAGNI」で凍結済み
  （ranking-prebuilt 設計書セクション 8 の decision）。本件は logic-training-1 専用の載せ替えとして扱う

## 壁打ち記録

### 2026-09-02（1 巡目: 現状把握と論点の切り出し。着地は醸成中のまま）

- **前提の事実確認**: 現行レンダラーは `gpt_quiz_multicut.py`（Pillow + ffmpeg、`-loop 1` の静止 PNG を concat）。
  16 秒・3 カット・7 版面のうち 5 枚が完全静止、動きはバウンド 2 箇所（16-4b で追加）。連続ズームは 16-4c で廃止済み。
  TTS・ナレーション・字幕なし。演出面の伸びしろは現方式内では概ね使い切っている
- **Remotion 側の追い風**: pref-ranking-1 で Docker レンダリング環境・LICENSES・pytest 体制・レビューシートが整備済み。
  R-1（冒頭ルーレット予熱）は起票 → 実装 → 30 本再ビルド → 差し替えが 1 日で完了。追加費用ゼロ
- **逆風 1（動機の裏付けなし）**: 設計課題リスト・セット計画書バックログに動画品質・演出の課題はゼロ。
  スキップ率 95%（2026-07-31）は 16-4b/16-4c 前の数字で、現行フォーマットの水準は 16-5 で見る予定のまま未着手。
  「Remotion にすれば良くなる」は現時点でユーザー発の未検証仮説
- **逆風 2（タイミング）**: 16-5 は「9 月上旬以降にデータが溜まってから」が適期 = 今。作り直しを先に走らせると
  3 度目のフォーマット変更で母集団が再分断される → 順序は 16-5 → 作り直し、が筋
- **論点の切り出し**: 「Remotion で作り直す」は手段。良くしたいものを ① 動き ② 音声（TTS） ③ 版面表現力 に分解し、
  ②は Remotion と独立であることを指摘。ユーザーがどれを狙っているかが 2 巡目の入口
- **足りない情報**: logic-training-1 の視聴維持カーブ（崖の位置）。pref-ranking-1 では実データ提示で設計が変わった
  （速度ランプ撤回）実績があり、本件でも同じ手順で採否・スコープが決まる見込み
- **積み残し**: ユーザーの「いい動画」の定義の確認 / 維持カーブの提示 / レーン確定（batch-flow.html の方式カタログ行の扱い）
  → 前 2 点は同日中に解消（下記）

### 2026-09-02（2 巡目: 維持カーブの実データで仮説を検証）

ユーザーの「いい動画」の定義 = **① 動き ③ 版面表現力**（② TTS は狙いではない）。
Instagram アプリ「あなたのリール動画の再生時間」を 3 本提示（16 秒版・サンプル数は少ない）。

| | 夜・とんち（屏風の虎） | 朝・なぞなぞ（9 匹の虎） | 夜（木箱の問題） |
|---|---|---|---|
| 0:02 時点（目視） | 約 70% | 約 75% | 約 70% |
| 0:06 時点（表示値） | **40%** | **41%** | **47%** |
| 0:16 時点（目視） | 約 20% | 約 20% | 約 32% |
| 形 | 一定勾配の減衰 | 同 | 同（やや浅い） |
| 流入 | リールタブ 73.5% / 発見 23.4% | リールタブ 81.2% / 発見 13.3% | リールタブ 70.3% / 発見 16.5% / フィード 11.8% |

読み取りと判断:

- **0〜2 秒の崖がない**。pref-ranking-1（0:02 で 25〜50%・0:05 で 18〜37%）とは形が別物で、logic-training-1 の冒頭は
  むしろ**良く機能している**（0:05 で 45% 前後）。静止版面でもタイトル帯 + 問題文は読まれている。
  → 「ミュート勢が動きの無さで即スキップ」という R-1 型の仮説は**本セットには当たらない**。①動きを冒頭フックとして
  足しても改善余地は小さい
- **損失は 16 秒全体に一定勾配で分散**している。8.0 秒のカウントダウン開始（tick SE）・13.0 秒の答え誘導（chime SE）の
  いずれにもカーブの変曲点が見えない = 現行の「イベント」は視聴者を引き留めていない
- **形が示す本質**: 減衰が止まらない = **動画内にペイオフ（見届ける理由）がない**。答えはキャプションで開示する設計
  （16-1 / 16-4c。「わかったらコメントしてくれ！」でコメント誘発を狙う意図的な判断）のため、問題を読み終えた人・
  解けた人・興味を失った人がそれぞれのタイミングで離れ、最後まで残る理由が構造的に無い。pref-ranking-1 が崖のあとに
  平坦なのは「1 位発表」というペイオフが末尾にあるから。これは**レンダラーの問題ではなく情報設計の問題**
- **Remotion が効きうる残りの余地**: 2〜8 秒（問題を読み終えてからカウントダウンまでの死に時間）と 8〜13 秒の
  カウントダウンの「間延び」を、問題文の段階表示やカウントダウンの動きで埋める**ペーシング用途**。ただし現行の
  8 秒・13 秒イベントが効いていない以上、動きを足せば留まる、という保証はない（未検証）。③版面表現力についてはカーブから
  読み取れる信号がない
- **派生の論点（親とは独立）**: 動画内で答えを開示する（末尾ペイオフを作る）か、コメント誘発を優先して現状維持か。
  維持率とコメント数のトレードオフで、事業上の判断（16-12 の指標セットで何を主 KPI にするか）に直結する。
  Remotion とは無関係にカット追加で実現できるため、独立の価値がある → 別アイデアとして捕捉する候補
- **暫定結論**: Remotion 作り直しは「動きの無さで離脱している」という前提を失った。単独で進める根拠は現時点で無い。
  情報設計（答え開示・カット構成）を変える判断が出たときに、そのレンダラー選定として再検討するのが筋

### 2026-09-02（3 巡目: ペーシング用途に絞った案の具体化。着地は醸成中のまま）

ユーザー判断: 醸成中のまま続ける / 派生（動画内で答え開示）は別アイデアとして捕捉しない（本記録の記述で足りる）。

**動きの候補（情報設計は不変・カット内だけ）**

| 区間 | 現行 | 案 | Remotion が要る度合い |
|---|---|---|---|
| 0〜3 秒 | 全要素が 1 フレーム目から静止表示 | つかみ帯は 0 秒から即出し（維持）。問題文を読む速さに合わせて**節ごとに段階表示**、イラストは軽いフェード + 微ズームで着地 | 低〜中（段階表示だけなら現行方式でも PNG 枚数を増やせば可能） |
| 3〜8 秒 | 完全静止（バウンド 1 箇所のみ） | 「考える」ビート: コーチ吹き出しの周期的な揺れ、イラストのごく遅い ken-burns、時計 / 砂時計などの経過表現 | 中（ffmpeg の overlay 式で書けるが保守が辛い領域） |
| 8〜13 秒 | 静止 5 枚（5→1 のバッジ差し替え） | 数字のスケールイン / アウト、円バッジのリング進行、tick に同期した版面の微パルス | **高**（フレーム補間が本領。現行方式では実質不可） |
| 13〜16 秒 | 静止 1 枚 | 吹き出し「答えは投稿のキャプションへ！」を矢印 / 指差しの動きで強調、コーチのガッツポーズにアニメーション | 中 |

- **正直な線引き**: 0〜3 秒の段階表示だけが目的なら Remotion は不要で、現行パイプラインに PNG を数枚足せば済む。
  Remotion を選ぶ理由が立つのは 8〜13 秒のカウントダウンと、ffmpeg 式ハックの積み増しを止める保守面。
  ③版面表現力は「動きが乗ることで版面の見え方が変わる」以上の具体案が現時点で無い（ユーザーの具体イメージ待ち）
- **効果の不確実性は残る**: 現行の 8 秒 tick・13 秒 chime に変曲点が出ていない = 音のイベントでは留まっていない。
  視覚イベントなら留まる、は仮説。だから段階投入（プロトタイプ → パイロット → 全数）で確かめる
- **コスト見積り（概算）**: (a) プロトタイプ 1〜2 セッション（pref-ranking-1 の Dockerfile.render・build.py の `_render()` を流用、
  TTS 同期・地図データ・ラウドネス後処理が無いぶん 17-3〜17-4d より大幅に軽い）。(b) パイロットは通常の補充作業 + 新版面レビュー。
  (c) 全数は再ビルド 1 時間以内 + 56 本の人間レビュー。API 費用ゼロ
- **16-5 との順序は維持**: (a) は投稿に影響しないため 16-5 と並行可。(b) 以降は 16-5 の水準評価を済ませてから投入し、投入日をセット記録に残す
- **次の一手（案）**: (a) プロトタイプ 1 本の着手判断。着手するならセットレーン（`content/video-build/logic-training-1/` 配下で閉じる。
  git 管理外の試作なので設計書には触れない）
