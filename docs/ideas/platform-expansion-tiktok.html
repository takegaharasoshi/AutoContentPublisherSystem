プラットフォーム展開（ウミガメのスープをコメント返信ごと他プラットフォームへ）

再醸成待ち 種別: 単発 / 作成 2026-09-03 / 更新 2026-10-13 / 記録層: platform-expansion-tiktok.md 再開条件: umigame-soup-1 のフォロワーが 2,000 人に到達
本書の位置づけ（設計書に非ず） 採用判断のための検討記録。2026-10-13 の Web 調査（公式ドキュメント優先）の結果を整理したもので、API 仕様・料金・審査要件は変わりうる。再開時に一次情報で再確認し、採用が決まったら docs/app/ / docs/infra/ の設計プロセスへインプットとして引き継ぐ。展開方針の正は事業戦略書セクション 5（本書の結論は採用時に転記する。現時点では書き換えていない）。

1. 前提（2026-10-13 の壁打ちで確定）

  • 展開対象は umigame-soup-1（探偵カメロックのウミガメのスープ）。logic-training-1（脳みそコーチ）ではない
  • 展開の形は「同じセット・同じ動画を複数プラットフォームへ」（セット : アカウント = 1 : N）。世界観違いの複数アカウント（umigame-multi-account-worldview）との組み合わせは本件では扱わない
  • コメント自動返信は必須。ウミガメはコメント欄が企画の本体のため、返信できない面へ動画だけ転用しても成立しない
  • 返信の遅延は数分おきの巡回（ポーリング）でも可。Webhook の有無は除外理由にしない。判定軸は「コメントを読む API」と「特定コメントへ返信する API」が公式にあるか

2. 結論（実現しやすい順）

順位プラットフォーム判定決め手

decision: ウミガメの展開では「TikTok 第一候補」の前提が崩れる（2026-10-13） 事業戦略書 5 の「TikTok を第一候補」は動画資産をそのまま転用できることを根拠にしていた。ウミガメはコメント返信が企画の本体なので選定基準が変わり、Facebook リールと YouTube Shorts が現実的な第一候補群になる（Facebook = 既存基盤の流用、YouTube = 視聴者の多さ）。TikTok は「個人で開発者登録できるか」を実機で試せば白黒がつく。法人化が前提なら別の事業判断。戦略書への反映は採用時の転記で行う。

3. プラットフォーム別の詳細

【二次】は公式文書で確認できず、二次情報のみで確認した主張。

3.1 Facebook リール（ページ）

  • 動画の自動投稿: POST /{page_id}/video_reels（3 段階アップロード）。24 時間で 30 件まで。権限 pages_manage_posts 等
  • コメント取得: ページ Webhook の feed フィールド（item=comment）。subscribed_apps へのアプリ登録が必要。リールへのコメントで通知が飛ぶかは公式で未確認
  • 返信: コメント ID に対して POST。権限 pages_manage_engagement / pages_read_engagement / pages_read_user_engagement、ページタスク MODERATE + CREATE_CONTENT。自分のページだけなら Standard Access で動く【二次】
  • 規約: Meta の自動化ルールで Instagram と同系統
  • 判定: 可能。現行の Instagram 実装（Meta Graph + Webhook）の流用度がいちばん高い

3.2 YouTube Shorts

  • 動画の自動投稿: videos.insert（専用枠 1 日 100 回）。未検証プロジェクトの投稿が非公開に固定されるかは要確認（現行の videos.insert 頁は「制限なし」、改訂履歴には 2020-07-28 の「非公開に制限」告知のみで撤廃告知が見当たらない）
  • コメント取得: commentThreads.list（1 単位）のポーリング。コメントの push 通知はない（PubSubHubbub は新規動画の通知のみ）
  • 返信: comments.insert（parentId 指定でスレッド返信）が 1 件 50 単位。既定枠 1 万単位/日なので返信は 1 日約 200 件が上限。増枠は申請制・無料
  • 規約: スパムポリシーは大量・反復コメントやボットによる操作を禁止。合成コンテンツの開示義務は写実的な内容のみ（アニメ調は対象外）
  • 判定: 条件付きで可能。弱点はポーリング（遅延とクォータ按分）と返信件数の上限

3.3 Threads

  • 動画の自動投稿: VIDEO コンテナ作成 → threads_publish。5 分・1 GB まで、24 時間で 250 件
  • コメント取得: Webhook の replies フィールド（threads_read_replies）。アプリ審査（Advanced Access）とビジネス認証が必要。非公開アカウントの投稿では通知されない
  • 返信: reply_to_id 付きでコンテナを作って公開（threads_manage_replies）。24 時間で 1,000 件・無料
  • 判定: 可能（Webhook は審査要）。ただしテキスト中心の場で短尺動画が伸びるかは未知数

3.4 X

  • 料金: 2026-02 から従量課金が既定。投稿 1 件 0.015 ドル（URL 付き 0.20 ドル）。一般向け無料枠は事実上廃止、Basic（月 200 ドル）は新規受付停止【二次】。動画アップロードの料金は公式頁で未確認
  • コメント取得: 自分宛てメンションの読み取り 1 件 0.001 ドル。ポーリング（push は Enterprise 系）
  • 返信: 投稿作成と同じ扱いと推定（1 件 0.015 ドル程度）
  • 規約: 自動化ルール（2026-04 更新）は「自分のコンテンツに反応した人への自動返信」を許容例に挙げる。スパム・未承諾メッセージは禁止
  • 判定: 可能（有料）。事業戦略書 5 の「X は当面見送り（API 有料化が予算方針と不整合）」は、従量課金化で前提が変わった可能性がある（月 50 ドル前後の規模）

3.5 TikTok

  • 動画の自動投稿: Content Posting API の Direct Post（/v2/post/publish/video/init/、video.publish）。未監査クライアントは非公開投稿（SELF_ONLY）のみで、公開投稿には監査が要る（2〜6 週・1 日約 15 件【二次】）
  • コメント取得: Display API / Login Kit にはない。TikTok API for Business の Accounts API（オーガニック動画）で取得。Webhook comment.update（5 分以内に通知・本文は含まれず再取得が必要）【二次】
  • 返信: /business/comment/reply/create/【二次】。公式の「Reply to a comment」（/comment/post/）は広告コメント用で使えない。スコープ comment.list / comment.list.manage（TikTok Accounts 権限。2026-03 から別途申請フォーム）。開発者登録は法人のみ・会社ドメインのメールが必要【二次】
  • 規約: 写実的な AI 生成コンテンツには AIGC ラベル。ボットによるエンゲージメント操作は禁止。似た文面の返信の連投がスパムとして非表示にされた報告あり【二次】
  • 判定: 条件付き。関門は「法人として開発者登録」「Accounts 権限の審査」「投稿の監査」の 3 つ。個人運営では登録段階で不可の可能性

3.6 その他

  • LINE VOOM: 公開の投稿 API が見当たらない → 不可
  • ニコニコ: 公式は検索 API のみ。コメント投稿は非公式 API しかない → 不可

4. 現行の返信基盤との関係（見積もりの材料）

現行のコメント返信（services/comment-reply/・CommentReplyStack）は「Webhook Lambda → SQS FIFO + DLQ → Reply Lambda」の構成。

  • Webhook がある面（Facebook・Threads・TikTok）: 受け口の Lambda をプラットフォーム別に足せば、SQS から先は流用できる見込み
  • ポーリングの面（YouTube・X）: Webhook Lambda の代わりに、定期起動でコメントを取得し SQS へ積む Lambda を置く。返信 Lambda と LLM の判定は流用できる見込み
  • いずれも 1 セット : N アカウントの実装（現状は Instagram 1 アカウント分のみ）と、投稿バッチのプラットフォーム別分冊が前提になる

5. 再開までに潰したい不明点（実機確認）

  1. TikTok に個人で開発者登録できるか（法人要件・2026-03 の申請フォーム・日本からの利用可否）。無料・数十分で白黒がつく
  2. Facebook ページの Webhook（feed）がリールへのコメントで届くか（Standard Access のままで届くかも）
  3. YouTube の未検証プロジェクトから videos.insert した動画が公開のまま残るか
