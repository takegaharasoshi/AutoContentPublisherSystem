多めの候補から選び、保留・NGは後日振り返る

醸成中2026-09-21 / 原文・壁打ち履歴
今回の方針変更ユーザーの提案を受け、従来の「完成稿だけを人間レビューする案」を候補選別と完成稿確認の2段階へ変更した。補充中は理由の説明を求めず、後日じっくり振り返る。これは採用判断のための検討資料であり、設計書ではない。スキル本体・候補の保存場所・新しいスキルはまだ作成していない。

1. Webリサーチは続ける。先に作るものを変える

変更後もWebで題材を探し、出典の本文を確認する。既出の問題、過去の保留・NG、未使用の候補も調べる。候補を2倍に増やすために出典確認を省いたり、同じ問題の言い換えで数を埋めたりしない。

9月w1・w3の記録では、朝7問・夜7問の計14問を執筆・機械検証してから人間レビューへ進んでいた。補欠のリサーチメモは別にあったが、28問の短い候補を人間が先に選ぶ運用ではなかった。

変更前変更後
14問を全項目まで作る → レビュー → 微妙な点や修正方法を人間が説明 → AIが直す／差し替える。 28問の短い候補を作る → 人間はOK・NG・保留だけを返す → 朝7問・夜7問のOKが集まったら、その14問だけ全項目を仕上げる。NG・保留の理由を考える作業は後日に分ける。

目的は、レビュー工程の数を減らすことではなく、補充のたびに人間が「何が微妙で、どう直せばよいか」を考えて言語化する負担を減らすこと。AIの調査量は増えるため、全体の作業時間が必ず短くなるとは限らない。

2. 週次補充の新しい流れ

  1. 必要な問題数を決める。1週間分なら朝7問・夜7問。
  2. Webリサーチをして短い候補を作る。AIが成立・字数・出典・既出との重複を確認し、確認後に残った候補を朝14問・夜14問、合計28問用意する。
  3. 人間が直感でOK・NG・保留を選ぶ。理由の記入は不要。1問ずつ短く提示し、返答が来たら次へ進む。その場でNGの理由を尋ねたり、改善案を議論したりしない。
  4. OKが不足したら、②と③を繰り返す。朝夜を別々に数える。朝7問が揃っても夜5問なら、夜を2問追加で通す必要がある。
  5. 朝7問・夜7問のOKが揃ったら、選んだ14問を仕上げる。つかみ・ヒント・解説・情景などを完成させ、現行の機械検証を行う。
  6. 完成稿を人間が確認する。候補選別のOKは、問題の方向性へのOK。完成稿の承認とは分ける。仕上げで新しい答え漏れや条件不足が出ていないかを見る。
  7. 全問承認後、投入・画像生成・ビルド・動画レビュー・配置へ進む。現在の承認ゲートは残す。

追加候補の数は、不足数の2倍を推奨。例えば初回の判定で朝5問・夜4問がOKなら、不足は朝2問・夜3問。次は朝4問・夜6問を用意する。これは初回28問というユーザー提案を不足時へ適用した運用案で、毎回28問作り直す意味ではない。

枠を満たしたスロットの提示は止める案。残りは「未レビュー」として残し、NG・保留に混ぜない。複数件まとめて判定してOKが目標を超えた場合は、使わないOKを「候補OK・未仕上げ」として残す。どちらも投稿できる完成在庫には数えない。

3. 候補レビューで、何を見せるか

人間向けの表示は以下だけに絞る。採用を説得する長い説明や採点表は付けない。

  • 候補ID・朝／夜。
  • 問題文（最終の80字上限で成立する文面）。
  • 必要な図の内容。図形問題は、配置を理解できる簡単な図や文字配置も添える。全28問の完成イラストを生成する必要はない。
  • 答え。答えだけでは筋が分からない場合に限り、短い解法説明を添える。

出典・確認内容・懸念はAI側の記録に残し、必要なときに開けるようにする。論理の確認は候補段階でも必要で、計算や図形の成立に機械的な確認が要る場合は先に行う。全フィールド向けの検証は仕上げ後に行う。

返答その場の扱い後日の扱い
OK朝／夜それぞれのOK件数へ加算。必要数に達するまでは全項目を仕上げない。選んだ版を仕上げる。問題の仕掛けを大きく変えたら候補判定を取り直す。
NG今回の補充から外す。理由は尋ねず、原案を保存する。振り返り時に改善するか、再提案しないかを決める。理由不明のNGからジャンル全体の禁止を作らない。
保留今回のOK件数へ含めない。原案を保存して次へ進む。余裕のあるときに再評価・修正する。数合わせのため自動でOKへ変えない。

理由の空欄は正しい記録。AIが「簡単すぎたはず」などと補完しない。ユーザーが自発的に一言添えた場合はそのまま保存する。AIの仮説を書くなら、人間の発言と明確に分ける。

完成稿の確認で問題そのものがNGになった場合も、その場で理由の言語化を必須にしない。別の候補OKがあれば差し替え、なければ不足スロットの候補作りへ戻る。文章や図の軽微な修正は従来どおり対応する。

4. NG・保留は、補充用の完成在庫とは別に保存する

保存先の案は content/quiz-stock/logic-training-1/candidates/。1候補1ファイルとし、バッチをまたいで振り返れるようにする。候補は stock_items.py や投入SQLへ混ぜず、仕上げ・承認まで終えた問題だけを完成在庫へ進める。既存のバッチ記録にはIDと参照先を残す。

  • 判定時の原案：候補ID、版、朝／夜、問題文・答え・図の内容・必要な短い説明、出典と確認日。
  • 判定：日時、OK・NG・保留・未レビュー。ユーザーの理由は任意。理由がなければ「未記入」。
  • 振り返り：ユーザーの説明、AIの仮説、改善案、再判定、スキルへ反映した内容と版へのリンク。

原案と元の判定を上書きせず、修正版を追記する。次回の補充ではNG・保留の原案を勝手に再提示しない。振り返って修正版にOKが出たものは再利用できるが、出典・既出・現在の基準を再確認する。明示的に「再提案しない」と決めた候補は、その指定も保持する。

時間がない間は貯めるだけでよい。全件の消化、期限、週次の振り返りを必須にしない。NGが多く候補が集まらない場合は、件数不足を報告して追加探索か中断を選べるようにし、理由の説明を補充の継続条件にしない。

5. 「スキルを育てるスキル」は、クイズ専用から始める案

補充と振り返りは目的が違うため、入口を分ける価値がある。まずは quiz-review-learn（仮称）のようなクイズ専用スキルを推奨する。対象は quiz-stock-replenish と上の候補記録に限定し、ほかのスキルも自動で書き換える汎用の仕組みには広げない。

補充スキル振り返りスキル（新設案）
目的：必要数の問題を揃える。
人間：OK・NG・保留を選ぶ。
AI：調べる、候補を用意する、OKを仕上げる。
NG・保留は記録して次へ進む。		 目的：微妙だった理由を理解し、問題と作問ルールを改善する。
人間：余裕のあるときに対象を選び、理由や好みを説明する。
AI：修正案を作る、再判定を受ける、一般化できる教訓をスキルへ反映する。
  1. ユーザーが振り返りを開始し、NG・保留から今回扱う問題を選ぶ。
  2. 判定時の原案を見て、「何が微妙だったか」「どうすればよいか」を人間とAIで整理する。分からないまま残してもよい。
  3. AIが問題を修正し、必要な確認を行い、人間が再判定する。OKになった問題は候補へ戻し、完成稿承認・投入は補充工程で行う。
  4. 得られた内容を「この問題だけの修正」「次回から使える作問ルール」「まだ仮説」に分ける。
  5. 一般化できる作問ルールは、スキルのどの文をどう変えるかという差分で示す。既存の承認例を誤って排除しないか確かめ、合意した範囲をスキルと参照例へ反映する。
  6. 修正した問題、更新したルール、根拠、未解決の点を保存して終了する。

「理由不明のNGが付いた」「1問にだけ改善が効いた」だけでは共通ルールにしない。一方、ユーザーが共通の方針として明示した場合は同じ指摘を何回も繰り返す必要はない。ルールは追記するだけでなく、重複・矛盾を整理して育てる。

新スキルはこの補充改善を支えるための案として、同じアイデア内で扱う。他セットにも共通化する話が出たら、その時点で汎用化の価値を別途検討する。

6. 今回の案に合わせて、評価方法も変える

候補のNG率が高いこと自体は失敗ではない。選択肢を多めに用意する方式なので、前の「初回に通る率を上げる」だけでは評価できない。

  • 補充中に、ユーザーが理由や改善方法を詳しく説明しなくても必要数のOKを揃えられたか。
  • 完成稿にしてからの問題ごとの差し替えが減ったか。
  • 28候補を読む負担とAIの追加リサーチが、減らした修正負担に見合うか。朝夜のOK率は次の候補数を決める参考にする。
  • 条件不足・答え漏れ・出典不備・画像の作り直しが増えていないか。
  • 振り返りは別作業として時間と成果を記録する。補充時間だけを短く見せず、全体の負担も確認する。

最初の2回の補充で見直す案。過去の人間の読解時間・AIの実働時間は未計測なので、短縮率を推測で出さない。候補NGと完成稿の差し戻しを別々に数え、従来のCodex試行の差し戻し率とは同じ指標として比較しない。

実施時の転記下書き（未起票）

前の「G1で完成稿を用意してから初めて人間レビュー」という区切りは、そのまま流用できない。候補準備 → 人間の選別 → 完成稿の準備 → 人間の承認に分割し、ゴールを使う場合も人間の判断を待つ位置で止める。選別のOKで投入へ進まず、G2・G3相当の工程は完成稿承認後に維持する。
