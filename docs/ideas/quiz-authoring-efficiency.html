quiz-stock-replenish の作問条件と手順の整理

醸成中2026-09-21 / 原文・壁打ち記録
位置づけ（設計書に非ず）採用判断のための検討資料。以下はエージェントの提案であり、採用・スキル変更の承認は未取得。今回は docs/ideas/ 内で壁打ちを行う。既存の作問手順・品質基準をこの資料だけで変更しない。

1. 目的・根拠・不確実性

作問とレビューの手戻りを減らし、同じ品質の問題を継続して補充できるようにする。全項目を書き終えてから問題の核が却下される損失を減らすことを、改善の中心に据える案。

  • 9月w3は朝A45で5回差し替え、夜も全面再点検後に追加の差し替えが発生。9月w1では採用基準から外れると事前申告した問題がその理由で却下された。
  • 一方、9月w3の画像は再生成0回、動画レビューは1巡で承認。直近の記録からは候補選別を優先する根拠があるが、工程別の時間は未計測で、最大の時間要因と断定できない。
  • 収益への接続は、補充の継続性と運用者の時間の確保を介した間接的なもの。採用率向上を視聴者の満足や収益改善の証拠とは扱わない。

2. 論点と推奨方針

論点推奨案注意点・境界
何を短縮するか核の差し替えとレビュー往復を優先。AIの作業時間と人間の判断負担を別に記録する。ユーザーは差し替え・レビュー往復の削減を最優先と回答済み。レビュー待ちの日数をAIの作業時間に含めない。
品質の判定成立・必要条件・字数・答え漏れ・重複は必須確認。面白さは承認例との比較で評価。主観的な面白さを機械的な合格点へ変換しない。AIによる選別は人間承認を代替しない。
難度・驚き通常の読み方・用途・注目先から何を捉え直すかを一文にする。朝は言葉・視覚・参加時の驚き、夜は具体物の用途や配置、手順の転換を中心とする。一手・数値・有名さだけで排除しない。承認済みのタイヤ、計算マジック、9点問題が反例。難しくするための条件追加は避ける。
80字での成立本番同様の問題文と提示図の内容を候補段階で組み、目的と制約が伝わるか確認。問題文80字の上限を変更しない。内部の題名は条件に数えず、図だけで示す情報は検品対象にする。解説で条件を後付けしない。
説明の容易さ解法をキャプション内で再現できるか、候補段階で確認する。「3秒で納得するなら簡単」は使わず、発見しにくさと説明後の分かりやすさを区別する。既存の上限例外を自動で広げない。
候補数・探索の範囲不足数を満たす候補と少数の補欠を短いメモで選別。補欠は全項目を完成させない。大量の候補・採点表・独立したレビュー工程を新設すると逆に遅くなる。ユーザーは承認実績を中心に未採用の発想を少数残す方針を選択済み。初期目安は7問中0〜1問で、品質を満たす候補がない場合は無理に入れない。
調査と自作過去の不採用・既出・補欠を先に照合し、候補を絞ってから出典本文を確認する。出典が同じ問題かまで確かめる。出典未確認と内容不適合を区別。朝の自作承認例はあるが、8月にはリサーチ方針へ戻した経緯もあり、無制限の自作許可とは解釈しない。夜の古典方針も自動変更しない。
レビューの配置AI内部の選別を先行し、完成稿の1問ずつレビューを維持する案。核だけの人間レビューを全問に追加すると往復が増える。ユーザーはAIの事前選別と従来の完成稿レビューの維持を選択済み。方向性が繰り返し外れた場合だけ基準を短く確認する。
却下後の動き表現・条件の不足は修正。発想そのものが却下されたら、同じ核の言い換えを続けず候補を替える。1問の却下をジャンル全体の永久禁止にしない。ユーザーが修正を指定した場合は従う。
反復の上限同じ理由で2候補続けて却下されたら、未提示候補へ同じ欠点がないか再点検し、基準の解釈を短く確認する。回数は運用の初期案で実績由来の最適値ではない。在庫不足を理由に基準を下げない。
ヒントとイラスト完成稿では問題文・図・ヒントを合わせた提示全体で答え漏れを確認。文字・本数・接続・主役の大きさを必要な問題だけに明記する。箱を道具として提示するC43のように答えに使う物自体が登場してよい問題もある。答えの物を隠すことを全問題の必須条件にしない。
記録の負担詳細な採否は各バッチのSTATUS.mdを正とし、横断索引は核・判断理由・日付・参照リンクだけにする。全履歴の再編集や別DBは作らない。明示された共通基準と個別問題の好みを区別し、最新の個別承認を一律の基準変更と扱わない。
検証・自動化候補段階で成立を確認し、全項目を執筆したら現行のvalidate・verify_logic・generateを実施する。高速化のために実行時同等検証を省かない。新しい採点AIや並列エージェント、生成・DB基盤の改修は初回には含めない。
多様性と成果承認実績のある方向でも、解法構造と題材の重複・隣接を避ける。採否の理由を次回へ渡す。承認例の焼き直しだけで候補を埋めない。視聴者のコメント低下はI-034で別途切り分ける。

3. 初回に試す最小の手順案

  1. 在庫と必要数を確認し、最新の共通基準・採否の索引・未使用補欠を読む。既出の最終照合は現行手順どおり投入前にも行う。
  2. 候補ごとに「問題文と必要な図の内容 / 想定解 / 発想の転換 / 成立・説明・既出との懸念」を短くまとめる。核のカードは内部作業用で、ユーザーに全件を読む義務を追加しない。
  3. 条件不足、80字での不成立、単純な答え漏れ、明示的な再提案禁止に当たる候補を外す。出典確認が必要な候補は本文を確認する。出典確認不能は保留とし、別の候補へ進む。
  4. 通過候補だけを全フィールドへ展開し、必要な機械検証と提示全体の答え漏れ確認を行う。図の検品条件は既存の申し送りにまとめる。
  5. 1問ずつレビューし、修正と核の差し替えを分けて記録する。却下理由が他の未提示候補にも当てはまる場合は、提示前に横断点検する。
  6. 承認後は現行の投入・ビルド・全数レビュー・配置へ進む。各工程の承認ゲートは維持する。

不足N問に対する補欠の初期案は各スロット最大2問の核だけ。候補が足りなければ不足分だけ追加探索する。これは完成稿N+2問を毎回作る指示ではなく、作り置きによる無駄を抑える上限案。

4. 初回の変更範囲と費用

  • スキル本文は実行する順序と短い必須確認を中心に整理し、採否の具体例は参照資料へ分離する。条件の追記だけで長文化しない。
  • 採否索引は初期版では9月w1・w3の重要な承認／却下対と明示的な再提案禁止から作り、詳細にはリンクする。全バッチの全面移行は行わない。
  • 補充中の計測は既存STATUS.mdへ、作業区間と採否の短い記録を追加する。調査・核の選別、全項目の執筆・検証、レビュー修正、画像対応を分ける。
  • 初期整備は文書と索引の整理、運用負担は候補メモと計測。費用・時間削減量の見積もりは実測前のため未確定。別サービス・新しい有料ツールは前提にしない。
  • 既存在庫の作り直し、字数・動画構成・投稿頻度の変更、他セットへの横展開、検証ツールの共通化は対象外。

5. 効果の見方

スキル整理後の最初の2バッチを試行とし、各バッチ終了時にレビュー負担とAI作業を評価する案。過去にない時間を推測して比較値を作らない。

  • 核の初回通過率: 初めて提示した候補が核の差し替えなしで最終承認された件数 / 初めて提示した候補数。言い回しだけの修正は核の差し替えに数えない。朝夜別で集計する。
  • レビュー往復: 核の変更、条件の補正、表現、ヒント、図の指示に分けた再提示回数。集計の基礎となる候補・版・結果を記録し、AIが自主廃棄した候補を人間の却下に数えない。
  • 時間: 人間の回答待ち・中断を除き、記録可能な作業区間の合計を承認件数で割る。未計測区間は未計測とする。ユーザーの読解時間は自動で分からないので、負担感を短く確認する。
  • 品質の維持: 必要な機械検証の通過、条件不足・答え漏れ・既出との同型重複による後工程の差し戻し、画像再生成を確認。短縮だけを成功条件にしない。
  • 判断: 記録を集計したうえで、品質を維持しつつレビュー負担が減ったか、追加記録が負担にならないかをユーザーが判断する。増えたら候補メモや索引の項目を減らす。効果が不明なら断定せず次回の観測点を絞る。

Phase 23-3の既存確認待ちには「却下数 / 提出数」がある。上の核の初回通過率は定義が異なるため混同せず、同じ採否ログから必要に応じて両方を集計する。モデル・担当・問題の組合せも記録し、差をスキル変更の効果だけに帰属させない。

8. 確認済みの選択と最終判断

  • 確認済み: 最優先は差し替え・レビュー往復の削減。
  • 確認済み: AIが候補を絞り、完成稿を1問ずつレビューする。全問の二段階人間レビューは追加しない。
  • 確認済み: 承認実績のある方向を中心に、未採用の発想も少数残す。
  • 最終判断待ち: 上記を反映した最小の手順整理を実施する方針とし、今回は実施待ちの記録で壁打ちを閉じるか。具体的な補欠数・反復上限・試行2回は初期の運用案で、試行で調整する。

ユーザーの3回答は進め方の希望であり、スキルの実変更を承認した回答ではない。方針確定後も今回の作業は docs/ideas/ への記録に限定する。
