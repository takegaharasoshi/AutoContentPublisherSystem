## 要旨

umigame-soup-1 のコメント自動返信で、判定と返信文に使っている gpt-6-luna の代わりに Claude Haiku 5.5（`claude-haiku-5-5`）を候補に加える。
評価は既存の全件プローブ（21-6d11 の 525 件 × 6 パターン）に Haiku 版 2 パターンを足して比べる。⑦ = ① luna + 1b の Haiku 版、⑧ = ② luna + 1d-luna の Haiku 版。
**単価は luna と同額**（入力 $0.10 / 出力 $0.50 per MTok。2026-10-08 に公式料金ページで確認）。トークン数の差と思考量の差で実費は前後するが、月 6,000 件で判定の実費はどちらも数百円の幅に収まる。コストは選定の決め手にならず、**決め手はプローブの 16 指標と運用面（拒否・鍵の追加）**になる見込み。
狙いは luna とは別系統のモデルを持つこと。OpenAI 1 社への依存（luna・Decisions とも同じモデル）を減らせる。
開発レーンの作業（`services/comment-reply/` に触れる）なので、詳細を詰めたら転記下書きを作り、21-6e の前に挟むステップとして開発計画へ起こす。

## 壁打ち記録

### 2026-10-08

**コスト面の確認（観点 ④）**

- 出典: https://platform.claude.com/docs/en/about-claude/pricing （2026-10-08 取得）
- Haiku 5.5 の単価は、プロンプトが 10 万トークン以下なら入力 $0.10・出力 $0.50 per MTok で、luna と同額。10 万トークン超は 5 倍になるが、判定のプロンプトは約 2,700 トークンなので関係しない
- キャッシュの読み出しは $0.01 / MTok（入力の 0.1 倍）。書き込みは 5 分保持が 1.25 倍、1 時間保持が 2 倍。最小のキャッシュ長は 512 トークン
- Batch API は半額だが、即時返信には使えない。評価のプローブには使える
- 実費を動かす要素は 3 つある
  - トークナイザー: 同じ文でも Haiku 4.5 比で約 3 割多く数える。luna（OpenAI）との差は日本語の実測が要る
  - 思考量: Haiku 5.5 は思考が既定でオン（effort の既定は medium）。思考トークンは出力として課金される。luna の推論トークンは平均 102
  - キャッシュ: 問題文・真相・確定事実・正解基準は問題ごとに固定なので、system 側をキャッシュに載せられる。5 分以内に同じ問題へのコメントが続けば入力費はほぼ 1 割になる
- 試算（判定 1 回あたり。luna の実績は入力 2,700・出力 144 トークン）

| | 1 件あたり | 月 6,000 件 |
|---|---|---|
| luna（実績） | $0.00035 | 約 310 円 |
| Haiku・キャッシュなし・トークン 3 割増の仮定 | 約 $0.00045 | 約 400 円 |
| Haiku・キャッシュがすべて当たる仮定 | 約 $0.00016 | 約 150 円 |

- 結論: 「コスパが luna 並み」は単価の上では成り立つ。実費の差は月 ±200 円程度で、選定を左右しない。比べるべきは品質（P1〜P7・L1・L2）
- 注意: OpenAI 側も自動のプロンプトキャッシュを持つ可能性があり、現行コードは `cached_tokens` を記録していない。費用を公平に比べるなら両方のキャッシュ実績を記録する

**API の仕様で設計に効く点（観点 ⑤）**

- 構造化出力（JSON スキーマ）は使える。判定の出力形式 `{kind, answer, reply, reason, bare_term}` をそのまま移せる
- `temperature` などのサンプリング指定は送れない（既定値以外は 400）。現行の luna も送っていないので影響なし
- 思考は effort で調整する。`xhigh` と `max` では思考を切れない。luna 判定の `xhigh` に何を対応させるかは決めが要る
- 安全分類器による拒否（`stop_reason: "refusal"`）があり、Haiku 5.5 にはサーバー側の代替モデル切替がない。ウミガメの真相は死や事件を含むことが多く、`general_harms` で誤って断られる恐れがある。プローブでは拒否件数とカテゴリを記録し、本番に入れるなら拒否時に luna へ切り替える
- 実装は公式 SDK（`anthropic`）が推奨。現行は `urllib` 直叩きで依存ゼロなので、Lambda の依存追加とどちらを取るか決めが要る

**論点（ユーザーの判断待ち）**

1. 書き手も Haiku にするか: ⑦⑧ とも「判定 + 返信文の両方を Haiku」で揃えるのが自然。1b は書き手が別呼び出しのため、混在させると比較の意味がぼやける
2. effort の対応: 判定は luna の `xhigh` に合わせるか、`high` / `medium` で安く済むかを見るか。全件の前に 1〜2 問で effort を 2 段比べる小試走を挟む案がある
3. プロンプト: luna 用の `pattern1_rules.txt` をそのまま使う（公平な比較）か、Haiku 向けに手を入れるか。まずはそのまま使い、結果を見て直す案を推す
4. 評価の位置づけ: 21-6e（人間プローブと方式選定）の前に挟んで 8 パターンで選定するか、21-6e は 6 パターンのまま進めて Haiku は後から比べるか
5. 本番の構成: 採用時に luna の置き換えにするか、hybrid の見張り役（Jev の位置）に Haiku を入れて「別系統の二重確認」にするか。後者は Decisions 案で挙がった独立性の弱点を埋められる

**積み残し**: 日本語でのトークン数の実測（`count_tokens`）、拒否の発生率、レイテンシー。いずれも小試走で取れる
