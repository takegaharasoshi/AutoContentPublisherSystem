ウミガメのスープ参加型アカウント

待機 種別: 単発 / 作成 2026-08-28 / 更新 2026-08-28 / 記録層: umigame-soup-set.md 採用条件: Meta コメント Webhook + AI 自動返信 PoC の成功（今すぐ着手）
本書の位置づけ（設計書に非ず） 採用判断のための検討記録（フィージビリティスタディ）。ここに書かれた構成・コスト試算は暫定であり、設計書の正ではない。採用が決まったら docs/app/ / docs/infra/ の設計プロセスにインプットとして引き継ぎ、そこで改めて設計 Fix する。

1. 企画概要

Instagram で「ウミガメのスープ」（水平思考クイズ）を遊べるアカウントを運用する。

  • 1 日 1 本、リールでウミガメのスープの問題を投稿
  • ユーザーはコメント欄で「はい / いいえ / 関係ありません」で答えられる質問をする（例:「男は店員ですか？」「その場所は重要ですか？」）
  • AI が問題の真相を理解した上で出題者役として自動返信する。原則「はい・いいえ・関係ありません」中心、必要なら短い補足。正解そのものはネタバレしない

2. ゲーム体験（コメント欄での推理）

ユーザーA「男は以前この店に来たことがありますか？」
AI      「はい。」
ユーザーA「そのときの出来事が重要ですか？」
AI      「はい。重要です。」

初期版はルールを最大限シンプルにする方針: 質問回数無制限・ユーザーごとの回数を DB 管理しない・除外キーワード管理もしない・コメントは基本すべて AI に判定させる。

2.1 コールドスタート対策（呼び水設計）

参加型フォーマットの最大リスクは初期のコメント欄が空だと「誰も遊んでいない死んだ企画」に見えること（フォロワー 0 スタートでは想定 200 コメント/日は当面成立しない）。対策は次の 3 点（2026-08-28 第 2 回壁打ちで決定）。

  1. リール版面にプレイ例を焼き込む: 動画内で 2〜3 往復の質問 → 回答例を見せる（遊び方の教育 + 参加ゼロでもリール単体で面白さが伝わる）
  2. 本アカウントの固定コメントで質問例をピン留め:「質問例:『男は店員ですか？』のように聞いてください。何問でも OK」を毎回設置
  3. 必要に応じて、運営の助手キャラと明示した公式サブアカウント 1 つが最初の 1〜2 問を質問する（一般ユーザーへの偽装はしない）。1〜2 で足りるうちは作らない
decision: 桜アカウントは見送り（2026-08-28） 偽装した 3〜5 アカウントでコメント欄を賑わせる案は不採用。Meta の非真正行為（inauthentic behavior）規約に該当し、同一環境で運用する既存セット含む全アカウント資産と、真正性審査に敏感な本命収益経路（Meta ボーナス）を巻き添えリスクに晒すため。同じ狙いは上記 1〜3 で達成する。あわせて「翌日の解答編リール」案もシンプル化のため不採用（ユーザー判断）。

2.2 正解の開示方式

解答編リールを作らないため、正解の開示はコメント欄の AI が正解者に「正解です！」と宣言する方式とする（追加実装ゼロ）。誰かが当てるまで問題は開き続け、翌日以降もコメントが付く余地が残る。誰も当てずに流れた問題は初期版では開示しない。

3. AI 出題者の設計

コメント単体ではなく、そのリールに対応する問題情報を一緒に AI へ渡す。

入力内容
問題ある男がレストランでスープを飲んだ。その後、男は自殺した。なぜ？
真相男は過去に遭難しており……（正解全文）
ルール出題者として「はい・いいえ・関係ありません」で回答。必要なら短い補足。真相を直接教えない / 推理の余地を残す / 問題設定と矛盾する回答をしない
ユーザーの質問「男は以前にもこのスープを飲んだことがありますか？」→ AI「いいえ。」

4. アーキテクチャ

設計方針を一言で 「投稿時」と「コメント時」を完全に分離する。投稿時は Aurora を使う（既存 ECS が投稿 + S3 スナップショット保存）。コメント時は Aurora を一切使わず、S3 を media_id キーの Read Only データストアとして使う。

4.1 Webhook Lambda と Reply Lambda を分ける理由

Webhook 受信処理の中で OpenAI まで同期実行する必要はない。Webhook Lambda は SQS へ入れて即時に正常応答し、AI 処理は Reply Lambda で非同期に行う。メリット: Webhook タイムアウトを気にしない / OpenAI の遅延が Webhook に波及しない / コメント急増を SQS で吸収 / リトライ容易 / DLQ で失敗イベントを保全。

5. データ設計（S3 スナップショット）

リール投稿時に既存 ECS が問題・正解を S3 へコピーする。Aurora = マスターデータ、S3 = 公開中問題のスナップショット（コメント処理専用の Read Only データストア）。コメントが何件来ても Aurora にはアクセスしない。

s3://instagram-umigame-production/problems/{media_id}.json

{
  "media_id": "123456789012345",
  "question": "ある男がレストランでスープを飲んだ。その後、男は自殺した。なぜ？",
  "answer": "男は過去に遭難しており……",
  "instructions": { "response_style": "yes_no_irrelevant", "spoiler": false }
}
  • Aurora を切り離す理由: 現行は Min 0 ACU 運用で普段停止。コメントごとに Data API を叩くと 1 日 200 コメントの分散で Aurora が長時間起動し続けるおそれがあるため、コメント処理から完全に切り離す
  • Lambda メモリキャッシュは初期版では不要: 1 コメント = S3 GET 1 回で十分。月 6,000 GET はコスト極小。シンプル優先

6. 1 日の動き

時間帯流れAurora
朝: リール投稿ECS 起動 → Aurora から今日の問題取得（Data API）→ リール生成 → Instagram 投稿 → media_id 取得 → 問題・正解を S3 保存 → ECS 終了起動（従来どおり）→ 0 ACU へ
日中: コメント約 200 件コメント → Webhook → API Gateway → Webhook Lambda → SQS → Reply Lambda → S3 GET → OpenAI → Graph API 返信一度も起動しない

7. MVP スコープ（あえて実装しないもの）

初期版は「コメント → 問題取得 → AI 判定 → 返信」の最小構成。以下は作らない。

  • ユーザーごとの質問回数制限 / コメント回数の DB 管理 /「3 回以上コメントした人には返信しない」処理
  • 禁止ワード DB / 除外キーワード処理 / ルールベースの「はい・いいえ」判定
  • コメント履歴を使った会話状態管理 / Lambda メモリキャッシュ / RDS Proxy / コメント処理からの Aurora アクセス
  • 翌日の解答編リール（シンプル化のため作らない。正解開示はセクション 2.2 の方式）

モデレーションは DB・専用処理を作らず、出題者プロンプト内の一行（質問でないコメント・誹謗中傷には返信内容を返さず定型の受け流し、または「返信しない」判定を返す）のみを最低ラインとする。将来のゲーム化構想（セクション 10）を理由に状態管理を先行実装しない（ステートレス方針の維持）。

8. コスト観

  • 前提: 1 日 1 投稿 × 約 200 コメント × 30 日 = 約 6,000 AI 返信 / 月
  • 追加コストは API Gateway・Lambda・SQS・S3・OpenAI API・CloudWatch。この規模なら AWS 側は極小で、実質的な変動費は OpenAI API 料金のみ
  • Reply Lambda は VPC 外で動かすため NAT Gateway 不要（Aurora と直接通信しないため成立）

9. 問題ストックの供給体制

quiz-stock-replenish の骨格（リサーチ → 執筆 → 検証 → 人間レビュー → 投入）を流用する。ただしウミガメのスープ特有の 3 点を織り込む（2026-08-28 第 2 回壁打ちで決定）。

  • データ構造は 3 項:「問題文 + 真相」ではなく「問題文 + 真相 + 確定事実シート」（世界設定の Q&A 集: 場所・人物関係・時系列・「問題に関係ない事項」の明示）。真相の曖昧さ起因の AI 矛盾回答・捏造回答を、プロンプトではなくデータ側で防ぐ
  • 検証はプローブテスト: 機械検証が効かないため、問題ごとに想定質問 15〜20 問（正解に向かう質問・引っかけ・無関係な質問）を AI 出題者に実際に答えさせ、矛盾・ネタバレを人間が一括レビューする。確定事実シートの穴の発見工程を兼ねる
  • 完全オリジナル問題のみ: 著名問題（本家ウミガメのスープ等）の転載・改変は著作権と非オリジナル対策の両面で不可。執筆難度は logic-training-1 夜スロットの数倍と見込む（AI 下書き大量生成 → 人間選別の歩留まりは低め想定）
  • 補充ペース: 1 日 1 問 = 週 7 問。レビューは週 2 回 × 4 問の運用（一気に 7 問は重いというユーザー判断。既存 2 セットの週次補充と並走可能と確認済み）
  • 夜スロットとのネタ融通はしない: logic-training-1 夜スロット（とんち・水平思考）とはテーマが異なり、ストック共用はカニバリを助長するため不実施

10. 収益接続と将来構想（ゲーム化）

このセット固有の収益モデルは持たない。コメントエンゲージメント → リーチ増幅 → Meta ボーナスという事業戦略書の本命経路への乗り方が、放送型の既存セットより構造的に強いことが企画価値。ボーナスは真正性審査に敏感な経路のため、桜なし運用（セクション 2.1）と整合させる。

将来構想: ゲーム化（再検討トリガー付き・今は判断しない） 大きく当たった場合、専用ゲームへの展開を検討する（ユーザー構想・2026-08-28）: 正解到達回数に応じた得点、ユーザー記録の保持、全体ランキング。収益は広告収入 + ゲーム内課金。ゲームへ移行するメリット（記録・ランキング）を提供する設計。トリガーは「ものすごくバズって流行ったら」。独立アイデアにはせず本アイデアの再検討トリガーとして保持し、MVP はこの構想を理由に状態管理を先行実装しない（ステートレス方針の維持）。

11. 論点の決着一覧（2026-08-28 第 2 回壁打ち）

初回に積み残した 8 論点はすべて決着した。

#論点決着
1収益との接続固有モデルなし。コメント → リーチ → Meta ボーナスの既存本命経路（セクション 10）。将来構想としてゲーム化をトリガー付きで保持
2既存セットとの関係カニバリではなく分化（夜スロットは自己完結クイズ、本セットは多ターン参加型で価値が別物）。ネタ融通もしない。リソース配分は転記時に開発レーンのステップ順序で解決
3問題ストック供給3 項データ構造 + プローブテスト + 週 2 回 × 4 問レビュー（セクション 9）
4Meta 側の前提条件採用条件そのものに格上げ。PoC で実証する（セクション 12）
5モデレーションリスク専用処理は作らず、出題者プロンプト内の一行（非質問・誹謗中傷は受け流し / 無返信判定）を最低ラインとする（セクション 7）
6AI 回答品質確定事実シート（データ側の担保）+ 投入前プローブテストで検知（セクション 9）
7運用監視初期版は DLQ アラームを既存 MonitoringStack へ追加するのみ。詳細は採用後の設計で Fix
8効果仮説「コメント率（コメント数 / リーチ）が既存セット比で有意に高く、リーチの伸び率に転化する」。16-5 で確定する指標セットにコメント系指標を接続して検証

12. 採用条件と次アクション（PoC）

decision: 採用条件は「PoC 成功」のみ・ステータスは待機（2026-08-28） 当初候補だった「16-5 効果検証の完了」ゲートは議論の結果外した（16-5 は参加型フォーマットの成否を予測しない / 着手 → 稼働のリードタイム数週間の間に 16-5 の結果は自然に出る / 実制約はレビュー帯域〔クリア済み〕と開発レーンの直列化〔転記時のステップ順序で解決〕）。PoC が成功したら採用とし、開発計画（新セットのフェーズ起案）・事業戦略書（セットポートフォリオ）へ転記する。PoC は今すぐ着手（ユーザー決定）。

PoC の内容: 使い捨ての Meta アプリ + 最小 Lambda で「自アカウントのリールに付いたコメントを Webhook で受信し、Graph API で自動返信できる」ことを実証する。自アカウント運用ならアプリの開発モード（ロール保持アカウント）で App Review なしに動く公算があるが、仕様変更が多い領域のため実測で確認する。失敗（権限が取れない・返信が拒否される等）の場合は企画の根幹が不成立となり、見送りまたはピボットの再壁打ちを行う。
