## 原文メモ

### 2026-08-28（初回持ち込み。原文そのまま）

1. アカウントのテーマ・企画

Instagramで「ウミガメのスープ」を遊べるアカウントを運用する。

【基本アイデア】
・1日1本、リールでウミガメのスープの問題を投稿
・ユーザーはコメント欄で質問する
・AIが出題者役として自動返信する

【基本ルール】
ユーザーは、

「男は店員ですか？」
「その場所は重要ですか？」
「死人は出ていますか？」

など、

「はい」
「いいえ」
「関係ありません」

で答えられる質問をコメントする。

AIは問題の真相を理解した上で、
原則として

・はい
・いいえ
・関係ありません

のいずれかを中心に返信する。

必要であれば短い補足も返すが、
正解そのものはネタバレしない。

2. コメント欄でのゲーム体験

Instagramのリール投稿
→ ユーザーA「男は以前この店に来たことがありますか？」
→ AI「はい。」
→ ユーザーA「そのときの出来事が重要ですか？」
→ AI「はい。重要です。」

という形でコメント欄上で推理を進める。

現時点では、ユーザーごとの質問回数制限などは設けない方針。

・何回質問してもOK
・ユーザーごとの質問回数をDB管理しない
・除外キーワード管理も一旦しない
・基本的にコメントはすべてAIに判定させる

つまり初期版は、なるべくルールをシンプルにする。

3. AIに渡す情報

コメントだけをAIに渡すのではなく、そのリールに対応する問題情報も一緒に渡す。

AIへの入力イメージ

【問題】ある男がレストランでスープを飲んだ。その後、男は自殺した。なぜ？
【真相】男は過去に遭難しており……
【ルール】あなたはウミガメのスープの出題者です。ユーザーの質問に対して、原則として「はい・いいえ・関係ありません」で回答してください。必要なら短い補足を加えてください。ただし、真相を直接教えない・ユーザーが推理できる余地を残す・問題設定と矛盾する回答をしない。
【ユーザーの質問】「男は以前にもこのスープを飲んだことがありますか？」

これに対して生成AIが「いいえ。」などを返す。

4. Instagramコメント自動返信の基本フロー

ユーザー → Instagramリールにコメント → Meta Webhook → API Gateway → Webhook Lambda → SQS → Reply Lambda
Reply Lambda: S3から問題・正解を取得 / OpenAI APIで回答生成 / Instagram Graph APIで返信

Webhookでコメント発生を検知する。そのコメントに対応するリールの media_id を使って、どの問題なのかを特定する。

5. Webhook LambdaとReply Lambdaを分ける理由

InstagramからWebhookを受けた処理の中で、OpenAIまで全部同期実行する必要はない。
Webhook Lambda は SQS へイベントを入れて Instagram にはすぐ正常レスポンス。実際のAI処理は SQS → Reply Lambda で非同期に行う。

【メリット】
・Webhookのタイムアウトを気にしなくていい
・OpenAIが一時的に遅くてもWebhookに影響しない
・コメントが大量に来てもSQSで吸収できる
・失敗したコメントをリトライしやすい
・DLQを使って失敗イベントを残せる

6. 既存の投稿システム

すでにECSからInstagramへ投稿する仕組みがある。そのため、新しく投稿Lambdaは作らず、既存ECSを利用する。

【現在】Aurora →(Data API)→ ECS → Instagramへリール投稿
【変更後】ECS が Instagramへリール投稿して media_id を取得し、あわせて S3 へ問題情報を保存する処理を追加

7. AuroraではなくS3をコメント処理に使う理由

現在のAuroraは Serverless v2 / MinCapacity = 0 ACU で普段は停止している。既存用途では1日に数回程度しか起動しないため、DBコストはかなり小さい。
しかしコメントごとにData APIを実行すると、Auroraが0 ACUから起動する。1日200コメント来る場合、コメントが分散するとAuroraが長時間起動したままになる可能性がある。
そのため「コメント処理からAuroraを完全に切り離す」設計にする。

8. S3に保存する仕組み

リール投稿時に、問題と正解をS3へコピーする。

s3://instagram-umigame-production/problems/{media_id}.json

JSON例：
{
  "media_id": "123456789012345",
  "question": "ある男がレストランでスープを飲んだ。その後、男は自殺した。なぜ？",
  "answer": "男は過去に遭難しており……",
  "instructions": { "response_style": "yes_no_irrelevant", "spoiler": false }
}

9. コメント返信時の処理

コメントが来たら、Webhook → コメント情報取得 → 対象リールの media_id 取得 → S3 の problems/{media_id}.json を取得 → 問題文・正解・AIルール・ユーザーコメントを OpenAI へ送る → AI回答 → Instagram Graph API でコメント返信。
重要なのは「コメントが何件来てもAuroraにはアクセスしない」という点。

10. 当初検討していた「キャッシュ」について

当初は Aurora → キャッシュ → Lambda という考え方もあった。ただ、今回の要件ではユーザー状態を保持しないため、もっと単純にできる。
Aurora = マスターデータ、S3 = Instagram公開中問題のスナップショット。つまり S3 は単なる高速キャッシュというより「Instagramコメント処理専用の Read Only データストア」として使う。

11. Lambdaメモリキャッシュは初期版では不要

最初の1回だけ S3 から取得して Lambda メモリに保持する最適化もできるが、初期版では必要ない。1コメント = S3 GET 1回 → OpenAI → Instagram返信で十分。月6,000回程度のS3 GETならコスト的にも非常に小さい。まずシンプルな実装を優先する。

12. 現時点のAWS全体構成

（詳細 HTML の構成図を参照。Aurora → ECS →（Instagram投稿・S3保存）、Instagram コメント → Meta Webhook → API Gateway → Webhook Lambda → SQS → Reply Lambda →（S3 / OpenAI API / Graph API 返信））

13. 1日の具体的な動き

【朝：リール投稿】
1. ECS起動 2. Data API経由でAuroraから今日の問題取得 3. リール動画生成・取得 4. Instagramへ投稿 5. media_id取得 6. media_id + 問題 + 正解をS3保存 7. ECS処理終了 8. Auroraは条件を満たせば0 ACUへ戻る

【昼：コメント200件】
ユーザーコメント → Webhook → API Gateway → Lambda → SQS → Reply Lambda → S3 GET → OpenAI → Instagram返信
この間、Auroraは一度も起動しない。

14. 初期版で「あえて実装しないもの」

× ユーザーごとの質問回数制限
× コメント回数DB管理
× 「3回以上コメントした人には返信しない」処理
× 禁止ワードDB
× 除外キーワード処理
× ルールベースでの「はい / いいえ」判定
× コメント履歴を使った複雑な会話状態管理
× Lambdaメモリキャッシュ
× RDS Proxy
× コメント処理からのAuroraアクセス

まずは、コメント → 問題取得 → AI判定 → 返信という最小構成を作る。

15. コスト面の考え方

1日1投稿・1投稿あたり約200コメント・30日運用 → 約6,000 AI返信 / 月。
既存Auroraを使用 + InstagramコメントではAuroraを起動しないため、主要な追加コストは API Gateway・Lambda・SQS・S3・OpenAI API・CloudWatch。月6,000コメント程度なら AWS 側は非常に小さく、「実質的にはOpenAI API料金が主要な変動費になる」と考えてよい。
NAT Gateway も基本的には不要。Reply Lambda は VPC 外で動かし、S3・OpenAI・Instagram へアクセスする。Aurora とは直接通信しないため、Lambda → VPC → NAT Gateway という構成を避けられる。

16. 今回の設計方針を一言でまとめると

「投稿時」と「コメント時」を完全に分離する。
投稿時は Aurora を使う（既存 ECS が投稿 + S3 保存）。コメント時は Aurora を一切使わない（S3 スナップショットを media_id キーで取得）。

この構成にすることで、
・既存のECS + Auroraの投稿システムをほぼ変更しない
・Aurora Serverless v2の0 ACU運用を維持しやすい
・コメントによってAuroraが頻繁に起動する問題を防げる
・NAT Gatewayを不要にできる
・コメント数が増えてもSQSで吸収できる
・AI返信処理を独立してスケールできる
・MVPとして実装が比較的シンプル
