1. 設計原則

  1. インフラとアプリの関心の分離: インフラ設計（docs/infra/）とアプリ設計（docs/app/）を明確に分ける。設計はインフラ → アプリの順に Fix し、インフラ構築はアプリ実装より先に行う。アプリ設計は 2 段階で行い、大枠（設計書構成・主要方針の骨子）は Phase A で、詳細は Phase 9 で作成する（2026-07-06 にインフラ構築より前へ前倒し。インフラ構築の知見反映は Phase 10 冒頭の最終 Fix で行う。経緯は plans/development-plan.html を参照）
  2. 完璧より前進（一時 Fix 運用）: 設計書は「次フェーズの作業に着手できる」水準で一時 Fix とし、先に進む。詳細はセクション 4 の Fix 基準を参照
  3. 実装を正とする: 設計と異なる実装をした場合は、実装に合わせて設計書を修正する（変更理由はページ末尾の判断の記録に残す。未移行のページは従来の decision 囲み）
  4. 同じ情報を 2 箇所に書かない: 詳細の「正」は 1 つのドキュメントに置き、他からは参照リンクで辿る
  5. 2 面と 3 段で描く: システムを生産面（スキルで素材・動画を事前に作り、人がレビューして S3 / DB へ置く）と配信面（AWS 上のバッチが選んで投稿し、インサイト収集・コメント自動返信・トークン更新を回す）の 2 面で描き、設計書は基本設計 → 層の概要 → 詳細設計の 3 段で読めるようにする（セクション 2.1。Phase 30・I-040）
  6. 事業とシステムの分離: 事業の意思決定（収益化戦略・予算・KPI・プラットフォーム展開方針）は事業戦略（docs/strategy/）に書き、システム設計書（docs/infra/・docs/app/）には書かない（2026-07-23 に層を新設。Phase 14-1）

2. ドキュメント構成

2.1 3 段の構成（基本設計（全体）→ 機能別の基本設計 → 詳細設計）

設計書は、上の段だけ読めば全体が分かり、必要なときだけ 1 段ずつ下へ降りられるように 3 段で組む。1 段目は全体を 1 ページで見る基本設計（全体）、2 段目はシステムの機能ごとに 1 ページずつの機能別の基本設計、3 段目は設定値・手順・表の全件を持つ詳細設計。ディレクトリは再編せず、既存の infra/ app/ と新設の production/ を詳細設計に位置づける（計画書・記録・課題表からのリンクを切らない）。

図 1 は 3 段のつながりを表す。実線は「機能の詳細をたどる」道筋で、基本設計（全体）から機能ページへ、機能ページから詳細設計へと 1 段ずつ降りる。点線は、基盤やデータ全体のようにどの機能にも属さない横断の内容で、基本設計（全体）から詳細設計の層のページへ直接つなぐ。

次の表は、段ごとの置き場所と、その段だけで分かることをまとめたもの。

段置き場所ここだけで分かること
基本設計（全体）docs/overview/system-overview.html2 面（生産面 / 配信面）の構成、機能の一覧、2 面の受け渡しの契約、データの流れ、構成要素の一覧
機能別の基本設計docs/overview/functions/（配信面: 投稿・インサイト収集・コメント自動返信・トークン更新〔30-3b〕/ 生産: 生産ライン（共通）・logic-training-1・pref-ranking-1・umigame-soup-1〔30-3c〕）その機能の目的・きっかけ・入力と出力・流れ・関わる部品・ほかの機能との受け渡し

4. 設計 Fix 基準とレビュー運用ルール

「生成 AI レビューの指摘が尽きず設計が Fix しない」問題の再発防止ルール。設計書の作成・レビュー時は必ずこのルールに従う。

4.1 Fix 基準（Definition of Done）

  • 設計書は「次フェーズの作業に着手できる」水準で一時 Fix とする
  • インフラ設計の Fix 基準: 開発計画 Phase 0〜8 の各ステップが着手できる程度に、CDK リソース・設定値・手順が決まっていること
  • 「生成 AI の指摘ゼロ」を Fix 条件にしない。AI は何度でも改善提案を出せるため、指摘ゼロを目指すと原理的に終わらない
  • 実装中に判明した設計の誤りは、実装に合わせて設計書を修正すればよい（設計原則 3）。だからこそ一時 Fix で先に進んでよい

4.2 レビュー運用ルール

  1. 観点を限定する: 生成 AI にレビューさせる際は、必ず観点を明示指定する（レビュープロンプトのテンプレートは plans/development-log.html の Phase D（D-2 備考）を参照）。観点を指定しないフリーレビューは行わない
  2. 指摘を分類する: 指摘は「blocker（誤り・矛盾・欠落で、次フェーズの作業を妨げるもの）」と「改善提案（あった方が良いが、なくても作業は進められるもの）」に分類する
  3. blocker のみ修正する: 改善提案は修正せず、課題体系（issues/index.html）に据え置き課題として起票（トリガー付き）して Fix を妨げない（2026-09-19 までは plans/development-plan.html の「設計課題リスト」。既存行は Phase 22-2 で課題体系へ移設）
  4. レビューは最大 2 巡まで: 3 巡目以降の指摘はすべて課題体系行きとし、レビューを打ち切って Fix を宣言する
  5. YAGNI: 将来拡張（AdminApiStack 等）は「拡張ポイントがある」ことの記載まで。詳細設計はしない

5. 書式ルール（Phase 30-1）

設計書（docs/overview/ docs/infra/ docs/app/ docs/production/）の書き方。見本は 設計書ページの雛形で、新しいページはこれをコピーして作る。既存のページは Phase 30 の各ステップで順にこの書式へ移す（移すまでは従来の書き方のままでよい）。docs/plans/ docs/issues/ docs/ideas/ docs/strategy/・壁打ち記録（requirements-notes*.html）・docs/_archive/ は対象外で、それぞれの体系のルールに従う。

5.1 ページの並び

位置書くこと書き方
冒頭の要約図 1 枚 + 要点の表。そのページの全体がここだけで分かるようにするh1 とページ情報の直後に <section class="page-summary" id="summary"> を 1 つ置く
リード文各章・各図表の前に、「この章で何を説明するか」「この図・表は何を表すか」を日本語の文章で書く。章のリード文では、その章がどの上位の章・ページを詳しくしたものかも書く（例:「この章は 1 章の生産面を工程の単位まで詳しくしたもの」）<p class="lead">。図・表をリード文なしで始めない（要約の図も同じ）
本文事実だけ（何がある・どう動く・どこに何を置く・設定値）。図と表を中心にする理由・経緯・比較した案は書かず、判断した箇所に <a class="decision-ref" href="#d-01">→ 理由 D-01</a> を置く
さらに詳しく章の末尾に、その章の内容を 1 段下で詳しく書いた資料（同じページの後の章・詳細設計・セット別設計書・SKILL.md）へのリンクを並べる。「何を見たいならどこ」の形で書く（段階的詳細化のつながり）<div class="drilldown"><span class="drilldown-title">さらに詳しく</span><ul>…</ul></div>。1 段下だけを指す（基本設計〔全体〕からは機能ページか同じページの章へ、機能ページからは詳細設計へ。段を飛ばさない。基盤・データなど横断の内容だけは基本設計〔全体〕から層のページへ直接つなぐ）。機能ページから詳細設計へは観点ごとに 1 リンク（処理の詳細 / AWS の定義 / 運用の手順）。詳しくする先がない章は置かない
判断の記録本文の判断の理由。1 件 = 1 判断ページ末尾に <section class="decisions" id="decisions"> を 1 つ置く（5.2）

5.2 判断の記録

  • 判断は D-01 からページごとに採番し、1 件を <article id="d-01">（見出し D-01 タイトル）で書く。中身は「決めたこと / 理由 / 退けた案（あれば）/ 日付・出典」の定義リスト
  • 本文からは同じページの判断の記録へ片方向にリンクする（判断の記録から本文へは戻りリンクを張らない）。リンクの表示に番号（D-01）を入れる
  • 番号は振り直さない。判断が覆ったら新しい番号で書き、古い記録の決めたことに「D-07 で変更」と書き足す
  • 従来の decision 囲み（本文中の判断の囲み）は新しい書式のページでは使わない
  • tools/docs_check.py が、判断リンクが同じページの section#decisions の中の d-NN を指していること・表示に番号が入っていることを確かめる

5.3 図の描き方

  • 図は Mermaid で文字で書く（<figure class="diagram"><pre class="mermaid">…</pre><figcaption>図 n …</figcaption></figure>）。構成・処理の流れ・データ・状態など、文章より図の方が早く分かるものは積極的に図にする。使い分け: 構成図 = architecture-beta（AWS アイコン）か flowchart / 処理の順序 = sequenceDiagram / テーブル = erDiagram / 状態 = stateDiagram-v2
  • pre.mermaid の中は HTML として読まれるため、< > & は文字参照で書く（改行の <br> も &lt;br&gt;）。矢印の --> はそのままでよい
  • 縦向きの流れを基本にする（flowchart TB 等。スマホで縮みすぎないため）。横に広くなる図だけ <figure class="diagram" data-wide> にして、縮めずに枠の中で横スクロールさせる
  • AWS のサービスは aws:<名前> のアイコンで描く（例: service sfn(aws:step-functions)[Step Functions]）。使える名前は tools/docs_aws_icons.py の ICON_NAMES
  • 配色・字体は docs/assets/docs-diagrams.js が style.css の変数から 1 か所で決める。図の中で色を指定しない（style / classDef で色を書かない。ライト / ダークで崩れるため）
  • 図は「拡大」ボタンで全画面に開き、拡大・縮小・移動できる（svg-pan-zoom）。小さく読めない図は分けるか縦にする
  • 図を使うページは本文の後（</body> の直前）で次の 4 本を順に読む（相対パスはページの深さに合わせる）: vendor/mermaid-12.1.0/mermaid.min.js → vendor/svg-pan-zoom-3.6.2/svg-pan-zoom.min.js → vendor/aws-icons-07312026/aws-icons.js → docs-diagrams.js
  • tools/docs_check.py は図の描画完了を待ってから横はみ出しを測り、描けなかった図を不備として数える

5.4 使ってよいライブラリ

6. 更新ルール

  • コードやインフラに変更を加えた際は、対応する設計書も同時に更新する
  • 設計と異なる実装をした場合は、実装に合わせて設計書を修正し、変更理由をページ末尾の判断の記録（セクション 5.2）に残す（新しい書式へ移す前のページは従来の decision 囲み）
  • 同じ情報を複数ドキュメントに書かない。詳細は 1 箇所に書き、他からは参照リンクを張る
  • 設計書は HTML（本体系）で記述する（計画・記録も Phase 18 で HTML 化済み）。書式はセクション 5
  • 表は必ず <div class="table-wrap"> で包む（狭い画面で列幅を保ち、収まらない分を表内の横スクロールへ逃がすための共通規則。Phase 24-1）。HTML の機械検証は python3 tools/docs_check.py（対象件数・リンク / アンカー整合・図の描画完了を待った指定幅の横はみ出し・判断リンクの飛び先）

7. 旧設計書（_archive）について

docs/_archive/ には旧 Markdown 設計書を保管している。これらは現役の設計書ではない。特にアプリ設計（バッチ処理フロー・DB スキーマ・冪等性設計）はよく検討された内容を含むため、Phase 9 のアプリ設計で参考資料として活用する。
