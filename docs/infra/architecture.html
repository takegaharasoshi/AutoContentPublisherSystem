要約

このページは、配信面（AWS）で使っているサービスと、その組み合わせ方を説明する詳細設計で、基本設計（全体）の配信面と、機能別の基本設計（投稿・インサイト収集・コメント自動返信・トークン更新）の AWS の構成を詳しくしたものである。配信面は 4 つの系統（①投稿 ②インサイト収集 ③コメント自動返信 ④トークン更新）からなり、①②は Step Functions が ECS Fargate のバッチを動かし、③④は Lambda で動く。共通の土台（VPC・Aurora・S3・Secrets Manager・ECS クラスター）のうち、①②のバッチは VPC の中で全部を使い、③④の Lambda は VPC の外から S3・SQS・Secrets Manager だけを使う。生産面（ローカル PC）はこの土台の S3 と Aurora に素材を置くだけで、AWS 上には生産面の部品はない。

図 1 は、4 系統と共通の土台を AWS のアイコンで表したもの。上段が時刻で動く系統（①②④）、中段が Instagram の通知で動く系統（③）、下段が共通の土台。続く表はこのページの要点。

Phase 31 で 5 つ目の系統 ⑤ 脳みそコーチの正解返信（Scheduler → Lambda 1 本・VPC 外・Aurora 非接続・CoachReplyStack）を足す。31-4 で AWS に載るまでは図 1 に描かず、構成は stacks.html 3.7 と機能別の基本設計を正とする（AWS に載せた時点で図 1 に足す）。

項目要点
リージョン・環境ap-northeast-1。本番 1 環境（コメント自動返信だけ、確認用のステージング面を持つ → 理由 D-06）
実行基盤バッチは ECS Fargate の RunTask（ECS Service は使わない）、①②は Step Functions Standard が動かす。③④は Lambda
ネットワークVPC 1 つ・NAT Gateway なし。Fargate はパブリックサブネットでパブリック IP を持ち、Aurora は隔離サブネット → 理由 D-01。Lambda は VPC の外
データストアAurora Serverless v2（MySQL 互換・自動一時停止）・S3 バケット 1 つ・Secrets Manager
監視・配備CloudWatch のアラームと EventBridge ルールから SNS トピックへ通知。ECS のバッチは CodePipeline でイメージを更新し、インフラと Lambda は手動の cdk deploy

2. ネットワーク構成

この章は、VPC の分け方と、各部品がどの経路で外部や他の部品とつながるかを示す。ECS のバッチは VPC の中、Lambda は VPC の外で動く。

2.1 VPC

要素構成
VPC1 つを全バッチで共有（2 AZ）
パブリックサブネット各 AZ に 1 つ。ECS Fargate のタスクを置き、パブリック IP（assignPublicIp=ENABLED）で Internet Gateway から外へ出る
隔離サブネット各 AZ に 1 つ。Aurora を置く（インターネットへの経路なし）
NAT Gateway使わない → 理由 D-01
VPC エンドポイントS3 の Gateway 型だけ → 理由 D-07
Security Groupバッチ共通の Security Group はインバウンドをすべて拒否する。Aurora の Security Group は、バッチ共通の Security Group と DB 準備確認専用の Security Group からの接続だけを受ける（規則の詳細はセキュリティ設計）

ECS Fargate のタスクはパブリック IP を持つため、バッチ共通の Security Group にインバウンドの許可を足してはならない。リソースを足すときも同じ Security Group を流用しない。

次の表は、配信面の部品から各接続先への経路。

接続元接続先経路
ECS Fargate外部 API（Instagram Graph API）パブリック IP → Internet Gateway
ECS FargateAuroraVPC の中（Security Group で制御）

ECS FargateSecrets Manager・CloudWatch Logsパブリック IP → Internet Gateway（TLS）
Instagram動画（投稿時）S3 の署名付き URL（標準エンドポイント）をインターネットから取得する

3. コンピューティング

この章は、処理を実際に動かす部品（ECS のタスク定義・Step Functions・EventBridge Scheduler・Lambda）を種類ごとに一覧にする。ステートの並びや Retry の値など、ワークフローの定義はワークフローにある。

3.1 ECS Fargate

ECS クラスターは 1 つで全バッチが共有し、ECS Service は使わず RunTask だけで動かす → 理由 D-08。次の表は 4 つのタスク定義。

タスク定義（family）中身CPU / メモリ起動元
acps-prod-db-readiness-checkAurora の起動を待って接続を確かめる256 / 512 MiB3 つの SFN の先頭
acps-prod-image-batch当回の動画を在庫から選んで登録する1024 / 2048 MiBimage-generation-sfn
acps-prod-sns-post-batchInstagram へ投稿する256 / 512 MiBsns-posting-sfn
acps-prod-insights-batchインサイトとコメント記録を集める256 / 512 MiBinsights-collection-sfn

SFN はタスク定義を family 名で指定し、常に最新の ACTIVE なリビジョンを動かす。イメージは ECR の 4 リポジトリ（auto-content-publisher/{image-batch, sns-post-batch, insights-batch, db-readiness-check}）に置く。

3.2 Step Functions

ステートマシンは 3 つで、すべて Standard。次の表はその構成（ステートの定義と Retry / Catch はワークフロー 3・4・11 章）。

ステートマシンステートの並び起動元
acps-prod-image-generation-sfnDB 準備確認 → 選定のバッチ → 投稿の SFN を非同期で起動EventBridge Scheduler
acps-prod-sns-posting-sfn入力の確認 → DB 準備確認 → 投稿のバッチ選定の SFN（手動の単独実行もできる）
acps-prod-insights-collection-sfnDB 準備確認 → 収集のバッチEventBridge Scheduler

入力のセットコードと予定時刻を ECS タスクの環境変数として渡し、実行 ID を EXECUTION_ARN として渡す。各 Task ステートには明示のタイムアウトがある。Standard には同時実行数を制限する機能がなく、同じセットのバッチが重ならないようにスケジュールの間隔を空けている → 理由 D-09。

3.3 EventBridge Scheduler

スケジュールは CDK を唯一の正として定義し、3 つのグループに分かれる。次の表は各グループの役割（個々のスケジュールの一覧はワークフロー 1 章）。

グループターゲット本数起動に失敗したとき
acps-prod-image-schedule-groupimage-generation-sfnセット × 時刻（5 本。うち 1 本は停止中）再試行 → SQS DLQ acps-prod-image-scheduler-dlq
acps-prod-insights-schedule-groupinsights-collection-sfnセット × 朝夕（6 本）再試行 → SQS DLQ acps-prod-insights-scheduler-dlq
既定のグループ（CommentReplyStack）トークン更新の Lambda面ごとに 1 本（月曜 04:00）再試行（Lambda の中の失敗は Errors アラーム）

3.4 コメント自動返信とトークン更新（Lambda）

コメント自動返信は、外部（Meta の Webhook）からの要求を受け、ユーザーに向けて自動で発信する唯一の経路である。投稿のバッチとは独立し、VPC の外で Aurora を使わずに動く → 理由 D-05。図 2 はこの経路の AWS 構成で、トークン更新の Lambda も同じスタックにある。

要素構成
受け付けLambda acps-prod-comment-reply-webhook の関数 URL（認証タイプ NONE）。署名（X-Hub-Signature-256。HMAC-SHA256・鍵は Instagram アプリの秘密鍵）を検証し、自分の返信を除いて SQS に入れ、すぐ応答を返す → 理由 D-04
キューSQS FIFO acps-prod-comment-reply.fifo。再配信の上限を超えたメッセージは DLQ acps-prod-comment-reply-dlq.fifo へ移る
返信Lambda acps-prod-comment-reply-reply（SQS をイベントソースに 1 件ずつ処理）
トークン更新Lambda acps-prod-comment-reply-token-refresh（Scheduler から週 1 回）
データS3 の問題スナップショット assets/umigame-soup-1/problems/{media_id}.json（投稿のバッチが公開に成功した直後に PUT する。ステージング面は assets/umigame-soup-1/staging/problems/）を読み（該当プレフィックスだけを許可）、comment-log/ に書く。Aurora・VPC・NAT には依存しない
秘密情報Secret acps/prod/umigame-soup-1/comment-reply（Webhook の検証用トークン・アプリの秘密鍵・Instagram のトークン・LLM の API キー）
面同じ定義から本番面（CommentReplyStack）とステージング面（CommentReplyStagingStack。テスト用の Meta アプリとアカウント）を作る → 理由 D-06。本番面はプライバシーポリシーの公開バケット acps-prod-umigame-privacy-policy も持つ

7. デプロイ方式

この章は、変更が本番に届く経路を示す。経路は「ECS のバッチのイメージ」と「それ以外（インフラと Lambda）」の 2 つに分かれる。

変更するもの経路
ECS のバッチ（image-batch・sns-post-batch・insights-batch）main への push → CodePipeline → CodeBuild → ECR へ push → タスク定義の新しいリビジョンを登録。Blue/Green・ECS Service は使わない → 理由 D-08
インフラ・Lambda（comment-reply）・db-readiness-check手動の cdk deploy
さらに詳しく
  • スタックごとのリソースの定義・デプロイの順番・スタック間の受け渡し → CDK スタック実装仕様
  • SFN の定義・スケジュールの一覧・環境変数・アラーム → ワークフロー
  • IAM・Secret・ネットワークの規則 → セキュリティ設計
  • パイプラインの動き → CI/CD 設計
  • デプロイ後の確認・コスト・運用 → インフラ運用

判断の記録

本文の「→ 理由 D-xx」から飛んでくる先。

D-01 NAT Gateway を使わず、Fargate にパブリック IP を持たせる

決めたこと
ECS Fargate のタスクをパブリックサブネットに置き、パブリック IP で外へ出る。Aurora だけを隔離サブネットに置く
理由
NAT Gateway の費用を払わないため。インバウンドはバッチ共通の Security Group で全拒否にする
退けた案
プライベートサブネット + NAT Gateway（セキュリティ要件が強まったときの移行先として残す）
日付・出典
当初設計（Phase D〜1）

D-02 DB 準備確認を ECS タスクにし、SFN の先頭に置く

決めたこと
Aurora の起動待ちと接続確認を独立した ECS タスクにし、すべての SFN の最初のステートで動かす
理由
DB の再試行をバッチのコードから外し、バッチは DB が使える前提で書けるようにするため。Lambda にしなかったのは、VPC の中の Lambda はパブリック IP を持てず、NAT Gateway か Interface 型のエンドポイントなしでは Secrets Manager に届かないため（Fargate の起動の遅さ 30〜60 秒はバッチでは許容でき、費用も月 $0.01 未満）
日付・出典
当初設計。ワークフロー 2 章

D-03 Webhook は API Gateway を使わず Lambda の関数 URL で受ける

決めたこと
関数 URL（認証タイプ NONE）で受け、Meta の署名を Lambda の中で検証する
理由
WAF やスロットリングが要るまで API Gateway は不要で、関数 URL は無料のため
日付・出典
Phase 21-1（⑥ の決定）・21-3

D-04 受け付けはキューに入れてすぐ応答する

決めたこと
受け付けの Lambda は署名の検証と自分の返信の除外だけを行い、SQS FIFO に入れて即座に 200 を返す。判定と返信は別の Lambda が行う
理由
応答が遅れると Meta が Webhook を再送するため
日付・出典
Phase 21-3（設計）・21-6（実装）

D-05 コメントの経路は VPC の外で、Aurora を使わない

決めたこと
返信の Lambda は S3 の問題スナップショットだけを読み、記録も S3 に書く
理由
コメントが何件来ても Aurora を起こさず、VPC・NAT にも依存しないため
日付・出典
Phase 21-3

D-06 ステージング面はコメント自動返信の経路だけに持つ

決めたこと
フルのステージング環境は作らず、外部へ発信するコメント自動返信の経路だけを本番面とステージング面の 2 面で持つ
理由
日次バッチは影響の範囲が小さく、ソロ運用の維持費と月 2 万円の予算に見合わない。外部へ発信する経路だけは本番の投稿に触れずに試す必要がある
日付・出典
2026-08-28（課題 I-027）・Phase 21

D-07 S3 には Gateway 型の VPC エンドポイントを使う

決めたこと
ECS から S3 への通信は Gateway 型のエンドポイントを通す
理由
無料のため（Interface 型のエンドポイントは費用がかかるので使わない）
日付・出典
当初設計

D-08 ECS Service と Blue/Green を使わず、RunTask とリビジョン登録で配備する

決めたこと
バッチは RunTask だけで動かし、イメージを更新したらタスク定義の新しいリビジョンを登録する。SFN は family 名で最新を動かす
理由
常駐しないバッチ用途で、切り替えの仕組みが要らないため
日付・出典
当初設計。CI/CD 設計

D-09 同時実行はスケジュールの間隔で避ける

決めたこと
Step Functions には同時実行数の上限を設けず、同じセットのバッチの起動間隔を実行時間より十分長くとる。データの整合（DB の排他）はアプリ側で扱う
理由
Step Functions Standard にはステートマシンの同時実行数を制限する機能がないため
日付・出典
当初設計

D-10 Aurora は最小 0 ACU で自動一時停止させる

決めたこと
0 ACU の自動一時停止に対応する版を使い、使わない時間は止める
理由
バッチは 1 日数回しか動かず、止めている時間の費用を払わないため
日付・出典
当初設計。基本設計（全体）D-06

D-11 S3 の自動削除は生成物のプレフィックスだけにする

決めたこと
30 日の自動削除は images/・videos/・comment-log/ だけに掛け、ビルド済み動画・問題スナップショット・BGM は残す
理由
長く使う素材（BGM のストックなど）が自動で消えないようにするため。コメント記録は DB への取り込みが動いていることを確かめてから自動削除を有効にした
日付・出典
Phase 14-4（生成物に限定）・2026-10-13（21-7b でコメント記録を追加）
