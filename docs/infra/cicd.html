CI/CD 設計

一時 Fix 最終更新: 2026-10-19（30-9a: 新しい書式へ移した。判断の記録 D-01〜D-10）/ 2026-08-10 開発計画 Phase 8 で構築 1 段上: 基本設計（全体）（CI/CD は配信面の 4 系統を横断する土台。構成要素の一覧は 6.2 CDK スタック）

要約

このページは、配信面のバッチ（ECS Fargate）のコンテナイメージを本番へ届ける仕組み（CI/CD）の詳細設計である。基本設計（全体）の詳細にあたる。サービスのコードは GitHub の main へ push すると、サービスごとのパイプライン 3 本（image-batch / sns-post-batch / insights-batch）がイメージを作って ECR へ push し、ECS タスク定義の新リビジョンを登録する。インフラ（infra/）は自動のパイプラインを持たず、開発者が手で cdk diff → cdk deploy する。

図 1 は、サービスのパイプラインとインフラの手動デプロイの 2 本の道筋を表したもの。続く表はこのページの要点。

項目要点
パイプラインサービスごとに 3 本（acps-{env}-image-batch-pipeline / -sns-post-batch-pipeline / -insights-batch-pipeline）。shared/** の変更は 3 本すべてを起動する
GitHub 接続CodePipeline V2 + CodeStar Connections（GitHub App）。起動はトリガー設定のファイルパスフィルタで判定する
ビルドCodeBuild が pytest → Docker build（リポジトリルートがビルドコンテキスト）→ ECR push → タスク定義の新リビジョン登録
タスク定義の正CDK。CodeBuild は最新 ACTIVE リビジョンの image URI だけを差し替える → 理由 D-06
インフラパイプラインなし。cdk diff → cdk deploy を手動で、イメージタグの Context は常に 4 つとも指定する → 理由 D-01
対象外db-readiness-check はパイプラインを持たず、手で ECR へ push して FoundationStack の deploy で反映する → 理由 D-04
失敗の監視コンソールで手動確認（自動通知なし）

1. 全体フロー

サービスのパイプラインは、GitHub への push を受けて CodeBuild でテスト・ビルドし、ECR へ push してタスク定義の新リビジョンを登録するところまでを行う（図 2）。インフラの変更はパイプラインを通さず手動でデプロイする。

インフラのパイプラインは構築しない。インフラの変更は cdk diff -c env=prod で差分を確認した上で手動でデプロイする → 理由 D-01。

1.1 GitHub 接続方式

  • CodePipeline V2 + CodeStar Connections（GitHub App）を使用する
  • CodeStar Connections は AWS コンソールで事前に作成し、GitHub リポジトリとの接続を承認する
  • パイプラインの Source Stage で CodeStar Connections をソースプロバイダーとして指定する
  • トリガーフィルタ: CodePipeline V2 のトリガー設定でファイルパスフィルタ（services/image-batch/**、shared/** 等）を指定し、関連ファイルの変更時のみパイプラインを起動する
  • Source アクションの DetectChanges は false（CDK では CodeStarConnectionsSourceAction の triggerOnPush: false）。起動の判定はトリガー設定側が担う → 理由 D-02
  • Source アクションロールには、CDK が自動で付ける codestar-connections:UseConnection に加えて codeconnections:UseConnection を明示で付ける（security.html セクション 2.5） → 理由 D-03

2. パイプライン分割

サービスごとにパイプラインを分割する。

パイプライン対象サービスCDK スタックトリガー条件
acps-{env}-image-batch-pipeline画像生成バッチImageBatchStackservices/image-batch/** OR shared/** の変更
acps-{env}-sns-post-batch-pipelineSNS 投稿バッチSnsPostBatchStackservices/sns-post-batch/** OR shared/** の変更
acps-{env}-insights-batch-pipelineインサイト収集バッチInsightsBatchStackservices/insights-batch/** OR shared/** の変更
db-readiness-check について db-readiness-check は FoundationStack で管理し、CI/CD パイプラインの対象外とする → 理由 D-04。更新時は開発者が不変タグ（例: Git コミットハッシュ）で Docker イメージを ECR へ push し、dbReadinessCheckImageTag の CDK Context にそのタグを渡して cdk deploy -c env=prod -c dbReadinessCheckImageTag=<tag> FoundationStack を実行する。FoundationStack はこのタグを使って新しい ECS Task Definition revision を登録する。
トリガー条件の補足
  • shared/** の変更は全サービスパイプラインをトリガーする → 理由 D-05
  • infra/** の変更に対する自動パイプラインは設けない → 理由 D-01。インフラ変更時は開発者が cdk diff -c env=prod → cdk deploy -c env=prod を手動で実行する。サービスパイプラインは最新 ACTIVE revision をベースに image URI だけを差し替えて新 revision を登録するので、後続のイメージ更新時にも CDK 変更が引き継がれる → 理由 D-06

3. CodeBuild 設定

CodeBuild サービスロールの権限詳細は security.html セクション 2.5 を参照。

3.1 バッチサービス用（image-batch / sns-post-batch / insights-batch）

  • buildspec.yml の配置: サービスごとに services/{service-name}/buildspec.yml に配置する（例: services/image-batch/buildspec.yml）
  • Docker ビルドコンテキスト: リポジトリルートをビルドコンテキストとし、サービスごとの Dockerfile を -f オプションで指定する（例: docker build -f services/image-batch/Dockerfile .）。shared/ ディレクトリは COPY でコンテナに含める → 理由 D-07
  • .dockerignore: リポジトリルートに .dockerignore を配置し、ビルドに不要なファイル（docs/, .git/, infra/, plans/, ルート直下の *.md）を除外する → 理由 D-07
  • テスト実行: Docker イメージを push する前に対象サービスの pytest を実行し、失敗時はパイプラインを停止する
# buildspec.yml の概要
version: 0.2
phases:
  install:
    commands:
      - Python 依存関係のインストール
  pre_build:
    commands:
      - ECR ログイン
      - イメージタグの設定（コミットハッシュ）
  build:
    commands:
      - pytest によるユニットテスト実行
      - Docker イメージのビルド
      - ECR へ push
  post_build:
    commands:
      - family 名で最新 ACTIVE な ECS タスク定義を取得（aws ecs describe-task-definition）
      - 取得した定義のコンテナ image URI だけを新タグへ差し替える
      - 新しい ECS タスク定義リビジョンを登録（aws ecs register-task-definition）
      # Task Definition 全体の SSOT は CDK。CodeBuild は image URI の差し替えだけを担う
      # Step Functions の更新は不要（タスク定義を family 名で参照し、常に最新リビジョンを使用するため）

3.2 インフラデプロイ（手動）

インフラ変更は CI/CD パイプラインを経由せず、開発者がローカルから手動で実行する。

# 手動デプロイ手順（イメージタグ Context は常に 4 つとも指定する。下記の注記を参照）
cd infra
cdk diff -c env=prod \
  -c dbReadinessCheckImageTag=<tag> \
  -c imageBatchImageTag=<tag> \
  -c snsPostBatchImageTag=<tag> \
  -c insightsBatchImageTag=<tag> \
  <StackName>                               # 差分を確認
cdk deploy -c env=prod \
  -c dbReadinessCheckImageTag=<tag> \
  -c imageBatchImageTag=<tag> \
  -c snsPostBatchImageTag=<tag> \
  -c insightsBatchImageTag=<tag> \
  <StackName>                               # 確認後にデプロイ

# 全スタックを依存順にデプロイする場合も同じ Context 指定で StackName だけ変える
# （FoundationStack → SnsPostBatchStack → ImageBatchStack → InsightsBatchStack → MonitoringStack の順。CommentReplyStack は FoundationStack の後・MonitoringStack の前〔MonitoringStack が DLQ とトークン更新 Lambda を参照する〕、CommentReplyStagingStack は FoundationStack の後）
イメージタグ Context の指定ルール（開発計画 Phase 8-3 で確認）
  • 各スタックは現行イメージの不変タグを CDK Context で受け取る。未指定のスタックは synth エラーとなる: dbReadinessCheckImageTag（FoundationStack、Phase 3-3 以降）/ imageBatchImageTag（ImageBatchStack、Phase 8-1 以降）/ snsPostBatchImageTag（SnsPostBatchStack、Phase 8-2 以降）/ insightsBatchImageTag（InsightsBatchStack、Phase 16-10 以降）
  • 1 スタックだけを diff / deploy する場合でも、CDK は上流の依存スタック（例: ImageBatchStack なら FoundationStack と SnsPostBatchStack）を選択に含めて synth 検証する。対象スタック以外のタグも必要になるので、常に 4 つとも指定する → 理由 D-08
  • 現行タグの確認方法: 各サービスの latest ACTIVE タスク定義のイメージ URI（aws ecs describe-task-definition --task-definition acps-prod-<service> --query 'taskDefinition.containerDefinitions[0].image'）。image-batch / sns-post-batch はパイプラインが push した Git コミットハッシュ先頭 12 文字が現行タグとなる
  • サービスパイプラインの実行後は、CloudFormation 側のテンプレートが前回 CDK デプロイ時点のタグを保持しているため、cdk diff にタスク定義のイメージタグ変更（旧タグ → 指定した現行タグ）が現れる。これは設計どおりの挙動であり、現行タグを指定してデプロイすれば同一イメージの新 revision が登録されるだけでロールバックは起きない
注記 上記の FoundationStack などは CDK app 内の論理スタック ID であり、-c env=prod を付与した場合の CloudFormation 実スタック名は Prod-FoundationStack のように環境名付きとなる。

4. ECR リポジトリ

サービスごとに ECR リポジトリを作成する。

リポジトリ名対象サービス
auto-content-publisher/image-batch画像生成バッチ
auto-content-publisher/sns-post-batchSNS 投稿バッチ
auto-content-publisher/insights-batchインサイト収集バッチ（保持ルールはサービス用と同じ）
auto-content-publisher/db-readiness-checkDB 準備確認（パイプライン対象外・手動更新）

ライフサイクルポリシー

ECR リポジトリにはライフサイクルポリシーを設定し、古いイメージを自動削除する。

  • 保持ルール（サービス用）: auto-content-publisher/image-batch / auto-content-publisher/sns-post-batch / auto-content-publisher/insights-batch は通常ビルドタグ（Git コミットハッシュ等）を最新 10 個まで保持し、それ以前は自動削除する
  • 保持ルール（ロールバック保護用）: 長めに残したいイメージには release-* などの保護用タグを追加し、通常ビルドタグとは別ルールで最新 30 個程度を保持する。保持対象外のタグは Task Definition が参照中でも Lifecycle Policy により削除され得るため、ロールバック前に ECR 上のイメージ存在を確認する
  • 保持ルール（db-readiness-check）: auto-content-publisher/db-readiness-check は保持数を 30 個にする → 理由 D-09。Task Definition が参照中のタグも Lifecycle Policy の保護対象にはならないため、保持数を超えた古いタグへロールバックする場合は、同等内容のイメージを新しい不変タグで再 push してから CDK Context を更新する
  • 設定箇所: FoundationStack の ECR リポジトリ定義に含める（リポジトリごとに LifecyclePolicy を個別指定する）

5. デプロイ方式

  • Blue/Green デプロイは採用しない
  • ECS Service は使用しない
  • Docker イメージを ECR に push し、新しい ECS タスク定義リビジョンを登録する
  • タスク定義の参照方式: Step Functions はタスク定義を family 名（例: acps-prod-image-batch）で参照し、ECS RunTask API が常に ACTIVE な最新リビジョンを使用する
  • Task Definition の SSOT: Task Definition 全体（family、ロール、環境変数、ログ設定、CPU/メモリ）の正は CDK とする。CodeBuild は最新 ACTIVE revision を取得し、コンテナ image URI だけを差し替えて新 revision を登録する → 理由 D-06

Task Definition の管理責任

操作担当説明
db-readiness-check の初期作成・更新CDK（FoundationStack、手動）開発者が Docker イメージを不変タグで ECR push し、cdk deploy -c env=prod -c dbReadinessCheckImageTag=<tag> FoundationStack でそのタグを参照する新 revision を登録する
初期作成・設定変更CDK（ImageBatchStack / SnsPostBatchStack / InsightsBatchStack）Task Definition、IAM Role、Log Group、環境変数等を一括作成し、Task Definition 全体の正とする
イメージ更新時の revision 登録CodeBuild（post_build）aws ecs describe-task-definition で latest ACTIVE revision を取得し、コンテナ image URI だけを差し替えて aws ecs register-task-definition で新 revision を登録する
インフラ変更後の確認開発者cdk deploy -c env=prod 後に latest ACTIVE revision を確認し、ロール・環境変数・リソース参照が反映されていることを確認する
注意 サービスパイプライン（image-batch-pipeline / sns-post-batch-pipeline / insights-batch-pipeline）に Deploy Stage（CDK Deploy）は含めない。インフラ変更は必ず CDK の手動デプロイで反映し、アプリ更新時の Task Definition revision 登録は CodeBuild が担う。

6. インフラ変更時の運用手順

CDK Deploy でタスク定義に影響する変更（ロール、環境変数、リソース参照等）を行った場合も、CDK が latest ACTIVE revision を更新する。CodeBuild は後続のイメージ更新時にこの latest ACTIVE revision をベースに image URI だけを差し替えるため、設定変更は自動的に引き継がれる。インフラ変更時は以下の手順を実施する。

6.1 手順

  1. cdk diff -c env=prod <StackName> で差分を確認する（イメージタグ Context 4 つの指定が必要。セクション 3.2 の指定ルールを参照）
  2. db-readiness-check のイメージ更新を伴う場合、手動で Docker イメージをビルドし、不変タグで ECR に push する
  3. cdk deploy -c env=prod <StackName> でインフラを更新する
    • イメージに変更がない場合も、各タグ Context には現行の不変タグを指定する（db-readiness-check の更新時のみ dbReadinessCheckImageTag に新タグを指定する）
  4. ImageBatchStack・SnsPostBatchStack・InsightsBatchStack のどれかに変更が含まれる場合、latest ACTIVE revision を確認する
    • 期待するロール、環境変数、ログ設定、リソース参照が反映されていることを AWS Console または CLI で確認する
  5. Step Functions が次回実行時に latest ACTIVE revision を使用することを確認する

6.2 パイプライン手動実行が必要なケース

変更内容パイプライン手動実行
FoundationStack のみ（VPC、S3、Aurora 等。db-readiness-check を除く）不要（タスク定義に影響しない）。ただしデプロイ時は現行の dbReadinessCheckImageTag の指定が必要
FoundationStack + db-readiness-check イメージ更新サービスパイプライン不要。手動で Docker ビルド・ECR push 後、cdk deploy -c env=prod -c dbReadinessCheckImageTag=<tag> FoundationStack を実行
ImageBatchStack（ロール、環境変数等）不要（CDK が latest ACTIVE revision を更新する）
SnsPostBatchStack（ロール、環境変数等）不要（同上）
InsightsBatchStack（ロール、環境変数等）不要（同上）
CommentReplyStack / CommentReplyStagingStack（Lambda のコード・設定）対象外（コメント返信は CodePipeline を持たず、Lambda のコードも cdk deploy で更新する。stacks.html 3.6）
MonitoringStack のみ不要
注意 インフラ変更の直後にアプリケーションコードも差し替えたい場合のみ、対応するサービスパイプラインを任意で手動実行する。設定反映だけが目的であれば、手動実行は不要である。

8. パイプラインの失敗監視

CodePipeline / CodeBuild の失敗はコンソールで手動確認する。現時点では自動通知の仕組みは構築しない。

将来の改善 パイプライン失敗の検知を自動化する場合は、CodePipeline のステート変更を EventBridge Rule で検知し、SNS Topic に通知する構成を検討する。

9. 環境分離方針

9.1 現在の運用

現時点では本番環境（main ブランチ）のみを運用する。環境は 1 つだが、将来の複数環境対応に備えて環境名は prod として扱う。開発環境の分離は将来拡張とする。

9.2 命名規約（将来の複数環境対応に備えた方針）

将来的に開発環境を追加する際は、同一 AWS アカウント内で環境を分離する（アカウント分離は行わない）。以下の命名規約でリソースを区別する → 理由 D-10:

リソース命名規約例（本番）例（開発）
CDK スタック{EnvName}-{StackName}Prod-FoundationStackDev-FoundationStack
ECR リポジトリ環境共通（イメージタグで区別）auto-content-publisher/image-batch:abc123同左
Secrets Manageracps/{env}/...acps/prod/db/credentialsacps/dev/db/credentials
S3 バケットCDK Context で環境ごとに別バケットacps-prod-imagesacps-dev-images
Step Functions ステートマシンacps-{env}-{ワークフロー名}-sfn（運用者がコンソールから手動実行するため明示命名。stacks.html の D-10 を参照）acps-prod-sns-posting-sfn、acps-prod-image-generation-sfnacps-dev-sns-posting-sfn、acps-dev-image-generation-sfn
  • CDK Context パラメータ（-c env=prod）で環境名を渡し、リソース名に反映する
  • 現時点の単一環境でも env=prod を付与して運用し、Secret 名・IAM スコープ・スタック名に反映する
  • ECS Task Definition には ENV_NAME を環境変数として注入し、アプリケーションが Secret 名を導出できるようにする
  • S3 バケット名には CDK でアカウント ID をサフィックスとして明示で付ける（バケット名はグローバルに一意である必要があるため）。上表の例（acps-prod-images）は論理名で、実際のバケット名は acps-{env}-images-{アカウント ID}（例: acps-prod-images-123456789012）の形式になる

D-01 インフラのパイプラインは作らず、手動の cdk deploy にする

決めたこと
infra/** の変更に自動のパイプラインを設けない。開発者が cdk diff -c env=prod で差分を確認した上で cdk deploy する
理由
FoundationStack に Aurora・VPC など破壊的変更のリスクが高いリソースが含まれるため、差分を人が目で見てからデプロイする。個人開発でインフラ変更頻度は低く、手動運用のコストも小さい
退けた案
インフラ用のパイプライン（CDK Deploy ステージ）を置く案
日付・出典
当初設計（Phase 8 で構築）

D-02 Source アクションの DetectChanges を false にする

決めたこと
トリガーフィルタを使うので、Source アクションの DetectChanges は false（CDK の triggerOnPush: false）にする
理由
トリガーフィルタを使う構成では false が正しい設定（AWS 公式のトリガー設定表のとおり。パイプラインの起動判定はトリガー設定側が担う）。バグではない
日付・出典
実装メモ（Phase 8-1）

決めたこと

理由
接続 ARN が新形式（サービス名 codeconnections）のため、CDK が自動付与する codestar-connections:UseConnection だけでは足りない
日付・出典
実装メモ（Phase 8-1）

D-06 タスク定義の正は CDK、CodeBuild は image URI だけを差し替える

決めたこと
CodeBuild は最新 ACTIVE リビジョンを取得し、コンテナ image URI だけを差し替えて新リビジョンを登録する。Step Functions はタスク定義を family 名で参照する
理由
最新 ACTIVE リビジョンをベースにするので、CDK で変えたロール・環境変数などが後続のイメージ更新にも引き継がれる。family 名で参照するので、イメージ更新のたびに Step Functions を更新しなくてよい
退けた案
パイプラインに Deploy ステージ（CDK Deploy）を含める案（インフラ変更は D-01 のとおり手動に限る）
日付・出典
当初設計（Phase 8）

D-07 Docker のビルドコンテキストをリポジトリルートにする

決めたこと
