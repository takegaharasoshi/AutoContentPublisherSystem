要約

このページは、配信面（AWS）の実行基盤をどう動かし続けるか ― スケジュールの変え方・手動での起動・デプロイ後の確認・DB・監視通知が来たときの対応・コスト ― をまとめたインフラの運用の詳細設計である。系統ごとの全体像は、1 段上の基本設計（全体）と、機能別の基本設計 投稿 / インサイト収集 / コメント自動返信 / トークン更新 にある。このページは実行基盤（インフラ）の運用だけを扱い、業務データに関わる運用（投稿失敗時の手動補正・プロンプト管理・SNS アカウントの追加・DDL のマイグレーション等）はアプリの運用設計 app/operation.html が持つ。

図 1 は、バッチ運用の流れ（スケジュール → 実行 → 通知 → 対応）。続く表はこのページの要点。

項目要点
スケジュールEventBridge Scheduler の cron。定義のマスタは CDK で、変えるときは CDK を直して cdk deploy（1.1）。投稿は画像生成の成功後に連鎖して起動し、専用のスケジュールを持たない → 理由 D-01
手動起動画像生成も投稿も set_code と scheduled_at の 2 キーで Step Functions を直接起動する（1.2）→ 理由 D-02
デプロイ後latest ACTIVE のタスク定義リビジョンにロール・環境変数・ログ設定・イメージタグが載ったかを確かめる（1.3）
DBAurora Serverless v2 は最小 ACU 0 で自動一時停止し、各 SFN の先頭の DB 準備確認で起こす（2 章）→ 理由 D-05
監視・通知失敗はすべて SNS トピックからメールで届く。通知ごとの対応は 3・4 章の表

1. バッチ運用

1.1 スケジュール管理

  • EventBridge Scheduler で cron 式により画像生成 Step Functions・インサイト収集 Step Functions・コメント返信のトークン更新 Lambda を定期実行する（一覧は workflow.html 1.5・1.6・10.1）
  • SNS 投稿バッチは画像生成 Step Functions の成功後に自動起動し、SNS 投稿用の EventBridge Scheduler は持たない → 理由 D-01
  • スケジュールはバッチセットごとに個別設定可能とする
  • スケジュール定義のマスタは IaC（CDK）とする

スケジュール変更手順

  1. CDK コードの EventBridge Scheduler の cron 式を変更する
  2. 系統ごとのスタックを cdk deploy して EventBridge Scheduler を更新する: 画像生成（投稿）は ImageBatchStack、インサイト収集は InsightsBatchStack、コメント返信のトークン更新は CommentReplyStack（どのスタックでもイメージタグ Context 4 つの指定が必要。cicd.html セクション 3.2 の指定ルールを参照）

1.2 バッチ実行時の動作

  1. EventBridge Scheduler が画像生成 Step Functions（image-generation-sfn）を起動
  2. Step Functions が DB 準備確認 ECS タスクを実行（WaitForDbReady ステート）
  3. DB 準備完了後、Step Functions が画像生成 ECS Fargate RunTask を実行
  4. 画像生成タスク成功後、Step Functions が SNS 投稿 Step Functions（sns-posting-sfn）を StartExecution で起動
  5. SNS 投稿 Step Functions が DB 準備確認 ECS タスクを実行
  6. DB 準備完了後、SNS 投稿 Step Functions が SNS 投稿 ECS Fargate RunTask を実行
  7. 各タスク完了後、Fargate タスクは自動的に停止（課金終了）

手動での SNS 投稿実行

SNS 投稿の単独実行が必要な場合は、AWS Console や CLI から sns-posting-sfn を直接起動する。入力は set_code と、投稿する生成実行の実際の scheduled_at（UTC・秒精度の YYYY-MM-DDTHH:MM:SSZ。generation_runs.scheduled_at の値に Z を付けたもの）の 2 キーが必須。指定した回だけが処理され、最古の未投稿分を自動で消化することはない → 理由 D-02。現在時刻を便宜的に入れない（該当 run がなく異常終了する）。起動前の対象 run・時間帯の確認は app/operation.html セクション 4.1。EXECUTION_ARN は Step Functions が $$.Execution.Id から自動設定するため、手動指定は不要。起動時に何が投稿されるか（投稿対象の決定）はアプリ設計（バッチ処理フロー設計 セクション 3）で定義する。

# CLI での手動実行例
aws stepfunctions start-execution \
  --state-machine-arn arn:aws:states:ap-northeast-1:123456789012:stateMachine:acps-prod-sns-posting-sfn \
  --input '{"set_code": "logic-training-1", "scheduled_at": "2026-10-13T12:00:00Z"}'
# ↑ logic-training-1 の 2026-10-13 夜（21:00 JST）の回。朝 7:30 JST の回は前日付の 22:30:00Z になる点に注意

手動での画像生成実行

Scheduler DLQ からの復旧や検証で画像生成 Step Functions を直接起動する場合は、set_code と scheduled_at を入力パラメータとして渡す。Scheduler DLQ からの復旧時は、DLQ のメッセージに含まれる scheduled_at の値を使用する。検証目的で新規実行する場合は UTC の ISO 8601 形式で明示する。

aws stepfunctions start-execution \
  --state-machine-arn arn:aws:states:ap-northeast-1:123456789012:stateMachine:acps-prod-image-generation-sfn \
  --input '{"set_code": "fashion-set-1", "scheduled_at": "2026-04-19T00:00:00Z"}'

1.3 CDK デプロイ後チェックリスト

CDK デプロイ実行後は、以下のチェックリストを確認する。

  • ImageBatchStack に変更があった場合: latest ACTIVE revision に期待するロール、環境変数、ログ設定が反映されていることを確認する
  • SnsPostBatchStack に変更があった場合: latest ACTIVE revision に期待するロール、環境変数、ログ設定が反映されていることを確認する
  • db-readiness-check を更新した場合: cdk deploy -c env=prod -c dbReadinessCheckImageTag=<tag> FoundationStack を使用し、latest ACTIVE revision が該当タグを参照していることを確認する
  • デプロイ結果の確認: AWS Console で各リソースの状態が正常であることを確認する

1.4 SNS 投稿の当回固定への切替（26-3 の切替チェック表・切戻し。26-1 で確定）

この節は 26-3（2026-10-13）で実施済みの、一度きりの切替手順の記録である。実施の証跡（各行の aws cli 出力）は 開発記録の 26-3 にある。切戻しの手順と、同じ型の「アプリ・子 ASL・親 ASL を同時にそろえる切替」の手本として本文に残す → 理由 D-06。

投稿アプリ（新しいイメージは SCHEDULED_AT 必須）・子 ASL（sns-posting。入口で scheduled_at を必須化）・親 ASL（image-generation。子へ scheduled_at を渡す）の 3 つは、Scheduler を止めた窓で 3 つをそろえて切り替える（作業はユーザー。エージェントは承認なしにデプロイしない）→ 理由 D-03。3 つの新旧の組み合わせと結果は次の表のとおり。

親 ASL子 ASLアプリ結果
旧旧旧旧方式（最古選定）で投稿される（切替前）
新旧旧子が余分なキーを無視するため旧方式のまま動く（無害）
旧 / 新旧新アプリが SCHEDULED_AT なしで INVALID_INPUT 終了 = 投稿されない
旧新旧 / 新子の入口で RejectInput = 投稿されない
新新旧旧アプリが SCHEDULED_AT を無視して最古選定 = 当回固定にならない
新新新当回固定（切替後）
Scheduler の手動停止は ImageBatchStack の deploy で戻るとは限らない Scheduler の State は CDK が単一の正（workflow.html セクション 1.5・I-018）で、手動で DISABLED にしても cdk deploy ImageBatchStack で ENABLED に戻る（昼スロットのように CDK 上 DISABLED のものは戻らない）。ただし戻るのはスケジュールのリソース自体に差分があるときだけ。親 ASL を載せる ImageBatchStack の deploy を最後に置き、deploy 後の S-9 で状態を確かめ、DISABLED のままなら S-8 合格を確認してから手動で停止前の状態に戻す（戻った場合も、戻らなかった場合も S-9 が再開の確認点）→ 理由 D-04。窓は「Scheduler 停止 → ImageBatchStack の deploy 完了」までの間にどのスケジュール時刻（logic-training-1 7:30 / 21:00、pref-ranking-1 20:00、umigame-soup-1 日・火・木・土 20:00 JST）もまたがない時間帯を選ぶ（目安: 21:00 の夜投稿の完了後〜翌 7:00、または 8:00〜19:30）。窓を確保できない場合は停止状態を CDK 側にも持たせる変更（スケジュールの enabled をフラグ化。インサイトの insightsCollectionSchedulesEnabled と同型）を加えて設計し直す。

2. データベース運用

2.1 Aurora Serverless v2 の自動一時停止

  • 自動一時停止を有効にする → 理由 D-05
  • 最小 ACU は 0 とし、0 ACU の自動一時停止をサポートする Aurora MySQL バージョンを採用する
  • 一時停止中にアクセスがあると自動的に再開する（再開には数十秒〜数分）

2.2 DB 準備確認

  • 各 Step Functions ワークフローの最初のステートとして DB 準備確認 ECS タスクを実行する
  • 仕様の詳細は workflow.html セクション 2 を参照

2.3 バックアップ

  • Aurora のスナップショットによるバックアップ（自動バックアップ有効）
  • 保持期間: CDK では指定していない（foundation-stack.ts の DatabaseCluster に backup の指定がなく、既定の 1 日）。運用状況に応じて調整する

テーブル設計・DDL のバージョン管理・マイグレーション方針はアプリ設計（data-model.html・app/operation.html）が持つ。

3. エラーハンドリング（運用対応）

Step Functions の Retry/Catch 設定の詳細は workflow.html セクション 6 を参照。

エラー種別運用対応
ECS タスク起動失敗（Retry 超過）CloudWatch Logs を確認し原因を調査。必要に応じて手動再実行
ECS タスク異常終了（Retry 超過）CloudWatch Logs でエラー内容を確認。アプリケーションのバグの場合は修正してデプロイ

外部 API 失敗時の再試行・投稿結果の手動補正など、業務データに関わる運用対応はアプリの運用設計（app/operation.html）が持つ。

4. 監視・通知

4.1 監視方式

監視リソースの具体的なメトリクス名・しきい値と Scheduler DLQ は workflow.html セクション 7〜10 を参照。

監視対象通知が来たらやること
Step Functions 失敗CloudWatch Logs で失敗原因を確認。一時的なエラーであれば手動再実行
Scheduler 起動失敗Scheduler DLQ のメッセージを確認し、対象 set_code と scheduled_at で画像生成 Step Functions を手動実行する（セクション 1.2 の手順）
SNS 投稿起動失敗カスタムメトリクス（SnsPostStartFailureCount）で検知。親の画像生成 SFN の実行入力から scheduled_at を取り、同じ set_code と scheduled_at で sns-posting-sfn を手動起動する（セクション 1.2。時間帯の確認を含む）
ECS タスク異常終了CloudWatch Logs でエラー内容を確認。アプリケーションのバグの場合は修正してデプロイ
Aurora 異常Aurora の状態を AWS Console で確認。ACU 設定の見直しを検討
コメント自動返信 DLQ の滞留（acps-prod-comment-reply-dlq-messages。21-3 追加・21-6 実装）DLQ のメッセージ本文（comment_id / media_id / コメント本文）と Reply Lambda のログで原因を分ける: ① OpenAI 障害・レート制限 → 復旧後に SQS コンソールの「DLQ 再処理」でメインキューへ戻す ② Graph API のトークン失効（401）→ Secret の ig_access_token を再生成して再処理 ③ スナップショット欠落（S3 404 は本来 DLQ に入らない。入っていれば Lambda のバグ）→ umigame_items.snapshot_s3_key IS NULL を確認し手動再出力。古すぎるコメント（数日前）は返信の鮮度を優先して破棄してよい。投稿バッチには影響しない
コメント返信トークンの自動更新失敗（acps-prod-comment-reply-token-refresh-errors。21-6g 追加）トークン更新 Lambda（acps-prod-comment-reply-token-refresh）のログで原因を分ける: ① Graph API の一時障害（5xx・429）→ 次の週次実行を待つか、Lambda を手動実行する ② トークン失効・権限取り消し（400 / 190 系）→ 手動でトークンを再発行して Secret を更新する（app/operation.html セクション 5.4）。失敗した週は Secret を書き換えないため、旧トークンで返信は続く

4.2 通知先

  • SNS Topic 経由でメール通知
  • 将来的には Slack 連携等も検討

SNS Topic サブスクリプション設定手順

  1. MonitoringStack のデプロイ後、AWS Console で SNS Topic を開く
  2. 「サブスクリプションの作成」からプロトコル「Email」を選択し、通知先メールアドレスを入力する
  3. 入力したメールアドレスに確認メールが届くので、メール内のリンクをクリックして承認する
  4. サブスクリプションのステータスが「確認済み」になったことを確認する
注意 サブスクリプションの承認を行わないと通知が届かない。MonitoringStack デプロイ後は必ず承認を完了すること。 確認メール（差出人 no-reply@sns.amazonaws.com、件名「AWS Notification - Subscription Confirmation」）は迷惑メールフォルダに振り分けられることがある（Gmail で実績あり）。届かない場合は迷惑メールフォルダを確認し、見つからなければコンソールでサブスクリプションを選択して「リクエストの確認」から再送する。確認リンクの有効期限は 3 日間。

判断の記録

本文の「→ 理由 D-xx」から飛んでくる先。なぜそうしたかをここにまとめる。番号は振り直さず、判断が覆ったら新しい番号で書き足す。

D-01 投稿用の Scheduler を持たず、画像生成の成功から連鎖して起動する

決めたこと
EventBridge Scheduler が起動するのは画像生成 Step Functions だけ。SNS 投稿 Step Functions は画像生成の成功後に StartExecution で起動する
理由
SNS 投稿バッチは画像生成 Step Functions の成功後に自動起動されるため、SNS 投稿用の EventBridge Scheduler は不要
日付・出典
当初設計（記録なし）

D-02 手動の投稿起動に scheduled_at を必須にする（当回固定）

決めたこと
sns-posting-sfn の入力は set_code と、投稿する生成実行の実際の scheduled_at の 2 キーが必須。指定した回だけを処理し、最古の未投稿分を自動で消化しない
理由
投稿する回を起動側で固定し、古い未投稿の回が意図しない時間帯に出ないようにするため（SNS 投稿バッチの当回固定 = I-014 の展開）。26-1 で確定し、26-3 の切替以後に有効（それまでは set_code のみ）
退けた案
旧方式（set_code だけを受け取り、最古の未完了 run を選ぶ）
日付・出典
26-1 で確定・26-3（2026-10-13）で切替（Phase 26）

D-03 当回固定への切替は、Scheduler を止めた窓でアプリ・子 ASL・親 ASL の 3 つをそろえて行う

決めたこと
投稿アプリ・子 ASL（sns-posting）・親 ASL（image-generation）を、Scheduler を停止した窓で同時に新へ切り替える。切戻しではアプリと子 ASL を必ず組で旧へ戻す
理由
3 つのうちどれか 1 つでも旧のまま動くと投稿されない組み合わせがあるため（1.4 の組み合わせ表。新アプリ + 旧子は INVALID_INPUT、旧親 + 新子は RejectInput で投稿されない）。親 ASL だけ新でも無害なので、切戻しでは親は新のままでよい
日付・出典
26-1 で確定・26-3（2026-10-13）で実施

D-04 ImageBatchStack の deploy を最後に置き、Scheduler の状態を S-9 で確かめる

決めたこと
親 ASL を載せる ImageBatchStack の deploy を最後に置き、deploy 後の S-9 で Scheduler の状態を確かめ、DISABLED のままなら S-8 合格を確認してから手動で停止前の状態に戻す
理由
手動で DISABLED にした Scheduler が cdk deploy ImageBatchStack で ENABLED に戻るのはスケジュールのリソース自体に差分があるときだけで、26-3（2026-10-13）では差分がなく DISABLED のまま残った（26-3 で確認）。戻る・戻らないのどちらでも再開の確認点を 1 つにするため
退けた案
停止状態を CDK 側にも持たせる（スケジュールの enabled をフラグ化。インサイトの insightsCollectionSchedulesEnabled と同型）。スケジュール時刻をまたがない窓を確保できる限り不要とし、確保できない場合の代替として残した（その場合は 26-2 に追加して設計し直す想定だった）
日付・出典
26-3（2026-10-13）

D-05 Aurora Serverless v2 を最小 ACU 0 で自動一時停止させる

決めたこと
最小 ACU を 0 にし、0 ACU の自動一時停止をサポートする Aurora MySQL バージョンを採用する。起こすのは各 SFN の先頭の DB 準備確認
理由
コスト最適化のため（バッチは 1 日に数回しか DB を使わない）。再開に数十秒〜数分かかる点は、DB 準備確認を SFN の最初のステートに置くことで吸収する
日付・出典
当初設計（記録なし）

D-06 26-3 の切替チェック表を、実施後も本文に残す
