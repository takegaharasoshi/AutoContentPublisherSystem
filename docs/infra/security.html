要約

このページは、配信面（AWS）の秘密情報の置き方（Secrets Manager）、IAM ロールの権限、ネットワークの守り方、セキュリティ運用を説明する詳細設計である。基本設計（全体）と、機能別の基本設計 投稿・インサイト収集・コメント自動返信・トークン更新 のうち、認証と権限の部分を詳しくしたもの。

図 1 は、Secret とそれを読む（書く）ロールの関係。ECS のバッチのタスクロールは acps/{env}/ 配下を種別のプレフィックスで読み、Step Functions・Scheduler・CI/CD のロールは Secret を読まずに、タスクの起動とロールの受け渡し（iam:PassRole）だけを行う。コメント返信の Lambda は自分の面の Secret 1 件だけを読み、トークン更新 Lambda だけがその Secret に書き戻す。続く表はこのページの要点。

項目要点
Secret の名前すべて acps/{env}/ で始め、種別ごとの規約でアプリが名前を導出する（DB に ARN を持たない）→ 理由 D-01
Secret の権限サービスごとに必要な種別のプレフィックスだけ読み取りを許可する。コメント返信用の Secret は投稿用と分け、書き込みはトークン更新 Lambda だけ → 理由 D-02
IAM ロールECS のタスクロールとタスク実行ロールを分ける（ログはタスク実行ロール）。SFN・Scheduler・CI/CD・Lambda はそれぞれ専用ロールで対象リソースを絞る
ネットワークAurora は隔離サブネット、Fargate はパブリックサブネットでインバウンド全拒否。コメント返信の Lambda は VPC の外で、関数 URL は署名検証で守る → 理由 D-06
運用ログと DB にキー・トークン・Secret 値を出さない。コメント返信の変更はステージング面で確かめてから本番へ

1. Secrets Manager 管理方針

1.1 管理対象

以下の秘密情報を Secrets Manager で管理する:

  • Aurora DB の認証情報（ホスト、ポート、ユーザー名、パスワード、DB 名）
  • 画像生成 API のキー
  • SNS 認証情報（プラットフォームごとの API 認証情報）

1.2 Secret 名規約

すべての Secret は acps/{env}/ プレフィックスで始まる。種別ごとの命名規約:

種別Secret 名パターン例
DB 認証情報acps/{env}/db/credentialsacps/prod/db/credentials
画像生成 API キーacps/{env}/image/api-keyacps/prod/image/api-key
SNS 認証情報acps/{env}/{set_code}/sns/{platform}/{account_code}acps/prod/fashion-set-1/sns/instagram/main-account
コメント自動返信（Webhook + OpenAI + 返信用トークン。21-3 追加）acps/{env}/{set_code}/comment-reply{-staging}acps/prod/umigame-soup-1/comment-reply / acps/prod/umigame-soup-1/comment-reply-staging

SNS 認証情報の Secret 名の構成要素:

要素説明例
env環境識別子（ECS タスクの ENV_NAME 環境変数）prod
set_codeバッチセット識別コードfashion-set-1
platformSNS プラットフォーム名instagram
account_codeアカウント識別コード（不変）main-account
  • Secret 名はアプリケーション側で上記規約に基づき導出する（DB に Secret 名・ARN は保持しない）
  • account_code は Secret 名の導出に使用するため、作成後に変更してはならない
  • 環境分離は env 部分で行い、IAM ポリシーのプレフィックスベース制御と整合する → 理由 D-01
アプリ設計での最終確認 構成要素の定義はアプリ設計大枠 セクション 5 で確定した（set_code = batch_sets.set_code、account_code = sns_accounts.account_code）。アカウント追加手順の具体化と、インフラ構築の実態を踏まえた規約の最終確認はアプリ設計（Phase 9-4）で行う。acps/{env}/ プレフィックスと IAM のプレフィックスベース制御という骨格はインフラ設計として Fix とする。

Secret の値は JSON 文字列で管理する。アプリケーションは以下のキーを前提に読み取る。

DB 認証情報

Aurora 作成時に CDK / RDS が生成する Secret を使用する。アプリケーションは以下のキーを参照する。

passwordYESDB パスワード
hostYESAurora writer endpoint
portYESMySQL ポート（通常 3306）
dbnameYES接続先 DB 名

画像生成 API キー

Secret 名: acps/{env}/image/api-key

{
  "api_key": "..."
}

SNS 認証情報（Instagram）

Secret 名: acps/{env}/{set_code}/sns/instagram/{account_code}

  "ig_user_id": "...",

token_expires_atNOトークン失効日時の運用メモ。アプリケーションの認証には使用しない

コメント自動返信（umigame-soup-1。Phase 21-3 設計・21-6 実装）

Secret 名: acps/{env}/{set_code}/comment-reply（ステージング面は -staging 接尾辞）。CDK（stacks.html セクション 3.6）が空値テンプレートで作成し verify_token だけを自動生成する。他の値は手動投入（PoC と同じ運用）。ig_access_token と token_expires_at は初回投入後、トークン更新 Lambda が週 1 回自動で書き戻す（21-6g）。

{
  "verify_token": "（CDK が自動生成。Meta の Webhook 購読設定に貼る）",
  "app_secret": "...",
  "ig_access_token": "...",
  "ig_user_id": "...",
  "openai_api_key": "...",
  "typesafe_api_key": "...",
  "anthropic_api_key": "...",
  "token_expires_at": "2026-11-02T00:00:00Z"
}
キー必須説明
verify_tokenYESWebhook 購読時の GET 検証（hub.verify_token）に使う共有文字列。CDK が生成し変更しない
app_secretYESWebhook 署名（X-Hub-Signature-256）の HMAC 鍵。Instagram アプリシークレット（Facebook 側「アプリ設定 → ベーシック」の app secret ではない。PoC 2026-09-03 で実測）
ig_access_tokenYESコメント返信用の長期アクセストークン（Instagram ログイン方式・スコープ instagram_business_basic + instagram_business_manage_comments）。投稿用 Secret の access_token（Facebook ページ経由・既存 Meta アプリ）とは別のアプリ・別の方式のトークンで、同じアカウントに 2 本のトークンが存在する。60 日で失効するため、トークン更新 Lambda が毎週 GET /refresh_access_token で更新し、新しいトークンを書き戻す（21-6g）。初回の投入だけは手動
ig_user_idYES自アカウントの Instagram user ID。自己返信ループ防止の照合キー（未設定のままコメントが来ると自分の返信に返信し続けるため、投入を最優先する）
openai_api_keyYESOpenAI API キー（プロジェクト単位で月額予算上限を設定したもの。利用上限の 1 段目）。既定構成では haiku 判定が失敗したときのサブ判定（luna）に使う。Reply Lambda は空でも起動時に必須キーとして検査するため、必ず投入する
typesafe_api_keyYESJev 判定（JUDGE_MODE=jev）の API キー。既定構成では呼ばないが、Reply Lambda が起動時に必須キーとして検査する（21-6f 追加）
anthropic_api_keyYES（既定構成）Anthropic API キー。既定の判定 JUDGE_MODE=haiku と書き手 REPLY_VARIANT=1b-haiku（Claude Haiku 5.5・effort max。21-6e 決定・21-8e で effort を変更）に使う。Console のワークスペース単位で月額上限を設定したものを入れる（21-6f 追加）
token_expires_atNOコメント返信用トークンの失効日時（YYYY-MM-DDTHH:MM:SSZ）。トークン更新 Lambda が更新のたびに「実行時刻 + 応答の expires_in」で書き戻す。アプリケーションの認証には使わず、失効までの余裕を人が確かめるための値（app/operation.html セクション 5.4）
  • PoC の Secret umigame-poc/credentials は acps/{env}/ 規約の外にある（PoC のため）。21-6 でステージング面を acps/prod/umigame-soup-1/comment-reply-staging に作り直し、UmigamePocStack と一緒に削除する → 2026-10-11 に削除した（21-6f の接続後・課題 I-032。値は新しいステージングの Secret へ写してから消した）
  • 書き込み権限: この Secret への書き込み（secretsmanager:PutSecretValue 等）はトークン更新 Lambda の実行ロールだけに、当該 Secret に限って付与する（Webhook / Reply Lambda は読み取りのみ。stacks.html セクション 3.6）。更新 Lambda はトークンと要求 URL（クエリにトークンを含む）をログ・例外に出さない
  • 投稿用 Secret（上記「SNS 認証情報」）は本セットでも既存どおり作る。コメント返信用 Secret とキーを混ぜない → 理由 D-02

2. IAM ロール設計

2.1 ECS タスクロール

ロール権限
DB 準備確認タスクロールSecrets Manager 読み取り（acps/{env}/db/*）
画像生成バッチタスクロールS3 読み書き、Secrets Manager 読み取り（acps/{env}/db/* + acps/{env}/image/*）
SNS 投稿バッチタスクロールS3 読み取り、S3 書き込みは assets/umigame-soup-1/problems/* の s3:PutObject のみ（問題スナップショット。21-7 追加）、Secrets Manager 読み取り（acps/{env}/db/* + acps/{env}/*/sns/*）
インサイト収集バッチタスクロール（16-7 設計・16-10 実装）Secrets Manager 読み取り（acps/{env}/db/* + acps/{env}/*/sns/*。SNS 投稿バッチと同じ Instagram トークンを読む）。S3 はコメント記録の読み取りだけ（21-7b。s3:ListBucket を条件 s3:prefix = comment-log/* で、s3:GetObject を comment-log/* に。書き込み・削除は付与しない）
  • Secrets Manager 権限はサービスごとに必要最小限のプレフィックスで制限する。DB 認証情報（acps/{env}/db/*）は全サービス共通、それ以外は各サービスが必要とする種別のみ付与する
  • DB にアカウントを追加するだけで、IAM ポリシーの変更なしに新しい Secret へのアクセスが可能になる
  • ECS のタスクロールには cloudwatch:PutMetricData を付与しない（アプリはカスタムメトリクスを発行しない）。付与しているのは Step Functions 実行ロール（image-generation-sfn）の SnsPostStartFailureCount 発行用だけ（セクション 2.3） → 理由 D-03

2.2 ECS タスク実行ロール

  • ECR イメージの pull 権限
  • CloudWatch Logs への書き込み権限
注記 CloudWatch Logs への書き込みは ECS Fargate の awslogs ドライバがタスク実行ロールの権限で行う。タスクロール（セクション 2.1）には CloudWatch Logs 権限を含めない。

2.3 Step Functions 実行ロール

ステートマシン権限
image-generation-sfnECS RunTask（DB 準備確認タスク + 画像生成バッチタスク）、iam:PassRole（ECS RunTask 時にタスクロール・タスク実行ロールを渡すため）、SNS 投稿 Step Functions の StartExecution、CloudWatch PutMetricData（カスタムメトリクス発行用。詳細は下記注記を参照）
sns-posting-sfnECS RunTask（DB 準備確認タスク + SNS 投稿バッチタスク）、iam:PassRole（ECS RunTask 時にタスクロール・タスク実行ロールを渡すため）
insights-collection-sfn（16-7 設計・16-10 実装）ECS RunTask（DB 準備確認タスク + インサイト収集バッチタスク）、iam:PassRole（同上）。sns-posting-sfn と同構成
ECS RunTask の Resource 指定 Step Functions ASL は Task Definition を family 名（revision なし）で指定し、ECS RunTask が最新 ACTIVE revision を解決する。Step Functions 実行ロールの ecs:RunTask は arn:aws:ecs:{region}:{account}:task-definition/{family}:* のように family 配下の全 revision を許可する → 理由 D-04
Run a Job（.sync）に必要な補助権限 ecs:StopTask と ecs:DescribeTasks は Step Functions が起動したタスクを待機・停止するために必要で、対象 task ARN は実行時まで確定しないため Resource: "*" を許容する。EventBridge 連携用の events:PutTargets、events:PutRule、events:DescribeRule は StepFunctionsGetEventsForECSTaskRule に限定する。
iam:PassRole の条件 iam:PassRole は各タスクの task role / execution role の ARN に限定し、iam:PassedToService = ecs-tasks.amazonaws.com 条件を付与する。
cloudwatch:PutMetricData の IAM 条件 PutMetricData のステートメントは Resource を "*" とし、条件キー cloudwatch:namespace で発行可能な Namespace を ACPS（本システムのカスタムメトリクス Namespace）に制限する → 理由 D-05。例: 
{
  "Effect": "Allow",
  "Action": "cloudwatch:PutMetricData",
  "Resource": "*",
  "Condition": {
    "StringEquals": { "cloudwatch:namespace": "ACPS" }
  }
}

CodeBuild サービスロール

パイプライン権限

3. ネットワークセキュリティ

  • Aurora: Isolated Subnet に配置し、インターネットからの直接アクセスを遮断する。Security Group はアウトバウンド通信を完全に遮断する（CDK で allowAllOutbound: false を明示指定）
  • S3: 画像保存バケットは Block Public Access を有効化し、サーバーサイド暗号化と SSL 強制を設定する。Instagram への画像連携は Presigned URL のみで行い、バケットやオブジェクトを public にはしない
  • ECS Fargate: Public Subnet に配置し、Security Group でアクセスを制御する
    • インバウンド: 全ポート拒否（バッチ処理であり外部からの着信接続は不要）
    • アウトバウンド: インターネットアクセス（外部 API、Secrets Manager、CloudWatch Logs）と VPC 内通信（Aurora）を許可
  • コメント自動返信 Lambda（21-3 追加）: VPC 外で実行し、Function URL を認証なし（authType: NONE）で公開する。インバウンドの正当性は Meta の X-Hub-Signature-256 署名検証（鍵は Instagram アプリシークレット）で確かめ、署名不一致は 401 で捨てる → 理由 D-06。Reply Lambda はインバウンドを持たず SQS トリガーのみ。アウトバウンドは Secrets Manager・S3・Anthropic・OpenAI・Typesafe・Graph API（すべて TLS）。NAT Gateway・VPC Endpoint は使わない（architecture.html セクション 3.4）
  • プライバシーポリシー用 S3 バケット（21-3 設計・21-7 構築）: Meta アプリの公開モードに必須の到達可能 URL を提供する。専用の小バケット acps-{env}-umigame-privacy-policy だけを公開読み取り（当該バケット限定の s3:GetObject）にし、https のオブジェクト URL で公開する。ウェブサイトエンドポイントは使わない。画像保存バケットの Block Public Access は維持する（stacks.html セクション 3.6） → 理由 D-07
  • Secrets Manager: ECS Fargate のパブリック IP 経由でアクセス（通信は TLS で暗号化）
    • Interface VPC Endpoint は使用しない → 理由 D-08

4. セキュリティ運用

  • API キー・DB 認証情報は定期的なローテーションを検討する
  • ECS タスクには最小権限の IAM ロールを付与する
  • Secrets Manager 権限はサービスごとに最小プレフィックスで制限し、環境およびサービスを跨いだ参照を避ける
  • Security Group で不要な通信を遮断する
  • コメント自動返信の Lambda コード・プロンプトの変更は、必ずステージング面（PoC の Meta アプリ + テスト用アカウント）で実コメントを打ってから本番面の Webhook 先を切り替える（外向き発信を持つ経路の変更手順。21-3 追加）
  • CloudWatch Logs と DB の API レスポンス保存欄には、API キー、アクセストークン、Authorization ヘッダー、Presigned URL、Secret 値を出力・保存しない。外部 API レスポンスを保存する場合はマスキング済みの値のみを保存する（アプリ実装時のログ出力方針はアプリ設計で具体化する）

判断の記録

本文の「→ 理由 D-xx」から飛んでくる先。なぜそうしたかをここにまとめる。番号は振り直さず、判断が覆ったら新しい番号で書き足す。

D-01 Secret は名前の規約で導出し、IAM はプレフィックスで絞る

決めたこと
Secret 名を acps/{env}/… の規約に統一し、アプリが規約から名前を導出する。DB に Secret 名・ARN を持たず、IAM ポリシーはプレフィックスで許可する
理由
Secret の ARN を DB カラムで管理する方式では、アカウントを追加するたびに IAM ポリシーの個別 ARN 追加が必要になる。Secret 名規約に統一することで、プレフィックスベースの IAM ポリシーで最小権限と運用の簡便さを両立する（DB にアカウントを足すだけで、IAM を変えずに新しい Secret を読める）
退けた案
Secret の ARN を DB カラムで管理する
日付・出典
当初設計（インフラ設計 Fix 時）

D-02 コメント返信用の Secret を投稿用と分ける

決めたこと
コメント自動返信のキー・トークンは acps/{env}/{set_code}/comment-reply{-staging} に置き、投稿用 Secret（…/sns/instagram/…）とキーを混ぜない。書き込みはトークン更新 Lambda の実行ロールだけに、当該 Secret に限って付与する
理由
読むサービスが違い、IAM の許可プレフィックスも違うため。コメント返信用のトークンは投稿用とは別のアプリ・別の方式（Instagram ログイン方式）のトークンでもある。書き込みを 1 つのロールに絞り、Webhook / Reply Lambda は読み取りだけにする
日付・出典
21-3（2026-09-04）設計、21-6g でトークン更新 Lambda の書き戻しを追加

D-03 SNS 投稿バッチのタスクロールから cloudwatch:PutMetricData を削除

決めたこと
SNS 投稿バッチタスクロールの cloudwatch:PutMetricData を削除した。Step Functions 実行ロール（image-generation-sfn）の PutMetricData は SnsPostStartFailureCount の発行に使用中のため残している（セクション 2.3）
理由
当初はアプリ発行カスタムメトリクス用に cloudwatch:PutMetricData（Namespace を ACPS に制限）を先行付与していたが、Phase 9-2 のアプリ設計で「アプリ側は個別カスタムメトリクスを持たず、通知は既存の Step Functions 失敗アラーム 1 本に一本化する」方針が確定し、使用しない権限として残っていたため、最小権限の原則に従い削除した（設計課題リスト 2026-07-07 の項目を解消）。将来アプリ発行カスタムメトリクスを導入する際は、セクション 2.3 の「cloudwatch:PutMetricData の IAM 条件」の Namespace 制限方式で再付与する
日付・出典
2026-07-15、Phase 10-1

D-04 ecs:RunTask は family 配下の全 revision を許可する

決めたこと
Step Functions 実行ロールの ecs:RunTask を task-definition/{family}:* で許可する
理由
ASL は Task Definition を family 名で指定し、最新 ACTIVE revision を実行時に解決する。revision 固定 ARN のみを許可すると、CodeBuild が新 revision を登録した後に実行できなくなる
退けた案
revision 固定の ARN だけを許可する
日付・出典
（記録なし）

D-05 PutMetricData は Resource "*" + Namespace 条件で絞る

決めたこと
cloudwatch:PutMetricData は Resource: "*" とし、条件キー cloudwatch:namespace を ACPS に限る
理由
PutMetricData API はリソース ARN をサポートしていないため、Resource は "*" にせざるを得ない。過剰権限化を避けるため、Namespace の条件で発行先を制限する
日付・出典
（記録なし）

D-06 Webhook の関数 URL は認証なしで公開し、署名検証で守る

決めたこと
Webhook Lambda の Function URL を authType: NONE で公開し、Meta の X-Hub-Signature-256 署名（鍵は Instagram アプリシークレット）を検証して不一致は 401 で捨てる。Lambda は VPC の外で動かし、NAT Gateway・VPC Endpoint は使わない
理由
インバウンドの正当性は Meta の署名検証で担保する
日付・出典
21-3（2026-09-04）。構成の判断は architecture.html セクション 3.4

D-07 プライバシーポリシーは専用バケットを https のオブジェクト URL で公開する

決めたこと
専用の小バケット acps-{env}-umigame-privacy-policy だけを公開読み取りにし、https のオブジェクト URL で公開する。画像保存バケットの Block Public Access は維持する
理由
Meta アプリの公開モードには到達可能なプライバシーポリシーの URL が必須のため。公開範囲をこの小バケットに閉じ込め、画像保存バケットは公開しない
退けた案
S3 のウェブサイトエンドポイント（http のみのため使わない）
日付・出典
21-3 設計・21-7 構築（stacks.html セクション 3.6 の決定 21-7）

D-08 Secrets Manager へは Interface VPC Endpoint を使わずパブリック IP 経由で届く

決めたこと
ECS Fargate はパブリック IP 経由（TLS）で Secrets Manager に届く。Interface VPC Endpoint は使わない
理由
コスト削減のため。より厳格なネットワーク分離が必要な場合は導入を検討する
退けた案
Interface VPC Endpoint。セキュリティ要件の強化やトラフィック増加時には、ECS Fargate を Private Subnet に移動し NAT Gateway 経由の構成に変更可能（移行パスとして残す）
日付・出典
当初設計
