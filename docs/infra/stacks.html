要約

このページは、配信面（AWS）を CDK のスタックにどう分けて定義しているかを書く詳細設計である。基本設計（全体）3 章の配信面の 5 系統のうち、①投稿は SnsPostBatchStack と ImageBatchStack（機能別の基本設計: 投稿）、②インサイト収集は InsightsBatchStack（インサイト収集）、③コメント自動返信と④トークン更新は CommentReplyStack（コメント自動返信 / トークン更新）、⑤脳みそコーチの正解返信とその返信用トークンの更新は CoachReplyStack（脳みそコーチの正解返信）が持つ。共通の土台は FoundationStack、監視と通知は MonitoringStack にまとめる。AWS の構成の全体像は architecture.html。

図 1 は 9 つのスタック（31-4 で CoachReply の 2 面が加わった）の依存。矢印は「参照される側 → 参照する側」で、矢印のラベルは受け取るもの。丸数字はデプロイ順（順番だけを並べた図は 4 章の図 2）。続く表はこのページの要点。

1. スタック分割方針

責務ごとに AWS CDK のスタックを分割する。

  • 共通基盤は FoundationStack で一元管理し、各バッチスタックから参照する
  • 業務機能はサービスごとにスタックを分離し、独立したデプロイ・保守を可能にする
  • 監視・通知は MonitoringStack として業務スタックから分離する

CDK 実装時の注意
  • CDK はデフォルトで全アウトバウンドを許可する Security Group を作成する。上表の 3 つの SG はいずれもアウトバウンドを限定するため、3 つとも allowAllOutbound: false を明示的に指定し、必要な Egress ルールのみを個別に追加すること（Aurora 用 SG は Egress ルールを追加しない。この場合 CDK が 255.255.255.255/32 宛 ICMP の「Disallow all traffic」ダミー拒否ルールを挿入するが、実質アウトバウンド通信なしを意味する仕様であり問題ない）
  • ec2.Vpc のデフォルト構成は Private Subnet + NAT Gateway を含むため、natGateways: 0 と subnetConfiguration（PUBLIC と PRIVATE_ISOLATED のみ）を明示しないと意図しない NAT Gateway が作成され課金が発生する
  • ecs.Cluster は vpc 未指定だとデフォルト構成の新規 VPC（NAT Gateway 付き）を自動作成するため、必ず FoundationStack の既存 VPC を渡すこと
  • Aurora Serverless v2 の enableDataApi: true を有効化していない場合、AWS Console の Query Editor からの DDL 実行・データ確認ができない（開発計画 Phase 6 の検証ステップで使用するため有効化必須）
  • Aurora の serverlessV2MaxCapacity を未指定にするとデフォルト値（リージョンによる）まで自動スケールしてコスト事故の要因となるため、必ず上限値を指定する
  • Aurora の DB 認証情報 Secret はデフォルトではランダムな名前で生成される。Credentials.fromGeneratedSecret の secretName に acps/{env}/db/credentials を明示指定しないと、Secret 名規約（security.html セクション 1.2）および IAM のプレフィックスベース制御（acps/{env}/db/*）と不整合になり、ECS タスクからの Secret 読み取りが権限エラーになる。Secret 名を後から変更すると Secret リソースの置換（マスターパスワードの再生成）が発生し手戻りが大きいため、Phase 3-1 の初回デプロイ時に必ず指定する

ネットワークセキュリティの方針は architecture.html セクション 2 および security.html セクション 3 を参照。

Webhook は Lambda の Function URL（認証なし・署名検証）で受け、SQS FIFO を挟んで Reply Lambda で返信する。VPC の外に置き、本番面とステージング面を同一コード（CommentReplyStack クラス）で立てる。Lambda コードは標準ライブラリ + boto3 のみのため lambda.Code.fromAsset で直接デプロイし、コンテナではないので CodePipeline は通さず手動 cdk deploy に乗せる（21-1 ⑥）
理由
  • Function URL（21-1 ⑥ ユーザー決定）: API Gateway の WAF・スロットリング・使用量プランが要る規模になるまで不要。Function URL は無料で、署名検証を Lambda 内で行うため認証なしで公開しても Meta 以外の要求は 401 で落ちる（Meta 以外は正しい署名を作れない）。DDoS 級の呼び出しは Lambda の同時実行上限（アカウント既定）で頭打ちになり費用も僅少
  • SQS FIFO: 標準キューの at-least-once では Meta の再送 + SQS の重複配信で同じコメントに二重返信しうる（ユーザーに見える不具合）。FIFO の重複排除 ID に comment_id を使えば追加実装なしで 5 分窓の重複を抑止できる。スループット上限（300 msg/秒）はコメント規模（1 日 200 件）に対して十分。窓外の再送による二重返信は許容（発生したら設計課題へ）
  • VPC 外: Aurora に触れないため VPC に置く理由がなく、置くと NAT Gateway（月 4,000 円超）が要る。Secrets Manager・S3・OpenAI・Graph API はいずれもパブリックエンドポイント（TLS）
  • ステージング面を同一コードで立てる: PoC ハンドラを別コードで残すと本番と乖離するため、21-6 で新スタックをステージング面としても立て、PoC の Meta アプリの Webhook 先を切り替えてから UmigamePocStack（と規約外の Secret umigame-poc/credentials）を削除する（21-1 ⑦。2026-10-11 に削除した。infra/lib/umigame-poc-stack.ts と bin/infra.ts の配線も外した。課題 I-032）。恒久利用するのは PoC の Meta アプリとテスト用アカウントで、スタックではない。2 面分の定常費はほぼゼロ（Lambda・SQS は従量、Secret は月 0.4 USD × 2）
