Step Functions・EventBridge Scheduler・DB 準備確認タスク・監視リソースの実装仕様を定義する。アーキテクチャ上の位置付けは architecture.html、CDK リソース定義は stacks.html、運用時の対応手順は operation.html を参照。

アプリ仕様は未確定 本ドキュメントの ASL・環境変数はワークフローの「器」の定義であり、業務ロジックに依存しない。ECS タスク内部の処理内容（画像生成・SNS 投稿のロジック）はアプリ設計（docs/app/）で定義する。

要約

このページは、配信面のうち時刻で動く 2 つの系統（①投稿・②インサイト収集）を動かすワークフローの実装仕様で、機能別の基本設計 投稿・インサイト収集（上は基本設計（全体））の AWS の定義にあたる。Step Functions（SFN）の定義、EventBridge Scheduler のスケジュール、ECS タスクへ渡す環境変数、失敗を知らせる監視リソースを定める。ECS タスクの中で何をするか（業務の処理）は書かず、アプリ設計に任せる。

図 1 は、ワークフローの全体を表す。Scheduler が選定の SFN と収集の SFN を起こし、選定の SFN が成功すると投稿の SFN を起こす。どの SFN も最初に DB 準備確認を動かす。起動や実行の失敗は監視リソースから通知される。

1. ワークフロー構成

この章は、要約の図 1 の起動の仕方を詳しくしたもの。SFN どうしのつながり（1.1）、全 SFN に共通する実装の決まり（1.2）、Scheduler の入力・再試行・スケジュールの一覧（1.3〜1.6）を示す。

1.1 順次実行

画像生成バッチと SNS 投稿バッチは順次実行される（全体像は architecture.html セクション 1 の図を参照）。

  1. EventBridge Scheduler が cron 式で image-generation-sfn を起動する
  2. image-generation-sfn: WaitForDbReady（DB 準備確認）→ RunImageBatchTask（画像生成バッチ）→ 成功時に StartSnsPostBatch で sns-posting-sfn を非同期起動する
  3. sns-posting-sfn: WaitForDbReady（DB 準備確認）→ RunSnsPostBatchTask（SNS 投稿バッチ）
  • SNS 投稿 Step Functions（sns-posting-sfn）は独立したステートマシンのため、手動での単独実行も可能。起動時に何が投稿されるか（投稿対象の決定）はアプリ設計（バッチ処理フロー設計 セクション 3）で定義する。入力は set_code と scheduled_at（対象生成実行の予定時刻・UTC 秒精度）の 2 キーが必須（26-1 で確定・26-2 で実装。手動起動でも省略不可）
  • EventBridge Scheduler は画像生成 Step Functions のみに設定し、SNS 投稿用のスケジューラは不要
  • インサイト収集ワークフロー（16-7 追加）: insights-collection-sfn は上記チェーンから独立し、専用の Scheduler（セクション 1.6）で 1 日 2 回起動される。構成は WaitForDbReady → RunInsightsBatchTask の同型 2 ステート（ASL はセクション 11）。手動での単独実行（疎通確認・バックフィル）も運用ユースケース（app/operation.html セクション 6）

1.2 共通の実装方針

  • TaskDefinition の指定方式: ASL 内の ${...TaskDefFamily} プレースホルダには、CDK が ECS Task Definition の family 名（例: acps-prod-image-batch）を渡す。ECS RunTask API は family 名指定で常に ACTIVE な最新リビジョンを使用するため、デプロイ時に ASL の更新は不要
  • SecurityGroup の指定方式: ${BatchSgId} は FoundationStack で定義される「ECS Fargate 用（バッチ共通）」Security Group を指す。画像生成バッチと SNS 投稿バッチは同一の Security Group を共有する。DB 準備確認タスクには専用の ${DbReadinessCheckSgId} を使用する
  • Task ステートのタイムアウト: WaitForDbReady=900 秒、RunImageBatchTask=3600 秒、StartSnsPostBatch=60 秒、RunSnsPostBatchTask=3600 秒の明示タイムアウトを設定する → 理由 D-09
  • StartSnsPostBatch の呼び出し方式: arn:aws:states:::states:startExecution（.sync サフィックスなし）は非同期呼び出しであり、子実行（sns-posting-sfn）の完了を待たずに即座に成功を返す。画像生成ワークフローは SNS 投稿の起動のみを行い、投稿処理の完了は待機しない
  • StartSnsPostBatch の冪等性: StartExecution.Name には親ワークフローの $$.Execution.Name を渡す。Step Functions Standard の StartExecution は同一 Name / 同一 Input の実行が実行中であれば冪等に同じ応答を返す。一方、同名実行が既に終了済みの場合は ExecutionAlreadyExists となるため、このエラーは「子実行は既に作成済み」とみなし成功扱いにする
  • 実行名の文字数制限: Step Functions の実行名（Name）は最大 80 文字に制限されている。本システムでは $$.Execution.Name を子実行の Name として使用する。EventBridge Scheduler がデフォルトで生成する実行名は UUID ベース（36 文字）のため通常は問題ないが、カスタム名を使用する場合は 80 文字制限に注意すること
  • ResultPath の設定: WaitForDbReady と RunImageBatchTask には "ResultPath": null を設定し、ECS RunTask.sync の出力（DescribeTasks レスポンス）で入力パラメータ（$.set_code 等）が上書きされるのを防ぐ

1.3 EventBridge Scheduler の Input テンプレート

Scheduler は以下の形式で画像生成 Step Functions を起動する。<aws.scheduler.scheduled-time> は EventBridge Scheduler が実行時刻（UTC、ISO 8601）に自動置換する。

{
  "set_code": "logic-training-1",
  "scheduled_at": "<aws.scheduler.scheduled-time>"
}

set_code はスケジュールごとの固定値（セクション 1.5 の一覧）。スロット対応方式のセットでも Input にスロットは持たせず、方式側が scheduled_at の JST 時から決定的に解決する。インサイト収集 Step Functions の Input テンプレートはセクション 1.6 を参照。

1.4 EventBridge Scheduler の Retry / DLQ

Scheduler には RetryPolicy と SQS DLQ を設定する。RetryPolicy は MaximumRetryAttempts=3、MaximumEventAgeInSeconds=3600 を初期値とする。リトライを使い切っても画像生成 Step Functions を起動できない場合は、失敗イベントを Scheduler DLQ（セクション 10）に送信し、MonitoringStack の CloudWatch Alarm で検知する。

1.5 EventBridge Scheduler のスケジュール設定

命名規約（Phase 15-15 で確定）: acps-{env}-image-generation-{set_code}[-{slot_code}]

  • スロット非対応方式のセット: 1 セット 1 件。スロットサフィックスを付けない（例: acps-prod-image-generation-fantasy-animals-1）
  • スロット対応方式のセット（prompt_configs.parameters.slots を持つ方式。例: quiz-prebuilt）: スロットごとに 1 件で slot_code をサフィックスにする（例: acps-prod-image-generation-logic-training-1-morning）。スロットは方式側が SCHEDULED_AT の JST 時から決定的に解決するため、スケジュール時刻がそのままスロットの指定になる。名前にスロットを入れておくことで、実行時刻とスロットの対応が Scheduler 一覧だけで追える
  • 1 セットで 1 日複数回投稿する場合も 1 スケジュール 1 時刻を原則とする → 理由 D-08
  • Schedule 名の上限は 64 文字。acps-prod-image-generation-（27 文字）を差し引いた 37 文字が {set_code}-{slot_code} の予算になる

2. DB 準備確認タスク（db-readiness-check）仕様

この章は、すべての SFN の先頭で動く DB 準備確認の ECS タスクの仕様を示す。 → 理由 D-04 → 理由 D-05

Aurora Serverless v2 の自動一時停止からの再開に対応するため、各 Step Functions ワークフローの最初のステートとして DB 準備確認 ECS タスクを実行する。バッチアプリケーション（後続の ECS タスク）は DB が利用可能な状態を前提とする。

  • ECS Task Definition: FoundationStack で定義（db-readiness-check）。3 つのワークフロー（選定・投稿・収集）で共有する
  • リソース: 最小構成（0.25 vCPU / 0.5 GB）
  • 配置: Public Subnet（assignPublicIp=ENABLED）。Aurora（Isolated Subnet）へ VPC 内部ルーティングで接続する
  • リトライ設計: 
    最大リトライ回数: 8
リトライ間隔: 指数バックオフ（2, 4, 8, 16, 32, 64, 128, 256 秒）
対象例外: OperationalError, InterfaceError
    総待機時間は最大約 510 秒 → 理由 D-10
  • Step Functions との責務分担: WaitForDbReady ステートには Step Functions の Retry を設定しない。待機・再試行は db-readiness-check コンテナ内部で完結させ、総待機時間を上記の約 510 秒に固定する
  • 認証情報: Secrets Manager（DB 認証情報）から取得
  • 成功時: 終了コード 0 で終了し、Step Functions が次のステートへ遷移する
  • 失敗時: 終了コード 1 で終了し、Step Functions の Catch でハンドリングする

3. 画像生成 Step Functions ASL 定義

この章は、選定のワークフロー（acps-prod-image-generation-sfn）の定義を示す。図 2 はステートの流れで、続く JSON が CDK に渡す ASL の全文（infra/lib/asl/image-generation.asl.json）。

{
  "StartAt": "WaitForDbReady",
  "States": {
    "WaitForDbReady": {
      "Type": "Task",
      "Resource": "arn:aws:states:::ecs:runTask.sync",
      "TimeoutSeconds": 900,
      "Parameters": {
        "LaunchType": "FARGATE",
        "Cluster": "${EcsClusterArn}",
        "TaskDefinition": "${DbReadinessCheckTaskDefFamily}",
        "NetworkConfiguration": {
          "AwsvpcConfiguration": {
            "Subnets": ["${PublicSubnetId1}", "${PublicSubnetId2}"],
            "SecurityGroups": ["${DbReadinessCheckSgId}"],
            "AssignPublicIp": "ENABLED"
          }
        }
      },
      "ResultPath": null,
      "Catch": [
        {
          "ErrorEquals": ["States.ALL"],
          "Next": "HandleError"
        }
      ],
      "Next": "RunImageBatchTask"
    },
    "RunImageBatchTask": {
      "Type": "Task",
      "Resource": "arn:aws:states:::ecs:runTask.sync",

      "Parameters": {
        "LaunchType": "FARGATE",

            "AssignPublicIp": "ENABLED"

        },

          "ContainerOverrides": [

              "Name": "image-batch",

                { "Name": "SCHEDULED_AT", "Value.$": "$.scheduled_at" }
              ]
            }
          ]
        }
      },
      "Retry": [
        {
          "ErrorEquals": ["States.TaskFailed", "States.Timeout"],
          "IntervalSeconds": 30,
          "MaxAttempts": 2,
          "BackoffRate": 2.0
        }
      ],
      "ResultPath": null,
      "Catch": [
        {
          "ErrorEquals": ["States.ALL"],
          "Next": "HandleError"
        }
      ],
      "Next": "StartSnsPostBatch"
    },

          "IntervalSeconds": 10,
          "MaxAttempts": 2,
          "BackoffRate": 2.0
        }
      ],
      "Catch": [
        {
          "ErrorEquals": ["StepFunctions.ExecutionAlreadyExistsException"],
          "Next": "SnsPostAlreadyStarted"
        },
        {
          "ErrorEquals": ["States.ALL"],
          "Next": "NotifySnsPostStartFailure"
        }
      ],
      "End": true
    },
    "SnsPostAlreadyStarted": {
      "Type": "Succeed",
      "Comment": "同じ実行名の SNS 投稿 SFN は既に作成済みのため、二重起動せず成功扱いとする"
    },
    "NotifySnsPostStartFailure": {
      "Type": "Task",
      "Resource": "arn:aws:states:::aws-sdk:cloudwatch:putMetricData",

        "Namespace": "ACPS",
        "MetricData": [

            "MetricName": "SnsPostStartFailureCount",
            "Dimensions": [

                "Name": "StateMachineName",
                "Value": "${ImageGenerationSfnName}"
              }
            ],
            "Value": 1,
            "Unit": "Count"
          }

      },

      "Next": "ImageBatchSucceeded"
    },

      "Type": "Succeed",

    },
    "HandleError": {
      "Type": "Fail",
      "Error": "ImageBatchFailed",
      "Cause": "Image batch task failed after retries"
    }
  }
}
StartSnsPostBatch のエラーハンドリング 子の Input には set_code に加えて親の $.scheduled_at（Scheduler の予定時刻。WaitForDbReady / RunImageBatchTask は ResultPath: null のため上書きされない）を渡す（26-1 で追加）。Retry・ExecutionAlreadyExists の場合も同じ値・同じ実行名で、子が扱う回は変わらない。 ExecutionAlreadyExists は子実行作成済みとして成功扱いにする。それ以外のエラーで Retry 後も起動に失敗した場合は NotifySnsPostStartFailure でカスタムメトリクスを発行し、ImageBatchSucceeded で成功終了する。画像生成 ECS タスクは既に成功しているため、SNS 投稿の起動失敗のみでワークフロー全体を失敗にはしない。

4. SNS 投稿 Step Functions ASL 定義

この章は、投稿のワークフロー（acps-prod-sns-posting-sfn）の定義を示す。図 3 はステートの流れで、最初に入力の予定時刻が正しい形かを確かめる。

画像生成 Step Functions から startExecution（非同期）で起動される。画像生成 Step Functions は SNS 投稿の完了を待たずに終了する。手動での単独起動も可能。

本文の「→ 理由 D-xx」から飛んでくる先。

D-01 新しいセットのスケジュールは有効のまま追加し、稼働は is_active で切り替える

決めたこと
新しいセットのスケジュールは有効のままデプロイし、稼働の開始は batch_sets.is_active の UPDATE 1 文で行う（umigame-soup-1 では set-registration/04_activate.sql）。セット追加手順の「バックログ 0 件確認」（アプリ運用設計 2.1）は is_active を 1 にする直前に行う。長期の停止は CDK でスケジュールを外す
理由
3 つのバッチとも停止中のセットでは何もせず正常終了するため、有効化のためだけの 2 回目の cdk deploy が要らない。停止中に増えるのは SFN の空実行と DB 準備確認だけで、同じ時刻に他のセットが Aurora を起こしているので追加の費用はほぼない
日付・出典
2026-10-12（21-7）

D-02 スケジュールの設定・停止・再開は CDK を唯一の正とする

決めたこと

D-13 トークン更新 Lambda は DLQ を持たず、実行エラーを再試行しない

決めたこと
トークン更新 Lambda の非同期起動の再試行を 0 回にし、DLQ を置かず、失敗は Lambda の Errors アラームで即通知する。Scheduler のターゲット呼び出しの再試行（2 回・最大経過 1 時間）は呼び出しの失敗だけを対象とするので残す
理由
週 1 回の実行で、失敗した週は Secret を書き換えないため旧トークンのまま返信は続く。更新は失効（60 日）の 50 日以上前に行うので、数回続けて失敗しても人が直す余裕がある。自動で繰り返すより、すぐ人に知らせる方がよい
日付・出典
