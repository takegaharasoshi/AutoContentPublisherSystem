## 要旨（対応方針の現在形）

設計書の骨格が当初構成（Scheduler → その場で画像生成 → 投稿）のままで、今のシステムが読み取れない。文章が続くばかりで視覚的に追いにくい。「なぜ」の説明が事実の間に挟まり、抽象度の高い視点だけで確認することもできない。スキル主体の動画生産ラインには設計書上の居場所がない。

- **骨格（2 面）**:
  - **生産面（ローカル）**: スキル + `content/` のビルドツール → 人間レビュー → S3 / 在庫テーブルへ投入
  - **配信面（AWS）**: 素材の選定 → 投稿 / インサイト収集（コメントログの取り込みを含む）/ コメント自動返信 / トークン更新
  - 両面の接点 = 受け渡しの契約（S3 キー + 在庫テーブル）
- **段階化**: 基本設計 → 層の概要 → 詳細設計の 3 段にする
  - 基本設計: `docs/overview/` を作り直し、図と表で数ページにまとめる
  - 詳細設計: 既存の `docs/infra/` `docs/app/` と新設の `docs/production/` をそのまま位置づける。ディレクトリは再編しない（リンクを切らない）
- **置き場**: 第 3 の層 `docs/production/`（コンテンツ生産設計）を新設する。全体像・人間の関所・受け渡しの契約・スキル一覧を書き、工程の細部は SKILL.md を正とする
- **書き方**:
  - 各ページの冒頭に 1 画面の要約（図 1 枚 + 要点の表）を置く
  - 本文は事実だけにし、判断箇所には「→ 理由 D-xx」のリンクだけを置く。理由はページ末尾の「判断の記録」節にまとめる
  - 図は Mermaid をリポジトリに同梱して文字で書く（`docs/assets/vendor/`。外部 CDN には依存しない）。差分で追え、文章と同じ手間で直せるため、処理フローや状態遷移なども積極的に図にする
- **時期**: 据え置き。Phase 27（I-039）の後に Phase 28 として展開する。書式の移行は量が多いため、Phase 29 に分けることも検討する。下書きは壁打ち記録 2026-10-17 にある

## 選択肢と判断

- 生産ラインの置き場
  - **採用: 新しい層 `docs/production/`**。アプリ設計（AWS で動くプログラム）とは関心も実行場所も違う。「仕組みとして設計を見る」というユーザーの意図に合う
  - 不採用: `docs/app/` に分冊を足す案。体系の変更は小さいが、プログラムとスキルが同じ層に混ざって分かりにくさが残る
  - 不採用: SKILL.md を正にして設計書は索引だけにする案。最も軽いが、関所や受け渡しの契約を設計として見られない。ただし工程の細部を SKILL.md に任せる点だけは採用案に取り込んだ
- 時期
  - **採用: 方針だけ決めて据え置く**（Phase 26 完了がトリガー）
  - 不採用: Phase 26 の前に割り込ませる案（作業中の `docs/app/` 差分と衝突する）
  - 不採用: 今すぐフェーズを起票する案（ユーザー判断で、着手時期は Phase 26 の後に寄せた）
- 段階化の反映方法
  - **採用: 基本設計を新設し、既存を詳細設計に位置づける**。計画書・記録・課題表・スキル・CLAUDE.md にある大量のパス参照を切らずに済む
  - 不採用: ディレクトリごと `basic/` `detail/` に再編する案。構成は一目で分かるが、全参照の貼り替えが要り、作業量とリンク切れの危険が大きい
- 理由（なぜ）の置き場
  - **採用: 各ページの末尾に「判断の記録」節を置く**。理由が事実の近くにあり、ページごとに完結する
  - 不採用: `docs/decisions/` に集約する案（ADR）。判断を横断で一覧できるが、本文から別ページへ飛ぶことになる。開発記録との役割分担も新たに決める必要がある
- 文体の整形（アイデア「読みやす」）: 2026-10-17 の壁打ちで使わないことになった（再醸成待ち）。I-040 には含めない
- 図の描き方
  - **採用: Mermaid を `docs/assets/vendor/` に同梱する**（1 ファイル版 `mermaid.min.js` を `<script>` で読む。`file://` で直接開いても、スマホ閲覧の HTTP 経由でも動く）
  - 不採用: インライン SVG / HTML の手描き。外部ライブラリは要らないが、直す手間が重く、図にできる範囲が狭まる

## 原文メモ

> 設計書についての課題です。
>
> 設計書がだいぶ読みにくく、分かりにくいと感じています。当初想定していたシステム構成とだいぶズレてきているのが原因です。
>
> 具体的には：
> ・開発当初のベース構成：EventBridge でスケジュール実行をして、その場で画像生成を行い、その後、作成した画像を SNS に投稿する投稿バッチが動く
> ・現状の構成：Claude Code 上でスキルなどを使い事前に動画生成を行い、その動画を S3 などにアップロードした上で、SNS 投稿バッチで SNS に投稿する
>
> 現状、当初想定の構成のまま動いているものはない認識なので、このあたりをまるっと修正できればと思っています。
>
> あわせてシステム構成に表現したい点：
> ・コメント自動返信機能
> ・インサイト収集バッチ
> ・トークンを更新するバッチ
> ・コメントを集計するバッチ
>
> また、それに伴うアプリ設計についてですが、現状は基本的にプログラムに関わる内容が記載されているかと思います。
> 一方で、このシステムの動画生成部分はすべてスキルで実現しているため、スキルの仕様（どういうスキルがあって、どういう風にレビューをしていくかなど）が設計書上で表現できていません。
>
> 一応、運用設計に書いているのかもしれませんが、ちょっと分かりにくい気がしています。動画生成は単なる運用というよりは、スキルを使って仕組み自体を作っているイメージなので、ただの運用には収まらないと考えています。そのあたりも分かりやすく、設計書の体系として表現したいです。

（2026-10-17 追記）

> 設計書の構成について諸々検討していただきましたが、補足として、私がさらに分かりにくいと考えているポイントについて説明します。
>
> 現状、かなり文章がつらつらと並んでいるように見えるので、表や図などをたくさん使って、より見やすくしたいと考えています。視覚的に見やすいというところが一番大事かなと思っています。
>
> あと、設計書の中に「なぜこのような設計にしたのか」や「なぜこういう判断にしたのか」といった背景の説明が、結構な分量あると考えています。これは非常に大切なところですが、現状の事実のみ知りたい場合には邪魔になってしまうかもしれません。
>
> そのため、設計書の本文には基本的に「なぜそうしたのか」は記載せず、最後の方にまとめて「ここをこう判断した理由はこうです」と参照で飛ばすような形で書くのが良いのかなと考えています。
>
> また結構細かいところまで設計書に書かれていると思います。それについては正直問題ないんですが、細かいところはあまり見ず、もう少し概要というか、抽象度が高い視点でチェックしていきたいと考えています。
>
> 一般的にはこういう設計って段階的に詳細化していくようなイメージですので、設計書の構成自体も、例えば基本設計と詳細設計というように、段階的に詳細化するような構成に変更するのもありなんじゃないかなと考えています。
