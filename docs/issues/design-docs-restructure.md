## 要旨（対応方針の現在形）

設計書の骨格が当初構成（Scheduler → その場で画像生成 → 投稿）のままで、今のシステムが読み取れない。スキル主体の動画生産ラインは設計書に居場所がない。

- **骨格**: システムを 2 つの面で描き直す。
  - **生産面（ローカル）**: Claude Code のスキル + `content/` のビルドツール → 人間レビュー → S3 / 在庫テーブルへ投入
  - **配信面（AWS）**: 素材の選定 → 投稿、インサイト収集（コメントログの取り込みを含む）、コメント自動返信、トークン更新
  - 両面の接点 = 受け渡しの契約（S3 キー + 在庫テーブル）
- **置き場**: 設計書体系に第 3 の層 `docs/production/`（コンテンツ生産設計）を新設する。設計書には全体像・人間の関所・受け渡しの契約・スキル一覧を書き、工程の細部は SKILL.md を正とする（二重管理しない）
- **時期**: 方針だけ決めて据え置く。Phase 26 が `docs/app/` を改訂中のため、完了後に新フェーズ（Phase 28 想定。Phase 27 は I-039 に充てた）へ展開する。展開の下書きは壁打ち記録 2026-10-13 にある

## 選択肢と判断

- 生産ラインの置き場
  - **採用: 新しい層 `docs/production/`**。アプリ設計（AWS で動くプログラム）とは関心も実行場所も違う。「仕組みとして設計を見る」というユーザーの意図に合う
  - 不採用: `docs/app/` に分冊を足す案。体系の変更は小さいが、プログラムとスキルが同じ層に混ざって分かりにくさが残る
  - 不採用: SKILL.md を正にして設計書は索引だけにする案。最も軽いが、関所や受け渡しの契約を設計として見られない。ただし工程の細部を SKILL.md に任せる点だけは採用案に取り込んだ
- 時期
  - **採用: 方針だけ決めて据え置く**（Phase 26 完了がトリガー）
  - 不採用: Phase 26 の前に割り込ませる案（作業中の `docs/app/` 差分と衝突する）
  - 不採用: 今すぐフェーズを起票する案（ユーザー判断で、着手時期は Phase 26 の後に寄せた）

## 原文メモ

> 設計書についての課題です。
>
> 設計書がだいぶ読みにくく、分かりにくいと感じています。当初想定していたシステム構成とだいぶズレてきているのが原因です。
>
> 具体的には：
> ・開発当初のベース構成：EventBridge でスケジュール実行をして、その場で画像生成を行い、その後、作成した画像を SNS に投稿する投稿バッチが動く
> ・現状の構成：Claude Code 上でスキルなどを使い事前に動画生成を行い、その動画を S3 などにアップロードした上で、SNS 投稿バッチで SNS に投稿する
>
> 現状、当初想定の構成のまま動いているものはない認識なので、このあたりをまるっと修正できればと思っています。
>
> あわせてシステム構成に表現したい点：
> ・コメント自動返信機能
> ・インサイト収集バッチ
> ・トークンを更新するバッチ
> ・コメントを集計するバッチ
>
> また、それに伴うアプリ設計についてですが、現状は基本的にプログラムに関わる内容が記載されているかと思います。
> 一方で、このシステムの動画生成部分はすべてスキルで実現しているため、スキルの仕様（どういうスキルがあって、どういう風にレビューをしていくかなど）が設計書上で表現できていません。
>
> 一応、運用設計に書いているのかもしれませんが、ちょっと分かりにくい気がしています。動画生成は単なる運用というよりは、スキルを使って仕組み自体を作っているイメージなので、ただの運用には収まらないと考えています。そのあたりも分かりやすく、設計書の体系として表現したいです。

## 壁打ち記録

### 2026-10-13

- 実態の確認（調査）:
  - 実行時の AI 生成は本番で未使用。稼働 3 セットはすべて prebuilt 方式
  - 画像生成バッチは Scheduler → SFN で毎回動くが、中身は「S3 の事前ビルド済み動画を在庫から LRU で 1 本選んで登録」。枠組みは当初のまま、役割が「生成」から「素材の選定」に変わった
  - トークン更新 = CommentReplyStack の Lambda（毎週月曜 4:00 JST）
  - **コメント集計は独立バッチではない**: insights-batch が 6:00 / 18:00 に S3 の comment-log を `umigame_comment_logs` へ取り込む。図ではインサイト収集の 1 機能として描く
- 設計書側のズレ（改訂時の掃除リスト）:
  - `system-overview.html` が全面的に当初構成。`architecture.html` も同じで、comment-reply が 1.1 節に後付けされ、insights とトークン更新は載っていない
  - `workflow.html` の insights Scheduler 表が古い（fantasy・logic のみ。実際は logic・pref・umigame）
  - `batch-flow.html` の方式カタログ: ranking / umigame-prebuilt が「採用予定」、kenburns が「採用中」のまま。comment-reply の処理フローがない
  - `design-outline.html`「インフラはセット追加で増えない」が CommentReplyStack と矛盾
  - `app/index.html` の umigame「1 日 1 回」は誤り（週 4 回）
  - `operation.html` 3 節に umigame の節がない。5.5「画像生成 API キー」は実行時生成前提
  - 生産側の説明が 3 か所に散在（`generators/*-prebuilt.html` 8 節 / `operation.html` 3 節 / `content/` README）。人間の関所（候補選別・G1〜G5 等）と quiz-review-learn は設計書に記述がない
