3. 確認待ちリストとの関係

各計画書の確認待ちリスト（計画体系 5.2）は本体系へ統合しない。ステップ・レーンに紐づく短命の観察項目で、レーンの入口（/step・補充スキル）が既に読んでいるため計画書に残す。違いはトリガーが引かれたときの動作にある。

  • 確認待ち: 観察して OK / NG を判定し 1 回で閉じる（OK → 記録へ移す / NG → 課題として本体系へ起票）
  • 課題: トリガーごとに再判断を繰り返しうる（据え置き継続〔トリガー更新〕/ 展開 / 受容）
  • 共通化するのはトリガーの書式（4.4）と棚卸しの節目（4.8）だけ。確認待ちの「NG 時の扱い: 課題として起票」の行き先は本ページ

4. 運用ルール（正）

4.1 課題の単位とアイデアとの境界

  • 1 課題 = 対応方針を 1 つ決められる単位で、表の 1 行。課題とアイデアの境界（リトマス）: 課題 = 何もしないと損なわれるものがある（既存の欠陥・持ち越し・リスク・設計レビューの改善提案）/ アイデア = やれば増える価値がある（アイデア体系）。迷ったら「放置したとき何が損なわれるか」を具体的に言えるほうが課題
  • 課題は「これから変えるべきこと + トリガー」だけを持つ。起きたこと（事象・復旧手順・解決策）は書かない（4.7）
  • 粒が大きく複数の対応方針に割れる課題は、壁打ち（4.5）で割ってから行を分ける。起票時は曖昧でよい（ステータス 起票）

4.5 2 層構造（表が正・壁打ち時のみ MD）

  • 正は本ページの表。起票時にファイルは作らない（課題は件数が多く粒が小さい。全件にファイルを作ると墓場化する）
  • 壁打ちを始める時点で docs/issues/<slug>.md を _template.md から作り、壁打ち列にリンクを付ける。MD が持つのは「要旨（対応方針の現在形・Claude が毎回書き直す）」「選択肢と判断」「原文メモ（追記のみ）」「壁打ち記録（追記のみ・蒸留）」。表と MD が乖離したら表が正（ステータス・トリガーは表にだけ書き、MD には写さない）
  • 詳細 HTML <slug>.html は構成図・比較表が要るときだけ。作ったら MD の要旨はリンク 1 行に置き換える（同じ情報を 2 箇所に書かない）
  • 壁打ちの終了規律（アイデア体系 4.4 と同型）: 1 回の壁打ちは必ず 据え置き（トリガー更新）/ 展開（ステップ起票）/ 受容（理由付き） のどれかに着地し、表を同期する。「なんとなく放置」を許さない。壁打ち中に出た別の課題はその場で起票（壁打ちはしない）し、本筋に戻る。入口はスキル /issue の壁打ちモード（22-3 で新設）

4.6 エスカレーション規則（発生実績型の既定）

  • 「発生実績を見て判断」型のトリガーは回数を明記し、発生ごとに発生履歴列へ日付 + 事象記録リンクを足す
  • 既定: 1 回目 = 記録 + 再判断（据え置き継続を選んでよいが、トリガーの回数を「2 回目で据え置き不可」に更新する）。2 回目 = 据え置き不可。ステップとして起票（展開）するのが既定で、受容へ倒すのはユーザーの明示の判断がある場合のみ（理由付き）
  • 既定より厳しくするのは自由（初回で展開）。緩めるとき（3 回目まで据え置く等）は理由をトリガー列に書く
  • 再発の検知と発生履歴の更新は /incident（22-3）の工程。それまでは障害対応の冒頭で本ページを症状・セット名・パスで grep する

4.7 事象記録との切り分け

  • 事象（起きたこと・復旧手順・解決策 = 過去向き）は記録ファイルへ: セット固有は docs/plans/<set_code>-log.html、横断・基盤は 開発記録の「事象記録」節（22-2 で新設。旧トラブルシューティングログの 3 行を移す）。課題（これから変えること = 未来向き）は本ページへ。行に復旧の経緯を書き込まない（行の肥大を防ぐ。2026-07-22 起票の「空 generation_run」の項がその実例）
  • 障害 1 件から出るもの = 事象記録 1 件（必ず）+ 課題 0〜n 件（恒久対策が要るとき）+ 既存課題の発生履歴更新（再発のとき）
  • その場で直した対策も課題として起票し、即 解消 に落とす（「何が変わったか」の知識をクローズ節に集める。「何が起きたか」は記録に、と置き場を一意にする）
  • 障害対応の入口はスキル /incident（22-3）: 症状の聞き取り → 照合（本ページの live + クローズ・当該レーンの確認待ち・事象記録を症状・セット名・パスで検索し「予言されていた課題」「前にも起きた事象」を原因究明の前に提示） → 切り分けと復旧（本番操作は人間ゲート）→ 事象記録 → 課題の更新 → コミット・push。コードでの修正は /incident の中では行わず、課題を起票して /step（開発レーン）で行う

4.8 課題レーン・照合の入口・棚卸し

  • 課題レーン: docs/issues/ 配下 + スキル .claude/skills/issue/ .claude/skills/incident/ で閉じる作業は常に並行可・宣言不要（アイデアレーンと同じ。計画体系セクション 2 の判定表）。セットレーンのセッションが開発レーン向けの課題を見つけた場で起票できる。ただし展開（ステップ起票）は展開先の計画書のレーンで行う（開発計画なら開発レーン、セット計画書ならそのセットレーン）
  • 照合の入口 5 つ（据え置き課題のトリガーを引く動線。22-3・22-4 で各入口に組み込む）: (a) /step 起動時に触るパスで対象パス列を照合 (b) 補充スキル起動時にセット名で照合 (c) 起票チェックリスト 5.1（フェーズ・改修・採用転記のすべての起票で、触るパスに該当する据え置き課題を同梱するかトリガーを更新する） (d) /incident（障害時） (e) 棚卸し
  • 該当行があったときの動作: そのゴール・起票の中で「同梱する（展開）/ トリガーを更新して据え置き継続 / 受容」を決めて表を更新する。黙って通り過ぎない（/step は「課題表: 該当なし」の宣言を残す）
  • 棚卸しの節目（新しい儀式は作らない）: 月次 KPI 転記（運用設計 6.3）と、フェーズ完了・改修完了の節目に、live のトリガー列を上から確認する（日付型・節目型を拾う）。起票 のまま残っている行はここで対応方針を決める。確認待ちリストの棚卸しと同時に行う

4.9 クローズの運用

  • 解消: 展開したステップの完了時に、/step の完了手順（22-4 で追加。それまでは手動）が行をクローズ節へ移す（クローズ日 + ステップ・コミットへのリンク）
  • 受容: 直さない理由を「結果」列に書いてクローズ節へ。再検討の余地があるなら受容ではなく据え置き（トリガー付き）にする
  • 再発: /incident がクローズ節から live へ戻す（ID・発生履歴を継続し、エスカレーション規則を適用）
  • クローズ節が 50 行を超えて閲覧の妨げになったら closed.html へ分け、本ページにリンクを残す（/incident の照合対象は分けた後も両方）
