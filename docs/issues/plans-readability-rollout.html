2. テンプレートと検査の契約

見出しの日本語だけで機械判定せず、HTML に構造を示す属性を付ける。本文の正は各計画書であり、属性は検査と表示のために使う。

  • ページ：data-plan-format="1"。検査対象はモジュール内の明示リストに登録し、この属性を消しても検査を回避できない。登録済みページのファイル削除、ステップ 0 件、形式の混在も NG。25-5（2026-09-22）で追加：ステップを 1 件も持たないページは data-plan-steps="none" で明示的に宣言した場合だけステップ 0 件を許す（宣言したページにステップがある、none 以外の値を書く、はどちらも NG）。
  • フェーズ：data-plan-phase。内部に完了済みグループと進行中グループを持ち、完了済みが先。完了済みグループは details で open を付けない。
  • ステップ：article.plan-step、安定した id="step-21-6"、data-step-id、data-status="todo|doing|done|blocked"。完了状態は完了日が必須。ID 重複と状態に合わないグループ配置を NG とする。
  • 常時表示の欄：data-field="overview|prerequisites|constraints|acceptance|gate|stop|result"。空欄は不可で、該当なしなら明記する。完了条件は ul/ol のリストで、実装詳細や記録の折りたたみ内に入れてはいけない。完了済みグループ自体の折りたたみは許容する。
  • 実装詳細：details[data-field="implementation"]。作業記録：details[data-field="record"]。別要素として置き、初期状態は閉じる。記録未作成はその旨を明記。整理後の記録欄は section[data-field="record"] 内の記録リンクだけでも可。
  • ユーザー判断のステップ：data-kind="decision" と「ゴール対象外」を表示し、完了条件には判断内容、停止点にはゴールにしない旨を記載。
  • 完了条件等が残っていない古い完了ステップ：data-kind="legacy-completed" を明記した場合だけ、未記録の説明と記録リンクで代替可。done 以外でこの例外を使うことは禁止する。過去の条件を推測で作らない。

検査が担保しないこと：重要な制約が文章としてすべて拾われているか、要約が正しいか、記録と最新状態が一致するか。更新者は差分のステップについてこの 3 点を読み直す。構造検査の成功を内容の正しさと同一視しない。

3. 日常更新の流れ

  1. 新規ステップはテンプレートの枠をコピーして ID と内容を記入。既存ステップは同じ枠内を更新。
  2. 作業中は記録の折りたたみに追記し、状態と短い結果・次の作業も更新。完了時は完了日を付け、同フェーズの完了済みグループへ移動する。
  3. 計画整理時に詳細を log へ移す。移した本文を plan に残さずリンクへ置き換える。経緯がまだ未移管でも、状態・完了日・要点の更新は遅らせない。
  4. python3 tools/docs_check.py --plan-only（追加予定）を実行。NG なら修正する。成功表示は「構造・参照のみ」で、表示の実測は別扱い。
  5. CSS・テンプレート変更または新しい計画書への初回適用では、python3 tools/docs_check.py --widths 360,390,768,1280 と折りたたみ・フォーカスの確認も行う。

スキル外で手動編集したときも CLAUDE.md の共通規約から同じ検査へつなぐ。この案は検査を実行すれば崩れを検出する仕組みであり、検査を飛ばした push をサーバー側で阻止するものではない。現在リポジトリに .github/ はなく、CI の新設は別判断とする。
