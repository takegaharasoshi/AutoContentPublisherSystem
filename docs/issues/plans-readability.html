進め方の方針運用ルールを失わないよう、本適用時に計画体系 5 の様式・切り方と既存の重複を統合し、未収録の共通方針だけ補う。計画体系 5 冒頭には開発計画のこの節への参照があるため修正が必要。設計 Fix は docs/index.html のセクション 4、モデル割当は CLAUDE.md の既存規約への参照を使い、ルール全文を重複移管しない。CDK の論理 ID・env 指定の注意も削除前に適切な参照先を確保する。
計画書の更新履歴ページの変更理由をその場で追う便宜は減るが、開発記録と Git 履歴で追跡できる。更新日と記録リンクだけ残す。履歴を計画体系 index へ移す必要はない。

記載方針を維持する仕組み（本適用時の案）

共通ルール・HTML テンプレート・更新手順・構造検査を一組で導入する。現在の検証ツールはリンク・横幅・課題表などを確認するが、ステップの 5 項目や記録の置き場は検査していない。以下は未実装の導入案。

  1. 正を一本化：計画体系 index の記載様式に、常時表示する情報・独立した 2 つの折りたたみ・完了済みステップの位置・記録を整理時に移す運用を定義する。既存の「完了時に詳細を記録へ移す」規則との整合も取る。
  2. 共通テンプレート：ステップ ID・状態・着手条件・概要・箇条書きの完了条件・人間ゲート・停止点・実装詳細・作業記録の枠を用意する。新規作成はその枠から行う。
  3. 既存スキルに組み込む：step の着手・分割・終了、idea / issue の計画下書き、補充スキルの計画更新が同じ様式を参照する。記録追記時には状態と短い要点も更新する。新しい儀式や別の作業入口は増やさない。
  4. 機械検査：既存 docs_check.py に、対象計画書の必須項目・ID 重複・完了条件のリスト構造・実装詳細と記録の初期閉状態・完了済みグループの位置を検査する規則を追加する。計画更新の完了条件へ組み込み、不備があれば非ゼロ終了にする。旧形式や別種の表は対象を明示して区別する。
  5. 内容の確認：重要な制約が詳細に埋もれていないか、概要が実態と一致するかは機械だけで判断できない。更新したステップだけを終了時に読み直す。検査を実行しなければ防げないため、完全自動の強制が必要なら別途 CI に接続する。
