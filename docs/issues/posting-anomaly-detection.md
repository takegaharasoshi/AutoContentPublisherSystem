## 要旨（対応方針の現在形）

投稿予定の枠ごとに成功を確認し、欠番と処理途中の残留を通知する案を検討する。以下は初回の提案であり、合意済みの仕様ではない。
I-017 の過去分持ち越し・朝夜ずれ防止は Phase 26 に同梱されており、ここでは残る検知を扱う。
「当日 success 0 件」では朝が成功した日の夜の欠番を見逃すため、セット・予定時刻・投稿先アカウント・必要な投稿種別を判定単位の候補とする。
通知までの猶予、ストーリーズの扱い、監視の実行方式はユーザーとの壁打ちで決める。

## 選択肢と判断

- 既存の失敗通知だけを使う: 0 件処理で正常終了する欠番と、成功が続く滞留を十分に拾えない。
- バッチ終了時に成否を検査する: 終了時点の異常に近い位置で検知できるが、起動しなかった場合は別の検知が必要。
- 投稿予定から独立した照合を行う（提案）: 予定枠と結果を比較し、生成実行や投稿行自体がないケースも拾う。停止中のセット・意図的なスケジュール停止を除外できる予定情報の正を決める必要がある。
- ダッシュボード中心: 人が見に行くまで気づかないため、通知の代替にはしない。必要性は別途判断する。

判定案:

- 猶予を過ぎた予定枠に成功記録がない: 「投稿成功を確認できない」と通知する。`published_unconfirmed` は未投稿と断定せず「公開結果の確認が必要」と区別する。
- `pending` / `container_created` の残留: 実行中・再試行中との区別、経過時間を踏まえて通知する。欠番と同じ枠なら通知をまとめる案。
- `records_processed=0` は補助情報とし、それだけで異常とは判定しない（既に投稿成功している再実行などを区別）。
- 既存のメール通知先を使い、セット名・予定枠・確認できた状態・確認先を伝える案。自動再投稿や在庫戻しは今回の検知とは分ける。
- 同じ異常の繰り返し通知、復旧通知、監視自体の失敗検知は方式決定時に詰める。
