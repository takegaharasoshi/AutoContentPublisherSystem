空の生成実行が、後続の投稿を止める

なぜ正常に生成できた動画まで投稿されなくなるのか。原因と、投稿対象の選び方を変える対策をまとめます。

推奨：素材のある実行だけを投稿候補にする

推奨は、投稿対象の選定 SQL に「その生成実行の generated_media が 1 件以上ある」という条件を加えること。生成に失敗した空の実行を候補から外し、後続の正常な実行を投稿できるようにする。 I-022・I-024 と同じ改修フェーズで管理する既存方針は維持し、I-014 は独立した先頭ステップにする案を提案する。API クライアント統合やリトライ設計の完了を、この修正のリリース条件にしない。 本書は事象と対策を一緒に読める検討資料であり、実装済みの設計書ではない。実装・本番操作は今回行っていない。管理状態・再判断条件・発生履歴の正は 課題表 I-014。

1. 事象と原因

現状：空の実行で止まる

  1. 古い A：素材なし ／ 新しい B：素材あり
  2. 古い A が投稿候補になる
  3. キャプション生成・素材取得で失敗
  4. 次回も A が選ばれる

B は正常でも、投稿に進めない。

対応案：素材のある実行を選ぶ

  1. 古い A：素材なし ／ 新しい B：素材あり
  2. 素材なしの A を候補から外す
  3. 既存条件を満たす B を選ぶ
  4. B の投稿処理に進める

空の実行が、後続を塞がなくなる。

generation_runs は「生成処理を始めた記録」、generated_media は「生成できた画像・動画の記録」である。実行記録があることと、投稿できる素材があることは同じではない。

現行の画像生成バッチは、生成実行を確定（commit）してから素材の生成処理に進む。途中で検証などに失敗すると、実行記録だけが残り、素材が 0 件になることがある。これは投稿 API のエラーや在庫枯渇に限った問題ではない。

投稿バッチは、同じセットの実行から「有効アカウントの少なくとも一つに、終端状態の投稿がないもの」を古い順に 1 件選ぶ。素材の有無を調べる条件がないため、空の実行も候補になる。

  1. 古い実行 A は生成失敗で素材が 0 件。新しい実行 B は生成成功で素材がある。
  2. 投稿バッチが A を選ぶ。
  3. A のキャプション生成または素材取得で失敗する。アカウントごとの投稿処理に入る前なので、候補から外す終端状態の posts が作られない。
  4. 次回も A が選ばれ、B が投稿されない。この繰り返しが後続の投稿を塞ぐ。

影響は選定対象のセット内で生じる。1 回分の生成失敗が、その後の正常な生成分まで止める点が問題である。

実際の事象から分かること

logic-training-1 の事象記録では、実行時生成の検証失敗で残った空の run 44 が後続を塞いだ例と、ストック方式の実行時文字数検証で残った run 165 が、正常生成された run 168 を塞いだ例が記録されている。後者は課題表で約 13 時間の停止として扱われている。日時と復旧操作の原記録は同リンクおよび課題表に集約する。

run 44 は素材なしの例外、run 165 はそれより前のキャプション生成で例外になった。したがって、素材取得後の例外を握りつぶすだけでは両方を防げない。候補の選定段階で空の実行を外す必要がある。

ストックの入力検証を改善しても、別の生成失敗で空の実行が残る経路はある。I-033 の対策だけで I-014 が解消したとは扱えない。

2. 推奨する対応

既存 SQL の WHERE gr.set_id = %s に続く条件として、次を追加する案とする。

AND EXISTS (
    SELECT 1
    FROM generated_media gm
    WHERE gm.generation_run_id = gr.id
)

既存の有効アカウント・終端状態の条件、scheduled_at ASC, id ASC の順序、1 回に 1 実行だけ処理する方針は維持する。EXISTS なら素材が複数ある場合でも実行候補を重複させず、必要な「少なくとも 1 件」を直接表せる。

この修正後、A が空で B に素材があれば B が選ばれる。空の実行しかない場合は対象なしとなり、既存仕様どおり records_processed=0 の正常終了になる。空の実行自体を削除したり、架空の投稿失敗行を作ったりする必要はない。後から生成の再実行で素材が登録されれば、その実行は再び候補になり得る。

変更対象案:

  • services/sns-post-batch/app/target_selection.py: 素材の存在条件を追加する。
  • services/sns-post-batch/tests/test_target_selection.py と test_e2e_local_mysql.py: 条件と実際の選定結果を検証する。
  • docs/app/batch-flow.html 3.1: 投稿可能な候補の定義を更新する。
  • docs/app/data-model.html 4.4: 掲載している選定 SQL も同期する。フローだけ直すと SQL の説明が古いまま残る。

既存の generated_media には generation_run_id を先頭とする一意キーが設計されている。DDL 変更を前提にせず、開発時に実 DDL とローカル MySQL の実行計画を照合する。

この対策の限界

  • DB に素材レコードがあることは、S3 上の実体やキャプション用データの健全性までは保証しない。今回防ぐのは素材 0 件の実行による連続停止である。
  • 空の実行だけなら正常終了になるため、「投稿できたか」を別途見る必要がある。空の実行の可視化・投稿ゼロ検知は既存の I-006・I-025 の検討へつなぐ。今回の SQL 修正に監視基盤の完成を必須条件として足さない。
  • 過去の正常な素材の滞留や、朝用動画を夜に投稿してしまう問題（I-017）は残る。空の実行を外せば、次に選ばれるのは「当回分」とは限らない。リリース前に対象セットのバックログと時間帯を確認し、復旧で必要な対象外化・在庫戻しは既存運用の人間ゲートで扱う。
  • main.py の素材なし例外は残す。選定後にデータが変更されるなどの不整合まで、成功として隠さない。

3. 対応案の比較

  • 選定時に素材の存在を確認する（推奨）: 投稿側に閉じた変更で、生成失敗の原因によらず後続への波及を防げる。検証範囲が小さく、既存の再開条件も保てる。
  • 空の実行を手動削除・対象外化する: 過去の復旧には有効だったが、検知と人手に依存する。恒久対策にはしない。
  • 生成側の commit を遅らせる・失敗時に必ず削除する: 再実行の識別や途中成果の保存に関わる。外部 API・S3 操作まで DB の rollback で戻せるわけでもない。広い再開設計の変更を今回の前提にしない。
  • 生成完了ステータスを新設する: 将来、素材と付随データの完成を厳密に保証するなら検討余地はあるが、DDL・生成側・投稿側の更新が必要。素材 0 件の除外には大きすぎる。
  • 最新の実行だけ投稿する: 後続へ進めても、未投稿分の順序と再開方針を変える。I-017 と合わせた別の判断になる。
  • 生成失敗の原因だけ直す・何もしない: 異なる生成方式でも空の実行が詰まることが記録されており、再発経路を塞げない。

4. 開発への引き継ぎ

既存の I-014・I-022・I-024 を束ねるフェーズ内で、I-014 を先頭の独立ステップにする案。残りの API 統合・エラー理由の保存・リトライは後続ステップとして分ける。ここでは I-022 の API バージョン移行や I-024 のリトライ仕様を新たに確定しない。

実装範囲・完了条件・受け入れケースを開く

ステップ案: 空の生成実行を投稿対象から除外する

  • 内容: 上記の選定 SQL・テスト・設計書 2 本を変更する。実装前に課題表を再照合し、同一フェーズの I-022・I-024 は後続ステップへ分離する。共通パスを持つ I-006・I-017・I-025 の監視・滞留対策、I-012 の SNS 別分冊、I-015 の AI 開示タグ検証は今回の修正に同梱しない。後続分のトリガー更新はフェーズを正式起票する開発レーンで行う。
  • 完了条件: ローカル MySQL で下記の選定ケースが通り、投稿バッチの既存テストが通る。フローと SQL の説明が実装と一致する。DB テストが実行できず skip の場合は合格としない。本番での再発なしや翌日の投稿は完了条件に含めない。
  • 人間ゲート: 差分・検証結果・既存バックログの扱いを確認してから push する。承認後の CodePipeline 確認は既存の開発手順に従う。本番データの削除・補正や SNS 投稿をこのステップで自動実行しない。
  • 停止点・上限: 実装セッションはコミットと証跡提示まで。目安 20 ターン。DDL や生成側の変更が必要と判明した場合は範囲を広げず、開発レーンで分割を再判断する。

選定ロジックの受け入れケース

  1. 古い空の実行 + 新しい素材あり実行 → 新しい実行を選ぶ。空の実行にキャプション用データもない場合を含める。
  2. 空の実行だけ → 対象なし。main の既存の 0 件終了へ進む。
  3. 素材ありの未完了実行が複数 → 既存どおり最古を選ぶ。同時刻なら ID 順。
  4. 素材ありでも有効アカウントすべてが終端状態 → 選ばない。有効アカウントがない場合も選ばない。
  5. 複数アカウントのうち一部だけ未完了、または pending / container_created → 既存の再開対象として選ぶ。
  6. 別セットの素材しかない実行 → 選ばない。同一実行に素材が複数 → 実行は 1 件として選ぶ。
  7. 一度空として除外した実行に素材を追加 → 終端条件を満たさなければ再び候補になる。
  8. 既存の素材なし例外テストを維持し、選定後の不整合は失敗として検知する。

現行の test_target_selection.py はカーソルをモックして SQL の一部を検査するため、それだけでは「空の先頭を飛ばして次を選ぶ」を実証できない。既存のローカル MySQL テストの仕組みを使って DB 上の選定を確認する。外部投稿 API は偽物を使う。

計画体系 5.1 の照合: 変更は開発レーン内、I-014 単体は 20 ターン目安で収め、API 統合とは分離する。将来の定時実行を完了条件にせず、リリース後の投稿・時間帯・0 件処理の観察は必要に応じ開発レーンで確認待ちへ登録する。
