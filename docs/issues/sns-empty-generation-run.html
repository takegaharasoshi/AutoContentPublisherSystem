朝の失敗を夜へ持ち越さない投稿にする

当回の予定時刻で投稿対象を固定し、生成失敗や未投稿分の滞留があっても、次の回はその回の素材だけを扱う方針です。

承認された方針：当回だけを対象にし、過去分へ戻らない

セット名と当回の予定時刻で生成実行を特定し、素材がある場合だけ投稿する。朝の空の実行も、素材はあるが未投稿の朝の実行も、夜の投稿候補には入れない。夜・翌朝それぞれの生成と投稿が成功すれば、その回の内容で投稿する。当回が失敗した回は欠番を許容する。

2026-09-21 にユーザーが方針を承認。以下は実コードを照合した変更範囲と開発レーンへの展開案であり、実装・本番操作は未実施。I-014 と I-017 の時間帯ずれ防止をまとめ、I-022・I-024 は同じフェーズの後続へ分ける。

管理状態・再判断条件・発生履歴の正は I-014 / I-017。正式なステップ番号は開発計画への転記時に採番する。

1. 事象と原因2. 推奨する対応3. 対応案の比較4. 変更ファイル5. ステップ展開案6. 根拠と確認範囲

1. 事象と原因

現状：空の実行で止まる

  1. 古い A：素材なし ／ 新しい B：素材あり
  2. 古い A が投稿候補になる
  3. キャプション生成・素材取得で失敗
  4. 次回も A が選ばれる

B は正常でも、投稿に進めない。

対応案：夜の回は夜の実行を指定

  1. 朝 A：失敗 ／ 夜 B：生成成功
  2. 夜の予定時刻を投稿側まで引き継ぐ
  3. 夜 B だけを照合し、素材があれば投稿
  4. 翌朝も、翌朝の予定時刻の実行だけを照合

朝 A の素材の有無にかかわらず、夜 B を塞がない。

generation_runs は「生成処理を始めた記録」、generated_media は「生成できた画像・動画の記録」である。実行記録があることと、投稿できる素材があることは同じではない。

現行の画像生成バッチは、生成実行を確定（commit）してから素材の生成処理に進む。途中で検証などに失敗すると、実行記録だけが残り、素材が 0 件になることがある。これは投稿 API のエラーや在庫枯渇に限った問題ではない。

投稿バッチは、同じセットの実行から「有効アカウントの少なくとも一つに、終端状態の投稿がないもの」を古い順に 1 件選ぶ。素材の有無を調べる条件がないため、空の実行も候補になる。

  1. 古い実行 A は生成失敗で素材が 0 件。新しい実行 B は生成成功で素材がある。
  2. 投稿バッチが A を選ぶ。
  3. A のキャプション生成または素材取得で失敗する。アカウントごとの投稿処理に入る前なので、候補から外す終端状態の posts が作られない。
  4. 次回も A が選ばれ、B が投稿されない。この繰り返しが後続の投稿を塞ぐ。

影響は選定対象のセット内で生じる。1 回分の生成失敗が、その後の正常な生成分まで止める点が問題である。

実際の事象から分かること

logic-training-1 の事象記録では、実行時生成の検証失敗で残った空の run 44 が後続を塞いだ例と、ストック方式の実行時文字数検証で残った run 165 が、正常生成された run 168 を塞いだ例が記録されている。後者は課題表で約 13 時間の停止として扱われている。日時と復旧操作の原記録は同リンクおよび課題表に集約する。

run 44 は素材なしの例外、run 165 はそれより前のキャプション生成で例外になった。したがって、素材取得後の例外を握りつぶすだけでは両方を防げない。候補の選定段階で空の実行を外す必要がある。

ストックの入力検証を改善しても、別の生成失敗で空の実行が残る経路はある。I-033 の対策だけで I-014 が解消したとは扱えない。

2. 対応の仕組みと境界

既存の予定時刻を、そのまま投稿まで渡す

現在の Scheduler は set_code と scheduled_at を画像生成 SFN に渡している。生成側は UNIQUE (set_id, scheduled_at) で実行を一意に管理する。一方、子の投稿 SFN の起動入力は set_code だけで、ここで当回の識別情報が失われている。

  1. 親 ASL の StartSnsPostBatch.Input に scheduled_at.$: $.scheduled_at を追加する。
  2. 子 ASL から ECS の SCHEDULED_AT へ渡す。
  3. 投稿アプリが UTC・秒精度の YYYY-MM-DDTHH:MM:SSZ を必須入力として検証する。現在時刻の代入・最新実行の検索・最古の実行へのフォールバックは行わない。
  4. 同一セット・同一予定時刻の実行だけを照合し、素材の存在と既存のアカウント別終端条件を確認する。
Scheduler の scheduled_at
  → 画像生成 SFN / generation_runs.scheduled_at
  → 投稿 SFN の scheduled_at
  → 投稿 ECS の SCHEDULED_AT
  → WHERE gr.set_id = %s AND gr.scheduled_at = %s

SQL はこの完全一致条件に EXISTS (SELECT 1 FROM generated_media gm WHERE gm.generation_run_id = gr.id) と既存の有効アカウント・非終端条件を組み合わせる。最古順の選定は廃止する。一意キーは実 DDL に存在するため、新規カラム・DDL・生成アプリからの run ID 返却は不要な見込み。

失敗と再実行を区別する

  • 生成が失敗：現行の親 SFN は生成成功時だけ投稿 SFN を起動する。朝の生成が失敗すれば朝は欠番。夜の親は夜の予定時刻だけを渡す。
  • 当回の run がない・素材がない：過去を探さず、指定したセット・予定時刻と理由を記録して異常終了する案を推奨する。生成成功後に呼ばれる契約では不整合であり、単なる「投稿済み」と同じ 0 件成功にまとめない。
  • 当回が投稿済み・終端状態：既存の二重投稿防止を維持し、再投稿しない。終端状態による処理 0 件と、run / 素材欠落の理由を区別する。
  • 当回の pending / container_created：同じ予定時刻での Retry は同じ run の復旧処理につなぐ。success / failed / published_unconfirmed の扱いとストーリーズの現行方針は変更しない。
  • 過去分が滞留：自動で選ばない。削除・架空の failed 登録・在庫の last_used_at 巻き戻しは行わず、必要な補正は既存の人間ゲートで扱う。
  • 手動起動：対象 run の実際の予定時刻を明示する。現在時刻を便宜的に入れず、公開済み・未確認状態と時間帯を確認する。欠けた入力で旧選定へ戻す互換モードは設けない。

run / 素材欠落と終端状態を分けるため、単一の actionable 検索の None だけで結論を出さず、「指定 run の取得 → 素材・投稿状態の判定」を分けるか、結果型で理由を返す設計にする。実装の形はステップ A で確定する。

保証することと、別途扱うこと

保証の単位は「予定された回」。夜の定時実行が朝の run を拾わず、翌朝も翌朝の run を扱う。素材に焼き込まれた朝夜ラベルと生成側スロット選択が正しいことは前提となる。

一方、朝の古い実行そのものが大幅に遅延して夜に動く場合や、夜に朝の予定時刻を指定して手動再実行する場合は、完全一致だけでは防げない。これは後続が過去分を拾う問題と区別する。通常運用では期限を過ぎた旧実行の再開を避け、古い実行を確認して停止する手順を設ける。実時刻での投稿まで保証する期限ガードは、許容遅延・判定タイミング・手動復旧の例外をステップ A で判断する追加設計項目とする。未設計のまま「どんな遅延でも朝夜は絶対にずれない」とは扱わない。

投稿ゼロ・stale の監視（I-006・I-025）、在庫の自動返却、期限ガード、コンテナリトライは、この当回固定だけで解決したとは扱わない。素材レコードがあっても S3 や付随データの破損までは保証しない。

3. 選択肢と判断

  • セット × 予定時刻で固定（採用方針）既存の一意キーと Scheduler 入力を利用できる。朝夜だけでなく日付も固定し、欠番を翌回へずらさない。
  • 素材の EXISTS だけ追加（旧案）空 run は除外できるが、素材がある未投稿 run の持ち越しは防げない。今回の要件には不足するため、当回固定へ置き換える。
  • generation_run_id を渡す対象は明確だが、現在の ECS 実行結果から業務 ID を返す経路を新設する必要がある。既存の予定時刻で同じ実行を特定できるため採らない。
  • 朝・夜だけで絞る／最新だけ選ぶ前日以前の同じ時間帯や別の回を拾い得る。当回と完全一致する契約にはならない。

5. ステップ展開案

A：設計 → B：実装・機械検証 → C：本番切替（人間）→ D：反映確認の 4 工程を推奨する。すべて開発レーン。I-014 と I-017 の時間帯ずれ防止を先に完了させ、I-022・I-024 は同じフェーズ内の独立した後続ステップへ置く。

各工程は計画体系 5 の 4 項目で示す。今回の着地は承認方針を展開するための下書き完成。計画書への正式転記前なので「展開済み」とは記録しない。

A. 入力契約・選定・切替手順を設計する

  • 完了条件：設計・環境変数・SQL・手動入力例が同じ契約。現役設計書内の「SNS は scheduled_at 不要」「最古 actionable」の旧記述を全件照合し、履歴と現行説明を区別。リンク検査に新規不備なし。B の受け入れケース・切替チェック表が揃う。

C. 定時実行を止めた窓で切り替える（ユーザー操作・ゴール対象外）

  • 完了条件：停止・実行中 0 件・パイプライン・イメージ・親子 ASL・再開前確認の証跡が揃う。親子 ASL とアプリが全て新契約になったことを確認するまで実行を再開しない。
  • 人間ゲート：Scheduler 操作、push 承認、cdk deploy、再開、必要なら切戻し。本番 DDL は不要。本番 SNS をテスト目的で自動投稿しない。
  • 停止点・上限：—（人間作業をゴールにしない）。反映確認は既存の CodePipeline 確認手順を利用し、エージェントが承認なしにデプロイしない。

切替の注意：Scheduler の手動停止がスタックの deploy で戻る可能性を考慮し、定時刻をまたがない窓を確保して、各 deploy 後に有効状態を再確認する。窓を確保できない場合は停止状態を CDK 側にも保持する変更を A で追加設計する。既存実行は更新前の入力を持つので、単なる定義更新をもって新契約へ移ったとは扱わない。

切戻し：停止状態を保ち、旧イメージと両 ASL を対応する組合せに戻してから再開を判断する。旧選定へ戻すと滞留を再び拾うため、既存 backlog の確認なしに再開しない。片側デプロイ失敗時も自動で旧方式へフォールバックしない。

D. 反映を確認し、記録と確認待ちを整理する（C 完了後）
  • 内容：実環境の親子 ASL、task definition、Scheduler 設定、投稿入力契約を読み取り確認し、開発記録へ証跡を残す。I-014 と I-017 の今回対処した範囲を課題表へ反映し、可視化の残件は I-006・I-025 との関係を整理して残す。
  • 完了条件：反映コミット・イメージ・ASL とコードが一致し、入力転送経路が追える。課題表と計画記録が一致する。将来の朝夜投稿を待つことは本ステップの完了条件にしない。
  • 人間ゲート：反映証跡の確認。投稿の目視は下記の確認待ちで扱う。
  • 停止点・上限：記録の push まで、目安 15 ターン。新旧混在があれば完了扱いにせず C の人間判断へ戻す。

受け入れケース（B の必須検証）

  1. 朝の空 run を残し、夜の予定時刻を指定 → 夜だけ選ぶ。その夜が成功した後、翌朝の予定時刻で翌朝だけ選ぶ。
  2. 朝に素材あり・posts なし／pending／container_created をそれぞれ残す → 夜は夜だけ選ぶ。朝の run や在庫を勝手に書き換えない。
  3. 指定した当回が欠落または素材なし、過去には正常素材あり → 過去へ戻らず理由付き失敗。
  4. 同じ時刻の別セット、前日の同じ朝スロット、当回より新しい実行 → いずれも選ばない。
  5. 当回が success / failed / published_unconfirmed → 再投稿しない。複数アカウントは当回の未完了分だけ、既存の投稿・ストーリーズ規約を維持。
  6. Retry で予定時刻を維持し、同じ run を再開。途中で新しい run を作っても対象が変わらない。
  7. SCHEDULED_AT 欠落・空・不正形式・存在しない日時 → 投稿 API 呼出し 0 件で失敗。旧選定には戻らない。
  8. 親 Input → 子 Input → ECS の値が一致し、UTC 日付と JST 日付が異なる朝のケースでも DB の予定時刻と一致する。
  9. 既存の選定後不整合の失敗検知、リール・ストーリーズ・1 日 1 回セットの正常系を維持。
