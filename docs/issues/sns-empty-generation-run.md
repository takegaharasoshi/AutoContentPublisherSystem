### 2026-09-21

- 事象と現行コードを照合し、素材取得後の処理変更ではキャプション段階の失敗を防げないことを確認した。
- 対応の中心は選定 SQL の EXISTS 条件とする。データモデル側の掲載 SQL も同期対象に加える。
- 着地は展開の提案・下書き作成まで。3 課題の同一フェーズ管理を維持し、I-014 を先行できるステップに分ける案を提示した。正式転記前に展開済みとは記録しない。
- 積み残しはユーザーの提案確認と開発レーンでの計画転記・実装。既承認の猶予を今回さらに延長する判断はしていない。
- 開発計画の issue 壁打ち初回試行項目も照合した。結果欄の更新は開発レーンで行う。

### 2026-09-21（当回固定の承認・変更範囲と展開案）

- ユーザーは「当回の生成実行に限定し、当回が失敗しても過去分へ戻らない」方針を承認した。素材存在チェックのみの旧案を、セット × scheduled_at の完全一致へ置き換えた。
- 親 ASL が子へ予定時刻を渡していないこと、生成側と DB が既に一意キーを持つことを確認。生成アプリ・DDL の変更を前提にしない構成を提案した。
- I-017 の時間帯ずれ防止を同梱し、同じ HTML に変更ファイル、4 工程、受け入れ条件、停止窓と切戻し、確認待ちの案を集約した。
- 当回固定と、古い実行自体の遅延を区別した。期限ガードの要否・閾値は設計工程の判断点として明示し、絶対的な時刻保証とは表現しない。
- 着地は展開の下書き完成。計画書への正式転記と実装は開発レーンへ引き継ぐ。I-014 の既承認の猶予は延長せず、次の開発計画起票時に本案を扱う。
