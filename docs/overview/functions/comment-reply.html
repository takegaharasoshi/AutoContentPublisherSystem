コメント自動返信（配信面の機能 ③）

現行版 最終更新: 2026-10-18（Phase 30-3b で新設） 1 段上: 基本設計（全体）3 章 配信面の 4 系統

要約

コメント自動返信は、umigame-soup-1（ウミガメのスープ）の投稿に視聴者が書いた回答コメントを判定し、探偵カメロックとして自動で返信する機能である。ほかの配信面の機能と違い、時刻ではなく Instagram からの通知（Webhook）をきっかけに、コメント 1 件ごとに数十秒以内で動く。判定と返信文づくりには LLM を使い、正解は投稿時に S3 へ置いた問題スナップショットから読む。

図 1 は、コメントが届いてから返信と記録が終わるまでの部品のつながりを表す。上が受け付け（署名の検証とキューへの投入）、下が返信（判定・返信・記録）。

項目要点
目的参加型の問題で、視聴者の質問や回答に判定（はい / いいえ など）をすぐ返し、やり取りを続けてもらう
きっかけInstagram の Webhook（コメントの通知）
入力コメント本文・投稿の media_id、問題スナップショット（真相・判定の基準・核心語）
出力Instagram への返信、S3 のコメント記録（Aurora には書かない → 理由 D-01）
主な判断受け付けと返信をキューで分ける → 理由 D-02 / 本番面とステージング面を同じ定義で持つ → 理由 D-03

1. きっかけ

この機能は Instagram からの通知だけで動く。Meta の Webhook の設定で、umigame-soup-1 のアカウントのコメントを受け付け用 Lambda の関数 URL に送らせている。受け付けは、Webhook の登録確認（GET）には確認用の文字列を返し、通知（POST）は署名（X-Hub-Signature-256）を検証し、自分の返信を除いたコメントの通知だけをキューに入れて、すぐ応答を返す。

2. 入力と出力

次の表は、返信 1 件ごとに何を読み、何を書くか。

区分もの置き場所
読むコメントの通知（コメント ID・本文・media_id）SQS FIFO acps-prod-comment-reply.fifo（media_id ごとに順番どおり。Webhook が同じコメントを重ねて送ってきたときは、キューに入れる時点で重複として除く）
読む問題スナップショット（真相・判定の基準・核心語など）S3 assets/umigame-soup-1/problems/{media_id}.json（投稿が書く）
読むInstagram のトークン・アプリの秘密鍵・LLM の API キーSecrets Manager acps/prod/umigame-soup-1/comment-reply
書く返信Instagram（Instagram ログイン方式の Graph API）
書くコメント記録（判定の結果と理由を含む JSON。返信できなかったときも書く）S3 comment-log/umigame-soup-1/dt={UTC 日付}/{comment_id}.json

3. 流れ

この章は、要約の図 1 の「返信」の Lambda の中で起きることを詳しくしたもの。図 2 は、キューから 1 件を受け取ってから記録を書くまでを時間の順に表す。

返信の Lambda は同時に 2 件までしか動かない。処理に失敗したメッセージはキューに戻って再試行され、決まった回数失敗すると DLQ（acps-prod-comment-reply-dlq.fifo）へ移り、アラームが鳴る。

5. ほかの機能との受け渡し

コメント自動返信は、投稿から正解を受け取り、インサイト収集へ記録を渡す。トークンはトークン更新が保つ。

判断の記録

本文の「→ 理由 D-xx」から飛んでくる先。

D-01 Aurora には書かず、記録を S3 に置く

決めたこと
返信の Lambda は DB に接続せず、問題は S3 のスナップショットから読み、記録は S3 に置く。DB への取り込みはインサイト収集が行う
理由
Aurora が自動停止していても、起こさずに数十秒で返信できるようにするため
日付・出典
2026-10（Phase 21）。database/V016__umigame_comment_logs.sql

D-02 受け付けと返信を FIFO キューで分ける

決めたこと
受け付けの Lambda は検証とキューへの投入だけを 10 秒以内で行い、判定と返信は別の Lambda がキューから 1 件ずつ処理する
理由
Webhook にすぐ応答して再送を避けつつ、LLM の呼び出しに時間がかかっても取りこぼさないため。同じ投稿のコメントは順番どおりに処理し、Webhook の再送による二重の投入をコメント ID で抑える（返信に失敗したメッセージの再試行は別で、キューの再配信で行う）
日付・出典
Phase 21-3（設計）・21-6（実装）。アーキテクチャ 3.4

D-03 本番面とステージング面を同じ定義で持つ

決めたこと
同じ CDK のクラスから、名前の末尾だけ違う本番面とステージング面を作る
理由
判定や返信の変更を、本番の投稿に触れずにテスト用アカウントで試せるようにするため（PoC の後継。フルのステージング環境は作らない）
