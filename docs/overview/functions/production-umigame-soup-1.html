umigame-soup-1 の生産（ウミガメのスープ）

現行版 最終更新: 2026-10-18（Phase 30-3c で新設。30-6a で「さらに詳しく」を生産の詳細設計へ向け、30-6b で 3 章 レビューのやり方を追加） 1 段上: 生産ライン（共通）。ここには共通との違いだけを書く

要約

umigame-soup-1 は、探偵カメロックが出すウミガメのスープ（不思議な状況から真相を推理する問題）のリールを週 4 回投稿し、視聴者のコメントにコメント自動返信が答える参加型のセットである。生産では、問題をオリジナルで作問し、動画の素材に加えて、コメントを判定するための材料（判定の基準・核心語）まで作る。そのため、ほかのセットにはない「判定の試行（プローブ）」の工程と関所がある。

図 1 はこのセットの工程の名前と関所の並びを表す。工程の細部（ゴールの区切り・候補の数など）は補充スキルの SKILL.md が正。共通との違いは、判定の試行が入ることと、動画のビルドを DB への投入より前に行い、投入と配置を最後にまとめて行うこと。

項目このセットでは
作るものウミガメのスープの問題 1 問 1 本のリール。物語復元型と意味誤誘導型の 2 つの型を同数ずつ作る

音Irodori-TTS（ローカル）のナレーションと BGM

1. 何を作り、素材をどう集めるか

このセットの問題はすべてオリジナルで、作問スキルが決まった工程で作る。既存の問題と似すぎていないかも作問の中で確かめる。

2. 共通との違い

生産ライン（共通）1 章の骨組みと比べたときの、このセットの違い。

  • 判定の試行（プローブ）: 動画を作る前に、問題ごとに試行用のコメントと期待する判定を用意し（人がレビュー）、本番と同じ判定に通して結果を人が確かめる。食い違いは素材の穴かラベルの誤りかを切り分けて直し、GO が出た問題だけを動画へ進める → 理由 D-01
  • ビルドが投入より前: 動画のビルドは stock_items.py を読むので DB への投入を待たない。投入（ローカル DB と Aurora）と配置（S3）は最後の G5 で一括して行う
  • 作問を別のスキルに分ける: 作問は umigame-problem-writer が受け持ち、G1a で候補（コア宣言）までをまとめて、G1b で OK になった案を 1 問ずつ素材にする
  • 背景とナレーション: 背景画像を生成して全数を目視で確かめ、Irodori-TTS でナレーションを付けてビルドする
さらに詳しく

3.1 ① 候補の選別（チャット）

素材を書く前に、問題の芯だけを見て反射的に選ぶ関所。ここでの OK は「素材にしてよい」の意味で、投入の承認ではない。

AI が出すもの: 型（物語復元 = s・意味誤誘導 = m）ごとに、1 案を 3 行（コア宣言 / 問題文の案 / 何を言われたら「正解です！」か）で並べた一覧を 1 通で出す。既存の問題・台帳・Web との照合は AI が済ませてあり、引いた語や連想、物語の下書きは候補ファイルに残すだけで一覧には載せない。

例:

【物語復元型・候補選別 4 件】各候補に OK / NG / 保留 を返してください(理由は不要)
s01 コア: …(型の様式どおりの 1 文)
    問題文の案: …
    正解判定: 「…」と言われたら正解
s02 …

ユーザーの返し方: 候補 ID を OK / NG / 保留に振り分けて 1 行で返す（例: OK: s01 s03 m02 m04 / NG: s02 m01 / 保留: s04 m03）。理由は書かなくてよく、書かなかった理由を AI が推測で埋めることはない。迷ったら保留でよい。

返した後: AI が判定を候補ファイルに記録し、集計（tally.py）の出力を貼る。型ごとに「不足 = 目標 − OK」を出し、どちらかの型が足りなければ不足の 2 倍の候補を追加して同じ形で選び直す。両方の型で足りたら G1b へ進む。NG・保留は消さずに残す。

3.2 ② 素材のまとめレビュー（素材シート + チャット）

選んだ候補を素材 18 項目まで仕上げたものを、まとめて確かめる関所。矛盾とネタバレを止める。

AI が出すもの:

  • 素材シート: 入口は素材シートのインデックス content/umigame-stock/umigame-soup-1/work/review.htmlで、バッチを選ぶとそのバッチの <バッチ>/work/review.html（review_sheet.py が作る）が開く。目次の下に問題ごとに、コア宣言（問題文の直前）・版面に出る文言・ナレーション（読み上げ用の文）・キャプション・背景イラストのプロンプト・出典とオリジナル性のメモ・真相と確定事実（ネタバレ）が並ぶ。ブラウザーで開く（スマホなら /docs-mobile-view の要領で HTTP 配信したものでもよい）
  • チャットに自己検査と一次スクリーニングの結果: 問題ごとの自己検査 10 行と、先に見た 4 点（問題文と真相の語・時制が合っているか / title が真相の手がかりになっていないか / truth が公開して自然な文か〔次回のキャプションで全文を公開する〕/ 既存の問題とモチーフ・仕掛けが近すぎないか〔近ければ投稿の順を離す申し送り〕）

ユーザーの返し方: シートを見て、問題番号ごとに直してほしい点をチャットに書く。問題がなければ「全件 OK」。問題そのものをやめるなら「U.. は NG」。

例:

U31 真相の 2 段落目が問題文の「夕方」と合わない
U33 title が答えに近すぎる
ほかは OK

返した後: AI が stock_items.py（全問共通なら common/umigame_common.py）に反映し、validate.py → review_sheet.py を回してシートを作り直して出し直す。指摘のうち作り方の穴は作問スキルへ反映する。NG の問題は候補へ差し戻し（final_ng）、余っている OK を先に使う。

3.3 ③ コメントのレビュー（判定の試行のページ + チャット）

機械プローブに流すコメントと、期待する判定（正解ラベル）が妥当かを確かめる関所。ラベルが誤っていると、プローブの結果が意味を持たない。

AI が出すもの: バッチの判定の試行のページ docs/app/sets/umigame-soup-1-probe-<バッチ名>.html の末尾の「コメントレビュー」の節に、問題ごとのコメント（質問・回答の試み）と正解ラベル（期待する判定の種類）を載せる。入口は判定の試行の一覧。コメントは、確定事実シートの「はい / いいえ」の境目・正解と惜しいの境目・否定形や限定つきの質問・ネタバレを誘う質問・関係ない質問を混ぜて作る。

ユーザーの返し方: 問題ごとに、コメントの追加・削除・ラベルの修正をチャットで指示する。問題がなければ「OK」。

例:

U31 「夜だった？」のラベルは いいえ ではなく 関係ない
U33 「犯人は家族？」を足して（期待: 惜しい）
ほかは OK

返した後: AI がページとコメントを直し、承認されたものを評価データ content/umigame-stock/umigame-soup-1/judge-trial/data/eval_problems.json に入れる（G3 の最初でもよい）。

3.4 ④ 結果の確認と GO（判定の試行のページ + チャット）

本番と同じ判定・返信文の経路に通した結果を見て、動画にしてよいかを決める関所。

AI が出すもの: probe_run.py の結果から作ったバッチのサマリーページと問題別のページ（一覧に 1 行足す）と、チャットに不一致の一次分析（確定事実シートの穴 → 素材を直す / 正解ラベルの誤り → ラベルを直す / 判定の揺れ → 実行し直して確かめる）。

ユーザーの返し方: 問題ごとに GO か「素材に戻す」を返す。気になる問題は、自分で local_trial.py --problem <no> --comment … を使って自由にコメントを試してから決めてよい（人間プローブ）。

例:

GO: U31 U32 U34 / 素材に戻す: U33（「家族」の扱いが確定事実シートに無い）

返した後: 素材に戻した問題は ② の検証からやり直し、必要なら ③・④ に戻る。GO が出た問題だけを G4（動画ビルド）へ進める。

3.5 ⑤ 動画の全数レビュー（レビューシート + チャット）

ビルドした動画を全部見て、本番へ上げるものを決める関所。

AI が出すもの: レビューシート（review_sheet.py が作る）。入口はインデックス content/video-build/umigame-soup-1/work/review.htmlで、過去のビルド分も含めたバッチの一覧（件数・最終ビルド日時・今回の印）から、バッチごとのシート work/review/<バッチ名>.html を開く。シートは問題ごとに動画・静止フレーム・ffprobe の結果・キャプションが並ぶ。背景は先に background_sheet.py で AI が全数を見て（文字の混入・構図）、気づいた点をチャットに添える。

見るところ: 導入シーンと本編の版面（文字の欠け・はみ出し）・背景（文字の混入・真相の手がかりを描いていないか）・ナレーション（読み間違い・切れ・BGM とのバランス）・キャプション。

ユーザーの返し方: content_key ごとに直してほしい点をチャットに書く。問題がなければ「全件 OK」。

例:

031-xxx 「真相」の読みが「しんそう」になっていない
033-xxx 背景の窓に文字のような模様がある
ほかは OK

返した後: AI がナレーションを取り直し（build.py --retake-tts。1 問 3 回まで）、背景を作り直すか素材を直してビルドし直し、review_sheet.py でシートを作り直して出し直す。全件 OK になったら、AI が承認した content_key を work/approved.txt に足し、G5（本番へ一括アップロード）のゴールを出す。

判断の記録

D-01 動画を作る前に判定の試行を通す

決めたこと
問題ごとに試行用のコメントで本番と同じ判定を走らせ、人が GO を出した問題だけを動画にする
理由
投稿後のコメントには自動で返信するため、素材（真相・判定の基準・核心語）に穴があると誤った返信が出る。動画にする前に見つければ、素材の手直しだけで済む
