生産ライン（共通）

現行版 最終更新: 2026-10-18（Phase 30-3c で新設） 1 段上: 基本設計（全体）2 章 生産面

要約

生産ラインは、投稿する動画をあらかじめ作って在庫に積む機能である。人が Claude Code や Codex のスキル（作業の手順書）を起動し、AI と一緒に、素材の企画 → 執筆 → 検証 → 動画のビルド → 配置までを進める。途中には人が中身を確かめて止める関所があり、OK になったものだけが先へ進む。最後に、全数を人が見た動画だけが S3 と在庫テーブルに置かれ、配信面の投稿がそこから選ぶ。

このページは 3 セットに共通する骨組みを書く。セットごとの違い（何を作るか・素材の集め方・工程の差）は、セット別の 3 ページ（logic-training-1 / pref-ranking-1 / umigame-soup-1）に書く。図 1 は共通の骨組みで、四角が AI と人が一緒に進める工程、ひし形が人だけが判断する関所。

項目要点
目的配信面の在庫が尽きないよう、レビュー済みの動画を週単位で補充する
きっかけ人がスキルを起動する（週次補充。在庫の水位が目安を下回ったら）
入力ネタ（Web・官公庁統計・ランダムな語など。セットによる）、既存の在庫と過去の問題
出力S3 のビルド済み動画、在庫テーブルの行（ローカル DB と Aurora の両方）、作業の記録
主な判断投稿前に全数を人が見る → 理由 D-01 / 工程の細部はスキルの手順書を正にする → 理由 D-02

2. 人の関所

関所は、人（ユーザー）が中身を見て先へ進めるかを決める場所で、AI は決めない。AI は関所の前で一次スクリーニングを済ませ、人が判断しやすい形（一覧・レビューページ）にして出す。次の表は関所の種類と、どのセットにあるか。関所の数はセットにより 2〜5 か所。

関所見るもの判断logic-training-1pref-ranking-1umigame-soup-1
候補の選別1 候補 3 行の一覧OK / NG / 保留（理由は任意）ありなしあり
素材のレビュー完成稿・素材シート承認 / 差し戻しあり（1 問ずつ）あり（全件を一覧で）あり（まとめて）
試行用コメントのレビュー判定の試行に使うコメントと期待する判定（プローブページ）追加・削除・期待の修正なしなしあり
判定の試行の確認本番と同じ判定に通した結果（必要なら人が自分でコメントを試す）GO / 素材に戻すなしなしあり
動画の全数レビュー動画のレビューシート（入口はインデックス work/review.html。過去分もバッチごとに見られる）承認した分を approved.txt に書くありありあり

DB や S3 を書き換える工程（投入・配置）は auto mode で走らせず、許可のプロンプトを最後の関所として使う。

3. 受け渡しの契約

生産ラインの出口は配信面への受け渡しで、置き場所と書き方が決まっている。全体の契約は基本設計（全体）4 章にあり、ここでは生産ラインの側から見た「どう入れるか」を書く。

受け渡すもの置き場所入れ方
素材の行在庫テーブル quiz_stock_items / ranking_stock_items / umigame_stock_itemsgenerate.py が作る INSERT の SQL を、ローカル DB と Aurora（RDS Data API）の両方に流す。両環境の中身が一致することを確かめる
ビルド済み動画S3 assets/{set_code}/prebuilt/publish.py が承認した分だけを上げ、在庫の行の動画キーを埋める（Aurora 側の更新は SQL を作って適用する）

行どうしの照合には、環境で変わる ID ではなく content_key を使う。動画キーが入っていない行は、配信面に選ばれない。

5. レビューの仕方

3 セットに共通するレビューの進め方。どの関所でも同じ考え方を使う。関所ごとの具体的なやり方（AI が何を出し、ユーザーがどう返すか）は、セット別ページの 3 章（logic-training-1・pref-ranking-1）にある。

  • AI が先に一次スクリーニングし、人が判断する: AI は機械検証と目視の一次確認を済ませ、気になる点を添えて出す。採否は人が決める
  • 動画は全数を見る: 抜き取りにしない。承認したものだけを approved.txt に書き、配置はそのファイルに載った分だけ行う
  • 候補の選別は反射的に: 候補の段階は OK / NG / 保留だけを返し、理由は任意（AI は推測で理由を埋めない）→ 理由 D-03
  • 指摘は手順書へ書き戻す: レビューで出た共通の指摘は、合意したものだけスキルの作問基準や執筆の勘所に反映する（logic-training-1 は quiz-review-learn、pref-ranking-1 は WRITING-NOTES.md）
さらに詳しく
  • logic-training-1 の生産 → 機能別の基本設計 logic-training-1
  • pref-ranking-1 の生産 → 機能別の基本設計 pref-ranking-1
  • umigame-soup-1 の生産 → 機能別の基本設計 umigame-soup-1

判断の記録

本文の「→ 理由 D-xx」から飛んでくる先。

D-01 投稿前に全数を人が見る

決めたこと
動画は生産ラインで事前に作り、人が全数をレビューして承認したものだけを配置する
理由
実行時に生成すると人が見ないまま投稿される。画像生成の品質確認で文字や数字の崩れが出たため、投稿前に全数を直せる形にした
日付・出典
2026-08-08（Phase 16-3b）。基本設計（全体）D-01

D-02 工程の細部はスキルの手順書（SKILL.md）を正にする

決めたこと
設計書には全体像・関所・受け渡しの契約・スキルの一覧だけを書き、工程ごとの手順・コマンド・ゴールの切り方は SKILL.md に書く
理由
手順は補充のたびに改善され、設計書と二重に書くとすぐにずれるため
日付・出典
2026-10-17（I-040 の壁打ち・Phase 30 の方針 ⑤）

D-03 候補の選別では理由を求めない

決めたこと
候補を目標の 2 倍出し、人は OK / NG / 保留だけを返す。理由の整理は後日の振り返りへ分ける
理由
補充中の判断から理由の言語化を外して速く選べるようにし、振り返りの成果でスキルを育てるため
日付・出典
2026-09-22（logic-training-1 の改修 R-3）。umigame-soup-1 も同じ形を使う
