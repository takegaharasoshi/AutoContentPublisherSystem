基本設計（システムの全体像）

現行版 最終更新: 2026-10-19（30-9b: 課題 I-042 の ①②④ を直した〔1 章にコメント返信のステージング面と D-08、図 5 に記録の保持期限、2 章・6.3 のスキルの表に起動できる場所〕）。前回: 2026-10-18（30-3c で 2 章の「さらに詳しく」を生産の機能別の基本設計へ向けた。30-3b で 3 章の「さらに詳しく」を機能別の基本設計へ向けた。Phase 30-3 で旧「システム概要」を基本設計として作り直し、生産面と配信面の 2 面で描いた） 設計書の 3 段の構成（基本設計 → 層の概要 → 詳細設計）は設計書体系ガイド 2.1

要約

このシステムは、Instagram にショート動画（リール）を毎日決まった時刻に投稿し、その反応を集めて次の企画に生かすための仕組みである。全体は生産面と配信面の 2 つに分かれる。生産面では、人が AI のスキルと手元のツールを使って動画をあらかじめ作り、全部を目で確かめてから置き場所へ置く。配信面では、AWS 上のプログラムが決まった時刻にその置き場所から 1 本を選んで投稿し、反応の数値やコメントを集める。2 つの面をつなぐのは、S3 の動画の置き場所と Aurora の在庫テーブルの 2 つだけである。

下の図 1 はこの全体像を 1 枚で表したもの。上から、生産面で作ってレビューする流れ → 受け渡しの置き場所 → 配信面の 4 つの仕事（投稿・インサイト収集・コメント自動返信・トークン更新）→ Instagram の順に並ぶ。続く表は、このページ全体の要点をまとめたもの。

項目要点
何をするシステムかショート動画（リール）を Instagram に定時投稿し、反応を集める。テーマ単位の「セット」を足し替えて運用する（稼働中は logic-training-1・pref-ranking-1・umigame-soup-1 の 3 セット）。事業の目的・KPI は事業戦略書
生産面スキル（Claude Code / Codex）と content/ のツールで、問題・ランキングなどの素材と動画を事前に作る。人が全数を見てから配置する → 理由 D-01
受け渡しビルド済み動画を S3 の assets/{set_code}/prebuilt/ に、素材の行を Aurora の在庫テーブル（quiz_stock_items / ranking_stock_items / umigame_stock_items）に置く。2 面はこの 2 つだけでつながる → 理由 D-02
配信面4 系統: ①投稿（Scheduler → SFN → ECS） ②インサイト収集（同）③コメント自動返信（Lambda）④トークン更新（Lambda）。動画は投稿時に生成しない（AI を呼ぶのはコメントの判定と返信文だけ）
主な技術Python・AWS CDK（TypeScript）・ECS Fargate RunTask・Step Functions・EventBridge Scheduler・Aurora Serverless v2・S3・Lambda・SQS。ローカルは Docker（Remotion・ffmpeg）とローカル TTS

このページは要約の内容を、1 章（2 面の関係）→ 2 章（生産面）・3 章（配信面）→ 4 章（2 面のつなぎ目）→ 5 章（データの流れ）→ 6 章（構成要素の一覧）の順に詳しくしていく。各章の末尾の「さらに詳しく」から、1 段下の機能別の基本設計（functions/）や詳細設計へ進める（7 章に一覧）。

1. 2 面の全体構成

このシステムは大きく生産面と配信面の 2 面で構成されている。生産面は「投稿する動画を作って在庫に積む」側で、人の手元の PC で、人の判断を挟みながら週単位で進む。配信面は「在庫から取り出して投稿し、反応を集める」側で、AWS 上で人の手を介さずに毎日自動で動く。2 面は動く場所・動かす人・周期がまったく違うため、互いに直接呼び合わず、在庫（S3 の動画と在庫テーブル）を介してだけつながる。

次の表は、2 面を「どこで動くか・誰が動かすか・どの周期か・何を生み出すか」で比べたもの。

面どこで動くか誰が動かすか周期成果物
生産面ローカル PC（WSL2 + Docker）人 + スキル（週次補充・作問）セットごとに週 1 回の補充が目安（在庫水位はセット別設計書）S3 の事前ビルド動画・在庫テーブルの行・BGM
配信面AWS（ap-northeast-1・本番 1 環境。コメント自動返信だけ、同じコードのステージング面 CommentReplyStagingStack を持つ → 理由 D-08）EventBridge Scheduler・Instagram の Webhook毎日の定時（セクション 3）Instagram の投稿・返信、DB の投稿結果・インサイト

2 面は同期しない。配信面は在庫テーブルの「ビルド済み（動画キーあり）・有効」の行から選ぶだけで、生産面の作業中かどうかを知らない。在庫が尽きないよう、生産面が在庫水位を見て補充する。

さらに詳しく
  • 生産面をもう 1 段詳しく（工程・関所・セット別の作り方）→ 2 章 生産面
  • 配信面をもう 1 段詳しく（4 系統の起動・実体・読み書き）→ 3 章 配信面の 4 系統
  • 2 面のつなぎ目（何をどこに置き、誰が書き誰が読むか）→ 4 章 受け渡しの契約

2. 生産面

この章は、1 章の生産面を「どんな工程を、どこで人が止めながら進むか」の単位まで詳しくしたもの。生産面は、Claude Code や Codex のスキル（作業手順書）に沿って、素材の企画から動画の配置までを進める。途中に人が中身を確かめて止める「関所」を置き（数と中身はセットにより 2〜5 か所）、OK になったものだけが次の工程へ進む。

図 2 は工程の流れの代表（logic-training-1 の形）を表す。四角が工程、ひし形が関所（人の判断）で、上から順に、候補づくり → 選別 → 完成稿 → 検証 → レビュー → 画像と動画のビルド → 全数レビュー → 配置と進む。セットにより、候補の選別がない（pref-ranking-1）・判定の試行が入り投入が最後になる（umigame-soup-1）などの違いがある。

工程の骨組みは共通だが、何を作るか（なぞなぞ・ランキング・ウミガメのスープ）・素材の集め方・ナレーションの有無はセットごとに違う。次の表は、セットごとの違いと、それぞれの手順書・ソース・ビルドツールの置き場所を示す。

セット補充スキル起動できる場所素材のソース動画ビルドナレーション
logic-training-1（なぞなぞ・とんち）quiz-stock-replenish（振り返りは quiz-review-learn）補充は Claude Code・Codex の両方。振り返りは Claude Code だけcontent/quiz-stock/logic-training-1/<バッチ>/stock_items.pycontent/video-build/logic-training-1/なし（BGM・効果音のみ）

3. 配信面の 4 系統

この章は、1 章の配信面を「AWS のどのサービスが、いつ、何をするか」の単位まで詳しくしたもの。配信面の仕事は 4 つの系統に分かれ、それぞれが別々のきっかけで動く。①投稿と②インサイト収集は時刻（EventBridge Scheduler）で動くバッチ、③コメント自動返信は Instagram からの通知（Webhook）で動く Lambda、④トークン更新は週 1 回の時刻で動く Lambda である。

図 3 は 4 系統を AWS の構成として描いたもの。枠 1 つが 1 系統で、矢印は起動の順番を表す。下に並ぶ Aurora・S3・Secrets Manager は、各系統が読み書きする共通の置き場所。

次の表は、4 系統それぞれについて「いつ起動するか・AWS 上の実体は何か・何をするか・どこを読み書きするか」をまとめたもの。系統の名前から、その機能別の基本設計へ進める。

② インサイト収集Scheduler: 3 セットとも毎日 06:00・18:00SFN acps-prod-insights-collection-sfn → ECS insights-batch直近 14 日の投稿のインサイトとアカウント日次インサイトを集め、コメント記録 JSON を DB に取り込む書く: post_insights・account_insights_daily・umigame_comment_logs。読む: S3 comment-log/

4. 2 面の受け渡しの契約

この章は、2 章の最後（配置）と 3 章の最初（素材の選定）をつなぐ部分を詳しくしたもの。2 面は互いを直接呼ばないため、「どこに・どんな形で置くか」という約束（契約）さえ守れば、片方を変えてももう片方に影響しない。ここではその約束の中身を示す。

次の表は、受け渡すもの 1 つごとに「置き場所」「書く側（生産面のツール）」「読む側（配信面のプログラム）」を並べたもの。生産面が書き、配信面が読む。配信面は在庫テーブルの選んだ行の last_used_at・use_count だけを更新し、素材の中身は書き換えない。

受け渡すもの置き場所書く（生産面）読む（配信面）
ビルド済み動画S3 assets/logic-training-1/prebuilt/{content_key}.mp4
assets/pref-ranking-1/prebuilt/{content_key}_{20s|30s}.mp4
assets/umigame-soup-1/prebuilt/{content_key}.mp4（ライフサイクルの失効対象外）		publish.py（aws s3 cp）image-batch が取得して当回の videos/{set_code}/{YYYYMMDD}/{run_id}/… へ写す（30 日で失効）
素材の行Aurora quiz_stock_items / ranking_stock_items / umigame_stock_itemsgenerate.py の INSERT SQL・publish.py の UPDATE SQL を apply_aurora.py（RDS Data API）で適用image-batch が「有効かつ動画キーあり」の行から、未使用 → 最も古く使ったものの順で 1 件選ぶ
動画キーの紐づけ在庫テーブルの video_s3_key（ranking は video_s3_key_20s / _30s）・video_audio_asset_idpublish.py（照合キーは環境に依存しない content_key）image-batch（キーが NULL の行は選ばない）
BGMS3 audio/{set_code}/…・Aurora audio_assetsセット登録・補充時の SQL動画に焼き込み済み。行は投稿の記録に紐づける

列の定義・選び方の詳細は下の「さらに詳しく」のとおり（データモデル設計と各方式設計書。quiz-prebuilt / ranking-prebuilt / umigame-prebuilt）。

さらに詳しく
  • 在庫テーブルの列の定義 → データモデル設計
  • 在庫から 1 件を選ぶ規則 → 方式設計書の 4 節（quiz-prebuilt / ranking-prebuilt / umigame-prebuilt）
  • 動画の取得と当回の登録 → 方式設計書の 5 節（quiz-prebuilt / ranking-prebuilt / umigame-prebuilt）
  • 生成方式そのものの契約 → バッチ処理フロー 2.1（方式の契約）

5. データの流れ

この章は、3 章の 4 系統が、どのデータを受け取ってどこへ書き残すかを、データの側から追い直したもの。3 章が「誰が動くか」の視点なのに対し、ここでは「1 本の動画の情報が、在庫から投稿・反応の記録へとどう移っていくか」の視点で見る。

図 4 は、在庫テーブルから始まり、投稿の記録 → Instagram → 反応の数値 → KPI の集計へと進む主な流れを表す。「umigame のみ」から分かれる枝は、umigame-soup-1 だけにあるコメントの返信と記録の流れ。

図 5 は、図 4 の umigame の枝（コメント）を時間の順に並べ直したもの。投稿したときに問題の答えを S3 に置いておき、コメントが来たらそれを読んで判定・返信し、記録を残し、後でインサイト収集が DB に取り込む、という順番になる。

さらに詳しく
  • すべてのテーブルと ER 図 → データモデル設計
  • 投稿の状態（成功・失敗・確認待ち）の移り方 → バッチ処理フロー（投稿の状態）
  • 問題スナップショットの中身 → バッチ処理フロー（問題スナップショット）
  • KPI の集計と月次の転記 → 機能別の基本設計 インサイト収集（そこから運用設計 6 章へ）

6. 構成要素の一覧

この章は、ここまでの図に出てきた部品を、リポジトリの置き場所ごとに一覧にしたもの。配信面のプログラム（services/）→ それを AWS に載せる定義（infra/）→ 生産面の手順書（スキル）→ 生産面の素材とツール（content/）の順に並べる。どの部品がどの章の何にあたるかを引くための索引として使う。

6.1 配信面のプログラム（services/）

3 章の 4 系統を実際に動かすプログラムの一覧。ECS で動くバッチが 4 つ、Lambda が 1 つ（中に 3 つの関数）と、バッチ共通のライブラリがある。

サービス実行形態役割
db-readiness-checkECS Fargate（3 SFN の先頭）Aurora の起動を待ち、接続を確かめる
image-batchECS Fargate（image-generation-sfn）セットの生成方式で当回の動画を用意し登録する。稼働 3 セットは事前ビルド方式（quiz-prebuilt / ranking-prebuilt / umigame-prebuilt）。実行時生成の方式（gpt-*）は登録だけ残り、使うセットはない
sns-post-batchECS Fargate（sns-posting-sfn）当回の生成結果を Instagram へ投稿し結果を記録する。umigame は問題スナップショットを書く
insights-batchECS Fargate（insights-collection-sfn）投稿・アカウントのインサイト収集とコメント記録の取り込み
comment-replyLambda 3 本（webhook / reply / token-refresh）umigame のコメント自動返信と返信用トークンの更新
shared/acps_sharedライブラリECS バッチ共通（DB 接続・Secrets・S3・Instagram API・SNS Secret の名前規約）

  • パイプラインの動き → CI/CD 設計

判断の記録

本文の「→ 理由 D-xx」から飛んでくる先。本文には事実だけを書き、「なぜそうしたか」はここにまとめている。1 件ごとに、決めたこと・理由・いつどこで決めたかを書く。

D-01 動画は事前にビルドし、人が全数を見てから置く

決めたこと
稼働セットの動画は生産面で事前に作り、人が全数レビューしてから S3 と在庫テーブルへ置く。配信面は投稿時に動画・画像を生成しない（実行時生成の方式は登録だけ残す）。配信面で AI を呼ぶのはコメント返信の判定と返信文だけ
理由
実行時に生成すると、人が見ないまま投稿される。画像生成 API の品質確認で、看板の文字やパネルの数字など崩れが出た（2026-08-07）。事前に作れば投稿前に全数を直せる
日付・出典
2026-08-08（logic-training-1 の quiz-prebuilt 転換・Phase 16-3b）。以後 pref-ranking-1・umigame-soup-1 も事前ビルド方式で開始。方式カタログ

D-02 2 面は S3 のキーと在庫テーブルだけでつなぐ

決めたこと
生産面から配信面へ渡すのは、S3 assets/{set_code}/prebuilt/ の動画と在庫テーブルの行だけにする。照合は環境に依存しない content_key で行う
理由
配信面のバッチを変えずに、セットごとの素材と版面を生産面だけで作り直せる。ローカル DB と Aurora で行の ID が違っても同じ素材を指せる
日付・出典
Phase 16-3b〜17・21 の事前ビルド方式の設計（quiz-prebuilt ほか）

D-03 投稿は「選定 → 投稿」の 2 つの SFN を続けて動かす

決めたこと
投稿は生成（選定）の SFN が成功した後に、投稿の SFN を起動する。投稿の SFN は自分のスケジュールを持たず、手動で単独実行もできる
理由
生成と投稿を別のタスク・別の失敗単位にして、投稿だけをやり直せるようにする。1 回の起動で当回の分だけを投稿する（Phase 26 で当回固定）
日付・出典
当初設計（Phase D〜10）・Phase 26。ワークフロー

D-04 コメント返信は Aurora に書かず、記録を S3 に置く

決めたこと
返信の Lambda は S3 の comment-log/ にコメント記録を置くだけにし、DB への取り込みはインサイト収集（06:00 / 18:00）に相乗りする
理由
返信の経路を Aurora が停止中でも動かすため。取り込みを相乗りにして Aurora の起動回数を増やさない
日付・出典
2026-10（Phase 21-7b）。database/V016__umigame_comment_logs.sql の冒頭

D-05 返信用トークンだけ自動で更新する

決めたこと
コメント返信用の Instagram 長期トークンは Lambda で毎週更新する。投稿用トークンは手動更新とリマインドのまま
理由
返信用は 60 日の失効が実際に起きる方式で、失効すると返信が全件止まる
日付・出典
2026-10-11（Phase 21-6g）・課題 I-031。アプリ運用設計 5.4

D-06 Aurora は自動で一時停止させ、SFN の先頭で起動を待つ

決めたこと
Aurora Serverless v2 の自動一時停止（最小 0 ACU）を使い、どの SFN も先頭で DB 準備確認を走らせる
理由
バッチは 1 日数回しか動かないため、止めている時間のコストを払わない。バッチ側は DB が使える前提で書ける
日付・出典
当初設計（技術選定）。ワークフロー 2 節

D-07 技術の選定

決めたこと
言語 Python・インフラ定義 AWS CDK（TypeScript）・実行は ECS Fargate RunTask（ECS Service は使わない）・ワークフロー Step Functions Standard・スケジューラ EventBridge Scheduler・DB Aurora Serverless v2（MySQL 互換）・CI/CD CodePipeline + CodeBuild。モノリポジトリで、サービスごとにコンテナイメージ・CDK スタック・パイプラインを分ける
理由
Python は API 連携と AI ライブラリが揃う。Fargate はサーバー管理が要らずタスク単位の課金。Step Functions は Retry / Catch と可視化。Scheduler は cron 式とタイムゾーン指定。CDK は型のある IaC。CodePipeline は ECR との連携が容易
日付・出典
当初設計（Phase D）。旧「システム概要」の技術選定表を移した

D-08 ステージング面はコメント自動返信の経路だけに持つ

決めたこと
配信面は本番 1 環境とし、フルのステージング環境（Aurora・ECS・SFN・パイプラインの 2 面化）は作らない。例外としてコメント自動返信は、同じコードからステージング面（CommentReplyStagingStack。テスト用の Meta アプリ・テスト用アカウントにつながる）を立てて恒久的に使う
理由
日次バッチは影響半径が小さく、フルの 2 面はソロ運用の維持コストと月の予算に見合わず、Instagram との境界は複製では再現できない。コメント返信の経路は PoC で作ったテスト用の Meta アプリとテスト用アカウントをそのまま使えて Instagram の境界まで試せ、2 面分の定常費もほぼゼロ（Lambda・SQS は従量）
日付・出典
2026-08-28 課題 I-027（据え置き。導入の条件はトリガー列）・Phase 21-1 ⑦ / 21-6。スタック設計 3.6（理由 D-12）
