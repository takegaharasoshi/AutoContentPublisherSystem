開発計画・進捗管理（開発レーン）

開発レーン 最終更新: 2026-09-03（20-1 の作業を実施〔Scheduler 3 件削除・is_active = 0・設計書 / 計画書 / 事業戦略書の更新〕。人間ゲート待ち: push → cdk deploy → Aurora の UPDATE。同日に 16-12b 完了と人間ゲート〔V011 を Aurora へ適用・本番値の確認 OK〕。開発レーンの次は Phase 20 の効果確認〔確認待ちリスト〕を経て Phase XX〔プラットフォーム展開〕の着手判断）
本書の位置づけ（Phase 18 で 2 レーン化） 本書は開発レーン（フェーズ制の新規開発・基盤改修。services/ shared/ infra/ database/・共通設計書に触れる作業）の計画書。セット別の保守運用・セット内で閉じる改修は各セット計画書（計画体系の目次参照）で管理する。レーンの判定ルール・並行作業ルールの正は index.html。

進め方の方針

  • 設計（インフラ → アプリ）を先に固め、構築はインフラ → アプリ実装の順に進める
    • Phase D: インフラ設計の一時 Fix → Phase A: アプリ設計の大枠 → Phase 9: アプリ設計（詳細・前倒し）→ Phase 0〜8: インフラ構築 → Phase 10〜13: アプリ実装・定常運用開始 → Phase 14〜17: 収益化に向けた機能拡充（上位方針は 事業戦略書）。前倒しの経緯は開発記録の Phase A・9 を参照
  • 各ステップで実際に AWS 上で稼働確認を行い、動作を確認してから次に進む
  • 1 ステップ = 人間ゲート間の 1 ゴール（Phase 19-4〔2026-09-02〕で改訂。旧「1 ステップ = 1 プロンプト + ユーザー確認」）: ステップ境界は人間ゲート（稼働確認・レビュー・go / no-go・設計判断）だけで決め、「Claude が 1 ターンでこなせる量」では区切らない（/goal が完了条件まで自走するため）。切り方の目安は 3 つ — (a) ゲートのない連続作業（実装 → テスト → 設計書 → コミット）は 1 ステップにまとめる / (b) 確認・判断で終わる地点は境界に残し、ユーザー作業のステップはゴールにしない（「ユーザー判断・ゴール対象外」と明記する）/ (c) 20〜30 ターンを超えそうなもの・2 レーンをまたぐものは機械検証できる中間点で割る。ステップの記載様式（内容 / 完了条件 / 人間ゲート / 停止点・上限）の正は計画体系セクション 5。各ゴールの終了後、ユーザーが人間ゲートの確認を行い、チェックを入れる
  • 記録の運用: ステップ完了時、本書にはチェック + 完了日 + 要点（1〜2 行）のみを記録し、詳細な実施記録（検証内容・決定事項の全文）は 開発記録に追記する（計画書の肥大化防止。セット計画書 / セット記録も同じ作法）
  • ステップ実行は /goal をラッパーにする（Phase 19 で導入）: 計画書のステップ着手は /step スキルから行い（起動がレーン宣言と完了条件の宣言を兼ねる。開発レーン・セットレーン共通）、services/ shared/ への push 後は /goal で CodePipeline 完走を確認する。手順の正は CLAUDE.md、検討経緯はアイデア詳細
  • CDK コマンド例では app 内の論理スタック ID（FoundationStack など）を指定する。-c env=prod により、CloudFormation 上の実スタック名は Prod-FoundationStack のように環境名付きで作成される

設計 Fix の運用ルール

設計書が Fix しない問題の再発防止ルール（詳細は docs/index.html セクション 4 を参照）:

  • 設計書は「次フェーズの作業に着手できる」水準で一時 Fix とする。「生成 AI の指摘ゼロ」は Fix 条件にしない
  • 生成 AI レビューは観点を限定して依頼し、最大 2 巡まで
  • 指摘は blocker（誤り・矛盾・欠落）と改善提案に分類し、blocker のみ修正する。改善提案・3 巡目以降の指摘は「設計課題リスト」（本書末尾）に記録する
  • インフラ設計書にアプリ仕様を書かない。アプリの論点は docs/app/index.html の検討メモへ
