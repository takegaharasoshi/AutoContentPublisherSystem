グレーゾーンの判定

3. 並行作業ルール

  • セッション起動時にレーンを宣言する: 「開発レーン: 16-5」「セットレーン: pref-ranking-1 の週次補充」のように、レーンと触るパスを冒頭で確認してから着手する。補充スキル（/quiz-stock-replenish / /ranking-stock-replenish）の起動はセットレーン宣言を兼ねる
  • 計画書のステップ着手は /step <識別子> から（両レーン共通・Phase 19-2 で導入）: 起動がレーン宣言と /goal 完了条件の宣言を兼ねる。手順・テンプレの正は .claude/skills/step/SKILL.md
  • git は trunk（main）直 push を継続し、push 前に git pull --rebase origin main を必ず挟む。書き込みファイルがレーンで分離されているため、競合は原則発生しない
  • 開発レーンは常に 1 本: services/ / shared/ に触れる push は CodePipeline 完走 + タスク定義新リビジョン確認まで見届ける必要があり、並行すると確認が混線するため
  • レーンをまたぐ気づき（セット作業中に見つけた基盤の課題等）は、自分で直さず課題体系の相手レーンの節に課題として起票する（課題レーンは常に並行可のため、見つけた場で書ける。2026-09-19 までは相手レーンの計画書〔設計課題リスト / バックログ〕に記録していた）
  • 本ディレクトリの整理・ルール変更（Phase 18 級の作業）は、他セッションが 1 本も動いていないフリーズ窓で単独実施する

4. 記録の分担

  • plan（毎セッション読む）: ステータス / バックログ / 進行中ステップ。完了したらチェック + 完了日 + 要点 1〜2 行だけ残す
  • log(必要なときだけ読む): 実施の詳細全文。週次補充は「1 回 = 表 1 行(日付・投入件数・在庫水位・特記)」の定型とし、特記事項があるときだけ本文を書く
  • 課題と事象と確認待ちの 3 分（Phase 22-1 で「トラブルの二分」を改訂）: 課題（これから変えるべきこと + トリガー）は両レーンとも課題体系へ / 事象（起きたこと・復旧・解決策）は記録ファイルへ（セット固有はセット log、横断・基盤は開発 log の「事象記録」節〔22-2 で新設〕）/ 確認待ち（ステップ付随の短命の観察項目）はそのレーンの plan の確認待ちリスト（5.2）へ。計画書の設計課題リスト・バックログ・トラブルシューティングログは 22-2 で廃止し、リンク 1 行に置換する。切り分けの詳細は課題体系 4.7
  • 移管の時期（Phase 25-2 で明文化）: ステップ完了時は plan の状態・完了日・要点・作業記録の更新を最優先で行う（記録ファイルへの詳細転記が済んでいなくても遅らせない）。計画整理のタイミングで、作業記録の本文を log へ移し、plan 側は log へのリンクに置き換える（移した本文を plan に残さない）。完了したフェーズは plan の「完了フェーズのサマリ」へ畳み、ステップ一覧の原文は log の移設ブロックに残す
  • 完了済みの配置: 移行済み計画書では、完了したステップを同じフェーズの中で進行中より上に置き、折りたたんだグループにまとめる（様式は 5 を参照）
  • 同じ情報を複数ドキュメントに書かない原則は従来どおり。詳細は 1 箇所に書き、他からは参照リンクを張る

5. ステップの記載様式（/goal 前提・両レーン共通）

Phase 19-4（2026-09-02）で導入。計画書のステップは人間ゲート間の 1 ゴールを単位とし、/step が読んでそのままゴール行に埋められるよう、開発計画・セット計画書とも次の 4 項目を書く。着手は /step <識別子> から行い（起動がレーン宣言と完了条件の宣言を兼ねる）、services/ shared/ への push 後は /goal で CodePipeline 完走を確認する（手順の正は CLAUDE.md、検討経緯はアイデア詳細）。

ステップの切り方の目安（2026-09-02 に開発計画「進め方の方針」で定め、25-2 で本書へ集約）: ステップ境界は人間ゲート（稼働確認・レビュー・go / no-go・設計判断）だけで決め、「Claude が 1 ターンでこなせる量」では区切らない（/goal が完了条件まで自走するため）。目安は 3 つ — (a) ゲートのない連続作業（実装 → テスト → 設計書 → コミット）は 1 ステップにまとめる / (b) 確認・判断で終わる地点は境界に残し、ユーザー作業のステップはゴールにしない / (c) 20〜30 ターンを超えそうなもの・2 レーンをまたぐものは機械検証できる中間点で割る。

項目書くこと書き方の目安
内容成果物と触るパス（レーン判定に使う）「何を作るか」を成果物で書く。前提ステップがあれば見出しに「（X 完了後）」
完了条件機械検証できる形で、証跡をコマンド出力で示せるものpytest の要約行 / validate・build --dry-run の出力 / 件数クエリの結果 / cdk synth の成否 / HTML のタグ対応・リンクの機械チェック 等。「適切に」「きれいに」のような判定不能な条件を書かない（/goal の evaluator は会話ログしか見ない）
人間ゲートゴール終了後にユーザーが行う確認稼働確認 / レビュー / go・no-go / 本番 DDL 適用 等。なければ「なし」と書く。ゲートがステップの途中に入るなら、そこでステップを割る
停止点・上限ゴールがどこで止まるかと stop after N turnsservices/ shared/ infra/ database/ を触るなら「コミットまで」（push は差分確認後）、docs / content/ のみなら「push まで」。N の既定は 20
  • ユーザー判断のステップ（目視評価・設計判断・go / no-go）は見出しに「ユーザー判断・ゴール対象外」と明記し、停止点は「—（ゴールにしない）」とする。/step はこれを見て断る
  • 旧形式のステップ（完了条件のないもの）は全面書き直しをせず、/step 起動時のフォールバック（.claude/skills/step/SKILL.md 手順 1）で「内容」から 4 項目を起こし、ユーザー確認のうえ計画書を書き換えてから着手する

5.0 移行済み計画書の記載様式（Phase 25 で導入）

適用対象は新様式へ移行済みの計画書だけ（2026-09-21 時点は開発計画のみ。セット計画書は未移行で、上の 4 項目をそのままの形で書く）。移行済み計画書では、1 ステップを常時表示の要点と折りたたみに分けて書く。

置き場所書くこと旧 4 項目との対応
常時表示（見出し部）ステップ ID・状態（未着手 / 作業中 / 完了 + 完了日）・着手条件・結果 / 現況（1〜2 行）旧「内容」冒頭の「（X 完了後）」と、完了行に書いていた完了日・要点
常時表示（本文 1〜3）何をするか（成果物の要約）・守る条件（触らない範囲。無ければ「なし」）・完了条件（箇条書き）・人が確認すること・止まる場所・上限「内容」= 概要 + 実装詳細に分割 / 「完了条件」/ 「人間ゲート」/ 「停止点・上限」
折りたたみ（既定は閉じる）実装の細部・背景（着手時に読む仕様・定数・設計判断の理由）と作業記録（作業中の追記。整理後は記録ファイルへのリンク 1 本でよい）を別々に置く旧「内容」の長い仕様と、完了行の長い要点
  • 完了条件を折りたたみの中に入れない（/step と /goal が常時表示だけで読めるようにする）。方針が変わったら作業記録だけでなく常時表示側も直す
  • 完了済みのステップは同じフェーズの中で進行中より上に置き、折りたたんだグループにまとめる（初期状態は閉じる）
  • ユーザー判断のステップは「ユーザー判断・ゴール対象外」を常時表示に出し、停止点は「—（ゴールにしない）」とする。完了条件が残っていない古い完了ステップは例外形式として記録リンクで代替してよい（推測で 4 項目を作らない）
  • 雛形: docs/plans/_templates/step.html（コピー範囲・属性の早見表つき）。構造の契約の正は変更ファイル・展開草案セクション 2
  • 検査: 移行済み計画書を更新したら python3 tools/docs_check.py --plan-only（構造 + 参照のみ・ブラウザー不要）を実行する。CSS・テンプレートを変えたとき、または新しい計画書を移行したときは python3 tools/docs_check.py --widths 360,390,768,1280 と折りたたみの実機確認も行う。検査が担保しないこと（重要な制約を文章として拾えているか・要約が正しいか・記録と最新状態が一致するか）は更新者が差分のステップを読み直す

5.1 起票チェックリスト（ステップを起こすすべての入口で使う）

ステップは「アイデアの採用（/idea の待機 → 採用の転記）」「壁打ちでのフェーズ起票」「セット改修の起票」のどこで起こしても、書く前に次を確認する。2026-09-02 の Phase 19 で「Claude の作業と初回稼働確認が 1 ステップに同居し、いつまでも閉じないステップ」が生じた再発防止。

  1. 完了条件に「自セッションの外で起きる出来事」が入っていないか（次の push・次の週次補充・翌週のデータ・稼働してからの効果 等）。入っていたら、その部分を確認待ち項目（5.2）へ分離し、ステップの完了条件は自セッション内で検証できるもの（テスト・dry-run・自己確認・機械チェック）だけにする
  2. 人間ゲートは push 直後に行えるものか。後日でないとできない確認は 1 と同じく確認待ちへ
  3. ユーザー作業（目視・go / no-go・設計判断）はステップとして残すがゴールにしない（見出しに「ユーザー判断・ゴール対象外」）
  4. 切り方: ゲートのない連続作業はまとめる。20〜30 ターンを超えそう・2 レーンにまたがるものは機械検証できる中間点で割る
  5. 課題表の照合（Phase 22-1 で追加）: 起票するステップが触るパス・セット名で課題体系の live 表を照合し、該当する据え置き課題があれば同梱する（展開済みにしてステップに含める）か、トリガーを更新して据え置きを続けるかを決めて表を更新する。判断の結果（「課題表: 該当なし」を含む）を起票文に 1 行残す。「〜の次回改修時」型のトリガーはここで引かれる

5.2 確認待ち項目（トリガー付き・ステップにしない）

初回試行・効果観察・「次の機会に確かめる」ものはステップではなく確認待ち項目として、トリガーが起きるレーンの計画書の「確認待ちリスト」に置く（開発レーンのトリガー〔services/ push 等〕は開発計画、セットの週次補充や投稿観察は各セット計画書）。フェーズや改修は作業ステップが全部終われば完了とし、確認待ちの結果でフェーズを開けたままにしない（NG なら新しいステップか課題として起こす）。

列書くこと
日付 / 対象起票日と、どのステップ・変更の確認か（リンク）
トリガーいつ確認するか。入口が機械的に照合できる形で（「次に services/ shared/ を push したとき」「logic-training-1 の次の週次補充」「投稿 2 週間後（= 絶対日付を併記）」）。書式の正は課題体系 4.4（パス型 / セット型 / 日付型 / 発生実績型 / 節目型の 5 型。課題表と共通）
確認内容・判定基準何を見て、何なら OK か（証跡はコマンド出力・画面の観察項目）
NG 時の扱い戻す / 直す / 課題として起票する（起票先は課題体系）、のどれか
結果確認したら日付 + 結果 + 記録へのリンク。OK なら行を記録へ移す

眠らせない仕組み: トリガー側の入口が起動時に確認待ちリストを読む — /step は触るパスと開発計画の確認待ちを照合し、該当行があればそのゴールの中で確認して結果を書く。補充スキルは起動時に当該セット計画書の確認待ちを読む（Phase 19-5 で各スキルに追記）。棚卸しはフェーズ完了・改修完了・月次 KPI 転記の節目で、リストのトリガー列を上から確認する（アイデア体系の条件待ち棚卸し・課題体系 4.8 の棚卸しと同じ節目・同じ作法。課題表の照合も同じ入口が行う〔22-4 で各スキルに追記〕）。確認待ちと課題の違いは課題体系セクション 3（確認は 1 回で閉じる / 課題は再判断を繰り返しうる）。
