要約

このページは、機能別の基本設計 logic-training-1 の生産の 1 段下で、問題ストック（quiz_stock_items）の作り方と、事前動画のビルドから配置までの詳細を書く。手順の細部（ゴールの切り方・コマンド・作問の勘所）は補充スキル quiz-stock-replenish が正で、ここには資材の置き場・工程ごとの入出力・守る規定・在庫の数え方を書く。

図 1 は、資材がどのファイル・ツールを通って S3 と DB に届くかを表す。ひし形は人の関所。

2. 問題ストックの作り方

この章は、図 1 の上半分（候補から投入まで）を詳しくしたもの。手順の順番と各工程のコマンドは SKILL.md のセクション 0〜6 が正で、ここには工程ごとの規定を書く。

2.1 著作権の規定

出回っている問題のアイデアと解き方の構造は題材にしてよいが、問題文の文面は写さない → 理由 D-02。

  • 書き直し: 問題文・答え・解説はすべて自分の言葉と、このセットの書式（世界観・文体・文字数の上限）で書く。登場人物・場面・数値は元から変え、解き方の構造だけを残す
  • 証跡: source_note に「元ネタの類型・参照元（URL 等）・表現は書き直した旨」を書く。別の台帳は持たない（音源のライセンスの証跡 3 点と同じ扱い）
  • 使わないもの: 特定の書籍・サイトに固有の独創的な問題（アイデア自体に強い独自性があり、出どころが特定できるもの）、実在の企業名を冠した出題（「○○社の入社試験」のように確かめられない断定）、問題集から数値・配役までそのまま流用したもの、解釈が割れて炎上しうる問題

2.2 リサーチ

  • Web で類型の候補を出し、流布を裏取りする。採ってよいのは作者不詳で、複数の独立したサイトに出回っている問題だけで、出回っている例の URL を 1 件以上直接確かめて research*.md と候補の source に残す
  • 成果物は「類型・解き方の構造の要約・出典 URL」まで。問題文を転載しない
  • 裏取りの手段（Claude Code は WebSearch か委譲した Codex、Codex 直接セッションは組み込みの検索）はエージェントで違う。どちらでも採否はスキルを回しているエージェントが決める

2.3 候補と選別

完成稿を書く前に、問題文・答え・必要な図の内容・出典メモだけの「候補」を、朝と夜それぞれ目標の 2 倍用意し、人が OK / NG / 保留だけを返す → 理由 D-09。

  • 集計: 不足 = 目標 − OK、追加 = 不足 × 2。朝と夜の両方で不足が 0 になるまで完成稿へ進まない。余った OK は候補のまま次のバッチへ持ち越す
  • 候補 OK は投入の承認ではない: 「仕上げてよい」の意味で、投入の承認は完成稿の 1 問ずつのレビュー（2.5）で行う。完成稿で NG になった問題は候補へ差し戻す（final_ng）
  • NG と保留は消さない: 理由は任意で、後日の振り返り（quiz-review-learn）で言葉にし、合意した共通ルールだけを補充スキルの作問基準へ足す
  • 状態（8 種）・必須項目・集計の検査は candidates/README.md と tally.py が正

2.4 完成稿の執筆

  • 文体・題材の条件は prompt_configs.prompt_text の執筆ガイド（セット別設計書 4 節）に従い、文字数の上限は方式のフィールド仕様（gpt-quiz-multicut 5 節）を守る。問題文の上限は全角 80 字（版面が受けられる長さ。3.4）
  • hook はキャプション冒頭のつかみとして問題ごとに書く。動画のカット 1 の吹き出しは固定文で、動画上部の「つかみ帯」はスロット別の slot_hook（prompt_configs.parameters）が受け持つ（16-4c から）
  • 昼（L3 / フェルミ推定）は捻った分解型・解説は 5 ステップ・explanation は 240 字上限で書く（gpt-quiz-multicut 5 節）。昼は停止中で補充しない（セット別設計書）
  • 機械検証は validate.py（文字数・tags 数・出典・実行時と同じ検証。image-batch の uv 環境で動かす）・verify_logic.py（算数・全列挙で答えを確かめる）・generate.py（レビュー用の review.md と投入 SQL）の 3 つ。なぞなぞ・とんちの想定解は機械で確かめられない

2.5 完成稿のレビュー

投入の前に、ユーザーが 1 問ずつレビューする。観点は次の 4 つ。

  1. 誤答チェック（答え・解説が正しいか）。実行時に答えを検証する仕組みはなく、ここが誤答を防ぐ唯一の関所
  2. 表現の独自性（書き直しが十分か。2.1 の規定）
  3. 既存のストック・出題履歴との重複（同じ解き方の構造の問題が近くに並ばないか）
  4. 書式への適合（文字数・L3 の幅の表現「約〇〇（目安）」・トーン）

2.6 投入

  • レビュー済みの問題を、generate.py が出す insert_quiz_stock.sql でローカル MySQL と Aurora の両方へ入れる（運用設計 2.1 手順 2 の (6) の INSERT の形）。quiz_type / difficulty は parameters.slots の値と一致させ、source_note は必須
  • content_key（{slot_code}-{3 桁連番}。V007）は、SQL がスロット内の既存の最大連番 + 1 を適用時に解決し、両環境に同じ値で入る。手で採番しない。content_key は NOT NULL なので、採番が漏れると投入時に必ずエラーになる
さらに詳しく
  • 工程ごとのコマンド・作問の勘所・スロット別の書き方 → quiz-stock-replenish の SKILL.md
  • 候補ファイルの形式・状態・集計 → candidates/README.md
  • quiz_stock_items の列 → データモデル設計 4.10

3. 事前ビルドパイプライン

この章は、図 1 の下半分（投入した行を動画にして配置するまで）を詳しくしたもの。投入しただけの行（video_s3_key IS NULL）は出題されない。表 2 は 5 つの工程の入力・処理・出力を表す。

表 2 事前ビルドの 5 工程
工程ツールやること
1. 対象の抽出build.py --listvideo_s3_key IS NULL の有効なストック行を挙げる（初回の 16-3d は 42 問全部、以後は補充分）
2. イラストの生成export_prompts.py → imagegen → intake.py行の illustration_scene からプロンプトを作り、imagegen で生成し、3:2・1536x1024 に整える（3.1）
3. レンダリングと音build.pyRemotion で映像を描き、ffmpeg で BGM と効果音を載せる（3.2〜3.4）
4. 全数レビューreview_sheet.py動画・イラスト・スチル 5 枚の一覧を作り、ユーザーが全数を見る（3.5）
5. 配置publish.py承認した動画を S3 へ上げ、ローカル MySQL と Aurora に反映する（3.6）

3.1 イラスト

  • プロンプトは gpt-quiz-multicut のコード側の固定プロンプト（情景 + スロット別のムード + ブランドの配色 + 禁止事項 = gpt-quiz-multicut 6 節）を使い、画風の 1 行（フラットデザイン・ベクター調・写実の禁止・全枚の統一）を常に足す。組み立ては export_prompts.py だけが gpt_quiz_multicut の _build_illustration_prompt を使う → 理由 D-04
  • 生成は Codex の組み込みの画像生成（imagegen）で行い、OpenAI Images API は使わない
  • プロンプトの末尾にサイズの明示行（export_prompts.py の SIZE_LINE。3:2・1536x1024）を付ける → 理由 D-05。生成した側が保存ファイルのサイズを確かめ、違えば作り直す
  • intake.py は 3:2 の中央切り抜き → 1536x1024 へ縮小し、3:2 でなかった素材は WARNING と切り捨て率を出す。見切れた問題だけイラストを作り直す。3:2 で来た素材は何も捨てない

3.2 レンダリングと音

  • 実行の場所: build.py は WSL のホストで、対象の抽出・スロットの解決・props の生成（ローカル DB。依存は pymysql だけ）を行う。Remotion のコンポジション Quiz16s（Remotion 4 + React 19。版面・動き・タイムラインは remotion/src/、構成の一覧は remotion/README.md）は Docker（remotion/Dockerfile.render。WSL に Chrome の共有ライブラリがないため）で映像だけを描き、remotion/scripts/mix_audio.py が image-batch イメージの ffmpeg で BGM と効果音を載せる（pref-ranking-1 の build.py と同じ方式）
  • 変えない条件: 尺 16 秒・3 カット・効果音 8.0 / 13.0 秒・音量・CRF 20・書体 Noto Sans JP。Python 側の単一ソースは remotion/scripts/spec.py で、tests/test_timeline_sync.py が remotion/src/timeline.ts と突き合わせる（TypeScript 側で壊すと pytest が落ちる）。答えはキャプションで明かし、TTS は入れない
  • ループ: 周期のある動きは、すべて周期を 480 フレームの約数にする（timeline.ts の LOOP_PERIODS。外れるとモジュールの読み込み時に例外）。16 秒の末尾（frame 480 = 次の周回の 0f）の状態を先頭 0f に一致させ（479f の次に 0f が自然につながる）、継ぎ目は 15.8 秒で導入カットの状態へ切り替える（クロスフェードしない）。問題文はフレーム 0 から全文を出し、冒頭 0 秒にもコーチの跳ねを置く → 理由 D-06
  • BGM: スロット別の LRU で選曲し、last_used_at をビルド時に更新する（quiz-prebuilt 6 節）。--rebuild では既存の video_audio_asset_id を引き継ぎ、LRU を消費しない
  • services/image-batch の gpt_quiz_multicut.py へのレンダリングの import 依存はない。services/ 側の方式は休止方式として残してある
  • フォントは pref-ranking-1 の remotion/public/fonts/ から build.py が複製する

3.3 版面のセーフエリア

セーフエリアは高さで 2 つのゾーンに分ける。上部（時間帯のピル・つかみ帯・見出し・問題文）は左右対称の余白でカードの幅を使い切り、Instagram の UI のための右 12% は下部（イラスト・コーチ・吹き出し）にだけ空ける。本文の実効幅は 902px。

3.4 版面の導出（イラストを先に取る）

版面の定数は remotion/src/layout.ts、導出は remotion/src/design.ts が正。イラストの箱を先に確保してから、残りの高さに問題文を fitText で収める順に固定してある → 理由 D-07。

  • イラストの保証高 ILLUSTRATION_GUARANTEED_HEIGHT = 500px と間隔 48px を、イラストの下端（コーチの真上 = y 1293）から引いた残り 294px が問題文に使える高さ
  • 問題文は上限 68px・下限 44px・行間 1.4 で長さに応じて変わる（実測: 18 字 = 68px・2 行 / 50 字 = 54px・3 行 / 76 字 = 50px・4 行）。下限でも収まらなければ例外で落とす。これで受けられる問題文は全角 80 字まで（補充側の question の上限 80 字。I-035）
  • つかみ帯 52px 上限・見出し「問題」72px・見出しから問題文まで 115px
  • containRect は箱の上端寄せ（余りが出ても問題文の直下に置く。左右は中央）。イラストの実寸は 797×531px（最も長い問題でも 771×514px）
  • 導出値は tests/test_layout_design.py が最短・中央・最長の 3 問で固定する（検査用の入口 remotion/src/deriveDesignCli.ts を esbuild で束ねて node で動かす。コンポジションからは参照しない）

3.5 全数レビュー

  • review_sheet.py は、ビルドのたびに work/build_manifest.json を累積の台帳 work/review_archive.json に足し、インデックス work/review.html（全バッチの一覧）とバッチごとのシート work/review/<バッチ名>.html を書く。バッチは stock_items.py の問題文との一致で決める。シートは動画・イラスト・完成 MP4 から抜いたスチル 5 枚（先頭 0f・各カット・末尾 479f）を一覧にする。先頭と末尾を隣に並べ、ループの継ぎ目を全数で目で見る。--slot で対象スロットを絞り、--per-page（既定 14）でページを分ける（スマホで見るため）
  • 観点: ①イラストの品質（指定していない文字・数字・記号が混じっていないか / フラットイラストの画風か / 情景が問題と合っているか）②版面（文字の欠け・重なり・吹き出しとヒントの整合）③音（BGM・効果音のタイミングと音量）
  • NG はイラストの作り直し（imagegen の再試行）か、illustration_scene の書き直し（DB の更新）→ 再ビルドで直し、直るまで S3 へ置かない

3.6 配置

  • 承認した ID を work/approved.txt に書き、publish.py が動画を assets/{set_code}/prebuilt/{content_key}.mp4 へ上げる。イラストの原画 {content_key}_illustration.png も再ビルド用に一緒に置く（DB には記録しない）
  • quiz_stock_items の video_s3_key / video_audio_asset_id / video_built_at（V006）の 3 列を同時に更新する。publish.py はローカル MySQL を更新し、Aurora 用の work/update_prebuilt.sql を残す。運用者がこれを Data API で Aurora に適用し、更新行数が承認件数と一致することを確かめる
  • Aurora の SQL も S3 のファイル名も環境ごとの id を使わず、set_code + question_text（BGM は s3_key）と content_key で解決する（データモデル設計 4.10）。work/ の中間生成物だけがローカルの id をファイル名に使う
  • 未ビルドの行が残っても投稿は止まらない（出題の候補から外れ、ビルド済みの在庫で回る）。実行時の WARNING と在庫確認（5 章）で見つかるので、投入したらビルドまで続けて終える
さらに詳しく
  • 実行コマンド・環境変数・Docker イメージ → content/video-build/logic-training-1/README.md
  • 出題時の動画の選び方・取得 → 方式設計書 quiz-prebuilt 4・5 節
  • スロット・パレット・音源などセットの設定 → セット別設計書 logic-training-1

4. 再ビルドが必要になる変更

事前動画にはスロット別のパレット・slot_label・slot_hook・BGM・効果音・版面が焼き込まれている。表 3 の変更は、該当する事前動画をすべて作り直して差し替える必要がある。

表 3 再ビルドが要る変更
変更範囲
版面・カット構成・尺全量。実例は 16-4c（3 カット化・つかみ帯・ズーム廃止。全 63 本）・改修 R-1（Remotion へ載せ替え。2026-09-03。朝・夜 56 本）・改修 R-2（イラスト優先の配分。2026-09-19。朝・夜 70 本）。R-1・R-2 では停止中の昼 21 本を --slot で外し、旧版のまま残した（再開を決めたときにまとめて作り直す）
parameters.slots の型・難度とスロットの対応、パレット・slot_label / slot_hook該当スロット（動画は行の型・難度で決まるスロット向けに作るため、対応を変えると版面とスロットが食い違う）
BGM の差し替え（ミュート検知のときを含む）video_audio_asset_id で特定した動画。is_active=0 にするだけではビルド済みの動画に古い曲が残る（運用設計 4.4）

一括の作り直しは build.py --rebuild（--slot <slot_code> を複数指定して対象を絞れる）。ビルド済み（video_s3_key IS NOT NULL）の行を対象に、BGM を video_audio_asset_id から引き継ぐので選曲の LRU を消費せず、last_used_at（出題の順番）も変えない。そのため差し替えで同じ問題が再投稿されることはない。作り直した後も全数レビュー → S3 の上書き → 両環境の DB 反映は新規と同じ。R-1・R-2 は補充分だけ新しい版面にする段階的なビルドをせず、稼働中の在庫をまとめて作り直して全数をレビューしてから差し替えた。効果は差し替えの 2 週間後にセット計画書の確認待ちで判定する。

5. 在庫と補充

この章は、補充の要否の判断に使う数え方と、取り下げの扱いを書く。補充の目安の値と直近の在庫はセット計画書が持つ。

  • 出題の順番: 型・難度で絞った LRU の順繰り。未使用を使い切ると最も古く使った問題を自動で再利用するので、在庫切れで投稿は止まらない。再利用すると WARNING がログに出る（補充が遅れているしるし）
  • 初期在庫（16-2 で投入）: 42 問 = 2 週間分（当時の消費は週 21 問。L1/light 14・L3/standard 14・L1/deep 14）
  • 補充: 週 1 回、各「型 × 難度」の未使用かつビルド済みが 7 問（1 週間分）以上を目安に回す。再利用の WARNING が出たら優先して補充する。停止中の昼（L3 / standard）は補充せず、既存の在庫を凍結扱いにする（下のクエリの L3 / standard 行は判断に使わない）
  • 在庫確認のクエリ（週次の補充の判断・投入の確認・ビルド漏れの検出に使う。unbuilt が 0 以外ならビルド漏れなので、補充より先にビルドする）: 
    SELECT quiz_type, difficulty,
       SUM(last_used_at IS NULL AND video_s3_key IS NOT NULL) AS unused_built, -- 出題可能な未使用在庫
       SUM(video_s3_key IS NULL)     AS unbuilt,  -- 動画未ビルト（出題対象外。0 が正常）
       SUM(last_used_at IS NOT NULL) AS used,     -- 使用済み（再利用候補）
       SUM(use_count)                AS total_uses
FROM quiz_stock_items
WHERE set_id = :set_id AND is_active = 1
GROUP BY quiz_type, difficulty;
  • 取り下げ: 誤答や表現の問題が見つかった問題は is_active=0 にする（行は消さない。証跡と使用履歴を残す）。ある「型 × 難度」の有効在庫が 0 件になると、そのスロットの実行が異常終了するので、0 件になるなら先に代わりを入れる。S3 の事前動画は消さない → 理由 D-10
  • 在庫専用のアラームは持たない。再利用の WARNING と週次の在庫確認で回す → 理由 D-11
さらに詳しく
  • 補充の目安・直近の在庫・確認待ち → セット計画書 logic-training-1
  • 昼の停止の範囲 → セット別設計書

D-01 出題は人がレビューした問題ストックからだけ行う

決めたこと
クイズの出題は quiz_stock_items から取るだけにし、実行時の LLM による問題の生成は休止する。ストックは音源と同じ「調達 → 書き直し → 投入 → 順繰り」の型で回す
理由
スキップ率 95% を受けたテコ入れの一つ。誤答のリスクを投入時の人のレビューで担保し、実行時の LLM の生成・検証チェーンを休止する
日付・出典
2026-08-01（Phase 16-1・ユーザー決定）。gpt-quiz-multicut 冒頭・セット別設計書

D-02 定番の問題は「アイデアを借りて表現を書き直す」

決めたこと
アイデア・解き方の構造は題材にしてよく、問題文の文面は転載しない（2.1 の規定）
理由
著作権が守るのはアイデアではなく表現で、問題文の文面は創作的な表現として守られうるため。既存の問題の文面を転載する案はこの理由で採らなかった
退けた案
既存問題の文面の転載
日付・出典

D-04 イラストは imagegen + 画風の 1 行で作る

決めたこと
事前ビルドのイラストは Codex の imagegen で作り、画風の 1 行をプロンプトに常に入れる。OpenAI Images API は使わない

16-3 (8) の比較（gpt-image-1 の実 API / imagegen / imagegen + 画風行）で、imagegen + 画風行が禁止事項を全部守り、画風もそろって品質が最もよかった。イラストの API 費もゼロになる。imagegen は自動のバッチに組み込めないが、事前ビルドは人のレビューを挟むローカルの運用なので成り立つ
退けた案
gpt-image-1 の実 API
日付・出典

D-05 プロンプトで 3:2（1536x1024）を明示する

決めたこと
プロンプトの末尾にサイズの明示行を常に入れ、守られなかったときに備えてスキル側のサイズ確認と intake.py の WARNING の二重で見つける
理由
16-3c では「imagegen は 3:2 を直接指定できない」と記録していたが、16-4b の見切れ調査で誤りと分かった。初期 42 問の出力の比率は同じセッションの中でも 1672x941 / 1693x929 / 1774x887 …とばらつき、3 問はちょうど 1536x1024 だった。指定しないと 16:9 前後に揺れるだけだった。組版側の枠埋めの廃止（gpt-quiz-multicut 8.2）と合わせ、3:2 で来た素材は何も捨てずに動画に載る
退けた案
プロンプトでセーフエリア（主要素を中央 3:2 に収める）を指示する（情景の構図に影響するため見送り。必要になれば検討する）
日付・出典
2026-08-09（16-4b・ユーザー決定）

D-06 レンダラーを Pillow の組版から Remotion へ載せ替える

決めたこと
どのフレームも動いている動画にするため、レンダラーを pref-ranking-1 で使っている Remotion へ替え、ループの継ぎ目を作り込む。尺・カット・効果音のタイミング・ミックス・答えの開示・イラストの再利用・書体は変えない。build.py はコンテナの中からホストでの実行に変え、Remotion と ffmpeg だけを Docker に任せる
理由
16-5 の評価で 3 カット化の後もスキップ率 50.6%・平均視聴 12.4 秒だった。R-1-1 で平均再生時間が尺の 16 秒を超える動画が多く、ループして見られるのが普通だと分かった一方、旧レンダラー（Pillow の 7 枚の版面 + ffmpeg の連結）は 7 枚中 5 枚が完全に止まっていて、ループの頭 0〜7 秒が止まって見えた。変えない条件を守るのは前後で比べられるようにするため。問題文の行ごとの段階表示は、2 周目以降に「読み始めた文がまだ出ていない」状態を作るので R-1-3 でやめた。継ぎ目のクロスフェードは二重露光に見え、不具合と区別がつかないので採らなかった
退けた案
補充分だけを新しい版面にする段階的なビルド（新旧が混ざる）・継ぎ目のクロスフェード
日付・出典
改修 R-1（2026-09-02〜03・セットレーン）。アイデア記録・セット記録。当時、方式カタログと gpt-quiz-multicut 冒頭の転用の注記の書き換えは開発レーンへ起票した

D-07 版面の配分を「イラスト優先」にし、問題文の大きさが変わるのを受け入れる

決めたこと
イラストの箱（保証高 500px）を先に取り、残りに問題文を収める。原資は文字の縮小（つかみ帯 64 → 52px・見出し 92 → 72px・見出しから問題文 150 → 115px・行送り 1.5 → 1.4）で作る。問題文の下限を 32 → 44px に上げ、補充側の question の上限を 90 → 80 字に下げた
理由
R-1 の版面は問題文の最大高 430px（QUESTION_MAX_HEIGHT）を先に取ってから残りをイラストに回したので、4 行の問題（当時 56 問中 37 問）ではイラストが 504×336px と幅の約 6 割まで痩せた。3 カット中 2 カットの主役がイラストなのに、問題の長さで主役が小さくなっていた
退けた案
見出し「問題」をなくす案（静止画 PoC で比べて採らなかった）
日付・出典
改修 R-2（2026-09-19・セットレーン）。採用値はセット計画書の改修 R-2・I-035

D-08 両環境の反映を content_key などの安定したキーで行う

決めたこと
S3 のファイル名は content_key、Aurora の SQL は set_code + question_text（BGM は s3_key）で解決し、環境ごとの id を使わない
理由
quiz_stock_items.id は環境ごとの AUTO_INCREMENT で、ローカルと Aurora で一致しない
日付・出典

D-09 作問を候補と完成稿の 2 段階にする

決めたこと
問題文・答え・図だけの候補を目標の 2 倍出して人が反射的に選び、OK だけを完成稿に仕上げる。NG・保留は消さずに後日振り返る
理由
14 問を全項目まで作ってからレビューすると、補充のたびに人が「何が微妙で、どう直せばよいか」を考えて言葉にする負担が大きかった。選別は OK / NG / 保留だけにし、理由を考える作業を後日に分けて負担を減らす（レビューの工程の数を減らすのが目的ではない）。理由のない NG からジャンル全体の禁止を作らないよう、理由は人が言葉にしたものだけを残す
日付・出典
2026-09-21 方針確定（ユーザー提案）・改修 R-3（2026-09-22）。アイデア詳細

D-10 取り下げは is_active=0 にし、S3 の動画を消さない

決めたこと
取り下げた問題の行も事前動画も消さない
理由
行を残すと証跡と使用履歴が残る（音源と同じ）。is_active=0 で出題の候補から外れるので動画を消す必要はなく、戻すときに作り直さずに済む
日付・出典
Phase 16-1・16-3b

在庫が切れても再利用で投稿は止まらない。失敗の通知を起点にする運用方針（運用設計 4 章）と合わせる
