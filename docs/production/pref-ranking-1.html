2. ランキングストックの作り方

この章は、図 1 の上半分（一次情報から投入まで）を詳しくしたもの。工程の順番とコマンドは SKILL.md のセクション 0〜6、フィールドごとの書き方は WRITING-NOTES.md が正。

2.1 ネタ選定とリサーチ

  • ネタの基準は「下位の県の人が笑って自虐できるか」（事業戦略書 6 節。下位を晒さない TOP5 の版面が前提）
  • 都道府県別の統計・調査を一次情報（官公庁の統計・業界団体の調査など）から集める。成果物は出典 URL・データ年・TOP5 の生の値まで。Codex に任せるときは検索を使う codex --search exec で行い、採否と数値は 2.2 の機械読み取りで取り直す
  • 主な供給源は、家計調査の品目別ランキング（rank01〜14。common/convert.py で TOP6 の同値をすぐ判定できる）と社会生活基本調査の公表ランキングの系列。17-1 のネタ帳（plans/ranking-set-research/neta-30.md。git 管理外）は 17-7 で使い切った

2.2 データの検証と県への換算

  • 一次データとの突き合わせ・順位と値の再計算・市区町村の統計の県への換算を機械検証のスクリプトで行い、ranking_data（数値と都道府県コードだけ）を作る。出典と換算の計算過程は source_note に書く
  • 投入ツールは data/*.json を読む。value_prefix / value_suffix は JSON の meta から転記する

家計調査（県庁所在市・政令指定都市の 52 市）の品目別の値は、common/convert.py が次の規則で 47 都道府県の値にする（Phase 17 の決定。セット別設計書 1 節）。

  1. 公表の対象は 52 市 = 47 の県庁所在市（東京は「東京都区部」）+ 県庁所在市でない政令市 5（川崎・相模原・浜松・堺・北九州）
  2. 同じ県に複数の市がある 4 県は世帯数による加重平均で合わせる（神奈川県 = 横浜 + 川崎 + 相模原 / 静岡県 = 静岡 + 浜松 / 大阪府 = 大阪 + 堺 / 福岡県 = 福岡 + 北九州）→ 理由 D-02
  3. 残りの 43 県は県庁所在市の値をそのまま県の値にする
  4. 合わせた後も母集団は県庁所在市・政令市の世帯だけなので、動画の出典行とキャプションに「※家計調査（県庁所在市・政令市の世帯数加重平均）」の類の注記を必ず入れる（content_fields.source_display）
  • 世帯数のウェイトは二人以上の一般世帯数（一般世帯数の総数 − 世帯人員 1 人の一般世帯数）。出典は令和 2 年国勢調査の人口等基本集計 第 6-3 表で、52 市すべてを持つ（出典の詳細と取得日は common/README.md）
  • 国勢調査は 5 年ごと。令和 7 年の人口等基本集計が公表されたら households.csv を差し替え、data_year / source_name / source_url も替える。差し替えても既存のストックの ranking_data は計算し直さない（投入時点の出典・データ年を source_note が持つ。計算し直すなら動画の再ビルドを伴う）
  • convert.py は家計調査専用。人口動態統計・社会生活基本調査など都道府県単位で公表される統計は換算せず、ネタの資材の側で直接 ranking_data を作る

2.3 ネタの採否のルール

  • TOP6 に同値があるネタは採らない。5 位と 6 位が同値のときも採らない（例: 睡眠時間 = 4 位が同率 2 県 / カレールウ = 5 位と 6 位が同額）。validate.py とビルド前の検査（3.2）も 1〜5 位の一意性を確かめる → 理由 D-03
  • 時刻・時分の指標は今のデータモデルに載らない。表示は value + value_suffix の組み立てなので、平均就寝時刻（23:39）のような表記は表せない（課題 I-023）
  • TOP5 全体が団子のネタ（例: バナナ = 1〜5 位が 35 円幅）は、同値でなくても採らない（「1 位を当てる」演出の前提が崩れる。17-7・WRITING-NOTES.md）
  • データ年の古い統計を使うときはデータ年を明記する。僅差は同値でなければ採ってよく、research.md に順位の確定性の注記を残す。不採用とその理由も記録する

2.4 文言とナレーションの執筆

  • title / content_fields（hook / trivia / source_display / value_suffix / subtitle / bg_motif）/ narration を書く。narration は 30 秒版の cue 台本だけを書く（5.1 の cue 体系。既存の行の 20 秒版の台本は残してよい）
  • result_list は手で書かず、ツールが ranking_data + value_suffix から整形して入れる（データモデル設計 4.13）
  • ナレーションは cue ごとの時間の予算（5.2）を意識して短く書く。長さは文字数ではなくモーラ数で見積もる（12899円 は 6 文字だが読みは 19 モーラ相当）。金額・件数などの数値は読み上げず、版面の表示に任せる。validate.py がモーラの推定で予算を検査する
  • 吹き出しで熟語の途中で改行しないかを目で見る（禁則処理で直らない語中の改行は文言で直す。4.2）

2.5 素材のレビュー

投入の前に、ユーザーが review.html で全件をレビューする（Claude が先に一次スクリーニングする）。観点は次の 4 つ。

  1. データの正しさ（出典が実在するか・データ年・県換算の再計算・TOP5 の順位）。誤ったデータを防ぐ唯一の関所
  2. 表現（下位を晒していないか・煽りすぎていないか・出典表記とキャプションの注記が妥当か）
  3. 既存のストックとの重複（同じテーマ・同じ出典が近くに並ばないか）
  4. 書式への適合（文字数・cue 台本の長さ・bg_motif が妥当か）

2.6 投入

  • レビュー済みのネタを両環境へ入れる。content_key（{3 桁連番}-{slug}。例: 001-gyoza-spend）は、SQL が既存の最大連番 + 1 を適用時に解決し、両環境に同じ値で入る。content_key は NOT NULL なので、採番が漏れると投入時に必ずエラーになる
  • 投入後に両環境の中身の一致（全行の MD5・CHAR_LENGTH）を確かめる（コマンドは WRITING-NOTES.md セクション 6）
さらに詳しく
  • 工程ごとのコマンドと落とし穴 → ranking-stock-replenish の SKILL.md
  • フィールドの出る場所・文体・モーラ推定の癖・投入のコマンド → WRITING-NOTES.md
  • ranking_stock_items の列 → データモデル設計 4.13

3.2 ツールの構成と実行の境界

5 つの工程は content/video-build/pref-ranking-1/ 直下のスクリプトで、logic-training-1 と同じ構成・同じ名前にしてある。remotion/ 側のスクリプト（build_narration.py / normalize_loudness.py / build_timeline.py）は呼ばれる側で、ツールは薄い取りまとめに徹する。

  • 実行の境界: ツール本体は WSL ホストの Python で動かし、Docker が要る処理だけを外に出す（レンダリング = remotion-render イメージ、ラウドネスの正規化と背景の画像処理 = image-batch イメージ、TTS = VOICEVOX Engine の HTTP）。ホストに要る依存は pymysql / boto3 だけで、PIL を使う intake.py だけはコンテナの中で動かす
  • ナレーションの合成は build_narration.build_narration() をライブラリとして直接呼ぶ。予算検査の失敗を戻り値で受け、レンダリングへ進ませない
  • props はツールが組み立てる（build_props()。ストックの行 → PrefRankingProps）。組み立ての前に、1〜5 位の一意性・pref_code の範囲・必須の content_fields・当該尺の cue ID の集合がタイムラインの定数と過不足なく一致すること・背景の JPEG があることを確かめる。1 件の不備で止めず、全件を処理してから失敗の一覧を出して終了コード 1 にする
  • BGM は行に記録があれば必ず引き継ぐ: LRU で選ぶのは video_audio_asset_id が NULL の行だけで、記録がある行は --rebuild でなくても引き継ぎ、last_used_at も更新しない → 理由 D-04
  • 背景は 2 つの形で持つ: S3 に上げる原本 {content_key}_bg.png（1080x1920）と、レンダリング用の JPEG（remotion/public/bg/）。2MB 級の PNG のままだとフォントの読み込みが delayRender でタイムアウトする（17-3 の知見）
  • 検証用の --no-bgm: BGM なしでツールを通しで確かめられる。この動画は audio_asset_id が null で記録され、publish.py が拒否する（本番へ出ない）

3.3 言語をまたいで再利用するための要件

ネタ・素材・コンポジションを英語のセットで使い回せるよう、次の 4 点を守る → 理由 D-06。

  1. 背景に文字を焼き込まない（imagegen のプロンプトで「文字・数字・記号を描かない」を必ず指定する）
  2. Remotion の画面の文言はすべて props から渡す（コンポーネント内に直書きしない。文言の正はストックの行の content_fields / narration）
  3. TTS はアダプタ層で分ける（5.3。VOICEVOX 固有の呼び出しはアダプタの中だけ）
  4. ネタの元データと県換算のテーブルは言語を含まない形で持つ（ranking_data は数値と都道府県コードだけ）

ツールの共通部分の切り出しは英語のセットを足すときに行い、今は pref-ranking-1 専用の構成のまま。

3.4 全数レビュー

  • review_sheet.py は、ビルドのたびに work/build_manifest.json を累積の台帳 work/review_archive.json に足し、インデックス work/review.html（全バッチの一覧）とバッチごとのシート work/review/<バッチ名>.html を書く。バッチは content_key の番号と stock_items.py の no の一致で決める
  • 観点: ①背景の品質（文字・数字・記号が混じっていないか / 和モダンの画風か / 版面の読みやすさを邪魔しないか）②版面（県名・数値が正しく出るか / 金が沈んだりにじんだりしていないか / 文字の欠け・見切れ / 地図の点灯と順位の行が合っているか）③音（ナレーションが合っているか〔県名が停止のフラッシュに合うか〕・語尾が切れていないか・BGM とのバランス）
  • NG は背景の作り直し・bg_motif / セリフ / 文言の修正（DB の更新）→ 再ビルドで直し、直るまで S3 へ置かない
  • 承認はネタ単位（20 秒版もビルドしたときは 2 尺まとめて）。承認した content_key を work/approved.txt に 1 行ずつ書く → 理由 D-05

3.5 配置

  • publish.py は S3・DB に触れる前に、承認の対象を全件検査する（manifest があるか・MP4 と背景の PNG があるか・audio_asset_id が記録されているか）。1 件でも欠ければ中断し、一部だけの配置を作らない
  • ローカル MySQL はビルドした尺の列だけを 1 トランザクションで更新し、Aurora へは既定で Data API（common/apply_aurora.py）で自動適用する → 理由 D-05。SQL を作るだけにしたいときは --no-aurora（生成した SQL は常に work/update_prebuilt.sql に残る）
  • S3 のキー・ローカルの UPDATE・Aurora の SQL のどれも環境ごとの id を使わず、content_key で解決する。Aurora 側の video_audio_asset_id は audio_assets.s3_key からのサブクエリで解決し、WHERE に同じ音源の EXISTS を置く（Aurora に該当の音源がないとき、NULL で黙って上書きせず更新行数 0 で気づける。video_audio_asset_id が NULL だと実行時に異常終了する）
  • publish.py は承認ファイルに載っている全部の content_key を対象にする。既定の累積の approved.txt のままだと、配置済みのネタも上げ直して video_built_at を書き換えるので、補充のたびにそのバッチ分だけを並べたファイルを作って --approved-file で渡す（累積の approved.txt は承認の台帳として残す。17-7 で判明）
  • 未ビルドの行が残っても投稿は止まらない（その尺の候補から外れるだけ）。実行時の WARNING と在庫確認（7 章）で見つかるので、投入したらビルドまで続けて終える
さらに詳しく
  • 事前準備（イメージ・フォント・五郎の素材・VOICEVOX の起動）と工程ごとのコマンド → content/video-build/pref-ranking-1/README.md
  • 投稿時の動画の選び方・取得 → 方式設計書 ranking-prebuilt 4・5 節
  • 話者・デザイントークン・キャラの配置値などセットの設定 → セット別設計書 pref-ranking-1

4. 動画の作り（TOP5 地図ルーレット型）

この章は、3.1 の工程 3 で描く動画の中身を書く。版面は 1080x1920 / 30fps で、上からタイトル帯・日本地図（ルーレットの主役）・順位の行の積み上げ・キャラの常駐枠と吹き出し・出典行の帯。配色はパレットのトークン（Palette 型）で動かし、値はセット別設計書 8 節のデザイントークンが正。実装の正は content/video-build/pref-ranking-1/remotion/（layout.ts = 寸法 / theme.ts = トークン / scripts/build_timeline.py = タイムラインの定数〔src/timeline.json は生成物〕 / PrefRankingVideo.tsx = 版面）。

各順位の発表は「地図の上で候補の県が速く光る（スピン）→ 停止のフラッシュで確定 → 確定した県が順位の色に塗られ、順位の行に県名と数値が足される」の繰り返し。確定した県は塗りが残るので、進むほど地図が塗り上がる。表 3 はシーンの配分を表す（17-4d の値。正は build_timeline.py の DURATION_SPECS）。

2 尺を作ったのは「20 秒 = 完走率・リプレイに強い / 30 秒 = 保存・コメントに強い」の仮説を確かめるためだったが、検証せずに 30 秒で確定した（セット別設計書 3 節）。

4.1 版面の構成

  • タイトル帯は 2 段: 上段に金でセット固定のラベル（「都道府県ランキング TOP5」= labels.setLabel）、下段にネタのタイトル 56px・1 行。縁は下辺だけ 2px・不透明度 50%
  • タイトル帯・地図・全国平均のプレートは登場アニメなしで 0 秒から出す → 理由 D-07
  • 順位の行は下端に固定し、5 位から上へ 1 行ずつ足す。未発表の「？？？」枠は置かない。空いている序盤は content_fields.subtitle の全国平均のプレートが受ける（固定のラベル「全国平均」は付けず、subtitle を 1 行でそのまま出し、最初の数字の位置で分けて前半を小さく・後半の数値を大きく描く）
  • 順位の行は順位のバッジ + 県名 + 数値だけ（バーなし）。数値の前に content_fields.value_prefix（「年間」など）を置く。数値の小数の桁数は、その動画の 5 件の実値から 1 本の中でそろえる（全部整数の円額ネタは 0 桁）
  • 1 位の強調: 1 位の行は行高 104px（2〜5 位は 82px）+ 明るい金のグラデーション + 強いグロー。1 位の県名は発表時に 148px + 二重のグローのバーストで出し、余韻の後で順位の行へ落とす
  • 確定した県は「地図 → 順位の行へ県名が飛ぶ」動きで結ぶ。地図の上に順位のラベル（ピン）は置かず、確定した県は塗り + 縁 1.8px + drop-shadow で強める。2〜5 位のラベルは県の重心の真上から飛ばし、1 位だけ地図の中央下に大きく置く
  • 地図は viewBox の全域（0 0 1000 1000）で描く（陸地の外接矩形は x 3.9〜996.7 / y 0.0〜1000.0 で、切り詰めると九州南部と南西諸島のインセットが欠ける）。地図の箱は 890×866 で、拡大率は 1.04 倍が上限（行が増えるほど縮める。これ以上拡大すると九州南部が順位の行のゾーンへ押し出される）
  • キャラ: 煽り・実況はキャラの吹き出しに出す（ナレーションの cue と同じテキスト = 音と字幕の二重化）。ポーズは 3 種（基本 → タメ〔1 位のスピン中〕→ 軍配〔1 位の発表後〕）。アセット・配置の値はセット別設計書 7 節
  • 吹き出しの表示: スピン中は labels.searching（「第{rank}位は…？」）を点滅で出す。5〜2 位の cue は県名を含むので、吹き出しに出すのは停止のフラッシュから後だけ（スピン中に出すと結果が先に分かる）。冒頭だけは音と字幕を合わせず、ナレーションが intro（タイトルの読み上げ）を話す 0〜2.5 秒の間、吹き出しには teaser の問いかけを出す → 理由 D-07。吹き出しは文字数で 48 → 44 → 40px に下げ、line-break: strict を指定する
  • 出典行は生成り 86% の角丸の帯で常に出し、必ず 1 行に収める（文字数から字送りを自動で決める。下限 20px。source_display は全角 36 文字以内が推奨）。家計調査のネタは換算の注記を帯に含める（文言の正は content_fields.source_display）
  • 下位を晒さない: TOP5 だけを扱い、下位（ワースト）の表示を版面に持たない（事業戦略書 6 節のネタの判定基準に合わせた構造上の歯止め）
  • 結果総覧と締めは版面の上でひと続きの区間（recapAt === closingAt）で、シーンの境で版面を切り替えない。1 位の行だけ緩やかに明滅させる
  • props の duration（尺）は必須で、Composition は calculateMetadata で props.duration から durationInFrames を出す。cue には合成音声の実測の長さ frames を持たせ、音声の Sequence の長さに使う

4.2 明るい背景での読みやすさの規定

生成り系の明るいパレットでは金（アクセント）が沈むので、次の規定を守る → 理由 D-09。トークンの実値はセット別設計書 8 節。

  • 生成りの地の上に金を単独で使わない。文字の金は淡墨茶（sumiDeep）の 8 方向の縁取り（outlineShadow）+ グローを必ず付ける
  • 面の金（1 位の行の帯）は深金 → 金 → 明金のグラデーション + 内側の輪郭で作る（単色の金の面は使わない）
  • 背景の上の減光は 3 層（全面のベース + 上帯 + 下帯）。中央の減光は 30% で、和紙のノイズとヴィネットを重ねる
  • 禁則処理で直らない行またぎ（「マイホームの地図は、日 / 本海側にずらりだ！」のような語中の改行）は文言の側で直す（content_fields.trivia の書き直し → 再ビルド。WRITING-NOTES.md にも記載）

4.3 冒頭 5 秒の動き

冒頭（30 秒版の 0.00〜5.00 秒 = intro 89f + teaser 61f）に、既存の区間へ動きを足してある。タイムラインの定数 DURATION_SPECS は変えていない → 理由 D-10。パラメータの正は src/PrefRankingVideo.tsx（PREHEAT_TICK / PREHEAT_LIT_INTENSITY / TEASER_POP_FROM / TEASER_NUDGE_AT / TEASER_NUDGE_DUR）。

  • 予熱のスピン: 本番のスピンの前（frame < rounds[5].start）も、フレーム 0 から県を点滅させる。速さは本番のスピンの最高速と同じ（spinTicks の初期間隔 = 2 フレーム固定・減速なし）。予熱の区間は spinningRank を null のままにする（吹き出しの点滅は本番のスピン中だけ）
  • 速さと眩しさを分ける: JapanMap の litIntensity（既定 1）で塗りの不透明度と drop-shadow のにじみだけを比例させ、縁取りは残す。予熱 0.42 → 本番のスピン 1.0 → 停止のフラッシュ最大の 2 段で 5.00 秒の変わり目を作る
  • 煽りの吹き出しの動き: 尻尾の付け根（transformOrigin: 78px 100%）を基点に、拡大 0.62 → 1.0 のポップイン（spring・約 0.4 秒）+ 減衰する 2 度の揺れ（0.43〜1.1 秒）。動きは 0〜1 秒に集める。不透明度は変えないのでフレーム 0 から読める。変形はレイアウトの後に効くので、改行の位置・フォントサイズの段階・尻尾の相対位置は変わらない。teaser の区間の外は恒等変換

5. ナレーションと TTS の同期

この章は、3.1 の工程 3 のうち、ナレーションを合成して動画のタイミングに合わせる部分を書く。ナレーションは cue（セリフ）ごとに合成し、タイムラインの定数に固定したアンカーのフレームへ置く。

5.1 cue の体系

表 4 は narration JSON のキー（cue ID）と、置く位置を表す（データモデル設計 4.13）。

表 4 cue の体系

teaser煽り（「みんなはどこだと思う？」の類。視聴者に 1 位を予想させる）。全ネタ必須 → 理由 D-12両方煽りシーンの先頭

5.2 固定アンカーと予算検査

アンカーの表と解決の処理の正は remotion/scripts/build_timeline.py（cue_anchors() / resolve_cue_frames()）。cue ごとに揃え方（head = 頭合わせ / name = 後ろ合わせ）と予算の区間 [budget_start, budget_end) を持ち、TTS の実測値（frames と、後ろ合わせの cue は県名の発話の開始位置 name_offset_frames）を渡すと、配置のフレームと違反の一覧を返す純関数 → 理由 D-08。

  • head: start_frame = anchor。name（r5〜r2）: start_frame = anchor（停止のフラッシュ）- name_offset_frames
  • cue の間には MIN_GAP_FRAMES = 2（0.07 秒）の無音を必ず空ける
  • 後ろ合わせの cue は、直前の cue と重なるときだけ後ろへずらす。ずらせる上限は NAME_LAG_MAX_FRAMES = 8（0.27 秒。県名の発話が停止のフラッシュより遅れる量）で、ここまで詰めても重なれば head_overrun
  • 頭合わせの cue はアンカーに固定したまま（ずらさず head_overrun）。tail_overrun は「次の cue の開始 − 最小の間」（最後の cue は総尺）で判定する。ほかに missing（実測なし）・unknown（尺にない cue ID）・missing_name_offset
  • 例外は投げず全件を返し、ツールがまとめて出す。予算内の余りは無音で吸収する。超過の対処はセリフを短くすることだけ（既定の話速 speedScale は上限の 1.2。これより速いと聞き取りにくい）
  • 予算の区間は参考値として残してある（順位の cue は呼び込み 30f・県名 30f。20 秒版 intro 75f / teaser 60f / r1_call 75f / r1_name 60f / outro 90f、30 秒版 intro 105f / teaser 60f / 各 *_comment 45f / r1_call 90f / r1_name 75f / closing 150f）。頭の側の判定は区間ではなく直前の cue との重なりで行う → 理由 D-13

5.3 TTS のアダプタと県名の位置の実測

  • TTS はアダプタ層 remotion/scripts/tts.py に閉じてある。CueRequest（cue ID・テキスト・県名）→ CueAudio（WAV のパス・実測の秒・フレーム・name_offset_frames・話速・エンジンの識別子）が固定のインターフェースで、VOICEVOX の HTTP 呼び出しはこの中だけ。合成・検査・props の解決を通す CLI は remotion/scripts/build_narration.py（違反があれば props を書かずに終了コード 1）
  • name_offset_frames は cue の audio_query のモーラの長さを積み上げて出す。県名は単体の audio_query でモーラの列を得て、cue のモーラの列の右端から一致を探す（読点のポーズも要素として積むので、ポーズを挟んだ県名でも一致する）
  • cue 全体の長さは WAV の実測から取り、モーラの積み上げの予測との差が 0.08 秒を超えたら異常終了する（エンジンの更新で長さのモデルが変わったことを見つけるため）
  • 疑問形の語尾上げ（enable_interrogative_upspeak。既定で有効）は audio_query に出ず、合成時に末尾のモーラの母音が 1 つ足されるので、予測の側で補う（補わないと疑問形の cue が 0.15 秒ずれる）
  • 話者・既定の合成パラメータはセット別設計書 7 節

5.4 音のミックスとラウドネス

  • 相対のバランスだけをコンポジションで決め、配信のレベルはレンダリングの後にそろえる。remotion/src/audio.ts が BGM をナレーションの 18 LU 下に置き、remotion/scripts/normalize_loudness.py（ffmpeg loudnorm の 2 パス・映像は再エンコードしない）が I = -14 LUFS / TP = -1.5 dBTP を目標にそろえる（linear モードでピークの制約が効き、実測は -15.0 / -14.8 LUFS）
  • ダッキングはしない（ナレーションがほぼ全編を占め、常に効いて一定の減衰と変わらないため）
  • BGM は頭 0.5 秒のフェードイン / 尻 1.5 秒のフェードアウトで、曲が尺より短いときはループする。BGM の前処理（30 秒ちょうど・フェードは焼かない・I = -14 LUFS）は prepare_bgm.py

6. 再ビルドが必要になる変更

事前動画には版面・パレット・背景・ナレーション・BGM が焼き込まれている。次の変更は、該当する事前動画をすべて作り直して差し替える必要がある。

  • 版面・タイムライン・尺の構成（コンポジションの改修 → 全量）。実例は 17-5c（版面 2 件の修正で初期 14 本を同じ版で作り直し）と R-1（冒頭の動き。2026-08-29 に使用済みを含む在庫 30 件を同じ版で作り直した）。どちらもコンポジションの版が混ざらないよう全量を作り直した → 理由 D-14
  • パレット（デザイントークン）・キャラのアセット・地図の SVG（17-4 の地図の差し替えは初期ビルドの前で影響なし）
  • BGM の差し替え（ミュート検知のときを含む。対象は video_audio_asset_id で特定する）・VOICEVOX の話者やセリフ

一括の作り直しは build.py --rebuild。ビルド済みの行を対象に、BGM を video_audio_asset_id から引き継ぐので選曲の LRU を消費せず、last_used_at（投稿の順番）も変えない。作り直した後も全数レビュー → S3 の上書き → 両環境の DB 反映は新規と同じ。

7. 在庫と補充

この章は、補充の要否の判断に使う数え方と取り下げの扱いを書く。補充の目安と直近の在庫はセット計画書が持つ。共通する考え方（取り下げは is_active=0・在庫専用のアラームなし・再利用の WARNING は補充が遅れているしるし）は logic-training-1 の 5 章と同じ。

  • 投稿の順番: 当該尺がビルド済みの行だけの LRU の順繰り（ranking-prebuilt 4 節）
  • 稼働開始の条件（2026-08-24 のユーザー判断）: 14 ネタ（約 2 週間分）の 30 秒版がビルド・全数レビュー済みであること。消費は 1 日 1 投稿 × 7 日 = 週 7 ネタ。17-7 で残り 16 件を入れ、計 30 件がそろった
  • 補充: 週 1 回、7 ネタ（1 週間分）を目安に回し、未使用かつ 30 秒版ビルド済みを 14 件（2 週間分）以上に保つ
  • 在庫確認のクエリ（週次の補充の判断・投入の確認・ビルド漏れの検出に使う。尺は 30 秒で確定したので *_30s の列だけを見る。20 秒版はビルドしないので unbuilt_20s は在庫の全数と一致するのが正常で、*_20s の列は見ない）: 
    SELECT
       SUM(last_used_at IS NULL AND video_s3_key_20s IS NOT NULL) AS unused_built_20s, -- 20 秒スロットで投稿可能な未使用在庫
       SUM(last_used_at IS NULL AND video_s3_key_30s IS NOT NULL) AS unused_built_30s, -- 30 秒スロットで投稿可能な未使用在庫
       SUM(video_s3_key_20s IS NULL) AS unbuilt_20s,
       SUM(video_s3_key_30s IS NULL) AS unbuilt_30s,
       SUM(last_used_at IS NOT NULL) AS used,     -- 使用済み（再利用候補）
       SUM(use_count)                AS total_uses
FROM ranking_stock_items
WHERE set_id = :set_id AND is_active = 1;
  • 取り下げ: 誤ったデータや出典の問題が見つかったネタは is_active=0（行も S3 の動画も消さない）。有効在庫が 0 件になるとそのスロットの実行が異常終了するので、0 件になるなら先に代わりを入れる
さらに詳しく
  • 補充の目安・直近の在庫・確認待ち → セット計画書 pref-ranking-1

D-02 家計調査の市の値は世帯数の加重平均で県の値にする

決めたこと
同じ県の複数の市は、二人以上の一般世帯数で重みを付けて合わせる
理由
家計調査の支出額は「1 世帯あたりの平均」なので、単純な平均や合計は誤り。調査対象が二人以上の世帯なので、重みも二人以上の一般世帯数にする（総世帯数は施設等の世帯を含み、単独世帯を含む一般世帯数は大都市ほど大きく出る）。実際に効くのは 4 県の 9 市だけだが、透明性のため 52 市すべてを持つ
日付・出典
Phase 17 の決定（開発計画 Phase 17 冒頭②）・2026-08-10 にウェイトを取得

D-13 頭の側の判定を直前の cue との重なりにし、話速を上限に上げて間を作る

決めたこと
5.2 の判定基準（最小の間 2f・後ろ合わせのずれ上限 8f）にし、既定の話速を 1.1 → 1.2 に上げて、総尺を変えずにシーンの配分を組み直した（表 3 の値）
理由
実測すると 5〜2 位の cue の呼び込みは 29〜38f あり、17-4c の予算 30f を第 1 バッチの全件が超えた。一方、後ろ合わせに置いた実音声どうしの重なりは最悪 3f で、頭が 0.2 秒ほど前のシーンへ食い込んでも視聴上は問題ない（吹き出しは停止のフラッシュ以降のままで先に出ない）。第 1 バッチ 10 件 × 2 尺（cue 220 本）を話速 1.1 で合成して違反 0 件、県名の遅れは 80 本中 65 本が 0f・最大 6f。ユーザーの実物確認で「順位間の間がなさすぎでメリハリがない」となり、実測の最小の間が 2f しかなく発話の密度が 79% と高かったため、話速を上限まで上げ（ユーザー判断）、最悪のケースの最小の間が最大になる配分を選んだ。結果、最小の間は 15f（20 秒版）/ 13f（30 秒版）、典型は 0.5〜0.7 秒。補正後のモーラの予測と実測の差は中央値 0.01 秒・最大 0.06 秒
